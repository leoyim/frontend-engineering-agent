## 1.1 模块是什么：从脚本到模块

### 先看没有模块时会怎样

早期页面把 `<script>` 一个接一个贴上，所有声明都落在**同一个全局作用域**里：

| 问题 | 表现 |
|---|---|
| 命名冲突 | 两个脚本都定义 `init`，后者覆盖前者 |
| 依赖靠人工维护 | "A 必须在 B 之前加载"只写在文档或注释里，机器不知道 |
| 无封装 | 内部辅助函数也暴露在全局 |
| 顺序耦合 | 改了加载顺序就可能静默出错 |

当时的模拟手段是 **IIFE**（立即执行函数）：把代码包进函数，用闭包（D0 第 4 章 §4.3 的 `[[Environment]]`）做出私有作用域，只把需要的接口挂到一个命名空间对象上。**它解决了封装，但没解决"依赖声明"**——依赖关系依然只存在于人的记忆里。

### 规范意义上的"模块"是什么

ECMA-262 的《Modules》给出的定义性区别不在语法，而在**求值单元的性质**：

> 模块是一段**独立的源文本单元**：它有**自己的作用域**、用**声明式语法**表达导入导出，并被**单独求值一次**。

这四句话对应四条可验证的规则：

| 规则 | 与脚本的差别 |
|---|---|
| **自己的作用域** | 模块顶层的 `var` 不会变成全局属性；脚本会 |
| **声明式依赖** | `import` / `export` 是**语法**，不是函数调用 |
| **只求值一次** | 同一模块被多处引用也只求值一次（结果被缓存） |
| **自动严格模式** | 模块代码始终以严格模式执行；脚本需要显式 `"use strict"` |

（后两条在 D0 第 3 章 §3.8 已经出现，本章会给出机制层面的解释。）

### 在 HTML 里：`type="module"` 改变了什么

HTML Standard 的《Module scripts》规定，`<script type="module">` 与经典脚本有四处**语义差异**：

| 差异 | 机制 | 对加载的影响 |
|---|---|---|
| **默认延迟执行** | 模块脚本自带 `defer` 语义：在文档解析完成后、`DOMContentLoaded` 之前执行 | **不阻塞解析**——这是它与无属性 `<script>` 的关键区别 |
| **按 CORS 获取** | 模块脚本一律以跨源规则获取 | 跨域脚本必须返回正确的 CORS 头 |
| **不共享全局** | 每个模块有自己的作用域 | 不能用全局变量做模块间通信 |
| **严格模式** | 无需声明 | 一些"静默失败"的写法会直接报错 |

**接回渲染管线**：D0 第 1 章 §1.6 讲过"无属性 `<script>` 阻塞解析"。模块脚本**不阻塞解析**，这看起来是好事，但它带来另一个代价——**模块树的获取是递归的**：

```text
下载入口模块 → 解析出它的 import → 再去下载那些模块 → 再解析、再下载……
```

也就是说，**首屏需要的模块数量决定了请求轮次（瀑布）**。这正是 D3 领域要做"打包/合并"与"依赖预构建"的动机之一：把多次往返压成少数几次。

### 关键性质：模块图是**静态可分析**的

这是本章最重要的一条结论。因为 `import` / `export` 是**语法声明**（而非运行时函数调用），工具**不执行代码**就能算出完整的依赖图。

由此推出的连锁后果（后续章节反复引用）：

| 后果 | 依赖这条性质的地方 |
|---|---|
| 可以摇树（Tree Shaking） | 只有静态可分析，才能判断"某个导出从未被引用"（本章 §1.6） |
| 可以先链接再求值 | ESM 的两阶段处理让循环依赖可控（本章 §1.5） |
| 可以做代码分割 | 工具知道"哪里是图的断点" |
| 可以做依赖预构建 | 开发服务器能提前算出要处理哪些模块 |

## 1.2 `import/export` 与 `require`：声明 vs 调用

### 两种写法放在一起对比

```js
// ESM：声明式
import fs from "node:fs";
import { readFile } from "node:fs/promises";
import * as path from "node:path";
import "./side-effect.js";           // 只为了执行副作用

export const VERSION = "1.0";
export default function main() {}
export { readFile as read };          // 重命名导出

// CJS：运行时调用
const fs = require("node:fs");
const { readFile } = require("node:fs/promises");
module.exports = { VERSION: "1.0", main };
exports.read = readFile;              // 注意这一行的陷阱，见下
```

### 机制差异：这张表是本章的地基

| | ESM（`import` / `export`） | CJS（`require` / `module.exports`） |
|---|---|---|
| 本质 | **语法声明** | **运行时函数调用** |
| 位置 | 只能在模块顶层 | 可以在任何地方（条件里、函数里） |
| 时机 | 在模块求值**之前**完成链接与解析 | 执行到那一行才发生 |
| 依赖图 | **运行前**即可算出 | 执行过程中才能确定 |
| 绑定 | **实时绑定**（live binding） | **值拷贝**（对原始值而言） |
| 导出可否被改 | 导入方只读，导出方修改会同步给导入方 | 导入方拿到的是当时的快照 |

**"值拷贝 vs 实时绑定"值得单独举例**：

```js
// counter.js（ESM）
export let count = 0;
export function inc() { count++; }

// main.js（ESM）
import { count, inc } from "./counter.js";
inc();
console.log(count);   // 1 —— 拿到的是「当前值」，不是导入那一刻的快照
```

CJS 里同样的写法会打印 `0`——因为它拷贝的是值。

### 两个高频陷阱

**陷阱一：`exports` 被重新赋值就失效了。**

```js
exports = { a: 1 };        // ✗ 只是把局部变量重新指向新对象，模块导出不变
module.exports = { a: 1 }; // ✓ 改的是真正的导出对象
```

机制原因：`exports` 只是 **`module.exports` 的一个初始别名**。重新给它赋值就切断了这层关系。

**陷阱二：动态 `import()` 是唯一的例外。**

```js
const mod = await import("./feature.js");   // 返回 Promise
```

按 ECMA-262 的《Import Calls》，`import()` 是**表达式形式**的模块加载：它返回 Promise、**可以出现在任何位置**（包括条件分支与函数体内）。这是"静态声明"之外唯一的动态入口，也是代码分割的语法基础（D3 领域重点）。

## 1.3 ESM / CJS / UMD：三种格式与它们的互操作

### 三种格式的定位

| 格式 | 形态 | 谁在用 |
|---|---|---|
| **CJS** | `require` / `module.exports` | Node 生态的历史基础 |
| **ESM** | `import` / `export` | 语言标准，浏览器原生支持 |
| **UMD** | 外层做环境探测，分别走 CJS / AMD / 全局 | 需要同时兼容"有模块系统"与"只有全局变量"的时代产物 |

**UMD 现在基本不再需要**：浏览器原生支持 ESM 后，"兼容两种环境"这个前提消失了。见到它，通常说明这个包很老。

### 互操作：两个方向，两套规则

**方向一：ESM 里导入 CJS（Node 环境下）**

```js
import React from "react";          // 默认导入
import { useState } from "react";   // 命名导入 —— 未必可用
```

Node 的规则是：

| 写法 | 结果 |
|---|---|
| 默认导入 | 拿到整个 `module.exports`（即"**default 包装**"） |
| 命名导入 | **只有静态可分析出导出名时才可用**（Node 用工具扫描 CJS 源码找 `exports.x = …` 这类赋值） |
| 命名空间导入 | 会额外带一个 `default` 属性指向 `module.exports` |

**所以"为什么 `import React from 'react'` 与 `require('react')` 拿到的形态不一样"**：前者多包了一层 `default`，后者直接是 `module.exports`。这是互操作最常见的一处形态错位。

**命名导入依赖静态扫描**这一点，解释了另一个现象：**同一个包，有的导出能命名导入、有的不能**——取决于它是怎么写上去的（`exports.x = …` 能被扫到；`Object.assign(exports, …)` 或循环挂载常常扫不到）。

**方向二：CJS 里导入 ESM**

历史上一律不行（`require` 是同步的，而 ESM 的求值可能是异步的——例如顶层 `await`）。【待验证】较新的 Node 版本对「`require` ESM」的支持在逐步放开，但限制随时间变化，**用前必须查目标运行时的文档**。

### `type` 字段：`.js` 到底是哪一种

`package.json` 的 `type` 字段决定 `.js` 的解析方式：

| 文件 / 字段 | 解释为 |
|---|---|
| `.mjs` | **总是** ESM |
| `.cjs` | **总是** CJS |
| `.js` + `"type": "module"` | ESM |
| `.js` + `"type": "commonjs"` 或缺省 | CJS |

**这是一处容易被忽略的"环境决定语义"**：同一个 `.js` 文件，放在两个不同的包里，可能被按两种格式解析。所以排障时**必须先看这个包的 `type`**。

## 1.4 模块解析规则：从 import 语句到实际文件

### 解析分三个阶段

ECMA-262 只定义语言层的模块语义，**"从哪里取到这个模块"是宿主环境的事**。把宿主与打包器的实现归纳起来，解析分三步：

```text
① 解析（resolve）：把 import 里的字符串转成「一个具体的模块标识」
② 加载（load）：取到源码，并判定它按哪种格式解释
③ 链接（link）：把导入名与导出名对上，建立实时绑定
```

**第 ③ 步是 ESM 独有的**——正因为它先于求值发生，循环依赖才可控（本章 §1.5）。

### `exports` 条件导出：顺序敏感

```json
{
  "name": "mylib",
  "type": "module",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.mjs",
      "require": "./dist/index.cjs",
      "default": "./dist/index.cjs"
    },
    "./feature": "./dist/feature.mjs"
  }
}
```

三条必须记住的规则：

| 规则 | 说明 |
|---|---|
| **条件从上到下匹配，第一个命中的生效** | 所以**顺序是语义**，不是排版 |
| `default` 必须放在最后 | 它是兜底，放前面会吞掉其他条件 |
| 一旦声明了 `exports`，**包的内部路径就被封起来** | 消费者不能再 `import "mylib/dist/internal.js"`——这是它从"建议"变成"边界"的关键 |

最后一条是向后兼容的常见破坏源：**老版本被消费者按深层路径引用，新版本加了 `exports` 就全断了**。

### 历史字段与它们的局限

| 字段 | 给谁看 | 局限 |
|---|---|---|
| `main` | CJS 消费者 | 只给一个入口 |
| `module` | 打包器（非标准约定） | **不是标准字段**，Node 不认 |
| `types` | TypeScript | 与 `exports` 里的 `types` 可能不一致 |

**实践结论**：新包应优先用 `exports` 统一声明；`main` / `module` / `types` 保留是为了兼容老工具链。

### 别名：两套系统必须对齐

```js
// vite.config.js / webpack.config.js
resolve: { alias: { "@": "/src" } }
```

```json
// tsconfig.json
{ "compilerOptions": { "paths": { "@/*": ["./src/*"] } } }
```

**这是最典型的"两套别名系统"**：打包器有自己的别名，TypeScript 有自己的路径映射。**两者不一致时会出现"构建能过但类型报错"或反之**，而且报错信息通常指向一个看起来完全正确的 import 语句。

### 扩展名省略：一个真实的环境差异

| 环境 | `import "./util"` 是否可解析 |
|---|---|
| 浏览器原生 ESM | **不可以**，必须是 `./util.js`（浏览器不会替你猜） |
| Node 的 ESM | **不可以**，同样要求完整 specifier |
| CJS | 可以（有扩展名补全算法） |
| **打包器** | 可以（默认允许省略） |

**这条差异是"本地能跑、直接丢给 Node 跑就挂"的高频原因**。TypeScript 侧还多一层：`moduleResolution` 设为 `bundler` 时允许省略，设为 `node16` / `nodenext` 时要求写全——**所以 TS 配置要跟着运行环境走，不能照抄**。

### 目录导入与 `index`

`import "./utils"` 能否解析到 `./utils/index.js`，同样是环境相关行为（CJS 与打包器支持，原生 ESM 不支持）。**规则：在 ESM 里一律写全路径。**

## 1.5 循环依赖：解析顺序与求值顺序的错位

### 成因

A 导入 B，B 又导入 A。**这不是"错误"，两个格式都能表达它**——问题在于**求值顺序**必然有一个要先开始：

```text
先开始求值 A → A 需要 B → 开始求值 B → B 需要 A，但 A 还没求值完……
```

### ESM 与 CJS 的表现完全不同

| | ESM | CJS |
|---|---|---|
| 处理时机 | **先完成全部链接，再求值** | **边求值边解析** |
| 拿到的绑定 | **实时绑定**（引用同一处） | 当时的快照（`module.exports` 的一部分） |
| 典型症状 | 访问尚未初始化的绑定时抛 **`ReferenceError`** | 拿到 **`undefined`**，不报错 |

**ESM 为什么抛 `ReferenceError` 而不是给 `undefined`**：回到 D0 第 3 章 §3.2 的 TDZ——模块的绑定在链接阶段就创建了，但在求值到那一行之前处于**未初始化**状态。访问未初始化的绑定按规范就是 `ReferenceError`。

**CJS 为什么只是 `undefined`**：它没有"先链接"这一阶段，`require` 返回的是**此刻已经挂上去的那部分** `module.exports`。代码不报错，但拿到的对象不完整——**这是更危险的一种**，因为它会一路带着残缺状态跑到运行时才炸。

ECMA-262 用《Cyclic Module Records》专门处理这种情况，**核心手段就是"链接与求值分离"**（`ResolveExport` 在先，求值按深度优先后序进行）。这也是"ESM 更适合静态分析"的另一面。

### 排查手段

| 手段 | 用法 |
|---|---|
| 打包器的循环依赖告警 | webpack / Rollup 在检测到循环时会给出提示 |
| 把依赖图画出来 | 可视化工具能一眼看出环 |
| `pnpm why` / `npm ls` | 排查**包层面**的循环与多版本（本章 §1.7 会用到） |
| 断点看时序 | 在 `ReferenceError` 抛出处断点，读 Scope 面板（D0 第 5 章 §5.4） |

### 修复策略（从优到次）

| 策略 | 说明 |
|---|---|
| **提取共享模块** | 把双方都要用的部分抽到第三个模块，环就断了 |
| **依赖注入** | 让一方通过参数接收另一方，而不是导入 |
| **把"运行时才需要的引用"改成函数内引用** | 顶层引用会立刻求值；放进函数体则推迟到调用时 |

## 1.6 `sideEffects`：告诉工具"导入这个模块会做事"

### 为什么需要它

Tree Shaking 要判断"某个模块可以被安全移除"，这需要两个不同层次的信息：

| 问题 | 谁能回答 |
|---|---|
| 这个**导出**被引用了没有？ | **工具可以自己算**（因为 ESM 静态可分析） |
| 导入这个模块**这件事本身**有没有副作用？ | **只有作者知道** |

第二问就是 `sideEffects` 字段要回答的。**典型的有副作用的模块**：

```js
import "./global.css";        // 注入样式
import "./polyfill.js";       // 修改全局对象
import "./register-sw.js";    // 注册 Service Worker
```

这些模块**没有导出任何被引用的东西**，但删掉就会出问题。

### 默认值是"有副作用"（保守）

**未声明 `sideEffects` 时，工具按"有副作用"处理**——这是安全的选择，代价是摇不干净。

```json
{
  "name": "mylib",
  "sideEffects": false
}
```

```json
{
  "sideEffects": ["*.css", "./src/polyfill.js"]
}
```

两种写法：`false` 表示"所有模块都无副作用"；数组表示"**只有这些路径有副作用**"（其余可摇）。

### 误标的后果：副作用被删掉

**这是"误标比不标更危险"的典型场景**：

```json
// 一个包含样式导入的组件库
{ "sideEffects": false }     // ✗ 构建后样式可能整块消失
```

因为工具被告知"导入任何模块都不会有副作用"，于是**在它认为某模块的导出没被用到时，会连模块本身一起删掉**——连带着那句 `import "./style.css"` 也没了。症状是"组件渲染出来了但没有样式"，而且**本地开发时往往正常**（开发模式不做摇树），只在生产构建后出现。

### 怎么验证

不要靠配置猜，**对比打包产物**：

```text
① 改配置前后各构建一次
② 对比产物体积
③ 用包体积可视化工具确认目标模块是否真的进/没进包
```

（这条"用产物验证配置"的做法与原书第 2 章 §2.4 的结论一致：**不要凭配置猜**。）

## 1.7 双包危害：同一个包被加载了两份

> **本章前向依赖点**：本节需要"同一个包在依赖树里出现多份实例"这个背景，其完整机制属于D2 第 2 章的 `D2.L2.05`（依赖提升与硬链接）。此处按统一规则就地简要交代。

### 【补充背景】为什么同一个包会有多份实例

包管理器把依赖摊平成目录树时，**不同包要求同一依赖的不同版本**，就可能装出多份副本。所以"我明明只装了一个 React"这句话在依赖树层面未必成立——`npm ls react` 经常会列出两三个版本。

**完整机制见D2 第 2 章 §2.1**：提升把传递依赖提到顶层、版本冲突时在消费者内部嵌套——这两步共同造出"同一个包的多份实例"。此处保留这段简述只为让本节可独立阅读，细节请回看D2 第 2 章。

### 双包危害是什么

Node 官方文档专门为这件事写了条目：**同一个包同时提供 CJS 与 ESM 两份产物时，一个应用可能把两份都加载进来。**

```text
app.mjs  →  import "pkg"   →  pkg/dist/index.mjs   （实例 ①）
dep.cjs  →  require("pkg") →  pkg/dist/index.cjs   （实例 ②）
```

两份产物**各自有自己的模块作用域与模块级状态**——于是：

| 症状 | 原因 |
|---|---|
| 单例失效 | 两处各持一个"唯一实例" |
| `instanceof` 判断失败 | 两个类不是同一个类对象 |
| 状态不同步（如缓存、注册表、计数器） | 两份状态互不可见 |
| React 生态里的 Hooks 报错 | 两个 React 实例（这是最出名的一例） |

### 为什么它是"隐蔽"的

它**不报错**。代码能跑，只是行为不可预测：可能"开发环境正常、生产异常"，也可能"某个路径下正常、换个入口就异常"——取决于哪条链路先加载了哪一份。

### 缓解手段

| 手段 | 思路 |
|---|---|
| 只出**单格式**产物 | 最简单，代价是放弃某一侧的原生体验 |
| 让 `import` 与 `require` **指向同一份实现** | 常见做法是用 ESM 实现 + 一个 CJS 包装入口去引用它 |
| 用**符号而非 `instanceof`** 做判断 | 绕开"类对象必须是同一个"的假设 |
| 用包管理器约束版本 | `overrides` / `resolutions` 强制统一（D2 第 2 章展开） |

## 1.8 动手

| 任务 | 验收 |
|---|---|
| 写一个模块，用顶层 `let` + 修改函数，再从另一模块导入并调用 | **打印出修改后的值**，并说出这与 CJS 的行为差异（值拷贝 vs 实时绑定） |
| 在同一份代码里用 `exports = {…}` 与 `module.exports = {…}` 各写一次 | 说出为什么前者无效 |
| 给一个包加 `"type": "module"`，观察 `.js` 的行为变化 | 说出 `.mjs` / `.cjs` 与 `type` 字段的优先关系 |
| 写一个含 `exports` 条件导出的包，用 `import` 与 `require` 各引一次 | 说出条件匹配的顺序规则，以及为什么 `default` 必须放最后 |
| 构造一次 ESM 循环依赖，制造 `ReferenceError` | 说明它与 CJS 下 `undefined` 的机制差异（链接与求值的先后） |
| 构造一次 CJS 循环依赖，拿到残缺的 `exports` | 说明为什么它比 ESM 的报错更危险 |
| 在一个含 CSS 导入的模块上误标 `sideEffects: false` | **在生产构建产物里确认样式丢失**，并用可视化工具定位 |
| 在同一个项目里同时 `import` 与 `require` 一个双格式包 | 说出发什么症状、以及怎么验证（提示：看模块级状态是否共享） |

**进阶挑战**：

1. 用 `import()` 做一个条件加载，并说明它为什么是"静态 import 的唯一例外"。
2. 把 `resolve.alias` 与 `tsconfig.paths` 故意写成不一致，制造"构建能过但类型报错"，记录报错信息的特点。
3. 写一个不写扩展名的 import，分别在打包器与 Node 里运行，说明差异。

## 1.9 本章常见误区

| # | 误区 | 事实 |
|---|---|---|
| 1 | "`<script>` 加不加 `type="module"` 只是写法区别" | 模块脚本**默认延迟执行、按 CORS 获取、不共享全局、自动严格模式**，四项语义都不同 |
| 2 | "`import` 可以写在条件里" | 静态 `import` 只能在模块顶层；条件加载要用动态 `import()` |
| 3 | "`exports` 和 `module.exports` 可以随意互换赋值" | `exports` 只是 `module.exports` 的初始别名；给它重新赋值就切断了关系 |
| 4 | "`import React from 'react'` 和 `require('react')` 拿到的一样" | 前者经过 **default 包装**，多了一层 `default`；形态不同是互操作的常见错位点 |
| 5 | "加了 `exports` 字段只是多加个入口" | 它同时**封住内部路径**——老版本靠深层路径引用的消费者会直接断掉 |
| 6 | "`exports` 里条件的顺序无所谓" | **第一个命中的条件生效**，顺序即语义；`default` 必须放最后 |
| 7 | "`module` 字段是标准字段" | 它是**打包器的非标准约定**，Node 不认；`main` 才是 CJS 的入口字段 |
| 8 | "别名配置写一处就行" | 打包器别名与 `tsconfig.paths` 是**两套系统**，不一致会产生"构建能过但类型报错" |
| 9 | "import 时省略扩展名没关系" | 浏览器与 Node 的原生 ESM **都要求写全**；只有 CJS 与打包器允许省略 |
| 10 | "ESM 循环依赖会拿到 `undefined`" | 它抛 **`ReferenceError`**——因为绑定在链接阶段已创建但未初始化（TDZ） |
| 11 | "CJS 循环依赖只是 `undefined`，问题不大" | 它**不报错**却带着残缺对象继续跑，往往在更晚的时刻以更模糊的方式炸开 |
| 12 | "`sideEffects` 不写就会自动优化" | 默认按**有副作用**处理（保守）；不写只是摇不干净，不会出事故 |
| 13 | "`sideEffects: false` 写了更安全" | **误标比不标危险**：它会让工具把"没被引用的模块"整块删掉，连样式与 polyfill 的副作用导入一起删 |
| 14 | "双包危害会报错" | 它**不报错**，只表现为单例失效、`instanceof` 失败、状态不同步——排查成本极高 |

## 本章小结

**七条最该记住的结论**

1. **模块的规范性质是"独立求值单元"**：自己的作用域、声明式依赖、只求值一次、自动严格模式。这四条共同支撑了"静态可分析"。
2. **`import` / `export` 是语法声明，`require` 是运行时调用**——这一条差异推出后面几乎所有结论（依赖图可提前算出、可摇树、可预构建）。
3. **ESM 是实时绑定，CJS 是值拷贝**；互操作时 CJS 会经过 **default 包装**，这是形态错位的来源。**`exports` 只是 `module.exports` 的初始别名**。
4. **解析分三步：resolve → load → link**。`exports` 条件**顺序敏感**且会**封住内部路径**；扩展名在原生 ESM 中必须写全；打包器别名与 `tsconfig.paths` 必须对齐。
5. **循环依赖的差别在"链接与求值的时机"**：ESM 先链接后求值 → 访问未初始化绑定抛 `ReferenceError`；CJS 边求值边解析 → 静默拿到 `undefined`（**后者更危险**）。
6. **`sideEffects` 回答的是"导入这个模块是否有副作用"**——这是工具唯一算不出来的信息。**误标 `false` 会删掉副作用，且只在生产构建暴露。**
7. **双包危害不报错**，只让单例与状态悄悄失效。它的根因是"同一包的多份实例"，完整机制在D2 第 2 章的依赖提升与硬链接。
