## 6.1 URL：它不是字符串，是一个解析器

### 结构

```text
https://user:pass@example.com:8443/a/b?x=1&y=2#section
└─┬─┘   └───┬───┘└────┬────┘└┬─┘└──┬──┘└────┬───┘└──┬──┘
scheme  userinfo    host    port  path    query   fragment
        └─────────────── authority ───────────────┘
```

| 部分 | 作用 | 关键点 |
|---|---|---|
| scheme | 协议 | 决定默认端口（http 80 / https 443） |
| host | 主机 | **大小写不敏感**（会被规范化为小写） |
| port | 端口 | 省略时取 scheme 的默认端口 |
| path / query | 资源路径与参数 | 参与**缓存键**与 CORS 判定 |
| **fragment** | 页内锚点 | **根本不发给服务器**——只在浏览器内部使用 |

最后一行是常见误解的源头：`#section` 之后的内容**不会出现在请求里**，所以服务端拿不到它。

### WHATWG URL Standard 定义的是"解析算法"

URL 不是"用字符串拼出来的"，而是**由一套状态机解析出来的**（WHATWG《URL Standard》）。这解释了几个反直觉现象：

| 现象 | 机制 |
|---|---|
| 同样的路径写成 `a/../b` 与 `b` 会**被规范化成同一个 URL** | 解析时消解了 `.` 与 `..` |
| `http://example.com` 与 `http://example.com/` 是同一个 | 空路径被补为 `/` |
| 中文域名会被转成 `xn--` 形式 | IDNA 处理 |

**实践结论**：比较两个 URL 是否"同一个"，不要靠字符串比对，用 `new URL(a).href === new URL(b).href`。

### 相对 URL 需要一个"基准"

`href="detail.html"` 是相对路径，它的解析依赖**基准 URL**。默认基准是当前文档 URL，但可以用 `<base href="…">` 改写——**这个标签会影响页面上所有相对链接与相对资源路径**，是排查"路径突然全错"时的第一个检查点。

### 编码：两个函数的分工

| 函数 | 不编码的字符 | 用于 |
|---|---|---|
| `encodeURI` | 保留字符（`: / ? # & = +` 等） | 编码**整个 URL** |
| `encodeURIComponent` | 只有 `A–Z a–z 0–9 - _ . ! ~ * ' ( )` | 编码**参数值** |

**用错就会出错**：把参数值用 `encodeURI` 编码，值里的 `&` 与 `=` 不会被转义，于是会被解析成额外的参数分隔符。参数拼接的正确姿势是让 `URLSearchParams` 处理编码。

## 6.2 请求-响应模型：方法与状态码的语义

### HTTP 是无状态协议

RFC 9110《HTTP Semantics》定义的模型是：**每次请求-响应独立**，服务器不"记得"上一次请求。所有"状态"都靠外部机制携带（Cookie、token、URL 参数）——这正是 Cookie 存在的理由，也是后面有状态框架要解决的核心问题。

### 两个正交的性质：安全与幂等

| 方法 | 安全（不改状态） | 幂等（重复执行结果相同） | 说明 |
|---|---|---|---|
| GET / HEAD | 是 | 是 | 只读取 |
| POST | 否 | **否** | 每次都可能创建新资源 |
| PUT | 否 | **是** | 整体替换 |
| PATCH | 否 | 否 | 部分修改 |
| DELETE | 否 | **是** | 删除已删除的仍是"已删除" |
| OPTIONS | 是 | 是 | 预检与能力查询 |

**这张表不是学术分类**。浏览器与中间设备会**依据它做决策**：

- **可以安全重试**的只有幂等方法（网络中断后自动重发 GET 是安全的，重发 POST 可能产生重复订单）。
- **可以被预取/预加载**的只有安全方法。

这就是为什么"用 GET 做删除"是危险的（D0 第 3 章 §3.8 也提过）：爬虫预取、浏览器加速都可能触发它。

### 状态码：按语义分类

| 类别 | 含义 | 常用码 |
|---|---|---|
| 1xx | 信息性 | `101 Switching Protocols`（升级到 WebSocket） |
| 2xx | 成功 | `200` / `201 Created` / `204 No Content` / `206 Partial Content`（范围请求） |
| 3xx | 重定向 | `301` / `302` / `304` / `307` / `308` |
| 4xx | 客户端错误 | `400` / `401` / `403` / `404` / `405` / `409` / `429` |
| 5xx | 服务端错误 | `500` / `502` / `503` / `504` |

### 重定向四兄弟的差别只在两处

| 码 | 永久 / 临时 | 是否保留方法与正文 |
|---|---|---|
| 301 | **永久** | 历史上不保证（多数客户端会改成 GET） |
| 302 | 临时 | 同上 |
| 307 | 临时 | **保留** |
| 308 | **永久** | **保留** |

"永久"意味着**可以被缓存**——所以误用 301 会让浏览器长期记住旧地址，难以撤销。需要保留 POST 方法与正文的重定向，必须用 307 / 308。

### 容易混淆的状态码对

| 对 | 差别 |
|---|---|
| `401` vs `403` | 401 = **未认证**（凭据缺失或无效）；403 = **已认证但无权** |
| `404` vs `410` | 404 = 不存在；410 = **曾经存在且已永久移除** |
| `400` vs `422` | 400 = 请求本身格式错误；422 = 语义错误（格式对但值不合法） |
| `503` vs `500` | 503 = **临时不可用**（可带 `Retry-After`）；500 = 服务端内部错误 |
| `304` | **不是错误**：表示"你的缓存副本仍有效"，响应**不带正文**（本章 §6.4） |

## 6.3 报文字段与内容协商

### 两类头字段

| 类别 | 方向 | 作用 |
|---|---|---|
| **表示字段**（representation metadata） | 主要响应方向 | 描述正文本身：`Content-Type` `Content-Length` `Content-Encoding` `Last-Modified` `ETag` |
| **控制字段** | 双向 | 控制传输与缓存：`Cache-Control` `Vary` `Connection` `Accept-*` `Authorization` |

常用请求头的用途：

| 头 | 作用 |
|---|---|
| `Host` | 目标主机（HTTP/1.1 起必需，用于虚拟主机） |
| `Accept` / `Accept-Language` / `Accept-Encoding` | **内容协商的输入** |
| `Cookie` | 携带 Cookie（本章 §6.6） |
| `Referer` | 来源页地址（拼写错误是历史遗留） |
| `Origin` | 跨源请求的来源（**CORS 与 CSRF 防护的依据**，不同于 Referer：它不含路径） |
| `If-None-Match` / `If-Modified-Since` | **条件请求**（协商缓存的输入，本章 §6.4） |

### 内容协商：谁来选

客户端用 `Accept*` 头表达偏好，服务端决定返回什么：

```http
Accept: text/html, application/json;q=0.9, */*;q=0.1
Accept-Language: zh-CN,zh;q=0.9,en;q=0.8
Accept-Encoding: gzip, br, zstd
```

（`q` 是权重，默认 1.0。）

### `Vary`：告诉缓存"这个响应随什么变化"

这是最容易被忽略、后果又最严重的一个头。看一个场景：

```http
# 同一个 URL，服务端按 Accept-Encoding 返回不同压缩格式
200 OK
Content-Encoding: br
Cache-Control: max-age=3600
Vary: Accept-Encoding        ← 关键
```

**`Vary` 的作用是扩充缓存键**：把列出的**请求头**一起纳入"这是不是同一个缓存条目"的判定。

| 漏写 `Vary` 的后果 | 例子 |
|---|---|
| 同一 URL 的不同变体被当成同一个 | 给 A 用户返回的压缩格式被复用给不支持它的 B 用户 |
| 语言串味 | 服务端按 `Accept-Language` 返回不同语言，缓存只留一份 |
| 移动端/桌面端串味 | 靠 `User-Agent` 区分的响应被互相复用 |

**判断标准**：只要响应内容**依赖某个请求头**，就必须在 `Vary` 里列出它。

### 压缩是协商的，不是默认的

`Content-Encoding`（gzip / br / zstd）由 `Accept-Encoding` 协商决定。这解释了 Network 面板里的一个常见困惑：**同一个文件在不同浏览器下传输大小不同**——因为选中的压缩算法不同。

【待验证】各压缩算法（尤其 zstd）的浏览器与 CDN 支持度仍在演进，上线前需查目标环境。

## 6.4 HTTP 缓存：一套可推导的判定算法

RFC 9111《HTTP Caching》把缓存行为定义成一套判定流程。**把它记住，缓存问题就不再靠猜。**

### 判定流程

```text
① 有可用的缓存条目吗？
     没有 → 发完整请求
② 条目是「新鲜」的吗？（在新鲜度寿命内）
     是  → 直接用，不发请求                        【强缓存命中】
     否  → 进入验证
③ 发「条件请求」，带上 If-None-Match / If-Modified-Since
④ 服务器判定：
     · 未变 → 304 Not Modified（无正文）→ 用本地副本，按新头部更新新鲜度
     · 已变 → 200 + 新正文 → 替换缓存条目
```

两个关键区分：

| 类型 | 是否发请求 | 依据 |
|---|---|---|
| **强缓存**（fresh） | **不发** | `Cache-Control: max-age` / `s-maxage` / `Expires` |
| **协商缓存**（stale 后验证） | **发一个轻量请求** | `ETag` / `Last-Modified` |

所以"304"**不是省掉了请求，而是省掉了正文**——它省的是流量与解析时间，不省 RTT。

### 新鲜度从哪来

| 来源 | 说明 |
|---|---|
| `Cache-Control: max-age=N` | 相对时间，**优先级最高** |
| `Expires` | 绝对时间，受时钟漂移影响，已被 `max-age` 取代 |
| **启发式新鲜度** | 完全没给 `Cache-Control` / `Expires` 时，缓存可以**自行推断**（常见做法取 `(Date − Last-Modified)` 的约 10%） |

**启发式缓存是"忘了配缓存"时的隐患**：你以为没缓存，实际浏览器可能自作主张缓存了几分钟。

### `Cache-Control` 指令表（最该记住的部分）

| 指令 | 含义 | 常见误解 |
|---|---|---|
| `max-age=N` | 客户端缓存的**新鲜度寿命** | — |
| `s-maxage=N` | **共享缓存**（CDN、代理）的寿命，覆盖 `max-age` | — |
| `no-cache` | **每次都必须向服务器验证**（等于强制协商） | **"不缓存"是错的**——它是"缓存但必验" |
| `no-store` | **完全不存储**（不写内存也不写磁盘） | 这才是"不缓存" |
| `must-revalidate` | 过期后**不许用陈旧副本**，必须验证 | 与 `no-cache` 的区别在"过期前" |
| `immutable` | 在寿命内**连用户刷新都不重新验证** | 只对带内容哈希的静态资源用 |
| `private` / `public` | 是否允许共享缓存持有 | 含用户数据的响应应 `private` 或 `no-store` |
| `stale-while-revalidate=N` | 过期后先给旧副本，**同时后台更新** | 对"允许短暂陈旧"的场景体验很好 |

### 一套可靠的静态资源策略

```http
# 带内容哈希的文件（如 app.8f3a2b.js）——内容变了文件名就变
Cache-Control: public, max-age=31536000, immutable

# HTML 入口——绝不能长缓存，否则永远发不出新版本
Cache-Control: no-cache

# 含用户信息的接口响应
Cache-Control: private, no-store
```

**这套策略的机制依据**：因为文件名带内容哈希，"同一个 URL 的内容永远不变"这个前提成立，所以可以放心长缓存；而 HTML 是"版本入口"，必须每次验证。

这也是 D3 领域反复强调 `contenthash` 的原因——**缓存策略的前提是构建产物能产出稳定的内容哈希**（详见地图 §2 的 `D3.L4.07`）。

### 缓存位置不止一层

| 位置 | 特征 |
|---|---|
| 内存缓存 | 最快，随进程消失 |
| 磁盘缓存 | 持久，容量大 |
| Service Worker | **由 JS 完全控制**（可编程缓存） |
| **CDN / 代理（共享缓存）** | 受 `s-maxage` / `private` 约束，影响所有人 |

**`private` 与 `no-store` 的意义就在这里**：只考虑浏览器缓存的策略，会在 CDN 上出事故。

## 6.5 同源策略与 CORS：限制的是"读"，不是"发"

### 同源的判定

**scheme + host + port 三者全等**才算同源。三个常见陷阱：

| 对比 | 同源？ |
|---|---|
| `http://a.com` vs `https://a.com` | **不同源**（scheme 不同） |
| `https://a.com` vs `https://a.com:443` | 同源（443 是 https 默认端口） |
| `https://a.com` vs `https://b.a.com` | **不同源**（子域不算同源） |

### 它限制什么、不限制什么

这是理解后续一切安全问题的分水岭：

| 行为 | 是否被同源策略阻止 |
|---|---|
| 向跨源地址**发出**请求（`fetch`、表单提交、`<img>`、`<script>`） | **不阻止** |
| **读取**跨源响应内容 | **阻止**（需 CORS 授权） |
| 读取跨源 iframe 的 DOM | 阻止 |
| 发送/读取跨源 Cookie | 受 `SameSite` 与 `credentials` 双重约束 |

**关键结论：同源策略是"读"的边界，不是"发"的边界。** 这正是 CSRF（跨站请求伪造）能成立的原因——攻击者**不需要读取响应**，只要请求被发出就够了。理解这一点，才能理解为什么防护要靠 CSRF token 与 `SameSite`。

### CORS 的两条路径

浏览器把跨源请求分两类处理：

| 类型 | 判定条件 | 处理 |
|---|---|---|
| **简单请求** | 方法为 `GET`/`HEAD`/`POST`，且头字段仅限 CORS 安全清单（`Accept` `Accept-Language` `Content-Language` `Content-Type`），且 `Content-Type` 仅限 `application/x-www-form-urlencoded` / `multipart/form-data` / `text/plain` | **直接发出**，靠响应头判定是否允许读取 |
| **需预检请求** | 其余（如 `PUT`/`DELETE`、带自定义头、`Content-Type: application/json`） | **先发 `OPTIONS` 预检**，通过后才发真实请求 |

**注意最后一行**：`Content-Type: application/json` 会触发预检——这就是"接口用 JSON 提交时多了一个 OPTIONS 请求"的原因。

预检的往返内容：

```http
OPTIONS /api/items HTTP/1.1
Origin: https://app.example.com
Access-Control-Request-Method: PUT
Access-Control-Request-Headers: content-type

HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: GET, PUT
Access-Control-Allow-Headers: content-type
Access-Control-Max-Age: 600          ← 预检结果可缓存，减少往返
```

### 几个必须记住的约束

| 约束 | 说明 |
|---|---|
| `Access-Control-Allow-Origin: *` **不能**与 `credentials: "include"` 共用 | 必须回显具体来源 |
| 默认只有 **7 个响应头**可被 JS 读取 | `Cache-Control` `Content-Language` `Content-Length` `Content-Type` `Expires` `Last-Modified` `Pragma`；其余需 `Access-Control-Expose-Headers` |
| 预检失败 = 真实请求**根本不会发出** | 所以在 Network 面板只能看到一个失败的 OPTIONS |
| **CORS 是浏览器强制的** | 服务端拿 `curl` 永远能成功。所以 **CORS 不是鉴权机制**，它只防"别的站点读你的响应" |
| 错误信息被刻意模糊 | 表现为 `TypeError`，详情只在控制台（D0 第 4 章 §4.7） |

最后两条合起来是常见误区的根源：**"本地能调通、浏览器报 CORS"不代表服务端坏了**；而"加了 CORS 就安全了"也是错的。

## 6.6 存储：四种机制，四套代价

### Cookie：代价是"每次请求都自动携带"

| 属性 | 作用 |
|---|---|
| `Domain` / `Path` | 作用域（决定发给哪些请求） |
| `Expires` / `Max-Age` | 过期（不设则为会话 Cookie，关标签页即失效） |
| `HttpOnly` | **JS 读不到**（`document.cookie` 不可见） |
| `Secure` | 只在 HTTPS 下发送 |
| `SameSite` | 跨站请求是否携带：`Strict` / `Lax`（现代浏览器默认）/ `None`（必须配 `Secure`） |

**为什么 `HttpOnly` 与 `SameSite` 是关键**：

- `HttpOnly` 抵御 **XSS 窃取**——脚本读不到凭据，就无法外发。
- `SameSite` 抵御 **CSRF**——跨站发起的请求不带上凭据（Lax 下，顶层导航用 GET 仍会带）。

Cookie 的硬代价：**每个同域请求都会自动带上它**。所以不要把大量数据塞进 Cookie——它会被附加到每一次静态资源请求上（`Domain` / `Path` 设置不当尤其严重）。

### 四种存储的对照

| | Cookie | localStorage | sessionStorage | IndexedDB |
|---|---|---|---|---|
| 容量 | 约 4KB / 条 | 约 5MB / 源 | 约 5MB / 源 | 大（按配额） |
| API | 同步（`document.cookie`） | **同步** | **同步** | **异步** |
| 随请求发送 | **是** | 否 | 否 | 否 |
| 生命周期 | 可设过期 | 永久（手动清） | 标签页关闭即清 | 永久（可被清除） |
| 存什么 | 字符串 | 字符串 | 字符串 | 结构化数据、二进制 |
| 阻塞主线程 | 否 | **是** | **是** | 否 |

**"同步 API"这一行值得单独强调**：`localStorage` 的读写发生在主线程上，大数据量或频繁读写**会直接造成卡顿**——按D0 第 5 章的说法，它会占住主线程、推迟渲染与输入响应（可能抬高 INP）。所以它适合小配置，不适合大缓存。

### 凭据该放哪里：一个需要权衡的问题

| 方案 | 抵御 XSS | 抵御 CSRF | 说明 |
|---|---|---|---|
| `localStorage` | **弱**（脚本可读） | 强（不自动带） | 一旦 XSS，凭据立即外泄 |
| `HttpOnly` Cookie | **强** | 弱（需 `SameSite` + CSRF token） | 但会自动携带，要防 CSRF |
| 内存变量（配 refresh 流程） | 中 | 强 | 刷新即丢，需配合续期 |

**没有"全都赢"的方案**，选的是"更愿意承担哪一类风险"。这条权衡在 X2 / D6 领域会展开——本章只建立"存储不是免费的、各有攻击面"这个认知。

## 6.7 DNS / TCP / TLS：一次冷请求的开销链

D0 第 5 章的 Network 瀑布图把请求拆成若干段，本节解释**每一段为什么存在、能不能省**。

### 开销链

```text
DNS 查询 → TCP 三次握手 → TLS 握手 → 发送请求 → 等待首字节(TTFB) → 下载响应体
   1 RTT       1 RTT        1–2 RTT
```

`RTT`（往返时间）是这一节的通用货币。**每一个 RTT 都是"物理距离 / 光速"决定的**——本地优化改不了它，只能靠"减少次数"和"提前建立"。

### DNS

| 机制 | 说明 |
|---|---|
| 解析层级 | 递归解析器 → 根 → 顶级域 → 权威服务器 |
| 缓存 | 按 TTL 缓存，命中时几乎无开销 |
| **`dns-prefetch`** | 提前解析域名，把 DNS 时间从关键路径上挪走 |
| **`preconnect`** | 更进一步：提前做 DNS + TCP + TLS |

这两个提示是**"减少关键路径 RTT"的最廉价手段**——它们不减少总量，只是把开销**提前到空闲时间**。

### TCP 与 TLS

| 阶段 | 成本 | 可优化点 |
|---|---|---|
| TCP 三次握手 | 1 RTT | 连接复用（keep-alive） |
| TLS 1.3 握手 | 1 RTT（0-RTT 可用早数据，但有重放风险） | `preconnect`、会话复用 |
| 慢启动 | 初期吞吐受拥塞窗口限制 | 减少关键资源数 |

### 协议版本解决的问题不同

| 版本 | 解决什么 | 遗留什么 |
|---|---|---|
| HTTP/1.1 | — | **同域并发连接上限**（通常 6）导致请求排队；应用层队头阻塞 |
| HTTP/2 | 一个连接上**多路复用**并发流；头部压缩（HPACK） | **传输层仍队头阻塞**（TCP 丢包会拖住所有流） |
| HTTP/3 | 基于 QUIC（UDP），**解决传输层队头阻塞**；建连更快 | 部署与中间设备兼容性 |

**注意"队头阻塞"出现了两次，层次不同**：

- **应用层（HTTP/1.1）**：同一个连接上前一个响应没完，后面的要等。
- **传输层（HTTP/2 over TCP）**：TCP 是可靠有序的，一个包丢了，**所有流**都得等它重传。

HTTP/3 的意义正是把可靠性与有序性**下移到每条流**（QUIC 层），从而消除第二个队头阻塞。【待验证】HTTP/3 的 CDN 支持度与真实收益随网络条件变化，需按目标环境实测。

## 6.8 CDN：为什么"离得近"能解决问题

### 原理

CDN 把资源副本放到**离用户更近的边缘节点**，直接减少 RTT；同时它替你承担了 TLS 终止、压缩、连接复用。

### 三个层次的命中

```text
① 边缘节点命中 → 最快
② 上层节点回源途中命中 → 较快
③ 回源到你的源站 → 最慢（但仍可能比用户直连快）
```

### CDN 的缓存规则来自哪里

**它遵循的仍然是 本章 §6.4 的那套算法**，只是角色是"共享缓存"：

| 指令 | 对 CDN 的意义 |
|---|---|
| `s-maxage` | 覆盖 `max-age`，专管共享缓存 |
| `private` | **禁止 CDN 缓存**（含用户数据的响应必须这样） |
| `no-store` | 任何一层都不许存 |
| `Vary` | **直接决定命中率**——变体越多，命中越低 |
| `stale-while-revalidate` | 过期后先给旧副本、后台回源，把回源延迟挡在用户之外 |

**所以"CDN 缓存没生效"的排查顺序是**：先看响应头里有没有可缓存的指令 → 再看 `Vary` 是否过于严格 → 最后看 CDN 自身配置。

### 与构建的接回：为什么发布必须改文件名

把D0 第 5 章的观察连起来：

- 本章 §6.4 允许对"内容永不变化的 URL"设超长缓存（`immutable`）；
- 但 CDN 与浏览器**都不会主动猜**你的文件变了；
- **所以让文件"变化"的方式不是覆盖内容，而是改 URL** ——即内容哈希文件名。

| 发布方式 | 后果 |
|---|---|
| 覆盖同名文件 | 浏览器与 CDN 都持旧副本，用户可能拿到新旧混搭的产物（甚至版本不匹配导致白屏） |
| **改文件名（内容哈希）** | 新 URL 无缓存，旧 URL 自动失效；回滚只需回退 HTML 引用 |

这就解释了 D3 领域里 `contenthash` 与"入口 HTML 短缓存"这对搭配的完整动机：**它们不是为了构建好看，而是为了让缓存策略成立**。

### 刷新缓存的两种手段

| 手段 | 说明 |
|---|---|
| 主动刷新（purge） | 通知 CDN 立即失效指定 URL，有传播延迟 |
| **版本化（改 URL）** | 依靠内容哈希，天然无传播延迟 |

**优先用版本化**：它没有传播延迟，且天然支持灰度与回滚（D6 领域展开）。

**进阶挑战**：

1. 设计一份完整的缓存策略（HTML / 哈希 JS / 图片 / 接口），逐条写出指令与理由。
2. 用 `stale-while-revalidate` 构造一次"过期后仍秒开、后台更新"的体验，并在 Network 面板证明回源发生了。
3. 制造一次 `Vary` 缺失导致的缓存串味（同一 URL 返回不同语言），说明排查过程。

## 本章小结

**八条最该记住的结论**

1. **URL 由解析算法规范化**，不是字符串；fragment 不发往服务器；参数编码要用 `URLSearchParams` 与 `encodeURIComponent`。
2. **方法与状态码的"安全 / 幂等"性质会被浏览器用来做决策**（能否重试、能否预取）。重定向要保留方法时用 307 / 308。
3. **`Vary` 是正确性字段**：响应依赖哪个请求头，就必须列出它，否则缓存会串味。
4. **缓存是一套四步判定算法**：有条目 → 是否新鲜（强缓存）→ 条件请求验证（协商缓存）→ 304 用旧副本 / 200 换新。**304 省正文不省 RTT**。
5. **`no-cache` ≠ `no-store`**：前者"必须验证"，后者"不许存储"。**没配缓存头会走启发式缓存**。
6. **同源策略限制的是"读"，不是"发"**——这是 CSRF 成立的前提。CORS 由浏览器强制，因此**不是服务端鉴权**；`application/json` 会触发预检。
7. **存储各有代价**：Cookie 随请求自动携带（故须 `HttpOnly` + `SameSite` 防 XSS 与 CSRF），`localStorage` 同步 API 会阻塞主线程。凭据存储**没有全赢方案**。
8. **一次冷请求的开销是若干 RTT 之和**；DNS/TCP/TLS 靠 `preconnect` / `dns-prefetch` 提前化，HTTP/2 解决应用层队头阻塞、HTTP/3 解决传输层。**CDN 的有效性依赖内容哈希命名**——缓存策略与构建产物是一体两面。
