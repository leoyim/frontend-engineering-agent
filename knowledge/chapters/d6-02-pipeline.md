## 2.1 流水线的产出是"制品"，不是"构建成功"

先把一件事摆正。多数人描述 CI 时会说"流水线跑通了"，而"跑通"是个**过程状态**，不是一个**可交付物**。

**流水线真正该产出的东西**（第 1 章 §1.5 已定义）：

> **一整套不可变的制品**：产物 + sourcemap + 版本号 + 构建元信息 + 清单。

| 如果流水线只保证 | 那么出问题时 |
|---|---|
| "构建成功" | 你不知道线上那份是怎么来的、能不能复现、能不能回退 |
| **"产出了第 N 号制品"** | 每一份上线的东西都有编号、有档案、可追溯 |

**这条差异也决定了流水线的失败标准**：**"构建通过但制品不完整"应当算失败**（缺 sourcemap、缺 commit 标识、缺版本号）。否则你会在故障当天才发现缺东西。

## 2.2 通用模型：六个概念

跨平台看，任何 CI 系统都由这六个概念组成。**记住它们，就能读懂任何平台的文档。**

| 概念 | 回答什么问题 | 关键性质 |
|---|---|---|
| **触发器**（trigger） | 什么时候跑 | 事件 / 定时 / 手动 / 上游 |
| **阶段**（stage） | **按什么顺序**推进 | **门**：前一阶段全过才进下一阶段 |
| **任务**（job） | 一个独立执行单元 | **可能并行**，也可能串行（取决于平台默认） |
| **步骤**（step） | 任务内部的原子动作 | 顺序执行，共享同一个工作区 |
| **执行器**（runner / agent） | 在哪台机器上跑 | 决定环境；**决定"缓存能不能命中"** |
| **产物与缓存** | 什么东西要留住 | **artifact 与 cache 是两件不同的事**（下节） |

### artifact 与 cache：三件不同的事

这是本章最容易混的一对，也是**最多故障的源头**。三平台文档对二者的定位高度一致：

| 维度 | **artifact（制品 / 作业产物）** | **cache（缓存）** |
|---|---|---|
| **目的** | **把结果交给别人或下一个阶段** | **让自己下次省时间** |
| **正确性要求** | **必须正确**。缺了就是失败 | **可以失效**。失效只是慢 |
| **生命周期** | 与这次运行绑定，可长期归档（GitLab 有 `expire_in`） | 会被淘汰；键变或超期即失效 |
| **作用范围** | 通常是**一次运行内**的传递 + 归档 | **跨运行**复用 |
| **失败时的处理** | 缺了 → 流水线失败 | 恢复被跳过 → **当作 miss**，不失败 |

**最后一行是判据**，而且两个官方页面都印证了它：

- **GitHub Actions** 的 `cache-mode` 文档明确：**被拒绝的缓存操作只记日志、不使 job 失败**；恢复被跳过视为 **cache miss**，保存被跳过就是**不保存**。
- **GitLab** 的 `artifacts` 默认**在 job 结束（成功/失败/总是）时上传**，并可在 UI 下载 —— 它是**归档品**，不是"临时复用"。

**一句话判据**：

> **artifact 是"要给别人的"，cache 是"给自己省时间的"。**
>
> 判错的后果不对称：**该用 artifact 却用了 cache，会出现"偶发失败"**（缓存被淘汰的那次就失败）；**该用 cache 却用了 artifact，只会浪费存储与时间**。

### 一个具体的机制差异：恢复顺序

**GitLab 官方文档给了一条别处少见的细节**：

> **Caches are: … Restored before artifacts.**

**缓存在 artifacts 之前恢复。** 这意味着：

| 后果 | 说明 |
|---|---|
| **artifacts 会覆盖 cache 中的同名文件** | 所以"上一次构建的中间产物"不会盖住"这一次的产出" |
| 反过来则是灾难 | 若 cache 后恢复，它可能覆盖掉本次刚产出的文件 |

**这条对排查很有用**：当出现"产物里混进了上一次的东西"，先怀疑是不是把**产出物放进了 cache**。

**⚠️ 诚实标注**：这一条是 **GitLab 的官方表述**。**GitHub Actions 与 Jenkins 的同类文档本次未覆盖**，本章**不外推**到其他平台。

## 2.3 三个平台的默认行为完全不同

这一节是本章最有价值的对照，因为它解释了一类**只在"搬迁流水线"时才出现**的故障。

### 默认并行模型：三种完全不同的设计

| | **GitHub Actions** | **GitLab CI** | **Jenkins（声明式）** |
|---|---|---|---|
| **默认并行单位** | **job**（同一 workflow 内**全部并行**） | **同一 stage 内的 job** | **无**（stage 默认串行） |
| **默认串行机制** | **`needs` 显式声明** | **stage 顺序**（隐式门） | `stage` 顺序（隐式门） |
| **要并行怎么办** | 默认就是并行 | 放进同一个 stage | 显式 `parallel` |

**三句官方原文**（各一行，足够定论）：

| 平台 | 原文 |
|---|---|
| GitHub Actions | "A workflow run is made up of one or more jobs, **which run in parallel by default**." |
| GitLab CI | "**Jobs in the same stage run in parallel.**" / "Jobs in the next stage run after the jobs from the previous stage **complete successfully**." |
| Jenkins | `stages` 嵌套是**串行**（Sequential Stages）；并行需 `parallel` 段 |

### 为什么会因此出事故

**把一条 GitLab 流水线搬到 GitHub Actions**：

| 原语义 | 搬过去之后 |
|---|---|
| build → test → deploy（三个阶段，**依次门控**） | 三个 job **同时开始** |
| 测试跑完才部署 | **部署与测试并行启动** —— 测试还没结果，产物已经上线了 |

**反过来，把 GitHub Actions 搬到 GitLab**：

| 原语义 | 搬过去之后 |
|---|---|
| 五个 job 全并行（靠 `needs` 精确门控） | 它们被放进某个 stage，**同 stage 内并行**；一旦被分到不同 stage，就变成**串行等待** |

**这条的关键认识**：**"阶段"在两个平台上不是同一个东西。**

| 平台 | 阶段是什么 |
|---|---|
| GitLab | **并行的容器**（同 stage 并行、stage 间串行） |
| Jenkins | **串行的容器**（stage 之间天然串行） |
| GitHub Actions | **没有内建"阶段"概念** —— 顺序完全由 `needs` 图表达 |

**所以"把阶段的含义照搬过去"一定会错。** 搬迁时唯一可靠的做法是：**先把依赖关系画成一张图**（谁必须在谁之后），再按目标平台的默认模型去表达 —— 而不是逐个翻译关键字。

### 另两条值得对照的机制差异

| 维度 | 事实 | 出处 |
|---|---|---|
| **失败传播** | GitHub `needs` 的上游失败/被跳过 → 下游**全部跳过**，除非用 `always()` 一类条件 | GitHub 官方 |
| **中断行为** | GitLab：某 job 失败后，**后续 stage 不再开始**，但**当前 stage 中正在运行的 job 不会被停止** | GitLab 官方 |
| **矩阵任务顺序** | GitHub **明确不保证** matrix 各实例的运行顺序，并警告"输出名必须唯一，否则最后跑完的会覆盖" | GitHub 官方 |
| **Jenkins 的结构约束** | 一个 `stage` **必须有且仅有一个** `steps` / `stages` / `parallel` / `matrix` 之一 | Jenkins 官方 |
| **Jenkins 的 stage 级顺序** | `options` → `input` → `agent` → `when`（默认）；可用 `beforeOptions` / `beforeInput` / `beforeAgent` 提前 | Jenkins 官方 |

**"GitLab 不停止正在运行的 job"这一条值得记**：它意味着**失败之后你还会看到一批"白跑完"的 job** —— 这是设计如此，不是 bug。要更早停止，得靠 `needs` 或 `fail-fast` 一类的机制。

**"GitHub 不保证 matrix 顺序"这一条也很实用**：矩阵实例之间**无序且并发**，所以**任何依赖顺序的写法在矩阵里都是错的**。

### 两条诚实标注

1. **GitHub Actions 的 `matrix` 完整定义**（含 `include` / `exclude` / `fail-fast` / `max-parallel`）在本次核验的页面上**属于未覆盖部分**（正文被截断，仅有目录条目与三处间接表述）。本章因此**只引用已核验的两条**：matrix 会**展开成多个 job**、以及上面那条**顺序不保证**的警告。
2. **Jenkins 的 `archiveArtifacts` 与 `stash` / `unstash`** 在官方「Pipeline Syntax」页**没有定义** —— 该页把所有 step 的清单指向「Pipeline Steps reference」。所以：

| 机制 | 本章能否断言 |
|---|---|
| Jenkins **没有原生 cache 概念** | ✅ 可以：该页语法体系里**没有任何 cache 指令** |
| `archiveArtifacts` 是"持久归档"、`stash` 是"过程内临时传递" | ⚠️ **本章不作断言** —— 该页未覆盖，需查 Pipeline Steps reference |

**第 2 条恰好印证了 §2.2 那个二分**：Jenkins 的 `stash`/`unstash` 在语义上更接近"artifact 的临时形态"，而**它没有与 cache 对应的原生原语** —— 这决定了 **Jenkins 的缓存要靠插件或外部存储**，是搬迁时的实际成本项。

## 2.4 阶段与并行：门与并行单元

抛开平台差异，有一条设计原则是共同的。

### 阶段是"门"，不是"分组"

**门的语义**：前一阶段**全部成功**，才允许进入下一阶段。

**推论**：**把不构成"门"的东西放进阶段，会让流水线时间变成各阶段耗时之和。**

| 反例 | 后果 |
|---|---|
| 把"单元测试"与"E2E 测试"放进两个阶段 | 串行执行，总时长相加 |
| 把"lint"与"类型检查"放进两个阶段 | 同上，而它们都不依赖彼此 |

**正解**：把它们放进**同一个阶段（或同一次并行）**，因为它们**互不构成前置**。

### 但"并行"有一个隐藏前提

**并行成立的前提是"互不依赖"，而不只是"看起来无关"。** 两个常被忽略的依赖：

| 依赖类型 | 例子 | 症状 |
|---|---|---|
| **隐式共享状态** | 两个 job 写同一个缓存键 | 后写者覆盖，偶发失败（§2.5） |
| **隐式顺序依赖** | 都假设"依赖已安装" | 谁先跑谁成功 |

**所以"把两个 job 并行化"之前，必须先确认它们不共享可写状态。**

### 失败要早：但"最快的"不等于"最先的"

**fail fast 的动机**：让开发者在最短时间内知道"这提交不行"。

**但这里有一个真实的冲突**：

| 排序依据 | 会选出什么 |
|---|---|
| **最快失败** | lint（几秒） |
| **最重要** | 类型检查 / 单元测试 |
| **最贵** | E2E（几分钟） |

**如果只按"最快"排**，那么 lint 通过就给人一种"没问题"的错觉 —— 而真正会阻断发布的问题在后面几个阶段。

**推荐的判据**：

> **先放"最便宜、且能挡住最多错误"的检查。**

它同时满足两个目标：**成本低**（失败很便宜）与**覆盖广**（挡住的多）。而"最贵的检查"（E2E）应当**与它并行**，或者放到"已确认基本正确"之后。

### 一条与 D1 的连接

流水线的**第一阶段**应该是 **D1 那三层门禁**（提交信息 → lint → 单测）。本章不重复其机制（`D1` 第 1–3 章已讲），只补一条判断：

> **流水线不负责"发现代码问题"，它负责"阻止已知问题进入主干"。**

因为**流水线的反馈延迟是分钟级，而编辑器是秒级**。把能在编辑器里发现的问题推到 CI，等于**用最贵的方式做最便宜的事**（这与 D3 第 9 章 §9.3 的"不要把代码质量塞进构建"是同一条纪律的不同侧面）。

## 2.5 CI 独有的四个缓存问题

`D3.L3.02`。**缓存的失效机制在 D3 第 5 章 §5.4 已讲完**（`buildDependencies` / `version` / `maxAge` / 绝对路径 / `npm ci` prune），本节**只写 CI 场景独有的四件事**。

### 问题一：缓存键必须包含"决定产物的一切"

**缓存键的作用是"声明这份缓存适用什么输入"。** 键漏掉一项，就会**命中本该 miss 的缓存**。

| 键里该有什么 | 漏了会怎样 |
|---|---|
| **锁文件**（或它的指纹） | 依赖升级了，仍用旧缓存 → 产物与锁文件不符 |
| **构建器/转译器版本** | 换了打包器，仍用旧缓存 → **产物由旧工具生成** |
| **构建配置的指纹** | 改了配置，仍用旧缓存 → 与第 5 章 §5.4 的 `buildDependencies` 同一个坑 |
| **运行时大版本**（如 Node 主版本） | 换 Node 后行为可能变 |

**一条核心判据**（D3 已埋下伏笔，这里给出它的 CI 版本）：

> **缓存命中错了，比缓存没命中更糟。**
>
> **没命中只是慢；命中错了是"用别人的结果冒充自己的"，而且不报错。**

**这也解释了为什么 CI 缓存必须"宁可多失效"**：多失效的代价是时间，错误命中的代价是**正确性**。

### 问题二：缓存作用域

**缓存不是全局的**，它有作用域，而作用域决定了"一段缓存能影响谁"。

| 作用域形态 | 影响 |
|---|---|
| **分支隔离** | 一个 PR 的缓存不影响主干 |
| **全局共享** | 复用率高，但**一个坏缓存会污染所有分支** |
| **受保护分支隔离** | GitLab 官方明确："**默认不在受保护与未保护分支之间共享**" |

**GitLab 这一条值得单列**：**受保护分支（如主干）与普通分支的缓存默认不共享**。它带来一个**安全上的好处**（未受信任的 PR 无法污染主干缓存），代价是**主干经常 miss**。

**⚠️ 这也指向一类真实攻击面**：如果缓存是全局共享的，那么**任何人只要能提交一个 PR，就能往一个主干也会命中的键里写东西**。缓存里放的是"依赖"时，这就等于**供应链入口**。**这是"缓存作用域"不只是性能问题、也是安全问题的原因。**

### 问题三：并行任务之间的竞争

**多个 job 同时写同一个缓存键**时：

| 结果 | 说明 |
|---|---|
| 后写者覆盖 | 谁最后完成，缓存就是谁的（GitHub 对 matrix 输出名有明确警告，同一类问题） |
| 平台拒绝某些写 | GitHub 的 `cache-mode` 可限制为 `read` / `write-only` / `none` |

**治理动作**：**同一份缓存只允许一个 job 写**。多个 job 需要它时，让其中一个"产出"，其余只读。

**这条与 §2.4 的"并行前提"是同一件事**：**共享可写状态会破坏并行的正确性**，缓存就是最常见的共享可写状态。

### 问题四：artifact 与 cache 混用

已在 §2.2 给出判据，这里补一个**具体的失败模式**：

| 混用 | 症状 |
|---|---|
| 把"跨 job 传递的产物"放 cache | **偶发失败** —— 缓存被淘汰的那次就失败，且**只在某些运行里出现** |
| 把"依赖安装结果"放 artifact | 能跑，但**每次都完整上传/下载**，比 cache 慢，且占用归档空间 |

**"偶发失败"是最难查的一类**：它看起来像 flaky 测试，实际是**把必需的东西放在了可丢弃的位置**。

## 2.6 制品归档：为什么制品必须由流水线产出

`D3.L3.02`。这条看起来像"规定"，其实是**可复现性的必然要求**。

### 本地构建的产物为什么不能直接上线

| 本地状态 | 是否可复现 |
|---|---|
| 机器上的 Node 版本 | 只有你知道 |
| `node_modules` 是否与锁文件一致 | 未必（`npm install` 可能改锁文件） |
| 有没有未提交的改动 | 只有你知道 |
| 环境变量的值 | 只有你知道 |

**所以"本地构建 + 上传"的问题不是"不规范"，而是**：**上线的那份字节，无法从任何记录重建**。

**这与 D6 第 1 章 §1.5 的"三个必答问题"直接冲突** —— 答不出"对应哪份源码"，就不是流程问题，是**制品本身不可信**。

### 归档的三个要求

| 要求 | 判据 |
|---|---|
| **可追溯** | 从制品能反查到 commit、依赖锁指纹、构建器版本（第 1 章 §1.5 的元信息） |
| **不可变** | 同一版本号永远同一份字节（第 1 章 §1.5） |
| **可下载** | 任何人（有权限的）能在不重跑流水线的情况下取到它 |

**第三行常被忽略**：如果制品只能通过"重跑流水线"获得，那么**回退就等于重新构建** —— 这正是第 1 章 §1.2 说的"回退需要 5 分钟以上"的成因之一。

### 与缓存的分界再强调一次

| | 制品 | 缓存 |
|---|---|---|
| 能不能删 | **不能**（删了等于失去回退能力） | **应该能**（淘汰是正常行为） |
| 保留多久 | **与"还要支持回退多久"对齐** | 越短越好（长了会命中过期内容） |

**这条对比说明了一件容易被忽略的事**：**制品的保留策略是一个产品决策，不是一个存储成本决策。** 如果保留 3 天，那你就只能回退 3 天内的版本。

## 2.7 多环境部署：同一制品，不同目标

`D3.L3.02`。这一节把第 1 章 §1.4 的 build once 落到流水线里。

### 正确的结构：一个构建，N 个部署

```
build（产出制品 #123）
   ├─→ deploy:staging（输入：制品 #123）
   ├─→ deploy:prod   （输入：制品 #123）
   └─→ deploy:dr     （输入：制品 #123）
```

**关键性质**：**部署 job 的输入是"制品编号"，不是"重新构建"。**

| 如果每个环境各构建一次 | 如果所有环境部署同一份制品 |
|---|---|
| staging 测的产物 ≠ prod 上线的产物 | **同一份字节** |
| 回退要重新构建 | 回退只是"部署旧编号" |

### 反模式：用分支表达环境

**常见写法**：`if 分支 == 'main' → 部署 prod`。

**它的问题不在"不安全"，而在"不可回退"**：

| 场景 | 后果 |
|---|---|
| 需要从旧版本热修 | 旧版本的分支上**没有部署逻辑**（或者指向错误的环境） |
| 需要补发一个历史版本 | 只能"把旧代码合到 main" —— 于是**代码历史被打乱** |
| 需要在任意时刻部署任意版本 | 做不到 |

**正解**：**版本号是部署的输入，分支只是触发器之一。**

| 概念 | 该由什么表达 |
|---|---|
| **要部署哪个版本** | **制品编号 / 版本号**（显式参数） |
| **为什么触发** | 分支、标签、手动、定时 |
| **部署到哪个环境** | **显式的环境参数** |

**这条把"触发"与"目标"解耦了** —— 于是"部署 v1.4.2 到 prod"变成一个**可以随时执行的动作**，而不是"某次 push 的副作用"。

### 多环境部署的两个必查项

| 检查 | 为什么 |
|---|---|
| **所有环境用的是同一个制品编号** | 否则回到"测的没发、发的没测" |
| **每个环境都能独立回退** | 不能"回退 prod 顺带回退 staging" |

**第二项容易被忽略**：环境之间的回退**不该耦合** —— staging 出问题不该影响 prod，反之亦然。

### 部署 job 该验证什么

**部署不是"上传完就结束"。** 最小验证集：

| 验证 | 判据 |
|---|---|
| **索引指向新版本** | 实际请求一次，确认拿到的是新版本号 |
| **关键资源可达** | 至少一个带 hash 的产物与一个 `.map`（若部署了） |
| **运行期配置已下发** | 第 1 章 §1.4：运行期注入让产物不自解释，部署后必须确认 |

**第三条是本章与第 1 章的接点**：**build once 把风险从"构建期"转移到了"部署期"** —— 所以部署后的验证**必须包含配置检查**，否则"同一份字节在不同环境表现不同"就无从解释。

## 2.8 治理动作：六个判定阈值

与前几章同体例。**全部是起点值，需按项目校准。**

| # | 现象 | 判定阈值（起点值） | 动作 | 依据 |
|---|---|---|---|---|
| 1 | 部署与测试"看起来同时开始" | **任意一次部署 job 未依赖测试 job** | 查目标平台的**默认并行模型** —— 它可能与你原来的平台相反 | §2.3 |
| 2 | 流水线偶发失败，重跑就好 | **同一提交重跑成功率 < 95%** | 查是不是把**必需的传递物**放进了 cache（应改 artifact） | §2.5 |
| 3 | 依赖升级后产物没变 | **锁文件变了但产物 hash 没变** | 缓存键漏了锁文件（或它的指纹） | §2.5 |
| 4 | 改了构建配置但 CI 产物没变 | **任意一次"配置改了、产物一样"** | 缓存键漏了配置指纹；同时核对第 5 章 §5.4 的 `buildDependencies` | §2.5 |
| 5 | 回退需要重跑流水线 | **回退耗时 > 5 分钟** | 制品没有归档，或保留期太短 | §2.6 |
| 6 | 无法部署一个历史版本 | **任意一次"能不能发 v1.2.0"答不上来** | 部署入口应当是**制品编号**，不是分支 | §2.7 |

### 三条使用说明

**① 阈值 1 是本章最容易被漏掉的一条。**

它不会报错 —— 流水线照样"成功"，只是**部署跑在了测试结果之前**。只有**去看依赖图**才能发现。

**② 阈值 2 与 3、4 的排查方向相反。**

- 阈值 2 是"**该用 artifact 却用了 cache**"（正确的做法是改类型）；
- 阈值 3、4 是"**缓存键漏了输入**"（正确的做法是补键）。

两者都表现为"结果不对"，但修法完全不同。

**③ 阈值 5 与 6 都在同一个根因上：制品没有成为一等公民。**

如果流水线的产出被当作"一次性结果"，而不是"可归档、可按编号部署的制品"，那这两条必然命中。

### 什么时候"不该上流水线"

| 情况 | 为什么 |
|---|---|
| **项目只有一个开发者、且没有部署环境** | 流水线的收益来自"多人 + 多环境" |
| **还没有任何自动化测试** | 流水线只能跑"构建"，价值有限（但它仍能保证"制品由 CI 产出"这条） |
| **构建本身不可复现**（第 8 章 §8.2 的四个成因未解决） | 流水线会把不可复现放大成"每次构建都不同"，反而更难查 |

**最后一条值得强调**：**流水线不能修复不确定的构建，只会让它更显眼。** 如果 hash 不稳，先修构建（`D3` 第 8 章 §8.2），再上流水线。

## 2.9 动手

**每一项都要求说出理由**：

| 任务 | 验收 |
|---|---|
| 画出你流水线的**依赖图**（谁必须在谁之后） | 不看 YAML，只看语义；标出哪些其实是并行的 |
| 查一次你平台的**默认并行模型**，与你画的图是否一致 | 说出"如果换到另一个平台，哪些会变成并行/串行" |
| 列出你流水线里每个 job 的**输入与输出** | 逐项标注属于 artifact 还是 cache（§2.2 的判据） |
| 找出一个"偶发失败、重跑就好"的 job | 判断它是不是把必需物放进了 cache |
| 列出每个缓存的**键组成** | 对照 §2.5 的四项输入，标出缺哪一项 |
| 查一次缓存作用域：分支隔离还是全局共享 | 说出如果是全局共享，一个未受信任的 PR 能影响什么 |
| 查一次有没有多个 job 写同一个缓存键 | 若有，说出为什么这会让并行变得不可靠 |
| 确认制品的保留期是多久 | 说出"能回退多久"与它是否一致 |
| 尝试"部署一个历史版本"（不改代码） | 记录是否可行；若不可行，说出卡在哪一步 |
| 查一次部署后有没有验证"索引已指向新版本" | 说出如果没有，会怎么发现"发了但没生效" |
| 检查构建是否可复现（连续两次构建产物是否一致） | 若不一致，说出在上流水线之前必须先修什么 |

**进阶挑战**（任选一项）：

1. **把一条流水线做"平台无关化"**：先只画依赖图（阶段与并行），再分别用两个平台的模型表达出来。记录两版在默认行为上的差异 —— 这份对比是最有说服力的搬迁风险证据。
2. 给你的流水线做一份**"缓存可信度审计"**：每个缓存键列出它包含的输入、作用域、写入者。目标是回答"如果我改了 X，这份缓存该不该失效"。
3. 设计一个**"任意版本可部署"**的方案：要求能用一条命令把制品编号 #N 部署到任意环境，且不重新构建。这是第 1 章"回退是切索引"在流水线里的落地检验。

## 2.10 本章常见误区

| # | 误区 | 纠正 |
|---|---|---|
| 1 | "流水线跑通就算完成" | 流水线的产出是**制品**，不是"构建成功"。制品不完整应当算失败 |
| 2 | "缓存失败应该让流水线失败" | **不该**。GitHub 官方明确：被拒绝的缓存操作只记日志、不使 job 失败（恢复被跳过 = miss） |
| 3 | "该用 artifact 的地方用 cache 也行" | 会**偶发失败** —— 缓存被淘汰的那次就失败，看起来像 flaky 测试 |
| 4 | "该用 cache 的地方用 artifact 只是慢点" | **基本正确**（不会错，但更慢、更占空间）。这说明两边判错的代价不对称 |
| 5 | "产物混进了上次的东西，是构建工具的问题" | 先查是不是**把产出物放进了 cache**（GitLab：cache 在 artifacts 之前恢复） |
| 6 | "所有平台的流水线模型都一样" | **默认并行模型完全不同**：GitHub 的 job 默认全并行；GitLab 是"同 stage 并行、stage 间串行"；Jenkins 声明式 stage 默认串行 |
| 7 | "GitLab 的 stage 和 Jenkins 的 stage 是一回事" | GitLab 的 stage 是**并行容器**，Jenkins 的 stage 是**串行容器**。GitHub 干脆没有内建 stage 概念 |
| 8 | "看起来无关的 job 就能并行" | 并行前提是**不共享可写状态**（最常见的就是同一个缓存键） |
| 9 | "缓存键加个分支名就够了" | 必须包含**决定产物的一切**：锁文件、构建器版本、配置指纹、运行时大版本 |
| 10 | "缓存作用域只是性能问题" | 也是**安全问题**：全局共享时，任何能提 PR 的人都能往主干也会命中的键里写内容 |
| 11 | "多个 job 同时写同一个缓存没问题" | 后写者覆盖。**同一份缓存只允许一个 job 写**，其余只读 |
| 12 | "本地构建完直接上传也行" | 那份字节**无法从任何记录重建**，直接违反制品可追溯的前提 |
| 13 | "制品留三天够了" | 制品的保留期**决定你能回退多久**。这是产品决策，不是存储成本决策 |
| 14 | "回退就是重跑流水线" | 说明制品没有归档或保留期太短。回退应当只是"部署旧编号" |
| 15 | "用分支表达环境很方便" | 它让"部署任意历史版本"变得不可能，热修时只能打乱代码历史 |
| 16 | "版本号与触发条件是一回事" | 必须解耦：版本号是**部署的输入**，分支只是**触发器之一** |
| 17 | "部署完就结束了" | 还要验证"索引已指向新版本"与"运行期配置已下发"（第 1 章的 build once 把风险移到了部署期） |
| 18 | "上流水线能解决构建不可复现" | **不能**。流水线会把不可复现放大成"每次构建都不同"，先修 hash 稳定性（`D3` 第 8 章） |
| 19 | "Jenkins 也有原生 cache" | 本次核验的官方 Pipeline Syntax 页**没有任何 cache 指令**。Jenkins 的缓存靠插件或外部存储 |
| 20 | "`stash`/`unstash` 就是 artifact" | 官方 Pipeline Syntax 页**未定义**这两者。本章**不作断言**，需查 Pipeline Steps reference |
| 21 | "matrix 里的任务会按顺序跑" | GitHub 官方明确：**不保证 matrix 运行顺序**，并警告输出名必须唯一，否则最后跑完的会覆盖 |
