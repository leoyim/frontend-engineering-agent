## 3.1 覆盖率阈值：数字之外的三件事

`D5.L3.04`。第 2 章已给出工具侧的默认值（`include` 只统计被导入的文件、`perFile` 默认 false、glob 分组不继承）。这一节讲**为什么两个项目的"85%"不可比**。

### 三件事，一件都不在数字里

| 变量 | 影响 | 后果 |
|---|---|---|
| **分母怎么定** | 统计范围 | 分母只含"被导入的文件" vs 全量源码，同样的代码能跑出 95% 和 60% |
| **聚合还是逐文件** | 掩盖程度 | 聚合口径下，一个 0% 的关键模块可以被 100% 的工具模块平均掉 |
| **测什么（行/分支/函数/语句）** | 难度 | 分支覆盖天然低于行覆盖；两个数字不同口径不能并列 |

**所以"我们的覆盖率是 85%"这句话，在没交代这三件事之前，几乎不携带信息。**

**一个具体的对比**（用第 2 章核验过的 Vitest 默认值）：

| 口径 | 设置 | 同一份代码可能的数字 |
|---|---|---|
| **默认口径** | `coverage.include` 不设（= 被导入的文件）+ 聚合阈值 | 95% |
| **全量口径** | `coverage.include: ['src/**']` + 聚合阈值 | 70% |
| **全量 + 逐文件** | 上面 + `thresholds.perFile: true` | 55%（因为每个文件都要达标） |

**同一份代码、同一套测试，三个数字。** 这就是为什么**跨项目比较覆盖率没有意义** —— 而**同一项目内的趋势有意义**（只要口径不变）。

### 阈值的三种用法，效果完全不同

| 用法 | 效果 | 适用 |
|---|---|---|
| **全局单一阈值**（如 80%） | 容易达成，也容易被平均掉 | 起步阶段 |
| **逐文件阈值**（`perFile: true`） | **能发现"某个文件根本没人测"** | 成熟项目 |
| **按目录分组阈值**（glob 分组） | 核心目录严、工具目录松 | 推荐 |

**⚠️ 第 2 章已核验的一条**：Vitest 的 **glob 分组不继承顶层阈值** —— 所以分组是"独立设定"，不是"覆盖"。**这意味着你给某个目录设了宽松阈值后，顶层阈值对它完全不再生效**，而不是"取两者更严的"。

**一个被低估的技巧：负数阈值**（第 2 章已核验）。

`lines: -10` 表示**未覆盖行数不得超过 10 行**。它对两类模块特别合适：

| 模块类型 | 为什么百分比不合适 |
|---|---|
| **代码量小但每条都关键**（金额计算、权限判断） | 10 行里漏 1 行 = 90%，看起来很"高"，但漏的是关键分支 |
| **新写的模块** | 5 行里漏 2 行就是 60%，看起来"很差"，但其实只漏了 2 行 |

**所以负数是"绝对量"的语言，百分比是"相对量"的语言。** 对**小块重要代码**，绝对量才是对的度量。

### `autoUpdate`：一个需要警惕的便利

Vitest 的 `thresholds.autoUpdate` **默认 `false`**；开启后**当实际覆盖率优于配置时会自动把阈值写回配置**。

**⚠️ 这个功能有一个必须想清楚的后果**：**它让"阈值"变成了"当前状态的记录"，而不是"目标"。**

- 好处：阈值不会长期虚低（不会有人因为"反正早就超了"而不看）。
- 风险：**覆盖率下降时不会自动降，但上限被不断抬高** —— 某次偶然的高覆盖率会把门槛永久推高，之后必须一直维持。

**判定**：`autoUpdate` 适合**刚开始建阈值**的阶段；一旦阈值稳定，应当关掉，否则它会悄悄把"偶然的好成绩"变成"必须达到的门槛"。

## 3.2 变更覆盖率：把分母换成"变更行"

`D5.L3.04`。这是本章第一个"没有统一标准"的主题 —— 所以这一节讲**口径分歧**，而不是某个工具的用法。

### 它想解决什么问题

传统覆盖率的困境：

| 困境 | 表现 |
|---|---|
| **历史包袱** | 老代码覆盖率 30%，新代码写得再好，全局数字也上不去 |
| **无法推动** | 提高阈值 = 逼所有人补历史测试，通常推不动 |
| **改进无感** | 这次的改动很扎实，但数字一点没变 |

**变更覆盖率的思路**：**只统计"这次改动涉及的行"**。于是：

> **分母 = 本次变更的行；分子 = 其中被测试执行到的行。**

**这把手里的标尺从"存量质量"换成了"增量质量"** —— 而增量是**可以要求**的。

### 四个口径分歧（每一处都能让两个数字不可比）

#### 分歧一：变更集相对什么算

| 基准 | 含义 | 问题 |
|---|---|---|
| 与目标分支的最新提交比 | 只看"相对主干新增的" | 主干在此期间前进了，会出现大量"别人的变更" |
| 与分叉点（merge base）比 | 只看"这个分支自己带来的" | **最符合直觉**，但需要先算分叉点 |
| 与上一次 CI 成功比 | 只看"上次绿到现在" | 会随重跑次数漂移 |
| 与指定 commit 比 | 显式指定 | 最可控，但需要维护这个 ref |

**这是最重要的一处分歧**：**"与目标分支的最新提交比"会把主干上的变更算进你的分母** —— 于是你的 PR 覆盖率会因为别人合了代码而下降。

**推荐：分叉点（merge base）。** 它对应"这个 PR 到底改了什么"这个自然语义。

#### 分歧二：删行算不算

| 处理 | 后果 |
|---|---|
| **只算新增与修改行** | 合理 —— 删掉的代码不需要被覆盖 |
| **把删除也算进变更** | 分母里出现"不存在的行"，覆盖率被稀释 |

**这是最常见的实现 bug。** 它会让"纯删除的 PR"显示很低的覆盖率，而那个 PR 其实**没有任何需要测的新逻辑**。

#### 分歧三：忽略哪些文件

必须显式排除，否则分母会被噪声污染：

| 应忽略 | 原因 |
|---|---|
| 测试文件自身 | 它们是"测的工具"，不是"被测的对象" |
| 生成代码 / 类型声明 | 覆盖率对它无意义 |
| 配置、样式、静态资源 | 无"执行"概念 |
| 只含类型/接口的文件 | 编译后不存在 |

#### 分歧四：分子怎么匹配

这一处最微妙：**"变更行"与"被覆盖的行"是两个坐标系。**

- 变更行来自 **diff**（按 hunk 计算）；
- 覆盖行来自**插桩后的运行记录**（按语句/分支计算）。

**两者常常对不齐**：改了 1 行，可能让一大段行被重新编译、插桩位置偏移；一条变更可能展开成多条分支。

**后果**：**"分母里的一行"与"分子里的一行"可能根本不是同一行**。所以变更覆盖率**天然有误差**，它适合当**趋势与提醒**，不适合当**精确判据**。

### 三个必须知道的失真模式

| 失真 | 机制 | 后果 |
|---|---|---|
| **改一行、覆盖很多行** | 改了一个被大量测试调用的公共函数 | 覆盖率虚高（分子涨得比分母快） |
| **改一行、零行覆盖** | 改的是只在特定分支/环境触发的代码 | 覆盖率骤降，但其实无法轻易测 |
| **纯重构** | 行号全变、逻辑没变 | 分母暴涨，分子不变 → **重构被惩罚** |

**第三行是一条重要的设计缺陷**：**变更覆盖率会惩罚重构**。这直接与 §3.6 的"不要惩罚正确行为"原则冲突。缓解办法是**对纯重命名/移动类变更单独豁免**，但自动化很难判断"这是否只是移动"。

### 一句结论

> **变更覆盖率的价值不在数字精度，而在它把"存量包袱"从讨论里拿掉了。**

**它让"这次改动有没有被测到"成为一个可以要求的问题** —— 而这一点，全局覆盖率做不到。

## 3.3 变更影响分析：依赖图能告诉你什么、不能告诉你什么

`D5.L3.05`。上一节讲"只统计变更行"，这一节讲"只跑受影响的测试"。两者的前提是同一个问题：**怎么知道哪些测试会受影响。**

### 机制：沿依赖图反向查找

```text
正向（构建）：入口 → import → 模块
反向（选测试）：被改的文件 ← 谁 import 了它 ← 谁 import 了那个…… ← 测试文件
```

**这条链的准确性完全取决于"依赖图有多完整"。** 而依赖图**只看 import 语句**。

### ⭐ 官方明确的一条边界

Vitest 的 CLI 文档对 `--related` 写得很直接：

> 只运行覆盖给定源文件列表的测试。适用于**静态 import**，**但不适用于动态 import**（`import(filepath)`）。

而 `--changed` 的机制，也可以从另一条配置说明反向确认 —— `experimental.recordDependencies` 的官方描述是"记录每个测试文件加载的模块，并在 `--changed` 与 `--related` 中**使用这些记录代替静态模块图**"。

**所以默认机制是：静态模块图。**

**这意味着一条必须记住的推论**：

> **通过动态 import 加载的模块，被改动后不会触发任何测试重跑。**

**而动态导入恰好是代码分割（`D3` 第 3 章 §3.5）的标准做法。** 于是：

| 改动 | 会被发现吗 |
|---|---|
| 一个被静态 import 的工具函数 | **会** |
| 一个被 `import()` 动态加载的路由页面组件 | **不会** |

**这是一个安静的错误**：`--changed` 会跑得很快、很绿，**因为它少跑了该跑的测试。**

### 依赖图看不见的五类依赖

| 依赖类型 | 例子 | 依赖图能看到吗 |
|---|---|---|
| **静态 import** | `import x from './a'` | 能 |
| **动态 import** | `import('./page')` | **不能**（官方明确） |
| **require / 条件加载** | `if (x) require('./a')` | 视实现，通常不能 |
| **非代码引用** | CSS、JSON、图片、i18n 词条 | 通常不能 |
| **环境与配置** | `.env`、`define` 常量、feature flag | **完全不能** |
| **测试自身的公共代码** | 测试工具函数、fixture、setup 文件 | 部分工具支持，但常被忽略 |

**第二到第六行合起来意味着**：

> **"只跑受影响的测试"这个优化，本身就是一个漏测机制。**

**它不是 bug，是取舍。** 所以它只应当用在**本地开发与 PR 快速反馈**；**主干/发布分支上必须跑全量**。

### 一条推论：`--changed` 的绿，与"全量绿"不是同一个东西

| 场景 | `--changed` | 全量 |
|---|---|---|
| 本地开发 | ✅ 快，够用 | 太慢 |
| PR 快速反馈 | ✅ 有意义（但需全量兜底） | 有时太慢 |
| **合并前 / 主干** | ❌ **不能替代全量** | ✅ 必须 |
| **发版前** | ❌ | ✅ 必须 |

**所以变更影响分析的正确用法是"分层"，不是"替代"**：

```
本地：--changed（秒级）
  ↓
PR：--changed + 全量（并行跑，全量可延后）
  ↓
主干 / 发版：全量（唯一判据）
```

### `--shard` 与 `--changed` 的组合陷阱

**两个开关同时用，语义会变得难以推理**：

- `--changed` 先缩小集合 → `--shard` 再把这个**已经缩小的集合**均分；
- 于是**每个分片的负载极不均衡**（某个分片可能只分到 1 个测试）。

**建议**：这两个开关**不要同时用于"判断"**。分片用于全量跑（负载均衡有效），`--changed` 用于快速反馈（不并行分片）。

## 3.4 CI 卡点：卡什么

`D5.L3.06`。**⚠️ 再次说明分工**：流水线的阶段划分、并行策略、制品传递在 `D6` 第 2 章（已写）。**本节只讨论"哪些指标适合当门禁"。**

### 四条准入判据

一个指标要能当"门禁"（blocking gate），必须同时满足：

| # | 判据 | 不满足会怎样 |
|---|---|---|
| 1 | **可判定**：pass/fail 边界明确 | 需要人解读 → 不是门禁，是报告 |
| 2 | **低假阳性**：失败大概率指向真实问题 | 开始被忽略（`D5` 第 1 章 §1.7 的机制） |
| 3 | **可行动**：失败信息能指向"该改什么" | 失败只是让人焦虑 |
| 4 | **足够快**（相对所在环节） | 会被挪到"上线后再看" |

**这四条里最容易漏的是第 2 条与第 3 条。** 一个"满足前三条但不满足第四条"的门禁会被搬走；一个"满足 1/3/4 但不满足第 2 条"的门禁会被静音。

### 用这四条筛一遍常见指标

| 指标 | 可判定 | 低假阳 | 可行动 | 够快 | 结论 |
|---|:-:|:-:|:-:|:-:|---|
| 类型检查 | ✅ | ✅ | ✅ | ✅ | **强门禁** |
| Lint 错误（非警告） | ✅ | ✅ | ✅ | ✅ | **强门禁** |
| 单元测试 | ✅ | ✅ | ✅ | ✅ | **强门禁** |
| **覆盖率（全局阈值）** | ✅ | ✅ | ⚠️ | ✅ | **弱门禁** —— "数字不够"不指向具体改什么 |
| **覆盖率（逐文件）** | ✅ | ✅ | ✅ | ✅ | **较好** —— 能指名"这个文件没人测" |
| **变更覆盖率** | ⚠️ | ⚠️ | ✅ | ✅ | **弱门禁**（§3.2 的四个口径分歧 + 会惩罚重构） |
| E2E | ✅ | ❌ | ✅ | ❌ | **谨慎** —— 假阳性高、慢 |
| 视觉回归 | ✅ | ❌ | ⚠️ | ✅ | **谨慎** —— 误报会训练出"点更新" |
| 包体积预算 | ✅ | ✅ | ✅ | ✅ | **强门禁**（`D6` 第 4 章） |
| 性能预算（Lighthouse 等） | ⚠️ | ⚠️ | ⚠️ | ❌ | **弱门禁** —— 波动大 |
| 无障碍检查 | ✅ | ⚠️ | ✅ | ✅ | 中等（`D5` 第 1 章已讨） |

**注意这张表里的一个反直觉结论**：

> **覆盖率作为门禁，是"弱门禁"** —— 不是因为数字没意义，而是因为**"数字不够"不告诉任何人该去改什么**。

而"逐文件覆盖率"反而是**较好**的门禁：它输出的是"**这个文件一行都没跑过**"，这句话是可行动的。

### 门禁的三种状态，只有两种是真的

| 状态 | 效果 |
|---|---|
| **阻断**（blocking） | 真的拦住 |
| **警告**（warning） | **在实践中等于不卡** |
| **记录**（report-only） | 明确不拦，用于观察 |

**"警告"为什么等于不卡**：因为它**把判断责任推给了人**，而在"绿灯能过"的现实压力下，人会选择忽略。**这不是态度问题，是机制问题** —— 任何需要在时间压力下额外做判断的门禁，都会被绕过。

**所以门禁只有两种有效形态**：**阻断**，或**明确不卡（报告）**。**"警告"是一个欺骗性的中间态。**

### 谁有权改阈值

这是"用机制替代质量文化"的具体落点。**注意本节只解决"改动有多难"这一轴，"谁有权限改"是另一轴，见 `D5` 第 4 章 §4.5 的杠杆四 —— 两者要一起用。**

| 设计 | 后果 |
|---|---|
| **阈值改动需要评审** | 阈值变动成为**显式的、有记录的决策** |
| **阈值只能收紧、放宽需单独 PR** | **最有效** —— 收紧是顺手，放宽要理由 |

**第二行值得单独讲**：它把"降低标准"从"顺手改一个数字"变成了"需要写理由的动作"。**成本的不对称会塑造行为** —— 这比"请大家重视质量"有效得多。

**配套一条**：**阈值的变更应当出现在与代码同一个 review 流程里**，而不是在某个人的本地配置里。

> **为什么本表不写"任何人都能改阈值"这一行**：那是**权限**问题（谁按得动），不是**难度**问题（按下去要付出什么）。两者混在一张表里，会让人以为选一个就够 —— 实际是**两个都要设**：权限上"谁都能提、但需一位非作者的评审"（第 4 章 §4.5），难度上"收紧顺手、放宽要理由"（本表）。

### 卡点数量与可信度成反比

| 阻断项数量 | 常见结果 |
|---|---|
| 1–3 项 | 每一项都被认真对待 |
| 4–6 项 | 开始出现"先合了再说" |
| > 6 项 | **总有人能绕过某一项** —— 因为绕过的选项变多了 |

**这条与 `D6` 第 4 章 §4.6 的"告警数与健康度负相关"是同一个机制**：**当违规成为常态，规则就失去了约束力。**

### 一个必须保护的例外通道

**任何门禁都需要一条"确知原因、留痕、限定范围"的绕过通道**（例如 `skip-ci` 标签 + 必须写明理由 + 事后补）。

**没有例外通道的门禁会被用更糟的方式绕过**（改阈值、拆分 PR 规避检查、本地跳过钩子）。**给它一条合法的窄门，比让它被非法绕过好。**

## 3.5 测试提速：并行、分片、结果缓存

`D5.L3.07`。三种办法，**代价完全不同** —— 而最容易做错的是第一种。

### 办法一：并行（加 worker）

**Playwright 的机制（官方）**：

| 事实 | 内容 |
|---|---|
| 粒度 | **默认「文件之间」并行，同一文件内按顺序**在**同一个 worker** 中执行 |
| worker 是什么 | **独立的 OS 进程**，各自启动浏览器，**worker 之间无法通信** |
| 复用 | **尽量复用同一个 worker** —— 所以多个文件常在一个 worker 里**先后串行** |
| 失败后 | **worker 总是被关闭**（保证后续环境干净） |
| `fullyParallel` | 让**文件内**的测试也并行 |
| **隔离** | 默认保证到 **`BrowserContext`** 级别；**但 worker 进程不是每个测试都新建** |

**最后一行是一个常见误解的纠正**：**"每个测试一个全新进程"是错的。** 实际是"每个 worker 一个隔离的 context，而 worker 会被复用"。

**`fullyParallel` 的代价（官方）**：并行测试在**不同 worker 进程**中，**不能共享任何状态或全局变量**，且**每个测试各自执行全部钩子，包括 `beforeAll` / `afterAll`**。

**这条代价有具体的工时成本**：如果你的 `beforeAll` 里做了"登录一次、拿 token"，开 `fullyParallel` 后会**每个测试登录一次** —— 于是"并行变快"可能被"重复准备"吃掉。

### ⭐ "加 worker 反而更慢"的官方机制

Vitest 的 `vitest doctor` 文档里有一条极精确的说明：

> **每个 worker 都把它的转换请求漏斗到单线程的主 Vite server**，所以**超过某个数量后，更多 worker 会让运行变慢**。

**这是本章最有价值的一条机制**，因为它解释了"为什么堆机器不线性加速"：

```
worker 1 ─┐
worker 2 ─┼→ 单线程主 Vite server（转换请求的唯一入口）→ 排队
worker 3 ─┤
worker N ─┘
```

**所以并行的加速上限不在 CPU 核数，而在"转换服务的串行瓶颈"。**

**推论**：**并行的收益曲线是先升后降的**。这也解释了为什么 `vitest doctor` 会存在 —— 官方说它会**从当前 worker 数的一半开始，每提速 ≥5% 就继续减半**，自动找出拐点。

**实践含义**：**worker 数量应当实测，不该按核数猜。**

### 办法二：分片（shard）

| 工具 | 语法 | 语义 |
|---|---|---|
| **Vitest** | `--shard=<index>/<count>` | **把全部测试均分为 count 份**，只跑第 index 份；**不能与 `--watch` 同用** |
| **Playwright** | `--shard=<index>/<count>` | 切分套件分发到多台机器 |

**⚠️ 一处缺口**：Playwright 的 Parallelism 页**没有说明切片算法**（只是给了语法）。所以本章**不推断两边的切片策略是否相同**。

**分片的真实瓶颈：最慢的分片决定总时长。**

| 问题 | 原因 |
|---|---|
| **分片不均** | 均分的是"测试数量"，不是"耗时" —— 一条慢测试就能拖垮一个分片 |
| **固定成本被复制** | 每个分片都要独立装依赖、起服务、编译一次 |
| **分片数超过收益点** | 固定成本 × 分片数 > 节省的时间 |

**所以在分片之前，应当先知道"哪几条测试最慢"。** 否则分片只是在"均匀地分摊一个不均衡的分布"。

### 办法三：只跑该跑的（结果复用 / 变更筛选）

| 手段 | 工具支持 | 风险 |
|---|---|---|
| **只跑变更影响的测试** | Vitest `--changed` / `--related` | **§3.3 的漏测**（动态 import、配置、环境） |
| **只跑上次失败的** | **⚠️ Playwright 的 Parallelism 页明确没有这个机制**（只有 `--max-failures` 提前终止） | —— |
| **缓存测试结果** | 取决于工具链 | 缓存键不对 → 复用了错误的结果 |

**⚠️ 必须如实标注**：**Playwright 的 parallel 页完全没有"只重跑失败用例"的机制**（`--last-failed` 一类的开关不在该页）。所以"Playwright 支持断点续跑"这句话**本章不作断言**。该页确实有的是 `--max-failures`，但它是**达到失败数就停**，不是复用结果。

**缓存的核心判据**（与 `D6` 第 2 章的缓存同构）：**缓存键必须覆盖所有能影响结果的输入。**

| 影响结果的东西 | 是否常被放进取值 |
|---|---|
| 测试代码 | ✅ 通常 |
| **被测源码** | ✅ 通常 |
| **依赖锁文件** | ✅ 通常 |
| **环境变量 / 配置** | ❌ **常被漏** |
| **测试数据 / fixture** | ❌ 常被漏 |
| **工具自身版本** | ❌ 常被漏 |

**漏了后三项的缓存，会产生"本地绿、CI 绿、线上红"这类最难查的问题** —— 因为**结果是对的，但对应的是错误的输入**。

### 一条纪律：串行（serial）是最后手段

Playwright 的 `test.describe.configure({ mode: 'serial' })`：**一个失败则后续全部 skip，整组一起重试**。

**官方明确：不推荐使用。**

**代价是双重的**：

| 代价 | 说明 |
|---|---|
| **信息丢失** | 一个失败会**跳过后面所有测试** —— 你只看到第一个问题，不知道还有几个 |
| **重试放大** | 整组一起重试 → 通过的那几个也重跑（时间成本） |

**所以 serial 只应作为"确实有顺序依赖、且无法拆开"时的临时手段** —— 而那种情况本身通常说明**测试设计有问题**（一个测试依赖另一个测试留下的状态）。

## 3.6 治理动作：六个判定阈值

| # | 现象 | 判定阈值（起点值） | 动作 | 依据 |
|---|---|---|---|---|
| 1 | 覆盖率数字很好看但没人信 | **口径未文档化**（分母/聚合/指标类型任一未写明） | 先写清口径，再谈数字；跨项目不可比 | §3.1 |
| 2 | 某关键模块覆盖率 0%，但总覆盖率达标 | **`perFile` 未开启** | 开 `perFile`，或对核心目录用 glob 分组（注意**不继承**顶层阈值） | §3.1 |
| 3 | 纯删除的 PR 显示覆盖率很低 | **删除行被算进分母** | 变更集只算新增与修改行 | §3.2 |
| 4 | 重构 PR 的变更覆盖率骤降 | **重构被惩罚** | 对纯移动/重命名类变更豁免；或把变更覆盖率降为报告项 | §3.2 |
| 5 | `--changed` 快速通过，但全量有失败 | **依赖图看不见的依赖**（动态 import、配置、环境） | `--changed` 只用于本地与 PR 快速反馈；**主干/发版必须全量** | §3.3 |
| 6 | 加 worker 之后总时长没降 | **转换服务是单线程瓶颈**（Vitest 官方机制） | **实测**找拐点；用 `vitest doctor` 的思路对半试探 | §3.5 |

### 三条使用说明

**① 阈值 1 是元问题。**

如果口径没文档化，后面所有关于覆盖率的讨论都是**在比较不同的东西**。**先统一口径，再定阈值。**

**② 阈值 3、4 都指向"变更集算错了"。**

它们**不会报错**，只会给出一个"看起来很低"的数字 —— 然后团队会得出"这次改动质量差"的错误结论。

**③ 阈值 6 反驳的是"堆机器"这个直觉。**

**并行的收益有结构性上限**（单线程转换服务）。**先测，再加。**

### 什么时候该把门禁降级

| 情况 | 动作 |
|---|---|
| 某个门禁**一周内 3 次以上的失败被判定为误报** | 降为**报告项**，或修掉误报源 —— **不要留着当阻断** |
| 某个门禁**连续一个月没有被任何人看过** | 删掉它 —— **它在消耗时间而不产生信息** |
| 绕过的 PR 占比 **> 20%** | 门禁设计有问题，不是纪律有问题 |

**第二行值得单独说**：**一个没人看的门禁，成本是"每次 CI 都要跑"，收益是零。** 删掉它比留着更诚实。

## 3.7 动手

| 任务 | 验收 |
|---|---|
| 把你的覆盖率口径写成一句话（分母 / 聚合 / 指标） | 说出改其中任一项，数字会怎么变 |
| 对比"默认 include"与"全量 include"的覆盖率差 | 说出差额来自哪些从未被导入的文件 |
| 打开 `perFile`，看有多少文件跌破阈值 | 说出哪些是关键模块、哪些是工具代码 |
| 找一个纯删除的 PR，看它的变更覆盖率 | 说出删除行是否被算进了分母 |
| 找一个纯重构的 PR，看它的变更覆盖率 | 说出它是否被"惩罚"了 |
| 用 `--changed` 与全量各跑一次，对比通过情况 | 若有差异，说出差的测试是因为哪类依赖被漏掉 |
| 列一份"依赖图看不见的依赖"清单（针对你的项目） | 至少列出 5 项，含动态 import、配置、环境变量 |
| 数一下你 CI 的阻断项数量 | 若 > 6，说出哪几项其实是"警告" |
| 查一次谁能改覆盖率阈值 | 若任何人都能改，说出这会怎样改变行为 |
| 把你项目最慢的 10 条测试列出来 | 说出分片若按"测试数量"均分，最慢分片会长多少 |
| 查一次你的 worker 数量是怎么定的 | 若是"按核数猜"，说出该怎么实测 |
| 查一次测试缓存键包含了哪些输入 | 补上环境变量、fixture、工具版本 |

**进阶挑战**（任选一项）：

1. **重建卡点清单**：用 §3.4 的四条判据筛一遍现有门禁，把不满足的改成"报告项"或删掉。目标是**阻断项 ≤ 5 且每一项都有过真实拦截**。
2. **测一次并行的拐点**：固定测试集，逐次减半 worker 数量，记录总时长。画出曲线，找出拐点，并解释它为什么在那里。
3. **盘点变更影响分析的漏测面**：对项目做一次"动态 import / 配置 / 环境变量"的全量盘点，估一个"`--changed` 的漏测率"。

## 3.8 本章常见误区

| # | 误区 | 纠正 |
|---|---|---|
| 1 | "覆盖率 85% 说明质量不错" | 在没交代**分母 / 聚合方式 / 指标类型**之前，这个数字不携带信息 |
| 2 | "覆盖率越高越好" | 会激励"执行了但没断言"的测试 —— 增加成本，不增加信心（第 2 章 §2.6） |
| 3 | "glob 分组会与顶层阈值取更严的" | Vitest 官方：**glob 分组不继承顶层阈值**，对它匹配的文件完全替代 |
| 4 | "阈值只能设百分比" | Vitest 支持**负数 = 未覆盖条数上限**。对小块重要代码，绝对量更合适 |
| 5 | "`autoUpdate` 很省事，开着就好" | 它会让阈值从"目标"变成"当前状态的记录"，并把偶然的好成绩推成永久门槛 |
| 6 | "变更覆盖率是行业标准指标" | **没有统一标准**。四个口径分歧（基准 ref / 删行 / 忽略项 / 分子匹配）任一不同，数字就不可比 |
| 7 | "变更集应该与目标分支最新提交比" | 那样会把**别人的变更**算进你的分母。应用**分叉点（merge base）** |
| 8 | "变更覆盖率是精确判据" | 变更行（diff 坐标系）与覆盖行（插桩坐标系）**常常对不齐**，它适合当趋势与提醒 |
| 9 | "改一行只影响一行覆盖率" | 改一个被大量测试调用的公共函数，**分子会涨得比分母快** → 虚高 |
| 10 | "`--changed` 能替代全量" | 依赖图**看不见**动态 import、配置、环境变量、fixture —— 它是**漏测机制** |
| 11 | "动态 import 也会被依赖图追踪" | Vitest 官方明确：`--related` 适用于**静态 import**，**不适用于动态 import**；`--changed` 默认机制是静态模块图 |
| 12 | "动态导入很少用，影响不大" | 动态导入是**代码分割的标准做法**（`D3` 第 3 章）—— 影响面很大 |
| 13 | "`--changed` 和 `--shard` 一起用更快" | `--changed` 先缩小集合再分片，**负载极不均衡**。两者不应同时用于判断 |
| 14 | "主干上也用 `--changed` 省时间" | **主干/发版必须全量**。`--changed` 只用于本地与 PR 快速反馈 |
| 15 | "门禁越多越安全" | **阻断项 > 6 项时开始有人绕过** —— 绕过的选项变多了 |
| 16 | "覆盖率适合当门禁" | 它是**弱门禁**：数字不够**不指向该改什么**。**逐文件覆盖率才可行动** |
| 17 | "门禁应该绝对没有例外" | 没有例外通道会被**更糟的方式绕过**（改阈值、拆 PR、跳过钩子）。给一条留痕的窄门 |
| 18 | "Playwright 默认每个测试一个新进程" | 官方：worker 进程**会被复用**；隔离保证到 **`BrowserContext`** 级别 |
| 19 | "Playwright 默认文件内也并行" | 默认是**文件级并行、文件内串行**。文件内并行要开 `fullyParallel` |
| 20 | "开 `fullyParallel` 一定更快" | 每个测试各自跑 `beforeAll`/`afterAll` —— 重复准备可能吃掉并行收益 |
| 21 | "worker 越多越快" | Vitest 官方：所有 worker 的转换请求漏斗到**单线程主 Vite server**，超过某数量**更多 worker 更慢** |
| 22 | "worker 数按 CPU 核数设就行" | 加速上限在**转换服务的串行瓶颈**，应当**实测**找拐点 |
| 23 | "分片能线性缩短时间" | **最慢的分片决定总时长**；均分的是数量不是耗时；且固定成本（装依赖、起服务）会被每片复制 |
| 24 | "Playwright 支持只重跑上次失败的用例" | 本次核验的 Parallelism 页**没有这个机制**（只有 `--max-failures` 提前终止）。本章不作断言 |
| 25 | "测试缓存加上源码和锁文件就够" | 还须覆盖**环境变量、配置、fixture、工具版本** —— 漏了会产生"本地绿、线上红" |
| 26 | "serial 模式更稳定" | Playwright **官方不推荐**：一个失败会跳过后续全部测试（丢信息），且整组一起重试 |

> - **Playwright Parallelism**：默认**文件级并行、文件内串行**；worker 是**独立 OS 进程**、间**无法通信**、**会被复用**；**测试失败后 worker 总是被关闭**；`fullyParallel` 使文件内也并行，代价是**不能共享状态且每个测试各自跑 `beforeAll`/`afterAll`**；隔离保证到 **`BrowserContext`** 级别；`mode: 'serial'` **官方不推荐**（一失败则后续 skip、整组重试）；**默认 worker 数量该页未给**；**切片算法该页未给**；**无"只重跑失败用例"机制**。

> **五处如实标注的缺口**：① **变更覆盖率无行业统一标准** —— 本章只讲四个口径分歧，不绑任何实现；② **Vitest `--changed` 的默认比较基准**该页未说明；③ **Playwright 的切片算法**该页未说明；④ **Playwright 默认 worker 数量**该页未给（"CPU 核数一半"不来自该页）；⑤ **Playwright 无 `--last-failed` 类机制**，本章据此外推。
