## 1.1 四个缩写，一个变量

`X2.L2.01`。这些缩写常被当成"四种架构"来比较，但它们其实是**同一个问题的四种答案**。

### 那个变量：HTML 在什么时候被算出来

Next.js 官方说得很直接：

> **区别就在「它何时为页面生成 HTML」。**

| 形态 | HTML 生成时刻 | 生成者 |
|---|---|---|
| **CSR**（Client-Side Rendering） | **浏览器里，运行时** | 浏览器 |
| **SSR**（Server-side Rendering） | **每次请求时** | 服务器 |
| **SSG**（Static Site Generation） | **构建时**，每次请求复用同一份 | 构建过程 |
| **ISR**（Incremental Static Regeneration） | **构建时 + 过期后按需重生** | 构建过程 + 服务器 |

**⚠️ 第一行要先说清一件事**：**CSR 与另外三个不是同一类。** 严格说 **CSR 不"生成"页面 HTML**，它给出的是一个**壳**，内容由客户端 JS 填。所以下面这个排序只在"HTML 什么时候就绪"这个维度上成立，**不代表优劣**：

```
CSR（最晚：运行时） → SSR（每次请求） → SSG（构建时） → ISR（构建时 + 可更新）
```

**这条序列越往右，HTML 越早、越"现成"** —— 而**代价也越往右转移**（转移到构建过程与缓存管理上）。

### 一条必须先纠正的类比

**"SSR 更快"是错的。** 官方在 Pages Router 的渲染总览页里写得很明确：

> 出于性能考虑，**我们建议用静态生成（Static Generation）而不是服务端渲染（Server-side Rendering）**。

**理由也很具体**：

> **静态生成的页面可以被 CDN 直接缓存，无需额外配置。**

**所以正确的理解是**：

| 形态 | 性能 | 数据新鲜度 |
|---|---|---|
| **SSG** | **最好**（静态 + 零配置 CDN） | 最差（构建那一刻的） |
| **SSR** | 较差（每次请求都要算） | **最好**（每次请求那一刻的） |

**⭐ 所以 SSR 的收益从来不是"快"，而是"必须是这一刻的数据"。** 如果一个页面不需要"此刻"，用 SSR 就是纯亏。

**而官方给出的第三种答案是"混着来"**：**可以按页面选，从而构建 hybrid 应用**（多数页面 SSG、少数页面 SSR）。

## 1.2 一个必须知道的事实：官方术语已经分叉

**这项知识最容易踩的坑不是理解，而是"查文档查错了分区"。**

| 分区 | 术语 |
|---|---|
| **Pages Router**（本项目核验的页） | **Static Generation / Server-side Rendering** + **Automatic Static Optimization** |
| **App Router** | **Static Rendering / Dynamic Rendering** |

**两者是同一件事的两套说法**，但**同一份文档站里并存**。

**所以"某页说 ISR 已经不存在了""某页说 SSG 没有这个术语"这类判断，往往只是查错了分区。**

**⚠️ 三处如实标注（本次核验的直接结果）**：

1. **Pages Router 的 Rendering 总览页里完全没有 ISR** —— 既无缩写也无全称。ISR 必须去独立页看（§1.4 用的就是那一页）。
2. **该页 CSR 只有标题，没有定义**（"学习如何在 Pages Router 中实现客户端渲染"）。
3. **该页没有系统性的代价对照表** —— 只有"SSG 更快、可 CDN 缓存；SSR 有时是唯一选择"这两条。

**所以本章 §1.1 那张对照表，是把两页（总览页 + ISR 页）的信息与"生成时刻"这个统一视角拼起来的**，不是某一页的原表。

## 1.3 ISR：它不是定时任务

`X2.L2.01`。**这一节是本章最值得读的一节**，因为它要纠正一个几乎人人都会误解的机制。

### 官方定义：四项能力，而不是一句话

ISR 的全称是 **Incremental Static Regeneration**（增量静态再生）。**官方没有给一句话定义**，而是给了**四项能力**：

| # | 能力（官方原文要点） |
|---|---|
| 1 | **无需重新构建整个站点**即可更新静态内容 |
| 2 | 对**大多数请求返回预渲染的静态页面**，从而降低服务器负载 |
| 3 | **自动为页面添加正确的 `cache-control` 响应头** |
| 4 | 承载**大量内容页**而不必让 `next build` 变慢 |

**第 4 条是最容易被忽略的价值**：**它解决的是"构建时间随内容量线性增长"这个问题**，不只是"数据会变旧"。

### ⭐ `revalidate` 是「请求驱动的节流」

**这是最关键的机制，而它常被误解成"后台定时任务"。**

官方原文：

> Next.js 会在**有请求进来时**使缓存失效，**最多每 60 秒一次**。

**注意这三个词**：**"有请求进来时"**、**"最多"**、**"每 60 秒一次"**。

**它不是**：

| 误解 | 实际 |
|---|---|
| 每 60 秒后台自动刷新一次 | **没有请求就不会刷新** |
| 60 秒后页面立刻是新的 | 60 秒后的**第一个请求**仍拿到**旧页面**，同时触发后台再生；**下一个**请求才拿到新页面 |
| 定时任务 | **惰性**（lazy）：由流量驱动 |

**⭐ 由此得出一条直接可用的推论**：

> **一个没有流量的页面，永远不会自我刷新。**
>
> 所以"我设了 60 秒，但打开时数据是三天前的"**不是 bug** —— 那是三天里没有人访问过它。

**这也解释了第 4 条能力为什么重要**：**大量冷门页面可以"只在你需要时才更新"**，而不必在构建时全部算一遍。

### 两种触发方式

| 方式 | 怎么做 | 关键约束 |
|---|---|---|
| **按时间** | `getStaticProps` 返回 `revalidate: 60` | **请求驱动**（见上） |
| **按需** | 在 API Route 里调 **`res.revalidate('/posts/1')`** | 见下面两条硬规则 |

**按需重验的两条硬规则**（官方明确）：

**① 必须传「真实路径」，不是 rewrite 后的路径**

官方注释原文：

> 这应当是**实际路径**而不是**rewrite 后的路径** —— 例如对 `/posts/[id]`，这里应当是 `/posts/1`。

**原因见 §1.5 的第三条 Caveat**：**Proxy 不会对按需 ISR 请求执行**，所以 rewrite 根本不生效。

**② 启用按需重验后，`revalidate` 默认变成 `false`**

官方：

> 若使用按需重验，**你不需要在 `getStaticProps` 里指定 revalidate 时间**。Next.js 会用默认值 **`false`（不自动重验）**，只按需重验。

**所以"两种方式同时配"这个直觉是错的** —— 至少默认语义是"按需优先"。

**⚠️ 还有一条安全要求**：按需重验需要**自建带鉴权的接口**（如 `/api/revalidate?secret=<token>`）。**泄露 token 就等于任何人都能触发重验** —— 这是一个很真实的攻击面。

### 六步时序（官方的完整描述）

| 步 | 发生什么 |
|---|---|
| 1 | `next build` 时，所有**已知**页面被生成（这就是 SSG 部分） |
| 2 | 对这些页面的请求被缓存，**瞬时**返回 |
| 3 | 60 秒过去后，**下一个请求仍然返回缓存的（此时已 stale 的）页面** |
| 4 | 缓存被失效，新版本页面**在后台开始生成** |
| 5 | 成功生成后，**之后的请求**返回更新后的页面并缓存 |
| 6 | 若请求一个**未预生成**的路径，按 `fallback` 策略现场生成 |

**⭐ 第 3 步是 ISR 的核心设计**：

> **过期不等于阻塞。** 过期的页面**继续被服务**，再生在后台发生。

**这正是 `stale-while-revalidate` 的语义** —— 但**⚠️ 官方这一页从未写出这个术语**，也没有给出具体的 `Cache-Control` 示例。**所以本章描述行为，但不把这个术语挂到官方头上。**

### 再生失败时会发生什么

官方有一条很重要的语义：

> 若 `getStaticProps` 在后台再生时抛出未捕获错误，**上一次成功生成的页面继续展示**，并在**下一个请求**时重试。

**这条的后果是双面的**：

| 好处 | 代价 |
|---|---|
| **不会因为一次失败就让页面 404** | **可能长期陈旧** —— 只要每次都失败，就一直返回旧内容 |

**所以 ISR 的"陈旧"有两种来源**：

1. **没有流量**（没人触发再生）
2. **再生持续失败**（触发了但没成功）

**两者在监控上都表现为"数据不新"，但处置完全不同。** 这与 `D6` 第 5 章 §5.3 的"命中率看着还行但构建没变快"是同一类问题：**表面指标相同，根因不同。**

## 1.4 ISR 的三条已知边界

`X2.L2.01`。官方「Caveats」章节给了三条，**每一条都会在某个部署形态下直接失效**。

### 边界一：只在 Node.js runtime 下支持

| 部署形态 | 官方支持 |
|---|---|
| **Node.js server** | ✅ |
| **Docker container** | ✅ |
| **Static export** | ❌ **不支持** |

**这条边界很硬**：**一旦选了"静态导出"（纯静态托管），ISR 就没有了。** 而"静态导出"恰好是最省事、最便宜的部署方式 —— **这就是一个明确的取舍点**。

### 边界二：Proxy 不会对按需 ISR 请求执行

官方：

> **Proxy 不会对按需 ISR 请求执行** —— 路径 rewrite 或 Proxy 中的逻辑不会生效，因此必须重验**精确路径**。

**这条解释了 §1.3 那条硬规则**：**不是"建议传真实路径"，而是"rewrite 根本没跑"**。

**它还有一个更广的含义**：**按需重验走的是"直连"路径，绕过了你在 Proxy 里做的一切**（鉴权、灰度、rewrite）。**所以不能指望"Proxy 里已经鉴权了"来保护重验接口。**

### 边界三：`fallback: 'blocking'` 下，冷路径首次请求会被阻塞

**这是"ISR 不影响首屏"这个说法唯一的例外，而且它很常见。**

| 情形 | 首字节 |
|---|---|
| 已生成且未过期 | **瞬时**（官方用词 "instantaneous"） |
| 已生成但**已过期** | **旧页面继续返回**，不等 |
| **未生成 + `fallback: 'blocking'`** | **首个请求被阻塞**，直到现场生成完毕 |
| 未生成 + 该路径不存在 | **404** |

**⭐ 第三行值得单独记**：

> **ISR 只对"已知页面"避免了阻塞。对"冷路径的第一次访问"，`blocking` 模式仍然是一次同步渲染。**

**所以"用 ISR 就不用担心首屏"这句话，在长尾内容页上是错的** —— 而那恰好是 ISR 最常用的场景（博客、商品详情）。

**官方也明确**：这个行为**可以通过换 `fallback` 值改变**，但**该页没有逐一展开 `false` / `true` 的差异**（所以本章不给那个对照）。

### 一处真实的长期陷阱

**`revalidate` 是惰性的**，加上"再生失败继续返回旧内容"，两条叠加会产生一个**很难察觉的状态**：

> **一个页面可以长期提供服务、长期是旧的、并且没有任何错误。**

**这与 `D5` 第 4 章 §4.2 的"F 高 → 重跑 → 真实缺陷被掩盖"结构相同**：**系统的默认行为让它看起来是健康的。**

**所以 ISR 必须配一个"内容新鲜度"的观测** —— 而它不能靠"页面有没有 500"来发现。

## 1.5 路由与数据获取：`loader` 的位置变了

`X2.L2.02`。渲染形态决定"HTML 何时生成"，**数据获取形态决定"数据何时到位"** —— 而后者有一个容易被忽略的副作用：**它对包体积有直接影响**。

### React Router 的三种形态

React Router（8.4.0，Framework 模式）官方给的定位是：

> 数据通过 **`loader` 与 `clientLoader`** 提供给路由组件。

| 形态 | 在哪取数 | 适用 |
|---|---|---|
| **`loader`** | **服务端** | 需要用服务端 API、或不想把取数逻辑发到浏览器 |
| **`clientLoader`** | **浏览器** | 纯前端取数（如只调公开 API） |
| **静态预渲染** | **生产构建时** | URL 在 `react-router.config.ts` 的 `prerender()` 中声明 |

### ⭐ 最有价值的一条：`loader` 会从客户端 bundle 中被移除

官方原文：

> **`loader` 会从客户端 bundle 中被移除**，所以你可以使用**服务端专属 API** 而不必担心它们被打进浏览器。

**这条机制的价值在于它是"结构保证"，不是"纪律要求"**：

| 做法 | 服务端代码会进浏览器吗 |
|---|---|
| 在组件里 `import` 一个用 `fs` 的工具 | **会**（除非靠条件导出等手段剔除） |
| 写在 `loader` 里 | **不会**（loader 本身不在客户端包里） |

**而它与 `D3` 第 4 章 §4.2 的"依赖图是从入口可达的子图"是同一个机制**：

> **没被客户端入口引用到，就不会进客户端包。**

**所以"把服务端逻辑放在哪里"这个问题，本质上是在问"它会不会被客户端入口可达"。** 而 `loader` 是一个**框架层面保证不可达**的位置。

**⚠️ 但这不等于"服务端代码绝对安全"** —— `D3` 第 4 章 §4.2 已证明**依赖图有看不见的边**（动态 import、条件导出、配置注入）。**结构保证只对它覆盖的那部分成立。**

### 服务端模式下：`loader` 同时服务「初次加载」与「客户端导航」

官方：

> 服务端渲染时，`loader` **既用于初次页面加载，也用于客户端导航**。客户端导航会由 React Router **从浏览器向你的服务器自动发起 fetch**。

**这条的设计意图很清楚**：**同一套数据入口，两处复用。**

| 场景 | 谁执行 loader |
|---|---|
| 初次加载（SSR） | **服务器** |
| 后续导航 | **浏览器发 fetch，服务器执行** |

**它的收益是"一致性"**：**页面首次渲染与后续导航走同一段取数代码**，不会出现"刷新时对、点进去错"这类分歧。

**而它的代价是"多一次网络往返"**：客户端导航时**必须等服务器**。这与 §1.1 的"SSR 每次请求都要算"是同一个成本结构。

### 三处配套机制

| 机制 | 官方内容 | 为什么重要 |
|---|---|---|
| **自动序列化 / 反序列化** | loader 数据自动序列化，组件里自动反序列化 | 省掉手写 JSON 编解码 |
| **可返回复杂类型** | 除 string / number 外，还可返回 **promises、maps、sets、dates** | 不必为了传输把所有东西压成 JSON 原始类型 |
| **类型自动生成** | `loaderData` 的类型自动生成 | 取数结果与组件消费之间有类型约束 |

**⭐ 第二行有一个细节值得记**：官方说这些类型是**刻意对齐 RSC（React Server Components）可传递的类型**，**为将来迁移铺路**。

**这是一条"设计上留后路"的实例** —— 与 `D4` 第 2 章 §2.5 的"组件库变量单向映射"是同一个思路：**让今天的实现不挡住明天的迁移。**

### `clientLoader` 的三个特殊点

| 场景 | 行为 |
|---|---|
| 默认 | 初次加载用 `loader`，后续导航用 `clientLoader` |
| **`clientLoader.hydrate = true`** | **在 hydration 期间、页面渲染前**也跑 `clientLoader`；需要配 **`HydrateFallback`** |
| `clientLoader` 内要服务端数据 | 用 **`serverLoader()`** 复用服务端 loader 的结果 |

**第二行的 `HydrateFallback` 说明了一件事**：**"loader 进行中"是一个真实存在的中间态**，组件本身还没渲染。**所以纯客户端取数必然要设计加载态**，而 SSR 取数不需要（数据在 HTML 里）。

**⚠️ 四处在官方该页**没有**的内容（本章据此不出断言）：

1. **多个 loader 是否并行执行**（该页无并行 / 瀑布流的内容）
2. **与 `useEffect` 取数的对比**（该页未出现 `useEffect`）
3. **`defer` / 流式渲染**（只提到 loader 可返回 Promise，未展开如何流式消费）
4. **错误边界与重定向的处理位置**（该页无 `errorElement` / `redirect` 的内容）

### 一条判据：数据获取的「位置」决定三件事

**这一节可以压成一个判据**：

> **数据在哪取，同时决定了：能否用服务端 API、是否产生请求瀑布、首屏是否等它。**

| 位置 | 服务端 API | 请求瀑布风险 | 首屏等它吗 |
|---|---|---|---|
| **服务端 loader** | ✅ 可用 | 取决于并行策略（**本章未核**） | **是**（在 HTML 里） |
| **客户端 loader / 组件内取数** | ❌ 不可用 | **高**（父先子后） | **不一定**（可先给骨架） |

**第二行与第三行的组合是 CSR 的本质**：**首屏不等数据 → 首屏快、但内容晚到。**

## 1.6 治理动作：六个判定阈值

| # | 现象 | 判定阈值（起点值） | 动作 | 依据 |
|---|---|---|---|---|
| 1 | "用了 SSR 所以更快" | **页面数据不需要"此刻"** | SSR 的收益是**新鲜度**不是性能；不需要就用 SSG | §1.1 |
| 2 | "设了 `revalidate: 60`，数据怎么是旧的" | **该页无流量** | `revalidate` 是**请求驱动**的，没有请求就不刷新 | §1.3 |
| 3 | 后台再生持续失败，但页面一直正常 | **内容陈旧但无错误** | 再生失败会**继续返回旧页** → 需要**内容新鲜度**观测，不能只看 5xx | §1.4 |
| 4 | 按需重验"不生效" | **传的是 rewrite 后的路径** | **Proxy 不执行按需 ISR 请求** → 必须传**真实路径** | §1.4 |
| 5 | 长尾内容页首屏偶发很慢 | **`fallback: 'blocking'`** | 冷路径**首次**请求是同步渲染；ISR 只对"已知页面"免阻塞 | §1.4 |
| 6 | 服务端代码被打进了浏览器包 | **取数逻辑写在组件里而不是 `loader`** | `loader` **会从客户端 bundle 移除** —— 这是结构保证，不是纪律 | §1.5 |

### 三条使用说明

**① 阈值 2 与 3 都属于"看起来正常"。**

一个因为没流量、一个因为再生失败 —— **两者都不会报错**，只会让数据变旧。**所以"页面能打开"不能作为数据新鲜度的证据。**

**② 阈值 4 的排查顺序很关键。**

先确认"传的是不是真实路径"，再怀疑配置。**因为 rewrite 不生效这件事在配置层面完全看不出来。**

**③ 阈值 6 的修法不是"加个环境判断"。**

`if (typeof window === 'undefined')` 这类判断**不能阻止代码进包**，只能阻止执行（`D3` 第 4 章 §4.2 的"依赖图看不见的边"已证明这一点）。**真正有效的做法是把它挪到 `loader` 这种"客户端入口不可达"的位置。**

### 什么时候"不该上服务端渲染"

| 情况 | 为什么 |
|---|---|
| **首屏不需要 SEO**（后台、内部工具） | SSR 的复杂度换不来收益 |
| **数据可以是构建那一刻的** | 用 SSG，还能白拿 CDN 缓存 |
| **团队没有服务端运维能力** | SSR 把"静态托管"变成"要运维进程" |
| **只是"觉得 SSR 更现代"** | 那是拿真实成本换一个标签 |

| 任务 | 验收 |
|---|---|
| 把项目每个页面按"HTML 何时生成"分类 | 说出哪些是 SSG、哪些是 SSR，以及为什么 |

| 查一次你是否手写了序列化 | 说出框架自动序列化省掉了什么 |

**进阶挑战**（任选一项）：

1. **给每个页面做一次"生成时刻审计"**：标出 HTML 生成时刻 + 数据获取位置 + 是否阻塞首屏。目标是**每一页都能回答"它为什么是现在这个形态"**。
2. **给 ISR 加一层新鲜度观测**：不只看有没有 5xx，还看"实际生成时间 vs 当前时间"的分布。目标是**把"长期陈旧"从静默状态变成可见状态**。
3. **把一处服务端逻辑从组件挪进 `loader`**：先验证它原本确实进了浏览器包，迁移后再验证。

## 1.8 本章常见误区

| # | 误区 | 纠正 |
|---|---|---|
| 1 | "只能整站选一种" | 可以**按页面选**，官方称之为 hybrid；还能叠加客户端取数让局部完全由客户端渲染 |
| 2 | "SSG / ISR 这些术语已经过时了" | **Pages Router 仍用这套**（Static Generation / SSR + Automatic Static Optimization）；App Router 用 **Static / Dynamic Rendering**。**两套并存** |
| 3 | "查文档说没有 ISR，所以 ISR 没了" | **Pages Router 的 Rendering 总览页里确实没有 ISR** —— 它在独立页。**这多半是查错了分区** |
| 4 | "`revalidate: 60` 是每 60 秒后台刷新" | **它是「请求驱动的节流」**：官方原文"**在有请求进来时**使缓存失效，**最多每 60 秒一次**" |
| 5 | "没流量的页面也会自己刷新" | **不会**。没有请求就不触发。所以"设了 60 秒但数据是三天前的"**不是 bug** |
| 6 | "60 秒后第一个请求就是新页面" | 那个请求**仍拿到旧页面**，同时触发后台再生；**下一个**请求才是新的 |
| 7 | "ISR 只是让数据变新" | 它还解决**构建时间随内容量线性增长**（官方四项能力之一） |
| 8 | "时间重验与按需重验可以并列配" | 启用按需重验后，`revalidate` **默认为 `false`（不自动重验）** |
| 9 | "按需重验传 rewrite 后的路径也行" | **Proxy 不会对按需 ISR 请求执行** → 必须传**真实路径** |
| 10 | "Proxy 里鉴权过就够了" | 按需重验**走直连**，绕过了 Proxy 里的鉴权 / rewrite / 灰度 |
| 11 | "按需重验接口不用鉴权" | 需要自建 token 校验。**泄露 token = 任何人可触发重验** |
| 12 | "ISR 不影响首屏" | 只对**已生成的页面**成立。**未生成 + `fallback: 'blocking'` 时，首个请求会被阻塞** |
| 13 | "ISR 用了 `stale-while-revalidate` 这个术语" | **官方该页从未写出这个词**。行为等价，但**术语不是官方表述** |
| 14 | "再生失败会报错" | **不会**：继续展示**上一次成功的页面**，并**在下个请求重试**。可能长期陈旧 |
| 15 | "页面能打开就说明数据不旧" | 陈旧有两种来源（**没流量** / **再生失败**），**都不产生错误** → 必须单独观测新鲜度 |
| 16 | "选静态导出更省事，反正有 ISR" | **Static Export 不支持 ISR**（官方 Caveats）。这是硬取舍 |
| 17 | "ISR 在哪都能跑" | **仅 Node.js runtime**；静态导出不支持 |
| 18 | "`fallback` 只影响首次访问快慢" | 它还决定**不存在的路径返回 404 还是现场生成** |
| 19 | "数据获取只是写法问题" | 位置同时决定：**能否用服务端 API / 是否产生瀑布 / 首屏是否等它** |
| 20 | "用条件判断就能让服务端代码不进包" | **不能**。`typeof window` 只阻止执行，不阻止进包。要挪到**客户端入口不可达**的位置 |
| 21 | "`loader` 里写的代码也在客户端包里" | 官方明确：**`loader` 会从客户端 bundle 中被移除**，可用服务端专属 API |
| 22 | "loader 只在初次加载时用" | 服务端渲染时它**同时服务初次加载与客户端导航**（导航由框架自动 fetch） |
| 23 | "loader 只能返回 JSON 原始类型" | 官方支持 **promises / maps / sets / dates**，且**刻意对齐 RSC 可传递类型**（为迁移铺路） |
| 24 | "纯客户端取数不用设计加载态" | `clientLoader.hydrate` 场景需要 **`HydrateFallback`** —— "loader 进行中"是真实存在的中间态 |
| 25 | "多个 loader 一定并行" | **本次核验的官方页未涉及并行策略**，本章不作断言 |
| 26 | "loader 抛错怎么处理，文档里写了" | **该页未覆盖错误边界与重定向**，本章不作断言 |

> - **Next.js v16.4.2 · Pages Router · Rendering 总览（2026-03-03 更新）**：核心概念是 **prerendering**（"默认预渲染每个页面"）+ **hydration**；**两种预渲染形式**为 SSG（构建时、每次请求复用）与 SSR（每次请求）；**官方原句"区别就在它何时为页面生成 HTML"**；**官方建议用静态生成而非 SSR，理由是性能**（静态页面**可被 CDN 直接缓存，无需额外配置**），但"某些情况下 SSR 可能是唯一选择"；**可按页面混合（hybrid）**；Pages Router 仍用 **Static Generation / SSR + Automatic Static Optimization**。
> - **Next.js v16.4.2 · ISR 页（2025-05-21 更新）**：全称 **Incremental Static Regeneration**；官方以**四项能力**定义（免全站重建 / 多数请求走静态以降负载 / 自动加 `cache-control` / 承载大量内容页而不拖慢 `next build`）；**`revalidate` 是请求驱动的节流**（"**在有请求进来时**使缓存失效，**最多每 60 秒一次**"）；两种触发（时间 / **`res.revalidate`** 按需）；**按需重验必须传真实路径**（"实际路径而非 rewrite 后的路径"），且启用后 **`revalidate` 默认 `false`**；**六步时序**（过期后**仍返回 stale 页**、后台再生、成功后下一请求拿新页）；**再生失败则继续展示上次成功页面并在下一请求重试**；**三条 Caveats**（**仅 Node.js runtime** / **Static Export 不支持** / **Proxy 不对按需 ISR 请求执行**）；部署支持表（Node.js server ✅ / Docker ✅ / Static export ❌）；**`fallback: 'blocking'` 下未生成路径的首个请求会被阻塞**。
> - **React Router 8.4.0 · Framework · Data Loading**：数据由 **`loader`（服务端）/ `clientLoader`（浏览器）/ 静态预渲染**提供；**`loader` 会从客户端 bundle 中被移除**（故可用服务端专属 API）；服务端模式下 **`loader` 同时服务初次加载与客户端导航**（导航由框架自动 fetch）；**自动序列化/反序列化**；可返回 **promises / maps / sets / dates**（**刻意对齐 RSC 可传递类型**）；`loaderData` 类型自动生成；**`clientLoader.hydrate = true`** 会在 **hydration 期间、页面渲染前**运行，需配 **`HydrateFallback`**；`serverLoader()` 可复用服务端结果。
>
> **五处如实标注的缺口**：① **Pages Router 的 Rendering 总览页完全不含 ISR**，CSR **只有标题无定义**，且**无系统性代价对照表**（§1.1 的表是跨两页 + "生成时刻"视角拼起来的）；② **ISR 页从未使用 `stale-while-revalidate` 术语**，也未给具体 `Cache-Control` 示例；③ **ISR 页未展开 `fallback` 各取值的差异**；④ **React Router 该页未覆盖**并行加载 / 与 `useEffect` 的对比 / `defer` 与流式 / 错误边界与重定向；⑤ **App Router 的 Static / Dynamic Rendering 一套本次未核验**，故本章只说明"两套并存"，不比较它们。
