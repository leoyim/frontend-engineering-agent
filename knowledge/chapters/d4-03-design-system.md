## 3.1 样式层架构：四层与一条边界

`D4.L4.01`。"设计系统"这个词常被当成"一套组件库"，但它真正要解决的是**依赖方向**问题。

### 四层

| 层 | 内容 | 依赖谁 |
|---|---|---|
| **① Token** | 值（颜色、间距、字号、圆角…） | 不依赖任何东西 |
| **② 原语（primitive）** | 无语义的组件：`Button`、`Input`、`Stack` | **只依赖 Token** |
| **③ 业务组件** | 带语义的组件：`SubmitOrderButton` | **只依赖原语 + Token** |
| **④ 页面 / 模板** | 布局与组合 | 依赖上面任一层 |

### 一条边界：依赖只能单向

**架构是否成立，只看一件事**：

> **有没有"下层依赖上层"的边？**

| 违规 | 后果 |
|---|---|
| Token 里引用了某个组件的变量 | Token 无法独立分发 → **多项目共用失败** |
| 原语依赖业务组件 | 原语无法复用 → **它就不是原语了** |
| 页面层向 Token 写入值 | 主题不可预测（谁最后写谁赢） |

**第三条最隐蔽**：它表现为"某个页面看起来颜色不对"，而根因在**页面层改了一个本应只读的变量**。

**⭐ 所以 Token 层的规则应当是一条硬约束**：

> **Token 层是「只读的」**：只有主题定义可以写它，其他层只能读。

**这与 `D0` 的变量作用域、`D1` 第 3 章的"规范的层级"是同一个机制**：**依赖方向决定可替换性。** 一旦出现反向依赖，被依赖的那层就再也单独升不了级。

**而它与 `X1` 第 1 章 §1.5 的"模板是复制、共享包是引用"是同一条**：**共享包能升级的前提是没有落到别人内部去。**

### 一个必须做的决定：组件库自足到什么程度

**组件库的两个需求天然冲突**：

| 需求 | 内容 |
|---|---|
| **自足** | 装进任何宿主都能用，不依赖宿主的环境 |
| **可定制** | 宿主要能改成自己的品牌外观 |

**冲突点很具体**：**越自足（内部结构固定），越难定制；越可定制（开放内部），越不自足。**

**三种方案**：

| 方案 | 自足性 | 定制能力 | 代价 |
|---|---|---|---|
| **全封闭**（只有预设主题） | 最高 | 低 | 宿主稍有不同就只能重写组件 |
| **全开放**（暴露内部类名/结构） | 低 | **最高** | **内部结构成为公共 API** |
| **变量契约**（只暴露 Token） | 高 | 中–高 | 需要 **Token 设计得当** |

### ⭐ 判据：暴露「值」，不暴露「结构」

**这是本章最实用的一条**：

> **组件库应当对外暴露「可替换的值」，而不是「可覆写的结构」。**

| 暴露什么 | 宿主改的是什么 | 后果 |
|---|---|---|
| `--btn-bg`、`--btn-radius` | **值** | 内部可以重构（DOM 结构、类名随便改） |
| `.btn__inner`、`.btn > span` | **结构** | **一旦有人用了，结构就不能改** |

**第二行的后果是刚性的**：**你不再拥有这个组件的内部结构**，因为它是别人代码里的选择器目标。

**这与 `D3` 第 4 章 §4.5 的"插件改产物要慎用 `emit`"、`D3` 第 6 章 §6.5 的"迁移成本在生态"是同一个机制**：

> **一旦某样东西被外部依赖，它就从"实现"变成了"接口"。**

**而"变量契约"有一个额外好处**：**它可以被逐层组合**（第 2 章 §2.2 的三层 Token），于是宿主只改语义层，组件库只读语义层 —— **两边都不碰对方的结构**。

**⚠️ 但"变量契约"有一个前提**，否则它会失败：

| 前提 | 不满足会怎样 |
|---|---|
| Token 覆盖了组件的**全部可定制点** | 宿主想改的地方没有变量 → **只能去改结构** |
| 变量名描述**用途**，不描述外观 | 主题改名时对不上（第 2 章 §2.2 已证明） |
| 有**默认值**（且合理） | 宿主不配变量时外观崩坏 |

**第一行是最常见的失败**：**契约不完整时，宿主会被迫破坏契约。** 而这不是宿主的问题，是**契约的覆盖度问题**。

## 3.2 跨项目主题：主题是「一份值的集合」

`D4.L4.02`。主题最容易被做成"另一套 CSS"，而它应当只是**同一套规则 + 另一组值**。

### 最小定义

> **主题 = 语义层的一组取值。**

**所以主题切换不涉及任何"样式规则"的变化**，只涉及变量的值：

```css
:root                  { --color-bg: #fff;    --color-fg: #111; }
[data-theme="dark"]    { --color-bg: #111;    --color-fg: #eee; }
```

**⭐ 这个实现有一个极重要的性质**：

> **切换主题的成本，与「规则条数」无关，只与「变量数量」有关。**

**为什么**：`[data-theme="dark"]` 只是**重新给一批变量赋值**，**不新增任何选择器规则、不触发任何结构变化**。

**而它的对立面（每个主题生成一份完整 CSS）成本完全不同**：

| 做法 | 切换成本 | 体积 |
|---|---|---|
| **变量重赋值** | 只重算受影响元素的样式 | **一份规则** |
| **每个主题一份 CSS** | 换一整份样式表（可能闪烁） | **N 份** |

**第二行还会带来另一个问题**：切换时**样式表要重新解析** —— 那是可见的闪烁。

### 多主题的乘法陷阱

**主题很少是"一维"的**：

```
主题（亮/暗）× 品牌（A/B/C）× 密度（舒适/紧凑）
= 3 × 4 × 2 = 24 种组合
```

**如果按组合生成 CSS**：**24 份** —— 而它们的**规则完全相同**，只有值不同。

**所以解法的方向是确定的**：

> **把维度正交拆开，每个维度只贡献一组变量的覆盖。**

```css
:root                       { --space-4: 16px; }
[data-density="compact"]    { --space-4: 12px; }
[data-theme="dark"]         { --color-bg: #111; }
```

**三个属性叠加，得到"暗色 + 品牌 B + 紧凑"** —— 而**只写三组变量**，不写任何组合。

**⭐ 这条能直接推出一个判据**：

> **如果新增一个"品牌"需要新增一份 CSS 文件，那说明维度没有拆开。**

| 现象 | 说明 |
|---|---|
| 新增品牌 = 新增一份 CSS | ❌ 维度未拆（品牌的值混在规则里） |
| 新增品牌 = 新增一段变量赋值 | ✅ 正交 |
| **新增品牌需要改组件** | ❌ 组件直接用了原始值（第 2 章 §2.2） |

### 主题的三个交付形态

| 形态 | 载体 | 能运行时切换吗 |
|---|---|---|
| **CSS 文件**（`:root` + 属性选择器） | 纯 CSS | ✅ **能** |
| **JS 对象**（运行时注入变量） | JS | ✅ 能，但依赖脚本执行 |
| **构建期常量**（Sass 变量 / 构建产物） | 编译产物 | ❌ **不能** |

**第一行是默认答案**，而它需要**主题在 CSS 里**，不在 JS 里。

**⚠️ 这与第 2 章 §2.2 的载体判据是同一条**：**Sass 变量做不出运行时可换的主题。** 所以：

> **"我们的主题用 Sass 变量管理" 这句话，等价于"我们不支持运行时切换主题"。**

### 一条容易忽略的要求：首屏不能闪

**主题的值如果在脚本执行后才注入，首屏会出现"闪一下"**（先默认色，再变色）。

**所以主题的默认值必须**：

| 要求 | 原因 |
|---|---|
| **写在与主样式同一份 CSS 里**（或更早） | 首屏就有正确的值 |
| **不依赖 JS 计算** | 脚本执行晚于首次渲染 |
| **用户的偏好在构建期无法知道时** | 需要"先按系统偏好给值，再用脚本纠正" |

**第二、三行合起来说明**：**"跟随系统深色模式"不能完全靠 JS**。而 **CSS 中能否直接读系统偏好**取决于媒体查询能力 —— **本章不给具体语法**（那属于 `L4` 之外的范围）。

## 3.3 迁移路径：先建边界，再换实现

`D4.L4.02`。样式方案迁移是实践里最容易失败的一类改造，而失败点几乎总在**顺序**上。

### 三种典型场景与一个共性

| 场景 | 表面看是 | 实际是 |
|---|---|---|
| CSS-in-JS → CSS Modules | 换写法 | **换"样式在哪计算"** |
| 传统 CSS → 原子化 | 换写法 | **换"样式写在哪"** |
| 组件库 A → B | 换库 | **换"变量归属"** |

**⭐ 共性**：

> **迁移不是"把 A 的写法改成 B 的写法"，而是"移动一条边界"。**

**而边界移动是可以分阶段的** —— 这正是迁移能做成的前提。

### 四个阶段（顺序不可交换）

| 阶段 | 做什么 | 关键约束 |
|---|---|---|
| **① 建映射层** | 组件库变量 → 你的语义层（单向，第 2 章 §2.5） | **不改任何视觉** |
| **② 收敛 Token** | 把散落的硬编码全部收到语义层 | **仍不改视觉** |
| **③ 逐组件迁移** | 新旧并存，按组件切 | **同一元素上不允许两套方案** |
| **④ 删旧** | 移除旧方案与映射 | —— |

**⭐ 第 ① ② 阶段的"不改任何视觉"是最关键的设计**：

**因为它们把"一次大改造"拆成了"两次纯重构 + 一次真改造"**。而**纯重构是可以靠视觉回归验证的**（`D5` 第 2 章 §2.5）。

**反过来做（直接开始改组件）**：**视觉变化与结构变化同时发生** —— 一旦出问题，**无法判断是"迁移改错了"还是"迁移本来就该这样"**。

**这与 `D3` 第 6 章 §6.3 的"只换转译层是低风险迁移"是同一条策略**：**先换不影响产物的层。**

### 第三阶段的硬规则

> **同一个元素上，不允许两套样式方案同时生效。**

**为什么必须是硬规则**：

| 情况 | 结果 |
|---|---|
| 旧的 CSS 规则 + 新的原子类同时命中 | **优先级打架**，而且**结果依赖加载顺序**（第 1 章 §1.9 已证明顺序不可靠） |
| 旧的 CSS-in-JS + 新的 CSS Modules 同时作用 | **两处都能改同一个属性**，改哪边都不确定 |

**所以"逐组件迁移"的粒度必须是"组件"，不是"属性"** —— **一个组件迁完，它的旧样式必须同时删掉。**

**这条与 `D5` 第 3 章 §3.4 的"门禁只有阻断与不卡"是同一种思路**：**中间态要有明确的边界，否则它会长期存在。**

### 并存期的成本

**必须承认**：**新旧并存期是有成本的**。

| 成本 | 来源 |
|---|---|
| **两套依赖** | 构建配置要同时支持两套（体积与时间） |
| **两套心智** | 新人要学两种写法 |
| **两套检查** | Lint 规则要覆盖两种 |
| **映射层维护** | ① 阶段建的映射要跟两边一起变 |

**所以并存期应当被明确限定**：

| 做法 | 效果 |
|---|---|
| 不设期限 | 并存期变成永久态 |
| **设期限 + 追踪进度** | 有收敛压力 |
| **设"禁止新增旧写法"的 Lint 规则** | **最有效** —— 它让旧方案的数量只减不增 |

**第三行是本章最可操作的一条**：**迁移的完成速度不取决于"迁得多快"，而取决于"旧方案是否还在增长"。**

**这与 `X1` 第 1 章 §1.5 的"模板退化成 N 份副本"是同一个机制**：**只要新入口还开着，旧的东西就永远清不完。**

### 回滚能力

**每个阶段都应当可以单独回滚**：

| 阶段 | 回滚方式 |
|---|---|
| ① 映射层 | 删掉映射（视觉不变） |
| ② Token 收敛 | 值没变，可保留 |
| ③ 组件迁移 | **按组件回滚**（所以粒度要小） |
| ④ 删旧 | **不可回滚** → 必须放在最后，且要在稳定期之后 |

**第四行的"不可回滚"值得强调**：**删旧的时点，应当是"旧方案已无引用且已稳定运行一段时间"之后** —— 而不是"最后一个组件迁完的那天"。

## 3.4 原子化的工程约束

`D4.L4.03`。第 1 章 §1.7 已给出"零运行时"的必然代价。这一节把它展开成**三条会实际卡住你的约束**。

### 约束一：类名必须可被静态扫描

**这是"构建期生成"的直接后果**（第 1 章已核验：官方说它**扫描源码中的类名 → 生成样式 → 写入静态 CSS**）。

| 推论 | 现象 |
|---|---|
| 拼出来的类名不生效 | `bg-${color}-500` 扫描不到 |
| **后端 / CMS 下发的类名不生效** | 那些字符**不在源码里** |
| 需要"安全名单" | 把可能的组合写进源码让扫描看见 |
| **可选值的数量决定产物体积上限** | 因为**所有用到的组合都必须预先出现** |

**⭐ 第四行值得单独说**：**原子化的产物大小不与"你写了多少类名"成正比，而与"源码里出现过多少不同的类名"成正比。**

**所以"支持任意值"（如 `p-[13px]`）会同时带来两个后果**：

| 后果 | 说明 |
|---|---|
| 可选值集合失去边界 | **每个新值都产生一条新规则** |
| 设计尺度失效 | 因为"任何值都可以" |

**这直接引出约束二。**

### 约束二：设计尺度必须闭合

**原子化的收益之一是"样式不可能写到一半"**（第 1 章 §1.7）—— 而它成立的前提是**可选值有限**。

| 尺度状态 | 原子化效果 |
|---|---|
| **闭合**（间距只有 4/8/12/16…） | ✅ 天然一致 |
| **半开放**（允许少量任意值） | ⚠️ 需要纪律 |
| **完全开放**（任何值都允许） | ❌ **退化成内联样式**，只多了个语法 |

**判据很简单**：

> **你能枚举出「这个属性允许的全部取值」吗？**

**能枚举 → 原子化有收益；不能 → 它只是个更长的 `style` 属性。**

**这与第 2 章 §2.2 的 Token 判据是同一条**：**Token 的价值在"值要能被换掉"，原子化的价值在"值只能是这些"。** 两者都要求**取值集合是明确的**。

### 约束三：抽象的时机变了

**这一条容易被忽略，但它影响代码组织**。

| 方案 | 抽象的触发点 |
|---|---|
| 传统 CSS | **先写样式**，发现重复后抽成类，再抽成组件 |
| **原子化** | **样式就在元素上** → 重复是"一长串类名的重复" |

**后果**：

> **在原子化里，"重复三次再抽象"这条原则必须更严格执行** —— 因为**过早抽象会把"外观"固化成"组件 API"**。

**具体的失败形态**：看到三个地方都有 `p-4 rounded shadow`，立刻抽成 `<Card>`。**而这三个地方只是"碰巧长得像"，语义并不相同。** 之后其中一个要改，你就得给 `Card` 加一个 prop —— **而那个 prop 是"外观差异"，不是"语义差异"**。

**这与 §3.1 的"暴露值而不是结构"是同一个陷阱的两面**：**把外观差异做成组件参数，等于把外观变成了接口。**

### ⭐ 性能边界：一次失败的核验，与一个重要的发现

**`D4.L4.03` 的标题含"性能边界"。这一小节记录核验过程与结果，因为结果本身改变了写法。**

#### 想核什么

流行说法是：**"复杂选择器更慢，因为浏览器自右向左匹配，最右侧的选择器决定匹配成本"**。按这个说法，**原子化的单类选择器"更简单所以更快"**。

#### 核验结果

| 尝试 | 结果 |
|---|---|
| `web.dev`（"减少样式计算的复杂度"） | **超时** |
| `web.dev`（"推迟未使用 CSS"） | **超时** |
| `developer.chrome.com`（Lighthouse Unused CSS） | **超时** |
| `developer.chrome.com`（选择器性能博客） | **超时** |
| **MDN「Performant CSS」（2025-12-19 修订）** | ✅ 抓到 |

#### 发现：MDN 的官方指南并不支持那个流行说法

| 流行说法 | MDN 该页的实际表述 |
|---|---|
| "浏览器自右向左匹配选择器" | **全页没有任何匹配方向的内容** |
| "复杂选择器 → 匹配变慢" | 官方归因是 **"增加文件体积"** 与 **"选择器的解析时间"** |
| "通配符选择器匹配慢" | 官方对 `body *` 的反对理由是 **"作用到过多元素"**（大量元素被赋 `display: flex` 会形成大量布局上下文），**不是"匹配慢"** |

**MDN 该页明确把选择器优化的理由落在**：

> "这不仅增加文件体积，也增加那些选择器的**解析时间**。"

**以及可维护性**（"低特异性更容易覆盖"）。

#### 一个必须承认的结论

> **"复杂选择器更慢"这个说法，在我能核到的官方文档里找不到出处。**

**而且更重要的是**：MDN 该页**专门提醒过"别把流行说法挂到本文头上"** —— 它没有"right-to-left matching""属性选择器更慢"这些论断。

**⚠️ 这不等于"那个说法一定错"** —— 引擎实现确实有各自的匹配策略。但：

1. **它没有被我能核到的官方文档支持**；
2. **所以本章不用它作为论证基础**。

#### 那么原子化的性能论证该落在哪

**只能落在那两条有官方依据的路径上**：

| 路径 | 官方依据 | 对原子化的含义 |
|---|---|---|
| **① 文件体积** | 选择器复杂度 → 文件体积 ↑ | 原子化的产物大小**与用到的不同类名数量成正比**（§3.4 约束一） |
| **② 解析成本** | **"所有样式都会被解析，无论是否在布局与绘制中被使用"**（官方原文） | **产物里"没被用到的规则"是要付代价的** → 又回到"清理" |

**② 的官方原文很关键**：

> "**All styles get parsed, whether they are being used during layout and painting or not**, so it can speed up page rendering to get rid of unused ones."

**所以"原子化省体积"这个收益，必须靠"只生成用到的类"来实现** —— 而那正是"构建期扫描"在做的事。**这条链条是闭合的**：

```
扫描源码 → 只生成用到的类 → 产物里没有冗余规则 → 解析成本不浪费
```

**而它的弱点是**：**一旦"用到的类"判断错了**（动态拼类名、后端下发），**产物里就会缺规则**（缺样式），或者为了保险而**允许任意值**（产物膨胀）。**两种失败是同一个机制的两端。**

#### 两处有官方依据的常见手段

**MDN 该页还给两个手段，且对其中一个给了很明确的边界**：

| 手段 | 官方表述 |
|---|---|
| **`will-change`** | **"作为最后手段使用，用来处理「已经存在」的性能问题。不应被用来「预期」性能问题。"** |
| **`contain` / `content-visibility` / `contain-intrinsic-size`** | 让浏览器**只对 DOM 的有限部分**重算布局/样式/绘制；`content-visibility` 让容器**在被需要前不布局与渲染**；`contain-intrinsic-size` 提供**占位尺寸**以避免滚动条跳动 |

**第一行的措辞值得记住**：**`will-change` 是"救火"，不是"防火"。** 而它常被当成"加上总没坏处"的优化 —— **官方明确否定了这个用法。**

#### 一处官方坦承的困难

**关于清理未使用 CSS，MDN 承认没有好办法**（它引用了外部文章的观点）：

> 这在大代码库里是个**很难解决的问题**，**没有银弹**能可靠地找出并删除未使用的 CSS。

**这与第 2 章 §2.4 的判据是一致的**：**工具不可靠，所以用"有没有主人"这个不需要工具的判据。**

### 原子化的收益与代价，最终清单

| 维度 | 收益 | 代价 |
|---|---|---|
| **产物体积** | 只包含用到的类 | **规则条数多、每条只有一条声明**；允许任意值就膨胀 |
| **构建时间** | —— | **需要扫描全部源码** |
| **解析成本** | 无冗余规则（条件：清理到位） | 规则**条数**通常多于手写 CSS |
| **可维护** | 改样式只影响一处；删掉就没 | **HTML 变长**；语义从类名消失 |
| **一致性** | 可选值有限 → 不可能写歪 | **要求设计尺度闭合**（约束二） |
| **动态能力** | —— | **构建期看不见的类名不生效**（约束一） |

**⚠️ 关于"规则条数"这一行**：它是**机制判断**（原子化的产物形态是"很多单声明规则"），**不是官方数据**。之所以列出来，是因为**它解释了"为什么原子化不一定减少 CSS 字节数"** —— 它减的是**冗余声明**，不是**规则条数**。

## 3.5 治理动作：六个判定阈值

| # | 现象 | 判定阈值（起点值） | 动作 | 依据 |
|---|---|---|---|---|
| 1 | Token 无法单独分发 | **Token 层出现了组件/页面的引用** | 反向依赖 → 拆掉；Token 层只读 | §3.1 |
| 2 | 组件库升版就破坏宿主 | **宿主的选择器命中了组件内部结构** | 内部结构已成公共 API → 改为**暴露值** | §3.1 |
| 3 | 新增一个品牌要新增一份 CSS | **品牌数 N → CSS 文件 N 份** | 维度未正交拆分；应只加一段变量赋值 | §3.2 |
| 4 | 切主题时闪一下 | **主题值靠脚本注入** | 默认值须写进同一份 CSS；不依赖 JS 计算 | §3.2 |
| 5 | 迁移做了一年还在做 | **旧写法仍在新增** | 加"禁止新增旧写法"的 Lint 规则 —— 决定完成速度的是**旧方案是否还在长** | §3.3 |
| 6 | 原子化产物比手写还大 | **源码里允许任意值（如 `p-[13px]`）** | 收紧设计尺度；任意值 = 每个值一条新规则 | §3.4 |

### 三条使用说明

**① 阈值 2 与 3 都是"边界没设好"的后果。**

一个让内部结构成为公共 API，一个让维度没拆开。**它们都不会报错**，只会让下一次改动变贵。

**② 阈值 5 的判据与直觉相反。**

直觉是"迁快点就行"，实际是**"把入口关掉"**。**只要还能写旧写法，新写法就不会成为默认。**

**③ 阈值 6 值得先算一次。**

**如果原子化后产物更大，那收益只能来自"一致性"，不能宣称"体积"** —— 而这份收益是否值得，取决于团队规模与设计尺度稳定性（第 1 章 §1.7 的判据）。

### 什么时候"不该建设计系统"

| 情况 | 为什么 |
|---|---|
| **只有 1 个产品且短期不会扩** | 四层架构的维护成本摊不平 |
| **设计尺度还没定** | 会把"临时值"固化成 Token，之后难改 |
| **没有跨项目复用需求** | 组件库的"自足性"要求会带来大量额外抽象 |
| **团队里没有人负责它** | 设计系统是**有主的资产**，无主会腐化得比普通代码更快 |

**第四行值得强调**：**设计系统横跨设计与工程**，它比普通代码更需要明确的 owner。**没有 owner 的设计系统，会在半年内变成"一个没人敢改的组件库"。** 这与 `X1` 第 1 章 §1.5 的"模板没人维护"是同一个失败模式。

## 3.6 动手

| 任务 | 验收 |
|---|---|
| 画出你项目的四层，标出每层的依赖 | 找出所有"下层依赖上层"的边 |
| 查一次 Token 层是否被写过 | 若有，说出它破坏了什么 |
| 列出组件库对外暴露的全部接口 | 分成"值"与"结构"两类，说出结构类能不能收回 |
| 查一次宿主有没有选择器命中组件内部 | 若有，说出组件库下次重构会遇到什么 |
| 数一次你的主题维度 | 算出组合数，说出你是"N 份 CSS"还是"N 段变量" |
| 查一次主题默认值在哪 | 说出首屏会不会闪 |
| 给你正在做的迁移划分四个阶段 | 说出第 ①② 阶段能不能做到"不改视觉" |
| 查一次是否允许两套方案作用于同一元素 | 若有，说出结果依赖什么 |
| 查一次有没有"禁止新增旧写法"的规则 | 若没有，说出旧方案的数量会怎么变 |
| 查一次你是否用了 `will-change` | 若是"预防性"加的，说出官方对它的定性 |
| 统计原子化产物里有多少条规则 | 说出它与"用到的不同类名数"是否对得上 |

**进阶挑战**（任选一项）：

1. **做一次"契约覆盖度"审计**：列出宿主想改但组件库没提供变量的点。**每一个都是宿主将来破坏结构的入口。**
2. **把多主题改成正交**：把"按组合生成"改成"按维度叠加"，验证新增品牌只需加一段变量。
3. **重算一次原子化的账**：分别统计"冗余声明减少"与"规则条数增加"，给出**你项目里的真实净值**（而不是引用别人的结论）。

## 3.7 本章常见误区

| # | 误区 | 纠正 |
|---|---|---|
| 1 | "Token 层可以随便引用" | 一旦 Token 引用了组件，它**无法独立分发** → 多项目共用失败 |
| 2 | "页面里改个变量没关系" | 那让主题**不可预测**（谁最后写谁赢）。Token 层应当是**只读的** |
| 3 | "组件库越封闭越稳" | 全封闭 → 宿主稍有不同就只能重写组件 |
| 4 | "把内部类名暴露出去，定制最灵活" | **内部结构会变成公共 API**，从此不能改 |
| 5 | "暴露变量和暴露类名差不多" | 变量是**值**（内部可重构），类名是**结构**（不能重构） |
| 6 | "给了变量就够定制了" | 若 Token **没覆盖全部可定制点**，宿主会被迫破坏契约。这是**契约覆盖度**问题，不是宿主的问题 |
| 7 | "主题切换会重算所有样式" | 变量重赋值**只影响用到该变量的元素**；且**成本与规则条数无关，只与变量数量有关** |
| 8 | "每个主题生成一份 CSS 更简单" | 体积 N 份，且切换时**要重新解析样式表 → 可见闪烁** |
| 9 | "多主题就是 24 份 CSS" | 那是把**维度当组合**。应正交拆开：主题 / 品牌 / 密度各贡献一段变量 |
| 10 | "新增品牌要新建一份样式" | 那说明**维度没拆开**。正确形态是"新增一段变量赋值" |
| 11 | "主题用 Sass 变量管就行" | 等价于**不支持运行时切换**（第 2 章 §2.2 已证明） |
| 12 | "主题值可以等 JS 算出来再注入" | 首屏会闪。默认值必须**写在同一份 CSS 里**，不依赖脚本 |
| 13 | "直接从改组件开始最快" | 会让**视觉变化与结构变化同时发生** → 出问题无法归因 |
| 14 | "先建映射层是浪费时间" | 那一步**不改任何视觉**，所以能靠视觉回归验证 —— 它是**把大改造拆成纯重构**的关键 |
| 15 | "新旧可以慢慢混，一个属性一个属性改" | **同一元素上不允许两套方案**，否则结果依赖加载顺序 |
| 16 | "并存期拖长点没关系" | 它有**四类成本**（依赖 / 心智 / 检查 / 映射维护），会变成永久态 |
| 17 | "迁移快慢取决于迁得有多快" | 取决于**旧方案是否还在增长** → 加"禁止新增旧写法"的规则 |
| 18 | "原子化的类名可以随便拼" | 构建期静态扫描 → **拼出来的、后端下发的都不生效**（第 1 章 §1.7） |
| 19 | "支持任意值更灵活" | 每个新值都是**一条新规则**，且**设计尺度失效** → 退化成内联样式 |
| 20 | "原子化一定能减小体积" | 它减的是**冗余声明**，不是**规则条数**；规则条数通常更多。**允许任意值时会更大** |
| 21 | "原子化的性能优势来自选择器更简单" | **本章的核验没能支持这个说法**（§3.4）。能站住的路径只有"体积"与"解析成本" |
| 22 | "浏览器自右向左匹配选择器，所以复杂选择器慢" | **MDN 的 CSS 性能指南全页没有这个内容**；它把成本归因于**文件体积与解析时间** |
| 23 | "通配符选择器慢" | MDN 反对 `body *` 的理由是**"作用到过多元素"**（大量 `display:flex` 形成大量布局上下文），**不是匹配慢** |
| 24 | "未使用的 CSS 不影响性能" | **"所有样式都会被解析，无论是否在布局与绘制中被使用"**（官方原文） |
| 25 | "有工具能可靠地找出未使用 CSS" | MDN 坦承**没有银弹**。这就是"有没有主人"判据存在的理由 |
| 26 | "`will-change` 加上总没坏处" | 官方：**最后手段**，用于**已存在**的问题；**不应被用来预防** |

## 3.8 D4 领域收束

D4 三章讲的是**一件完整的事**：

| 章 | 回答的问题 | 核心机制 |
|---|---|---|
| **第 1 章** | 选什么？ | **三个维度**（生成时刻 / 类名唯一性 / 语法扩展者）；**只有第一个给用户带来成本** |
| **第 2 章** | 怎么工程化？ | **顺序就是语义**；**载体决定能力**（Sass 变量不能换主题）；**缩放系数只能有一个来源** |
| **第 3 章** | 怎么共用与替换？ | **暴露值不暴露结构**；**主题是值的集合**（正交拆分）；**迁移是移动边界** |

### 一条贯穿三章的主线

**三章反复出现的是同一个判据**：

> **这个决定，会让"以后换掉它"变容易还是变难？**

| 章 | 它的表现 |
|---|---|
| 第 1 章 | 选 CSS-in-JS 之前问"值动态还是规则动态" —— 前者不必付运行时代价 |
| 第 2 章 | 用 Sass 变量做 Token → 换不了主题；组件库双向映射 → 换不了库 |
| 第 3 章 | 暴露内部类名 → 组件库不能重构；维度不拆 → 新增品牌要新增一份 CSS |

**所以 D4 全领域的判据可以压成一句话**：

> **样式的价值不在"现在写得多好"，而在"换一个主题、换一个库、换一个方案时，要改多少地方"。**

### 一处必须记住的核验教训

**§3.4 那一次"失败的核验"值得留在领域收束里**，因为它是 D4 最重要的一课：

> **一个说法被很多人重复，不等于它有出处。**

**"复杂选择器更慢"这条说法，在我能核到的官方文档里找不到支持** —— 而 MDN 恰恰把它归因于**体积与解析时间**。

**这不是说那个说法一定错**，而是说：**如果拿它当论证基础，你的结论会建在一个查不到出处的前提上。** 而在样式领域，这类"流传很广但没有出处"的说法特别多（第 1 章的"PostCSS 是预处理器"、第 2 章的"CSS 合并不一定更好"都是同类）。

### D4 与相邻领域的分界

| 领域 | 它负责的部分 |
|---|---|
| **D4（本领域）** | 样式的**方案、工程化与架构** |
| **D3** | 样式的**构建管道**（`cssCodeSplit`、压缩、提取时机） |
| **D5** | 样式变更的**验证**（视觉回归，第 2 章 §2.5） |
| **D6** | 样式的**线上代价**（缓存、CDN、Core Web Vitals） |
| **X2** | **同构渲染**下样式的收集与注入（服务端渲染特有） |
