# 第一部分 · 走进工程世界

## 7.1 命令行：程序之间的管道

### 它本质上是什么

命令行不是"另一种操作方式"，而是一个**统一的进程编排接口**。它由四个约定构成：

| 约定 | 含义 |
|---|---|
| **标准输入 / 输出 / 错误**（stdin / stdout / stderr） | 每个程序都有这三条流 |
| **管道** | 把上一个程序的 stdout 接到下一个程序的 stdin |
| **退出码** | 0 表示成功，非 0 表示失败 |
| **环境变量** | 进程启动时继承的一组键值 |

**为什么前端必须懂它**：npm、构建工具、测试框架、CI 流水线——**全都是命令行程序**。CI 脚本不过是这四条约定的组合。

### 管道与重定向：组合能力从哪来

```bash
npm run build 2>&1 | tee build.log      # 把 stdout 与 stderr 合并后同时输出与写文件
grep -rn "console.log" src/ --include="*.ts"   # 递归查找
cat list.txt | sort | uniq -c | sort -rn       # 管道串联：计数并按次数排序
```

| 符号 | 作用 |
|---|---|
| `>` / `>>` | 覆盖 / 追加 stdout 到文件 |
| `2>` | 重定向 stderr（文件描述符 2） |
| `2>&1` | 把 stderr 并入 stdout |
| `\|` | 管道 |
| `&&` / `\|\|` | 依据**退出码**决定是否执行下一条 |

**退出码是 CI 判断成败的唯一依据**：`npm run build && npm test` 只有在 build 退出码为 0 时才继续。所以"命令明明报错了但 CI 显示绿灯"，多半是脚本吞掉了退出码（例如管道最后一环是 `tee`）。

### 环境变量与 `PATH`：为什么能直接敲 `node`

```bash
echo $PATH            # 一串用冒号分隔的目录
which node            # 找出实际执行的是哪一个
```

**Shell 查找命令的机制**：按 `PATH` 里的目录**顺序**逐个查找同名可执行文件——所以 `PATH` 的顺序决定了"同名命令用哪个"，这也是 nvm 能通过改 `PATH` 切换 Node 版本的原因。

### 引号：脚本出错的高频原因

| 写法 | 行为 |
|---|---|
| `"$var"` | 做变量替换，**且变量值整体作为一个参数** |
| `'$var'` | **完全不替换**，原样传入 |
| `$var`（不加引号） | 做替换，**并按空白拆分成多个参数** |

第三种是隐患：路径含空格时会被拆成两个参数。**规则：变量一定加双引号**。

### 命令的分类视角

| 用途 | 命令 |
|---|---|
| 导航 | `pwd` `cd` `ls -la` |
| 文件 | `cp` `mv` `rm` `mkdir -p` `touch` |
| 查找 | `find` `grep -r` `rg`（更快） |
| 查看 | `cat` `head` `tail -f` `less` |
| 进程 | `ps` `top` `kill` `lsof -i :3000`（查端口占用） |

`lsof -i :3000` 值得单独记住——"端口被占用"是前端最高频的环境问题，它的机制是**操作系统同一端口只能被一个进程监听**。

## 7.2 Node.js 与版本管理：为什么必须锁版本

### Node 是"把事件循环搬到服务端"的产物

D0 第 3 章 §3.6 讲的事件循环是**运行时**的行为，不是语言语法。Node 实现的是同一套模型（V8 引擎 + 标准库 + 事件循环），只是把"渲染"换成了"文件与网络 I/O"。这也解释了为什么 `Promise`、微任务、`async/await` 的行为在两个环境里一致——它们由 ECMA-262 定义，与宿主无关。

### 版本差异是真实的风险

| 风险面 | 说明 |
|---|---|
| 语言特性 | 新语法靠 V8 升级才可用 |
| 内置模块行为 | 标准库接口会随主版本变化（弃用与移除） |
| 工具链要求 | 构建工具、测试框架会声明最低 Node 版本 |
| 捆绑的包管理器 | Node 发布包自带的 npm 版本随 Node 变化 |

### Node 的版本惯例不是 SemVer

| 发布线 | 含义 |
|---|---|
| **偶数主版本**（如 20、22） | 进入 **LTS**（长期支持），适合生产 |
| **奇数主版本**（如 21、23） | Current，用于尝鲜，不承诺长期维护 |

注意：这是 Node 项目自己的发布惯例，**与 npm 包的 SemVer 是两回事**。

### 三种"锁版本"的手段，强度不同

| 手段 | 作用 | 是否强制 |
|---|---|---|
| `.nvmrc` | 声明"本项目用哪个 Node"，供 nvm / fnm 等**手动或自动切换** | 否 |
| `package.json` 的 `engines.node` | 声明要求 | **默认只警告**，除非开 `engine-strict` |
| `package.json` 的 `packageManager` | 声明包管理器与版本（配合 Corepack 强制） | 是（启用后） |

**"我明明写了 `engines` 为什么还是跑挂了"** 的答案就在第二行：它默认不阻止安装。所以团队一致性要靠 **`.nvmrc` + CI 中显式指定 Node 版本**双保险。

**这条直连 D1 领域**：`D1.L3.01`（环境统一：EditorConfig、团队 VSCode 配置、`.nvmrc`）正是把它制度化。

## 7.3 编辑器与 VSCode：把约定前移到编辑期

### 编辑期的位置：反馈越早越便宜

D0 第 5 章提过质量门禁的分层：**编辑器 → pre-commit → CI → 发布前**。编辑器是第一层，它的价值是**把问题暴露在"还没提交"的时候**——此时成本最低。

### 项目级配置为什么要进版本库

| 文件 | 作用 |
|---|---|
| `.vscode/settings.json` | 团队共享的设置（格式化器、保存时动作） |
| `.vscode/extensions.json` | 推荐插件清单（新人打开项目即被提示安装） |
| `.editorconfig` | **跨编辑器的**基础约定（缩进、行尾、字符集） |

`extensions.json` 常被忽略但收益很高：**新人第一天的环境差异是团队协作最大的隐性成本**。

### LSP：能力与编辑器解耦

**语言服务协议**（Language Server Protocol）把"语言能力"从编辑器里抽出来变成独立进程，编辑器只负责 UI。于是同一个 TypeScript 语言服务可以同时服务于多种编辑器——**这解释了"为什么换编辑器也有同样的提示"**，也解释了为什么语言服务会成为独立生态。

### 与D0 第 5 章的接回

VSCode 的调试面板之所以能打断点、看调用栈、读作用域，靠的是与浏览器（或 Node）之间的**调试协议**——它和你在 DevTools 里用的机制是同一类。**调试能力是协议能力，不是编辑器能力。**

## 7.4 Git：内容寻址的版本控制

### 核心机制：Git 存的是快照，用内容哈希命名

这是理解 Git 一切行为的地基。Git 的四个对象类型构成一棵可寻址的树：

| 对象 | 存什么 |
|---|---|
| **blob** | 文件**内容**（不含名字） |
| **tree** | 目录结构（文件名 → blob / 子 tree） |
| **commit** | 指向一个 tree + 父提交 + 作者与信息 |
| **tag** | 指向某个对象的带注释引用 |

两个直接推论：

- **对象名由其内容算出**（内容哈希）→ **内容相同就是同一个对象**，天然去重。同一份内容出现在 100 个文件里也只存一份。
- 哈希是**内容的函数** → 内容一变，对象名就变，指向它的 commit 也会变。这正是"rebase 会改写历史"的机制根源。

### 三个区域与三条命令

```text
工作区（你编辑的文件） → 暂存区（index） → 仓库（对象库）
                     add                commit
```

| 命令 | 机制上的动作 |
|---|---|
| `git add` | 把**当前文件内容**写入 index（所以 `add` 之后又改了文件，需要再 `add`） |
| `git commit` | 把 index 固化为一个 commit 对象，并移动当前分支指针 |
| `git status` | 比较三个区域的差异 |

### 分支是指针，所以建分支几乎零成本

分支不是"目录拷贝"，而是一个**指向 commit 的引用**（就是一个文件里存了一行哈希）。所以：

- 建/删分支是**常数时间**操作。
- `HEAD` 也是引用，默认指向当前分支；直接指向某个 commit 时叫**游离头指针**（detached HEAD）。

### `merge` 与 `rebase`：一个保留历史，一个重写历史

| | `merge` | `rebase` |
|---|---|---|
| 历史形态 | 保留分叉（产生合并提交） | 变成一条直线 |
| 是否创建新 commit | 创建合并提交 | **重写已有 commit**（哈希全变） |
| 何时适用 | 已共享的分支 | **仅限本地未推送的提交** |

**"已推送的提交不要 rebase"** 的理由就在第二行：别人的仓库里还是旧哈希，你们的历史会对不上。需要撤销已推送的内容，应该用 `revert`（生成一个反向提交，历史仍然线性可追溯）。

### `reset` 的三种模式：它重置的是"哪一层"

| 模式 | 移动分支指针 | 重置 index | 重置工作区 |
|---|---|---|---|
| `--soft` | 是 | 否 | 否 |
| `--mixed`（默认） | 是 | **是** | 否 |
| `--hard` | 是 | 是 | **是**（修改会丢） |

按"三个区域"看这张表就非常直观：`reset` 是在**往回拨这三个区域的状态**。

### 冲突的本质

冲突不是"Git 不会合并"，而是**同一文件的同一区域被两边各自修改**，Git 无法替你判断保留哪个。所以：

- 冲突范围越小的改动，越不容易冲突 → **提交粒度小、推送频繁**能显著降低冲突成本。
- 冲突标记 `<<<<<<<` / `=======` / `>>>>>>>` 只是普通文本，手动编辑即可。

### 行尾符：一个纯粹由工具链差异引起的问题

这是跨平台协作最典型的"看起来像内容全变了"的问题：

| 配置 | 行为 |
|---|---|
| `core.autocrlf=false`（默认） | 不做任何转换，原样存取 |
| `core.autocrlf=true`（Windows 常见） | 检出时转 CRLF，提交时转回 LF |
| `core.autocrlf=input` | 只在提交时转 LF |

**症状**：`git status` 显示整个文件被修改，但 `git diff --stat` 的增删行数**完全对称**，逐行看却"没有变化"。原因是比较器把行尾符算进了差异。

**根治手段是 `.gitattributes`**（写进版本库、对所有人生效），例如统一为 LF：

```gitattributes
* text=auto eol=lf
*.png binary
```

**为什么必须用 `.gitattributes` 而不是靠 `core.autocrlf`**：前者是**仓库级约定**，会随代码一起分发给所有人；后者是**本机配置**，每个人各不相同——只要有一个人的配置不同，就会产生整文件级的假差异。

## 7.5 npm 与 `package.json`：声明、解析结果与实际安装

### 三层关系要先分清

| 层 | 文件 / 目录 | 角色 |
|---|---|---|
| **声明** | `package.json` | "我要什么"——**版本范围** |
| **解析结果** | lockfile | "实际装到了什么"——**精确版本 + 完整性哈希 + 依赖树结构** |
| **实现** | `node_modules` | 实际落盘的目录树 |

【现·1.3】原书第 1 章 §1.3 讲过 `package.json` 里与构建相关的字段（`sideEffects` / `exports` / `main` / `module` / `types`）。本节补齐**依赖管理**这一面。

### `npm install` 与 `npm ci` 的机制差异

| | `npm install` | `npm ci` |
|---|---|---|
| 依据 | `package.json` 的**范围**（可能重新解析） | **只依据 lockfile** |
| 是否改写 lockfile | **可能改写** | 不改写 |
| lockfile 与 `package.json` 不一致时 | 以 `package.json` 为准重新解析 | **直接失败** |
| 用途 | 本地开发、新增依赖 | **CI / 部署** |

**"CI 必须用 `ci`"不是风格要求**：`install` 有可能悄悄升级依赖，让"同一个 commit"在不同时间构建出不同结果——那就等于放弃了可复现性。（其他包管理器的等价命令：`pnpm i --frozen-lockfile`、`yarn --immutable`。）

### `scripts` 与它的 `PATH` 注入

```json
{
  "scripts": {
    "dev": "vite",
    "build": "tsc --noEmit && vite build"
  }
}
```

**为什么 `scripts` 里可以直接写 `vite`，而在终端里必须 `./node_modules/.bin/vite`？**

因为 npm 在执行脚本时，会把 `node_modules/.bin` **临时加到 `PATH` 最前面**（本章 §7.1 的查找机制）。这一条机制解释了：

- 本地安装的命令行工具为什么能在 `scripts` 里直接用；
- 为什么**全局安装的工具不该出现在 `scripts` 里**（CI 上没装就挂）。

`pre` / `post` 前缀可以定义生命周期钩子（如 `prebuild` 会在 `build` 前自动执行）。

## 7.6 依赖类型：三种声明，三种后果

| 字段 | 语义 | 装到生产环境吗 |
|---|---|---|
| `dependencies` | **运行期需要** | 是 |
| `devDependencies` | 只在开发 / 构建 / 测试期需要 | 否（生产安装可跳过） |
| `peerDependencies` | **由宿主提供**（插件、组件库常用） | 由消费者的 `dependencies` 提供 |
| `optionalDependencies` | 可选，安装失败不阻断 | 视情况 |

### 放错位置的后果

| 错误 | 后果 |
|---|---|
| 把构建工具（webpack、vite）放 `dependencies` | 生产镜像变大、攻击面变大、启动时无谓安装 |
| 把关卡检查类工具放 `dependencies` | 同上，且 CI 与生产环境耦合 |
| 把运行期用到的库放 `devDependencies` | 生产安装后模块缺失（`Cannot find module`）——**本地永远复现不出来** |
| 组件库漏写 / 写错 `peerDependencies` | 消费者装出**重复实例**：React Hooks 报错、单例失效（详见 D2 的 `D2.L3.05`） |

**判断方法**：问一句"**这个东西在应用启动后、处理请求时还需要吗**"。需要 → `dependencies`；只在"我写代码 / 打包时"需要 → `devDependencies`。

### 版本范围与它的代价

| 写法 | 允许范围 |
|---|---|
| `1.2.3` | 只允许这一版 |
| `~1.2.3` | 允许 `1.2.x` |
| `^1.2.3` | 允许 `1.x.x`（**默认且最常用**） |
| `1.x` / `*` | 更宽甚至任意 |

**`^` 的代价**：同一个 `package.json`，在不同时间安装可能得到不同版本——**这正是 lockfile 存在的理由**（本章 §7.7）。

当需要强制统一某个传递依赖版本时，用 `overrides`（npm）/ `resolutions`（yarn）/ `pnpm.overrides`。

## 7.7 lockfile：可复现构建的最小条件

### 它解决的是"同一份代码两次构建结果不同"

| 没有 lockfile | 有 lockfile |
|---|---|
| 每次安装按范围重新解析 → 可能装到新版本 | 按解析结果精确安装 |
| 本地与 CI 可能不同 | 本地与 CI 一致 |
| 线上问题无法复现（不知道当时装的是哪版） | 可复现 |

### 它记录了什么

| 内容 | 作用 |
|---|---|
| 精确版本号 | 保证装到同一版 |
| **完整性哈希**（integrity） | 校验下载到的内容未被篡改 |
| 完整依赖树结构 | 保证嵌套关系一致（§6 的"提升"与"幽灵依赖"由此确定） |

### 三条实践原则

1. **必须提交进版本库**——它是可复现性的一部分，不是本地产物。
2. **不要手改**——冲突时用命令重新生成（删掉重装或按包管理器提示处理）。
3. **两边必须同步修改**：新增依赖后，`package.json` 与 lockfile 要一起提交；只提交一个会让 CI 失败（`npm ci` 会检测到不一致）。

### 与后续领域的接线

| 接点 | 说明 |
|---|---|
| **D3 构建** | Vite 依赖预构建的**缓存键包含 lockfile** —— 改 lockfile 会让预构建缓存失效，重新预构建 |
| **D2 包治理** | `D2.L2.08`（lockfile 一致性与 CI）正是本节的展开 |
| **D6 交付** | CI 中的安装步骤必须用冻结模式，否则制品不可复现 |

## 7.8 为什么需要工程化

### 三个维度，三种症状

| 维度 | 典型症状 | 工程化手段 |
|---|---|---|
| **可维护** | "这段代码不敢动" | 类型检查、测试、lint、语义化提交 |
| **可协作** | "我这儿能跑" | lockfile、`.nvmrc`、`.editorconfig`、`.gitattributes`、规范与 CI 卡点 |
| **可交付** | "上线靠人手动点" | CI/CD、制品、内容哈希与缓存策略、回滚能力 |

### 工程化不是"工具越多越好"

它只有一件事：**把人的约定变成机器可执行的约束**。

回忆D0 第 5 章的四层门禁——**编辑器 → pre-commit → CI → 发布前**，越靠前越便宜。所以工程化的推进顺序不是"哪个工具流行先上哪个"，而是**按反馈成本从低到高逐层加约束**。

### 一个判据

> 一条规范如果只写在文档里、靠人记住，它一定会腐化。
> **只有被流水线卡住的规范才会被真正遵守。**

### 回到 D0 的起点

D0 第 1 章讲"页面怎么写"，本章讲"代码怎么进入协作与交付"。中间的六章分别交代了：**结构（1）、样式（2）、逻辑（3）、语言深水区（4）、浏览器与渲染（5）、网络与缓存（6）**。而下一个领域（D3 构建与打包）之所以是枢纽，是因为**它正好是"写代码"与"交付产物"的交汇点**——上游承接语言与模块，下游决定交付质量。

## 7.10 本章常见误区

| # | 误区 | 事实 |
|---|---|---|
| 1 | "命令行只是老式操作方式" | 它是统一的进程编排接口（三条标准流 + 管道 + 退出码 + 环境变量），CI 全靠它 |
| 2 | "管道和 `&&` 是一回事" | `\|` 传数据；`&&` / `\|\|` 依据**退出码**决定是否继续 |
| 3 | "命令报错了 CI 就会失败" | 只有退出码非 0 才算失败；管道末端的命令可能吞掉中间的错误 |
| 4 | "变量直接写就行" | 不加引号会按空白拆成多个参数；含空格的路径会出错 |
| 5 | "`.nvmrc` 会强制切版本" | 它只是声明，需要 nvm / fnm 等工具读取 |
| 6 | "写了 `engines` 就会拦住低版本 Node" | 默认只警告；要阻止需开 `engine-strict` |
| 7 | "Node 版本号是 SemVer" | 遵循 Node 自己的发布惯例（偶数 LTS / 奇数 Current），与包版本规则不同 |
| 8 | "编辑器配置是个人偏好" | `.vscode/` 与 `.editorconfig` 属于**团队约定**，应进版本库 |
| 9 | "Git 存的是差异链" | 存的是**快照**，用**内容哈希**寻址；内容相同即同一对象（天然去重） |
| 10 | "分支就是复制一份代码" | 分支只是**指向 commit 的指针**，建分支是常数时间操作 |
| 11 | "`merge` 与 `rebase` 效果差不多" | `rebase` **重写历史**（哈希改变），所以已推送的提交不能 rebase |
| 12 | "冲突是 Git 的缺陷" | 冲突表示同一区域被两边修改，Git 无法替你决定保留哪个 |
| 13 | "`git reset --hard` 和 `--soft` 差不多" | `--hard` 会**丢工作区修改**；三者分别重置"三个区域"的不同层 |
| 14 | "撤销已推送的提交用 reset" | 应改用 `revert`（生成反向提交，不重写历史） |
| 15 | "`git status` 显示变更就是内容变了" | 行尾符差异会导致**整文件级假差异**，`--stat` 会显示对称的增删行数 |
| 16 | "设了 `core.autocrlf` 就够了" | 它是**本机配置**，每人不同；仓库级根治要用 `.gitattributes` |
| 17 | "`npm install` 和 `npm ci` 等价" | `install` 可能改写 lockfile 并按范围重新解析；`ci` 只按 lockfile 装，不一致就失败 |
| 18 | "lockfile 是本地产物，可不提交" | 它承载可复现性；不提交等于放弃"同 commit 同结果" |
| 19 | "lockfile 冲突了手改一下就行" | 应删除或用命令重新生成，手改容易破坏完整性哈希与树结构 |
| 20 | "构建工具装 `dependencies` 也无所谓" | 会进生产环境：镜像变大、攻击面变大、无谓安装 |
| 21 | "类型定义放哪都行" | 类型与构建工具属**构建期**，应放 `devDependencies` |
| 22 | "组件库不用写 `peerDependencies`" | 漏写会导致消费者装出**重复实例**，引发 Hooks 报错与单例失效 |
| 23 | "`scripts` 里能用 `vite` 是因为全局装了" | 是 npm 把 `node_modules/.bin` 注入了 `PATH`；依赖全局安装的脚本在 CI 上会挂 |
| 24 | "工程化就是多装点工具" | 它是**把人的约定变成机器可执行的约束**，且应按反馈成本从低到高逐层加 |

| 76 | 4 | "每轮事件循环都会渲染" | 渲染由 refreshing 节奏决定，叫 rendering opportunity，**未必每轮发生** |
| 77 | 4 | "`setTimeout(fn, 0)` 是 0ms 后执行" | 嵌套超过 5 层时最小延迟被抬到 **4ms**；且它是下一个任务，要等微任务清空 |
| 78 | 4 | "`setTimeout` 适合做动画" | 它不参与渲染步骤；`requestAnimationFrame` 在 `update the rendering` 内、样式计算之前执行 |
| 79 | 4 | "`for...of` 能遍历任何对象" | 只有**实现可迭代协议**（`[Symbol.iterator]`）的才行；普通对象会抛 `TypeError` |
| 80 | 4 | "生成器函数一调用就开始执行" | 它只返回迭代器，函数体在首次 `next()` 才执行 |
| 81 | 4 | "`Promise.all` 失败后其他请求会被取消" | 不会。它只是立刻拒绝，其余 Promise 继续执行；停止需要 `AbortSignal` |
| 82 | 4 | "`Promise.all` 的结果顺序不确定" | 结果顺序与输入**一致**；`race` / `any` 才只给第一个 |
| 83 | 4 | "`Promise.race` 能实现超时取消 / Promise 可以被取消" | 规范层面**不可取消**；`race` 只停止**等待**，不中止**执行** —— 必须把信号传给执行者 |
| 84 | 4 | "`fetch` 遇到 404 会 reject" | 只在网络层失败时拒绝（含 CORS 被拒）；**4xx/5xx 是正常兑现** |
| 85 | 4 | "`fetch` 返回的就是数据" | 响应体是**流**，要再 `await r.json()`；且 body **只能消费一次** |
| 86 | 4 | "CORS 失败能从错误里看出原因" | 出于安全，只暴露为 `TypeError`，详情仅在控制台（第 6 章 §6.5 同一条） |
| 87 | 5 | "Paint 会生成像素" | Paint 产出**绘制指令**，像素化在光栅化阶段由光栅线程完成 |
| 88 | 5 | "渲染全在主线程" | 光栅与合成不在主线程；这正是"主线程卡住时 `transform` 动画仍流畅"的原因 |
| 89 | 5 | "CSS 只是样式，不影响加载" | 外部 CSS **阻塞渲染**（也阻塞脚本执行），所以关键 CSS 应内联（第 1 章 §1.1 同一条） |
| 90 | 5 | "`<script>` 都一样" | 无属性阻塞解析；`async` 执行顺序无保证；`defer` 在解析后按序执行 |
| 91 | 5 | "改 `transform` 一定只走合成" | 需要它在（或将被提升为）独立合成层；否则仍会走绘制 |
| 92 | 5 | "重绘和重排是一回事" | 改几何 → 布局 + 绘制；只改颜色 → 只绘制；只改 `transform` / `opacity` → 可能只合成 |
| 93 | 5 | "读写交替只是代码风格问题" | 它是**强制布局的直接成因**；应改为"先全读、再全写" |
| 94 | 5 | "改一个元素只影响它自己" | 改几何会波及后代与后续兄弟，改容器可能触发**全量布局** |
| 95 | 5 | "DevTools 的 Elements 看到的就是源码" | 那是**解析并容错后的实时 DOM**，文本节点与修复结果都在其中 |
| 96 | 5 | "网络面板只要能看请求就行" | 瀑布图各阶段（DNS / TCP / TLS / TTFB / 下载）对应不同的优化归属，**必须禁用缓存与限速**才有参考价值 |
| 97 | 5 | "本地很快 → 首屏没问题" | 实验室数据不能代表真实用户；需要 RUM 采集 |
| 98 | 5 | "内存占用高就是泄漏" | GC 是惰性的；判据是**反复操作后本应回收的同类对象是否持续增长**，且须先手动 GC |
| 99 | 5 | "看堆快照不用手动 GC" | 不触发 GC 看到的多是"尚未回收"，不是"无法回收" |
| 100 | 5 | "内存泄漏都是代码写错了" | 多数是**外部引用没解除**：定时器、监听器、缓存、未取消的异步 |
| 101 | 6 | "URL 就是字符串，可以拼接比较" | URL 由**解析算法**规范化（消解 `.` / `..`、补空路径、小写化 host），比较应用 `new URL().href` |
| 102 | 6 | "`#` 后面的内容会发给服务器" | fragment **只在浏览器内部使用**，不出现在请求里 |
| 103 | 6 | "`encodeURI` 和 `encodeURIComponent` 随便用" | 前者**不编码** `&=?/` 等保留字符，用于参数值会破坏结构 |
| 104 | 6 | "GET 和 POST 只是语义不同，实现上一样" | 安全 / 幂等性质会被浏览器与中间设备**用来做决策**（重试、预取） |
| 105 | 6 | "301 和 302 差不多" | 301 是**永久**（会被缓存，难撤销）；需保留方法与正文必须用 307 / 308 |
| 106 | 6 | "401 和 403 都是没权限" | 401 = 未认证；403 = 已认证但无权 |
| 107 | 6 | "304 是错误码" | 304 表示"缓存副本仍有效"，是**协商缓存命中**，且不带正文 |
| 108 | 6 | "`Vary` 是个可选的优化项" | 只要响应依赖某个请求头，**不写就会串味** —— 它是正确性问题 |
| 109 | 6 | "`no-cache` 是不缓存" | `no-cache` = **缓存但每次必须验证**；`no-store` 才是不存储 |
| 110 | 6 | "没配 `Cache-Control` 就等于不缓存" | 会走**启发式新鲜度**，浏览器可能自行缓存一段时间 |
| 111 | 6 | "`max-age` 对所有缓存生效" | 共享缓存（CDN / 代理）看 `s-maxage`；且 `private` 会禁止共享缓存 |
| 112 | 6 | "缓存只存在于浏览器" | 还有 CDN / 代理等**共享缓存**，它们同样遵守指令但遵循 `s-maxage` |
| 113 | 6 | "刷新页面就等于重新拉全部资源" | `immutable` 在寿命内连刷新都不重新验证 |
| 114 | 6 | "CORS 是服务端的安全机制" | CORS 由**浏览器强制**；`curl` 永远能成功。它防的是"别的站点读你的响应" |
| 115 | 6 | "同源策略阻止跨源请求发出" | 它限制的是**读取**。请求照样会发出 —— 这正是 CSRF 能成立的前提 |
| 116 | 6 | "所有跨源请求都会先发 OPTIONS" | 只有**非简单请求**才预检；`application/json` 的 POST 会触发 |
| 117 | 6 | "`Access-Control-Allow-Origin: *` 可以配凭据" | 与 `credentials: "include"` **互斥**，必须回显具体来源 |
| 118 | 6 | "跨源响应里所有头都能被 JS 读到" | 默认只有 7 个安全头，其余需 `Access-Control-Expose-Headers` |
| 119 | 6 | "`localStorage` 和 Cookie 差不多" | `localStorage` **不随请求发送**，但 API 是**同步的、会阻塞主线程**，且容量约 5MB |
| 120 | 6 | "把 token 放 `localStorage` 很方便" | 一旦 XSS 即被窃取；`HttpOnly` Cookie 可抵御 XSS，但要另防 CSRF —— **没有全赢方案** |
| 121 | 6 | "`SameSite` 默认可不管" | 现代浏览器默认 `Lax`；`None` 必须配 `Secure` |
| 122 | 6 | "HTTP/2 解决了队头阻塞" | 它解决了**应用层**的；**传输层**（TCP）仍在，要靠 HTTP/3（QUIC） |
| 123 | 6 | "发布新版本就是覆盖文件" | 覆盖后浏览器与 CDN 仍持旧副本。必须**改文件名**（内容哈希）才能安全长缓存 |
| 124 | 6 | "CDN 只是加速，与构建无关" | CDN 的缓存能力**依赖构建能产出内容哈希**；两者是同一套策略的两端 |

**共 124 条**。原六张表合计 132 条，处理如下：**合并 7 条跨章重复**（CSS 阻塞渲染 / `will-change` / `offsetHeight` 强制布局 / `setTimeout(0)` / `async` 错误捕获 / `Promise` 取消 / CORS 失败看不出原因），**另 1 条不再重复** —— "Lighthouse 无障碍满分不等于可访问"已在 **D0 第 8 章 §8.12 第 6 条**，那里才是它的主题所在。

1. **它不是复习材料，是排查索引**。读正文时不必看它；**遇到"这东西为什么不生效"时来查**。
2. **每条的"事实"都是机制解释，不是结论**。只记结论会在下一个项目里失效。
3. **带具体数字/具体写法的条目（如 1024 字节、7 个安全头、`minmax(auto, 1fr)`）是最该记的** —— 它们是可以直接验的。

## 7.12 D0 领域收束

七章、47 个节点到此收束。**D0 回答的是一个贯穿性问题**：

> **你写下的东西，最后是怎么变成用户屏幕上的像素的？**

| 章 | 回答什么 | 核心机制 |
|---|---|---|
| **第 1 章** | 第一个页面由哪几件事组成 | **HTML / CSS / JS 的职责分工**（结构 / 样式 / 行为） |
| **第 2 章** | 样式是怎么算出来的 | **盒模型与层叠** |
| **第 3 章** | 行为怎么组织 | 语句、函数、数据的基本组织方式 |
| **第 4 章** | 为什么有些行为反直觉 | **作用域与异步**（语言的深水区） |
| **第 5 章** | HTML 怎么变成像素 | **浏览器的渲染流水线** |
| **第 6 章** | 资源怎么到达浏览器 | **HTTP 缓存与协商** |
| **第 7 章** | 从"页面"到"系统" | **工程工具链的登场**（这也是后续九个领域的入口） |

### 一条贯穿 D0 的判据

> **遇到问题时，先问「它在哪一层」。**

| 现象 | 通常在哪一层 |
|---|---|
| 样式不生效 | **样式层**（层叠 / 特异性） |
| 点击没反应 | **行为层**（事件绑定时机） |
| 页面白屏 | **渲染层或网络层**（脚本报错 / 资源 404） |
| "本地是对的" | **网络层**（缓存） |

**⭐ 这条判据的价值在于"它先于任何工具"** —— 而 D0 的全部内容，本质上是**为这六层各建立一个"可提问的对象"**。

### D0 与后续领域的分界

| | D0 负责 | 后续领域负责 |
|---|---|---|
| 对象 | **语言与平台**（HTML / CSS / JS / 浏览器 / HTTP） | **协作与工具**（规范、模块、构建、测试、交付） |
| 判据 | "它在哪一层" | "它会不会被换掉"（`D4`）、"红灯可不可信"（`D5`）、"复杂度放在哪一侧"（`X2`） |

**一句话记住边界**：**D0 让你能看懂一个页面为什么长这样；从 D1 起，让你能看懂一个系统为什么这样做。**

## 本章小结

**九条最该记住的结论**

1. **命令行是四条约定的组合**（三条标准流 / 管道 / 退出码 / 环境变量）。**退出码是 CI 判断成败的唯一依据**——这也是"命令报错但 CI 绿灯"的原因。
2. **版本一致性靠约定与工具双保险**：`.nvmrc` 声明、`engines` 默认只警告。团队差异是最典型的"本地能跑、CI 挂"来源。
3. **编辑器是第一层门禁**，`.vscode/` 与 `.editorconfig` 属于团队约定，应进版本库。
4. **Git 是内容寻址的快照存储**：对象名由内容算出，所以内容相同即同一对象、内容一变哈希全变——这正是"rebase 改写历史"的机制。
5. **`reset` 的三种模式是在往回拨"三个区域"**；已推送的撤销要用 `revert`。**行尾符差异会造成整文件假差异**，根治靠 `.gitattributes`（仓库级）而非 `core.autocrlf`（本机级）。
6. **`package.json` 是声明、lockfile 是解析结果、`node_modules` 是实现**；`npm ci` 只信 lockfile 且不一致就失败——这是可复现构建的最小条件。
7. **依赖类型决定"装不装进生产"**：放错位置会带来镜像膨胀或运行时缺模块；`peerDependencies` 漏写会导致重复实例。
8. **工程化的唯一动作是"把人的约定变成机器可执行的约束"**，顺序应按反馈成本从低到高（编辑器 → pre-commit → CI → 发布前）。**只写在文档里的规范必然腐化。**
9. **工程化的每一个约定，都要回答"它由谁执行"**：写进文档的靠人，写进脚本的靠机器。前者会腐化，后者才有长期效力。

> **本章只覆盖工程流程。** 可访问性的可判定边界（可访问名计算、`aria-hidden` 与焦点冲突、自动化只覆盖约三分之一）与国际化三条纪律（格式化交给 `Intl`、时间存 UTC、句子不拼接，且与 `Vary` 是同一件事的两面）**已迁至 [D0 第 8 章](d0-08-a11y-and-i18n.md)**。
