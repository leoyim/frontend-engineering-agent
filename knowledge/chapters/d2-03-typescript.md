## 3.1 类型系统的行为模型：它不是"注解"

### 最关键的一条：类型只在编译期存在

```ts
type User = { name: string };
function greet(u: User) { return `hi ${u.name}`; }

// 编译后（示意）：
function greet(u) { return `hi ${u.name}`; }
```

**类型标注在产出中被完全擦除**。由此推出三条硬结论：

| 结论 | 含义 |
|---|---|
| **类型不能做运行时校验** | 从网络、`localStorage`、用户输入拿到的数据**类型声明只是断言**，运行时可能是任何东西 |
| **类型不能防住所有错误** | 它保证的是"在你声明的假设成立的前提下，代码自洽" |
| **`as` 是"我保证"而不是"已验证"** | 它不产生任何运行时代码，写错了后果自负 |

**"类型检查过了，上线却报 `Cannot read property of undefined`"的根因就在第一行**——外部数据的形状是运行时事实，不是编译期类型。要做运行时校验，必须用运行时校验库（Schema 校验），这是 X2 / D6 领域的话题。

### 结构化类型：兼容性看"形状"，不看"名字"

这是 TS 与其他语言最不同的一处：

```ts
interface Point { x: number; y: number }
interface Vector { x: number; y: number }

const p: Point = { x: 1, y: 2 };
const v: Vector = p;      // ✓ 合法 —— 形状相同即可
```

**推论**：

| 推论 | 说明 |
|---|---|
| 类型名没有身份 | 两个同名不同来源的类型**未必兼容**；两个不同名但结构相同的类型**兼容** |
| 多一个字段通常无害 | "子类型"只要包含目标类型的所有成员即可（对象字面量赋值有额外检查，见下） |
| "名义上的区分"要靠**标记位** | 想区分"用户 ID"与"订单 ID"（都是 `string`），要引入唯一的 brand 字段 |

### 类型的表达力核心：字面量类型与联合类型

```ts
type Status = "idle" | "loading" | "success" | "error";
```

**联合类型 + 字面量**是 TS 表达"有限状态"的基本手段，也是**判别联合（discriminated union）**的基础：

```ts
type Result =
  | { kind: "ok"; data: string }
  | { kind: "err"; message: string };

function handle(r: Result) {
  if (r.kind === "ok") {
    r.data;      // 收窄为 { kind: "ok"; data: string }
  } else {
    r.message;   // 收窄为 { kind: "err"; message: string }
  }
}
```

### 类型收窄：由控制流分析驱动的

**"收窄"是 TS 最被低估的能力**——它让类型跟着代码路径走：

| 手段 | 收窄依据 |
|---|---|
| `typeof x === "string"` | 运行时类型判断 |
| `"field" in obj` | 属性存在性 |
| `x instanceof Cls` | 原型链判断 |
| `x.kind === "ok"` | 判别联合的字面量判别位（最常用） |
| 自定义类型谓词 `function isCat(x): x is Cat` | **你自己写的**收窄函数 |
| 断言函数 `function assertDefined(x): asserts x is T` | 抛错即收窄 |
| 真值判断 `if (x)` | 剔除 `null` / `undefined` / `""` / `0` |

**注意最后一行**：真值判断会剔除**所有假值**（本章 §3.1 的七类），不只是 `null`/`undefined`。所以 `if (x)` 对 `0` 和 `""` 也会走 else 分支——这是真实 bug 的来源。

### 泛型：类型层面的函数

```ts
function first<T>(arr: T[]): T | undefined { return arr[0]; }

// 带约束
function pick<T, K extends keyof T>(obj: T, key: K): T[K] { return obj[key]; }
```

三个要点：

| 要点 | 说明 |
|---|---|
| 泛型是"类型参数" | 调用时由实参推断，也可显式指定 |
| `extends` 是**约束**不是继承 | 它表示"必须满足这个形状" |
| `keyof` 与索引访问类型 | 它们让泛型能"引用已知类型的成员"，是工具类型的基础（本章 §3.7） |

### 五个特殊类型的边界

| 类型 | 语义 | 何时用 | 何时别用 |
|---|---|---|---|
| `any` | **关闭检查** | 迁移中途的临时逃生口 | 长期停留会侵蚀整个代码库 |
| `unknown` | 未知但**必须先收窄** | **外部输入的首选** | — |
| `never` | 不可能的值 | 穷尽性检查、抛错函数 | — |
| `void` | 无返回值 | 只需副作用 | 别用它代替 `undefined` |
| `object` | 非原始值 | 很少直接用 | 通常应写具体形状 |

**`unknown` 是 `any` 的安全替代**：它同样接受任何值，但**不先收窄就不能用**。所以"外部数据的默认类型"应该是 `unknown`，而不是 `any`。

**穷尽性检查**是 `never` 的典型用法：

```ts
function assertNever(x: never): never { throw new Error("未处理的分支"); }

switch (status) {
  case "idle": /* … */ break;
  case "loading": /* … */ break;
  default: assertNever(status);   // ← 新增状态时这里会编译报错
}
```

**它的价值是把"漏处理一个状态"从运行时 bug 变成编译错误**。

## 3.2 `tsconfig`：配置是工程决策的载体

### 继承机制与一个易错点

```json
{ "extends": "../../tsconfig.base.json", "compilerOptions": { "outDir": "dist" } }
```

**易错点**：`extends` 里的**相对路径是相对于"写它的那个文件"解析的**，而 `include` / `exclude` 等字段中的路径也有各自基准。多级继承时，"这个路径到底相对谁"是排查配置失效的第一步。

（TypeScript 5 起 `extends` 支持数组，用于组合多份基础配置。）

### 关键字段按用途分组

| 组 | 字段 | 决定什么 |
|---|---|---|
| **目标环境** | `target` / `lib` / `module` / `moduleResolution` | 产出降级到什么语法、可用的运行时 API、模块系统的形态 |
| **严格性** | `strict` 及其子开关 | 检查的强度（本章 §3.4） |
| **产出** | `outDir` / `declaration` / `declarationMap` / `sourceMap` / `noEmit` | 生成什么文件 |
| **模块互操作** | `esModuleInterop` / `isolatedModules` / `verbatimModuleSyntax` | 与 CJS/ESM 的交互方式 |
| **检查范围** | `include` / `exclude` / `files` / `skipLibCheck` | 检查哪些文件 |

### `target` 与 `lib` 必须分开理解

这两个字段经常被混为一谈，但它们回答的是**两个不同的问题**：

| 字段 | 回答的问题 | 例子 |
|---|---|---|
| `target` | **语法**要降到哪一版 | 可选链 `?.` 要不要被降级 |
| `lib` | 我能用哪些**运行时 API 的类型声明** | 能不能用 `Promise`、`Array.prototype.at` |

**分开的意义**：降级语法（`target`）不等于补齐 API（`lib` / polyfill）。这正是 D3 领域"编译降级 ≠ API 补齐"那条结论在 TS 侧的对应——**`target` 设低了但 `lib` 设高了，会出现"类型检查通过、运行时报错"**（用了运行时不存在的 API）。

### `strict` 是一组开关的集合

**记忆它包含什么，比记住这个名字有用**：

| 子开关 | 拦什么 |
|---|---|
| `noImplicitAny` | 推断不出来的隐式 `any` |
| `strictNullChecks` | `null` / `undefined` 参与类型运算（**收益最大的一条**） |
| `strictFunctionTypes` | 函数参数的逆变检查 |
| `strictBindCallApply` | `bind` / `call` / `apply` 的参数类型 |
| `strictPropertyInitialization` | 类属性未初始化 |
| `noImplicitThis` | 无法推断的 `this` |
| `useUnknownInCatchVariables` | `catch (e)` 里的 `e` 默认变成 `unknown` 而非 `any` |
| `alwaysStrict` | 产出带 `"use strict"` |

（该集合随版本演进，新版本可能加入新成员。）

### `moduleResolution` 必须与运行环境一致

**回链 D2 第 1 章 §1.4**：解析规则由运行环境决定，而 TS 的解析是**独立实现**。所以这个字段配错，会出现"构建能过但类型报错"或反之。

| 取值 | 适用 | 是否要求完整扩展名 |
|---|---|---|
| `bundler` | 由打包器负责解析 | 允许省略 |
| `node16` / `nodenext` | Node 原生运行 | **要求写全** |
| `node10`（旧称 `node`） | 老式 Node/CJS 生态 | 允许省略 |

### `skipLibCheck`：一个需要明确取舍的开关

它会**跳过所有 `.d.ts` 的类型检查**。

| 好处 | 代价 |
|---|---|
| 编译大幅加速（三方声明文件通常庞大） | 三方类型里的错误不会暴露 |
| 避免被依赖里的类型问题拖住 | 某些版本冲突只能在运行时暴露 |

**"开了它就不再报错"是一种信号**：说明原本报的错来自依赖的类型声明，而不是你的代码——这类问题需要单独判断，而不是一直跳过。

## 3.3 检查与产出分离：为什么必须两条流水线

> **域外依赖（已闭合）**：本节需要"转译器"的背景，完整展开见 **`D3` 第 2 章 §2.2 / 第 3 章 §3.2**。此处就地交代必要部分。

### 【补充背景】什么是转译器

**转译器（transpiler）** 是"把源码变成源码"的工具，典型代表是 Babel、SWC、esbuild。它们做的是**语法层处理**：解析成 AST → 改写 → 生成新代码。

**关键区别：转译器剥离类型，但完全不做类型检查。** 对它们来说 `const x: number = "abc"` 里的 `: number` 只是"要丢掉的语法"。

### 为什么必须分离

| 能力 | 成本结构 |
|---|---|
| **类型检查** | 需要**全程序分析**（跨文件推断、泛型求解），天然慢 |
| **语法转译** | 只需**单文件**处理，可以被高度并行化与原生实现加速 |

**把两者绑在一起（只用 `tsc` 产出）意味着每次构建都要付全程序分析的成本**。所以现代流水线是分工的：

| 方案 | 结构 | 特点 |
|---|---|---|
| 只用 `tsc` | 检查 + 产出都归它 | 配置最简单，但慢 |
| **分离（主流）** | 转译器负责产出 + `tsc --noEmit` **只做检查** | 快，但**两条流水线都要跑** |

### 分离带来的头号风险：只跑了一条

```text
转译器不问类型 → 类型不匹配的代码照样产出 → 运行时才炸
```

**具体例子**：

```ts
function add(a: number, b: number) { return a + b; }
add("1", "2");     // 类型错误，但转译器不检查 → 会真的产出并运行
```

这就是"CI 里为什么必须同时跑转译与 `tsc --noEmit`"的完整理由：**它们拦的是不同类别的错误**。只跑转译 = 放弃类型安全；只跑检查 = 没有产物。

### `isolatedModules` 与 `verbatimModuleSyntax`：让"单文件转译"成为前提

分离能成立的**规范前提**是：**每个文件必须能独立转译，不依赖其他文件的类型信息**。这两个开关就是在强制这个前提：

| 开关 | 强制什么 | 典型报错场景 |
|---|---|---|
| `isolatedModules` | 每个文件的语义可独立判定 | `const enum`（其取值可能需要跨文件内联）、只导出类型却用了值导出语法 |
| `verbatimModuleSyntax` | **类型导入必须显式写 `import type`** | 否则转译器无法判断该不该保留这行 import |

**`verbatimModuleSyntax` 解决的是一类真实问题**：`import { SomeType } from "./types"` 在转译后如果被保留，运行时会去加载一个只有类型的模块——要么报错，要么引入无用依赖。显式 `import type` 让"这行该不该留"变成语法层面可判定的事。

**这与 D2 第 1 章 §1.6 的 `sideEffects` 是同一类思路**：把"只有作者知道的信息"变成**可静态判定的语法**，工具才能安全优化。

## 3.4 严格度进阶与增量收敛

### 两个进阶开关的机制

| 开关 | 改变什么 | 它拦的真实 bug |
|---|---|---|
| `noUncheckedIndexedAccess` | `obj[key]` 与 `arr[i]` 的结果变成 `T \| undefined` | **数组越界 / 键不存在**——JS 里最经典的运行时崩溃 |
| `exactOptionalPropertyTypes` | 区分"可选"与"可以是 `undefined`" | `{ a?: string }` 不接受显式 `a: undefined`；防止可选属性被当成"存在但为空" |

第二条值得展开：

```ts
interface Opt { a?: string }
const x: Opt = { a: undefined };   // exactOptionalPropertyTypes 打开后报错
```

**"属性不存在"与"属性存在但值是 `undefined`"在语义上不同**——前者在序列化时会消失、后者的键仍在。这个区别在对接外部系统时是真的会出问题的。

### 为什么不能"一次全开"

存量项目打开这些开关会**一次暴露成百上千个错误**，工程上无法落地。所以需要**增量收敛**：

| 手段 | 机制 | 注意 |
|---|---|---|
| **分目录渐进** | 新代码目录先开严格，老目录维持现状 | 需要多份 tsconfig（回链 本章 §3.2 的继承机制） |
| **基线机制** | 记录"当前错误数"，只允许减少不允许增加 | 需要 CI 支持（回链 D1 的 CI 卡点） |
| **局部豁免** | `@ts-expect-error` / `@ts-nocheck` | 必须有清理机制，否则会沉淀成永久债务 |

### `@ts-expect-error` 与 `@ts-ignore` 的差别不是"语气"

| 注释 | 下一行没有错误时 |
|---|---|
| `@ts-ignore` | 静默通过 |
| `@ts-expect-error` | **自己报错** |

**这就是它值得用的原因**：一旦底层问题被修好，这行会被"提醒删除"，而不是默默留成一句无意义的注释。**它是一种自带过期提醒的豁免。**

### 与 D1 的接回

这一节的策略与 `D1.L3.03`（存量项目增量接入规范）是**同一套思路**：规则分级 → 容忍策略 → 渐进收敛。区别只是对象是 lint 规则还是类型开关。所以 D1 写到这里时会回链。

## 3.5 类型发布：消费者拿到的是 `.d.ts`

### 类型也有"发布形态"

源码是 TS，但**消费者安装后拿到的是编译产物与类型声明**。类型是否可用，取决于三件事：

```text
① 声明文件有没有被生成      → declaration: true
② 有没有暴露到正确的入口    → types 字段 / exports 里的 types 条件
③ 声明里的引用能不能被解析  → 路径与 rootDir 的关系
```

### `declarationMap` 解决的是"跳转去哪"

| 字段 | 作用 |
|---|---|
| `declaration` | 生成 `.d.ts` |
| `declarationMap` | 生成 `.d.ts.map`，让 IDE 的"跳转定义"能**回到源文件**而不是跳到 `.d.ts` |
| `sourceMap` | 让运行时错误堆栈映射回源码（与构建产物相关，D3 领域展开） |

**没有 `declarationMap` 时**，消费者跳转定义会跳到 `.d.ts`——那里只有类型没有实现，读起来毫无帮助。

### `exports` 里的 `types` 条件：顺序是语义

**回链 D2 第 1 章 §1.4**：条件导出**从上到下匹配，第一个命中生效**。所以：

```json
{
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",     // ← 必须放最前
      "import": "./dist/index.mjs",
      "require": "./dist/index.cjs"
    }
  }
}
```

**`types` 放在后面会失效**——因为顺序在前的条件已经命中，TS 拿不到类型声明。

### "类型不见了"的四种症状与对应原因

| 症状 | 原因 |
|---|---|
| IDE 显示为 `any` | 声明没生成，或入口没指向 `.d.ts` |
| 跳转定义跳到 `.d.ts` 且难以阅读 | 缺 `declarationMap` |
| 安装了包却完全没有类型提示 | `exports` 里漏了 `types` 条件 |
| 原本报错的类型问题"消失"了 | `skipLibCheck` 开着（本章 §3.2） |

**排查顺序就是上表倒过来**：先看 `skipLibCheck` 是不是把问题藏了，再看入口是否暴露了 `types`，最后看声明有没有生成。

## 3.6 大仓库的类型提速：Project References

### 问题的本质

`tsc` 的类型检查是**全程序分析**——这意味着**改一个文件可能要重算整棵树**。项目一大，检查时间就不可接受。

### Project References 的机制

```json
// packages/ui/tsconfig.json
{ "compilerOptions": { "composite": true }, "references": [{ "path": "../core" }] }

// packages/app/tsconfig.json
{ "references": [{ "path": "../ui" }] }
```

把仓库切成**多个 TS 项目**并**显式声明依赖**，然后：

```bash
tsc --build        # 增量构建：只重建「输入变了」的项目
tsc --build --watch
```

| 机制 | 作用 |
|---|---|
| `composite: true` | 开启"可被引用"的模式（要求生成声明与 `.tsbuildinfo`） |
| **`.tsbuildinfo`** | 增量信息缓存——记录上次构建的输入指纹 |
| `references` | 项目之间的依赖声明，决定重建顺序与"谁受影响" |

**核心收益**：未变更的项目**直接复用已生成的 `.d.ts`**，不再重新分析它的源码。

### 与 Monorepo 的接回

**包边界天然就是项目边界**（回链 D2 第 2 章 §2.7）。所以 Monorepo 里 `tsc --build` 的"受影响项目"计算，与任务编排工具的"受影响包"计算是**同一张图**——只是一个在类型层，一个在任务层。

**反过来说**：如果包之间没有显式的项目引用（`references`），TS 就无法做这种增量判断，只能全量检查。

### 什么时候不需要它

中小项目收益不明显，而引入它要付出的代价是：每个包要有自己的 tsconfig、要维护 `references`、构建顺序变成有向图。**这是一条随规模才划算的优化。**

## 3.7 类型系统深度：它是"可以编程"的

### 四个机制，四种编程能力

TypeScript 的类型层其实是一门小语言，它的四个核心机制各自对应一种编程能力：

| 机制 | 语法 | 相当于 |
|---|---|---|
| **条件类型** | `T extends U ? X : Y` | **if** |
| **`infer`** | `T extends (infer R)[] ? R : never` | **解构 / 抽取** |
| **映射类型** | `{ [K in keyof T]: F<T[K]> }` | **遍历 / map** |
| **模板字面量类型** | `` `${A}-${B}` `` | **字符串拼接与匹配** |

**把这四条连起来，类型层就有了完整的编程能力**。

### 标准工具库就是它们的组合

```ts
type MyPick<T, K extends keyof T> = { [P in K]: T[P] };                    // 映射类型
type MyReturnType<T> = T extends (...args: never[]) => infer R ? R : never; // 条件 + infer
type MyAwaited<T> = T extends Promise<infer R> ? MyAwaited<R> : T;          // 递归
```

`Pick` / `Omit` / `Partial` / `ReturnType` / `Awaited` / `Parameters` 这些内置工具类型，全都是上面四个机制的组合。**理解机制之后，它们不再是"要背的 API"**。

### 类型性能：这是一项真实成本

类型运算**发生在编译期与 IDE 里**，所以它直接影响：编译时长、编辑器响应速度、CI 时间。

**常见的性能杀手**：

| 手法 | 问题 |
|---|---|
| 深层递归类型 | 复杂度爆炸（尤其是无深度限制的递归） |
| 超大联合类型 | 每次运算都要遍历成员 |
| 复杂模板字面量类型 | 字符串模式匹配代价高 |
| 过度使用交叉类型 `A & B` | 它需要**立即求交**，而 `interface extends` 更惰性 |
| 类型层面的"炫技" | 表达力越强，代价越高 |

**诊断手段**：

```bash
tsc --diagnostics            # 概览：检查时间、内存、文件数
tsc --extendedDiagnostics     # 更细：各类耗时拆解
tsc --generateTrace ./trace   # 生成可分析的性能轨迹
```

**"IDE 变得很卡"也是信号**——它不是编辑器的问题，是类型运算太重。

**缓解原则**：拆类型、给递归设深度上限、能用接口表达的关系不必用交叉类型、**把复杂类型限制在库的边界内**（不要让消费者触发深层运算）。

## 3.8 转译器插件开发

> **域外依赖（已闭合）**：本节需要 esbuild / SWC 的背景，完整机制见 **`D3` 第 6 章 §6.3**。此处就地交代必要部分。

### 【补充背景】三类工具形态不同

| 工具 | 实现语言 | 扩展方式 | 特点 |
|---|---|---|---|
| **Babel** | JS | 插件（JS 函数，遍历 AST） | 生态最大、最好写、较慢 |
| **SWC** | Rust | 插件（编译为 wasm） | 快，但开发成本高 |
| **esbuild** | Go | 插件（JS 对象，拦截 + 转换） | 极快；插件偏向"接入"而非"改语法" |

**共同点**：它们都走 **AST 转译三步**：

```text
parse（源码 → AST）→ transform（遍历并改写节点）→ generate（AST → 新源码）
```

**Babel 插件的形态**就是一个"访问者"对象：

```js
module.exports = function () {
  return {
    visitor: {
      Identifier(path) { /* 遇到标识符节点时执行 */ },
      CallExpression(path) { /* 遇到调用表达式时执行 */ },
    },
  };
};
```

### 插件最常做的三类事

| 类别 | 例子 |
|---|---|
| **语法扩展** | 支持自定义语法（宏、装饰器变体） |
| **代码转换** | 自动补 import、按需加载、注入埋点 |
| **静态分析** | 提取信息生成额外产物（如文档、依赖表） |

### 一条硬边界：**插件拿不到类型**

回链 本章 §3.1——**类型在转译阶段已经被擦除了**。所以转译器插件运行在"只剩运行时语义"的代码上，它**看不到类型信息**。

这解释了为什么很多"靠类型做决策"的转换（如基于类型的自动注入）在转译器插件里做不到，必须放到 `tsc` 的 Transformer API 里（那是在类型信息还在的阶段）。

### 什么时候不该写插件

| 更轻的替代 | 适用 |
|---|---|
| lint 规则 | 只是"检查与提示"而非"改写" |
| 代码生成（脚手架） | 一次性生成而非每次构建都转 |
| 独立的预处理器 | 与具体工具链解耦 |

**写插件的门槛不只是代码量，还有维护成本**：它绑定在特定工具的 AST 与版本上，工具升级就可能需要跟进。

## 3.10 本章常见误区

| # | 误区 | 事实 |
|---|---|---|
| 1 | "`as` 是转换" | 它不产生任何运行时代码，只是"我保证" |
| 2 | "同名类型一定兼容" | 取决于结构；靠名称区分要靠显式的标记位 |
| 3 | "`if (x)` 只排除 `null`/`undefined`" | 它排除**所有假值**（含 `0`、`""`、`NaN`），这是真实 bug 来源 |
| 4 | "`any` 和 `unknown` 差不多" | `unknown` **必须先收窄才能用**；`any` 直接关闭检查。外部输入应用 `unknown` |
| 5 | "`target` 和 `lib` 是一回事" | `target` 管**语法降级**，`lib` 管**可用 API 的声明**；配错会"类型过、运行时炸" |
| 6 | "`strict: true` 就够了" | 它是一个**集合**；`noUncheckedIndexedAccess` / `exactOptionalPropertyTypes` 等不在其中，需要单独开 |
| 7 | "`moduleResolution` 随便配" | 它必须与**运行环境**一致；配错会出现"构建过但类型错"或反之 |
| 8 | "`extends` 的路径基准无所谓" | 相对路径**相对于写它的文件**解析；多级继承时这是配置失效的首要原因 |
| 9 | "`skipLibCheck` 开着更省事" | 它跳过三方声明检查；"开了就不报错"说明问题来自依赖而非你的代码，需要单独判断 |
| 10 | "只用 `tsc` 产出就行" | 可行但慢（全程序分析）；主流做法是转译器产出 + `tsc --noEmit` 检查，**两条都要跑** |
| 11 | "`import type` 是风格偏好" | 在 `verbatimModuleSyntax` 下它决定"这行 import 该不该保留"，是**正确性**问题 |
| 12 | "`const enum` 只是写法" | 它与**单文件转译**不兼容（取值需跨文件内联），所以 `isolatedModules` 会报错 |
| 13 | "严格度一次全开最好" | 存量项目会一次暴露海量错误；需要**分目录 + 基线 + 局部豁免**的增量收敛 |
| 14 | "`@ts-ignore` 和 `@ts-expect-error` 一样" | 后者在"没有错误时**自己报错**"——这是它作为"自带过期提醒的豁免"的价值 |
| 15 | "类型声明会自动跟着走" | 需要 `declaration` 生成、入口暴露、路径可解析三件事同时成立 |
| 16 | "`exports` 里条件的顺序无所谓" | **顺序即语义**；`types` 放在后面会直接失效 |
| 17 | "大项目慢只能忍着" | Project References + `tsc --build` 让未变更项目复用 `.d.ts`；包边界即项目边界 |
| 18 | "接口和交叉类型可以互换" | `interface extends` 更惰性；大规模使用 `A & B` 会显著推高求交成本 |
| 19 | "转译器插件能拿到类型" | 类型在转译阶段已被擦除；需要类型信息的转换必须放在 `tsc` 的 Transformer 阶段 |

## 3.11 D2 领域收束

三章、24 个节点到此收束。**D2 回答的是一个结构性问题**：

> **一个文件，怎么变成一组可被依赖的单元？**

| 章 | 回答什么 | 核心机制 |
|---|---|---|
| **第 1 章** | 依赖关系怎么被定义 | **模块体系**（从脚本到标准的演进） |
| **第 2 章** | 单元怎么被分发与组合 | **包管理与仓库架构**（版本、monorepo） |
| **第 3 章** | 契约怎么被表达与检查 | **类型系统**，以及**检查与产出分离** |

### 一条贯穿 D2 的判据

> **这个依赖关系能不能被静态分析？**

| 依赖形态 | 能被静态分析吗 | 后果 |
|---|---|---|
| 静态 `import` | ✅ | **可以摇树、可以分割、可以增量** |
| 动态 `import()` | ⚠️ 部分 | 能分割，但**传递性弱**（`X2` 第 4 章、`D5` 第 3 章 §3.3 都踩过） |
| **运行时拼接的 `require`** | ❌ | 无法摇树，也**无法可靠地做变更影响分析** |

**⭐ 这条判据是 D3 全领域的前提**：**Tree Shaking 依赖静态图**、**代码分割依赖可识别的动态导入**、**增量构建依赖可追踪的依赖边**。**而这些能力的地基都在 D2。**

**而它与 `D3` 第 4 章 §4.2 的"图是从入口可达的子图"是同一条**：**D2 定义了什么算一条边，D3 才能谈"图上有什么"。**

### D2 与相邻领域的分界

| | D2 负责 | 相邻领域负责 |
|---|---|---|
| **D3** | 依赖**怎么被声明** | 依赖**怎么被打包与优化** |
| **D1** | **代码内部**的写法与契约 | **协作流程**上的约定 |
| **X1** | **包的形态** | 包的**起点**（脚手架与共享包） |

**一句话记住边界**：**D2 决定"有哪些单元、它们怎么互指"，D3 决定"这些单元怎么变成一个产物"。**

## 本章小结

**八条最该记住的结论**

1. **类型只在编译期存在，运行时被完全擦除**。所以类型不能做运行时校验，`as` 是"我保证"而非"已验证"——**这是全部"类型过了还是炸"问题的根**。
2. **TS 是结构化类型**：兼容性看形状不看名字；要靠名称区分就得引入标记位。
3. **类型层的表达力来自四个机制**：条件类型（if）、`infer`（解构）、映射类型（遍历）、模板字面量类型（字符串）。标准工具类型都是它们的组合。
4. **`target` 与 `lib` 回答不同问题**（语法降级 vs 可用 API），配错会产生"类型检查通过、运行时报错"。
5. **检查与产出必须分离**：类型检查是全程序分析（慢），转译是单文件处理（快）。**代价是两条流水线都必须跑**，否则类型错误照常上线。`verbatimModuleSyntax` / `isolatedModules` 是让"单文件转译"成立的语法前提。
6. **严格度要增量收敛**（分目录 + 基线 + 局部豁免），而 `@ts-expect-error` 的优势是"**问题修好后它会自己提醒你删除**"。
7. **类型发布要三件事同时成立**（生成声明、暴露入口、路径可解析）；`exports` 里 **`types` 条件必须在最前**，`declarationMap` 决定消费者跳转到哪。
8. **类型与转译是两项真实成本**：Project References 让大仓库复用 `.d.ts` 做增量；类型运算是编译期开销，"IDE 卡"往往是类型设计问题。
