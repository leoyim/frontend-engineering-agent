## 3.1 CDN 是"共享缓存"，它看到的世界与浏览器不同

这一条是本章全部差异的根源，而它只有一句话：

> **浏览器是私有缓存，CDN 是共享缓存。**

RFC 9111 的指令设计里，**"共享"与"私有"是一个显式的区分维度**（`private` / `s-maxage` / `proxy-revalidate` 三个指令存在的唯一理由就是这个区分）。所以**同一份响应头，两个角色会做出不同决定**。

### 一张表：同一份响应，两种角色

| 响应头 | 浏览器（私有） | CDN（共享） |
|---|---|---|
| `Cache-Control: max-age=600` | 可以存 600 秒 | **也可以**存 600 秒 |
| `Cache-Control: max-age=600, s-maxage=60` | 仍按 **600** 秒 | 按 **60** 秒（`s-maxage` **覆盖** `max-age`） |
| `Cache-Control: private, max-age=600` | **可以存** | **不得存**（官方："共享缓存 MUST NOT store"） |
| `Cache-Control: no-cache` | 可存，用前必验 | 可存，用前必验 |
| `Cache-Control: no-store` | 不得存 | 不得存 |

**第二行是实践中最容易出错的**：`s-maxage` 的意思是"**共享缓存按我说的算，私有缓存照旧**"。所以**它给你一个"CDN 短、浏览器长"的旋钮** —— 用于"希望用户本地留着，但边缘要尽快更新"的场景。

**第三行是安全边界**：任何**包含用户数据**的响应，缺 `private` 就可能被 CDN 缓存并**发给另一个人**。这不是性能问题。

### 一个特殊的后果：`must-revalidate` 让 CDN 在断连时返回错误

RFC 9111 对 `must-revalidate` 有一段很强硬的表述：

> **在所有情况下，缓存都不得忽略 `must-revalidate` 指令**；特别是，**如果缓存处于断连状态，它必须生成一个错误响应，而不是复用 stale 响应**。生成的 状态码 **SHOULD 是 504（Gateway Timeout）**，除非其他错误状态码更合适。

**这对 CDN 意味着什么**：

| 场景 | 行为 |
|---|---|
| 源站正常、内容已过期 | CDN 回源验证 → 正常 |
| **源站挂了、CDN 与源站断开** | **返回 504，而不是发旧副本** |

**这与很多人的直觉相反** —— 直觉是"CDN 应该兜底发旧内容"。但配了 `must-revalidate` 就是明确选择了"**宁可报错，也不发可能错误的内容**"。

**推论**：**如果某个资源在源站故障时"发旧内容"是可接受的（甚至更好），那就不该给它配 `must-revalidate`。** 这两个选择是互斥的，必须显式决定。

## 3.2 stale 的三类例外，与一个真实冲突

### stale 默认不可发

RFC 9111 的收口条件很明确：**缓存只有在三种情况下才能复用存储的响应**：

| 情况 | 说明 |
|---|---|
| **fresh** | `freshness_lifetime > current_age` |
| **被允许发 stale** | 断连，或客户端/源站**显式允许** |
| **已成功验证** | 走了一次条件请求并拿到 304 |

而"显式允许"的清单，官方给的是：

> `max-stale` 请求指令、**如 RFC 5861 所定义的扩展指令**、或按带外约定所做的配置。

### 关键：禁止性指令优先

同一节还有一段**必须先读的限定**：

> **如果协议内的显式指令禁止**（例如 `no-cache` 响应指令、`must-revalidate` 响应指令，或适用的 `s-maxage` / `proxy-revalidate` 响应指令），**缓存不得生成 stale 响应**。

**把这段与 `s-maxage` 的定义放在一起，就得到本章最重要的一条冲突**：

`s-maxage` 的定义里明确写着：

> `s-maxage` 指令**纳入了 `proxy-revalidate` 响应指令对共享缓存的语义**。**共享缓存不得复用带 `s-maxage` 的 stale 响应**来满足另一个请求，直到它被源站成功验证。

**所以**：

> **`s-maxage` + `stale-while-revalidate` 在 CDN 上会冲突。**
>
> `s-maxage` 内建了"stale 后必须回源验证"的语义，而 RFC 9111 又把 `s-maxage` 列为**禁止发 stale** 的指令之一。于是 SWR 想做的事（stale 后先给旧副本）**被 `s-maxage` 自己挡住了**。

### 这条解释了一种很常见的困惑

**现象**："我配了 `stale-while-revalidate=30`，本地用浏览器测有效，上了 CDN 就没反应。"

**机制**：

| 角色 | 有没有 `s-maxage` 的约束 | SWR 是否生效 |
|---|---|---|
| 浏览器（私有缓存） | `s-maxage` **对它不适用** | ✅ 生效 |
| **CDN（共享缓存）** | `s-maxage` **对它适用，且内建 proxy-revalidate** | ❌ **被禁止发 stale** |

**所以"本地有效、CDN 无效"不是配置写错，是两个角色的规则不同。** 这与 §3.1 的"同一份响应头两种行为"是同一个根源。

**⚠️ 一条必须如实标注的边界**：**本章不断言"所有 CDN 实现都严格遵循这条"**。缓存实现在细节上的遵循程度差异很大，而**本次核验的三个 RFC 页面都没有给出实现一致性数据**。所以准确的说法是：

> **按 RFC 9111 的条文，`s-maxage` 与 SWR 在共享缓存上存在冲突；实际行为取决于实现，必须实测。**

### RFC 5861 的地位：它是 Informational，不是标准

这一条值得单独写，因为它会影响"这条机制有多可信"的判断。

| 项 | 事实（RFC 5861） |
|---|---|
| 文档号 / 标题 | RFC 5861《HTTP Cache-Control Extensions for Stale Content》 |
| 作者 / 日期 | Mark Nottingham · **2010 年 5 月** |
| **类别** | **Informational（信息性）**，Independent Submission 流 |
| 官方自述 | "**本文件不是 Internet Standards Track 规范**；它出于**信息性目的**发布"、"RFC Editor 自行决定发布，**不对其实现或部署价值作任何声明**" |
| 规范依据 | 仅引用 RFC 2119 与 RFC 2616 |

**它定义了两个扩展**：

| 扩展 | 定义（原文要点） |
|---|---|
| `stale-while-revalidate` | 缓存**可以**在响应 stale 后**继续提供**它，最长到指定秒数；并且**应当在不阻塞的情况下**尝试再验证 |
| `stale-if-error` | **遇到错误时**，可以用 stale 的缓存响应满足请求，**不管其他新鲜度信息**；这里的"错误"指会返回 **500 / 502 / 503 / 504** 的情况 |

**⚠️ 一处必须点明的时效性问题**：

**RFC 5861 两处要求 stale 响应带 `warning header`**（依据是 RFC 2616）。而 **RFC 9111 已把 `Warning` 首部作废**（§5.5）。

**所以这条要求在现行体系中不再成立。** `Age` 首部的要求仍然有效。

**另一处更重要**：**RFC 5861 自己完全没有讨论它与 `must-revalidate` / `no-cache` 的关系。** 它的规范性引用只有 RFC 2119 与 2616，没有给出任何优先级规则。

> **那个优先级是 12 年后由 RFC 9111 §4.2.4 补上的**（即 §3.2 引的那段"禁止性指令优先"）。
>
> **所以引用优先级时，出处应当是 RFC 9111，而不是 RFC 5861。** 这条对任何写缓存策略文档的人都有用。

### 两个扩展的语义差别（一句话各一条）

| 扩展 | 一句话 |
|---|---|
| `stale-while-revalidate` | "**别等我**：先给旧的，我同时去更新" |
| `stale-if-error` | "**出错了也别空手**：源站 5xx 时给旧的" |

**它们解决的不是同一个问题**：前者优化**延迟**（把回源挡在用户之外），后者提高**可用性**（源站故障时的兜底）。

## 3.3 `immutable`：三条限制，与它不是"永久缓存"

RFC 8246（**Standards Track**，2017 年 9 月，Patrick McManus）定义了 `immutable`。

### 定义

> 源服务器在该响应的 **freshness lifetime（新鲜期）内不会更新该资源的表示**。

### 它解决的问题

**版本化 URL**（如 `main.4f3a1b.css`）的长缓存有一个副作用：**用户点刷新时，浏览器会对页面上大量子资源逐一发条件请求**，全部返回 `304 Not Modified` —— 大量**无意义的网络往返**。

`immutable` 就是告诉客户端：**在新鲜期内，不用再发条件请求确认了。**

### 三条限制（都比"能省请求"更重要）

| # | 限制 | 后果 |
|---|---|---|
| **1** | **只在新鲜期内有效**，且**自身不创建新鲜期** | 单独写 `immutable` **没有意义**，必须配合 `max-age` 一类能产生新鲜期的指令 |
| **2** | **不能对抗强制刷新** | 用户强制刷新时，客户端应**忽略** `immutable` |
| **3** | **非认证上下文（非 HTTPS）时，客户端 SHOULD 忽略它** | 它类似一种"软固定"，可能**放大缓存投毒的影响** |

**另外两条**（官方）：

- **只有响应里有意义** —— 出现在请求中**无效果**；
- **不能替代过期后的重新验证**，也不能替代 `ETag` / `Last-Modified`。

**第 3 条是最容易被忽略的安全约束**，而它的理由值得记：**`immutable` 让客户端"放弃复查"，所以它依赖传输层可信。** 明文 HTTP 下这个前提不成立。

**⚠️ 一处如实标注**：**RFC 8246 没有给出任何浏览器兼容列表**（它只使用 "clients" / "user agents" 这类通用词）。**所以"某浏览器支持 `immutable`"这句话，本章不给依据。**

### 一张对照：三个"别问了"的指令

| 指令 | 说的意思 | 有效期 |
|---|---|---|
| `immutable` | "**新鲜期内**别发条件请求" | 只在新鲜期内 |
| `stale-while-revalidate` | "stale 后先给旧的，我同时更新" | 窗口内（受禁止性指令约束） |
| `max-age` 很长 | "很久都不用问" | 到期后仍会**条件请求** |

**第三行是关键**：**超长 `max-age` 不等于"永不请求"** —— 到期后浏览器仍会发条件请求并期待 `304`。**`immutable` 补的正是这个缺口。**

## 3.4 缓存键与失效：为什么"换 URL"是唯一可靠手段

D0 §6.8 已经讲了 purge 与版本化两条路，并给出了"优先用版本化"的结论。**本节补它的机制理由**（D0 未展开）。

### purge 在结构上不可靠

| 问题 | 机制 |
|---|---|
| **不知道有多少副本** | 一个 URL 可能存在于**多层、多地域**的节点上，你无法枚举"应该清哪些" |
| **传播需要时间** | 官方在 D0 已说"有传播延迟"；而**延迟期间不同用户会拿到不同版本** |
| **清不掉客户端** | **purge 管不到浏览器**。用户本地那份只能等过期或换 URL |

**第三行是最硬的**：即使 CDN 全清完了，**已经缓存了旧响应的浏览器依然会用它**。所以 **purge 不可能让"全世界立刻看到新内容"** —— 这是它的结构性上限，不是实现质量问题。

### 换 URL 为什么可靠

> **它不依赖任何缓存的合作。**

新 URL 对**所有缓存**都是"从未见过" → 天然 miss → 必然回源。旧 URL 保持原样 → 已缓存它的客户端继续用旧内容，**不会出错**（它会继续加载旧的那一整套，而不是新旧混搭）。

**这正是 D3 第 8 章 §8.1–§8.2 那套 hash 命名的真正意义**：它不是为了"构建好看"，而是**让缓存策略成立**。

**唯一需要 purge 的地方**是**索引类资源**（`index.html`、manifest）—— 它们**不带 hash**，所以只能靠"不缓存"（第 1 章 §1.2）或"必要时 purge"。

### `Vary` 在 CDN 上是"副本数乘数"

D0 讲了 `Vary` 决定命中率。**在 CDN 上这个代价是乘法的**：

| `Vary` 的维度 | 副本数 |
|---|---|
| 无 | 1 份 |
| `Accept-Encoding`（通常 2–3 种） | **×2~3** |
| 再加 `Accept-Language`（n 种） | **×2n** |
| 再加一个**几乎每用户都不同**的头（如 `Cookie`） | **命中率趋近 0** |

**一条纪律**：

> **`Vary` 只放"真的会改变响应内容"的头。**

**漏写的后果是"串味"**（A 语言的用户拿到 B 语言的响应）；**多写的后果是"打不中"**（每份副本都只被极少数人用）。**两者都是错，但漏写更危险** —— 它是正确性问题。

**⚠️ 一个特别危险的组合**：把 `Cookie` 放进 `Vary` 看起来很"正确"（确实每用户不同），实际效果是**让 CDN 完全失效**。正确做法是**这类响应根本不该被共享缓存**（用 `private` 或 `no-store`）。

## 3.5 四种发布策略

`D6.L4.01`。这是本章 D0 完全没有覆盖的部分。

### 判据：三个维度

| 维度 | 问什么 |
|---|---|
| **切换粒度** | 一次性全切，还是能按比例/按人群切 |
| **可回退性** | 回退要多久、要不要重建 |
| **资源成本** | 是否需要双倍环境/双倍流量 |

### 四种策略

| 策略 | 做法 | 切换粒度 | 回退 | 成本 |
|---|---|---|---|---|
| **重建式**（recreate） | 停旧、起新 | **全量一次性** | 再切回旧版（**期间有中断**） | 最低 |
| **蓝绿**（blue-green） | 两套环境并存，切流量 | 全量，但**切换是原子的** | **切回另一套**（秒级） | **双倍环境** |
| **金丝雀**（canary） | 先放**小比例流量**到新版，逐步扩大 | **按流量比例** | 停止扩大 + 切回 | 双倍流量（短期） |
| **灰度 / A-B** | 按**用户/人群**分流 | **按用户维度** | 把该人群切回 | 需要分流能力 |

### 最容易混的一对：金丝雀 vs 灰度

**这两个词在团队里经常被混用，但机制完全不同**：

| | 金丝雀 | 灰度（按用户） |
|---|---|---|
| 分流依据 | **请求的比例**（如 5% 流量） | **用户的身份/分组** |
| 同一用户会不会看到两个版本 | **会**（每次请求可能落到不同版本） | **不会**（一旦分到某组，就固定） |
| 需要什么 | 能按比例分流 | **分流 + 用户粘性** |
| 适合什么 | 无状态、可重入的服务 | **有状态、有本地缓存的前端** |

**第三行是关键**：**前端产物是有状态的**（第 1 章讲的索引 + hash 文件）。如果同一用户一会儿拿到版本 A、一会儿 B，**会触发"旧 HTML 指向新资源"或反之的错配** —— 而这正是第 1 章 §1.2 说的白屏成因。

> **所以对静态前端产物，"按流量比例"的金丝雀必须配合"用户粘性"才能安全使用**，否则它退化成灰度的坏版本。

**这条判断在本章里最实用**：它解释了很多团队"做了金丝雀但还是出问题"的原因 —— 流量被随机分配，用户在两套产物间跳。

### 所有策略的隐藏前提

**四种策略都建立在一个前提上**（第 2 章 §2.7）：

> **任意版本可部署。**

| 如果没有这个前提 | 后果 |
|---|---|
| 蓝绿 | 无法"切回另一套"（另一套不存在或不是指定版本） |
| 金丝雀 | 无法"停止扩大并切回" |
| 灰度 | 同上 |
| 只剩重建式可用 | **每次回退都要重新构建，期间中断** |

**所以"发布策略"不是独立选型，它依赖"制品可归档、可按编号部署"这条基础设施。** 先做第 1、2 章，再谈策略。

### 回退判据：回退速度要快于故障扩散速度

这是判断一个策略是否够用的**唯一硬指标**：

| 量 | 怎么估 |
|---|---|
| **故障扩散速度** | 从新版本上线到"大部分用户受影响"要多久 |
| **回退耗时** | 从决定回退到"旧版本重新服务"要多久 |

**要求：回退耗时 < 扩散速度。** 否则"能回退"在事实上没有意义 —— 你退完时已经全量受害了。

**四者的这个比值**：

| 策略 | 回退耗时 | 是否够快 |
|---|---|---|
| 重建式 | 分钟到小时（要重建） | **常不够** |
| 蓝绿 | 秒级（切流量） | 通常够 |
| 金丝雀 | 秒级（停止扩大） | 通常够 |
| 灰度 | 秒级（切回该人群） | 通常够 |

### 一条反直觉：灰度不是"降低了风险"，而是"缩小了影响面"

**它不减少故障发生的概率** —— 新版本该有的 bug 一样有。它做的是：**让 bug 只影响一部分用户，并给你时间发现它。**

**所以灰度必须配"能判定好坏"的能力**：

| 缺什么 | 后果 |
|---|---|
| **没有指标** | 灰度变成"把故障延后"，因为你不知道小流量里已经有问题 |
| **没有基线** | 无法判断某个指标变化是不是新版引起的 |
| **没有告警** | 只能靠用户投诉发现 |

**这就是灰度与可观测性的绑定关系**（第 4 章）：**没有观测能力的灰度，只是一次更慢的全量发布。**

## 3.6 治理动作：六个判定阈值

与前面同体例。**全部是起点值，需按项目校准。**

| # | 现象 | 判定阈值（起点值） | 动作 | 依据 |
|---|---|---|---|---|
| 1 | 配了 SWR，浏览器有效、CDN 无效 | **CDN 命中时仍回源** | 查该响应有没有 `s-maxage`（它内建 `proxy-revalidate`，会禁止发 stale） | §3.2 |
| 2 | 源站故障时用户看到旧内容（或反之） | **任意一次源站 5xx 时 CDN 的行为与预期不符** | 检查有没有 `must-revalidate`：有则**必须返 504**，不返旧内容 | §3.1 |
| 3 | 用户拿到了别人的数据 | **任意一次跨用户串数据** | 查该响应是否缺 `private`（共享缓存不得存） | §3.1 |
| 4 | 缓存命中率异常低 | **命中率 < 60%** | 查 `Vary` 的维度数；`Vary: Cookie` 一类等于自毁缓存 | §3.4 |
| 5 | 回退之后仍有用户是坏版本 | **回退后 30 分钟仍有 > 1% 的异常版本** | 检查是否只 purge 了 CDN 而**管不到浏览器** | §3.4 |
| 6 | 做了灰度但问题照样全量暴露 | **一次灰度期内的故障未在小流量阶段被发现** | 灰度缺指标/告警，或分流未做用户粘性 | §3.5 |

### 三条使用说明

**① 阈值 1 与 2 是本章的"专业判断"分界线。**

它们不会报错，只表现为"配置没效果"或"故障时行为不符合直觉"。**只有理解 RFC 9111 的指令优先级才能查出来。**

**② 阈值 3 是安全事件，不是性能问题，优先级最高。**

跨用户串数据属于**数据泄露**，必须按事故处理。

**③ 阈值 5 与 6 都指向同一个误区：以为"发布/回退"能控制所有人。**

- 阈值 5：**浏览器侧的副本不在你的控制范围内**；
- 阈值 6：**灰度只缩小影响面，不减少故障**。

### 什么时候"不该做灰度"

| 情况 | 为什么 |
|---|---|
| **没有指标与告警** | 灰度变成"更慢的全量发布"（§3.5） |
| **产物无法按用户粘性分流** | 前端有状态，随机分流会导致新旧错配 |
| **故障是"全量必然发生"的**（如配置错误） | 灰度只会让同一错误扩散得更慢，不如先修 |
| **回退耗时 > 故障扩散速度** | 退不回来，"能灰度"没有意义 |

## 3.7 动手

**每一项都要求说出理由**：

| 任务 | 验收 |
|---|---|
| 用 `curl -I` 查你站点三类资源的响应头：HTML / 带 hash 的 JS / 带用户数据的接口 | 逐项说出 CDN 与浏览器**各自**会怎么处理（§3.1 的表） |
| 找一个配了 `stale-while-revalidate` 的响应 | 说出它有没有同时配 `s-maxage`；若有，解释为什么 CDN 上可能不生效 |
| 对同一个 URL 分别用浏览器与"绕过缓存"的方式请求，比对响应头 | 说出 `Age` / 命中标识的差异，以及这证明了"两个角色判法不同" |
| 检查所有含用户数据的响应是否有 `private` | 说出缺了会发生什么（按事故而非性能问题描述） |
| 列出一个响应的 `Vary` 全部维度，估算副本数 | 说出如果再答应一个语言维度，命中率会怎么变 |
| 找一个 `must-revalidate` 的资源，说明"源站挂了怎么办" | 说出 504 与"发旧内容"两种选择各自的取舍 |
| 查一次你的 `immutable` 用法 | 说出它有没有配合 `max-age`；若无，解释为什么单独写没意义 |
| 画一次"回退流程"，量它的耗时 | 与"故障扩散速度"比较，判断这个策略是否够用 |
| 写出你的灰度策略属于"按流量"还是"按用户" | 说出前端产物下"按流量"需要补什么（用户粘性） |
| 查一次灰度期间的观测手段 | 说出如果没有指标，灰度与全量发布的实质差别是什么 |

**进阶挑战**（任选一项）：

1. **做一次"缓存角色对照表"**：把站点所有响应类型列出来，标出"浏览器 / CDN"各自的行为与预期是否一致。目标是找出**"本地测不出、CDN 上不同"**的那几行 —— 它们是最难查的一类问题。
2. 给一个真实功能设计灰度方案：要求写清分流依据（流量还是用户）、粘性怎么保证、**判定好坏的指标是什么**、回退耗时估计。若写不出指标，说明这个灰度不该做。
3. 把 §3.5 的四种策略与第 2 章的"任意版本可部署"做一次依赖检查：逐条列出"如果只能重建式部署，哪些策略不可用"。

## 3.8 本章常见误区

| # | 误区 | 纠正 |
|---|---|---|
| 1 | "CDN 就是浏览器的缓存，规则一样" | **角色不同**：CDN 是**共享缓存**，浏览器是**私有缓存**。`s-maxage` / `private` / `proxy-revalidate` 三个指令就是为这个区分而存在 |
| 2 | "`s-maxage` 是 `max-age` 的别名" | 它**只对共享缓存生效且覆盖 `max-age`**，还**内建了 `proxy-revalidate` 语义**。它是"CDN 短、浏览器长"的旋钮 |
| 3 | "配了 `must-revalidate`，源站挂了 CDN 会发旧内容" | **相反**。官方明确：缓存断连时**必须生成错误响应**（通常 **504**），而不是复用 stale |
| 4 | "含用户数据的响应不加 `private` 也没事" | **共享缓存不得存储**。缺 `private` 可能把 A 的数据发给 B —— 这是**数据泄露** |
| 5 | "`stale-while-revalidate` 能覆盖 `must-revalidate`" | **不能**。RFC 9111 §4.2.4 明确：**禁止性指令优先**（`no-cache` / `must-revalidate` / 适用的 `s-maxage` / `proxy-revalidate`） |
| 6 | "`s-maxage` 与 SWR 可以一起配，效果叠加" | **会冲突**。`s-maxage` 内建 proxy-revalidate 语义，被 RFC 9111 列为禁止发 stale 的指令之一 |
| 7 | "本地测 SWR 有效，说明配置没问题" | 浏览器是私有缓存，**不受 `s-maxage` 约束**。CDN 上可能完全不生效 |
| 8 | "RFC 5861 是标准" | 它是 **Informational（独立提交）**，官方自述"**不是 Standards Track 规范**" |
| 9 | "RFC 5861 定义了 SWR 与 `must-revalidate` 的优先级" | **它完全没有讨论**这一交互（规范性引用只有 RFC 2119 / 2616）。优先级是 **12 年后由 RFC 9111 §4.2.4** 补上的 |
| 10 | "stale 响应要带 `Warning` 头" | RFC 5861 确实这么要求（依据 RFC 2616），但 **`Warning` 已被 RFC 9111 废弃**。该要求**在现行体系中不再成立**（`Age` 仍有效） |
| 11 | "`stale-while-revalidate` 和 `stale-if-error` 差不多" | 前者优化**延迟**（先给旧的、异步更新），后者提高**可用性**（源站 5xx 时兜底） |
| 12 | "`immutable` 等于永久缓存" | **它只在新鲜期内有效，且自身不创建新鲜期**。单独写没有意义 |
| 13 | "`immutable` 能省掉所有复查" | **不能对抗强制刷新**（客户端应忽略它）；**非 HTTPS 上下文客户端 SHOULD 忽略它** |
| 14 | "配个超长 `max-age` 就等于不再请求" | 到期后浏览器**仍会发条件请求**。`immutable` 补的正是这个缺口 |
| 15 | "有 `immutable` 就不需要 `ETag` 了" | **不能替代验证器**。它只覆盖新鲜期内 |
| 16 | "purge 能让所有人立刻看到新内容" | **不能**。purge **管不到浏览器**，且多节点传播有延迟。换 URL 才是可靠手段 |
| 17 | "`Vary` 多写几个维度更安全" | 每多一个维度就多一倍数副本，命中率下降。**只放真的改变内容的头** |
| 18 | "`Vary: Cookie` 很严谨" | 实际等于**让共享缓存完全失效**。正确做法是这类响应**不该被共享缓存**（`private` / `no-store`） |
| 19 | "前端做按流量的金丝雀很安全" | 前端产物**有状态**（索引 + hash 文件）。随机分流会导致**新旧错配**，必须补用户粘性 |
| 20 | "有了蓝绿就随时能回退" | 前提是**任意版本可部署**（第 2 章）。没有这个前提只有重建式可用 |

>
> **本章核验的规范事实（2026-10-17）**：
> - **RFC 9111（STD 98，2022-06，Standards Track）**：`no-cache` **允许存储但用前必验**；`no-store` **不是可靠的隐私机制**；`s-maxage` **仅共享缓存、覆盖 `max-age`、内建 `proxy-revalidate` 语义**；`must-revalidate` 断连时**必须返错（通常 504）**；**`Warning` 已作废（§5.5）、`Pragma` 已弃用（§5.4）**。
> - **RFC 8246（2017-09，Standards Track）**：`immutable` 只在新鲜期内有效、**自身不创建新鲜期**、不能对抗强制刷新、**非认证上下文 SHOULD ignore**、**未给浏览器兼容列表**。
> - **RFC 5861（2010-05，Informational / 独立提交）**：`stale-while-revalidate` 与 `stale-if-error` 的定义；**它自己不与 `must-revalidate` / `no-cache` 交互**（该优先级由 RFC 9111 §4.2.4 补上）；**它要求 stale 响应带 `Warning` 头，而 `Warning` 已被 RFC 9111 废弃**。
>
> **⚠️ 一处必须注意的结论强度**：本章提出"**`s-maxage` 与 `stale-while-revalidate` 在共享缓存上存在冲突**"，依据是 RFC 9111 的条文推理，**不是任何官方文档的原文断言**。缓存实现在细节上的遵循程度差异很大，**实际行为必须实测**。本章据此把它写为"按条文存在冲突"，而不是"一定不生效"。
