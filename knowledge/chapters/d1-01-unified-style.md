## 1.1 门禁的力学：为什么"写进文档的规范"必然腐化

先建立一个判据。判断一条规范会不会被长期遵守，看它是否满足两个条件：

| 条件 | 含义 | 反例 |
|---|---|---|
| **可判定** | 能由机器给出是 / 否，不留解释空间 | "命名要清晰" —— 不可判定 |
| **被执行** | 违反时会产生**代价**，而不是产生"提醒" | "PR 里请检查缩进" —— 没有代价 |

只有可判定，规范就只是文档；只有被执行，规范会被绕过。**两者同时满足，规范才变成门禁。**

门禁的位置决定它的代价与强制力，四层从便宜到贵：

| 层 | 时机 | 相对代价 | 能否绕过 |
|---|---|---|---|
| **编辑器（LSP）** | 打字时 | 最低 | **能** —— 不装插件 / 关了提示即可 |
| **pre-commit 钩子** | `git commit` 时 | 低 | **能** —— `--no-verify`、`HUSKY=0` |
| **CI** | 推送后 | 高（等流水线） | **不能**（对普通开发者） |
| **发布前** | 上线卡点 | 最高 | 不能 |

这张表解释了一个常见的工程失误：**把门禁只放在 pre-commit 就以为"规范被强制了"**。pre-commit 是可以被单方面关闭的（§1.9），它是"省 CI 时间"的手段，不是"最终强制"的手段。真正不可绕过的是 CI —— 那属于 D6 交付与运维领域。

本章只讲前两层：**编辑器层与本地提交层**。这也是"统一写法"这件事的完整闭环 —— 写完代码的那一刻就被拦住，而不是等到推送之后。

## 1.2 ESLint 的执行模型：规则是"访问者"，不是"检查清单"

多数人对 ESLint 的心智模型是"它把文件逐行扫一遍，看到不符合规则的就报"。这个模型能解释 80% 的现象，但在需要排查"这条规则为什么没报"时会立刻失效。

### 真实管线

ESLint 处理一个文件的顺序是：

```
源码文本
  │
  ├─ 1. 解析（parser，默认 espree）→ AST（ESTree 形状）
  │      解析失败 → 产出 fatal 解析错误，后续步骤不再进行
  │
  ├─ 2. 构建 SourceCode 与 ScopeManager
  │      SourceCode  = 源码 + 注释 + tokens（供规则做文本级操作）
  │      ScopeManager = 作用域链与变量引用关系（供规则做"这个变量是谁"的判断）
  │
  ├─ 3. 遍历 AST，调用规则的 visitor
  │      每条已启用规则各提供一个 visitor 集合
  │
  ├─ 4. 收集 report() 产出的问题描述符
  │
  └─ 5. 汇总 fix → 若有修复，回到第 3 步重跑（见 §1.3）
```

**第 3 步是理解 ESLint 的关键。** 官方在「Custom Rules」页对 `create()` 的描述是：

> `create()` 返回一个对象，其中方法是 ESLint 在遍历 JavaScript 代码的抽象语法树时**用来"访问"节点**的回调。

也就是说，**规则不是一份"应该怎样"的清单，而是一组挂在节点类型上的回调**。规则作者写的是"当我visit 到某个 `IfStatement` 时做什么"，而不是"扫描到某一行时做什么"。

三个由此推出的结论：

**① 规则的键可以是节点类型、selector 或事件。** 键为节点类型（或 CSS 风格的 selector）时，ESLint 在**向下**遍历时调用；键写成 `"节点类型:exit"` 时，在**向上**遍历（离开该节点）时调用。此外还有一类键是**代码路径分析事件**，如 `onCodePathStart` / `onCodePathEnd` —— 官方提到共七个与代码路径相关的事件。

**② 为什么必须用遍历模型，而不是逐行扫描。** 因为绝大多数规则需要**上下文**，而上下文不是行能表达的：

| 规则想知道 | 行扫描能回答吗 |
|---|---|
| 这个 `return` 是否在回调函数里（`array-callback-return`） | 不能 —— 需要知道它在哪个函数体内 |
| 这个变量是否被使用过 | 不能 —— 需要作用域链 |
| 这个标识符解析到哪里 | 不能 —— 需要声明与作用域 |
| 这个 `else` 后面该不该换行 | 能，但需要 token 与注释信息 |

这就是 `SourceCode` 与 `ScopeManager` 存在的原因。`SourceCode` 提供 token 级能力（`getTokenBefore/After`、`getTokensBetween`、`isSpaceBetween`、`getLocFromIndex` 等）与作用域查询（`getScope`、`getDeclaredVariables`、`getAncestors`、`isGlobalReference`、`markVariableAsUsed`），以及 `ast`、`scopeManager`、`visitorKeys`、`parserServices`。

**③ 规则之间没有通信机制。** 官方文档没有为"规则执行顺序"或"规则互相通信"提供任何机制。`context.settings` 是**配置层的共享数据**，供多条规则读取同一份配置，它不是运行时通信。这个约束很重要：它意味着**一条规则不能依赖另一条规则先跑过**。

### `context` 的字段与一处必须记住的变更

`context` 是 `create()` 的唯一参数。当前字段集合：

| 类别 | 内容 |
|---|---|
| 身份 | `id`（规则 ID）、`filename`、`physicalFilename`、`cwd` |
| 配置 | `options`（**不含 severity**）、`settings`、`languageOptions`（`sourceType` / `ecmaVersion` / `parser` / `parserOptions` / `globals`） |
| 源码 | `sourceCode`（`SourceCode` 对象） |
| 输出 | `report(descriptor)` —— **唯一的方法** |

**这里有两个会直接导致"照抄旧代码就报错"的点：**

**其一，`context.getSourceCode()` 已被移除。** 官方原文：

> 早期版本的 ESLint 在 context 对象上支持过一些额外方法，**这些方法在新格式中已被移除，不应再依赖。**

正确的写法是 `context.sourceCode`。迁移文档也给出了一整张对应表，例如 `context.getCwd()` → `context.cwd`、`context.getFilename()` → `context.filename`、`context.getSourceCode()` → `context.sourceCode`，以及一个**没有替代品**的 `context.parserPath`。

**其二，`context.options` 里没有 severity。** 官方说明：severity 会先被校验并**剥离**，`context.options` 只包含 severity 之后的元素。也就是说 —— **一条规则无法知道自己被配成了 `warn` 还是 `error`**。

第二条有个实际后果：规则不能根据 severity 改变自己的报告详略。如果想让某种问题"在 CI 上算错、在本地只算提示"，做法是**在配置里改 severity**，不是让规则去感知它。

### `context.report()` 能报什么

描述符字段：

| 字段 | 作用 |
|---|---|
| `messageId`（推荐）或 `message` | 报什么。`messageId` 指向 `meta.messages` 中的条目，便于国际化与统一文案 |
| `node` 或 `loc` | 报在哪。至少给一个 |
| `data` | `message` 里的占位符数据 |
| `fix(fixer)` | 自动修复（见 §1.3） |
| `suggest` | 建议改动 —— **与 fix 不同，建议不参与多轮修复** |

`fix` 与 `suggest` 的分界是本章一个重要的机制点：**能被确定性地写回文件的才用 `fix`，需要人做判断的用 `suggest`。**

## 1.3 修复循环：为什么 `--fix` 要跑 10 遍

这是本章最容易踩坑、也最能说明"文档要读到实现约束"的一处。

### 官方文档的分工

先看 CLI 页面怎么说 `--fix`：

> 该选项指示 ESLint 尝试修复尽可能多的问题。修复直接写入实际文件，只输出**剩余未修复**的问题。

CLI 页到此为止 —— 它**没有**说修复要跑几轮。

再看「Custom Rules」页，同一件事的完整表述在那里：

> **应用修复后，ESLint 会在修复后的代码上再次运行所有已启用的规则**，可能应用更多修复。**这个过程最多重复 10 次**，或直到不再发现可修复的问题为止。此后，任何剩余的问题照常报告。

这就是本章的第一个方法论示范：**同一条机制事实散落在不同官方页上。** 只想"知道 `--fix` 怎么用"的人读到 CLI 页就够了；想知道"为什么我的修复和另一个规则打架"的人，必须读到规则作者视角的页面。**读文档的深度，取决于你要回答的问题。**

### 从"最多 10 轮"推出的三条工程结论

**① 规则不必自己检查"这样修会不会违反别的风格规则"。** 官方明确这一点：

> 由于首轮修复后所有规则都会再次运行，**规则无需自行检查**某个修复的代码风格是否会被其他规则报错。

官方给的例子：给对象键加引号时，随便选单引号或双引号即可 —— 若猜错，`quotes` 规则会报告并修复它。**多轮修复机制天然解决了"修复之间的风格协调"问题。**

**② 修复必须尽可能小。** 官方最佳实践原文：修复要"尽可能小"，因为**过大的修复会与其他修复冲突，阻止其被应用**。这解释了一个常见现象：写了一条"顺手把整个函数重排"的修复规则，结果它自己经常不生效。

**③ 冲突修复无法指定谁赢。** 官方说明：冲突修复指对源码同一部分做不同修改的修复，而**"无法指定应用哪一个冲突修复"** —— 例如两个修复都要改字符 0–5，则只应用其中一个。

`meta.fixable` 是**强制项**：缺少它而规则尝试产出修复时，ESLint 会抛错。这是一个刻意的设计 —— 强制规则显式声明"我会改你的代码"。

### 还有一类"不参与多轮"的输出：建议

`context.report()` 的 `suggest` 与 `fix` 有本质区别：官方说明**建议是独立应用的变更，不触发多轮修复**。若某条建议的 `fix` 返回空，ESLint 会把整条建议从 lint 输出中移除。

## 1.4 配置解析：flat config 与"到底哪个配置生效"

"规则配了却没生效"这类问题，九成出在配置解析上。要能排查，必须知道解析算法。

### 一处必须先知道的事实：`eslintrc` 已不存在

ESLint 官方「Migrate to v10.x」页的原文：

> ESLint v9 引入了基于 `eslint.config.js` 的新默认配置格式。**旧格式（使用 `.eslintrc` 或 `.eslintrc.json`）在 v9 中仍可通过把 `ESLINT_USE_FLAT_CONFIG` 环境变量设为 `false` 来启用。**
>
> **从 ESLint v10.0.0 起，旧配置格式不再被支持。**

同一页还列出：`FlatESLint` 与 `LegacyESLint` 这两个已弃用 API 已移除，应始终使用 `ESLint`；`Linter` 类的 `configType` 选项不能再设为 `"eslintrc"`。

**这一条对存量项目影响最大**：网上大量"`.eslintrc` 这样配"的资料已经失效。读者遇到配置不生效时，第一个要确认的问题就是**配置文件是哪一代格式**。

### 配置文件的名字与优先级

官方列举的文件名（放在项目根目录，导出一个配置对象数组）：

```
eslint.config.js
eslint.config.mjs
eslint.config.cjs
eslint.config.ts     （需要额外设置）
eslint.config.mts
eslint.config.cts
```

同名多文件时的优先级就是上表顺序 —— 且官方明确指出：**JavaScript 文件优先于 TypeScript 文件**。

TypeScript 配置文件的"额外设置"指的是运行器：Node.js 需安装 `jiti` ≥ 2.2.0（不会自动安装）；Node.js ≥ 22.13.0 可用 `--experimental-strip-types` 配合原生加载。**且官方特别说明：ESLint 不对你的配置文件做类型检查，也不应用 `tsconfig.json` 里的任何设置。** 这句话解决了本节开头那类困惑 —— 用 `.ts` 写配置并不等于配置被类型检查了。

### 查找算法：从文件向上找（v10 的默认行为）

官方原文：

> 在命令行运行 ESLint 时，它为每个目标文件确定配置的**方式**是：先在**包含该文件的目录**中查找，然后**逐级向上搜索祖先目录**，直到找到 `eslint.config.*` 文件。这个行为改善了对 monorepo 的支持 —— 子目录可以有自己的配置文件。

这条在 v9 与 v10 之间变过：v10 把"从被 lint 文件所在目录向上查找"设为了默认，而 v9 需要显式打开 `v10_config_lookup_from_file` 特性开关。**v10 里这个开关已被移除，继续使用会直接报错** —— 包括 CLI 的 `--flag`、`ESLINT_FLAGS` 环境变量、以及 API 的 `flags` 数组三种用法。

**工程含义**：monorepo 里每个子包可以各有 `eslint.config.js`，各自向上搜索会先命中自己那份。这正是官方说"改善 monorepo 支持"的意思。若你依赖旧的**基于 cwd** 的查找行为，要显式传 `--config path/to/eslint.config.js`。

### 一个配置对象里的字段

官方对关键字段的定义（择要逐字）：

| 字段 | 官方定义 |
|---|---|
| `name` | 配置对象的名字，用于错误消息与 config inspector 中标识是哪一个配置生效 |
| `basePath` | 该配置对象适用的子目录路径 |
| `files` | glob 数组，指明该配置适用的文件。**若不指定，则该配置对象适用于任何其他配置对象匹配到的所有文件** |
| `ignores` | glob 数组。**若在没有其他键的情况下单独使用，则这些模式作为全局忽略，并应用到每一个配置对象** |
| `extends` | 一个数组，元素为字符串、配置对象或配置数组，表示要继承的额外配置 |
| `languageOptions` | `ecmaVersion`（默认 `"latest"`）、`sourceType`（`.js`/`.mjs` 默认 `"module"`，`.cjs` 默认 `"commonjs"`）、`globals`、`parser`（默认 `espree`）、`parserOptions` |
| `linterOptions` | `noInlineConfig`、`reportUnusedDisableDirectives`（默认 `"warn"`）、`reportUnusedInlineConfigs` |
| `plugins` | 插件名到插件对象的映射。**指定 `files` 时，这些插件只对匹配的文件可用** |
| `rules` | 规则配置。指定 `files` 或 `ignores` 时同样只对匹配文件可用 |
| `settings` | 对所有规则可用的键值信息 |

**`extends` 的语义与 eslintrc 时代不同。** eslintrc 里 `extends` 只能写字符串（`"airbnb"`、`"plugin:x/recommended"`）；flat config 里数组元素可以是三类：

- 插件中某个配置的**名字符串**（如 `"example/recommended"`，前提是该插件已在 `plugins` 里注册）
- **配置对象**（如 `pluginExample.configs.recommended`）
- **配置数组**

官方还给了一条使用忠告：**用 `extends` 时建议总是同时写 `files`**，否则被扩展的配置可能落到所有文件上。

### 合并规则：后者覆盖前者

官方原文：

> 当多个配置对象匹配到同一个文件名时，这些配置对象**被合并**，发生冲突时**后面的对象覆盖前面的对象**。

注意这不是"深度合并成一份大配置"，而是**按顺序叠加、后写者胜**。习惯 eslintrc 级联的人常在这里判断错。

### `ignores` 的两种身份（一个高频陷阱）

`ignores` 有两副面孔，取决于它在配置对象里是不是**唯一**的键（`name` 除外）：

| 形态 | 判定条件 | 能力 |
|---|---|---|
| **全局忽略** | `ignores` 单独出现（除 `name`） | 可匹配**目录**；应用到每一个配置对象；**你的模式追加在 ESLint 默认模式之后**（默认是 `["**/node_modules/", ".git/"]`） |
| **非全局忽略** | 配置对象里还有别的键 | **只能匹配文件名** |

第二行就是那个陷阱，官方原文：

> 非全局的 `ignores` 模式**只能匹配文件名**。像 `"dir-to-exclude/"` 这样的模式**什么都不会忽略**。要忽略某个目录下的所有内容，应改用 `"dir-to-exclude/**"`。

还有两条容易忽略的：

- 默认被 lint 的文件是 `**/*.js`、`**/*.cjs`、`**/*.mjs` —— **除非用全局忽略显式排除，否则这些文件总会被匹配**。所以"我不想 lint `dist/`"必须用全局忽略。
- `files` 与 `ignores` 中的模式用 minimatch 语法，**相对于 `eslint.config.js` 所在位置求值**；若用 `--config` 指定了其他配置文件，则相对于**当前工作目录**。**这条差异是"本地有效、CI 上失效"的常见成因。**
- 想同时匹配两个条件时用嵌套数组：`files: [["src/*", "**/*.js"]]` 表示"既在 `src` 下、又以 `.js` 结尾"。

### 版本相关的其他变化（可能影响存量项目）

官方迁移页还列了若干条，择要：

| 变化 | 影响 |
|---|---|
| **Node.js 版本要求** | 支持 v20.19.0+、v22.13.0+、v24+；**不支持 < v20.19、v21、v23**。同时要检查编辑器集成用的 Node 版本 |
| **`eslint-env` 注释现在被报为错误** | `/* eslint-env */` 是 v8 时代的写法，不再支持 |
| **`eslint:recommended` 已更新** | 新增三条规则：`no-unassigned-vars`、`no-useless-assignment`、`preserve-caught-error` |
| **JSX 引用被追踪** | `<Card />` 现在算作对 `Card` 的真实引用，可能出现新的未使用变量报告（也可能是旧的 workaround 规则不再需要） |
| **Jiti < v2.2.0 不再支持** | 用 TypeScript 配置文件的用户需升级 |
| **`no-shadow-restricted-names` 默认变化** | `reportGlobalThis` 由 `false` 改为 `true` |
| **POSIX 字符类支持** | 新 minimatch 支持 `[[:upper:]]` 这类写法，含此类模式的 glob 需复核 |

官方给出的迁移起点是一个 codemod：`npx codemod @eslint/v9-to-v10`。但官方同时明确：**"codemod 只是起点"**，要人工复核并对照破坏性变更清单处理未覆盖的部分。

## 1.5 退出码与缓存：把 lint 接进流水线的两个硬约束

工具在本地跑和接进流水线是两件事。接进流水线只关心两个东西：**退出码**与**耗时**。

### 退出码：三个码，两类责任

官方原文：

| 退出码 | 含义 |
|---|---|
| **0** | lint 成功且没有 lint 错误；若设置了 `--max-warnings n`，则警告数**至多**为 `n` |
| **1** | lint 成功，但**至少有一个 lint 错误**，或警告数**超过** `--max-warnings` 允许的数量 |
| **2** | lint **不成功**，原因是**配置问题或内部错误** |

这张表最值得记住的是 **0 与 1 的区别不是"有没有问题"，而是"问题算不算错误"**；以及 **2 与 1 的区别是"代码有问题"还是"工具本身有问题"**。

工程含义：CI 上这两类要分流。退出码 1 → 通知提交者改代码；**退出码 2 → 通知规范维护者改配置**。把两者混在一起，就会变成"每次配置坏了都在群里 @ 提交者"。

关于 `--max-warnings` 有三个精确之处：

1. 判定条件是警告数**严格大于**阈值 —— **等于阈值仍然通过**。
2. 触发时走的是**退出码 1**，不是 2。
3. 与 `--quiet` 同时使用时，官方特别提醒：**标记为 `warn` 的规则仍然会被运行，只是不被报告**。这是刻意的 —— 若 `warn` 规则不跑，警告计数就无从统计，`--max-warnings` 就失效了。

### 缓存：一个"用正确性换速度"的开关

`--cache` 的官方描述是"存储已处理文件的信息，以便只对变更过的文件操作"。但**官方在同一段里给出了三条反直觉行为**，这三条才是它的真实边界：

**① 缓存文件的存亡取决于下一次怎么跑。**
> 如果你用 `--cache` 运行 ESLint，然后又**不带** `--cache` 运行，`.eslintcache` 文件会被删除。

默认位置是 `.eslintcache`，可用 `--cache-location` 改（`--cache-file` 已废弃）。"不带缓存跑一次就把缓存删掉"这个设计是为了避免缓存与结果不一致 —— 但它也意味着**缓存难以跨命令形态复用**。

**② 被自动修复过的文件不会进入缓存。**
> 被自动修复的文件不会被放入缓存。后续不触发自动修复的 lint 才会把它放入缓存。

**③ 缓存不跟踪文件之间的依赖。** 这是最重要的一条，官方原文说得很具体：

> ESLint 判断缓存结果是否仍然有效，依据是**该文件自身**（内容或元数据，取决于 `--cache-strategy`）与**配置**。它**不跟踪文件之间的依赖**，因此即使某个文件依赖的另一个文件变了，它的缓存结果依然会被复用。**结果依赖其他文件的规则可能因此报告过期结果。** 这包括**类型感知规则**（如 `@typescript-eslint/eslint-plugin` 中的规则），以及跨模块解析导入的规则（如 `eslint-plugin-import`）。

官方举了两个方向相反的例子：

- 某个模块的改动**在导入它的未改动文件里**引入了问题 —— `--cache` **不会**报告，直到那个导入文件或配置发生变化。
- 反过来，**已经在别处修好的问题**会被继续报告。

官方给出的结论很直接：**需要这类规则的准确结果时，就带不带 `--cache` 跑一次。**

**这一节落到一条工程结论**：`--cache` 不是"无脑开就更快"的优化，它是一个**权衡开关**。开它的前提是你清楚哪些规则会失效 —— 用了类型感知规则或跨模块导入规则的项目，在 CI 上就**不该**无条件开缓存。

## 1.6 Prettier 的边界：它解决的不是"更严格的格式"，而是另一类问题

Prettier 官方在「Integrating with Linters」页给出的职责边界是一句可以直接当判据用的话：

> **用 Prettier 处理代码格式问题，用 linter 处理代码质量问题。**

边界为什么必须划清，官方给了理由：

> Linter 通常不只有代码质量规则，**也有风格规则**。在用 Prettier 时，大多数风格规则是多余的 —— 而更糟的是，**它们可能与 Prettier 冲突**。

注意这句话的重心在"更糟的是"三个字。**多余的规则只是浪费，冲突的规则会让两个工具互相打架** —— 一个想改成 A，另一个立刻改回 B。这类现象在真实项目里表现为"每次保存文件都在跳格式"。

### 官方的解法：让 linter 闭嘴，而不是让 Prettier 去当规则

官方推荐的方案是使用现成配置来**关掉那些冲突或多余的规则**：`eslint-config-prettier`。

这个方向值得琢磨：它不是"把 Prettier 的能力接进 ESLint"，而是**把 ESLint 里与格式相关的判断权交出去**。两个工具各自负责一类问题，交界处**由一方主动退出**，而不是双方争夺。

### 对 `eslint-plugin-prettier` 的官方立场

有一个流传很广的做法：用 `eslint-plugin-prettier` 把 Prettier 当作一条 ESLint 规则来跑。官方的立场写得比较含蓄，但在「NOTES」里说得很清楚：

> 在互联网上搜 Prettier 和你的 linter 时，你大概会找到更多相关项目。**这些通常不被推荐，但在某些情况下可能有用。**

针对"把 Prettier 当 linter 规则跑"的插件（`eslint-plugin-prettier`、`stylelint-prettier`），官方解释了这个做法的历史来历，并列出**三条缺点**：

1. **编辑器里会满屏红波浪线，很烦人。** 原文语气很鲜明："**Prettier 本应让你忘记格式这件事 —— 而不是把它怼在你脸上！**"
2. **比直接跑 Prettier 慢。**
3. **它们又是多出来的一层间接，可能出问题。**

官方给的历史解释是：这些插件**在 Prettier 还很新的时候特别有用** —— 那时你不需要搭任何新基础设施，可以直接复用编辑器的 linter 集成。但现在**可以直接跑 `prettier --check .`**，且大多数编辑器都原生支持 Prettier。

**「Prettier 本应让你忘记格式这件事」这句话是理解这个工具的设计意图的钥匙**：它的目标不是"让人看到格式问题"，而是"让格式问题不再需要被看到"。

### 一处引用精度

需要说明的是：官方页面里**没有**一句字面上的"禁止把 Prettier 当 lint 规则"。它表达立场的方式是"通常不被推荐"加上三条具体缺点。本书引用时用官方原话 **"generally not recommended"**，而不是写成"官方禁止" —— 这是本书引用规范的一个实例：**不把"不推荐"加重成"禁止"。**

另外官方还提到一类工具（`prettier-eslint` / `prettier-stylelint`，先跑 Prettier 再自动 `eslint --fix`）：官方说它们"**在你无法接受 Prettier 输出某些方面的结果**"时有用，代价是**比直接跑 Prettier 慢得多**。

## 1.7 Stylelint：CSS 侧的规则模型与一处语义不对称

Stylelint 是 CSS 侧的同类工具，它的规则模型有几处与 ESLint 不同的地方，这些差异直接决定配置怎么写。

### 配置查找与文件格式

优先格式是 `stylelint.config.js`（另有 `.mjs` / `.cjs` / `.ts`），**同样是从当前工作目录向上查找直到找到为止**。

`.stylelintrc` 系列（`.stylelintrc`、`.stylelintrc.json`、`.stylelintrc.yml`、`.stylelintrc.js` 等）以及 **`package.json` 里的 `stylelint` 字段**仍然支持，但官方把它们归入了"**未来可能移除**"的清单并给出警告。

这与 ESLint 的路径不同：ESLint 是**直接移除**旧格式，Stylelint 是**先标记再移除**。两种做法都会让"照抄网上配置"失效，只是失效的时点不同。

### `rules`：100+ 条内置规则，默认全部关闭

这是与 ESLint 最大的模型差异：

> （Stylelint）内置 **100+ 条规则**，**默认全部关闭**，需显式开启。

ESLint 有一个 `eslint:recommended` 作为"默认就有意义"的起点；**Stylelint 没有默认开启集合**。所以 Stylelint 的实际用法是：先 `extends` 一份共享配置（如 `stylelint-config-standard`），再在其上加自己的规则。这也解释了为什么"装完 Stylelint 却发现什么都没报"是常见的第一反应。

规则的取值形式有三种：`null`（关闭）、单值（开启并给 primary option）、二元数组 `[primary option, secondary options]`。另有一处实用能力：**字符串形式的 `"/regex/"` 会被解释为正则**，部分规则的**对象键**也支持正则（如 `"/^margin/"` 可匹配 `margin`、`margin-top`、`margin-inline`）。

### 五条通用 secondary options（跨所有规则）

这几条比单条规则更常被用到：

| 选项 | 作用 |
|---|---|
| `disableFix` | 按规则**禁用自动修复** |
| `message` | 自定义报错文案，支持 printf 风格 `%s` 或函数形式（可用消息参数） |
| `url` | 自定义外部文档链接，供自定义 formatter 展示 |
| `reportDisables` | **把该规则的 `stylelint-disable` 注释本身报为 lint 错误** —— 即禁止作者 opt-out |
| `severity` | `"warning"` 或 `"error"`（默认），也支持函数形式，返回 `null` 时回退到 `defaultSeverity` |

**`reportDisables` 值得单独说一句**：它是把"逃生通道"本身纳入检查。这与 §1.1 的门禁理论直接相关 —— 任何门禁都有绕过手段，`reportDisables` 的作用是**让绕过留下痕迹**。

### `extends` 与 `overrides`

`extends` 的语义是"**起始于对方属性，再追加与覆盖**"，数组时**后者覆盖前者**（最后一项优先级最高）。它的值是一个"locater"，最终会被 `require()`，因此需符合 Node 的 `require.resolve()` 算法：可以是 `node_modules` 里的模块名、带扩展名的绝对路径，或**相对于引用它的那个配置文件**的相对路径。被扩展的配置**自身还能再 `extends`**。

`overrides` 是本章最值得记的一处**语义不对称**：

| 属性 | 在 `overrides` 里的合并方式 |
|---|---|
| `customSyntax` | **替换** |
| `plugins` / `extends` / `rules` 等 | **追加** |

也就是说，`overrides` 里写 `customSyntax` 是"换掉这个文件类型的解析器"，而写 `rules` 是"叠加规则"。另外：**`overrides` 优先级高于常规配置**，同一份配置里多个 `overrides` 按顺序生效、**最后一个块优先级最高**；匹配基准是**相对于配置文件所在目录**的路径（配置文件在 `/project-foo/`、被检查文件是 `/project-foo/components/bar.css` 时，glob 匹配的是 `components/bar.css`）。

### 两个静默的坑

**坑一：`cache`、`allowEmptyInput`、`fix`、`maxWarnings` 不应按文件覆盖。** 官方明确标注这四个配置项不能被 per-file 覆盖 —— 它们是**全局运行行为**，不是文件级规则。

**坑二：`ignoreFiles` 一旦设置，会覆盖"默认忽略 `node_modules`"的行为。** 官方提示：文件很多时改用 `.stylelintignore` 或调整 `files` glob 更高效。

### 与 Prettier 的关系（一处诚实的缺口）

Stylelint 的配置页**完全没有提到 Prettier**，也没有出现任何"格式化交给 Prettier"的说明。因此从该页**无法**得出 `stylelint-config-prettier` 是否废弃的结论。

【待验证】社区普遍的做法是：Stylelint 15 移除了全部代码格式相关规则，因此 `stylelint-config-prettier` **不再必要**。**这一结论不在本节所引的官方配置页范围内**，本书不给确定性结论 —— 用前请查该包的仓库说明与 Stylelint 迁移指南。

## 1.8 环境统一：把不确定性从工具里挤出去

到这里出现一个问题：ESLint、Prettier、Stylelint 的行为，**都依赖运行环境**。同一份代码在两台机器上给出不同结果时，问题不在代码，在环境。

### EditorConfig 的解析规则

EditorConfig 的官方描述是三条规则：

> 遇到**根文件路径**或**含 `root=true` 的 EditorConfig 文件**时停止；EditorConfig 文件**自上而下读取，最后找到的规则取得优先**；匹配的 EditorConfig 文件中……

这三条对应三种行为：

| 规则 | 含义 |
|---|---|
| **向上查找** | 从被编辑文件所在目录向上逐级找 `.editorconfig` |
| **`root = true` 截止** | 遇到即停止上溯 —— 这是"项目边界"的声明。**漏写会导致继承机器上层的配置** |
| **同文件内后出现的规则覆盖先出现的** | 所以通用规则写在前面、特例（如 `[*.md]`）写在后面 |

**规范归属必须说清**：EditorConfig **不是标准化组织规范**，它由 `editorconfig.org` 与 `editorconfig-specification` 仓库定义。这与本书对 Node.js、Git、TypeScript 的处理一致 —— 引用时要说明"以谁为准"。

### `.nvmrc` 与 `engines` 的强制力差异

这条在 D0 第 7 章 §7.2 已经讲过一次，这里补上它在门禁链条里的位置：

| 机制 | 性质 | 强制力 |
|---|---|---|
| `.nvmrc` | 版本管理器的**读取约定**（多个工具都在读同一个文件） | **弱** —— 不切换也能跑 |
| `package.json` 的 `engines` | npm 的**声明字段** | **弱** —— 默认只警告 |
| `engines` + `engine-strict`（或在 CI 里显式校验） | 变成可执行的检查 | **强** |

**为什么它和 lint 放在同一章**：因为 §1.4 已经说明 ESLint 的配置解析与 Node.js 版本强相关（v10 要求 Node ≥ 20.19），而 Prettier、Stylelint 的行为也随版本变化。**环境不统一时，"规范"这件事本身就不可复现。**

### 编辑器是第一层门禁，也是唯一可绕过的一层

D0 第 7 章 §7.3 讲过 LSP 把约定前移到编辑期。这里补上它在四层门禁里的定位（回到 §1.1 的表）：

- 编辑器的好处是**反馈最快**，代价是**最容易被绕过**：换台机器、换个编辑器、关掉插件，门禁就没了。
- 因此编辑器的配置（`.vscode/settings.json`、`extensions.json`）的正确目标不是"强制"，而是**让默认路径上的人不犯错**。真正的强制交给 pre-commit 和 CI。

## 1.9 Git Hooks：从"能绕过"到"绕不过"

### Husky 做了什么

官方给出的最小路径是两条命令：

```shell
npm install --save-dev husky
npx husky init
```

`husky init` 的行为，官方原文：

> 它在 `.husky/` 下创建 `pre-commit` 脚本，并更新 `package.json` 里的 `prepare` 脚本。

三个值得注意的设计点：

**① 它用的是 Git 的 `core.hooksPath` 机制。** 官方特性列表里明确写到使用 Git 的新特性 `core.hooksPath`。这意味着 Husky 不是"往 `.git/hooks` 里写文件"，而是**把钩子目录整体指向 `.husky/`** —— 于是钩子脚本能进版本控制、能被团队共享。这是它相比"手写 `.git/hooks/pre-commit`"的根本差别：**后者不会随仓库分发**。

**② 它挂在 `prepare` 而不是 `postinstall`。** 官方把"遵循 npm 最佳实践使用 `prepare` 脚本"列为特性之一。`prepare` 在 `npm install` 与发布前都会运行，语义是"准备开发环境"——比 `postinstall` 更贴合意图。

**③ 它刻意不强制。** 官方原文：

> Husky 不强制 Git hooks。它可以被全局禁用（`HUSKY=0`），也可以按需改为 opt-in。

**`HUSKY=0` 是本节的机制要点**：它同时是逃生通道与风险。团队里任何人可以在自己的环境里把它关掉，然后 commit 一份 lint 不通过的代码。这不是 Husky 的缺陷，而是**本地门禁的固有上限**（回到 §1.1：pre-commit 层"能"被绕过）。所以它必须由 CI 兜底。

**一处诚实标注**：Husky 官方文档首页与 Get Started 页**都没有给出主版本号**，也没有明确说明旧版中的辅助脚本 `_/husky.sh` 是否已被移除。本书不推测这一点。可以确认的是：**Get Started 页给出的 `.husky/pre-commit` 示例是普通 shell 文件，源码中不含任何 source 辅助脚本的语句**，官方称其为"无需外部依赖的两行 shell"。

### 钩子本身不检查代码 —— lint-staged 才检查

一个必须澄清的层次：**Git 钩子只是"在提交时执行某段命令"的机制**，它自己不检查任何东西。Husky 与 lint-staged 是两个不同的东西：

| 组件 | 职责 |
|---|---|
| **Husky** | 把钩子目录指向 `.husky/`，让钩子脚本能被团队共享 |
| **lint-staged** | 决定**对哪些文件跑哪些命令**，并处理跑的过程中对工作区的改动 |

它们的分工在官方示例里一目了然 —— `.husky/pre-commit` 的全部内容就是：

```shell
# .husky/pre-commit
npx lint-staged
```

官方在这里附了一条容易忽略的提示：**不要给 runner 传路径参数** —— "这很重要，因为 lint-staged 会替你传。"

### 前向引用：`commit-msg` 钩子

pre-commit 之外，团队通常还会挂 **`commit-msg`** 钩子做**提交信息校验**（如 Commitlint），二者是不同的钩子、不同的执行时机：`pre-commit` 在**生成提交对象之前**，`commit-msg` 在**提交信息确定之后、提交完成之前**。

Commitlint、Commitizen 与 CHANGELOG 生成的完整机制属于 `D1.L2.05`，本章只交代到这里 —— **待 `D1.L2.05` 写完后在本节回链补全**。

## 1.10 lint-staged：它到底对你的仓库做了什么

这是本章机制最密集的一节。绝大多数人把 lint-staged 理解为"只对暂存文件跑命令"，但它的真实行为包含**五次 git 操作与一个备份 stash** —— 这些操作是有副作用的，不知道它们，就无法解释失败时看到的现象。

### 输入不是"改过的文件"，而是 git index 里的路径

官方对执行流程的描述：

> 自动解析 git 根目录，无需配置。**选取位于项目目录内、且处于暂存状态的文件。** 用指定的 glob 模式过滤它们。**以绝对路径作为参数传给任务。**

三句话对应三个机制点：

1. **数据来源是 index**（等价于 `git diff --staged`），默认 diff-filter 是 `ACMR`（新增 / 复制 / 修改 / 重命名），可用 `--diff` / `--diff-filter` 覆盖。
2. **过滤用 picomatch 的 glob 语义** —— 与 ESLint 的 minimatch 不是同一套实现，模式可能表现不同。
3. **它自己传绝对路径**。这解释了官方那句"不要传路径参数"。

### 五次 git 操作（官方原文的五个步骤）

官方对"stashing 如何工作"给了完整答案：

| 步骤 | 操作 | 目的 |
|---|---|---|
| **1** | 用 `git stash create` 加 `git stash store` 把**整个原始状态备份到一个 stash** | 备份。注意：**它默认保留工作区的所有文件** —— 而普通的 `git stash` 命令还会把文件从工作区移除 |
| **2** | 若某文件是"**部分暂存**"（同一文件里既有已暂存也有未暂存的改动），把这些改动**额外存成 patch 文件**（`.git/lint-staged_unstaged.patch`），并**从工作区移除**这些未暂存改动 | 让任务**只看到已暂存的内容** |
| **3** | 任务跑完后，把对已跟踪文件的**新改动加入 index** | 让自动修复的结果**进入这次提交** |
| **4** | 把第 2 步的 patch **应用回去**，恢复未暂存改动 | 恢复你的工作区 |
| **5** | 出错时用 `git reset` 复位并从第 1 步的备份 stash 恢复；**stash 只在最后一步、即前面所有步骤都成功之后才会被 drop** | 失败可恢复 |

**第 2 步是理解 lint-staged 全部争议的钥匙。** "部分暂存"在真实开发里极其常见：你改了三处，只想提交其中两处。lint-staged 的应对是**把第三处暂时藏起来**，让 lint 只看到你打算提交的内容。如果不这么做，lint 会检查到不该进入本次提交的改动，并把格式修复写进文件 —— 从而污染你的暂存区。

**第 5 步的顺序值得记住**：备份 stash **只在全部成功后**被删除。这就是为什么失败之后你的改动**一定还在**两者之一：要么在工作区，要么在 stash 里。

官方给出的手动恢复方法：

```shell
> git stash list --format="%h %s"
On main: lint-staged automatic backup
> git apply --index
```

### 那个危险的开关

```
--no-hide-partially-staged   hide unstaged changes from partially staged files (default: true)
```

官方对它的说明：

> 默认情况下，部分暂存文件中的未暂存改动**会被隐藏，并在任务跑完后应用回去**。此选项会**禁用**该行为，导致那些改动**也被一起提交**。

**这是一个"关掉就更方便，但会提交你没打算提交的代码"的开关** —— 它把 lint-staged 的核心安全机制关掉了。与之相邻的还有两个：`--hide-unstaged`（隐藏**所有**未暂存改动，而不只是部分暂存文件里的）与 `--hide-all`（连未跟踪文件一起隐藏，官方举的用例是跑 Knip 这类检查未使用代码的工具）。

### 失败时的默认行为

| 选项 | 默认 | 含义 |
|---|---|---|
| `--no-revert` | `revert` 为 `true` | **出错时把所有任务改动回滚到原始状态**。关掉它则任务改动会在中止提交前被应用到 index |
| `--continue-on-error` | 关闭（即"提前退出"） | 默认**任一任务失败就提前退出**，以保证运行时间短。打开后会跑完所有任务、最后统一失败，**让所有任务的输出都被看到** |
| `--fail-on-changes` | 关闭 | 默认任务产生的改动会被自动暂存进提交；该 flag 让 lint-staged 以**退出码 1 失败**，且**隐含 `--no-revert`**（改动留在工作区，供手动暂存后重试） |
| `--allow-empty` | 关闭 | 若任务撤销了全部暂存改动，默认报错并中止提交；此 flag 允许创建空提交 |

**`--fail-on-changes` 值得单独说**：它是"只要求格式化、不要求改动被提交"的用法 —— 让开发者自己决定要不要带上格式改动。代价是**它隐含 `--no-revert`**，失败时改动留在工作区。

### 并发：一个容易读错的默认值

```
-p, --concurrent   the number of tasks to run concurrently, or false for serial (default: true)
```

| 取值 | 行为 |
|---|---|
| `false` | 所有任务串行 |
| `true`（默认） | **无限并发** —— 尽可能多地并行跑 |
| `{数字}` | 并行指定数量的任务（`1` 等价于 `false`） |

官方特别标注：**它不影响子任务的并发（子任务总是串行执行）**。这里的层级关系是：**每个 glob 是一个"任务"**，任务之间受 `--concurrent` 控制；同一 glob 关联多条命令时，用数组让它们串行：

```json
{
  "*.ts": ["prettier --list-different", "eslint"],
  "*.md": "prettier --list-different"
}
```

要在某个 glob 内并行，则**再嵌一层数组**：

```json
{
  "*.ts": [["prettier --list-different", "eslint"]],
  "*.md": "prettier --list-different"
}
```

启动顺序的例子（`{ "*.ts": ["first", "second", ["third", "third"], "fourth"] }`）说明了这个嵌套结构的真实语义：`first`、`second` 串行，`third` 两个实例并行，`fourth` 在它们之后。

### 竞态：glob 重叠 + 任务会改文件

官方给了一条明确警告：**当配置的 glob 重叠、且任务会对文件做修改时，要格外注意。**

反例：

```json
{
  "*": "prettier --write",
  "*.ts": "eslint --fix"
}
```

`*.ts` 文件同时匹配两个 glob，于是**两个进程可能同时改同一个文件**。官方给出的解法是把重叠消掉：

```json
{
  "!(*.ts)": "prettier --write",
  "*.ts": ["eslint --fix", "prettier --write"]
}
```

注意解法的形状：**先 `eslint --fix`（可能改动代码），再 `prettier --write`（把格式统一）**，顺序不是随意的 —— 反过来的话 Prettier 的格式结果会被 `--fix` 打乱。

或者退一步：用 `--concurrent <数字>` 限制并发，或 `--concurrent false` 彻底关掉。

### 配置文件与官方示例

支持的形式：`package.json` 的 `lint-staged` 字段（或 `package.yaml`）、`.lintstagedrc`（JSON 或 YML）、`.lintstagedrc.json` / `.json` / `.yaml` / `.yml`、`.lintstagedrc.mjs` 或 `lint-staged.config.mjs`（ESM）、`.lintstagedrc.cjs` 或 `lint-staged.config.cjs`（CJS）、`lint-staged.config.js` / `.lintstagedrc.js`（按 `package.json` 的 `"type"` 决定 ESM 还是 CJS）、以及 `defineConfig` 助手与 `.ts` 配置（需 Node 22.6+ 的 `--experimental-strip-types`，v23.6.0 起无需 flag）。

官方 Examples 里的常见配置：

```json
{ "*.{js,jsx}": "eslint" }
{ "*.js": "eslint --fix" }
{ "*.js": "npm run my-custom-script --" }
{ "*": "prettier --ignore-unknown --write" }
{ "*.css": "stylelint", "*.scss": "stylelint --syntax=scss" }
```

官方还标注了两条限制：**任务命令不支持 shell 展开**（传环境变量需借助 `cross-env`）；**`ng lint` 这类面向整个项目的命令不建议通过 lint-staged 运行**。

## 1.11 一条完整的本地门禁链，以及它的盲区

把本章内容串起来，本地门禁的完整形状是：

```
编辑器：.editorconfig + 编辑器设置 + LSP
   │   作用：即时反馈。代价：最低。可绕过：能（换机器/关插件）
   ▼
git commit
   │
   ├─ pre-commit（Husky → lint-staged）
   │     1. 取出 index 里的路径
   │     2. 备份 stash + 隐藏部分暂存的未暂存改动
   │     3. 按 glob 分组、并发跑 ESLint / Prettier / Stylelint
   │     4. 修复结果写回 index
   │     5. 恢复工作区
   │   作用：拦住"这次提交引入的新问题"。代价：低。可绕过：能（--no-verify / HUSKY=0）
   │
   └─ commit-msg（Commitlint）  →  D1 第 2 章
   ▼
CI（全量 lint + 类型检查 + 测试）  →  D6 交付与运维
        作用：唯一不可绕过的强制层。代价：高
```

### 三个必须点明的盲区

**盲区一：lint-staged 只检查改动文件，因此它不能替代全量检查。** 它保证的是"这次提交没引入新问题"，而"存量问题在收敛"需要全量检查（CI 层）。这两件事的目标不同，不能互相替代。

**盲区二：`--cache` 与 lint-staged 叠加会产生双重盲区。** §1.5 已经说明缓存**不跟踪跨文件依赖**，而 §1.10 说明 lint-staged **只看改动的文件**。两者叠加时的极端情形是：你改了 `utils.ts` 的导出，lint-staged 只检查 `utils.ts`（它自己没问题），而依赖它的 `page.ts` 既不在暂存区、又可能命中缓存 —— 问题要等到 CI 全量检查时才出现。

**盲区三：本地门禁的一切都可以被单方面关闭。** `HUSKY=0`、`git commit --no-verify`，都是合法的 git 用法。这不是设计缺陷，而是**层次分工**：本地层负责"快速反馈"，CI 层负责"强制"。把规范最终寄托在本地层，等于寄在一个可以关掉的开关上 —— 这正是 §1.1 那张门禁表要说明的事。

## 1.12 实战：一个团队的规范是怎么长出来的

> **说明**：这一节是一条**构造示例** —— 它不是某个真实团队的经历，但每一步的**现象与成因**都能在 §1.2–§1.11 里找到对应机制。把它当"遇到这个现象，该往哪个机制上想"的索引来读。

### 第一阶段：靠 review 维持规范（会失败）

**现象**：PR 评论里一半是"这里缩进不对""引号统一一下"。

**为什么不成立**：缩进是**可判定**的，但 review 是人工的、有延迟的、会疲劳的 —— 按 §1.1 的两条判据，它只满足一条。**"规范写在 review 意见里"和"规范写在文档里"是同一种东西**，都会被耗尽。

### 第二阶段：把判断交给工具（编辑器层）

**做法**：引入 ESLint + Prettier，配编辑器插件。

**新现象**：**"同一条规则，小王的机器报、我的不报。"**

**排查路径**（按顺序问三个问题）：

1. 你们用的是**同一个配置文件**吗？
2. 有没有人用了 `--config`（或编辑器插件里配了别的路径）？
3. 这条 `ignores` 是**全局忽略**吗？

**成因**（§1.4）：`files` / `ignores` 的 glob **相对于配置文件所在位置**求值；一旦用 `--config` 指定了别的配置文件，就变成**相对于当前工作目录**。同一个模式在两种情况下匹配到的文件不同 —— 所以"配置一样、结果不同"是完全可能的。

**修法**：共享配置进版本控制、统一入口，**不鼓励个人 `--config`**。

### 第三阶段：格式争论还在发生

**新现象**：**每次保存文件，格式来回跳** —— A 改成 X，B 立刻改回 Y。

**成因**（§1.6）：linter 的风格规则与 Prettier 的关系不是"冗余"，而是**可能冲突**。官方原话的重心就在这里：多余的规则只是浪费，**冲突的规则会让两个工具互相打架**。

**修法**：`eslint-config-prettier` —— 注意这个修法的形状是**一方主动退出**（ESLint 交出格式判断权），不是"两个工具协商"。这是 §1.6 最值得记住的一点。

### 第四阶段：把门禁前移到 pre-commit

**做法**：引入 Husky + lint-staged。

**新现象 A**：**"有人提交了完全没格式化的代码。"**

**排查**：查三件事 —— ① 他本地有没有 `.husky/` 目录（`prepare` 没跑，或用 `--ignore-scripts` 装的）？② 他设了 `HUSKY=0` 吗？③ 他用了 `--no-verify` 吗？

**这条不能靠追责解决。** 它是 §1.11 盲区三的**必然结果** —— 本地门禁的一切都可以被单方面关闭。**修法是 CI 兜底，不是"在群里提醒大家别关"。**

**新现象 B**：**"`git commit` 失败之后，我的改动好像不见了。"**

**成因**（§1.10 第 5 步）：lint-staged 出错时会 `git reset` 复位，但**备份 stash 只在全部成功之后才会被 drop** —— 所以改动一定还在某处。

**修法**：

```shell
git stash list --format="%h %s"     # 找 lint-staged automatic backup
git apply --index <那个 stash>
```

**这是本章最值得记住的一条救火命令。**

**新现象 C**：**"我只想提交三处改动里的一处，但 pre-commit 之后另外两处也被提交了。"**

**成因**（§1.10）：有人为了"省事"打开了 `--no-hide-partially-staged`。它关掉的是 lint-staged 的核心安全机制 —— 隐藏部分暂存文件里未暂存的改动。

**修法**：关掉它，并在团队文档里写死原因：它的代价是**提交你没打算提交的代码**。

### 第五阶段：CI 兜底

**新现象**：**"CI 上报了一个本地从来没见过的问题。"**

**排查顺序**（顺序不是随意的，它按"最容易验证 → 最需要解释"排列）：

1. 本地**是不是带了 `--cache`**？（§1.5：缓存不跟踪跨文件依赖）
2. 这个规则是不是**跨文件**类型？（类型感知规则、跨模块 import 规则）
3. 涉及的文件**在本次提交里吗**？（§1.11 盲区一：lint-staged 只查改动文件）

三个问题对应三个不同的机制，**对应三种不同的修法** —— 这正是为什么排查顺序要固定：先排除最廉价的可能。

### 第六阶段：遇到存量项目

**新现象**：**老项目第一次接入，一开规则就是几千条报错。**

**成因**：规则集是按"新代码应该长什么样"设计的，而存量代码是历史上长出来的。**不是配置错了，是期望值错了。**

**这一阶段的做法**（分区、规则分级、容忍策略、渐进收敛）属于 `D1.L3.03`，本章只交代现象 —— **待 D1 第 3 章写完回链补全**。

### 反过来看：团队规范文档该写什么

把上面六个阶段倒过来看，团队规范文档的最小内容**不是"我们用什么工具"**，而是这几条「现象 → 先查什么」的对照：

| 现象 | 先查什么 | 对应机制 |
|---|---|---|
| 规则在某台机器上不生效 | 配置文件路径、有没有用 `--config` | §1.4 glob 的求值基准 |
| 保存文件时格式来回跳 | 是否同时存在格式类 lint 规则与 Prettier | §1.6 冲突而非冗余 |
| 有人提交了未格式化的代码 | `prepare` 跑没跑、`HUSKY`、`--no-verify` | §1.9–§1.11 可绕过性 |
| commit 失败后改动"不见了" | `git stash list` | §1.10 第 5 步 |
| 提交后多出没打算提交的改动 | 是否开了 `--no-hide-partially-staged` | §1.10 |
| 本地不报、CI 报 | `--cache`、是否跨文件规则、文件是否在本次提交里 | §1.5、§1.11 |
| 升级 ESLint 后旧配置全失效 | 版本号与配置格式的代际 | §1.4 |

**这一节回到 §1.1 的结论**：规范的落地不是"配置一次就好"，而是一条**故障驱动**的演进链。每个阶段的正确解法，都是先判断"这个现象属于哪一层的正常行为"，**而不是先改配置**。

## 1.13 动手

在本章所有机制上做一次验证。**每一项都要求说出理由**：

| 任务 | 验收 |
|---|---|
| 建一个空项目，装 ESLint v10，只写 `eslint.config.js` 而不装任何共享配置 | 说出为什么此时**什么都不报**（回到 `eslint:recommended` 是否被包含） |

| 故意写一条需要两次修复才能收敛的规则场景（如 `quotes` 与 `semi` 同时可修），跑 `--fix` | 说出**修复循环最多几轮**、这个数字来自官方哪个页面 |
| 让一条规则同时产出 `fix` 与 `suggest` | 说出为什么**建议不会触发多轮修复** |
| 写一条自定义规则，故意不写 `meta.fixable` 却调用 `fix` | 记录报错信息，说出为什么这是**刻意的设计** |
| 在规则里访问 `context.getSourceCode()` | 记录报错，说出替代写法与官方给出的理由 |
| 打印一条规则里的 `context.options` | 说出为什么**里面没有 severity** |
| 用 `--cache` 跑一次，改动一个被其他文件 import 的模块，再跑一次 | 说出为什么**导入方的错误没被报出来**，以及官方的两条例子 |
| 打开 `--quiet` 同时设 `--max-warnings 0` | 说出为什么 `warn` 规则**仍然会运行** |
| 制造一个配置错误（如 `parserOptions` 写错类型）并跑 lint | 记录退出码，说出 **1 与 2 的分工** |
| 在 `.husky/pre-commit` 里给 lint-staged 传一次路径参数 | 记录现象，说出官方为什么说"不要传" |
| 造一个部分暂存文件，跑一次 pre-commit，过程中 `git stash list` | 说出**备份 stash 的名字**与它**在什么时刻被 drop** |
| 让 lint-staged 的任务故意失败 | 用官方给的两条命令把改动找回来 |

**进阶挑战**（任选一项）：

1. 造一个 **glob 重叠 + 双任务改文件**的配置（`"*": "prettier --write"` + `"*.ts": "eslint --fix"`），故意让它竞态失败，再用官方的 `"!(*.ts)"` 解法修好，记录两次的现象差异。
2. 用 `TIMING=1 eslint lib` 找出项目里**耗时最长的规则**，解释它为什么慢（是遍历量？还是作用域查询？）。
3. 从零写一条自定义规则，要求它**同时**用到 `SourceCode` 的 token 能力与作用域能力，并为它写 RuleTester 用例。

| # | 误区 | 纠正 |
|---|---|---|
| 1 | "规则的 `context.options` 里第一个值是 severity" | severity 会被**先剥离**，`context.options` 只含其后的元素。**规则无法知道自己的 severity** |
| 2 | "`context.getSourceCode()` 是标准写法" | **该方法已被移除**，官方明确"早期版本的附加方法不应再依赖"。用 `context.sourceCode` |
| 3 | "规则之间可以互相传递信息" | 官方没有任何规则间通信机制。`context.settings` 只是配置层共享数据 |
| 4 | "`--fix` 只跑一遍" | 官方原文：修复后**在修复后的代码上重跑所有规则，最多 10 次** |
| 5 | "`.eslintrc` 还能用，加个环境变量就行" | 那是 **v9 的行为**。**v10.0.0 起旧配置格式不再被支持** |
| 6 | "`eslint.config.ts` 会被类型检查" | 官方明确：ESLint **不对配置文件做类型检查，也不应用 `tsconfig.json` 的设置** |
| 7 | "`ignores` 写在哪个配置对象里都一样" | `ignores` **单独出现**时才是全局忽略（可匹配目录）；否则**只能匹配文件名**，`"dir/"` 什么都不忽略 |
| 8 | "`files` 的 glob 总是相对项目根" | 相对**配置文件所在位置**；用 `--config` 时相对**当前工作目录** |
| 9 | "`--max-warnings n` 是"达到 n 就失败"" | 是**严格大于**才失败 —— 等于 n 仍然通过 |
| 10 | "`--quiet` 会让 warn 规则不跑，所以更快" | 官方特别提醒：**warn 规则仍然运行，只是不被报告**（否则 `--max-warnings` 就没法计数） |
| 11 | "退出码 1 和 2 都是"lint 没过"" | **1 = 代码有问题；2 = 配置或工具本身有问题**。责任方不同，CI 上要分流 |
| 12 | "`--cache` 只是更快，没有副作用" | 三条反直觉行为：**不带 `--cache` 跑会删缓存文件**、**被 autofix 的文件不进缓存**、**缓存不跟踪跨文件依赖**（类型感知与跨模块 import 规则会报过期结果） |
| 13 | "官方禁止把 Prettier 当 lint 规则" | 官方原话是 **"generally not recommended, but can be useful in certain circumstances"** —— 不推荐，不是禁止。引用不要加重 |
| 14 | "装了 Stylelint 就该开始报错" | Stylelint 的 **100+ 条内置规则默认全部关闭**，没有 `eslint:recommended` 那样的默认集合 |
| 15 | "`overrides` 里的配置都是追加" | **`customSyntax` 是替换**，而 `plugins` / `extends` / `rules` 是追加 |
| 16 | "设置 `ignoreFiles` 不影响别的" | 它会**覆盖"默认忽略 `node_modules`"** 的行为 |
| 17 | "`.nvmrc` 能强制团队用对 Node 版本" | `.nvmrc` 与 `engines` 的强制力都**弱**（前者是读取约定、后者默认只警告）。要强制需 `engine-strict` 或 CI 显式校验 |
| 18 | "装了 Husky 规范就被强制了" | 官方明确 Husky **不强制**：`HUSKY=0` 可全局禁用。**本地门禁的固有上限就是可绕过** |
| 19 | "lint-staged 是对"我改过的文件"跑命令" | 它的输入是 **git index 里的路径**（等价 `git diff --staged`，默认 diff-filter `ACMR`），不是工作区的改动 |
| 20 | "lint-staged 只是过滤文件列表" | 它会做**五次 git 操作**：建备份 stash、把部分暂存文件的未暂存改动存成 patch 并移除、跑完后把改动写回 index、把 patch 应用回去、出错则 `git reset` 并从 stash 恢复 |
| 21 | "lint-staged 失败后我的改动丢了" | **备份 stash 只在全部成功后才会被 drop**。用 `git stash list` 找到 `lint-staged automatic backup`，再 `git apply --index` |
| 22 | "`--no-hide-partially-staged` 能省事" | 它会让部分暂存文件里**你没打算提交的改动也被提交**。这是关掉了 lint-staged 的核心安全机制 |
| 23 | "lint-staged 的任务默认串行" | 默认 `--concurrent true` 是**无限并发**（每个 glob 是一个任务）；但**子任务总是串行**。数组内串行、数组套数组才并行 |
| 24 | "glob 重叠没关系" | 官方明确警告：**glob 重叠且任务会改文件时可能竞态**。解法是消掉重叠（`"!(*.ts)"`），而不是加大并发 |
