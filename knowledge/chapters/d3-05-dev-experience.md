## 5.1 "快"不是一个指标，是四个

先把这条摆前面，因为本章之后所有的混淆都源自这一条。

| # | 指标 | 回答的问题 | 谁的体验 |
|---|---|---|---|
| 1 | **冷启动** | 从敲下命令到能访问页面，多久？ | 开始一天工作时 |
| 2 | **首次可见** | 页面第一次出现内容，多久？ | 开始调试某个页面时 |
| 3 | **增量重建** | 改一个文件到产物更新，多久？ | 跑 `watch` 或 build 时 |
| 4 | **HMR 更新** | 改一个文件到浏览器里生效，多久？ | 写代码时（最高频） |

**为什么必须拆开**：这四者的**成本函数完全不同**。

| 指标 | 成本由什么决定 |
|---|---|
| 冷启动 | 要不要**先处理整个应用**（架构问题） |
| 首次可见 | 当前页面**依赖多少个模块**（请求数与图的分支） |
| 增量重建 | 有多少模块**需要重算**（缓存命中率） |
| HMR 更新 | 变更点**离最近的边界有多远**（图的局部性） |

**推论**：一个工具在指标 1 上可以压倒性领先，在指标 2 上却可能落后（因为请求数）。**"某工具更快"这句话，如果不指明是哪个指标，就没有信息量。**

**本章的结构正是按这四个指标组织的**：§5.2 讲指标 1 的架构来源，§5.3 讲指标 4 的机制，§5.4 讲指标 3 的缓存层次，§5.5 讲"dev 与 prod 差在哪"（它同时影响四个指标），§5.6 把它们收成一张判据表。

## 5.2 架构分野：为什么 dev server 敢不打包

### 打包式的成本

Vite 官方对"传统打包式工具"的描述（原文）：

> 传统构建工具（常被称为打包器）会**在你把任何东西展示到浏览器之前，先把整个应用处理一遍**。**应用越大，你等得越久。**

**这句话的关键词是"整个应用"与"之前"。** 打包式的成本不是"处理慢"，而是**"必须全部处理完才能开始"** —— 所以启动成本是应用体积的函数，且是**线性**的。

### Vite 的拆法：两段，各有各的缓存

官方原文：

> Vite 采取了不同的方法。它把工作拆成两部分：
> - **依赖**（很少变化的库）**用快速的原生工具预打包一次**，所以它们**立刻可用**。
> - **源码**（你频繁改动的应用代码）**通过原生 ESM 按需提供**。浏览器**只加载当前页面需要的东西**，而 Vite **在每次请求时转换每个文件**。

两条路线的图注也很干脆：

> 在打包式 dev server 中，**整个应用在被提供之前就被打包了**。
> 在 ESM 式 dev server 中，**模块按浏览器请求的节奏被按需提供**。

**这里有两个不同性质的"缓存"，不能混为一谈**：

| 对象 | 变化频率 | 策略 | 结果 |
|---|---|---|---|
| **依赖**（`node_modules`） | 很少变 | **预打包一次**，结果落在磁盘缓存 | 启动时**不需要**重新处理 |
| **源码**（你的代码） | 频繁变 | **不预打包**，每次请求时转换 | 启动时**不需要**处理它 |

**所以启动成本与"你的应用有多大"解耦了。** 官方结论句："dev server 的启动**几乎是瞬间的，且与应用体积无关**"。

**注意这句话的精确范围**：它说的是**启动**与应用体积无关。它**没有**说"页面加载"与体积无关 —— 那是 §5.2 末尾要讲的代价。

### 三条代价，每条都真实

**代价一：请求数。** 源码不打包，意味着浏览器要为**每个模块发一次请求**。官方在"未来方向"里把这件事说得很直白：

> 由于**超大型代码库**可能因为**未打包网络请求数量过多**而经历**慢页面加载**，团队正在探索一种**让 dev server 像生产那样打包代码**的模式，以减少网络开销。

并且给了一句极重要的背景：

> 在 Vite 被创造出来时，**未打包 ESM 是正确的权衡**，因为当时没有工具既**足够快**、又具备在 dev 期打包所需的 **HMR 与插件能力**。**Rolldown 改变了这一点。**

**这是 2026 年 D3 领域最值得注意的一条动向**：**"dev 不打包"不是一个不可动摇的原则，而是一个当时的权衡。** 当打包器本身变快之后，这个权衡的等号开始倾斜 —— 官方已经在探索"dev 期也打包"的模式。

**代价二：生产仍然要打包。** 官方给的理由只有一条，但很硬：

> 尽管未打包 ESM 在**开发期**工作良好，但**在生产环境发布它仍然低效**，因为**嵌套 import 会带来额外的网络往返**。**这就是为什么打包对于优化的生产构建仍然是必要的。**

**这条的机制值得展开**（本书的补充）：生产环境的每一次网络往返都有**固定延迟**（DNS、TLS、RTT）。开发时你在本机，RTT ≈ 0，所以 100 个模块 100 个请求几乎无感；上线后 RTT 可能是 100ms，100 层嵌套 import 就是**串行等待**。`D0` 第 6 章讲过 HTTP 层的往返成本，这里是它在构建层的直接体现。

**代价三：dev server 是非打包的，这改变了插件的可用面。** 这是第 4 章 §4.6 已经遇到的后果：**`moduleParsed` 在 dev 期不调用**（Vite 为避免全量 AST 解析）；**Output Generation Hooks 在 dev 期不调用**。**"不打包"不只是一个速度策略，它决定了哪些概念在 dev 期根本不存在。**

### 历史与前身

官方提到的三个前身，各贡献了一样东西：

| 项目 | 贡献 |
|---|---|
| **Snowpack** | 开创**未打包开发**，并启发了 Vite 的**依赖预打包** |
| **WMR**（Preact 团队） | 启发了**通用插件 API** |
| **@web/dev-server** | 影响了 Vite 1.0 的**服务器架构** |

### 一处诚实的说明

旧版 Why Vite 有一段经典论述：HMR 时间在打包式设置下随应用体积增长；而 Vite 只需**失效被编辑模块与其最近 HMR 边界之间的链**，因此 HMR 速度恒定。

**本次核验抓到的 v8.3.4 版本页面里，这段内容已不存在**，也没有任何基准数字（该页只有 "nearly instant"、"painfully slow" 这类定性词）。

**本章因此不把它当作官方原文引用。** 但该机制本身是成立的，且可从 §5.3 的边界模型推出——所以在 §5.6 讨论 HMR 指标时，本书会明确标注这是**机制推导**，而不是官方断言。

## 5.3 HMR：只换一个模块

### 定义与三个收益

Webpack 官方定义：

> HMR **在应用运行过程中交换、添加或移除模块，而不整页刷新**。

三个收益（官方原文）：

1. **保留整页刷新会丢失的应用状态。**
2. 通过**只更新变化的部分**来节省开发时间。
3. 源码中的 CSS/JS 修改后**立即更新浏览器**，几乎等同于在 DevTools 里直接改样式。

**第 1 条是 HMR 与 LiveReload 的分界线**：整页刷新会把所有内存状态清空（表单输入、滚动位置、弹窗状态、`useState` 里的值）。**HMR 的存在理由不是"快一点"，而是"不丢状态"。**

### 两个必要条件

官方把 HMR 的定位说得很明确：

> HMR 是**opt-in 特性，只影响含 HMR 代码的模块**。

需要两样东西：

| 条件 | 内容 |
|---|---|
| **HMR 运行时** | 运行时**额外注入代码**来追踪模块的父子关系；管理侧提供 **`check`** 与 **`apply`** 两个方法；通过 **`status`** 报告所处阶段 |
| **模块级接受（边界）** | 模块自身或其父级必须有**更新处理器** |

**"opt-in"这个定位很重要**：未写 HMR 代码的模块**不是"坏掉的 HMR"，而是"没参与 HMR"**。它会走冒泡路径（下节）。

`check` / `apply` 的分工值得记：`check` **请求更新清单**（浏览器构建走 HTTP，`target: 'node'` 走 `fs.readFile`，请求失败即"没有可用更新"）；`apply` 把更新模块**标记为 invalid**、处理 accept / dispose、更新 hash、回到 idle。

### 冒泡：没有 accept 的真实后果

这是本节最容易被误传的一处。官方原文（两段，都值得逐字读）：

> **如果模块没有 HMR 处理器，更新会冒泡**：webpack 从**变更模块**出发，**沿着 import 它的模块向上走**，直到**找到一个接受该变更的模块**。因此，**一个放在足够高层的处理器可以覆盖整棵子树**。

> 对每个 invalid 模块，**模块自身或其父级必须有更新处理器**。否则 invalid 标记会**向上传染**。冒泡**直到入口点或带处理器的模块（先到者为准）**。**如果从入口点冒出来，过程失败** —— 更新被**中止**，并给出一个消息指明**"没有人接受"的文件**，而**应用继续跑旧代码**。**这就是 dev server 会把它变成整页刷新的那件事。**

**注意这里的层次**：

| 层次 | 发生什么 |
|---|---|
| 核心 HMR 行为 | 更新**中止**，**应用保留旧代码继续跑** |
| dev server 行为 | 把这次失败**转化成整页刷新** |

**所以"没有 accept 就整页刷新"是不准确的。** 准确说法是：**一路冒泡到入口点仍无人接受 → 更新失败 → dev server 回退整页刷新**。如果中途有任何一个上层模块接受，更新就在那里停住，**不会刷新**。

**这条区分有实际用途**：如果你的模块改动总是导致整页刷新，先确认"链上真的一个接受者都没有"，而不是"我的模块没写 accept"。

### 官方例子：谁重跑，谁不重跑

官方给的三层例子 `top.js → middle.js → leaf.js`，只有 `top.js` 接受 `./middle.js`。改 `leaf.js` 时：

| 模块 | 是否重新执行 | 原因 |
|---|---|---|
| `leaf.js` | **是** | 它就是变更本身 |
| `middle.js` | **是** | 它位于变更与处理器之间 |
| `middle.js` 引入但**未变化**的模块 | **否** | 仍在模块缓存中，**原样复用** |
| `top.js` | **否** | **它是接受者，保持运行** |

而 `top.js` 虽然不重跑，它导入的**绑定已经指向新版本**。官方点出了这个的价值：

> 因此 `top.js` 自身状态保留，**适合作为重新渲染、或把新值换进长生命周期对象的位置**。

**这段是整个 HMR 模型的核心**：**边界模块不重跑，但能看到新值**。所以框架的 HMR 实现总是把 `accept` 放在**组件层**（那个能"重新渲染"的层），而不是放在叶子工具函数上。

另一个细节（官方）：**CSS 是特例** —— webpack 内建的 CSS 支持**已实现 HMR 接口**，样式更新**不需要你手写 accept**。

### Vite 侧：边界是同一个概念

Vite 官方的定义与 webpack 一致：

> 一个"接受"热更新的模块被认为是 **HMR 边界**。

传播模型（官方图示）：变更从**被编辑模块**沿 import 链**向上冒泡**，**直到遇到边界为止**；**边界模块上层的导入者收不到变更通知**。

**"收不到通知"这句话是边界的定义性后果**：边界是一道**截断**，不是一道"转达"。

### Vite 的 `accept` 两种形式

| 形式 | 签名 | 语义 |
|---|---|---|
| **自我接受** | `accept()` / `accept(cb)` | 模块**自己**成为边界；回调收到**更新后的模块命名空间** |
| **接受依赖** | `accept(dep, cb)` / `accept(deps, cb)` | 接受**指定依赖**的更新；多依赖时数组里**只有被更新的那个非 `undefined`** |

回调参数有一个必须处理的边界情况：**语法错误时为 `undefined`**（数组形式则为**空数组**）。

官方对 dep-accept 给了三条**限制**，都很实在：

1. **不真正替换原模块**。若边界模块 re-export 了依赖的导入，**它自己负责更新那些 re-export**（且必须用 `let` 声明）。
2. **边界之上的导入者不会被通知** —— 更新在边界处截断。
3. 这种简化实现**足够覆盖多数开发场景**，同时**省去生成 proxy 模块的高昂开销**。

**第 3 条点出了一个工程取舍**：完整的模块替换需要 proxy 层，而 proxy 层本身有成本。Vite 选了"够用 + 便宜"，代价是 re-export 的更新要你自己管。

### 一条静态分析的硬性要求（最实用的一条）

官方原文：

> 源码中必须**字面**出现 `import.meta.hot.accept(`（**对空白敏感**），否则 Vite **不会**为该模块启用 HMR 接受能力。**动态 / 计算调用无效。**

**这解释了"我写了 accept 但 HMR 还是不生效"**：如果你把 `accept` 藏在条件分支、变量或者换行拆开了括号，**静态分析看不到它**，这个模块就不是边界。

### `dispose` 与 `prune`：两种清理时机

| API | 触发时机 | 典型场景 |
|---|---|---|
| `dispose(cb)` | 模块**被新副本替换之前** | 清理旧副本创建的**持久副作用** |
| `prune(cb)` | 模块**不再被页面任何地方 import 时** | 只在"从页面移除"时兜底 |

**口诀**：**`dispose` = 每次更新都清一次；`prune` = 只在彻底没人用时清一次。**

官方举的例子很具体：**Vite 用 `prune` 处理 `.css` 导入** —— 因为样式是典型的"一旦引入就长期生效"，只在被移除时才需要清理。

### `decline` 已废弃，`invalidate` 有纪律

| API | 现状 |
|---|---|
| `decline()` | **目前是空操作（noop）**，仅为向后兼容保留。想表达"本模块不可热更新"，应改用 `invalidate()` |
| `invalidate(message?)` | 自我接受模块**运行时发现自己处理不了**本次更新，把更新**强制向导入者传播** |

`invalidate` 的机制：调用后，HMR 服务器会把调用者**当作"没有自我接受"**来处理（即继续向上冒泡）。消息会**同时打印到浏览器控制台与终端**。

而官方强调了一条**容易踩的纪律**：

> **即使打算立刻 invalidate，也务必先写 `import.meta.hot.accept`**，否则 HMR 客户端**不会再监听**该自我接受模块的后续变更。

**这条的成因在 §5.3 的模型里**：边界是**静态分析**出来的（要看到字面的 `accept(`）。没有 `accept` 就没有边界，也就没有"之后可以被 invalidate"这件事。

### `hot.data`：跨实例的状态

- 每个**模块路径**一个 `hot.data` 对象，在该模块的**连续多个 HMR 实例间持久存在**；
- 模块被 **prune** 时，其 `dispose` / `prune` 回调收到当前 `data`，**回调结束后 Vite 清空它**；若之后再次被 import，拿到**新的空对象**；
- **不支持整体重新赋值**，只能改属性 —— 否则其他 handler 写入的信息会丢失。

**最后一条的实现原因值得想一遍**：`hot.data` 是**多个 handler 共享**的一个盒子的引用。整体赋值等于换了个盒子，别人手里的引用还指向旧盒子。

### 生产环境里 HMR 是什么

| 侧 | 事实 |
|---|---|
| **Vite** | 类型声明是 `readonly hot?: ViteHotContext`（**可选**），生产构建里为 `undefined`。官方因此要求**必须**包在条件块里，**以便生产构建 tree-shake** |
| **Webpack** | 本次核验的 HMR 概念页**没有生产环境相关段落**。**不能**从该页得出"生产是否包含 HMR runtime"的结论 |

**Vite 那条守卫（官方称 "REQUIRED CONDITIONAL GUARD"）是必修的**：

```js
if (import.meta.hot) {
  // HMR 代码
}
```

**不写守卫的后果不是报错，而是 HMR 代码被打进生产产物** —— 因为摇树无法证明它无副作用。**这是第 3 章 §3.4 的"副作用"在 HMR 场景的直接应用。**

### `hot.on` 的内置事件（可观测性入口）

Vite 自动派发的内置事件：`vite:beforeUpdate` / `vite:afterUpdate` / `vite:beforeFullReload` / `vite:beforePrune` / `vite:invalidate` / `vite:error` / `vite:ws:disconnect` / `vite:ws:connect`。

**`vite:beforeFullReload` 是"整页刷新兜底路径"的官方钩子** —— 上一个"冒泡到顶"的结论，在这里有了可观测的落点：**想知道自己为什么总在整页刷新，监听这个事件就知道。**

## 5.4 增量构建与持久化缓存

### 三个层次，别混

HMR 只是"快"的一条路。开发期的"快"实际分三层，**它们的失效粒度不同**：

| 层次 | 在哪一侧 | 复用范围 | 失效条件 |
|---|---|---|---|
| **HMR** | 浏览器 | 应用内存状态 | 变更传播到边界 |
| **增量构建** | 进程内（内存） | 同一进程的多次构建 | 进程结束即丢 |
| **持久化缓存** | 磁盘 | **跨进程、跨构建**（含 CI） | 构建依赖 / 版本 / 时间 |

**混起来的典型错误**："我开了 HMR，为什么重启 dev server 还是慢？" —— 因为 HMR 管的是**浏览器侧**，重启慢是**磁盘缓存**的问题。**这是三个独立的旋钮。**

### webpack 的 `cache` 默认值：production 下是关的

这是本节最重要的一条，且**与很多人的印象相反**：

| `mode` | `cache` 默认值 |
|---|---|
| `development` | **`{ type: 'memory' }`** |
| `production` | **`false`** |
| `none` | **`false`** |

而 `cache: true` 是 `cache: { type: 'memory' }` 的**别名**。

**所以"webpack 5 默认有持久化缓存"是错的**：默认只有 **development 下的内存缓存**；**filesystem 缓存需要你显式配**，而且 **production 下默认什么都没有**。

**这条的实践含义**：**CI 里想复用缓存，必须显式写 `cache: { type: 'filesystem' }`。** 不写就是每次全量。

### 两种 `type` 的能力差

| `type` | 定位 | 可配项 |
|---|---|---|
| `'memory'` | 进程内增量重建（dev / watch） | 仅 `maxGenerations`、`cacheUnaffected` |
| `'filesystem'` | **持久化**，可跨进程 / 跨构建 / CI 复用 | 一大组（见下） |

`filesystem` 独有的关键项：

| 选项 | 作用 | 默认 |
|---|---|---|
| `cacheDirectory` | 缓存目录 | `node_modules/.cache/webpack` |
| `cache.name` | 缓存名（不同 name 互不干扰、可共存） | `${config.name}-${config.mode}` |
| `version` | 缓存数据版本；**不同版本不复用并覆盖旧内容** | `''` |
| `buildDependencies` | 构建所需的"额外代码依赖" | `webpack/lib` |
| `maxAge` | 未使用条目在磁盘上的保留时长 | `5184000000` ms（≈ 一个月） |
| `maxMemoryGenerations` | 内存中未使用条目的存活代数 | `production: Infinity` / `development: 5` |
| `compression` | 压缩缓存 | `false`（`'zstd'` 需 webpack ≥ **5.109.0** 且 Node ≥ **22.15.0**） |
| `hashAlgorithm` | 哈希算法 | `md4` |

**最终缓存位置 = `cacheDirectory` + `name`**（或用 `cacheLocation` 直接覆盖）。

### 官方给的那条配置建议

`buildDependencies` 的默认值是 `webpack/lib` —— 也就是说 **webpack 自身的变化会让缓存失效**。而官方另有一条 tip：

> 推荐在配置中设置 **`cache.buildDependencies.config: [__filename]`**，这样**配置文件的改动及其所有依赖都会被纳入**，从而拿到最新配置对应的缓存。

```js
cache: {
  type: 'filesystem',
  buildDependencies: { config: [__filename] },
}
```

**不写这一条的后果**：改了 `webpack.config.js`（比如换了个 loader 选项），缓存**仍然命中**，于是你拿到的是**用旧配置算出来的产物**。**症状是"改了配置没反应，删了 `.cache` 就好了"** —— 这是持久化缓存最经典的一类 bug。

### 四类失效来源

官方**没有**独立的 "cache invalidation" 章节，但把来源散在各选项里，可以归纳成四类：

| 类别 | 触发条件 |
|---|---|
| **构建依赖 hash** | `buildDependencies` 中每个条目**及其全部依赖**的 hash 变化 |
| **版本** | `cache.version` 变化（不同 version **不复用并覆盖**） |
| **时间** | 未使用条目超过 `maxAge`（默认约一个月） |
| **路径与清理** | CI 场景下**路径变化**，或 `npm ci` **prune 掉缓存文件** |

### CI 的两个坑（官方明列）

官方在 "Setup cache in CI/CD system" 里点出了两个**必然踩**的坑：

| 坑 | 官方说明 |
|---|---|
| **必须运行在相同的绝对路径** | 因为"webpack **缓存文件存储的是绝对路径**" |
| **`npm ci` 会 prune 缓存** | 若在该 job 中执行 `npm ci` 或改变默认缓存目录，`npm ci` 会**清掉缓存文件** |

**第一条尤其隐蔽**：不同 runner 的工作目录不同（`/home/runner/work/...` vs `/builds/...`），缓存直接失效，且**不报错**。

同一节还有两个可用项：`cache.readonly`（webpack **5.85.0**，`filesystem` + `store: 'pack'` 时可用，阻止写盘，适合 CI 只读复用）；`cache.store: 'pack'`（compiler 空闲时把**所有缓存项写入单个文件**，5.0.x 起为唯一模式）。

### 一处被静默忽略的配置

官方警告：**`cache.managedPaths` 已移到 `snapshot.managedPaths`**。

- `cache.managedPaths` **仍被 schema 接受**，但**会被忽略** —— webpack 在规范化配置时**将其丢弃**，只读取 `snapshot.managedPaths`。

**这类"配置被接受但不生效"的情况最费时**：不报错、不警告（仅文档里一句 warning），行为却与预期不符。**排查持久化缓存时，先确认你的选项在当前版本里还在不在原位置。**

### Vite 侧

Vite 对应的是**依赖预构建的磁盘缓存**（`node_modules/.vite` 一类），第 2 章 §2.4 已讲其机制与"为什么依赖要预打包"。**关键差别**：Vite 的持久化缓存**只管依赖，不管源码** —— 因为源码根本不预打包（§5.2）。**这是架构分野在缓存层的直接体现。**

## 5.5 开发与生产：差异全景与 `mode` 的边界

### 差异矩阵

把散在前四章的默认值收成一张表（都来自官方默认值）：

| 维度 | `development` | `production` |
|---|---|---|
| **压缩** | 关（`minimize: false`） | 开（`minimize: true`） |
| **`devtool`** | JS 默认 **`'eval'`** | **`false`** |
| **`chunkIds`** | `'named'` | **`'deterministic'`** |
| **`moduleIds`** | `'named'` | **`'deterministic'`** |
| **`cache`** | `{ type: 'memory' }` | **`false`** |
| **摇树** | 标记（`usedExports` 可观察） | **标记 + 删除** |
| **CSS** | 不抽取 | 抽取 |
| **HMR** | 可用 | **不存在**（`import.meta.hot` 为 `undefined`） |
| **`NODE_ENV`** | `development` | `production` |

**这张表的用法**：任何"本地正常、线上异常"的问题，先在这张表里找**哪一行变了**。

### `mode` 的真正边界

**`mode` 是一个"默认值集合"，不是一个"优化总开关"。** 这个区别很重要，分三点：

**① `mode` 只设置默认值，不阻止你覆盖。** 你可以 `mode: 'production'` 同时 `minimize: false`。此时产物**不是"生产模式的样子"**，尽管 `NODE_ENV` 还是 `production`。

**② `mode` 不包含全部优化。** 第 1 章 §1.4、第 3 章 §3.6 已经反复验证过：`usedExports` / `sideEffects` / `splitChunks` / `cache` 都**不在** `mode` 的承诺范围内。**"切了 production 就优化好了"是一个反复出现的错觉。**

**③ `mode` 与 `NODE_ENV` 不是同一件事。** `mode` 影响构建器的默认值；`NODE_ENV` 影响**你代码里和依赖里的** `process.env.NODE_ENV` 分支。两者通常联动，但**不是同一个旋钮** —— 三方库里的 `if (process.env.NODE_ENV !== 'production')` 靠的是后者（`D3.L2.03` 已讲替换机制）。

### 一个反直觉结论：dev 正常 ≠ prod 正常

有若干行为**只在生产模式下才完整生效**，所以**开发期根本测不出来**：

| 行为 | 为什么 dev 测不出 |
|---|---|
| **摇树** | 开发模式下模块被保留（为了 HMR 与调试），`sideEffects` 剪枝的后果**不显现**（第 3 章 §3.4 场景一：CSS 丢了但本地正常） |
| **CSS 抽取** | dev 期样式是注入的，prod 期是抽取成文件的 —— 所以"样式顺序不对""某条规则没了"只在 prod 出现 |
| **`deterministic` id** | dev 的 `named` id 让产物可读，**但也掩盖了"内容 hash 是否稳定"这个问题** |
| **HMR 代码** | dev 期 `import.meta.hot` 存在，**不写守卫也看不出问题** |

**所以第 3 章那条"产物优化里改了但没用"的清单，本质上都是这一类**：**dev 期的观察结果不能外推到 prod。**

**工程纪律**：**至少要有一处验证，是在 `mode: 'production'` 下跑的。** 只在 dev 里验收，等于没验收。

### 一个容易忽略的非对称

| 方向 | 是否可行 |
|---|---|
| 在 dev 配置里模拟 prod 行为 | **部分可行**（手动开 `usedExports`、生成 sourcemap） |
| 在 prod 配置里保留 dev 能力 | **不可行** —— HMR 依赖 dev server 与 `import.meta.hot`，生产环境不存在 |

**这个非对称解释了为什么"用 prod 跑一遍"不可替代**：dev 可以"假装生产"，但生产**不能**"假装开发"。

## 5.6 速度对比：四个指标各自的判据

### 判据表

| 指标 | 主要决定因素 | 怎么量（可复现） | 常见误判 |
|---|---|---|---|
| **冷启动** | 是否**先处理整个应用** | 从命令开始到 dev server 可访问，重复 5 次取中位数 | 拿"启动快"推断"页面快" |
| **首次可见** | 当前页面**依赖多少模块**（请求数） | 清缓存后首屏，看请求数与瀑布图 | 以为它随启动速度线性改善 |
| **增量重建** | **缓存命中率** | `watch` 下改一个文件到产物更新 | 用 dev 的内存缓存推断 CI 速度 |
| **HMR 更新** | 变更点**离边界的距离** | 改叶子文件，看边界在哪、是否整页刷新 | 把"整页刷新"当成 HMR 失败 |

### 四个指标的机制来源

**① 冷启动。**

| 架构 | 成本函数 |
|---|---|
| 打包式 | 与应用体积**线性相关**（"应用越大，你等得越久"） |
| 非打包 | **与体积解耦**（官方：启动"几乎是瞬间的，且与应用体积无关"） |

**但"解耦"有前提**：依赖仍要**预打包一次**。所以第一次启动（无缓存）和后续启动**不是一回事** —— 报冷启动数字时必须说明"缓存是否预热"。

**② 首次可见。** 这是非打包架构**唯一的成本项**，官方在"未来方向"里承认了：

> 超大型代码库可能因为**未打包网络请求数量过多**而经历**慢页面加载**。

**这条的判据**：如果你的项目模块数很大、且首屏依赖深，那么"启动快"可能被"首屏请求多"抵消。**这不是回退到打包式，而是调整图的结构**（减少首屏依赖、把非首屏的东西改成动态导入）。

**③ 增量重建。** 决定因素是**缓存层**（§5.4 的三层）。

**一个具体的判据**：CI 里没有 `cache: { type: 'filesystem' }`，那么"增量重建"这个概念**不成立** —— 每次都是全量。**所以量 CI 构建时间时，先说清有没有开缓存**，否则数字没有可比性。

**④ HMR 更新。**

**这一步的机制推导（本书的补充，非官方当前页面原文）**：按 §5.3 的边界模型，一次更新的代价取决于**从变更模块到最近边界的路径长度**：

- 边界就在模块自身（self-accept）→ **最便宜**，只重跑一个模块；
- 边界在组件层 → 重跑中间路径 + 边界重新渲染；
- 冒泡到入口 → **更新失败**，dev server 整页刷新 → **最贵**（等同于冷启动一次）。

**所以"HMR 慢"通常不是速度问题，而是"边界太远"**。判据：监听 `vite:beforeFullReload`（或观察是否整页刷新），如果频繁触发，是**边界缺失**，不是性能不足。

### 一条必须守住的诚实边界

**本次核验的 Vite Why Vite 页（v8.3.4）没有任何性能数字** —— 没有毫秒、没有倍率、没有基准图，只有 "nearly instant" / "painfully slow" 这类定性词。

**所以本书不给"X 倍快"这类结论。** 需要数字时，只能用**你自己的项目**量，且必须声明：① 量的是四个指标中的哪一个；② 缓存是否预热；③ 用的是什么规模的项目。

**任何"某工具快 N 倍"的说法，缺了这三条就不可采信** —— 因为它可能量的是指标 1，而项目大小恰好落在该架构的劣势区。

## 5.7 实战：六个"以为快了"的现场

> **说明**：构造示例，不是真实项目经历。每一步的成因都能在本章找到对应机制。

### 场景一：开了 HMR，重启 dev server 还是很慢

**现象**：HMR 生效，热更新也快，但每次重启都要等很久。

**成因**（§5.4）：**HMR 管浏览器侧，重启慢是磁盘缓存的问题。** 而 webpack 的 `cache` 在 `production` 下**默认 `false`**，`development` 下默认只有**内存**缓存 —— **内存缓存在进程结束时消失**。

**修法**：显式配 `cache: { type: 'filesystem' }`。

**这个场景的价值**：它把"三层快"分开的必要性讲透了 —— **一个旋钮解决不了另一个层次的问题**。

### 场景二：改了 `webpack.config.js`，产物毫无变化

**现象**：换了个 loader 选项，重新构建，产物和之前一模一样；删掉 `.cache` 后突然正常。

**成因**（§5.4）：`cache.buildDependencies` 默认只含 `webpack/lib`，**不含你的配置文件**。所以配置变了，缓存仍然命中。

**修法**：官方建议的 `buildDependencies: { config: [__filename] }`。

**这个场景的排查价值**：**"删缓存就好了"是持久化缓存的标志性症状**，而根因几乎总是"某个影响构建的东西没被纳入 `buildDependencies`"。

### 场景三：CI 上持久化缓存完全不命中

**现象**：本地配了 `filesystem` 缓存，搬到 CI 上，每次构建仍然全量。

**成因**（§5.4，官方明列的两个坑）：① 缓存文件**存储绝对路径**，不同 runner 的工作目录不同 → 直接失效；② job 里执行 `npm ci` 会 **prune 缓存文件**。

**排查顺序**：先确认两次构建的**绝对路径是否相同**，再看 `npm ci` 是否在缓存恢复之后跑。

### 场景四：写了 `import.meta.hot.accept` 但 HMR 不生效

**现象**：代码里明明有 `accept`，改文件还是整页刷新。

**成因**（§5.3）：官方要求源码中**字面**出现 `import.meta.hot.accept(`（**对空白敏感**），否则静态分析不认。**动态 / 计算调用无效。**

**常见触发写法**：把 `accept` 藏在 `if` 分支里、用变量持有 `import.meta.hot`、或者把括号和函数名拆到两行。

**修法**：**每次都在源码里写出完整的 `import.meta.hot.accept(`**。

### 场景五：HMR 代码被打进了生产产物

**现象**：生产产物里出现了 `import.meta.hot` 相关的逻辑。

**成因**（§5.3）：没写官方要求的 "REQUIRED CONDITIONAL GUARD"（`if (import.meta.hot) { ... }`）。**摇树无法证明这段代码无副作用，于是保留**。

**修法**：所有 HMR 代码**无条件**包进守卫。**这不是风格问题，而是"能否被摇掉"的前提。**

### 场景六：`decline()` 写了，但"不可热更新"没生效

**现象**：想让某模块拒绝热更新，写了 `hot.decline()`，行为没变。

**成因**（§5.3）：**`decline()` 目前是空操作（noop）**，仅为向后兼容保留。

**修法**：用 `hot.invalidate()`。但注意官方那条纪律：**即使打算立刻 invalidate，也要先写 `accept`**，否则 HMR 客户端不会再监听该模块的后续变更。

### 反过来看：本章机制该放进团队文档的哪几句

| 现象 | 先查什么 | 对应机制 |
|---|---|---|
| 启动慢 | 是否"先处理整个应用" | §5.2 架构分野 |
| 首屏请求多 | 首屏依赖的深度与广度 | §5.2 请求数代价 |
| 为什么生产还要打包 | 嵌套 import 的网络往返 | §5.2 代价二 |
| 改一个文件就整页刷新 | 链上有没有边界 | §5.3 冒泡模型 |
| `accept` 写了没用 | 是否字面出现 `import.meta.hot.accept(` | §5.3 静态分析要求 |
| HMR 代码进了生产 | 有没有 `if (import.meta.hot)` 守卫 | §5.3 守卫 |
| 重启 dev server 慢 | `cache` 是不是只有 memory | §5.4 三层快 |
| CI 构建没变快 | 有没有显式开 `filesystem` | §5.4 production 默认 `false` |
| 改配置没反应 | `buildDependencies.config` | §5.4 失效来源 |
| CI 缓存不命中 | 绝对路径 / `npm ci` | §5.4 两个坑 |
| 某选项配了不生效 | 是否已被移到 `snapshot.*` | §5.4 `managedPaths` |
| 本地正常线上异常 | 在 §5.5 的差异矩阵里找变化行 | §5.5 差异全景 |
| 切了 production 还没优化 | `mode` 只设默认值 | §5.5 `mode` 的边界 |
| 想量"快" | 先说是四个指标里的哪一个 | §5.1 |

## 5.8 动手

**每一项都要求说出理由**：

| 任务 | 验收 |
|---|---|
| 拿一个中型项目，分别记录：冷启动、首次可见、改一个叶子文件的 HMR 时间 | 说出这三个数字各属于 §5.1 的哪个指标、成本由什么决定 |
| 在同一个项目里再加 200 个未被首屏依赖的模块 | 说出启动时间与首屏时间**各自**怎么变，并解释为什么方向可能不同 |
| 清空依赖缓存后再启动一次，与预热后对比 | 说出"冷启动"这个数字为什么必须声明缓存是否预热 |
| 改一个位于依赖链最深处的文件，观察是否整页刷新 | 用 §5.3 的冒泡模型解释，并判断"是边界缺失还是性能不足" |
| 给某模块加 `hot.accept()`，再分别用"字面写法"与"变量持有 `hot` 的写法"各试一次 | 说出哪一种生效，依据是官方哪句静态分析要求 |
| 在 `accept` 回调里故意制造语法错误 | 说出回调参数为什么是 `undefined`（数组形式是空数组） |
| 写一个 `hot.dispose` 与一个 `hot.prune`，分别触发 | 说出两者的触发时机差（"每次更新"vs"彻底没人用"） |
| 写 `hot.decline()` 与 `hot.invalidate()` 各一次 | 说出前者为什么没反应、后者为什么要求先写 `accept` |
| 去掉 `if (import.meta.hot)` 守卫，构建生产产物 | 说出 HMR 代码为什么会进产物，接回第 3 章的副作用机制 |
| 在 dev 下开 `cache: { type: 'filesystem' }`，再切到 `production` 构建 | 说出 `cache` 在两个 mode 下的**默认值**分别是啥 |
| 配 `filesystem` 缓存但**不**加 `buildDependencies.config`，改一次配置 | 记录现象，说出"删缓存就好"的根因 |
| 在 CI（或模拟的两次不同绝对路径）里复用 `filesystem` 缓存 | 说出官方明列的两个坑 |
| 查一次你的 webpack 版本，确认是否还在用 `cache.managedPaths` | 说出它被移到了哪里、被忽略时的表现 |
| 在 dev 与 prod 下各构建一次，对比产物里的 CSS 与未使用导出 | 说出哪些差异是 `mode` 造成的、哪些不是 |
| 只把 `mode` 设成 `production`，不动其他配置，记录产物优化项 | 逐条对照 §5.5 的差异矩阵，指出哪些"以为会优化"的其实没发生 |

**进阶挑战**（任选一项）：

1. 给你自己的项目做一份**四指标基线**：四个数字、测量方法、缓存状态、项目规模。要求别人拿这份基线能在自己项目上复现同样的四项。**这份基线比任何"X 倍快"的说法都有用。**
2. 构造一个"dev 正常、prod 异常"的最小复现（提示方向：CSS 抽取、`sideEffects` 剪枝、`deterministic` id 之一），然后说明为什么**只在 dev 验收等于没验收**。
3. 把 §5.4 的"三层快"（HMR / 增量构建 / 持久化缓存）画成一张表，每层标注：**失效粒度、可复用范围、对应的配置项、量它的指标**。这张表的价值在于：**任何"慢"都能被定位到其中一层**。

## 5.9 本章常见误区

| # | 误区 | 纠正 |
|---|---|---|
| 1 | "dev 不打包是 Vite 的原则" | 官方明说这是**当时的权衡**："未打包 ESM 是正确的权衡……**Rolldown 改变了这一点**" |
| 2 | "边界模块也会重新执行" | **不会**。官方例子：`top.js` 是接受者，它**不重跑**，但导入的绑定已指向新版本 |
| 3 | "`accept` 怎么写都能被识别" | 必须**字面**出现 `import.meta.hot.accept(`（**对空白敏感**）。动态 / 计算调用**无效** |
| 4 | "`hot.decline()` 可以拒绝热更新" | 目前是**空操作（noop）**，仅为向后兼容保留。应用 `hot.invalidate()` |
| 5 | "随时可以 `invalidate`" | 官方纪律：**即使打算立刻 invalidate，也要先写 `accept`**，否则客户端不再监听后续变更 |
| 6 | "`dispose` 和 `prune` 差不多" | `dispose` = **每次更新都清一次**；`prune` = **只在彻底没人用时清一次** |
| 7 | "`hot.data` 可以整体重新赋值" | **不支持**，只能改属性。整体赋值会让其他 handler 写入的信息丢失 |
| 8 | "HMR 代码在生产会被自动移除" | 需要 `if (import.meta.hot)` **守卫**才可能被摇掉。官方称其为 **REQUIRED CONDITIONAL GUARD** |
| 9 | "webpack 5 默认就有持久化缓存" | **错**。默认：`development` = `{ type: 'memory' }`，**`production` = `false`**，`none` = `false` |
| 10 | "`cache: true` 就是持久化缓存" | `true` 是 **`{ type: 'memory' }` 的别名** —— 内存，进程结束即丢 |
| 11 | "改了配置缓存会自动失效" | 默认**不会**。`buildDependencies` 默认只有 `webpack/lib`；需加 `config: [__filename]` |
| 12 | "CI 里直接复用缓存目录就行" | 两个坑：缓存**存绝对路径**（路径变了就失效）；**`npm ci` 会 prune 缓存** |
| 13 | "`cache.managedPaths` 还能用" | 官方 warning：**已移到 `snapshot.managedPaths`**，旧写法**被接受但被忽略** |
| 14 | "`mode: 'production'` 就把优化都开了" | 它只设**默认值**。`usedExports` / `sideEffects` / `splitChunks` / `cache` 都**不在**它的承诺内 |
| 15 | "`mode` 和 `NODE_ENV` 是一个东西" | 不是。前者影响构建器默认值，后者影响代码与依赖里的环境分支 |
| 16 | "dev 里验证过就没问题" | 摇树、CSS 抽取、`deterministic` id、HMR 代码**都只在 prod 显现后果**。至少要有一处 prod 验证 |
| 17 | "可以给 prod 配上 HMR 来回测" | **不可行**。HMR 依赖 dev server 与 `import.meta.hot`，生产环境不存在 |
| 18 | "HMR 慢是性能问题" | 通常是**边界太远**。判据是频繁触发 `vite:beforeFullReload`（或整页刷新） |
| 19 | "Vite 官方页面上有 HMR 随体积增长的基准图" | 本次核验的 **v8.3.4 Why Vite 页已整体重写**，旧版"只失效链"论述与基准数字**均已不存在**。引用前先确认版本 |
| 20 | "dev server 的插件能力和 build 一样" | 不一样。**`moduleParsed` 与 Output Generation Hooks 在 dev 期不调用**（第 4 章 §4.6） |
