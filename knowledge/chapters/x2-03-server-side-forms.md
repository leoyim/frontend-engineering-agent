## 3.1 BFF：它解决什么，代价是什么

`X2.L3.02`。**先声明**：**BFF 是架构模式，没有官方规范文档。** 本节给的是**判据与代价**，不是"官方定义"。

### 它到底是什么

**Backend For Frontend** —— 名字里的关键词是 **for frontend**：

> **一层专门为某一类前端定制、且运行在服务端的聚合层。**

**注意"某一类"**：**BFF 通常是"一个端一个"**（Web BFF、App BFF、小程序 BFF），而不是"全公司一个"。

### 它解决三个具体问题

| # | 问题 | 没有 BFF 会怎样 |
|---|---|---|
| 1 | **多后端聚合**（一个页面要调 5 个服务） | 浏览器发 5 个请求；瀑布、错误处理分散在客户端 |
| 2 | **适配不同端的差异**（字段、粒度、聚合方式不同） | 每个端各写一套适配逻辑，且都在客户端 |
| 3 | **把服务端能力挡在服务端**（凭据、内部服务地址、权限判断） | **凭据必须发给浏览器** —— 这是安全问题，不是性能问题 |

### ⭐ 只有第 3 条是“必须”

**这是本节最重要的一条判据**。

| 需求 | 需要 BFF 吗 |
|---|---|
| 只是调一个接口 | ❌ **不需要**（直接调） |
| 想把字段名统一 | ❌ 不需要 —— 那是**契约问题**，改 API 契约即可 |
| 多个接口聚合、减少瀑布 | ⚠️ **值得，但有替代**（HTTP/2 多路复用、并行请求） |
| **需要隐藏凭据 / 不把内部服务暴露给浏览器** | ✅ **必须** —— 这个需求在客户端无解 |

**第四行之所以是"必须"**，是因为**浏览器是用户的**：

> **任何发到浏览器的凭据，都等于已经泄露。**

**所以"要不要 BFF"这个问题的正确问法不是"我们架构够不够现代"，而是**：

> **有没有一些东西，绝对不能出现在浏览器里？**

**有 → 必须 BFF。没有 → BFF 是一个可选的性能/维护性投资。**

### 代价是确定的，收益是概率的

**BFF 的三项代价，每一项都很大**：

| 代价 | 具体内容 |
|---|---|
| **① 多一跳** | 浏览器 → BFF → 后端。**网络往返从 1 次变成 2 次** |
| **② 多一个部署物** | 从"静态托管"变成"前端 + 服务端"，运维面扩大（`D6` 第 1 章） |
| **③ 它自己会长成"第 N 个后端"** | 一旦开始写业务规则，它就有状态、有复杂度、要独立测试 |

**⭐ 第 ③ 条是最常见的失败模式**，而它的成因很具体：

**BFF 一开始只做"聚合"，后来有人加了一个判断，再后来这个判断被另一个端复用……** 于是 **BFF 里出现了业务规则，而这些规则与主后端重复且会不一致。**

**所以有一条纪律**：

> **BFF 里只做「翻译」和「聚合」，不做「判断」。**

| 该做什么 | 不该做什么 |
|---|---|
| 把 5 个接口合成 1 个响应 | 判断"这个用户能不能下单" |
| 把 A 端的字段改名为 B 端要的 | 计算价格、库存、权限 |
| 转发并附带服务端凭据 | 在 BFF 里存业务状态 |

**判断标准很干脆**：

> **如果这条逻辑在"换一个端"之后仍然必须有 —— 它就不属于 BFF，属于主后端。**
>
> **如果它只在"某一个端"的展示上有意义 —— 它才属于 BFF。**

**第一条与第二条的分界，就是"业务"与"呈现"的分界。**

### 与第 1 章的连接：BFF 也是一种"渲染形态的延长"

**BFF 放在哪里，会与第 1、2 章的选择互相影响**：

| 组合 | 含义 |
|---|---|
| **SSR + 无 BFF** | 渲染层直接连主后端；适合后端接口本来就"够用"的情况 |
| **SSR + BFF** | 渲染层调 BFF；**BFF 与渲染层可能在同一进程**（省一跳） |
| **CSR + BFF** | 浏览器调 BFF；**BFF 就是你的"后端"** |
| **SSG + BFF** | 静态页 + 运行时数据；**BFF 承担"动态那一半"** |

**⭐ 第二行值得单独说**：**如果渲染层是服务端，那么"BFF"可以不是独立服务，而是同一个服务里的一个模块。** 这样**"多一跳"的代价就消失了**（进程内调用）。

**所以"要不要独立部署 BFF"与"要不要服务端渲染"是两个可以合并的决定** —— 而合并之后，BFF 的最大代价（多一跳）就被消掉了。

## 3.2 Serverless：约束在「配额」，不在「能力」

`X2.L3.03`。Vercel 的 Functions Limits 页（2026-08-24 更新）给了一份很具体的清单。**读它的正确方式不是"记数字"，而是看"哪些配额会改变架构"。**

### 最会咬人的三条

| # | 配额 | 为什么会改变架构 |
|---|---|---|
| **1** | **请求 / 响应体单次最大 4.5 MB**（超出 **413 `FUNCTION_PAYLOAD_TOO_LARGE`**） | **文件上传、大 JSON 导出必须走对象存储 + 签名 URL**，不能直接过函数 |
| **2** | **函数包未压缩 250 MB**（Python 500 MB；`Large Functions` Beta 最高 5 GB） | **打包体积成了架构约束**（与 `D3` 第 7 章的包体积分析同源，但这里限制的是**服务端包**） |
| **3** | **文件描述符 1,024，且由所有并发执行共享** | ← **这条最反直觉** |

**⭐ 第 3 条值得展开**：**"共享"意味着它不是"每个请求 1024 个"，而是"整个实例上所有并发加起来 1024 个"。**

**后果**：

| 做法 | 风险 |
|---|---|
| 每个请求都新建数据库连接 | **并发一高就 `too many open files`** |
| 不关文件 / 不关连接 | 泄漏会被放大到所有并发 |
| 用连接池 | **必须**，且池的上限要按"共享额度"算 |

**官方给的缓解建议方向是对的**：及时关闭文件/连接、使用连接池、做好资源清理。**但数字本身比建议更重要** —— **1024 是一个很小的数**，它把"随便开连接"这个习惯直接变成故障。

### 时长：流式不是免费的

**官方明确：时长计算包含处理请求和发送响应（含流式响应）的时间。**

| 运行时 | 默认 | 上限 |
|---|---|---|
| **Node.js / Bun / Python**（需 Fluid Compute） | **300 秒** | **800 秒**（GA，Pro/Ent）；**1800 秒 Beta** |
| **Edge Runtime** | —— | **必须在 25 秒内开始发送响应**，之后**最长可持续流式传输 300 秒** |

**⭐ 两个推论**：

1. **"用流式避免超时"是个误解** —— 流式时间**计入**总时长。流式改善的是**首字节时间**，不是**函数寿命**。
2. **Edge Runtime 有一个"25 秒内必须开始响应"的门槛** —— 这意味着**"先算很久再流式"是不行的**。它逼你把"开始输出"提前。

**而超时的表现是**：**504 / `FUNCTION_INVOCATION_TIMEOUT`**。

### ⭐ 默认单区域：Serverless ≠ 边缘

**这是本节最重要的一条架构事实**：

> **Vercel Functions 默认单区域运行（`iad1`），多区域仅 Pro / Enterprise 可配。**

**所以"把代码部署到 Serverless"并不等于"它离用户很近"** —— 它默认在**一个具体的数据中心**里。

**这条直接划出了 §3.3 的分界**：

| | Serverless（默认） | 边缘 |
|---|---|---|
| 跑在哪 | **一个默认区域** | **多个 PoP** |
| 上限靠什么 | **配额（时长/内存/体积）** | **更紧的配额（CPU/内存/体积）** |
| 主要收益 | 免运维、按用量计费 | **地理距离** |

**所以"要不要上边缘"的判据不是"想不想更快"，而是**：

> **你的用户与你的默认区域之间，距离成本有多大？**

**如果用户和默认区域在同一个国家/地区，边缘的收益很小** —— 而**你要付出 §3.3 那一整套更紧的约束**。

### 计费模型也在提示架构

**官方计费是 Active CPU time + Provisioned Memory time**，其中 **Active CPU 只计代码实际消耗的 CPU，等待 I/O（调 AI 模型、数据库查询）不计入**。

**⭐ 这条对架构的含义很直接**：

| 负载类型 | 在 Serverless 上的成本 |
|---|---|
| **I/O 密集**（等数据库、等第三方 API、等 AI） | **便宜**（等待不算 CPU） |
| **CPU 密集**（图像处理、大 JSON 转换、加解密） | **贵**，且**容易触时长上限** |

**所以"什么样的活该放 Serverless"有一个清楚答案**：**等得多的放进来，算得多的别放。**

### ⚠️ 必须如实标注的一处

**该页完全没有提「冷启动」（cold start / 启动时间 / boot time）。**

**所以本章不给 Serverless 的冷启动断言** —— 不确定它是一个"已解决的"问题还是"该页不管"的问题。**能确定的是：Vercel 另有 Fluid Compute 等页面在讲实例复用，但那些不在本次核验范围。**

**对照：Cloudflare 那一侧有一个明确的、可观测的对应量**（§3.3 的 startup time），**而 Vercel 这一侧没有**。**这个不对称本身就是本节最诚实的一句话。**

## 3.3 边缘：算力受限，但「启动」是硬的

`X2.L3.05`。Cloudflare Workers 的 Limits 页（2026-10-12 更新）给了一套**明显更紧**的约束 —— 而它们的**设计意图是一致的**。

### 三个时间必须分清

**这是边缘计算最容易混淆的地方**，而官方给了完整对照：

| 时间 | 定义 | 限制 |
|---|---|---|
| **CPU 时间** | **CPU 真正执行代码**的时长。**等待网络（`fetch`、KV、数据库）不计入** | Free **10 ms**/请求；Paid **5 分钟**（默认 **30 秒**） |
| **墙钟时间（wall time）** | 从调用开始到结束的**总实际耗时**，含等待 | **入站 HTTP：无限制**（客户端保持连接即可）；Cron / Queue / DO alarm **15 分钟** |
| **启动时间（startup time）** | **handler 之外的顶层代码（global scope）的解析与执行** | **1 秒** |

**⭐ 这三个量的关系值得说清**：

- **CPU 时间紧，墙钟时间松** → **故意设计**：它鼓励"等 I/O"，惩罚"算得久"。**这与 Vercel 的"等待不计入 Active CPU"是同一个导向。**
- **启动时间 1 秒**是**唯一一个"冷启动"性质的硬约束**，而且**它是可观测的**。

**⚠️ 注意"墙钟无限制"不等于"可以跑很久"**：**CPU 时间仍然会先耗尽**。**一个 while 循环不会因为墙钟无限制而跑下去。**

### 「冷启动」在这里叫 startup time，且能测

| 事实 | 内容 |
|---|---|
| 上限 | **1 秒**（global scope 的解析与执行） |
| 超限表现 | 部署被拒，**错误码 10021**，`Script startup exceeded CPU time limit` |
| 可观测 | 部署输出里有 **`startup_time_ms`** |
| **官方点名的常见原因** | **在顶层生成或读取大型 schema** |
| 优化方向 | **避免在全局作用域做昂贵操作**；初始化移入 handler 或移到构建期 |

**⭐ "在顶层生成大型 schema"这条极其实用**：**它同时是"启动慢"和"体积大"两个问题的来源**（§3.2 第 2 条）。

**而"把初始化移入 handler"是一个反直觉的建议** —— 常规做法是"把重活放全局只做一次"。**在边缘里这条被推翻了**，因为**全局作用域的代价被算进了每一个 isolate 的启动**。

**这与 `D3` 第 5 章 §5.3 的"预构建只在启动做一次"是恰好相反的取舍** —— 因为**Serverless/边缘的"进程"存活得短，而 dev server 存活得长**。**同一个优化动作在不同存活期的容器里方向相反。**

### 一套很紧的配额，而它们互相关联

| 配额 | Free | Paid |
|---|---|---|
| **CPU 时间 / 请求** | 10 ms | 5 分钟（默认 30 秒） |
| **内存 / isolate** | **128 MB** | **128 MB**（相同） |
| **Worker 体积（未压缩）** | **64 MiB** | **64 MiB** |
| **子请求数 / 调用** | **50** | 10,000（可提高到 10M） |
| **并发出站连接** | **6 个**（"等待响应头"状态） | 同 |

**⭐ 四条互相关联的机制**：

**① 内存是「每个 isolate」而非「每次调用」**

官方明确：**一个 isolate 可同时处理多个并发请求**；超 128 MB 时，运行时**让该 isolate 上 in-flight 的请求处理完，并为后续请求新建 isolate**。

**所以"128 MB"不等于"每个请求 128 MB"** —— 它是**共享的**。这与 §3.2 的"1024 个文件描述符共享"是同一个陷阱结构。

**② 子请求数：重定向的每一跳都算一次**

官方：**重定向链中的每一跳都计一次** → **实际子请求数可能多于代码里的 `fetch()` 调用数。**

**这条很隐蔽**：**一个 3 次重定向的请求 = 4 次子请求。** 在 Free 的 50 次配额下，这不是小数。

**③ 并发出站连接只有 6 个（"等待响应头"状态）**

**关键限定词是"等待响应头"**：**一旦收到响应头，这个连接就不占名额了。**

**所以"可以同时保持很多连接，只是同一时刻'等头'的不超过 6 个"** —— 第 7 个会**排队**。

**⭐ 这条的实际影响**：**串行 `await fetch` 不会命中它，但"同时发 20 个请求"会排队。** 而如果那 20 个请求的响应头都很慢，**总耗时会被这个 6 拉长**。

**④ 体积 64 MiB，且没有"压缩后"的上限**

官方：**只计算未压缩的 bundle 大小**，`gzip` 值仅供参考、**不是限制**。

**所以"压缩后很小"这个安慰在边缘上不成立。**

### 后台任务与长连接：都有硬边界

| 机制 | 官方限制 |
|---|---|
| **`ctx.waitUntil()`** | 响应已发出或客户端断开后，**最多延长 30 秒** |
| **未交给 `waitUntil()` 的任务** | 客户端断开或响应完成时**可能被取消** |
| **运行时更新时的宽限期** | 旧进程为已有请求与连接提供**最多 20 分钟**（**含流式 HTTP 与 WebSocket**） |
| **官方警告** | 崩溃、资源压力、关机都可能**更早**中断；长时运行的应用**必须能处理断连并安全重试** |

**⭐ "运行时更新宽限期 20 分钟"这一条很值得记**：

> **边缘的长连接有一个"由平台更新决定的上限"，而不是由你决定。**

**所以 WebSocket 这类场景在边缘上必须**按"随时可能断开"来设计**。**这与 `D6` 第 1 章 §1.5 的"回滚"、`D3` 第 9 章 §9.5 的"行为风险"是同一类思维方式**：**先问"这个平台会不会在我不知情时改变状态"。**

### ⚠️ 必须如实标注的两处

1. **该页未涉及 Node.js API 支持度与 `nodejs_compat`**（Workers 文档另有专页）。**所以本章不给"边缘不支持 Node 的哪些 API"的清单。**
2. **该页没有用"冷启动"这个词** —— 它用的是 **startup time**，且是**部署期校验的**（超限拒绝部署），而不完全是"运行时首请求的延迟"。**这两者不是同一件事，本章不混用。**

## 3.4 跨端：同一套后端，多种客户端

`X2.L4.03`。**先声明：本节无官方核验**，是机制与判据的整理。

### 跨端共享的三个层次

| 层次 | 共享什么 | 可行性 |
|---|---|---|
| **① 契约**（API 形状） | 接口定义、字段、错误码 | ✅ **总是可行** |
| **② 逻辑**（业务规则） | 校验、计算、状态机 | ⚠️ 看语言与运行时 |
| **③ UI** | 组件与样式 | ❌ 通常不值（`D4` 第 3 章的设计系统已证明 Cost） |

### ⭐ 一条判据：共享的层次越高，约束越强

**层次越高，对所有端的**共同要求**越多**：

| 共享到 | 对每一端的新增约束 |
|---|---|
| 契约 | 几乎无（只要求遵守形状） |
| **逻辑** | **必须用同一种语言/运行时**，且**不能依赖某一端独有的能力** |
| **UI** | **必须用同一套渲染模型**，且**样式能力取交集** |

**所以"能不能共享 UI"这个问题，答案是"能，但代价是每一端都退到最保守的那一端"。**

**这与 `D3` 第 3 章 §3.3 的"差异化产物的代价是部署一致性"是同一个结构**：**为了兼容最保守的一方，所有人都被拉下去。**

### BFF 与跨端的交叉：一个 BFF 还是 N 个

**这是 `X2.L4.03` 的核心决策**，而它只有两种形态：

| 形态 | 好处 | 代价 |
|---|---|---|
| **一端一个 BFF** | 每个端各自最优；改动互不影响 | **N 份维护**；共性逻辑 N 处重复 |
| **一个 BFF 服务多端** | 一处维护 | **被"最挑剔的端"绑架**（字段只能加不能改） |

**⭐ 判据：端的差异是否落在「数据形状」上？**

| 端的差异 | 该选 |
|---|---|
| 只是**字段多少**不同（App 少要几个字段） | **一个 BFF + 按端裁剪**（同一份逻辑，不同投影） |
| **聚合方式**不同（App 一个页面要 3 个接口，Web 要 5 个） | **一端一个**（聚合逻辑本身就不同） |
| **权限模型**不同 | **一端一个**（安全边界不该共用） |
| 只是**字段改名** | **都不该** —— 那是契约问题（§3.1） |

**⭐ 第一行与第三行的区分很重要**：

**"按端裁剪字段"是投影问题**（一个数据源，不同视图），**共享 BFF 是对的**。
**"按端换聚合方式"与"按端换权限模型"是逻辑问题**（不同的执行路径），**共享 BFF 会导致分支爆炸**。

**一个可判定的观察**：**如果同一个 BFF 里出现了大量 `if (client === 'app')`，那就该拆了。** 而**如果只是 `fields` 参数不同，那就不该拆。**

### 一条纪律：跨端共享的东西，应当与"端的能力"无关

**这条是把 §3.4 压成一句话**：

> **能被多端共享的逻辑，只应依赖「所有端都有」的能力。**

**而"所有端都有"这个集合，通常比想象的小**：

| 能力 | Web | App | 小程序 | 服务端 |
|---|---|---|---|---|
| 网络请求 | ✅ | ✅ | ✅ | ✅ |
| 定时器 | ✅ | ✅ | ⚠️ | ✅ |
| 本地存储 | ✅ | ✅ | ✅（有限） | ✅（不同语义） |
| 文件系统 | ❌ | ✅ | ⚠️ | ✅ |
| 长连接 | ✅ | ✅ | ⚠️ | ✅ |

**所以"共享逻辑"的安全区，基本只有"纯计算"**。**这与 `D3` 第 4 章 §4.2 的"依赖图可见子图"是同一个思路**：**能共享的前提是"它不依赖外部环境"。**

## 3.5 治理动作：六个判定阈值

| # | 现象 | 判定阈值（起点值） | 动作 | 依据 |
|---|---|---|---|---|
| 1 | 想上 BFF 但说不清为什么 | **回答不出"什么东西不能出现在浏览器里"** | 先确认需求：只是聚合 → 有替代；只是统一字段 → 改契约 | §3.1 |
| 2 | BFF 里出现了业务判断 | **同一规则在主后端也有一份** | 它属于主后端；BFF 只做翻译与聚合 | §3.1 |
| 3 | 上传/导出偶发 413 | **请求或响应体接近 4.5 MB** | 走对象存储 + 签名 URL，不过函数 | §3.2 |
| 4 | 并发一高就报资源耗尽 | **文件描述符 1024 由所有并发共享** | 用连接池并限制池大小；确保及时关闭 | §3.2 |
| 5 | 用了流式但仍超时 | **流式时间计入总时长** | 流式改善首字节，不延长函数寿命；重活应移到别处 | §3.2 |
| 6 | 边缘函数部署被拒 | **startup time > 1 秒（错误码 10021）** | 查全局作用域的重活（**顶层生成/读取大型 schema** 是官方点名的常见原因） | §3.3 |

### 三条使用说明

**① 阈值 1 的判定方式是"能不能说出一个具体的东西"。**

**"为了架构更现代"不是理由，"凭据不能下发"是理由。** 前者会让 BFF 变成一个纯成本项。

**② 阈值 4 与 6 都是"共享额度"类问题。**

一个是**文件描述符跨并发共享**，一个是**内存按 isolate 而非按调用**。**它们的共同点是"你以为的额度比实际大得多"。**

**③ 阈值 6 的修法方向反直觉。**

常规优化是"把重活放全局只做一次"，**而在边缘里这是错的** —— 因为**全局作用域的成本被算进了每个 isolate 的启动**。

### 什么时候"不该上边缘"

| 情况 | 为什么 |
|---|---|
| **用户与默认区域在同一地区** | 地理收益很小，而约束一堆 |
| **需要 CPU 密集计算** | Free 只有 **10 ms** CPU；Paid 默认 30 秒 |
| **依赖大量 Node.js 生态包** | 体积上限 **64 MiB 未压缩**，且**无压缩后上限** |
| **需要长连接 / 常驻任务** | `waitUntil` 最多 30 秒；宽限期由平台更新决定（20 分钟） |

## 3.6 动手

| 任务 | 验收 |
|---|---|
| 回答一次"我们有什么东西不能出现在浏览器里" | 若答不出来，说出 BFF 对你是否只是成本 |
| 查一次 BFF 里有没有业务判断 | 找出与主后端重复的规则 |
| 查一次函数体的最大请求/响应尺寸 | 若接近 4.5 MB，说出该改成什么 |
| 数一次单个实例的最大并发数据库连接 | 与 1024 对比，说出安全余量 |
| 查一次你的函数默认区域 | 说出用户与它的距离，以及这是否值得上边缘 |
| 查一次边缘函数的 startup time | 若接近 1 秒，找出全局作用域里的重活 |
| 查一次你的边缘 bundle（未压缩） | 说出 64 MiB 还剩多少余量 |
| 数一次最坏情况下一次调用的子请求数（含重定向） | 与 Free 的 50 对比 |
| 列出跨端共享的逻辑，标注它依赖哪些端能力 | 找出依赖"非全端通用能力"的那几个 |
| 查一次 BFF 里有多少 `if (client === ...)` | 若很多，说出该拆还是该改成投影 |

**进阶挑战**（任选一项）：

1. **做一次函数形态选型**：把项目里所有服务端逻辑按"CPU 密集 / I/O 密集 / 需要长连接"分类，给出"Serverless / 边缘 / 常驻服务"的分配，并说明每一类的约束来自哪条配额。
2. **给 BFF 做一次"翻译 vs 判断"审计**：把每个接口的处理逻辑逐行归类，目标是**业务判断为零**。
3. **压一次边缘的启动预算**：把一个 worker 的 `startup_time_ms` 从当前值压到一半，记录改了什么。

## 3.7 本章常见误区

| # | 误区 | 纠正 |
|---|---|---|
| 1 | "只要接口多就该上 BFF" | 聚合只是"值得"，还有替代（并行请求、HTTP/2）。**不是必须** |
| 2 | "BFF 是前端团队的后端" | 它是**翻译层**。**一旦写业务规则，就与主后端重复且会不一致** |
| 3 | "BFF 里做点判断没关系" | 判据：**换一个端之后仍然必须有的逻辑 → 属于主后端**；只在某一端展示上有意义 → 属于 BFF |
| 4 | "BFF 一定多一跳" | 不一定。**若渲染层是服务端，BFF 可以是同进程内的模块**，"多一跳"的代价消失 |
| 5 | "大文件可以直接过函数" | **请求/响应体单次最大 4.5 MB**（413 `FUNCTION_PAYLOAD_TOO_LARGE`）→ 走对象存储 + 签名 URL |
| 6 | "1024 个文件描述符是每个请求的额度" | **由所有并发执行共享**。并发一高就 `too many open files` |
| 7 | "用流式就能避免超时" | **流式时间计入总时长**（官方明确"含流式响应"）。流式改善**首字节**，不延长**函数寿命** |
| 8 | "Edge Runtime 没有时长限制" | **必须在 25 秒内开始发送响应**，之后**最长可持续流式 300 秒** → **"先算很久再流式"不行** |
| 9 | "部署到 Serverless 就等于离用户很近" | **Vercel Functions 默认单区域（`iad1`）**，多区域需 Pro/Ent。**Serverless ≠ 边缘** |
| 10 | "该不该上边缘看想不想更快" | 看**用户与默认区域的距离成本**。同地区则收益很小，而约束一堆 |
| 11 | "Serverless 冷启动时间是多少" | **Vercel 该限制页完全未提冷启动** → 本章不给断言。**Cloudflare 侧有明确的 startup time（1 秒）** |
| 12 | "CPU 时间与墙钟时间差不多" | 差别巨大：**等待网络不计入 CPU**。Free 只有 **10 ms CPU**，而**入站 HTTP 的墙钟无限制** |
| 13 | "墙钟无限制就能跑很久" | **CPU 时间仍然会先耗尽**。while 循环不会因为墙钟无限制而跑下去 |
| 14 | "边缘的 128 MB 是每个请求的" | 是**每个 isolate**，且**一个 isolate 可同时处理多个并发请求**。超限时让 in-flight 请求处理完，新请求新建 isolate |
| 15 | "gzip 后很小就够" | **只算未压缩体积，64 MiB**。**没有压缩后上限** |
| 16 | "子请求数就是 `fetch()` 的调用数" | **重定向每一跳都算一次** → 实际可能多于代码里的调用数 |
| 17 | "并发 6 个连接是指只能开 6 个" | 是**同时处于"等待响应头"状态的连接**不超过 6 个。收到头就释放名额 |
| 18 | "把重活放全局只做一次是优化" | **在边缘里这是反的**：全局作用域的成本被算进**每个 isolate 的启动**（1 秒上限）。官方点名"顶层生成大型 schema"是常见超限原因 |
| 19 | "startup time 就是冷启动延迟" | 它是**部署期校验**的（超限拒绝部署，错误码 **10021**），与"运行时首请求延迟"不是同一件事 |
| 20 | "边缘适合长连接 / 常驻任务" | `waitUntil` **最多延长 30 秒**；**运行时更新有 20 分钟宽限期**（含 WebSocket）→ 必须按"随时可能断开"设计 |
| 21 | "跨端共享逻辑很自然" | 安全区基本只有**纯计算**。依赖端能力的逻辑不能被共享 |
| 22 | "一个 BFF 服务多端更省事" | 若各端**聚合方式或权限模型不同**，会导致 `if (client === ...)` 分支爆炸 → 该拆 |
| 23 | "一个 BFF 就一定不好" | 若差异只是**字段多少**（投影问题），共享 BFF 是对的。判据是"差异是否落在数据形状上" |
| 24 | "边缘不支持哪些 Node API，文档里写了" | **Cloudflare 该限制页未涉及** Node.js API 与 `nodejs_compat` → 本章不给清单 |
