## 1.1 视角转换：AI 成了构建工具的用户

`X3.L3.01`。这个转变常被说成"AI 帮你写配置"，但那**不是主战场**。

### 真正的变化

**旧的默认假设**：

```
人读文档 → 人写配置 → 工具执行 → 人读日志 → 人判断
```

**新的情况**：

```
AI 读工具状态 → AI 提议 → 工具执行 → AI 读结构化结果 → AI 判断
```

**⭐ 差别不在"谁写下了那行配置"，而在「谁在消费工具的输岀」**：

| | 人类用户 | AI 用户 |
|---|---|---|
| 输入方式 | 读文档、抄示例 | 读**结构化能力清单** |
| 输出消费 | 读日志、看报错 | 读 **JSON / 诊断码 / 位置** |
| 容忍模糊 | 高（能猜） | **低**（猜错就编） |
| 速度 | 慢 | 快 |
| **验证** | 边做边验 | **需要另外设计** |

**⭐ 第三行是本章的核心**：

> **日志是给人看的，不是给 AI 看的。** 而"给 AI 看"需要的是**结构化数据**，不是更详细的文字。

**这与 `D5` 第 2 章 §2.3 的"错误信息质量决定 F（失败归因成本）"是同一个结论** —— 只不过那里的读者是人，这里的读者是模型。**而模型对模糊信息的容忍度更低**：它不会像人一样"隐约觉得是这个文件"，它会**编一个**。

### 频率差带来的性质变化

**同一条"构建很慢"的事实，对人和对 agent 的性质不同。** Cloudflare 的表述是（原书第 6 章已核验，2026-10-10）：

> 速度一直是开发者的**生活质量**改进。**对 agent 来说，速度是可靠性要求。**

**推论**：

| 对象 | "构建慢"的性质 |
|---|---|
| **人类开发者** | **体验问题** —— 等待时可以并行做别的事 |
| **Agent** | **可靠性问题** —— **一小时几百次循环**，慢被放大几百倍，直接影响能不能完成任务 |

**⭐ 这条推论的实质是"优先级排序变了"，不是"该学新技能"**：**速度从"nice to have"变成"必选项"**。

**而它对 `D5` 第 3 章 §3.5 的"测试提速"是一个新的理由** —— 那里提速是为了"人少等"，这里是为了"agent 能完成任务"。

### Cloudflare 列出的 agent 对工具的三条要求

（同出自原书第 6 章已核验材料）

| 要求 | 为什么 |
|---|---|
| **快的构建、测试、lint / format** | 三者从"偶发检查"变成**持续护栏** |
| **清晰结构化的错误** | agent 必须**程序化读取**并据此行动 |
| **一致的 CLI** | 输出或 flag 的小不一致，会导致 agent **大幅绕路** |

**⭐ 第一条里"护栏"这个词值得注意**：**人类跑 lint 是提交前跑一次，agent 是每改一次都跑。** 频率变了，**对延迟的容忍度也变了**。

**第三条是本节最容易被低估的**：**"一致的 CLI"对人的成本是"查一下文档"，对 agent 的成本是"走错一圈再回来"** —— 而**后者会被乘以循环次数**。

### 所以"AI 友好"是一个接口问题

**判据很干脆**：

> **如果一个工具只能被人用（只有交互式 CLI、输出只有人可读的日志），它就不能被 AI 用。**

| 工具形态 | 人能用的 | AI 能用的 |
|---|---|---|
| 交互式 CLI + 彩色日志 | ✅ | ❌ |
| CLI + `--json` 输出 | ✅ | ✅ |
| **声明式的能力清单 + 结构化调用** | ✅ | ✅✅ |

**第三行才是这一节的落点**：**不是"加个 `--json` 就够了"，而是"工具要能说出自己有什么能力"**。

**因为 AI 的困难不在"执行一个已知动作"，而在"不知道有哪些动作可用"。** 而**一份能力清单**解决的问题正是"有哪些"。

### MCP 的官方类比恰好说明了这一点

MCP（Model Context Protocol）官方的定义是：

> 一个**开源标准**，用于把 AI 应用连接到外部系统。借助 MCP，Claude、ChatGPT 这类 AI 应用可以连接**数据源**（如本地文件、数据库）、**工具**（如搜索引擎、计算器）与**工作流**（如专用提示词）。

而它给的类比是：

> **把 MCP 想象成 AI 应用的 USB-C 接口。**

**⭐ "USB-C"这个类比点出了成本结构**：**它解决的是 M×N 的适配问题，不是能力问题。**

> **每个 AI 应用 × 每个工具 = M×N 次定制集成；统一协议把它变成 M+N。**

**所以"AI 友好"不是"让 AI 更聪明"，而是"少写 M×N 个适配层"。** 这与 `X1` 第 1 章 §1.2 的"`npm create` 是统一入口"、`D3` 第 4 章 §4.6 的"插件接口是一套还是两套"是**同一个成本结构**：**接口统一的收益是乘法的，不是加法的。**

## 1.2 三层价值：分界在接口，不在模型

`X3.L3.02`。三层常被描述成"AI 越来越强"，但**它们的实际分界是"AI 能拿到多少结构化状态"**。

### 三层

| 层 | AI 做什么 | 需要工具提供什么 |
|---|---|---|
| **① 配置助手** | 生成配置文件文本 | **几乎没有要求**（它只需要知道语法） |
| **② 工具使用者** | 调用命令、读结果、迭代 | **结构化输出 + 可发现的能力** |
| **③ 诊断参与者** | 读状态、提假设、设计验证 | **可查询的内部状态**（依赖图、产物、耗时） |

**⭐ 三层的分界不在"模型多聪明"**：

| 从 → 到 | 真正的门槛 |
|---|---|
| ① → ② | **工具能不能输出结构化结果** |
| ② → ③ | **工具能不能暴露内部状态**（而不只是"成功/失败"） |

**所以一个"很强的模型"配一个"只会打印彩色日志的工具"，也停留在第 ① 层。**

**这条判断很重要，因为它把"提升 AI 效果"这件事从"等更好的模型"变成了"改工具的接口"** —— 后者是**你可以做的**。

### 一个技术之外的原因：训练数据里的出现频率（原书第 6 章已核验，2026-10-10）

**第三层还有一个非技术的解释。** 原书记录的数据点：`@cloudflare/vite-plugin` 周下载量约 **1400 万**，约为 Vite 自身安装量的 **10%**。Cloudflare 的解释是：

> **Agent 编码的应用正在选择 Vite。**

**而 Vite 胜出的原因里，有一条与本书其他章节不同**：快、文档好、兼容广 —— **而且在大模型训练数据中出现得多**。

**⭐ 这条呼应的是 `D3` 第 3 章讲过的「默认即权力」** —— 只是**从"框架的默认值"换成了"模型训练数据里的默认偏好"**：

> **当 AI 成为用户时，「训练数据里的出现频率」成了一种新的默认。**

**这条对"选型"有一个很实际的推论**：

| 你关心什么 | 该看什么 |
|---|---|
| **开发者的体验** | 文档、社区、生态 |
| **AI 的命中率** | **这个工具在语料里出现得够不够多** |

**而第二行是有代价的**：**它奖励"已经被写过很多次"的东西，不奖励"设计得更好"的东西** —— 这与 `D3` 第 9 章 §9.6 的"选型不能只看能力矩阵"是同一个提醒。

**⚠️ 这组数字来自原书 2026-10-10 的核验，本轮未复核**；而**"训练数据占比"本身无法被直接验证**（语料不公开），所以它是**一个解释，不是一条可证伪的机制** —— 这一点按本章 §1.1 的标准应当说清。

### 每一层的具体缺口

| 层 | 常见缺口 | 后果 |
|---|---|---|
| **①** | 模型不知道你的**版本**，会生成旧写法 | 配置看起来对，但选项已废弃（`D3` 第 3 章的 Babel 8、`D4` 第 1 章的 Tailwind v4 都是实例） |
| **②** | 输出只有人可读文本 | AI 只能"猜"失败原因 |
| **③** | 内部状态不可查 | AI 只能提"可能的"原因，无法验证 |

**⭐ 第一个缺口是"版本敏感"** —— 而它在本书里已经反复出现：

| 已被本书核验推翻的旧写法 | 出处 |
|---|---|
| `useBuiltIns: 'usage'` 是最佳实践 | `D3` 第 3 章（**Babel 8 已移除**） |
| Vite 用 `output.manualChunks` 拆包 | `D3` 第 3 章（**入口已改为 `codeSplitting`**） |
| Tailwind 需要 `tailwind.config.js` | `D4` 第 1 章（**v4 是 CSS-first**） |
| 原生嵌套可替代 Sass 的 `&__` | `D4` 第 1 章（**不能拼接**） |
| `revalidate` 是定时任务 | `X2` 第 1 章（**请求驱动**） |

**这张表本身就是"第 ① 层的固有缺陷"的证据**：**模型的训练数据里同时有新旧两种说法，而它不会告诉你哪个是旧的。**

**而这张表也解释了本书为什么要逐章核验官方文档** —— **不是为了纠正 AI，而是因为人也会犯同样的错。**

## 1.3 实践形态：结构化诊断与运行时感知

`X3.L3.03`。这一节把 MCP 的协议结构**映射到构建工具**上 —— 而这是本章唯一有官方依据的部分。

### MCP 的三个角色

官方定义（协议版本 **2026-07-28**）：

| 角色 | 官方定义 |
|---|---|
| **Host** | **协调并管理一个或多个 client 的 AI 应用** |
| **Client** | **维持与某个 server 的连接、为 host 获取上下文的组件** |
| **Server** | **向 client 提供上下文的程序** |

**拓扑是 `1 host : N client : N server`**：

> host 每连接一个 server，就**实例化一个专属 client**，各 client 与对应 server 保持**专用连接**。

**而本地与远程的差别在"一个 server 服务几个 client"**：

| 传输 | 典型情况 |
|---|---|
| **stdio** | 本地 server，**通常只服务单个 client** |
| **Streamable HTTP** | 远程 server，**通常服务多个 client** |

### Server 暴露的三个原语

官方称 server 暴露**三个核心 primitives**：

| 原语 | 官方定义 | 方法 |
|---|---|---|
| **Tools** | **可执行函数**，AI 可调用来执行动作（文件操作、API 调用、数据库查询） | `tools/list` / `tools/call` |
| **Resources** | **提供上下文信息的数据源**（文件内容、数据库记录、API 响应） | `*/list` / `*/get` |
| **Prompts** | **可复用的交互模板**（system prompt、few-shot 示例） | —— |

**⭐ 官方强调：列表是「动态的」。** 这条很关键 —— **能力不是编译期固定的，AI 应当重新发现**。

### ⭐ 映射到构建工具：这张表是本章的核心

| MCP 原语 | 构建工具里的对应物 | 有没有 |
|---|---|---|
| **Resources** | **构建统计、依赖图、产物清单、诊断列表** | 通常**没有**（只在日志里） |
| **Tools** | **触发构建、读诊断、跑测试、清缓存** | 通常**有**（就是 CLI） |
| **Prompts** | **预设的诊断流程**（"先看依赖图，再看产物"） | 通常**没有** |

**⭐ 所以"构建工具对 AI 不友好"的根因很具体**：

> **它的 `Tools` 齐全（CLI 什么都能干），但 `Resources` 几乎为零（内部状态只在日志里）。**

**这意味着 AI 能"做"，但不能"看"** —— 而**诊断恰恰是"看"的工作**。**这与 §1.2 的"② → ③ 的门槛是暴露内部状态"完全对应。**

**而 `D3` 第 4 章 §4.2 已经给出了"内部状态"里最关键的一份**：**依赖图**。

> **一个能查询依赖图的构建器，天然给 AI 提供了 `Resources`；一个只能打印"build failed"的构建器，什么都没给。**

### 一个具体的差距示例

**同一个失败，两种输出**：

| 输出形式 | AI 能做什么 |
|---|---|
| `Error: Module not found: ./utils` | 猜"是不是路径写错了" |
| `{ code: "MODULE_NOT_FOUND", importer: "src/a.ts", request: "./utils", candidates: [], resolveChain: [...] }` | **直接说出"它找了这几个位置，都不存在"** |

**第二行之所以可行，是因为它给了三样东西**：**诊断码**（可分类）、**位置**（含 importer）、**已尝试的候选**（可证伪）。

**⭐ "已尝试的候选"这一项最容易被漏掉，而它最有价值** —— 因为它把"我猜"变成了"我能排除"。

**这与 `D5` 第 4 章 §4.5 的"失败信息质量决定 F"是同一条，但标准更高**：**人能从"找不到"里猜出路径问题；模型不会猜，它会编一个看起来合理的路径。**

### 形态二：让 AI 感知运行时（原书第 6 章已核验，2026-10-10）

**问题**：**AI 看不见浏览器。** DOM、console 输出、computed style、组件树都在**运行时**，**源码里没有**。

**做法**：以 dev server 中间件 / 浏览器代理的形式，把运行时的东西通过 **MCP** 暴露给 agent。原书列出的暴露内容：

| 可暴露的运行时状态 |
|---|
| DOM 结构 |
| 组件树 |
| computed style |
| 编译后的模块图 |
| 路由状态 |
| 服务端日志 |

**⭐ 这个"形态二"恰好对应 §1.3 那张映射表里最空的一格**：**`Resources`（上下文数据源）**。**运行时状态在源码里不存在，所以它是唯一必须"专门暴露"的一类状态。**

### 一个官方动作：`server.forwardConsole`

**Vite 8 提供 `server.forwardConsole`：把客户端 console 转发到终端。** 官方文档明确说它"**在使用 AI 编码代理时尤为实用**"（原书第 6 章已核验，**本轮未复核该选项**）。

**⭐ 为什么这条值得单独记**：**它说明"AI 看不见浏览器"是一个被工具官方承认的痛点** —— 不再是社区自发的补丁。

**而它也是"工具侧改动"的范例**：**加一个转发选项，就让一类状态变得可被消费。** **这比"换更强的模型"便宜得多**（§1.2 的结论）。

### ⚠️ 四处版本敏感的变化（必须标注）

**MCP 在 2026-07-28 版里有几处与前代差异很大的变化**，而**这些变化恰好是"AI 友好"这件事本身在演进**的证据：

| 变化 | 内容 |
|---|---|
| **握手方式** | **`server/discover` 取代了 `initialize`**；MCP 现在是**无状态协议** —— **每个请求都在 `_meta` 里带协议版本、客户端信息与能力** |
| **Sampling 与 Logging 已弃用** | Sampling 的官方建议是"**新实现应直接对接 LLM 供应商 API**"；Logging 改为写 stderr 或 OpenTelemetry |
| **`roots` 未出现** | 该架构页**完全没有 `roots` 一词**（它属于早期 `initialize` 握手的 `clientCapabilities.roots`） |
| **变更通知改为 opt-in** | 客户端发 `subscriptions/listen` 建立长连接；**通知是 best-effort**，官方建议**仍要靠轮询保证新鲜度** |

**⭐ 第一行值得展开**：**"无状态"这个设计让每个请求自包含** —— 于是**服务器不需要依赖连接状态**。**这对"工具被多个 AI 客户端调用"这个场景是必要的**（远程 server 服务多个 client）。

**而第三行是一个提醒**：**如果你按一篇旧文章实现 MCP，你可能会去实现一个已经不存在的字段。** **这正是 §1.2 第 ① 层缺口的实例。**

### 一条判据

**判断一个构建工具"能不能被 AI 诊断"，只问一句**：

> **除了给人看的日志，它还能输出什么？**

| 还能输出 | 能到的层 |
|---|---|
| 什么都没有 | ① 配置助手 |
| **结构化诊断（码 + 位置）** | ② 工具使用者 |
| **+ 可查询的内部状态（依赖图 / 产物 / 耗时）** | ③ 诊断参与者 |

## 1.4 风险与边界

`X3.L3.04`。这一节给三类风险与一条判据 —— 而**它的重点不是"AI 会犯错"，是"错的代价不对称"**。

### 三类风险

| # | 风险 | 机制 | 为什么危险 |
|---|---|---|---|
| **1** | **幻觉的配置** | 模型生成**不存在的选项** | **很多工具会静默忽略未知选项**（`D3` 第 2 章）→ **看起来生效了** |
| **2** | **过时的知识** | 训练数据里**新旧说法并存** | 它**不会标注哪条是旧的**（§1.2 那张表） |
| **3** | **不可逆的动作** | AI 触发了部署、清缓存、删产物 | **动作一旦执行，讨论就结束了** |

**⭐ 第一行的危险在"静默"**：

**如果工具对未知选项报错，幻觉会立刻被抓住。** 而**现实是很多工具接受并忽略它** —— 于是**"AI 写的配置生效了"这句话可能是假的**。

**这与 `D5` 第 2 章 §2.2 的"`vitest.config.*` 存在时 `vite.config.*` 全被忽略"、`D4` 第 1 章 §1.5 的"改错配置入口不报错"是同一类陷阱**：**配置类错误的默认行为是"安静地不生效"。**

### 一条判据：读可以放开，写必须留痕

> **读操作可以放开，写操作必须留痕。**

| 操作类型 | 建议 |
|---|---|
| **读**（查依赖图、看诊断、读产物清单） | 放开 —— **错了也只是"多看了一点"** |
| **本地写**（改文件、生成配置） | 可回滚（git），**要能看到 diff** |
| **不可逆写**（部署、清缓存、删制品、改线上配置） | **必须人工确认 + 留痕** |

**⭐ 第三行的判据不是"危险程度"，而是"可回滚性"**：

> **判断一个动作能不能交给 AI，看它能不能被撤销。**

**这与 `D6` 第 1 章 §1.5 的"回滚是切索引"、`D4` 第 3 章 §3.3「回滚能力」的"删旧不可回滚所以放最后"是同一条纪律**：**不可回滚的动作要最后做、要有人看着。**

### 第四条边界：结构化诊断是「有损」的

（出自原书第 6 章已核验材料）

**诊断信息一旦结构化，就必然丢失细节** —— 因为**结构是"预选出的字段"，而失败的原因可能不在那些字段里**。

**所以需要"两步式"**：

| 步 | 返回什么 |
|---|---|
| **① 结构化摘要** | 码 + 位置 + 候选（小、快、可批量） |
| **② 取详情** | 完整堆栈 / 原始日志 / 上下文（大、慢、按需） |

**⭐ 只给第 ① 步会丢信息，只给第 ② 步会让 AI 无法批量处理。** 两步式的意义是**让"广度"和"深度"分开付费**。

**这与 `D6` 第 4 章 §4.6 的"可观测性三个层次"是同一个设计**：**指标（聚合）→ 追踪（单次）→ 日志（细节）**，**逐层变贵、逐层按需**。

**而它与 §1.3 的"已尝试的候选"是互补的**：**候选列表是"深度"的一种预取** —— 它在第 ① 步就把最常用的细节带上，从而减少第 ② 步的往返。

### 两个必须分开的等式

**这一节最容易出错的地方，是把两件事当成一回事**：

| 这句话 | 成立吗 |
|---|---|
| **"AI 说它改了"** | ❌ **不等于它改了** |
| **"构建成功了"** | ❌ **不等于改对了** |

**第一行**：模型可能表述一个它没做的动作（或做了另一个）。

**第二行**：**构建成功只证明"没有编译/打包错误"** —— 而**`D3` 第 9 章 §9.5 的行为风险、`D4` 第 2 章 §2.3 的样式覆盖、`D5` 第 2 章 §2.5 的视觉回归**都是"构建成功但行为错了"的实例。

**所以验证仍然是人的事（或者是另一套自动化的）** —— 而这就引出本节最重要的一条。

### ⭐ 生产成本降低了，验证成本没降

**这是本章唯一一个可以确定的结构性结论**：

| 成本 | AI 的影响 |
|---|---|
| **生产**（写代码、写配置） | **大幅降低** |
| **验证**（跑测试、看视觉、判对错） | **几乎不变** |

**推论**：

> **验证在总成本中的占比会上升** —— 而**它本来就已经是被忽略的那一半**。

**这与 `D5` 第 4 章 §4.1–§4.2 是同一个结论的直接延伸**：那章说 **F（失败归因成本）被系统性忽略**；这里说 **AI 让"生产"变便宜之后，被忽略的那部分占比更高了**。

**所以"用 AI 提效"这件事的正确问法不是"它能写多快"，而是**：

> **它的输出，我们要花多久才能确认是对的？**

**如果这个时间没有下降，那提效只发生在"写"这一半** —— 而**交付的总时间是两半之和**。

### 一条边界：不要问"AI 能不能做 X"

**这一类问题没有稳定答案**，因为**"能做"这件事每周都在变**。**有稳定答案的是**：

| 稳定可问 | 不稳定的 |
|---|---|
| 这个工具的**输出**是结构化的吗 | AI 能不能读懂这个日志 |
| 这个动作**可回滚**吗 | AI 会不会搞错 |
| 这份配置**有 schema 校验**吗 | AI 会不会写出不存在的选项 |

**左列的答案**由**你的工具**决定，**右列由模型决定** —— 而**你能改的是左列**。

**这与 §1.2 的结论完全一致**：**把"提升 AI 效果"从"等更好的模型"变成"改工具的接口"。**

## 1.5 治理动作：六个判定阈值

| # | 现象 | 判定阈值（起点值） | 动作 | 依据 |
|---|---|---|---|---|
| 1 | "AI 写的配置没生效" | **工具会静默忽略未知选项** | 加 schema 校验（`D3` 第 2 章）；**不要靠"看起来生效"** | §1.4 |
| 2 | AI 给了已废弃的写法 | **同一说法在文档里有新旧两版** | 以官方文档为准逐项核验（本书全书做法） | §1.2 |
| 3 | AI 只能"猜"失败原因 | **构建输出只有人可读文本** | 补结构化诊断（码 + 位置 + 已尝试的候选） | §1.3 |
| 4 | AI 无法验证假设 | **内部状态（依赖图/产物/耗时）不可查** | 把状态做成可查询的（`Resources`），而不只是日志 | §1.3 |
| 5 | AI 触发了线上变更 | **动作不可回滚** | 不可逆写必须人工确认 + 留痕（看可回滚性，不看危险程度） | §1.4 |
| 6 | 用了 AI 但交付周期没变短 | **验证时间没有下降** | 提效只发生在"生产"一半；去优化验证侧的自动化 | §1.4 |

### 三条使用说明

**① 阈值 1 与 3 都是"工具侧"的问题，不是模型侧。**

这是本章最实用的取向：**你能改的是工具**。

**② 阈值 5 的判据是"可回滚性"，不是"影响面大小"。**

一个"影响面很大但能一键回滚"的动作，比"影响面很小但不可逆"的动作更适合交给 AI。

**③ 阈值 6 是最容易被回避的一条。**

**"用了 AI"与"变快了"是两件事** —— 而**它们之间的差距通常就在验证侧**。

### 什么时候"不该让 AI 碰"

| 情况 | 为什么 |
|---|---|
| **没有 diff 可看** | 无法审阅就等于无法验证 |
| **没有回滚路径** | 一旦出错，讨论结束 |
| **输出不可结构化** | 它只能靠猜，而猜错会编 |
| **团队还没有验证手段** | 提效只会在"生产"半边兑现（`D5` 第 2 章） |

## 1.6 动手

| 任务 | 验收 |
|---|---|
| 查一次你项目的构建失败输出 | 它是"一句话"还是"码 + 位置 + 已尝试的候选" |
| 查一次你的工具链有没有 `--json` 一类的结构化输出 | 若有，说出它覆盖了哪些命令 |
| 列出你的"内部状态"（依赖图/产物/耗时） | 标出哪些只能从日志里读、哪些可查询 |
| 查一次你的配置有没有 schema 校验 | 若没有，说出"写错一个选项"会怎样 |
| 找一条你确信的配置写法，去官方文档核对 | 记录它是否已经变了（本书已有多处实例） |
| 列出你交给 AI 的全部动作 | 按"可回滚 / 不可回滚"分类 |
| 计时一次"确认 AI 的输出是对的"要多久 | 与"自己写"对比，说出提效发生在哪一半 |
| 查一次你的构建工具有没有可发现的能力清单 | 若无，说出 AI 怎么知道有哪些命令 |
| 复述一次 MCP 的三个原语 | 说出你的构建工具在哪个原语上是空的 |

**进阶挑战**（任选一项）：

1. **给构建工具补一份结构化诊断**：把最常出现的 3 类失败，从"一行文字"改成"码 + 位置 + 已尝试候选"。目标是**让"猜"变成"排除"**。
2. **把一处内部状态做成可查询的**：最值得做的是依赖图（`D3` 第 4 章 §4.2）。要求能回答"这个文件被谁引用"。
3. **做一次"验证成本"测量**：对同一类改动，分别记录"生产时间"与"验证时间"。目标是**给出你自己的比例**，而不是引用别人的结论。

## 1.7 本章常见误区

| # | 误区 | 纠正 |
|---|---|---|
| 1 | "AI 读日志和读人一样容易" | **日志是给人看的**。AI 需要**结构化数据**（JSON / 诊断码 / 位置） |
| 2 | "给 CLI 加个 `--json` 就够了" | 更关键的是**工具能说出自己有什么能力**（可发现的能力清单） |
| 3 | "AI 友好是让 AI 更聪明" | 是**少写 M×N 个适配层**（MCP 的"USB-C"类比正是这个成本结构） |
| 4 | "模型知道最新的写法" | 训练数据里**新旧并存**，而**它不标注哪条是旧的**。本书已核验推翻多条流行写法 |
| 5 | "AI 写的配置没生效，说明它写错了" | 也可能是**工具静默忽略了未知选项** —— 这是配置类错误的默认行为 |
| 6 | "构建工具对 AI 不友好是因为 CLI 不好用" | 根因是 **`Resources` 几乎为零**：**能"做"但不能"看"**，而诊断是"看"的工作 |
| 7 | "诊断就是把日志打详细点" | 结构化诊断需要**诊断码（可分类）+ 位置（含 importer）+ 已尝试的候选（可证伪）** |
| 8 | "AI 能提出可能原因就够了" | **能提假设 ≠ 能验证**。验证需要**可查询的内部状态** |
| 9 | "交给 AI 的动作看影响面大小就行" | 判据是**可回滚性**：影响大但可一键回滚，比影响小但不可逆更适合交给 AI |
| 10 | "读操作也要审批" | 读错了只是"多看了一点"；**写才需要留痕**，不可逆写需要人工确认 |
| 11 | "用 AI 就能缩短交付周期" | **生产成本降了，验证成本没降** → 验证占比上升。**总时间是两半之和** |
| 12 | "提效不明显，说明 AI 不行" | 可能只是**提效发生在"写"这一半**，而那一半不是瓶颈 |
| 13 | "问 AI 能不能做 X 就能知道" | 这类问题**没有稳定答案**。稳定可问的是"输出结构化吗 / 动作可回滚吗 / 配置有 schema 吗" |
| 14 | "MCP 是一个产品" | 它是**开放标准 / 协议**（官方：开源标准、开放协议），有独立的规范与提案流程 |
| 15 | "MCP 就是给 AI 加工具调用" | 它有**三个原语**（Tools / Resources / Prompts）与**三角色**（Host / Client / Server），且**列表是动态的** |
| 16 | "MCP 还是旧的握手方式" | **2026-07-28 版用 `server/discover` 取代了 `initialize`**，且**协议变为无状态**（每请求在 `_meta` 带版本与能力） |
| 17 | "Sampling 是 MCP 的核心能力" | **它在 2026-07-28 已弃用**，官方建议"新实现直接对接 LLM 供应商 API" |
| 18 | "MCP 有 roots 这个客户端能力" | **该架构页完全没有 `roots` 一词**（属早期 `initialize` 握手的 `clientCapabilities`） |
| 19 | "订阅式变更通知是默认的" | **改为 opt-in**（`subscriptions/listen`），且**通知是 best-effort**，官方建议**仍要靠轮询** |
| 20 | "协议版本不影响实现" | 上述四处变化（握手 / 无状态 / Sampling 弃用 / 订阅 opt-in）**都会让按旧文章写的实现失效** |
| 21 | "构建慢对人和对 agent 是同一件事" | **对人是体验问题，对 agent 是可靠性问题**（Cloudflare：速度是 agent 的**可靠性要求**）→ **速度从 nice to have 变成必选项** |
| 22 | "结构化诊断越全越好" | **结构必然有损**（结构是预选字段，而失败原因可能不在其中）。需要**两步式**：结构化摘要 + 按需取详情 |
| 23 | "AI 能读源码就够了" | **运行时（DOM / console / computed style / 组件树）源码里没有** → 必须专门暴露（如 `server.forwardConsole`） |
| 24 | "CLI 的写法不一致只是小问题" | 对人成本是"查一下文档"，对 agent 是"走错一圈再回来"，**且会被循环次数放大** |
