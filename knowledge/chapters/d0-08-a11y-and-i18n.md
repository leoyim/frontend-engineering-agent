## 8.1 可访问名是"按顺序算出来的"

D0 第 1 章说过图片的**可访问名**来自 `alt`。控件的可访问名则遵循一套**计算顺序**（Accessible Name and Description Computation）：

```text
① aria-labelledby（指向其他元素的 id）
② aria-label
③ 原生标签机制（<label for>、<legend>、<caption>、<figcaption>…）
④ 元素内容本身
⑤ title 属性（最后的兜底）
```

**顺序决定优先级**，由此可以推出两个重要结论：

- **`aria-label` 会覆盖可见文本**。给一个写着"删除"的按钮加 `aria-label="移除该条目"`，屏幕阅读器读的是后者，视觉用户看到的是前者 —— **两者不一致是很糟的体验**（语音控制用户按可见文字说话时会失败）。所以要覆盖，就要让两边含义一致。
- **`title` 是最差的来源**：它排在最后、在触屏上不显示、提示延迟长。不该把它当成命名手段。

**这套顺序有一个容易忽略的推论**：**"没有可访问名"不是指"没有 `aria-label`"**。一个 `<button><img src="x.svg"></button>` 的 `alt` 为空时，可访问名是**空字符串** —— 屏幕阅读器读作"按钮"，而用户不知道它做什么。

> **判据：把元素的可见表现完全遮住，只留可访问名 —— 用户还能知道它是做什么的吗？**

## 8.2 ARIA 的五条使用规则

| # | 规则 | 违反后的典型故障 |
|---|---|---|
| 1 | 能用原生语义就用原生语义 | 自己实现按钮，键盘行为缺失（D0 第 1 章 §1.2） |
| 2 | **不要改原生语义** | 给 `<h2 role="presentation">` 会让标题在 a11y tree 中消失 |
| 3 | 交互式 ARIA 控件必须支持键盘 | `role="button"` 却不响应 Enter / Space |
| 4 | **不要把可聚焦元素设为 `aria-hidden`** | 元素对屏幕阅读器不可见、但仍能被 Tab 聚焦 → 出现"无名的焦点"，用户彻底迷失 |
| 5 | 所有交互元素必须有可访问名 | 只有一个图标的按钮读作"按钮" |

第 4 条是最容易犯的一类错误。**修法是 `inert`，不是 `aria-hidden`。**

**这五条可以压缩成一句**：

> **ARIA 不增加能力，它只（部分地）补上你丢掉的原生语义。**

**所以"加更多 ARIA"从来不是解法。** `role` 不会让元素变得可交互，`aria-label` 不会让元素变得可见 —— 它们只影响**第二棵树**（a11y tree），不改第一棵树（DOM）的行为。

## 8.3 焦点管理：三件必须做的事

| 场景 | 要求 |
|---|---|
| **打开模态框** | 焦点移入框内；**把焦点限制在框内**（焦点陷阱）；关闭后**归还到触发元素** |
| **背景内容** | 用 `inert` 让背景整体不可交互（比手动逐个 `aria-hidden` 可靠，因为它同时移出 tab 序列） |
| **顺序一致性** | 焦点顺序应与视觉顺序一致；用 CSS 改变视觉位置时（如 `order`、`row-reverse`）会破坏它 |

关于 `tabindex` 的三个值：

| 值 | 含义 | 评价 |
|---|---|---|
| `0` | 加入 tab 序列，顺序按 DOM 位置 | 正确做法 |
| `-1` | **可用 JS 聚焦但不进 tab 序列** | 用于程序化移焦（模态框） |
| 正值 | 强制优先级 | **反模式**：会打乱自然顺序，且难以维护 |

**第三条（顺序一致性）是唯一没有工具能查的**：自动化测不出"焦点顺序和视觉顺序相反"。它只会在真实用户手里暴露 —— 而那时你通常已经上线了。

**`inert` 与 `aria-hidden` 的差别值得单独记住**：

| | `aria-hidden` | `inert` |
|---|---|---|
| 对屏幕阅读器隐藏 | ✅ | ✅ |
| **移出 Tab 序列** | ❌ | ✅ |
| **屏蔽鼠标点击** | ❌ | ✅ |

**只有第一列时，你得到的是"看不见但仍能按到"** —— §8.2 第 4 条说的就是这个坑。

## 8.4 自动化测试的边界：约三分之一

| 工具 | 位置 |
|---|---|
| axe-core | 可嵌入测试或页面 |
| Lighthouse | DevTools 内的快速体检 |
| Playwright + axe | **CI 中的自动化回归**（对应 D5 领域） |

**必须说清边界**：自动化只能查出**约三分之一**的问题 —— 主要是"可判定的"那些（缺可访问名、对比度、标签关联、`aria-hidden` 冲突）。而**键盘流程是否顺畅、语义是否合理、屏幕阅读器体验如何，只能人工验证**。

> **⚠️ 一处如实标注**：**"约三分之一"是业界广泛引用的量级，本次未核到唯一官方出处**（WebAIM 的年度调查给的是"首页错误数"分布，不是"可自动化比例"）。**本书使用它作为量级判断，不作为精确数字** —— 真正可靠的表述是：**自动化只能覆盖"结构可判定"的那一类，而这类问题在真实站点上只占少数。**

**所以"Lighthouse 无障碍 100 分"不等于"可访问"** —— 它只证明你通过了那一类。

**这条边界与 D5 第 2 章的分层判据是同一个道理**（"少写 E2E 的理由是失败信号里指向'代码错了'的比例低"）：**任何检查的价值取决于它能判定什么，不取决于它跑得多勤。**

**一个可操作的替代方案**（比"提高分数"有用得多）：**给键盘流程写一条逐步走的脚本** —— Tab 到哪、Enter 后焦点去哪、Esc 后焦点回哪。它不可自动化断言"体验好不好"，但能**守住不回退**。

## 8.5 `lang` 的层级与作用

- `<html lang="zh-CN">` 声明整页语言（D0 第 1 章 §1.1 讲过它决定发音引擎、断行规则、字体回退）。
- **`lang` 可以挂在任意元素上**：一段引用英文原文时写 `<blockquote lang="en">`，屏幕阅读器会切回英语音素。
- `dir="rtl"` 声明书写方向，此时**逻辑属性**（D0 第 2 章 §2.6）才真正发挥价值。

**第二行是最容易被忽略的**：`lang` 不是"页面级元数据"，它是**可继承的属性**。而它的实际后果比你预想的多：

| 后果 | 说明 |
|---|---|
| **发音引擎** | 用哪种语言的音素读这段文字 |
| **断行规则** | 中文按字断、英文按词断 —— 断错会读成两个词 |
| **字体回退** | 缺字时选哪个后备字体 |
| **引号与标点** | `q` 元素的引号形态随语言变化 |

**所以"混排不写 `lang`"不是一个小疏忽**：一小段没标 `lang` 的英文，可能被中文音素读成不可理解的音节。

## 8.6 不要手写格式化：用 `Intl`

| API | 解决什么 |
|---|---|
| `Intl.NumberFormat` | 千分位、小数、货币、百分比（各语言分组与小数符号不同） |
| `Intl.DateTimeFormat` | 日期时间格式（顺序与写法随地区差异极大） |
| `Intl.RelativeTimeFormat` | "3 天前"这类相对时间 |
| `Intl.ListFormat` | 列表连接词（"A、B 和 C" / "A, B, and C"） |
| `Intl.Collator` | **按语言规则排序**（拼音、变音符号的正确处理） |

最后一项常被忽略：**JS 的默认 `sort()` 是按 UTF-16 码元比较**，对中文与带变音符号的欧洲语言都不符合直觉，必须用 `Intl.Collator`。

**为什么这件事不该"自己写个函数"**：格式化规则**随语言版本变化**（CLDR 数据在更新）。手写函数冻结了某一年的规则，而 `Intl` 跟着运行时走。

**这也是"默认值"主题的一次重现**（D0 第 7 章 §7.8）：**`Intl` 的默认不是"英文格式"，是"当前语言环境"。** 你什么都不传时它已经在按环境做事 —— 手写格式化等于把这个默认值丢掉。

## 8.7 复数与语序：为什么不能在代码里拼句子

```js
// 反例：把句子拼在代码里
const msg = count + " items selected";
```

问题有两层：

- **复数规则因语言而异**。英语有单复数；有些语言有多个复数形式。`Intl.PluralRules` 就是为这件事存在的 —— **不要用 `if (count === 1)` 判断**。
- **语序不同**。中文"已选中 N 项"与英语"N items selected"的词序不同，硬拼字符串在翻译时必然出问题。

**正确做法**：用带占位符的文案模板（key-value），把语序交给译文：

```json
{ "selected": "已选中 {count} 项" }
```

**第三层问题最隐蔽**：**标点与空格也是语言相关的**。中文句末用"。"、英文用"." 加空格；`(`${name}，你好`)` 在英文界面里会变成"John，Hello"，多一个逗号、错一个标点。

> **判据：如果一句话里既有变量又有语法（复数、格、语序、标点），它就必须整体交给译文，不能由代码拼接。**

## 8.8 时区：存储与展示分离

| 原则 | 说明 |
|---|---|
| **存储用 UTC 或带时区的绝对时间戳** | 存本地时间字符串会在跨时区与夏令时上出错 |
| **展示时再转本地** | 由 `Intl.DateTimeFormat` 按用户时区渲染 |
| `Date` 的历史坑 | 月份从 0 开始、`getYear` 的废弃、解析字符串的行为不一致 |

`new Intl.DateTimeFormat().resolvedOptions().timeZone` 可读出运行环境的时区，便于调试。

**夏令时才是这条规则的真正理由**，不是"跨时区麻烦"：

| 存法 | 出问题的时刻 |
|---|---|
| 存本地时间字符串 | **夏令时切换那一小时**，同一字符串会指向两个时刻（或不存在） |
| 存 UTC 时间戳 | 从不。它只有一个含义 |

**所以"存 UTC"不是为了整齐，是为了让时间有唯一解释** —— 这与 D3 第 8 章讲"内容哈希让 URL 有唯一解释"是同一种结构。

**还有一条常被忽略**：**服务端渲染时"本地时区"是服务器的时区**。所以 SSR 页面里直接 `new Date().toLocaleString()` 会渲染出服务器的时区，而不是用户的 —— 这也是 D0 第 2 章 §2.4 讲的 hydration mismatch 的常见来源之一。

## 8.9 与服务端协商的接回

语言通常由 `Accept-Language` 请求头协商（D0 第 6 章 §6.3）。这里必须回看那条结论：

> **只要响应内容依赖某个请求头，就必须把它写进 `Vary`。**

漏写 `Vary: Accept-Language` 的后果是：**服务器按语言返回了不同内容，而中间缓存只保留了一份** —— 中文用户可能拿到英文页面，反之亦然。

**国际化与缓存策略是同一件事的两面。**

**这条接回不是巧合，而是本章最值得记住的结构**：**i18n 的失败通常不发生在渲染，而发生在缓存。** 页面本身完全正确，是"另一份正确的页面"被发给了错的人。

| 症状 | 真正的原因 |
|---|---|
| 部分用户看到英文 | `Vary` 漏了，共享缓存只留了一份 |
| 切换语言后不生效 | 缓存键里没有语言维度 |
| 只有某些地区的用户出错 | CDN 按地区分副本，但没按语言分 |

**判据**：**"同一 URL 是否可能对应多份内容"这个问题，必须由 `Vary` 回答 —— 否则就是缓存层在替你猜。**

## 8.10 治理动作：六个判定阈值

| # | 现象 | 判定阈值（起点值） | 动作 | 依据 |
|---|---|---|---|---|
| 1 | 交互元素只有图标，无文字 | **出现即改** | 补可访问名，并验证与可见含义一致 | §8.1（顺序决定优先级） |
| 2 | 用 `aria-hidden` 隐藏可聚焦元素 | **出现即错** | 改用 `inert` | §8.3（两者差两列） |
| 3 | `aria-label` 与可见文本不一致 | **任何** | 要么改一致，要么别覆盖 | §8.1（语音控制用户按可见文字操作） |
| 4 | 模态框没有焦点归还 | **任何** | 关框后焦点回触发元素 | §8.3 |
| 5 | 页面上出现未标 `lang` 的外文段 | **>1 段** | 加 `lang`，否则发音与断行都错 | §8.5 |
| 6 | 内容随语言变化却没写 `Vary` | **任何** | 补 `Vary: Accept-Language` | §8.9（i18n 的失败常在缓存层） |

### 三条使用说明

**① 第 2 行是本章唯一"出现即错"的判定。** 它没有程度问题 —— `aria-hidden` 加在可聚焦元素上，**一定是 bug**，因为它制造了"能按到但看不见"的元素。

**② 第 1、3 行必须一起看。** 单看第 1 行，你会给所有图标按钮补 `aria-label`；但补的时候若与可见文本冲突，就触发第 3 行。**先决定"哪一边是主"，再动手。**

**③ 第 6 行最容易被判定为"运维的事"而搁置**，但它的判定成本最低（查一眼响应头），收益却直接指向"部分用户看到错误语言"这类**只在线上发生、且极难复现**的问题。

### 什么时候不该接着加

**三种情况，加了反而更糟**：

| 情况 | 为什么 |
|---|---|
| **原生语义已经正确** | 再叠 ARIA 只会制造"两套说法"。§8.2 规则 1 就是这个意思 |
| **团队还不能跑键盘验证** | 补了 `role="button"` 却没有键盘支持，**比不加更糟** —— 屏幕阅读器会宣布"按钮"，而按下去没反应 |
| **页面还没有稳定结构** | 焦点顺序与语义都会随改版失效，**先稳定布局再做 a11y** |

**这三条的共同点**：**ARIA 的每一次使用都增加一份需要长期维护的承诺。** 承诺不了的，不要写。

## 8.12 本章常见误区

> **本表只收录"正文没有完整讲过"的条目。** 其余判断已在 §8.1–§8.9 展开 —— 复述只会让人以为"记住表格就够了"。

| # | 误区 | 为什么错（正文没讲的部分） |
|---|---|---|
| 1 | 「a11y 是给少数人做的附加功能」 | 键盘操作、放大、字幕、对比度对**所有人在特定场景下**都必要（强光下看屏幕、临时单手操作）。**它是可用性的下限，不是附加项** |
| 2 | 「加了 `role` 元素就可交互了」 | `role` 只改**第二棵树**，不改行为。**"宣布成按钮"与"表现得像按钮"是两件事** |
| 3 | 「`aria-hidden` 就是隐藏」 | 它只对辅助技术生效。**对 Tab 键与鼠标完全无效** → 应用 `inert` |
| 4 | 「`aria-label` 加得越多越友好」 | 它会**覆盖**可见文本；两者不一致时，语音控制用户按可见文字说话会失败 |
| 5 | 「`title` 可以当标签用」 | 它在可访问名计算里排最后，触屏不显示、提示延迟长 |
| 6 | 「Lighthouse 无障碍满分就可访问了」 | 自动化只覆盖"结构可判定"的一类；**键盘流程与屏幕阅读器体验必须人工验证** |
| 7 | 「高对比度模式是给视力障碍者的」 | 它也是**强光环境**下的可用性保障 —— 同一份设计对所有人的边界情况都适用 |
| 8 | 「i18n 只是翻译文案」 | 还包括语言协商与缓存（`Vary`）、排序规则、时区、数字与日期格式、标点与语序 |
| 9 | 「排序用默认 `sort()` 就行」 | 默认按 UTF-16 码元比较；中文与带变音符号的语言需 `Intl.Collator` |
| 10 | 「复数规则就是 `if (count === 1)`」 | 不同语言复数形式数量不同，应用 `Intl.PluralRules` |
| 11 | 「时间直接存本地字符串」 | 应存 UTC 或绝对时间戳；本地字符串在**夏令时切换那一小时**会指向两个时刻或不存在 |
| 12 | 「SSR 里用 `toLocaleString()` 没问题」 | 那是**服务器的时区**，不是用户的 —— 也是 hydration mismatch 的常见来源 |
| 13 | 「语言只影响文案，不影响缓存」 | 内容随语言变却没写 `Vary`，共享缓存只留一份 → **部分用户看到错误语言** |
| 14 | 「`lang` 只在 `<html>` 上写一次就够」 | 它是可继承属性，混排段落必须就地标注，否则发音、断行、字体回退全错 |
