# D5 第 4 章 · 体系与度量

> **本章定位**：D5 领域**收官章**。前 3 章讲具体机制（检查、测试、门禁），本章讲**怎么把它们的投入排个序**，以及**用什么量来判断做得对不对**。整章为【补充背景】。
>
> **对应地图节点**：`D5.L4.01`（测试体系设计：金字塔落地与 ROI 权衡）· `D5.L4.02`（质量度量体系与质量文化建设，**【新】来源**）
>
> **前置**：`D5.L3.01` `D5.L3.04`（第 2、3 章）。
>
> **⚠️ 一条写作约定（重要）**：`D5.L4.02` 的标题含"质量文化建设"。**本章不写管理向内容**，而是把"文化"换成**四个可度量的机制指标**（§4.4）与**四个机制杠杆**（§4.5）。理由与全书一贯的立场相同：**"大家要有质量意识"不是可执行的话，而"谁能改阈值"是。**
>
> **⚠️ 关于 ROI 的诚实声明**：**本章不给 ROI 公式。** 因为公式里的三个量**都只能估**，写成公式会伪装成精确。本章给的是**估算框架**与**一个可换算的锚点**（误报折算成工时）。
>
> **读完能做到**：说出 ROI 里最常被漏掉的量是什么；说出为什么"多测一点"可能是负收益；说出测试落地的顺序为什么与金字塔图形相反；说出质量文化可以用哪四个数替代。

## 4.1 先把"值不值"拆成三个可估的量

"测试值得投入吗"这个问法没法回答，因为它把三件不同的事混成了一件。**拆开之后，每个都能估。**

### 三个量

| 量 | 含义 | 怎么估 |
|---|---|---|
| **C**（成本） | **写 + 每次跑 + 维护**。维护是"你没改任何代码但测试红了"的处理成本 | 按工时估：单条测试的写/改时间 × 条数，加上每月维护工时 |
| **R**（拦截率） | 这个测试**实际拦下过**多少缺陷 | **只能回看**：翻历史，数"它红了并且确实指出了真问题"的次数 |
| **F**（失败归因成本） | 一次红灯，人要多长时间判断"这是真问题还是误报" | 抽样计时：从看到红到得出结论的分钟数 |

**⭐ R 的定义必须强调**：**不是"理论上能拦什么"，而是"实际拦下过什么"。**

这个区别很关键：一个"理论上能拦住所有边界情况"的测试，如果**从来没红过**（可能因为从没跑到那条分支），它的 **R 实际是 0**。而它的 C 是实打实的。

### 为什么"值不值"在 C 与 R 之外，还要看 F

因为**大多数人算 ROI 时只算 C 和 R** —— 于是得出"多加测试总是划算"（R 看起来无穷大）。而 F 才是**决定测试是资产还是负债**的那一项。

**一个具体的换算锚点**：

| 项 | 数 |
|---|---|
| 一次误报的排查时间（保守） | **15 分钟 = 0.25 人时** |
| 一个月 100 次误报 | **25 人时** |
| 折合 | 约 **半个星期的人力** |

**这 25 人时不在任何预算里** —— 它散落在 100 次"点开日志、皱下眉、重跑"里。**这正是它被系统性忽略的原因：日常小额支出，从来不进项目账。**

### ROI 的定性判据（不是公式）

> **当 `C + F × 误报次数` 持续大于 `R × 单次漏网成本` 时，这条测试是负债。**

**三个必须说明的地方**：

1. **"单次漏网成本"极难估**（线上故障的代价因业务而异），所以这个判据只能用于**比较两条候选测试的相对价值**，不能用来算"测试部门该拿多少预算"。
2. **`F × 误报次数` 这一项会自我放大**（见 §4.2），所以它不是线性可加的。
3. **R 是回看量，不是预测量** —— 所以新写的测试**无法先验评估 ROI**。它的价值只能通过"上线后是否拦住过问题"来验证。

**第 3 点有一个尴尬的推论**：**"这条测试该不该写"这个问题，在写之前无法用 ROI 回答。** 只能用一个更弱但可用的判据：**它锁定的东西会不会意外变化**（第 2 章 §2.1 的分层判据）。

## 4.2 最关键的量是 F，而它被系统性忽略

### F 的四个组成

| 步骤 | 时间花在哪 |
|---|---|
| **① 看日志** | 报错信息是否指向具体位置 |
| **② 复现** | 本地能复现吗？不能的话要几轮？ |
| **③ 判断真假** | 是代码问题、环境问题，还是测试自身写得不对？ |
| **④ 通知与等待** | 找相关人、等回应、决定"先合了还是等修" |

**第 ③ 步是主要的**，而它**完全取决于错误信息的质量**。

这解释了第 2 章 §2.3 那条纪律为什么重要 —— **`findBy*` 抛"等待超时"、手写 `waitFor` + `getBy*` 抛"找不到元素"**：两者修起来的时间差好几倍，因为前者直接告诉你"等太久了"，后者会让你去查查询条件。

### F 会自我放大（这是本章最重要的一条）

```
F 高
  → 红灯时倾向"先重跑一次"
  → 重跑掩盖了真实的不稳定
  → 真实缺陷在上线后暴露（漏网成本↑）
  → 团队更不信红灯
  → F 更高
```

**这是一个正反馈。** 所以 **F 不是"一项成本"，而是"一个会加速恶化的状态"**：

| F 水平 | 团队行为 | 长期结果 |
|---|---|---|
| **低**（几分钟能判定） | 红灯就查 | 拦截率上升，F 继续降 |
| **中** | 红灯先重跑 | 真实问题混在重跑里 |
| **高**（> 半小时） | **红灯不看，直接合** | **测试形同不存在** |

**所以 F 有一个阈值效应**：**一旦超过某个点，测试的 R 会突然归零**（因为没人看结果了），而 C 一分不少。

**这与 §4.1 的"R 只能回看"合起来，得出一条实践结论**：

> **优化 F 的收益，通常大于"多写测试"的收益** —— 因为它保住的是**已有测试的 R**，而不是增加新的 R。

### 一条被忽略的推论：F 不为零的测试是负资产

**"多测一点总没坏处"这句话错在**：它只算了 C 和 R，**把 F 当成了 0**。

**只要 F > 0，一条从不拦截任何问题的测试就是净负债** —— 它每次运行都要占时间，每次失败都要占人的注意力。

**这条推论有一个直接应用**：**"这条测试最近一次拦下真问题是什么时候"** 应当成为一个可以问的问题。**答不上来的，就该考虑删掉。**

## 4.3 金字塔落地：按"该锁什么"排，不按比例排

第 2 章 §2.1 给了分层判据（**反馈成本 × 真实度**）。这一节讲**落地顺序** —— 而它与金字塔图形**恰好相反**。

### 常见做法与它为什么失败

**常见的落地路径**：定一个覆盖率目标 → 从底层开始铺单元测试 → 再补集成 → 最后补 E2E。

**失败机制**：

| 步骤 | 发生什么 |
|---|---|
| 铺单元测试 | 速度快，但**测的都是"已经很清楚"的逻辑** |
| 覆盖率上升 | 数字好看，但**主路径仍然没有任何保护** |
| 某次上线出了主路径故障 | 团队发现"覆盖率没救我们" |
| **信任崩塌** | 之后所有测试投入都被视为"形式主义" |

**根本原因**：**先铺单元测试，等于先做 C 而不先降 F**。而 F 最高的正是 E2E —— **它恰恰是最后才做的那个。**

### 推荐的落地顺序（F 优先）

| 顺序 | 做什么 | 为什么排在这 |
|---|---|---|
| **1** | **类型检查 + Lint**（`D5` 第 1 章） | **C 极低、F 极低、R 高**（能立刻拦一批问题）。这是性价比最高的一步 |
| **2** | **少数关键 E2E**（3–5 条主路径） | **R 最高**（保护"绝不允许坏掉"的路径），且**必须尽早把 F 压下来** |
| **3** | **组件测试**（可访问性 + 交互） | 顺带做无障碍检查（第 2 章 §2.3 的推论），C 低 |
| **4** | **单元测试**（在逻辑复杂处补） | 数量最大，但**不急着铺** —— 它在"逻辑复杂"的地方才划算 |

**⚠️ 第 2 步排在单元测试之前，是本章最反直觉的一条。**

**理由**：**E2E 的 F 最高，而 F 有阈值效应（§4.2）。** 如果先做单元测试，主路径在很长一段时间里**完全无保护**；一旦期间出一次事故，**整个测试投入的正当性就没了**。

**而先做 3–5 条 E2E，能立刻建立"红灯意味着真的坏了"这个前提** —— 之后所有的测试投入都建立在这个前提上。

**这也解释了为什么"从 0 到 1 建测试"总失败**：**它们把最贵的信任建立环节放在了最后。**

### 一个必须接受的代价

**先做 E2E 意味着前期反馈慢**（E2E 本来就慢）。所以第 2 步只做 3–5 条，**且必须先把它们的 F 压到可接受**（固定数据、禁用动画、自动等待、明确的错误信息）。

**如果这 3–5 条 E2E 的 F 压不下来**，那就**不要继续往下走** —— 先把 F 解决掉，否则后面铺的每一层都建在"红灯不可信"的基础上。

### 什么时候该"反向"做（先砍后加）

| 信号 | 动作 |
|---|---|
| 现有套件跑一次 > 30 分钟 | **先删/合并**，不新增 |
| 假红率 > 20%（§4.4） | **先修误报源**，不新增 |
| 绕过率 > 20% | **先改门禁设计**，不新增 |
| 没人记得上次拦下真问题是什么时候 | **先盘点并删除** |

**这四行的共同逻辑**：**在 F 高的状态下增加测试，是在扩大负债规模。**

## 4.4 质量度量：四个可度量的量

`D5.L4.02`。**这一节是"质量文化用机制替代"的落点** —— 不给"要有质量意识"，只给四个能被统计、能被追踪、**且不会奖励刷量**的数。

### 四个指标

| # | 指标 | 定义 | 恶化信号 | 为什么不激励刷量 |
|---|---|---|---|---|
| 1 | **假红率** | 被判定为误报的失败次数 / 总失败次数 | **> 20%** 时红灯开始被忽略 | 它度量**噪声**，做低它只能靠"减少误报" |
| 2 | **信噪比** | 指出真实问题的失败 / 总失败 | **< 30%** 时套件的判断力已失效 | 分子只能靠"发现真问题"增长 |
| 3 | **修复时长**（time-to-green） | 从变红到变绿的中位时间 | **中位数 > 1 天** 说明修不动 | 想缩短只能靠"错误信息更清楚"或"改得更快" |
| 4 | **绕过率** | 绕过门禁的 PR / 总 PR | **> 20%** 说明门禁设计与实践冲突 | 降低它只能靠"让门禁更准"或"给合法窄门" |

### 为什么偏偏是这四个

**它们的共同点**：**度量的都是"机制的健康度"，不是"人的努力程度"。**

| 常见的错误指标 | 为什么它会坏事 |
|---|---|
| **覆盖率排名（按人/组）** | 会激励"写上但不写断言"的测试（第 2 章 §2.3 的 `getBy` 反而更省事） |
| **每人提测数量** | 会激励拆分测试、重复测试 |
| **缺陷数量（按人）** | 会激励**不记录缺陷** |
| **测试运行次数** | 与质量无关 |

**注意第 3 行**：**"缺陷数量"这个指标最危险的地方是它可以被"不记录"直接优化掉**。任何**能被"少记录"优化的指标，都会导致信息失真**。

### 一条元指标：度量工具自己，而不是度量人

**最有价值的一条**：**把"测试基础设施本身的健康度"当指标**。

| 度量对象 | 例子 |
|---|---|
| ✅ **机制** | 假红率、信噪比、修复时长、绕过率、测试总时长、缓存命中率 |
| ❌ **人** | 谁的覆盖率低、谁提的测试少、谁引入的缺陷多 |

**理由**：**度量机制会推动改进机制；度量人会推动改进行为的表象。**

**这也是为什么"质量文化"这个词在这里不需要出现** —— 当假红率是可见的、修复时长是被追踪的、绕过率会被复盘时，**行为自然会变**。而喊"大家要重视质量"不会。

### 指标怎么被看见

| 做法 | 效果 |
|---|---|
| 只写在文档里 | 无人看 |
| 只在季度汇报里出现 | 变成"汇报材料"，与日常决策脱节 |
| **贴在 CI 结果页 / 失败通知里** | **有效** —— 在决策发生的时刻可见 |

**第三行是关键**：**指标必须在"人们要做决定的那一刻"可见。** 一个在季度会上才出现的假红率，不会影响任何人下周的行为。

### 四个指标的一个陷阱

**它们都是"比率"，而比率可以被分母操纵**：

| 指标 | 操纵方式 |
|---|---|
| 假红率 | **减少总失败数**（把测试删掉，失败自然少了） |
| 信噪比 | 同上 |
| 修复时长 | 把慢的测试跳过（不进统计） |
| 绕过率 | 把绕过改成"临时关闭"（不计入绕过） |

**所以四个指标必须一起看，且配套"绝对量"**：

> **假红率下降，但总失败数也骤降 → 不是在减少误报，而是在减少测试。**

**这条与 `D3` 第 3 章"体积小了但功能少了"、`D6` 第 4 章"告警少了但覆盖少了"是同一个陷阱结构**：**比率类指标必须与绝对量配对。**

## 4.5 把"文化"落到四个机制杠杆上

`D5.L4.02`。如果文化不能被度量，那它能被**设计**吗？本章的答案是：**能，通过四个杠杆。**

### 杠杆一：成本的不对称

| 设计 | 塑造的行为 |
|---|---|
| 阈值**收紧**：改个数字即可 | 顺手就收 |
| 阈值**放宽**：需要单独 PR + 写理由 | 会先想清楚 |
| 门禁**添加**：直接加 | 容易膨胀（第 3 章 §3.4 的"阻断项 > 6 会被绕过"） |
| 门禁**删除**：也直接删 | 容易被顺手删掉 ← **需要反向不对称** |

**注意最后一行**：**只让"放宽"变难、不让"删除"变难，会诱导人们用"删掉"代替"放宽"。**

**正确的设计是双向的**：**任何降低保证的动作（放宽阈值、删除门禁、跳过测试）都应该留下理由；任何提高保证的动作应当顺手可做。**

### 杠杆二：失败信息的质量

| 红灯信息 | 效果 |
|---|---|
| `Expected true to be false` | **无法行动**，F 高 |
| `Expected element [data-testid=submit] to be visible, but it was covered by [class=loading-mask]` | **直接指向原因**，F 低 |

**这是最低成本的 F 优化手段**，也是最被忽略的 —— 因为它**不在"写测试"的任务里**，而在"把测试写好"的任务里。

**一条可执行的要求**：**每一条 E2E 的失败信息，都应当能让人在不看源码的情况下说出"哪里坏了"。** 做不到就改断言方式（第 2 章 §2.3 的 `findBy` vs `waitFor`、第 3 章 §3.1 的"逐文件覆盖率才可行动"是同一个逻辑）。

### 杠杆三：例外通道的留痕

第 3 章 §3.4 讲过"没有例外通道会被更糟的方式绕过"。这里补**留痕**这一层：

| 设计 | 后果 |
|---|---|
| 无例外通道 | 被用改阈值、拆 PR、跳过钩子绕过（**不留痕**） |
| 有通道，不留痕 | 例外数量无法统计 → **绕过率指标失效**（§4.4） |
| **有通道 + 强制留痕** | **绕过率可统计 → 成为可改进的指标** |

**第三行是"文化"能被度量的前提** —— **不是靠自觉，是靠"绕过这个动作必须留下一条记录"。**

### 杠杆四：谁能改

**这一节是"权限"轴**；"改动有多难"那一轴在 `D5` 第 3 章 §3.4（收紧顺手、放宽要理由）。**两轴必须一起设**，只设一个都会漏。

| 谁能改阈值 | 长期结果 |
|---|---|
| 任何人 | 阈值 = 当前状态 |
| 只有负责人 | 阈值僵化（负责人成为瓶颈） |
| **谁都能提，但需一位非作者的评审** | **最稳** —— 成本低、有第二双眼睛 |

**第三行值得展开**：它避免了"任何人"与"只有负责人"两个极端。**它的核心不是权限，而是"改动必须经过一个不为此事着急的人"。**

**两轴组合起来才是完整设计**：

| | 难度轴不管（谁改都行） | 难度轴管住（放宽要理由） |
|---|---|---|
| **权限轴不管（只有负责人能改）** | 负责人一人松动即可 → 门禁失效 | 有摩擦但瓶颈在一个人 → 会绕开流程 |
| **权限轴管住（谁都能提 + 非作者评审）** | 提议成本低、评审不设难度 → 阈值缓慢下滑 | **两条都成立**：提议通道畅通，降标准必留痕 |

### 一条反例：为什么"质量月"不起作用

| 做法 | 起作用的部分 | 不起作用的部分 |
|---|---|---|
| 质量月 / 质量之星 | **短期注意力** | **没有改变任何默认值** |
| 质量宣讲 | 共识 | 与日常决策无关 |

**失效机制很精确**：**它们改变的是"注意力"，而注意力会衰减；它们没有改变"默认值"，而默认值会一直生效。**

**对照四个杠杆**：**改一个默认值（如"阈值放宽需评审"）的效果，超过办十场宣讲。** 因为默认值**每天生效**，宣讲**一年一次**。

## 4.6 治理动作：六个判定阈值

| # | 现象 | 判定阈值（起点值） | 动作 | 依据 |
|---|---|---|---|---|
| 1 | 频繁说"先重跑一次" | **单条测试月误报 ≥ 2 次** | 它已是负资产（C > 0、R = 0、F 持续发生）→ 修或删 | §4.2 |
| 2 | 红灯被直接合掉 | **假红率 > 20%** | **停止新增测试**，先修误报源 | §4.4 |
| 3 | 套件跑一次很久但没人抱怨 | **总时长 > 30 分钟且无人在意** | 说明结果已不被使用 —— 查信噪比 | §4.3 |
| 4 | 覆盖率在涨但事故没少 | **两次事故都发生在覆盖率 100% 的路径附近** | 分两步查：**先查口径**（`coverage.include` 默认只统计"被导入过的文件"，见第 3 章 §3.1），**再数无断言的测试** —— 后者计入覆盖但不构成保护 | §4.1 |
| 5 | 门禁频繁被绕过 | **绕过率 > 20%** | 按第 3 章 §3.4 的**四条准入判据**重设该门禁（可判定 / 低假阳性 / 可行动 / 够快）；**加纪律通报无效** —— 绕过是设计冲突的症状 | §4.4 |
| 6 | 从 0 建测试总失败 | **3 个月内重启过 ≥ 2 次** | 落地顺序错了 —— 按 §4.3 的 F 优先顺序重来 | §4.3 |

### 三条使用说明

**① 阈值 1 与 2 都指向"F 已经过高"。**

在这个状态下，**任何新增测试都是扩大负债**。**先降 F，再加量。**

**② 阈值 4 的表述值得注意。**

它不是说"覆盖率没用"，而是说**覆盖率与事故的关系断了** —— 而断了的原因通常是**口径不对**（分母不含未导入文件）或**测试无断言**。**这两种情况的数字都"真的"很高。**

**③ 阈值 6 是最贵的一条。**

**"从 0 建测试"失败两次以上，通常不是团队不努力，而是顺序错了。** 而顺序错误的代价是**信任** —— 它比时间难恢复得多。

## 4.7 动手

| 任务 | 验收 |
|---|---|
| 抽 10 条测试，逐条估 C / R / F | 说出哪几条的 R 是 0（从没拦下过真问题） |
| 计时一次"从看到红到得出结论" | 给出你自己的 F 中位数（分钟） |
| 把 F 折算成月度人时 | 说出这个数是否在你的项目预算里（大概率不在） |
| 查一次"最近一次拦下真问题的测试"是哪条 | 若答不上来，说出这说明什么 |
| 统计你团队的假红率 | 若 > 20%，说出该先做什么（不是"多写测试"） |
| 统计绕过率 | 若 > 20%，说出是门禁设计问题还是纪律问题 |
| 看一眼你 CI 的失败信息 | 挑一条最差的，说出"不看源码能判断出原因吗" |
| 查一次"放宽阈值"要不要评审 | 若不用，说出这会怎样改变行为 |
| 列出你团队的四个指标是否可见 | 若只在汇报里出现，说出该贴在哪里 |
| 复盘一次"从 0 建测试"的经历 | 说出当时是先铺单元还是先做主路径 |

**进阶挑战**（任选一项）：

1. **做一次"测试盘点与删减"**：按 §4.2 的判据找出负资产（R = 0 且 F > 0），删掉或修好。目标：**总时长下降，而拦截能力不降**。
2. **把四个指标接进 CI 结果页**：假红率、信噪比、修复时长、绕过率。要求**与绝对量配对展示**（§4.4 的陷阱）。
3. **按 §4.3 的顺序重做一个模块的测试**：先类型+Lint，再 3 条主路径 E2E，再组件测试，最后补单元。记录每一步之后"红灯的可信度"变化。

## 4.8 本章常见误区

| # | 误区 | 纠正 |
|---|---|---|
| 1 | "ROI 可以算出来" | 三个量都只能估，**写成公式会伪装成精确**。它只适合比较两条候选测试的相对价值 |
| 2 | "新写的测试可以先评估 ROI" | **写之前无法用 ROI 回答**。只能用"它锁定的东西会不会意外变化"这个弱判据 |
| 3 | "维护成本 ≈ 改代码时顺手改测试" | **维护成本会因你没改任何代码而增长**（第三方变了、接口变了、证书过期） |
| 4 | "F（失败归因成本）不是成本" | 它**不在任何预算里**，所以被系统性忽略。但 100 次误报 ≈ 25 人时/月 |
| 5 | "误报多了就重跑，不影响" | **重跑会掩盖真实的不稳定**，而真实缺陷在上线后暴露 —— **F 是正反馈，会自我放大** |
| 6 | "优化速度最重要" | **优化 F 的收益通常更大** —— 它保住的是已有测试的 R |
| 7 | "建测试要从底层铺起" | **落地顺序与金字塔图形相反**：类型+Lint → 少数关键 E2E → 组件 → 单元。**因为必须先降 F** |
| 8 | "先铺单元测试最稳妥" | 主路径长期无保护；一旦期间出事故，**整个测试投入的正当性就没了** |
| 9 | "E2E 最慢，应该最后做" | **它 F 最高，必须尽早做 3–5 条**并把 F 压到可接受。压不下来就别往下走 |
| 10 | "覆盖率该按人排名" | 会激励"写上但不写断言"的测试。**度量机制，不要度量人** |
| 11 | "质量文化就是大家要有质量意识" | 这句话不可执行。**用四个可度量的机制指标替代**（假红率 / 信噪比 / 修复时长 / 绕过率） |
| 12 | "假红率降了就说明好了" | 比率可被分母操纵（**把测试删掉，失败自然少了**）。必须与**绝对量配对**看 |
| 13 | "例外通道会削弱门禁" | **没有通道会被用更糟的方式绕过**（不留痕）。要求是"留痕"，不是"禁止" |
| 14 | "失败信息不重要，看日志就行" | 日志质量**直接决定 F**。要求：不看源码能说出"哪里坏了" |
| 15 | "阈值只能由负责人改" | 会变成瓶颈。**谁都能提，但需一位非作者的评审** |
| 16 | "指标写在文档里大家会看" | **必须在决策发生的时刻可见**（CI 结果页、失败通知），否则与日常行为无关 |

## 4.9 D5 领域收束

D5 四章讲的是**一件完整的事**：

| 章 | 回答的问题 | 核心机制 |
|---|---|---|
| **第 1 章** | 有哪些检查？ | **三类检查的分工**：类型 / Lint / 格式，各自能发现什么、不能发现什么 |
| **第 2 章** | 怎么测？ | **分层依据是"反馈成本 × 真实度"**；工具默认值就是 bug 来源 |
| **第 3 章** | 测多少、卡哪、跑多快？ | **口径决定数字含义**；"只跑受影响的"是漏测机制；并行有结构性上限 |
| **第 4 章** | 值不值？怎么判断做得对？ | **F（失败归因成本）是最被忽略的量**；用机制指标替代"质量文化" |

### 一条贯穿四章的主线

**四章反复出现的都是同一个机制**：

> **一个不可信的红灯，会训练出"不看红灯"的行为；而一旦不看，所有的投入都归零。**

| 章 | 它的表现 |
|---|---|
| 第 1 章 | Lint 警告太多 → 加 `--max-warnings` 或干脆忽略 |
| 第 2 章 | 测内部 state → 重构就假红 |
| 第 3 章 | 门禁设成"警告" → 等于不卡 |
| 第 4 章 | F 超过阈值 → R 归零 |

**所以 D5 全领域的判据可以压成一句话**：

> **先让红灯可信，再让红灯变多。**

**顺序反了，就会得到一个"跑得很慢、谁都不看"的套件。**

### D5 与相邻领域的分界

| 领域 | 它负责的部分 |
|---|---|
| **D5（本领域）** | 检查与测试的**设计与度量** |
| **D6** | 流水线**结构**（这些检查卡在哪一步、怎么并行、制品怎么传） |
| **D3** | 构建**本身**（测试与构建共享同一套转换/配置，见第 2 章 §2.2） |
| **D2** | 类型系统的**原理**（第 1 章只讲"怎么当门禁"，不重复类型系统） |
| **D8** | **线上**可观测性（D5 管"上线前拦"，D8 管"上线后发现"） |
