## 2.1 同构不是「同一份代码跑两遍」

`X2.L3.01`。这个说法流传很广，但它**掩盖了真正的难点**。

### 实际发生的是什么

```
服务器：组件 → HTML 字符串        （这一份被发出去了）
        ↓
浏览器：拿到 HTML → 立刻可见       （还不可交互）
        ↓
浏览器：下载 JS → hydrateRoot     （接管已有 DOM，挂上事件）
```

**React 官方对 `hydrateRoot` 的定义**：

> 让你把 React 组件显示在**一个浏览器 DOM 节点里，而那个节点的 HTML 内容此前是由 `react-dom/server` 生成的**。

**⭐ 关键在"接管"这个词**：**hydration 不重新生成 DOM，它是在已有的 DOM 上挂事件、恢复状态。**

**所以它不是"跑两遍"**，而是**"算一遍、然后再认一遍"**。而"认"的过程有一个硬要求。

### 官方那句最该记住的话

> **`hydrateRoot()` 期望渲染出的内容与服务器渲染的内容完全一致。你应当把不匹配当作 bug 并修复它们。**

**"当作 bug 并修复"** —— 这五个字说明定位：**mismatch 不是"可以容忍的警告"，是缺陷。**

### 为什么"完全一致"这么难

**因为两端的输入天然不同**：

| 输入 | 服务端 | 客户端 |
|---|---|---|
| 当前时间 | 服务器时间 | 用户本地时间 |
| 随机数 | 服务端的 | 客户端的（不同） |
| 窗口尺寸 / 媒体查询 | **不存在** | 存在且各不相同 |
| 存储（localStorage） | **不存在** | 存在 |
| 数据 | 由 loader 取 | 可能后来变了 |

**⭐ 所以同构的本质是一条约束**：

> **两侧的「输入」几乎必然不同，但「输出」必须相同。**

**这不是框架能替你保证的事** —— 它是**代码必须满足的条件**。而下面两节，就是这条条件被违反时的两种典型形态。

## 2.2 `window` 未定义：它为什么必然发生

`X2.L3.01`。"`window` is not defined" 这个报错在同构项目里几乎人人遇到过，但它的**成因比"忘了加判断"更深**。

### 机制：不是"配置问题"，是"求值时机"问题

**服务端没有 DOM。** 所以 `window`、`document`、`localStorage`、`matchMedia` **在服务端根本不存在**（不是空值，是**未定义**）。

**而一段代码会不会报错，只取决于一件事**：

> **服务端会不会执行到这一行？**

**同一个 API，放在不同位置，后果完全不同**：

| 位置 | 服务端会执行吗 | 后果 |
|---|---|---|
| **模块顶层**（`const w = window.innerWidth`） | **会**（`import` 时求值） | **整个模块加载失败** → 可能整页 500 |
| **组件函数体内** | **会**（渲染时执行） | **SSR 时报错** |
| **`useEffect` 内** | **不会** | 安全 |
| **事件处理器内** | **不会** | 安全 |

**⭐ 第一行是最难查的**：**模块顶层的报错发生在 `import` 时，而不是在"用到这个组件"时。** 所以症状常常是"我根本没渲染这个组件，为什么报错" —— 因为**有人 import 了它**。

**这与 `D3` 第 4 章 §4.2 的"依赖图是从入口可达的子图"是同一个机制**：**只要被可达，模块体就会被求值。**

### 一条判据

**遇到 `window is not defined`，先问这一个问题**：

> **这行代码在服务端会被执行到吗？**

**答案"会" → 它必须挪位置，而不是加判断。**

### 修法的优先级

| 序 | 修法 | 代价 | 适用 |
|---|---|---|---|
| **1** | **挪到 `useEffect` 或事件处理器** | 需要一次额外渲染 | 绝大多数情况 |
| **2** | **挪到 `loader`**（第 1 章 §1.5） | 需要服务端能提供这份数据 | 数据类需求 |
| **3** | **两阶段渲染** | **渲染两次、hydration 变慢**（§2.3） | 无法避免"首屏必须不同"时 |
| **4** | ~~用 `typeof window !== 'undefined'` 包住渲染逻辑~~ | **这条路是错的** | 见下 |

**⭐ 第 4 行必须单独说**：**`typeof window` 判断在"阻止执行"上是有效的，但在"渲染逻辑里"它本身就是 mismatch 成因。**

**官方把这一条直接列进了 mismatch 的成因清单**：

> **在渲染逻辑中使用 `typeof window !== 'undefined'` 这类判断。**

**为什么**：因为**服务端会走到 `if` 的 false 分支、客户端会走到 true 分支** —— **两端渲染出不同的东西，正是 mismatch 的定义**。

**所以`typeof window` 的正确用法只有一个**：**在 `useEffect` / 事件处理器里做"这段逻辑只在客户端跑"的保护**（那时它不参与渲染输出）。**一旦它影响了"渲染出什么"，它就是错的。**

**这条区分很干净**：

| 用法 | 影响渲染输出吗 | 对错 |
|---|---|---|
| `useEffect(() => { if (typeof window === 'undefined') return; ... })` | 否 | ✅ |
| `return <div>{typeof window !== 'undefined' && <X/>}</div>` | **是** | ❌ **直接造成 mismatch** |

## 2.3 hydration 不匹配：官方的四项成因

`X2.L3.01`。这一节的骨架来自 React 官方，**而它顺带纠正了两个流传很广的说法**。

### 四项成因（官方原文）

| # | 成因（官方表述） |
|---|---|
| 1 | **React 生成的 HTML 在根节点内的多余空白**（如换行） |
| 2 | **在渲染逻辑中使用 `typeof window !== 'undefined'` 这类判断** |
| 3 | **在渲染逻辑中使用浏览器专属 API**（官方举例 `window.matchMedia`） |
| 4 | **在服务端与客户端渲染了不同的数据** |

**⭐ 第 1 条是最"低成本"的一条**：**一个换行就能造成 mismatch**。而它极难靠读代码发现 —— 只能靠工具或警告。

**⚠️ 一处必须如实标注**：**官方这一页没有提"随机数"**。它提了**时间戳**（但那个例子出现在 `suppressHydrationWarning` 的用法里，不是成因清单里），成因清单里写的是更宽的"**两端渲染了不同的数据**"。

**所以"随机数会导致 mismatch"这条本章不挂在官方名下** —— 它属于第 4 条成因的**一个具体实例**，`Math.random` 在两端确实不同，但**官方没这么举例**。

### ⭐ 纠偏一：“mismatch 会自动降级成 CSR”站不住

这是流传最广的一条说法，而**官方该页没有这个表述**。

官方实际说的三层：

| 官方原话 | 含义 |
|---|---|
| "**开发模式下** React 会警告 mismatch" | **只在开发模式** |
| "**不保证**属性差异会被修补" —— 理由是性能（"在多数应用里 mismatch 很少见，所以验证全部标记的代价过高"） | **不修补** |
| "React **能从部分 hydration 错误中恢复**，但你必须像修其他 bug 一样修它们。**最好的情况是变慢；最坏的情况是事件处理器被挂到错误的元素上**" | 部分恢复，**但后果可以很严重** |

**⭐ 第三行才是重点**：**最坏后果不是"闪一下"，而是"事件处理器绑错元素"** —— 那是**交互错乱**，用户点了 A 却触发 B。

**唯一明确会"整根切到客户端渲染"的条件**（官方）：

> **如果你在 root 完成 hydration 之前调用 `root.render`，React 会清空已有的服务端渲染 HTML 内容，并把整个 root 切换为客户端渲染。**

**注意这是"你主动调了 `root.render`"，不是"React 检测到 mismatch 后自动降级"。**

**所以修正后的说法应当是**：

> **mismatch 通常不降级，而是"带着不一致继续跑"** —— 而它的后果不保证被修补。

### 纠偏二：`suppressHydrationWarning` 不是万能开关

官方给了**三层限制**：

| 限制 | 官方原文 |
|---|---|
| **仅生效一层深度** | "这**只向下生效一层**" |
| 定位是逃生舱 | "它是**逃生舱**。**不要滥用**" |
| **不修补文本** | "React **不会**尝试修补不匹配的文本内容" |

**⭐ 第三条是关键**：**它只"消音"，不"修正"。** 所以加了之后，**服务端渲染的文本会保留在页面上**，客户端不覆盖它。

**这带来一个判定**：**如果你需要的是"显示客户端的时间"，`suppressHydrationWarning` 给你的是"显示服务端的时间且不报警"** —— **这两件事完全不同。**

### 三种规避手段，代价差一个量级

| 手段 | 官方定位 | 代价 |
|---|---|---|
| **两阶段渲染**（`isClient` + `useEffect`） | **官方给出标准写法** | **渲染两次**（见下） |
| **`suppressHydrationWarning`** | 逃生舱，一层深 | **不修补**，只消音 |
| **`use(browser())`** | 官方一句话提及 | 该页**未展开** |

**⭐ 两阶段渲染的官方 PITFALL 值得完整引用**：

> 这种做法会让 **hydration 变慢，因为你的组件必须渲染两次**。请注意慢速连接下的用户体验。JS 代码可能显著晚于初始 HTML 渲染到达，**所以 hydration 后立刻渲染出不同的 UI 也可能让用户感觉割裂**。

**这段话说明**：**两阶段渲染不是免费的"安全写法"** —— 它把"mismatch 的 bug"换成了"**确定的性能成本 + 确定的视觉割裂**"。

**所以它是一个取舍，不是一个改进。** 这与 `D4` 第 2 章 §2.3 的"1px 问题的三种应对各有代价"是同一种思维方式：**先问要什么，再选实现。**

**⚠️ 一处如实标注**：**`useSyncExternalStore` 在官方该页完全未被提及**。它是 React 核心 Hooks 的 API，**本章不把它列为"官方给出的 mismatch 规避手段"**。

## 2.4 部署形态：它决定了你能不能用 ISR

`X2.L4.02`。**部署形态不是"运维选择"，它对渲染能力有硬约束。**

### 官方支持表

| 部署形态 | 支持 |
|---|---|
| **Node.js server** | ✅ |
| **Docker container** | ✅ |
| **Static export** | ❌ **不支持** |
| **Adapters** | **平台特定** |

**这张表看起来只是"能不能用"，但它其实画出了一条链**：

```
部署形态 → 有没有常驻服务端进程 → 能不能跑服务端逻辑 → 能不能用 SSR / ISR
```

**⭐ 第三行是最容易忽略的**：**"静态导出"这个选项看起来只是"导出成文件"，实际上它等于放弃了 SSR 与 ISR 的**全部**能力。**

**而它恰好是最省事、最便宜的部署方式** —— 所以这是一个真的取舍，不是"选错了"。

**⚠️ 第四行值得单独看**：**Adapters 的能力是"平台特定"的** —— 意思是**"能不能用 ISR"不由框架决定，而由你部署到哪个平台决定**。**所以查"某框架支持 ISR 吗"这个问法本身不准确**，应当问"**在这个平台上**支持吗"。

## 2.5 缓存架构：`cacheHandler` 是那个可替换点

`X2.L4.02`。上一章说明了 ISR 的语义，这一节说明**它的缓存在多实例下会怎样**。

### 默认缓存住在哪里

Next.js 支持**自定义缓存处理器 `cacheHandler`**（官方标注 **v14.1.0 起稳定**），官方描述它的用途包括：

> 可**持久化到 durable storage**、**跨容器 / 多实例共享**。

**⭐ 这句话反过来读，才是它真正的信息量**：

> **默认缓存在进程内。** 所以**多实例部署时，每个实例各有各的缓存。**

**后果可以直接推出来**：

| 实例数 | 一个页面的 ISR 缓存有几份 |
|---|---|
| 1 | 1 份 |
| **N** | **N 份**（各自独立再生） |

**这就是为什么"，我用了 ISR，但不同请求拿到的内容不一样"是一个真实现象** —— **你的请求被负载均衡分到了不同实例，而它们的缓存不同步。**

**这与 `D4` 第 3 章 §3.2 的"主题按组合生成 N 份 CSS"是同一个结构错误**：**本该共享的东西被复制成了 N 份**，而**你不会收到任何报错**。

### 一条判据

> **你的实例数 > 1 吗？**

| 答案 | 该做什么 |
|---|---|
| **1**（单实例 / 本地） | 默认缓存够用 |
| **> 1** | **必须换成共享缓存**，否则 ISR 的"同一份"语义不成立 |

**而这条判据有一个前置问题**：**"并发会不会同时再生同一页"**。多实例下，**多个实例可能同时判断"这页过期了"** → 各自触发一次再生。**共享缓存 + 单飞（single-flight）才是完整答案**，而**官方该页未展开单飞机制**（本章据此不展开）。

### 调试手段（官方提到）

| 手段 | 用途 |
|---|---|
| `logging.fetches.fullUrl` | 记录完整 URL，便于对应到具体页面 |
| **环境变量 `NEXT_PRIVATE_DEBUG_CACHE=1`** | 观察 **ISR cache hits and misses** |

**⭐ 第二个是本章唯一的"官方给的观测入口"**：**它输出的是命中/未命中，不是命中率。** 这与 `D6` 第 5 章 §5.3 的结论完全一致 —— **平台给你的是单次信号，聚合指标要自己算。**

**⚠️ 一处如实标注**：本章**不展开自建 CDN 缓存规则**（已定的边界），所以"ISR 的响应头怎么被 CDN 消费"这一侧本章不给断言。相关机制在 `D6` 第 3 章（已写）。

## 2.6 治理动作：六个判定阈值

| # | 现象 | 判定阈值（起点值） | 动作 | 依据 |
|---|---|---|---|---|
| 1 | "没渲染这个组件，却报 `window` 未定义" | **报错发生在 `import` 时** | 查**模块顶层**的浏览器 API 调用；模块体只要被可达就会求值 | §2.2 |
| 2 | 加了 `typeof window` 判断后出现 hydration 警告 | **该判断影响了渲染输出** | 它只能用在 `useEffect` / 事件处理器里；**在渲染逻辑里它就是官方列的 mismatch 成因** | §2.2 |
| 3 | 等 mismatch "自动降级成 CSR" | **没有这个自动行为** | 官方只承诺"从部分错误中恢复"，**不保证修补**；最坏是**事件处理器挂错元素** | §2.3 |
| 4 | 用 `suppressHydrationWarning` 解决时间显示 | **期望"显示客户端时间"** | 它**只消音、不修补** → 页面上保留的是**服务端**文本 | §2.3 |
| 5 | 上 `suppressHydrationWarning` 后子元素仍警告 | **生效仅一层深度** | 需要逐层加，或改用两阶段渲染 | §2.3 |
| 6 | 用了 ISR，但不同请求内容不一致 | **实例数 > 1** | 默认缓存**在进程内** → 必须换共享缓存（`cacheHandler`） | §2.5 |

### 三条使用说明

**① 阈值 1 与 6 都是"归因错位"类。**

一个看起来像"组件问题"（其实是模块加载），一个看起来像"缓存不生效"（其实是缓存有 N 份）。**它们的症状都指向错误的方向。**

**② 阈值 3 的处置原则是"别赌"。**

既然官方不保证修补，**把它当成"必须修的 bug"是唯一安全的选择**。**指望"反正会降级"是在依赖一个不存在的保证。**

**③ 阈值 6 的排查顺序不能乱。**

先确认实例数，再查缓存实现。**反过来会花很长时间去调一个本来就正确的 ISR 配置。**

### 什么时候"不该上 SSR"

| 情况 | 为什么 |
|---|---|
| **首屏不需要 SEO / 不需要"立刻可见"** | SSR 的收益是新鲜度（第 1 章 §1.1），无收益 |
| **组件严重依赖客户端 API** | 会引出大量两阶段渲染与 mismatch |
| **实例数多但没能力做共享缓存** | ISR 语义会不成立（§2.5） |
| **团队没有定位 mismatch 的手段** | 那类问题在出问题后很难查 |

## 2.7 动手

| 任务 | 验收 |
|---|---|
| 全局搜一次 `window.` / `document.` / `localStorage` | 按"模块顶层 / 组件体 / effect / 事件"分类，标出必炸的那几个 |
| 挑一个"没渲染却报错"的案例 | 说出它是模块顶层求值导致的 |
| 搜一次渲染逻辑里的 `typeof window` | 逐个判断它是否影响了渲染输出 |
| 故意制造一次 mismatch（渲染里加 `Date.now()`） | 记录：开发模式会警告吗？会降级吗？ |
| 查一次有没有用 `suppressHydrationWarning` | 说出页面上最终显示的是服务端还是客户端的文本 |
| 查一次你的实例数 | 若是 1，说出扩到 2 之后 ISR 会怎样 |
| 查一次是否用了 `cacheHandler` | 若没有且实例数 > 1，说出缓存有几份 |
| 打开一次 `NEXT_PRIVATE_DEBUG_CACHE=1` | 观察输出的命中/未命中，说出它能不能直接当命中率 |
| 查一次部署形态 | 若是 static export，说出你放弃了哪些渲染能力 |

**进阶挑战**（任选一项）：

1. **做一次同构审计**：把项目里所有浏览器 API 调用按 §2.2 的四类位置分类，给出"必炸 / 有条件 / 安全"三档，并修掉"必炸"的。
2. **量化两阶段渲染的代价**：对一个用 `isClient` 的组件，测量 hydration 前后各渲染几次、hydration 耗时增加多少。目标是**为这个取舍给出你自己的数字**。

## 2.8 本章常见误区

| # | 误区 | 纠正 |
|---|---|---|
| 1 | "hydration 是重新渲染一遍" | 它**不重新生成 DOM**，是在已有 DOM 上挂事件、恢复状态 |
| 2 | "mismatch 只是个警告，不影响功能" | 官方：**"应当把不匹配当作 bug 并修复"**；最坏后果是**事件处理器被挂到错误的元素上** |
| 3 | "两端输入不同，输出自然会不同，没办法" | 输入不同是常态，但**输出必须相同** —— 这是代码要满足的**约束**，不是框架保证 |
| 4 | "我根本没渲染这个组件，为什么报错" | 报错发生在**模块顶层求值（import）时** —— 只要被可达，模块体就会执行 |
| 5 | "加个 `typeof window` 判断就安全了" | 在 `useEffect` / 事件处理器里**安全**；**在渲染逻辑里它就是官方列的 mismatch 成因** |
| 6 | "渲染里用 `typeof window` 至少不会报错" | 不报错，但**两端渲染出不同内容 = mismatch**。它把"崩溃"换成了"不一致" |
| 7 | "降级后至少能正常显示" | 唯一明确的整根降级条件是**你在 hydration 完成前调了 `root.render`** —— 那是你主动做的 |
| 8 | "mismatch 的成因主要是时间与随机数" | **官方四项成因**：多余空白 / `typeof window` 判断 / 浏览器专属 API / 两端数据不同。**官方该页没提随机数** |
| 9 | "一个换行不会造成问题" | **它就是官方四项成因的第一条** —— 根节点内多余空白 |
| 10 | "给父元素加上就够" | 它**仅向下生效一层**，不含子树 |
| 11 | "这是正式方案，可以放心用" | 官方定位是 **escape hatch**，"不要滥用" |
| 12 | "两阶段渲染是无代价的安全写法" | 官方 PITFALL：**组件必须渲染两次、hydration 变慢**；且"hydration 后立刻渲染不同 UI 会让用户感觉割裂" |
| 13 | "`useSyncExternalStore` 是官方推荐的规避手段" | **官方该页完全未提及**。本章不把它列为官方方案 |
| 14 | "`use(browser())` 有完整文档" | 官方只**一句话提及**，该页**未展开** |
| 15 | "某框架支持 ISR" 这种问法 | **Adapters 的能力是"平台特定"的** → 应当问"**在这个平台上**支持吗" |
| 16 | "ISR 的缓存在 CDN 里" | 默认缓存在**进程内**。所以**多实例 = 多份缓存** |
| 17 | "用了 ISR，同一页面的内容应当处处一致" | **实例数 > 1 且未换共享缓存时不会一致** —— 请求被分到不同实例，缓存不同步 |
| 18 | "缓存不一致会报错" | **不会**。它和 `D4` 的"主题 N 份 CSS"是同一个结构错误：**该共享的被复制了，且无报错** |
| 19 | "`cacheHandler` 只是个高级选项" | 它是**多实例部署的必需项** —— 否则 ISR 的"同一份"语义不成立 |
| 20 | "`NEXT_PRIVATE_DEBUG_CACHE` 能给出命中率" | 它给的是**命中和未命中的事件**，**不是聚合指标**（与 `D6` §4.10 的结论一致） |
| 21 | "多实例同时再生同一页没关系" | 会**重复再生**。完整答案需要共享缓存 + 单飞，而**官方该页未展开单飞**（本章不展开） |

> - **React 19.3 · `hydrateRoot`**：定义是"把组件显示在**HTML 此前由 `react-dom/server` 生成**的 DOM 节点里"；**"期望渲染内容与服务器渲染内容完全一致。你应当把不匹配当作 bug 并修复"**；**开发模式下会警告 mismatch**；**不保证修补属性差异**（理由：验证全部标记的性能代价过高）；**"能从部分 hydration 错误中恢复，但必须修；最好情况是变慢，最坏情况是事件处理器被挂到错误的元素上"**；**唯一明确的整根降级条件**是"在 root 完成 hydration 之前调用 `root.render`"；**四项成因**（根节点内多余空白 / `typeof window !== 'undefined'` 判断 / 浏览器专属 API 如 `window.matchMedia` / 两端渲染不同数据）；**`suppressHydrationWarning` 仅生效一层深度、是 escape hatch、不修补文本**；**两阶段渲染**（`isClient` + `useEffect`）有官方 PITFALL（**渲染两次、hydration 变慢、视觉割裂**）；另提到 **`use(browser())`**（未展开）。
