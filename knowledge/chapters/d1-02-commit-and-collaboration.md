> **本章定位**：D1 领域第 2 章。第 1 章解决了"代码写出来就被拦住"，本章解决**"变更怎么进入仓库、怎么被别人接受"**。深度标准同上：讲清 Git 钩子的精确语义、规范的可判定条款、以及每一种机制**在什么条件下失效**。本章回链闭合第 1 章 §1.9 留下的那处前向引用。

## 2.1 提交信息是接口，不是备注

第 1 章结束在一条结论上：门禁的位置决定它的代价与强制力。本章处理的是**另一类门禁** —— 它不是检查代码长什么样，而是检查**变更怎么被描述、怎么被接受**。

要先建立的是这件事的性质：**提交信息是"写一次、被多个工具读多次"的接口。**

| 读它的东西 | 用途 |
|---|---|
| 校验工具（commitlint） | 不合规就拒绝提交 |
| CHANGELOG 生成器 | 从 git 元数据聚合出发布说明 |
| 版本号推导 | `fix` → PATCH、`feat` → MINOR、破坏性变更 → MAJOR |
| 人（未来的同事、三个月后的自己） | 定位某一行代码是为什么改的 |

**一旦有工具在读，格式就从"风格"变成了"契约"。** 这是本章与第 1 章的分界：第 1 章的规范约束**代码本身**，本章的规范约束**关于代码的元数据** —— 而元数据一旦错，影响面比代码更大：它污染的是版本号与发布说明。

## 2.2 Git 钩子的精确语义：四个位置，四种能力

第 1 章 §1.9 讲了 Husky 与 lint-staged，但把钩子本身当成了黑盒。这一节补上底座 —— 因为**钩子能做什么、不能做什么，全由它的参数与执行时机决定**。

以下均为 Git 官方文档（`git-scm.com/docs/githooks`，核验时页面标注 `last updated in 2.54.0`，2.54.0 日期为 2026-04-20）的原文表述。

### `pre-commit`：拿不到提交信息

> 该钩子由 `git commit` 调用，**可被 `--no-verify` 选项绕过**。它**不接受任何参数**，在**获取拟用的提交日志信息之前**、以及创建提交之前被调用。从该脚本以非零状态退出，会导致 `git commit` 在创建提交之前中止。

三个要点：

1. **无参数** —— 它拿不到任何上下文，只能靠自己去查（`git diff --cached` 之类）。
2. **时机在"获取提交信息之前"** —— 这一句是理解 §2.4 的关键。
3. **可被 `--no-verify` 绕过。**

### `prepare-commit-msg`：一个特殊的例外

> 该钩子由 `git commit` 在**准备好默认日志信息之后、编辑器启动之前**调用。它接受一至三个参数……若退出状态非零，`git commit` 会中止。该钩子的用途是就地编辑消息文件，且**它不会被 `--no-verify` 选项抑制**。

**"不受 `--no-verify` 抑制"是全书唯一一处这样的钩子。** 它的定位是"帮你生成/整理默认提交信息"，不是门禁 —— 所以 Git 没有给它 `--no-verify` 这个逃生口。

### `commit-msg`：拿得到消息文件，且可以改它

> 该钩子由 `git commit` 与 `git merge` 调用，**可被 `--no-verify` 选项绕过**。它接受**一个参数**：保存拟用提交日志信息的**文件名**。以非零状态退出会导致命令中止。
>
> 该钩子**被允许就地编辑该消息文件**，可用于把消息规范化为某种项目标准格式。也可以在检查消息文件之后**拒绝这次提交**。

这一条给出了**两个能力**：既能读（校验），也能写（规范化）。第 1 章 §1.9 里 commitlint 用的 `--edit $1` 中的 `$1`，就是这个消息文件的路径。

### `pre-push`：参数是远端，待推内容走 stdin

> 该钩子由 `git push` 调用，可用于阻止推送发生。钩子被调用时带**两个参数**，提供目标远端的名称与位置（若未使用命名远端，两个值相同）。
>
> 待推送内容通过钩子的**标准输入**提供，每行格式为 `<local-ref> SP <local-object-name> SP <remote-ref> SP <remote-object-name> LF`……若该钩子以非零状态退出，`git push` 会中止且不推送任何内容。

它的形状与前两个不同：**参数给的是"推到哪"，stdin 给的是"推什么"**。所以"在 pre-push 里跑全量测试"是可行的（能拿到待推送的 ref 范围），代价是每次推送都要等。

### 钩子目录与一个容易被忽略的限制

官方对目录位置与执行条件的规定：

> 钩子是可以放在钩子目录里、在 git 执行的特定时点触发动作的程序。**没有设置执行位（executable bit）的钩子会被忽略。**
>
> 默认的钩子目录是 `$GIT_DIR/hooks`，但可以通过 `core.hooksPath` 配置变量改变它。

**"没有执行位会被忽略"是一个静默失败** —— 脚本写对了、文件名对了，但 `chmod +x` 忘了，Git 什么都不说就跳过了。这类问题在跨操作系统协作时尤其常见（Windows 上克隆下来的文件可能没有执行位）。

### 关键的一条：钩子不随 clone 分发

官方文档里**没有**"clone 会分发钩子"的表述。它给出的传播路径是另一回事：

> `git init` **可能**把钩子复制到新仓库，取决于其配置。详见 git-init 的「TEMPLATE DIRECTORY」一节。本文档后文提到「默认钩子」时，指的是 Git 随发行版附带的**默认模板**。

**这条把第 1 章 §1.9 的结论补全了。** 第 1 章说"Husky 用 `core.hooksPath` 把钩子目录指向 `.husky/`，于是钩子脚本能进版本控制、能被团队共享"，但没说清**为什么必须这么做**。现在清楚了：

- 钩子默认放在 `.git/hooks`，而 **`.git/` 目录不随 clone 传递**；
- 官方说明的另一种传播路径是 `git init` 从**模板目录**复制 —— 那是**本机配置**，不是仓库内容；
- 所以**手写 `.git/hooks/pre-commit` 的团队，每个新成员都要自己再写一遍**，而且没有任何机制保证他们写的是同一份。

**Husky 的价值不在于"帮你写钩子"，而在于把钩子变成了仓库内容。** 这是"统一"这件事在协作场景下的最小必要条件。

## 2.3 Conventional Commits 1.0.0：一份社区规范的确切形状

先把归属说清楚：**Conventional Commits 不是标准化组织的标准。** 它由 `conventionalcommits.org` 这一社区项目维护，自称"一种轻量级**约定**"，许可为 CC BY 3.0。它借用了 RFC 2119 的关键词（MUST / MUST NOT / REQUIRED / SHALL / SHOULD / MAY / OPTIONAL），官方明确这些词**应按 RFC 2119 所述解释** —— 但**借用术语惯例不构成 RFC 身份**。

认清这一点很重要：这意味着它的强制力来自"工具实现了它"，而不是"标准如此规定"。

### 结构

```
<type>[optional scope]: <description>

[optional body]

[optional footer(s)]
```

### 强制条款（官方用 MUST 措辞的部分）

| 部分 | 规范要求 |
|---|---|
| **type** | 提交**必须**以 type 开头，type 是一个名词；其后接**可选**的 scope、**可选**的 `!`，以及**必需的冒号加空格** |
| **scope** | **可以**提供，**必须**是一个描述代码库某部分的名词，用**圆括号**包裹，如 `fix(parser):` |
| **description** | **必须**紧跟在 type/scope 前缀之后的**冒号和空格之后** |
| **body** | **可以**提供；正文**必须**在描述之后**空一行**开始；是自由格式，可由任意多个以换行分隔的段落组成 |
| **footer** | **可以**提供；每个 footer **必须**由一个词元（token）构成，后接 `:<space>`（冒号+空格）**或** `<space>#`（空格+#）作为分隔符，再接一个字符串值。token **必须**用 `-` 代替空白字符（受 git trailer 约定启发） |
| **大小写** | 构成 Conventional Commits 的信息单元**不得**被实现者视为大小写敏感，**唯一例外是 `BREAKING CHANGE`，它必须大写** |

最后一行的例外很值得注意：**规范刻意避免大小写敏感**（因为提交信息是人手写的），只在一个地方破例 —— 破坏性变更标记。**这个例外的存在本身就是一条设计信号：破坏性变更的识别不允许有歧义。**

### BREAKING CHANGE 的两种写法

规范规定，破坏性变更**必须**在 **type/scope 前缀中**标明，**或**作为 **footer 中的一条目**标明；且它**可以是任何 type** 的提交的一部分。

| 写法 | 形式 | 附加规则 |
|---|---|---|
| **前缀式** | `!` 紧接在**冒号之前**：`feat!: ...`、`feat(api)!: ...` | 若使用了 `!`，footer 中的 `BREAKING CHANGE:` **可以省略**，此时**提交描述即用于说明破坏性变更** |
| **footer 式** | **大写**文本 `BREAKING CHANGE`、一个冒号、一个空格、描述 | 如 `BREAKING CHANGE: environment variables now take precedence over config files.` |

两条细则：**两种写法可以同时出现**；作为 footer token 时，**`BREAKING-CHANGE` 必须与 `BREAKING CHANGE` 同义**。

注意那个 `-` 号细节：footer token 通常必须用 `-` 替代空格，但 **`BREAKING CHANGE` 被豁免**，允许作为 token 直接出现 —— 这是规范为它开的第二处特例。**同一个标记上开了两处特例，说明它在整条链路上的地位最高。**

### 强制 vs 惯例：一处最容易搞混的地方

规范**强制**的 type 只有两个：

- **`feat`** —— 为应用或库新增功能时**必须**使用
- **`fix`** —— 表示应用的缺陷修复时**必须**使用

规范**允许**其他 type（原文举例 `docs: update ref docs.`），并明确规定：**其他 type 不由本规范强制，且在语义化版本中没有隐含效果** —— 除非其中包含 BREAKING CHANGE。

而日常见到的这一串 —— `build` `chore` `ci` `docs` `style` `refactor` `perf` `test` —— **属于 Angular 约定的惯例**，由 `@commitlint/config-conventional` 推荐，**不是本规范强制的**。

这个区分有实际后果：**换一个 commitlint 配置包，这套 type 列表就可能完全不同**，而 `feat` / `fix` / `BREAKING CHANGE` 三条则任何实现都不会变（否则与 SemVer 的映射就断了）。所以：

- 团队规范文档里，`feat` / `fix` / `BREAKING CHANGE` 是**可以对外承诺**的；
- 其余 type 是**内部约定**，改它不需要跟外部协商。

### 与 SemVer 的映射

| 提交内容 | 版本号变化 |
|---|---|
| `fix:` | PATCH |
| `feat:` | MINOR |
| 含 BREAKING CHANGE（任一 type） | MAJOR |

规范摘要的定位是"**与 SemVer 吻合**（dovetails with SemVer）"，方式是**在提交信息里描述特性、修复与破坏性变更**。也就是说：**提交信息是版本号的上游数据源** —— 这解释了为什么 §2.1 说它"错一次影响面更大"。

## 2.4 commitlint：为什么它必须挂在 `commit-msg`

### 官方给的是结论，不是理由

commitlint 官方文档在这件事上非常简短：

> 要使用 commitlint，你**必须**设置 `commit-msg` 钩子（**目前不支持 `pre-commit` 钩子**）。

并在另一处以 WARNING 强调：**钩子文件名必须是 `commit-msg`**。

**官方没有解释原因。** 这一点要如实标注 —— 但 §2.2 的机制已经足以推出答案：

> `pre-commit` 的官方描述是"在**获取拟用的提交日志信息之前**"被调用，且**不接受任何参数**。

也就是说：**在 `pre-commit` 触发的时刻，"这次提交的信息"还不存在。** 提交信息可能是 `-m` 的参数、也可能要等编辑器打开后才被写下来 —— 两者都在 `pre-commit` 之后。一个拿不到提交信息的钩子，无法校验提交信息。

而 `commit-msg` 的官方描述是"接受一个参数：保存拟用提交日志信息的**文件名**"。**信息的载体出现了，校验才成为可能。**

这就是 §2.2 那张表真正的用处：**钩子的能力边界由"它被调用时，世界处于什么状态"决定，而不是由它的名字决定。**

### 落地的确切形状

官方给出的集成步骤（面向 `husky@v9`）：

```shell
npm install --save-dev husky
npx husky init

# 把提交信息校验加到 commit-msg 钩子上
echo "npx --no -- commitlint --edit \$1" > .husky/commit-msg
```

写入文件后的实际内容是：

```
npx --no -- commitlint --edit $1
```

其中 `$1` 就是 Git 传给 `commit-msg` 钩子的那个**消息文件路径**。

官方另给了一个"把命令写成 npm script"的变体：

```shell
npm pkg set scripts.commitlint="commitlint --edit"
echo "npm run commitlint \${1}" > .husky/commit-msg
```

**这两种写法的差别不只是风格**：`npm run` 会多一层进程与 npm 的生命周期钩子（也就多一次可能失败的地方），换来的好处是命令进了 `package.json`、能被别的流程复用。选哪种取决于团队是否需要在别处调用同一条命令。

### 配置与规则的形态

安装与基础配置：

```shell
npm install -D @commitlint/cli @commitlint/config-conventional
```

```js
// commitlint.config.js
export default { extends: ['@commitlint/config-conventional'] };
```

**规则的严重级别只有三档**，官方原文把取值范围写成闭区间：

> Level `[0..2]`：**0** 禁用该规则；**1** 视为**警告**；**2** 视为**错误**。

注意是 `[0..2]` —— **没有 3**。这与 ESLint 的 0/1/2 一致，但比它更值得记住的是：**commitlint 的规则配置是一个数组，没有"裸数字"简写形式。**

官方对配置类型的定义是：

> 规则配置要么是挂在 `rules` 对象上、以规则名为键的**数组**，要么是一个**函数**，返回数组或 `Promise<数组>`。

数组的组成是**三个元素**：

1. **Level** `[0..2]` —— 0 禁用 / 1 警告 / 2 错误
2. **Applicable** —— `always` 或 `never`（`never` 表示反转该规则）
3. **Value** —— 该规则使用的值

三个示例正好覆盖三种形态：

```js
// 普通数组
export default { rules: { 'header-max-length': [2, 'always', 72] } };

// 函数返回数组
export default { rules: { 'header-max-length': () => [2, 'always', 72] } };

// 异步函数返回数组
export default { rules: { 'header-max-length': async () => [2, 'always', 72] } };
```

**`never` 这个维度值得单独看**：它意味着规则本身可以是"反向的"。比如"禁止某些 type"不是另有一条规则，而是把"type 必须属于某集合"反转过来 —— **同一套规则原语，靠 `always` / `never` 表达两个方向。**

### 默认开了哪些 type —— 从一条真实报错里读出来

`@commitlint/config-conventional` 默认开启的 type 列表，可以直接从官方给的失败示例里读到：

```
✖ type must be one of [build, chore, ci, docs, feat, fix, perf, refactor, revert, style, test] [type-enum]
```

**十一个**：`build` `chore` `ci` `docs` `feat` `fix` `perf` `refactor` `revert` `style` `test`。

对照 §2.3 就清楚了：**其中只有 `feat` 与 `fix` 是 Conventional Commits 强制的，另外九个是配置包的选择。** 而报错信息末尾方括号里的 `[type-enum]` 是**规则名** —— 看到它就知道该去查哪条规则的配置，这是 commitlint 输出格式里一个很实用的设计。

共享配置包的命名约定是两套前缀：**`@commitlint/config-*`**（官方与作用域包）与 **`commitlint-config-*`**（非作用域的社区包）。

### 两个版本行为变化（会影响你看到什么输出）

| 版本 | 变化 |
|---|---|
| **v8.0.0** 起 | 提交**无问题时默认不输出任何内容** —— 想看到正向输出要加 `--verbose` |
| **v21.0.0** 起 | 提交信息在**换行（EOL）之后**输出，而不是像以前那样跟在冒号之后；用 `--legacy-output` 可恢复旧格式 |

第一条的实际影响是：**"钩子跑完了但屏幕上什么都没有"是正常行为，不是钩子没跑。** 第二条影响的是**解析 CLI 输出做二次处理的脚本**。

### CI 补位：本地校验必然不够

官方在 Local setup 页的结尾明确建议：**本地 lint 反馈快但容易被绕过，应同时在 CI 上校验。**

机制上很清楚 —— §2.2 已经确认 `commit-msg` **可被 `--no-verify` 绕过**。所以本地这一层与第 1 章的 pre-commit 一样，是**快速反馈层**，不是强制层。

CI 上要解决一个本地不存在的问题：**PR 里有多个提交，本地每次只校验了一个。** 官方的做法是用 `--from` / `--to` 覆盖整个范围。以 GitHub Actions 为例：

```bash
npx commitlint --from ${{ github.event.pull_request.base.sha }} --to ${{ github.event.pull_request.head.sha }} --verbose
```

**这里有一个必须配套的设置：`fetch-depth: 0`。**

官方对 GitLab CI 版本给出了原因，这句话适用于所有平台：

> GitLab 默认把 git clone 深度限制为 20 个提交。设置 `GIT_DEPTH: 0` 解除这一限制，**这样 commitlint 才能检查更大的 MR**。

原因不难推：`--from <base.sha>` 要求那个提交对象**在本地存在**。浅克隆拿不到完整历史，起点就不存在 —— 校验会失败，而且**报的错看起来像"提交信息不合法"，实际是"起点找不到"**。这类"错误信息指向的位置与实际原因不一致"的问题，是本章后续要反复出现的模式。

其他几个有用的用法：

| 场景 | 命令 |
|---|---|
| 只校验最后一个提交（push 场景） | `npx commitlint --last --verbose` |
| 本地手工测最近一次提交 | `npx commitlint --from HEAD~1 --to HEAD --verbose` |
| 不建配置文件、直接用内置默认配置 | `npx commitlint --default-config` |

## 2.5 分支模型：两种模型的真实代价

### 先把"归属"说清楚

**Git Flow 与 Trunk Based Development 都不是标准。**

- **Git Flow** 是 Vincent Driessen 于 **2010-01-05** 发表的一篇**个人博客文章**。文章本身从未自称标准。
- **Trunk Based Development** 站点自述是"**试图把 Trunk-Based Development 相关的事实、理由与技巧汇集在一处**"的站点，作者 Paul Hammant —— 是**实践汇编**，不是规范。

它们的分量来自影响力，不是来自权威。认清这点，才不会被"某模型是行业标准"这类说法压住。

### Git Flow：五个分支与一次作者本人的反思

文章定义的**长生命周期分支**两个、**支持性分支**三个：

| 分支 | 从何分叉 | 合并回何处 | 要点 |
|---|---|---|---|
| `master` | — | — | HEAD **始终反映生产就绪状态**；每次合并回 master 即定义一个新发布 |
| `develop` | — | — | HEAD **始终反映下一次发布的最新开发变更**；即"集成分支" |
| Feature | `develop` | `develop` | **通常只存在于开发者本地仓库，不推送到 origin**；合并用 `--no-ff` 以保留分支历史 |
| Release | `develop` | `develop` **和** `master` | 发布准备；**版本号恰在创建发布分支时确定**；禁止加入大型新功能 |
| Hotfix | `master`（对应生产版本的 tag） | `master` **和** `develop` | 线上严重 bug 的紧急修复；**例外**：若已存在 release 分支，hotfix 应合入该 release 分支而非 `develop` |

两个容易被忽略的机制点：

- **"版本号恰在创建发布分支时确定"** —— 这是 Git Flow 把"版本号"从"打 tag 的那一刻"前移到了"切分支的那一刻"。它带来的直接后果是：**分支名里就该带版本号**，且 release 分支上不允许再进大功能。
- **Feature 分支通常不推送到 origin** —— 这条常被忽略。很多人以为 Git Flow 意味着"每个功能都开远程分支"，实际原文说的是它通常只存在于**开发者本地**。

**然后是最重要的一段。** 作者在 **2020-03-05** 给这篇文章加了一条顶部说明，标题是「NOTE OF REFLECTION」（反思注记）。原文关键句：

> 这个模型构思于 2010 年，距今已超过十年……在这十年里，git-flow 在许多软件团队中变得极其流行，到了人们开始**把它当成某种标准**的地步 —— 但不幸的是，也把它当成了**教条或万能药**。
>
> ……用 Git 开发的最流行的软件类型**正在转向 Web 应用** —— 至少在我的信息茧房里是这样。**Web 应用通常是持续交付的、不回滚的，而且你不需要同时支持线上运行的多个版本。**
>
> **这不是我十年前写这篇博文时所设想的软件类型。如果你的团队在做持续交付，我建议采用一个简单得多的工作流（比如 GitHub flow），而不是把 git-flow 硬塞进你的团队。**
>
> 但是，如果你构建的软件是**显式版本化的**，或者**你需要同时支持线上运行的多个版本**，那么 git-flow 可能仍然适合你的团队……最后，永远记住**不存在万能药**。考虑你自己的情境。别急着否定。自己决定。

这段话的价值在于它给出了**一条可用的判据**，而且是**模型作者本人**给的：

> **判据不是"团队大小"或"项目复杂度"，而是"你是否需要同时支持线上运行的多个版本"。**

需要 → Git Flow 那套 release / hotfix 分支才有存在意义（它们的核心职责就是**维护多条并行的版本线**）。不需要 → 它就是纯开销。

### Trunk Based Development：定义与硬性要求

站点的定义原文：

> 一种源码管理分支模型：开发者在一个名为 `trunk` 的单一分支上协作，**并通过采用有据可查的技术，抵御任何创建其他长生命周期开发分支的压力。**

要害在"**抵御压力**" —— 这个模型的核心不是"用一条分支"，而是**主动拒绝另一种做法**。

它与"短生命周期特性分支"的关系是明确的：允许两条提交路径 —— 极小团队直接 commit/push 到 trunk；或走 **Pull Request 流程，但特性分支必须是短生命周期的，且是单个开发工作站的产物**（solo / pair / mob 均可）。

两条边界值得记：

- **短分支仅用于 code review 与 CI 构建检查，不用于产物的创建或发布。**
- **站点没有给出"短"的具体数值**（如"不超过一天"）—— 只给定性表述。**任何声称"TBD 分支必须活不过 24 小时"的说法，都不是这个站点的表述。**

而站点给出的**硬性要求**，才是这个模型真正的成本所在：

| 要求 | 内容 |
|---|---|
| **提交频率** | 每个团队成员**至少每 24 小时提交一次**到 trunk（这是 CI 的核心要求） |
| **提交前** | 在自己的工作站上完成完整的 **"pre integrate" 构建**：编译、单元测试、集成测试 |
| **构建服务器** | 超过两三名开发者时，需接入构建服务器，验证合入 trunk 后没有破坏构建 |
| **底线** | **"Don't break the build"** |

配套技术是 **feature flags**（日常开发中使用，用于对冲发布顺序）与 **branch by abstraction**（用于需要较长时间才能完成的变更）。也就是说：**长周期的工作不是靠长分支承载的，是靠开关与抽象层承载的。**

关于发布分支，原文给出了两种都可能成立的做法：

> 视预期的发布节奏而定，可能有 release 分支 —— 它们**按需即时（just-in-time）从 trunk 切出**，发布前被"**硬化**"（且这**不是一项团队性活动**），发布后一段时间被删除。另一种可能是**完全没有 release 分支**：团队直接从 trunk 发布，并对 bug 采取 "**fix forward**"（向前修复）策略。

**"硬化不是团队性活动"这一句是理解 TBD 的关键**：release 分支上的工作由**少数人**完成，其余人继续在 trunk 上开发 —— 这与 Git Flow 把 release 分支当作全团队协作阶段的形态完全不同。

### 怎么选：一条可用的判据

把两边的判据放在一起，选择就变成可判定的：

| 你的情况 | 更契合的模型 | 理由 |
|---|---|---|
| 持续交付、不回滚、线上只有一个版本 | **Trunk Based** | Git Flow 作者本人的建议；release/hotfix 分支失去存在意义 |
| 显式版本化，或需同时支持线上多版本 | **Git Flow** | 多版本线的维护正是那套分支的职责 |
| 团队极小（2–3 人） | 任一，但代价不同 | TBD 在极小团队下不需要构建服务器；但它要求**每天提交**的纪律 |

**注意这里没有"用团队规模选模型"这一项。** 团队规模影响的是 TBD 的**实施成本**（要不要构建服务器），不是**该不该用它**。

## 2.6 协作流程的三块机制

### PR 模板：路径、命名与一条大小写陷阱

GitHub 官方文档给出的存放位置：

| 形态 | 路径 | 说明 |
|---|---|---|
| 单模板 | `pull_request_template.md` | 仓库根目录 |
| 单模板 | `docs/pull_request_template.md` | `docs` 目录下 |
| 单模板 | `.github/pull_request_template.md` | 隐藏目录中 |
| 多模板 | `.github/PULL_REQUEST_TEMPLATE/<文件名>.md` | 目录名**全大写** |
| 多模板 | 根目录或 `docs/` 下的 `PULL_REQUEST_TEMPLATE/` | 同上 |

**大小写不是可选的**：单模板文件名是小写 `pull_request_template.md`，而多模板的**目录名是全大写 `PULL_REQUEST_TEMPLATE` + 下划线**。写错了不报错，只是模板不出现。

三个机制点：

1. **模板只有在合并进默认分支后才对协作者生效** —— 官方原文："Templates are available to collaborators when they are merged into the repository's default branch."
2. **模板被自动填入 PR 的正文框（body）**，用户可以编辑。所以模板的价值不是"强制填写"，而是**把默认值设对** —— 大部分人会编辑已有内容，不会从空白开始写。
3. **多模板用 `template` 查询参数指定**，例如构造 PR 链接时带上参数选择要填充的模板。

**一处需要澄清的常见误解**：GitHub 的 **`config.yml` 是"议题模板选择器"的配置**，用于新建 Issue 时的选择界面。**PR 模板的多选机制走的是 `template` 查询参数，不是 `config.yml`。** 官方 PR 模板文档**完全没有提到 `config.yml`**。

另外，官方文档**没有给出**这些路径之间的优先级顺序，只说明会从"受支持的文件夹"读取；组织或个人账号还可以设置**默认模板**，其与仓库级模板的优先级同样未在该页说明。

### CODEOWNERS：它到底"强制"了什么

这是本章最容易被误解的机制。它做的事情远比"给文件指定负责人"要多，也比"自动分配评审人"要少。

#### 位置与优先级

三个位置（都在**目标分支**上）：`.github/`、仓库根目录、`docs/`。**多个位置同时存在时，按此顺序取用找到的第一个。**

**每个 CODEOWNERS 文件只作用于仓库中的某一个分支**，因此不同分支可以配置不同的 owner。关键约束：**要让 code owner 收到评审请求，CODEOWNERS 文件必须位于 PR 的基础分支（base branch）上。**

#### 语法：三处与 gitignore 的差异

官方明确警告，CODEOWNERS 遵循 gitignore 的大部分模式规则，但**以下 gitignore 语法无效**：

- 用 `\` 转义以 `#` 开头的模式 ❌
- 用 `!` 取反模式 ❌
- 用 `[ ]` 定义字符范围 ❌

**"不支持 `!` 取反"这一条要特别注意** —— 在 `.gitignore` 里用 `!` 排除是家常便饭，照搬到 CODEOWNERS 会静默失效，且**规则看起来完全合理**。

#### 匹配规则：最后匹配者生效

> 官方原文：**"Order is important; the last matching pattern takes the most precedence."**（顺序很重要；**最后匹配的模式优先级最高**。）

这一条与 `.gitignore` 的习惯相反（gitignore 后写的规则也覆盖前面的，但 CODEOWNERS 里"最后匹配"的含义更严格）。几个后果：

- **同一模式要绑定多个 owner，必须写在同一行。** 分多行写，只有**最后一个** owner 生效 —— 这是一个几乎必踩的坑。
- **路径区分大小写**，即使在大小写不敏感的文件系统（如 macOS 默认）上编写也必须写对。
- **先写通配、再写特例** 才是正确顺序：`* @global-owner1 @global-owner2` 写在前面，`*.js @js-owner` 写在后面，改 `.js` 时才只请求 `@js-owner`。

路径语义的几个对照：

| 写法 | 含义 |
|---|---|
| `*` | 匹配仓库中所有内容（全局默认 owner） |
| `/build/logs/` | **前导 `/` 锚定到仓库根**：根目录下的 `build/logs` 及其所有子目录 |
| `docs/*` | 匹配 `docs/getting-started.md`，**但不匹配** `docs/build-app/troubleshooting.md` —— `*` 不跨目录层级 |
| `apps/` | **无前导 `/`**：匹配仓库**任意位置**的 `apps` 目录内文件 |
| `**/logs` | `**` 跨层级匹配任意深度的 `/logs` |

#### 生效的前置条件：权限是硬性的

- 被列为 code owner 的人**必须拥有仓库的 Write 权限**。
- 若 code owner 是一个**团队**，该团队必须**可见（visible）且显式拥有 Write 权限** —— 官方反复强调：**即使团队成员已经通过组织成员身份、直接授权或其他团队获得了 Write 权限也不行**，团队本身必须被显式授权。
- **只有组织团队（organization teams）可以作为 code owner，企业团队不支持。**
- 若指定的用户/团队不存在或权限不足，**不会分配 code owner**（静默失效）。

#### 它实际触发什么

| 行为 | 说明 |
|---|---|
| **自动请求评审** | 有人打开修改了其拥有代码的 PR 时，code owner 被自动请求评审 |
| **草稿 PR 不触发** | **draft PR 不会**自动请求；把草稿标记为 **Ready for review** 时才触发。把 PR 转为草稿**不会**自动取消已订阅者 |
| **可作合并门禁** | 若启用分支保护规则 **"Require review from Code Owners"**，PR **必须获得 code owner 批准**后才能合并 |
| **但只需一人** | ⚠️ **任意一位 owner 批准即可满足要求，不要求所有 owner 都批准** |

最后一行是这一节最容易被高估的地方：**它不是一个"全体同意"机制。** 写 `*.js @a @b`，`@a` 一个人点了批准就够了。

#### 一个必须补上的安全盲区

官方专门提示：要完整保护仓库，**还需要为 CODEOWNERS 文件自身定义 owner**。最安全的做法是把 CODEOWNERS 放在 `.github` 目录，并把仓库 owner 设为该文件或其所在目录的 owner：

```
/.github/CODEOWNERS @owner_username
/.github/ @owner_username
```

**不这么做的后果很直接**：任何有 Write 权限的人都可以改 CODEOWNERS，把自己的评审要求删掉或改成自己 —— 这是一条**自我授权路径**。第 1 章 §1.7 提到 Stylelint 的 `reportDisables` 是"让绕过留下痕迹"，这里的思路是同一类：**门禁的配置本身必须被另一个门禁保护。**

#### 其他限制

- **文件中任何一行语法无效，该行即被跳过** —— 官方提示可在仓库中查看该文件时看到高亮错误，也可用 REST API `list-codeowners-errors` 取错误列表。
- **CODEOWNERS 文件必须小于 3 MB**，超出则**不加载**（既不显示归属信息，也不请求评审）。可用通配符合并条目缩小体积。
- Fork 场景：**PR 使用基础分支版本的 CODEOWNERS**。若基础分支在上游仓库，就用上游仓库该分支的文件。

### Code Review：Google 给了一条可判定的标准

Google 工程实践的 Code Review 指南自述为"**Google 代码审查流程与政策的权威描述**（canonical description）"—— 注意它描述的是**一家公司内部的流程**，不是行业标准。但它给出的标准足够清晰，可以直接当判据用。

**批准标准（原文）：**

> 总的来说，**一旦一个 CL 达到了"确实能改善所开发系统的整体代码健康度"的状态，审查者就应倾向于批准，即使这个 CL 并不完美。**
>
> **这是所有代码审查指南中最高层级的原则。**

并配了两条边界：

> 当然这有限制。例如，如果一个 CL 加入了一项审查者不希望出现在系统中的功能，那么即使代码设计良好，审查者当然也可以拒绝批准。

> 注意：本文档中没有任何内容为"提交明确会恶化系统整体代码健康度的 CL"提供正当理由。唯一会这么做的时候是紧急情况。

**关于"完美"（原文）：**

> 这里的关键点是：**不存在"完美的"代码 —— 只有更好的代码。** 审查者不应要求作者在批准前打磨 CL 的每一个细微之处……**审查者应当追求的不是完美，而是持续改进。**

**关于不重要意见的表达方式：**

> 如果某条意见不太重要，就以 `Nit: ` 之类的前缀开头，让作者知道这只是一处他们可以选择忽略的抛光点。

`Nit:` 这个约定解决的是一个具体问题：**审查者的意见在形式上都是"评论"，作者无法从形式判断哪条是阻塞性的。** 加一个前缀，就把"必须改"与"可以不改"分开 —— 二者混在一起时，作者的默认反应是全部照改，review 就失去了优先级。

**关于速度，Google 给了全书最具体的一条时间要求：**

> **一个工作日是响应代码审查请求的最长时间**（即第二天一早）。
>
> 遵循这些指南意味着，一个典型的 CL 应当在**一天之内**完成多轮审查。

并澄清了关注的到底是哪个时间：

> 当我们谈论代码审查的速度时，我们关注的是**响应时间**，而不是一个 CL 走完整个审查流程并被提交需要多久……**单次响应足够快，甚至比整个流程足够快更重要。**

关于"太忙"，官方给的是可执行的替代动作：

> 如果你在 CL 到来时忙得无法做完整审查，你**仍然可以快速回复**：让开发者知道你什么时候会看、建议可能响应更快的其他审查者、或给出一些初步的概括性评论。

以及一条对审查者的保护：

> 如果你正处在一个专注任务中（比如写代码），**不要打断自己去做代码审查** —— 应等工作中的自然断点。

**为什么速度重要**，官方给了三条后果，第二条尤其值得记：

> **大多数关于代码审查流程的抱怨，实际上都能通过让流程变快来解决。**

理由是：如果审查者每隔几天才响应一次、每次还都要求大改，作者会开始抵制这个流程（并且常常表现为抱怨审查者"太严格"）；而如果审查者每次响应都很快，**同样的实质要求，抱怨往往会消失**。

## 2.7 实战：一个团队的提交规范与协作流程是怎么长出来的

> **说明**：与第 1 章 §1.12 同一性质 —— 这是一条**构造示例**，不是某个真实团队的经历。每一步的现象与成因都能在本章找到对应机制。

### 阶段一：提交历史读不出信息

**现象**：`git log` 里是 `fix bug`、`update`、`修改`、`123`，要定位"这一行是为什么改的"，只能靠 `git blame` 猜。

**性质**：这不是"提交信息写得不好看"，而是**丢失了可用数据**。§2.1 说过提交信息是接口 —— 这个阶段的团队，等于把接口的返回值全设成了 `null`。

### 阶段二：把约定写进 CONTRIBUTING，无人遵守

**新现象**：文档写得很清楚，但遵守率取决于新人入职时有没有认真读。

**成因**：按 §2.1 的两条判据 —— Conventional Commits 的条款是**可判定**的（§2.3 里那些 MUST 都是机器能判的），但**没有代价**。所以它仍然只是文档。

**修法**：加 commitlint，挂 `commit-msg`。

### 阶段三："我的提交被拒了，但我不知道该怎么写"

**新现象**：钩子报出 `✖ type must be one of [...] [type-enum]`，作者改了两三次还是不对，开始烦躁。

**成因**：**校验只回答"错在哪"，不回答"该怎么写"。** 这两件事需要不同的工具：**commitlint 是校验器，Commitizen 是引导器。**

Commitizen 的官方定位正好说明了这个分工 —— 它在**提交时交互式提问**，即时给出格式反馈，作者不必先写错、被拒、再去翻文档。官方对二者关系的表述是明确的：**"Commitizen or Commit Hooks — Both!"** —— 它不是钩子的替代品，而是与之**并存**。

**一处要如实说明的地方**：Commitizen 的 README **把 commitlint 列在"相关项目"里，并提供官方适配器**（`@commitlint/cz-commitlint`、`@commitlint/prompt`），但**没有出现"强烈推荐搭配 commitlint"之类的明文表述**。准确的说法是"可搭配、被兼容"。

平台能力：

- 适配器通过 `package.json` 的 `config.commitizen.path` 或 `.czrc` 文件指定，**经 `require.resolve` 解析**；
- 交互入口是 `git cz` **或** `cz`（`git-cz` 是别名），也可用 `npx cz` 或 npm script；
- **未适配的仓库里 `git cz` 行为与 `git commit` 相同**（这点容易误判为"cz 没生效"）；
- 适配器普遍采用 `cz-` 前缀，官方也列出了 `@commitlint/cz-commitlint`。

### 阶段四：CI 上只有最后一个提交被校验

**新现象**：PR 里第三个提交的格式是错的，但本地每次都过、CI 也过了。

**成因**：本地 `commit-msg` 钩子**每次只校验一个提交**。如果 CI 上也只跑 `commitlint --last`，那 PR 里的中间提交就有系统性盲区 —— **恰好在本地被绕过、或作者用别的工具生成的提交，最容易落在这个盲区里。**

**修法**（§2.4）：CI 上用 `--from` / `--to` 覆盖 PR 全量提交范围：

```bash
npx commitlint --from ${{ github.event.pull_request.base.sha }} --to ${{ github.event.pull_request.head.sha }} --verbose
```

**然后立刻会遇到下一个坑**：`--from <sha>` 要求那个提交对象在本地存在，而 CI 默认做浅克隆。

**症状非常容易误判**：报错看起来像"提交信息不合法"，实际是"起点找不到"。

**修法**：`actions/checkout` 配 `fetch-depth: 0`（GitLab 是 `GIT_DEPTH: 0`，官方原文解释："GitLab 默认把 clone 深度限制为 20 个提交，设置 `GIT_DEPTH: 0` 解除限制，**这样 commitlint 才能检查更大的 MR**"）。

这条与第 1 章 §1.5 的缓存问题属于同一类：**错误信息指向的位置，与实际原因不一致。**

### 阶段五：有人用 `--no-verify`

**现象**：查到了一个格式不合规的提交，作者说是"当时赶时间"。

**成因**：§2.2 已经确认 —— `commit-msg` 与 `pre-commit` **都可以被 `--no-verify` 绕过**。这与第 1 章 §1.11 盲区三完全一致：**本地门禁天然可绕过。**

**修法**：不是"要求大家不用 `--no-verify`"，而是**把 CI 的校验作为强制层**。官方也正是在 Local setup 页末尾建议"应同时在 CI 上校验"。**任何"靠自觉"的修补方案，都会在三个月后失效。**

### 阶段六：CHANGELOG 靠手工维护，必然失真

**新现象**：CHANGELOG 停留在三个版本之前，要么就写成了流水账。

**成因**：手工维护的文档，**在信息已经存在于 git 历史里时，是纯粹的重复劳动** —— 而重复劳动的下场就是没人做。

**修法**：从 git 元数据生成。`conventional-changelog` 的定位就是这一句：**"Generate a CHANGELOG from git metadata."** 它的输入是**提交历史**，按 preset（如 Angular 格式或 Conventional Commits 格式）解析后生成日志。

它的生态里几个组件的分工值得记一下：

| 包 / 工具 | 职责 |
|---|---|
| `conventional-commits-parser` | 把提交信息**解析**成结构化字段 |
| `conventional-commits-filter` | **过滤**（如滤掉 revert 或特定类型的提交） |
| `conventional-changelog-writer` | 按模板**写出** CHANGELOG |
| `conventional-recommended-bump` | 根据提交**推荐版本号提升幅度** |
| `conventional-changelog` / `standard-changelog` | 命令行入口（后者针对 Angular 格式） |

README 另推荐了三个更高层的自动化工具（**不属于本仓库**）：`commit-and-tag-version`（自述为 npm `version` 命令的即插即用替代品）、`semantic-release`（在 CI/CD 中全自动完成版本判定、changelog 生成与发布）、`simple-release-action`。

**一处诚实的说明**：该 README 是**导航型入口页** —— 它**没有给出 CLI 命令示例**，也**没有给出 commit type → SemVer 的映射表**，更没有标注版本号。【待验证】社区中 `standard-version` 已归档、由 `commit-and-tag-version` 接续这一说法，**在该 README 中没有任何表述**，本书不引用它。

**这里有一步很关键的推理**：CHANGELOG 自动生成之所以可行，前提是**提交信息里已经编码了"这是什么类型的变更"**。§2.3 的强制条款 —— `feat` / `fix` / `BREAKING CHANGE` —— 正好构成这个编码。**所以"规范提交信息"不是形式主义，它是自动化流水线的输入格式。** 这也是本章跟第 1 章最大的区别：第 1 章的规范约束代码风格，本章的规范**驱动了发布流程**。

### 阶段七：review 慢，PR 巨大

**现象**：一个 PR 改了 40 个文件、活了十天；reviewer 每次只回复"等我看看"；作者开始抱怨"流程太重"。

**三条可以对照官方原文来纠正的地方**：

1. **响应时间有明确要求**：不是"尽快"，而是"**一个工作日是响应代码审查请求的最长时间**"。
2. **大 CL 的正确回应是要求拆分**，官方原文：**"你通常应当要求开发者把 CL 拆成若干个基于彼此的更小的 CL"**；如果拆不了又没时间快速看完，**至少要对整体设计写出评论并退回给开发者** —— 因为审查者的目标之一是**"始终让开发者解除阻塞、或能快速采取某种进一步行动，同时不为此牺牲代码健康度"**。
3. **"流程太重"的抱怨往往其实是"流程太慢"**：官方原文说得很直白 —— **"大多数关于代码审查流程的抱怨，实际上都能通过让流程变快来解决。"**

**这一阶段还有一个隐性的 bug**：作者把状态从草稿改成 Ready 之后，**没有人被通知**。原因在 §2.6 —— **草稿 PR 不会自动请求 code owner 评审**，只有标记为 Ready for review 时才会触发。

### 阶段八：CODEOWNERS 写了，但没人被自动分配

**现象**：CODEOWNERS 文件存在、内容看起来也对，但 PR 里始终没有自动出现评审人。

**排查清单**（每一项都对应 §2.6 的一条机制）：

| 检查 | 若不符合 |
|---|---|
| 被指定的人有 **Write** 权限吗？ | 权限不足 → 静默不分配。团队更严格：**成员有权限不算，团队本身必须被显式授权** |
| 用 `@org/team` 了吗？是**组织团队**吗？ | 企业团队**不支持**作为 code owner |
| 文件在**目标分支**上吗？ | 必须在 PR 的基础分支上 |
| 同一模式的多 owner 是**写在同一行**吗？ | 分多行只有最后一个生效 |
| 文件大小**超过 3 MB** 吗？ | 超出则**完全不加载** |
| 是不是 **draft PR**？ | 草稿不触发，改成 Ready 才触发 |

**这份清单值得单独保存在团队文档里** —— 因为六项里有四项都是**静默失效**（不报错、不提示，只是不生效）。静默失效的排查成本远高于会报错的失效。

### 阶段九：发现有人改了 CODEOWNERS 来绕过评审

**现象**：某次 PR 里，CODEOWNERS 被顺手改了。

**成因**（§2.6 的安全盲区）：CODEOWNERS 文件本身**如果没有被任何 owner 覆盖**，那么**任何有 Write 权限的人都可以改它** —— 包括删掉自己的评审要求、或把自己加成 owner。这是一条**自我授权路径**。

**修法**（官方建议）：把 CODEOWNERS 放在 `.github`，并把仓库 owner 设为该文件或该目录的 owner：

```
/.github/CODEOWNERS @owner_username
/.github/ @owner_username
```

**这一条值得记住的是它的形状**：门禁的**配置**必须被另一个门禁保护。这与第 1 章 §1.7 的 `reportDisables`（把 disable 注释本身报为错误）是同一种思路 —— **"绕过通道"如果不被监控，门禁就等于没有**。

### 反过来看：这一章的机制该放进团队文档的哪几句

| 现象 | 先查什么 | 对应机制 |
|---|---|---|
| 提交被拒但不知怎么改 | 是不是缺了引导（Commitizen） | §2.4 校验与引导分工 |
| 钩子跑完了屏幕上没输出 | v8.0.0 起无问题默认静默 | §2.4 版本行为变化 |
| CI 报"提交信息不合法"，但本地一样的信息能过 | 浅克隆 → `fetch-depth: 0` | §2.4 CI 补位 |
| 有人提交了不合规的信息 | 是否用了 `--no-verify` | §2.2 钩子可绕过性 |
| CHANGELOG 长期失真 | 是否还在手工维护 | §2.7 阶段六 |
| 新成员本地完全没有钩子 | 钩子不随 clone 分发 | §2.2 传播路径 |
| PR 巨大、review 拖很久 | 是否要求过拆分；响应是否超过一个工作日 | §2.6 Code Review 速度 |
| CODEOWNERS 不生效 | §2.7 阶段八的六项清单 | §2.6 静默失效 |
| CODEOWNERS 被人改过 | 该文件自身有没有 owner | §2.6 安全盲区 |

## 2.8 动手

**每一项都要求说出理由**：

| 任务 | 验收 |
|---|---|
| 本地手写一个 `.git/hooks/commit-msg`（不用 Husky），提交一次 | 说出为什么**新克隆的仓库里不会有它**，以及官方文档说的是哪条传播路径 |
| 同上，但故意不 `chmod +x` | 记录现象，说出 Git 官方对"没有执行位的钩子"怎么处理 |
| 把提交信息校验写进 `pre-commit` | 说出它**为什么不可能**拿到提交信息（引用官方对 pre-commit 时机的描述） |
| 给 `prepare-commit-msg` 加一个会失败的脚本，然后用 `--no-verify` 提交 | 说出结果与 §2.2 的哪一条相关 |
| 写一条只满足强制条款、不含任何惯用 type 的提交（如 `docs: ...`） | 说出它是否符合规范的 MUST 条款 |
| 写一条 `feat(api)!: ...`，不给 `BREAKING CHANGE` footer | 说出规范**是否允许**，以及依据是哪一条 |
| 写一条 footer 里用 `breaking change:`（小写）的提交 | 说出它是否有效，以及规范中"大小写"那条的例外规则 |
| 把同一条规则配置成 `[0, 'always', value]` 与 `[2, 'never', value]` | 说出两种写法在实际行为上的等价关系，以及 severity 的**取值区间上下界** |
| 用 `@commitlint/config-conventional` 提交一个 `foo:` 开头的信息 | 记录报错，说出方括号里的规则名有什么用、默认 11 个 type 里哪几个是规范强制的 |
| 在 CI 上跑 `commitlint --from <base> --to <head>`，**不**设 `fetch-depth: 0` | 记录报错，说出它**看起来像**什么错误、实际是什么原因 |
| 在同一模式的两行里分别写不同的 owner（如 `*.js @a` 和 `*.js @b`） | 说出谁生效（依据 §2.6 的顺序规则） |
| 在 CODEOWNERS 里用 `!` 取反排除一个文件 | 记录现象，说出它与 `.gitignore` 的差异 |
| 给 `@org/team` 指定一个团队成员已有 Write 权限、但团队本身未被授权的团队 | 记录现象，说出为什么"成员有权限"不够 |
| 开一个 draft PR 看是否自动请求评审，再改成 Ready | 说出两次的差别 |
| 让某文件的多个 owner 中只有一人批准 | 说出分支保护规则 **Require review from Code Owners** 是否被满足 |
| 从 CODEOWNERS 里删掉 `.github/CODEOWNERS` 自身的归属，然后修改它 | 说出这条**自我授权路径**的机制，以及官方建议的补法 |

**进阶挑战**（任选一项）：

1. 把 Git Flow 的五种分支在一条时间线上画出来（含 release 与 hotfix 的例外路径），然后**用作者 2020 年的反思原文**判断：你的项目属不属于"该换更简单工作流"的那一类。
2. 按 Trunk Based Development 的硬性要求，盘点你所在团队**四项要求各满足了几项**，并说明哪一项最难达到、为什么。
3. 用 `conventional-changelog` 从一个真实仓库的提交历史生成一份 CHANGELOG，然后统计：有多少提交**因为不符合规范而根本没被解析出来**。这个数字就是对 §2.3 强制条款价值的量化。

## 2.9 本章常见误区

| # | 误区 | 纠正 |
|---|---|---|
| 1 | "把提交信息校验放 pre-commit 也一样" | 官方明确 **commitlint 不支持 pre-commit 钩子**。机制原因：pre-commit 是在**获取提交信息之前**、且**无参数**被调用的 |
| 2 | "所有钩子都能被 `--no-verify` 绕过" | **`prepare-commit-msg` 不受 `--no-verify` 抑制**（官方明确），它是唯一一个 |
| 3 | "钩子会随 clone 分发" | 官方**没有**这个说法。默认目录是 `$GIT_DIR/hooks`，传播路径是 `git init` 从**本机模板目录**复制 —— 这正是 Husky 用 `core.hooksPath` 的意义 |
| 4 | "钩子文件放对位置就行" | **没有执行位的钩子会被忽略**（静默失效） |
| 5 | "`docs` / `chore` / `ci` 这些是规范要求的" | 规范**强制**的只有 `feat` 与 `fix`。另外九个（共 11 个默认 type）是 `@commitlint/config-conventional` 的选择 |
| 6 | "`feat!:` 后面必须再写 `BREAKING CHANGE` footer" | 用了 `!` 时 footer **可以省略**，此时提交描述本身即用于说明破坏性变更 |
| 7 | "`breaking change:` 小写也行" | **`BREAKING CHANGE` 必须大写** —— 这是规范中"大小写不敏感"的唯一例外 |
| 8 | "footer token 必须用 `-` 代替空格，所以得写 `BREAKING-CHANGE`" | 两种写法**必须同义**，且 `BREAKING CHANGE` 被**豁免**，允许直接作为 token |
| 9 | "commitlint 的 severity 可以设 3" | 官方写的是闭区间 **`[0..2]`** —— 0 禁用 / 1 警告 / 2 错误，**没有 3** |
| 10 | "规则可以直接写一个数字简写" | 官方定义的是**数组**（`[level, applicable, value]`）或返回数组的函数，**没有裸数字写法** |
| 11 | "`always` / `never` 是两条不同的规则" | 它是**同一个规则的反转维度** —— 一套原语表达两个方向 |
| 12 | "钩子跑完没输出说明没生效" | **v8.0.0 起无问题默认静默**，要加 `--verbose` 才看到正向输出 |
| 13 | "CI 上跑 `commitlint --last` 就够了" | 它只校验最后一个提交。**PR 中间的提交有系统性盲区**，要用 `--from` / `--to` |
| 14 | "CI 报了提交信息不合法，那就是信息不合法" | 很可能是**浅克隆导致 `--from` 的起点不存在**。要配 `fetch-depth: 0` / `GIT_DEPTH: 0` |
| 15 | "Git Flow 是行业标准做法" | 它是一篇**个人博客文章**（2010-01-05）。作者本人在 2020 年加了反思注记，说它"被当成了教条或万能药" |
| 16 | "TBD 的特性分支必须活不过 24 小时" | 官方站点**没有给出具体数值**，只给定性表述 "short-lived"。24 小时那条说的是**每人至少每 24 小时提交一次到 trunk** |
| 17 | "TBD 的长周期工作靠长分支承载" | 靠 **feature flags** 与 **branch by abstraction**。短分支**仅用于 code review 与 CI 构建检查**，不用于产物创建或发布 |
| 18 | "PR 模板文件名可以随便写" | 单模板是小写 `pull_request_template.md`，多模板目录是**全大写** `PULL_REQUEST_TEMPLATE/`。写错不报错，只是不生效 |
| 19 | "PR 多模板由 `config.yml` 配置" | **`config.yml` 是议题模板选择器的配置**。PR 多模板走 `template` **查询参数** |
| 20 | "PR 模板会自动成为强制要求" | 它只是**填入正文框的默认值**，用户可以编辑。而且**必须合并进默认分支后才生效** |
| 21 | "CODEOWNERS 的匹配谁先写谁生效" | 相反：官方原文 **"the last matching pattern takes the most precedence"** —— **最后匹配的生效** |
| 22 | "同一模式写多行可以列出多个 owner" | **必须写在同一行**。分多行只有**最后一个** owner 生效 |
| 23 | "CODEOWNERS 支持 `!` 取反、`[]` 范围、`\#` 转义" | 官方明确这三样**在 CODEOWNERS 中无效**（与 gitignore 的差异） |
| 24 | "团队成员有 Write 权限，团队就能当 code owner" | **不够**。团队必须**可见且本身被显式授予 Write**；且只有**组织团队**可用，企业团队不支持 |
| 25 | "指定了 code owner 就会自动请求评审" | 会——但**草稿 PR 不会**；且若权限不足/文件超 3 MB/不在基础分支上，都是**静默不生效** |
| 26 | "Require review from Code Owners 要求所有 owner 批准" | **任意一位批准即可**满足要求 |
| 27 | "CODEOWNERS 一旦配置就安全了" | **它自身必须被某个 owner 覆盖**，否则任何有 Write 权限的人都能改它 —— 这是一条自我授权路径 |
| 28 | "审查者应该要求代码达到完美" | Google 原文：**"不存在完美的代码 —— 只有更好的代码"**，应追求**持续改进**；批准标准是"**确实改善整体代码健康度**，即使不完美" |
| 29 | "审查意见都同等重要，作者应全部照改" | 不重要的应加 **`Nit: `** 前缀，让作者知道**可以选择忽略** |
| 30 | "代码审查的响应时间没有明确要求" | Google 的原文给了具体上限：**一个工作日**；且强调**单次响应快**比整个流程快更重要 |
| 31 | "流程太重是流程设计的问题" | Google 原文：**"大多数关于代码审查流程的抱怨，实际上都能通过让流程变快来解决"** |
