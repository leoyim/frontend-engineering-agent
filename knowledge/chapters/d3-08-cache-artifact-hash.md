## 8.1 三层缓存在同一条链上

先把三层的**位置**摆清楚。它们不是三种不同的技术，而是**同一条交付链上的三个存储点**：

```
构建（磁盘）  →  产物上传  →  CDN（边缘）  →  浏览器（本地）
   缓存构建结果              缓存响应副本        缓存响应副本
```

| 层 | 缓存什么 | 谁能命中 | 命中后省掉什么 |
|---|---|---|---|
| **构建** | 模块的转换结果 | **你的下一次构建**（或 CI 的下一个 job） | 重复的解析与转换（第 5 章 §5.4 / 第 7 章 §7.2） |
| **CDN** | 产物的响应副本 | **该边缘节点覆盖的所有用户** | 回源与跨地域传输 |
| **浏览器** | 产物的响应副本 | 单个已访问过的用户 | **整次请求** |

### 三层共用同一个前提

**这是本章的核心命题**：

> **三层缓存都要求"URL 与内容绑定"。** 只要这个前提被动摇，三层会**同时**失效。

具体地说，三层各自的失效判断**互相独立**：

| 层 | 它怎么判断"能不能用旧的" |
|---|---|
| 构建 | 该模块的输入与配置是否变过 |
| CDN | 缓存键（通常就是 URL）+ 缓存策略是否允许复用 |
| 浏览器 | 同一套 HTTP 语义（`D0` 第 6 章） |

**但它们判断的对象是同一个字符串 —— URL。** 所以只要"内容变了但 URL 没变"（或反过来"内容没变但 URL 变了"），三层就会**一起做出错误决定**：

| 错误 | 后果 |
|---|---|
| **内容变了、URL 没变** | 三层都继续用旧副本 → **用户拿到旧代码**（最严重） |
| **内容没变、URL 变了** | 三层全部弃用 → **本可复用的缓存全部作废**（只是浪费，不致命） |

**第一种是事故，第二种是成本。** 而两者**都源自同一件事：URL 没有忠实地反映内容。**

**Hash 稳定性（§8.2）治的正是第二种**，而第一种靠"文件名必须变"来保证。**这两件事是同一个机制的两面** —— 这就是为什么 hash 那节必须单独成节。

### 三层的失效条件对照

| 层 | 主要失效来源 | 治理动作 |
|---|---|---|
| **构建** | `buildDependencies` 未覆盖配置变更 / `cache.version` 未随配置语义升 / `maxAge` 过期 / **CI 绝对路径变化** / `npm ci` prune | 第 5 章 §5.4；第 7 章 §7.5 阈值 1–3 |
| **CDN** | 产物被删（新部署替换旧 assets） / 缓存键不含版本 / 回源策略 | 产物**不删除历史版本**；HTML 不缓存（见下） |
| **浏览器** | 强缓存未过期 / 协商缓存判定复用 | 带内容 hash 的文件名 + 长 `max-age` |

**⚠️ 一句话必须在三处都出现**：**`index.html` 不能长缓存。**

Vite 官方在部署相关说明里给的对策是：**对 HTML 设置 `Cache-Control: no-cache`**，并监听 **`vite:preloadError`** 事件（第 3 章 §3.5 已核验）。

**原因是结构性的**：hash 文件名解决的是"**这个文件的内容永不变**"，但**"旧 HTML 指向已被删除的文件"**这件事，只能靠"**HTML 每次都要问服务器**"来解决。所以：

| 文件 | 缓存策略 | 理由 |
|---|---|---|
| 带 hash 的 JS / CSS / 图片 | **强缓存、超长 `max-age`** | 内容与 URL 绑定，永不变 |
| `index.html` | **`no-cache`**（每次协商） | 它是"当前该加载哪些 hash 文件"的唯一索引 |
| `manifest.json` 一类 | 短缓存或按需 | 同上，属于索引而非内容 |

**这条的分工不能颠倒**：如果 HTML 被长缓存，那么"新部署"对已访问用户**根本不生效** —— 他们会一直加载旧 HTML，而旧 HTML 指向的旧 assets 已被删除，于是**白屏**。

### 与 D6 的边界

本章到"构建侧该输出什么"为止：

| 本章负责 | D6 负责 |
|---|---|
| 产物文件名是否带 hash | CDN 的缓存键与回源策略 |
| 产物结构（chunk 数量与边界） | 部署方式（滚动 / 蓝绿 / canary） |
| 是否保留历史版本 | 缓存失效的运维手段 |
| HTML 不缓存这条**要求** | HTML 响应头**怎么配** |

## 8.2 Hash 稳定性：长缓存的地基

### 什么叫"稳定"

一个可用的构建，应该满足这条性质：

> **输入不变 → 产物逐字节相同（包括文件名里的 hash）。**

这条性质有个名字：**确定性构建（deterministic build）**。它不是"优化"，而是**长缓存能不能成立的前提**。

### 为什么这条这么脆弱

因为产物里的 hash **不只是内容的函数** —— 它经常被一些"与内容无关"的东西污染。

**四个成因**（从机制推出，均可验证）：

| # | 成因 | 机制 |
|---|---|---|
| **1** | **id 分配策略不稳定** | 用序号（`natural`）时，**增删一个模块会让后面所有序号漂移**（第 1 章 §1.4 的默认值表） |
| **2** | **模块顺序不稳定** | 遍历顺序若依赖文件系统的返回顺序或并发完成顺序，每次可能不同 |
| **3** | **构建元信息进了产物** | 构建时间戳、随机数、`process.env` 的值被内联进代码 |
| **4** | **绝对路径进了产物** | 不同机器/不同目录构建，产物里带着不同路径（第 5 章 §5.4 的 CI 缓存坑同源） |

**这四条里，第 1 条是官方直接给了配置项的**：

| `mode` | `chunkIds` | `moduleIds` |
|---|---|---|
| `development` | `'named'` | `'named'` |
| `production` | **`'deterministic'`** | **`'deterministic'`** |
| `none` | `'natural'` | `'natural'` |

**`'deterministic'` 的语义是"稳定的确定性短标识"** —— 内容不变，标识不变。而 **`'natural'` 是自然递增序号**，**增删模块会让后面所有序号漂移**。

**⚠️ 一个容易踩的组合**：`mode: 'none'` 时两者都是 **`'natural'`**。所以"我不想让 mode 帮我设默认值，我自己配"的人，**会无意中拿到最不稳定的 id 策略**。

**这条是本章最实用的一条**：**如果你为了完全手动控制而设 `mode: 'none'`，必须显式把 `moduleIds` 与 `chunkIds` 设为 `'deterministic'`。**

### 拆得越碎，hash 不稳的代价越大

这是本节最值得单独讲的一条推论。

**假设一个极端情形**：100 个 chunk，每个 chunk 的 hash 里都包含"它依赖的 chunk 的 id 列表"。此时**一次 id 漂移会让所有引用它的 chunk 的 hash 全变** —— 这就是**级联缓存失效**。

| 结构 | 一次 id 漂移的影响 |
|---|---|
| 1 个大 chunk | 1 个文件失效 |
| 10 个 chunk | 可能 10 个全失效（因为互相引用） |
| 100 个 chunk | **可能 100 个全失效** |

**所以"拆更多 chunk"不是纯粹的好事**：它降低单次失效的**范围**（只重下改动的那个），但同时**放大了级联失效的概率**（链更长）。

**Vite 官方正在探索的解法**值得记：`build.chunkImportMap`（**实验性**）—— 生成 import map 把 **chunk ID** 映射到 URL，让 chunk 内的 import 语句**用 ID 而非 URL**，从而**避免级联缓存失效**。官方还注明它的限制：**"目前不适用于 CSS 与 assets"**，且失效不会级联（第 3 章 §3.5 已核验）。

**这个方案的思路是**：**把"引用"与"地址"解耦**。文件改名时，只改 import map，不改引用方 —— 于是引用方不需要重新下载。

### 怎么验证

**不需要任何工具，两次构建就够**：

```text
1. 清理产物目录与构建缓存
2. 完整构建一次，记录所有产物的文件名（含 hash）
3. 不做任何改动，再完整构建一次（同样清理缓存）
4. 逐项比对文件名
```

**三种结果的解读**：

| 结果 | 说明 |
|---|---|
| 文件名**完全一致** | hash 稳定（在当前配置与机器下） |
| 文件名**不一致** | 有 ≥1 个不稳定成因，按 §8.2 的四条排查 |
| 同一机器稳定、**换机器就不稳定** | 指向成因 4（绝对路径）或依赖版本差异 |

**⚠️ 一个必须点明的边界**：**"两次构建一致"不等于"永远稳定"** —— 它只证明在**当前配置、当前依赖版本、当前机器**下稳定。**加一个新依赖、改一个配置、换一台机器，都可能打破它。** 所以这条验证应该进入 CI（第 7 章 §7.4 第 6 步的"设阈值复核"）。

### 三种 hash 的范围

Webpack 官方在 Under The Hood 页给出的 `[contenthash]` 是**按该资源内容**计算（并注明算法为 `md4`）。而社区常说的三种要区分清楚：

| 占位符 | 范围 | 适用 |
|---|---|---|
| `[fullhash]`（旧称 `[hash]`） | **整次编译** | **不适合长缓存** —— 任一模块变动全部失效 |
| `[chunkhash]` | 单个 chunk | 尚可，但 chunk 边界一动就变 |
| **`[contenthash]`** | **该文件内容** | **长缓存的正解** |

**"三种里选哪个"的判据很简单**：**你希望"什么不变时文件名不变"**。

- 希望"**这个文件的内容**不变时不变" → `[contenthash]`；
- 希望"整个构建"不变时不变 → 那等于放弃长缓存。

**⚠️ 一处诚实的缺口**：**Vite 的文件名占位符（`[hash]` / `[name]` / `[ext]`）在本次核验的 Vite 页面里没有出现** —— Build Options 页把 `entryFileNames` / `chunkFileNames` / `assetFileNames` 指向 **Rolldown options 文档**（第 3 章 §3.6 已标注）。**本书因此不给 Vite 侧的占位符清单**，需要时请查 Rolldown 文档。

## 8.3 产物层优化：体积与结构

`D3.L4.04`。产物优化有**两个正交的维度**，混起来谈会导致"优化了体积但缓存变差"。

| 维度 | 优化什么 | 主要手段 | 反作用 |
|---|---|---|---|
| **体积** | 传输与解析的字节数 | 摇树、压缩、内联阈值（第 3 章 §3.4–§3.6） | 内联会让资源失去独立缓存 |
| **结构** | 文件数量与边界 | 代码分割（第 3 章 §3.5） | 拆太细 → 请求数与级联失效 |

**本节不重复前三章的手段**，只讲**治理：怎么定阈值、怎么判断方向对不对**。

### 体积：三个常见的错误方向

| 错误方向 | 为什么错 | 正确做法 |
|---|---|---|
| **只看主包体积** | 主包小了但总传输量变大（公共依赖被复制进多个 chunk） | 看**总请求字节数**，并检查公共依赖是否重复（第 3 章 §3.5 的 `splitChunks` 体积阈值） |
| **只看 gzip 后** | 解压后的大小影响**解析与执行**，而 gzip 后的大小只影响**传输** | 两个数都要看，但**关注的指标不同** |
| **把所有能内联的都内联** | base64 让体积**涨约三分之一**，且**失去独立缓存** | 按 §8.4 的阈值表决定，而不是"越小越内联" |

**第二条值得展开一点**：

| 指标 | 影响什么 | 由谁决定 |
|---|---|---|
| **传输大小**（gzip / brotli 后） | 首屏等待 | 压缩算法（第 3 章 §3.6） |
| **解压后大小** | 解析时间、内存占用（尤其移动端） | 代码量本身（摇树、分割） |

**所以"gzip 后只有 200KB"不能证明产物健康** —— 它可能解压后是 2MB，在低端设备上解析要一秒以上。

### 结构：太少与太多都是问题

| 结构 | 症状 | 后果 |
|---|---|---|
| **太少**（一个大包） | 改一行 → **整个包失效** | 每次发版用户都要重下全部 |
| **太多**（碎片化） | 首屏请求数爆炸、**hash 级联失效** | 首屏更慢；一次改动可能让大量文件失效（§8.2） |

**"刚好"的判据不是文件数，而是两个可测的东西**：

| 判据 | 怎么量 | 健康的含义 |
|---|---|---|
| **改一个业务模块后，失效的文件数** | 连改两次，比对产物文件名变化数量 | **只失效 1–2 个文件**（该模块 + 可能一个入口索引） |
| **首屏需要加载的文件数** | 首屏网络面板 | 在可接受范围内（与第 7 章 §7.5 阈值 7 联动） |

**第一条判据比"chunk 数量"有用得多**，因为它直接量的是**用户要重下多少**。

### 一个经常被忽略的产物层决策：内联阈值

第 3 章 §3.6 已核验：Vite 的 `build.assetsInlineLimit` 默认 **4096**（4 KiB），**设为 `0` 关闭内联**（**`false` 不是文档化类型**）；`build.lib` 下该选项被忽略、资源始终内联。

**治理层的补充判断**：内联阈值的本质是一个**权衡**：

| 阈值偏好 | 收益 | 代价 |
|---|---|---|
| 调大 | 少几个请求 | 体积涨约 1/3；**失去独立缓存**（随宿主文件一起失效） |
| 调小 / 归零 | 可独立缓存、体积小 | 请求数增加 |

**所以它不是"性能选项"，而是"缓存策略选项"** —— 这个认知转变很重要：**在多页或高频发版的项目里，内联会显著放大"每次发版用户要重下的量"**，因为被内联的资源**无法单独命中缓存**。

## 8.4 治理动作：六个判定阈值

与第 7 章同体例。**全部是起点值，需按项目基线校准。**

### 判定表

| # | 现象 | 判定阈值（起点值） | 动作 | 依据 |
|---|---|---|---|---|
| 1 | 发版后用户还在用旧代码 | **任意一次发版后 30 分钟内仍有旧版本请求** | 先查 `index.html` 的缓存策略（必须 `no-cache`） | §8.1 |
| 2 | 发版后部分用户白屏 | **出现 `vite:preloadError` 或资源 404** | 产物**不要删除历史版本**；配 `preloadError` 兜底 | §8.1 |
| 3 | 改一行代码，用户要重下很多文件 | **单次改动导致失效文件数 > 5** | 查 `moduleIds` / `chunkIds` 是否 `deterministic`；再查 chunk 粒度是否过碎 | §8.2 |
| 4 | 同样的输入，两次构建 hash 不同 | **连续两次构建产物文件名不一致** | 按四个成因排查（id 策略 / 顺序 / 元信息 / 绝对路径） | §8.2 |
| 5 | 主包看着不大，但总量很大 | **公共依赖在 ≥2 个 chunk 中重复出现** | 查 `splitChunks` 的体积阈值（默认会跳过小依赖）；不要把公共依赖复制进每个 chunk | §8.3 |
| 6 | 首屏在小屏设备上卡 | **解压后首屏 JS > 1 MB** | 看解压后而非 gzip 后；用动态导入收敛首屏依赖 | §8.3 |

### 三条使用说明

**① 阈值 1 与 2 是"事故类"，优先级高于其余四条。**

它们不是性能问题，而是**正确性问题**：用户拿到旧代码或白屏，**功能就是坏的**。所以这两条的排查顺序应当排在所有性能项之前。

**② 阈值 3 与 4 是同一个机制的两个观测面。**

- 阈值 4（hash 不稳）是**因**；
- 阈值 3（失效文件多）是**果**。

**先修因再修果**：如果 hash 本身不稳，那么"调整 chunk 粒度"只是在减少受害者数量，不是在解决根因。

**③ 阈值 5 与 6 容易互相掩盖。**

把公共依赖复制进每个 chunk，会让**主包变小**（阈值 5 的"看着不大"）—— 但总量变大。所以**永远看总量，不看主包**。这条与第 3 章 §3.5 的"`splitChunks` 解决重复、不解决冗余"是同一件事的两个说法。

### 什么时候"不该动产物结构"

| 情况 | 为什么不该动 |
|---|---|
| **hash 本身不稳定** | 先修 §8.2 的四个成因；否则结构怎么调都在漏 |
| **没有视觉回归与端到端测试** | 改 chunk 边界会改变**加载顺序**，而顺序可能影响行为（第 6 章 §6.5 的 CSS Module 排序问题） |
| **总量在可接受范围** | 拆分的收益（缓存粒度）小于代价（请求数、级联失效） |
| **只在开发环境观察** | 摇树、CSS 抽取、`deterministic` id **都只在生产模式显现**（第 5 章 §5.5） |

**最后一条是本章与第 5 章的直接接口**：**产物层的任何判断，都必须在 `mode: 'production'` 下做。**

## 8.5 动手

**每一项都要求说出理由**：

| 任务 | 验收 |
|---|---|
| 为你的项目画出三层缓存的链条，标出每一层"存在哪里" | 说出哪一层命中后省掉的是什么（构建时间 / 回源 / 整次请求） |
| 查一次你项目的 `index.html` 响应头 | 说出它是否 `no-cache`；若不是，说明会发生什么（§8.1 的第一种错误） |
| 清空缓存连续构建两次，逐项比对产物文件名 | 说出结果属于"稳定 / 不稳定 / 换机器才不稳定"哪一种 |
| 故意把 `moduleIds` 改成 `'natural'`，再重复上一步 | 说出为什么它不稳定，以及 `mode: 'none'` 下的默认值是什么 |
| 用 `mode: 'none'` 构建一次，检查 `moduleIds` / `chunkIds` 的实际取值 | 说出"为了手动控制而关 mode"会带来什么风险 |
| 改一个业务模块，统计产物文件名变化数量 | 用阈值 3 判断是否过碎；若过多，先查 hash 稳定性再查粒度 |
| 检查产物里有没有构建时间戳或绝对路径 | 说出这分别属于四个成因中的哪一条 |
| 找一个公共依赖，检查它出现在几个 chunk 里 | 用阈值 5 判断；并说明"主包小"为什么不能作为健康证明 |
| 对比同一个产物的 gzip 后与解压后大小 | 说出两者各自影响什么（传输等待 vs 解析与内存） |
| 把 `assetsInlineLimit` 从默认改为 `0`，对比产物 | 说出请求数、体积、独立缓存三者各怎么变 |
| 按 §8.4 判定表逐条过一遍你的项目 | 标出命中哪几条、哪几条属于"事故类"应优先处理 |

**进阶挑战**（任选一项）：

1. **把确定性构建变成 CI 门禁**：连续两次构建，比对产物文件名集合，不一致即失败。要求报告里输出**哪几个文件不一致**，并按四个成因给出排查提示。
2. 给你的项目做一份**"发版影响面"报告**：一次典型改动会让多少文件失效、用户需重下多少字节。然后用它验证"拆分是否过度"。
3. 把 §8.1 的三层缓存 × §8.2 的四个成因做成矩阵：**每个成因分别会让哪几层失效**。这张表的价值在于：**它把"缓存不生效"从模糊抱怨变成了分层定位**。

## 8.6 本章常见误区

| # | 误区 | 纠正 |
|---|---|---|
| 1 | "文件名带 hash 就万事大吉" | 还要**HTML 不缓存**。否则旧 HTML 指向已删除的旧产物 → 白屏 |
| 2 | "产物带 hash 了，历史版本可以随手删" | 已访问用户手里的旧 HTML **仍指向旧产物**。删除会造成 404 / 白屏 |
| 3 | "hash 变了只是文件名变了，无所谓" | 它是**成本**：三层缓存全部作废。而"内容变了 hash 没变"是**事故** |
| 4 | "默认配置下 hash 一定稳定" | 不一定。`mode: 'none'` 下 `moduleIds` / `chunkIds` 是 **`'natural'`**（序号），增删模块会全体漂移 |
| 5 | "`mode: 'none'` 只是不设默认优化，更干净" | 它会让 id 策略落到**最不稳定**的 `'natural'`。要手动控制就必须显式设 `deterministic` |
| 6 | "同一份代码两次构建结果一定一样" | 四个成因都会破坏它：id 策略、模块顺序、构建元信息、**绝对路径** |
| 7 | "在本机构建稳定就够了" | **换机器可能不稳定**（绝对路径）。这正是 CI 缓存失效的同源问题 |
| 8 | "拆更多 chunk 总是更好" | 它降低单次失效**范围**，但**放大级联失效概率**（链更长）。§8.2 的判据是"失效文件数"，不是 chunk 数 |
| 9 | "`[hash]` / `[chunkhash]` / `[contenthash]` 差不多" | `[fullhash]` 是**整次编译**，任一模块变动全失效；**长缓存必须用 `[contenthash]`** |
| 10 | "Vite 侧也能照抄 webpack 的占位符清单" | **本次核验的 Vite 页面没有给出占位符**（指向 Rolldown 文档）。不要凭印象写 |
| 11 | "gzip 后很小就没问题" | gzip 后大小只影响**传输**；**解压后**大小影响**解析与内存**（尤其低端设备） |
| 12 | "内联越多越快" | base64 让体积**涨约 1/3**，且**失去独立缓存**。它是**缓存策略选项**，不是纯性能选项 |
| 13 | "`assetsInlineLimit: false` 可以关闭内联" | 官方只记载 **`0`**，类型里没有 `boolean`（第 3 章 §3.6） |
| 14 | "产物结构可以在开发环境调" | 摇树、CSS 抽取、`deterministic` id **只在生产模式显现**。必须用 `mode: 'production'` 判断 |
| 15 | "缓存三层都归构建工具管" | 构建只管第一层与"文件名该长什么样"。CDN 配置与部署策略属 **D6** |
| 16 | "改 chunk 边界不影响行为" | 会影响**加载顺序**，而顺序可能影响行为（第 6 章 §6.5 的 CSS Module 排序）。**没有视觉回归就不要动** |
