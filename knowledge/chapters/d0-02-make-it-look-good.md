## 2.1 选择器与层叠：样式是怎么"赢"的

先建立一个正确的心智模型：

> **CSS 不是指令式代码，而是一组"声明"。浏览器为每个元素收集所有匹配到它的声明，然后按规范定义的排序规则挑出胜者。**

所以"样式没生效"从来不是"没写对"，而是"**写的这条排在了后面**"。

### 一、匹配方向：规范不管，实现反向

```css
.card .title a { color: blue; }
```

**先澄清一个常见说法**：Selectors Level 4 只定义"某个选择器**是否匹配**某个元素"，**并不规定怎么匹配**。所以"从右往左匹配"**不是规范要求，而是浏览器实现为了剪枝采用的策略**：

```text
实现的实际做法：找到所有 <a> → 逐个向上看祖先里有没有 .title → 再向上看有没有 .card
```

**为什么这样更快**：文档里 `<a>` 的数量通常远少于"整棵树的节点数"，从数量少的一端出发能最快排除不匹配的元素；若从左往右，`.card` 匹配后还要遍历它的整棵子树。

这条知识带出一个实践结论：**右边那一段（key selector）越具体，越容易被快速排除**。`.list li` 比 `li.list` 慢——前者要先遍历所有 `li` 再回溯，后者只需遍历 `li` 就能直接判断。

> **注意区分**："规范要求什么"与"实现怎么优化"是两件事。性能结论依赖后者，而正确性结论只依赖前者。

### 二、特异性：三元组**按位比较**，不是分数相加

Selectors Level 4 的《Calculating a selector's specificity》把每条选择器算成一个三元组 `(A, B, C)`：

| 位 | 计入什么 | 例子 |
|---|---|---|
| **A** | ID 选择器数量 | `#header` |
| **B** | class、属性选择器、伪类 | `.card` `[type=text]` `:hover` |
| **C** | 元素类型、伪元素 | `div` `::before` |

**比较方式是从左到右逐位比较，先分出胜负即停止。**

这一点常被讲错。"ID 算 100 分、class 算 10 分"是**错误模型**，因为按分数算：

```text
11 个 class → 110 分
1 个 id     → 100 分
→ 会得出"11 个 class 赢"   ← 错
```

按正确的按位比较，`(0,11,0)` 与 `(1,0,0)` 在第一位就分出胜负：**ID 赢**。位数之间不进位、不相加。

```css
#id .a .b .c .d .e .f .g .h .i .j .k { color: red; }  /* (1,11,0) 赢 */
.a .b .c .d .e .f .g .h .i .j .k .l   { color: blue; } /* (0,12,0) 输 */
```

> 顺带一提：通配符 `*` 与组合符（空格、`>`、`+`、`~`）**不 contributed 任何位**。

### 三、层叠排序：规范定义了六步

CSS Cascading and Inheritance Level 5 的《Cascade Sorting Order》规定的判定顺序是：

```text
① 来源与重要性（Origin and Importance）
② 上下文（Context，用于作用域封装）
③ 元素附着样式（Element-Attached Styles，即 style="…"）
④ 层（Layers，即 @layer）
⑤ 特异性（Specificity）
⑥ 出现顺序（Order of Appearance，后者胜）
```

**关键：特异性只是第五步。** 很多"我特异性更高为什么不生效"的问题，答案都在前四步。

**第 ① 步「来源与重要性」的优先级，从低到高：**

| 顺序 | 来源 |
|---|---|
| 1 | 浏览器默认样式（UA） |
| 2 | 用户样式表 |
| 3 | **你的 CSS**（作者，普通声明） |
| 4 | CSS 动画 |
| 5 | **作者 `!important`** |
| 6 | 用户 `!important` |
| 7 | UA `!important` |

**`!important` 的作用是让顺序反转**：普通声明里作者高于用户，加上 `!important` 后用户反过来高于作者（这是为了保障用户的无障碍偏好能覆盖站点样式）。滥用它等于跨来源越级，后续只能靠更高的 `!important` 压回去。

**第 ③ 步的存在解释了一个细节**：内联样式（`style="…"`）**不是靠"特异性极高"取胜，而是单独的第三步**——所以它能压过任何外部选择器，但仍然压不过作者来源的 `!important`（那是第 ① 步的胜负）。

`@layer` 是近年新增的排序维度，用于把样式表按层组织、显式控制优先级，从而摆脱"靠堆特异性取胜"的历史包袱。

### 四、与渲染管线的接点：样式计算是第 ③ 阶段

回看D0 第 1 章 §1.1 的管线。**上面这套"选择 → 排序 → 挑胜者"的过程，就是管线第 ③ 阶段「样式计算」的输入部分。**

```text
第 ③ 阶段的三类输入：
  ① 层叠排序后胜出的声明
  ② 继承（可继承属性从父元素取计算值）
  ③ 初始值（都没有时用规范定义的值）

→ 输出：每个节点的「计算后样式」（computed style）
```

由此可以推出两条与性能直接相关的结论（D0 第 5 章展开）：

| 结论 | 机制 |
|---|---|
| **改一个类名或加一条规则，会触发「重算样式」** | 第 ③ 阶段要重跑 |
| **它不一定触发布局** | 只有当计算后样式里的**几何相关属性**变了，才会进入第 ④ 阶段 |

**"重算样式（Recalculate Style）"在 Performance 面板里是独立一块紫色**——它比绘制便宜、比合成贵，量级取决于受影响的元素数量。

### 五、继承：不是"自动复制"，而是"属性挑值时的回退"

并非所有属性都继承。规范按属性性质区分：

| 类别 | 例子 | 是否继承 |
|---|---|---|
| **可继承**（影响文字流） | `color` `font-*` `line-height` `letter-spacing` `text-align` `visibility` | 是 |
| **不继承**（影响盒子本身） | `width` `height` `margin` `padding` `border` `background` `display` | 否 |

四个全局关键字：

| 值 | 含义 |
|---|---|
| `inherit` | 取父元素的计算值 |
| `initial` | 回到该属性**规范的**初始值（不是"浏览器默认值"） |
| `unset` | 可继承属性等同 `inherit`，不可继承属性等同 `initial` |
| `revert` | 回退到**上一层来源**（如从你的样式回退到 UA 样式）——这一条正是第 ① 步来源概念的直接应用 |

> **动手**：写一个 `.card` 规则与一条 `#main .card` 规则，让它们给同一元素上色，观察谁胜；再把低特异性的那条放进 `@layer` 试试，体会"层"抢在"特异性"之前生效。

## 2.2 盒模型：尺寸到底由谁决定

### 四个盒子

CSS Box Model 把一个元素抽象成四层同心矩形：

```text
┌─ margin（外边距，透明，不计入背景）
│ ┌─ border（边框）
│ │ ┌─ padding（内边距）
│ │ │ ┌─ content（内容区）
```

`width` / `height` 指哪一层，取决于 `box-sizing`——**而它的默认值恰好与解析模式有关**：

| `box-sizing` | `width: 200px` 表示 | 实际占位 |
|---|---|---|
| `content-box`（标准模式默认） | 仅内容区 = 200px | 200 + padding + border |
| `border-box` | 内容 + padding + border = 200px | 200px |

**回到D0 第 1 章 §1.1**：在怪异模式（quirks）下，浏览器退回 1990 年代实现，`width` 的行为等价于 `border-box`。所以"不写 DOCTYPE 会错版"和"加 `box-sizing: border-box` 就好了"讲的是**同一个盒模型分歧**，只是一个由解析模式决定、一个由 CSS 显式声明。

现代项目的通行做法是全局切换：

```css
*, *::before, *::after { box-sizing: border-box; }
```

**这不是"更好的写法"，而是一次明确的取舍**：换成 `border-box` 后，设定 `width` 的元素加 `padding` 会压缩内容区而不是撑大盒子——更符合"我要它总共这么宽"的直觉。

### 百分比参照谁：包含块（containing block）

`width: 50%` 的 50% 是相对**包含块的内容区**算的。包含块的定义随定位方式变化（由 CSS Display 与 CSS Positioned Layout 共同定义），这是很多"百分比不管用"问题的源头：

| 元素的定位方式 | 包含块是谁 |
|---|---|
| `static` / `relative` | 最近的**块级容器**的内容区 |
| `absolute` | 最近的**已定位**（`position` 非 `static`）祖先的**内边距框** |
| `fixed` | 视口（有例外，见 本章 §2.5） |
| `sticky` | 最近的滚动祖先 |

另外：**`height: 50%` 只在父元素有确定高度时才生效**。父元素高度是 `auto` 时，它的高度依赖子元素内容——子元素反过来参照它形成循环，规范直接规定此时百分比高度按 `auto` 处理。

### margin 折叠：CSS Box Model 的《Collapsing Margins》

**两个相邻的垂直外边距不会相加，而是合并为一个，取其中较大者。**

```html
<p style="margin-bottom: 20px">第一段</p>
<p style="margin-top: 30px">第二段</p>
<!-- 间距是 30px，不是 50px -->
```

三种折叠情形：相邻兄弟之间、父元素与第一个/最后一个子元素之间、空的块级元素自身。

**为什么会有这个设计**：为了让"段落间距"符合排版直觉——每段都写 `margin: 1em 0` 时，段间应是 1em 而不是 2em。

**以及它何时不适用**（这部分更该记住，因为折叠出问题通常在这里）：

| 情形 | 是否折叠 | 依据 |
|---|---|---|
| 元素有 `padding` / `border` 隔开 | 不折叠 | 有明显分隔 |
| 建立了新的格式化上下文（如 `display: flow-root`） | 不折叠 | CSS Display 的格式化上下文规则 |
| **Flex / Grid 容器的子项** | **不折叠** | 它们不参与块级格式化上下文的折叠 |
| 浮动 / 绝对定位元素 | 不折叠 | 已脱离正常块流 |

最后一行是现代布局的一大好处：**用 Flexbox 或 Grid 排布时，不需要再和 margin 折叠打交道。**

### 单位：`em` 与 `rem` 的差别是"参照谁"

CSS Values and Units 定义的单位体系，关键在参照对象：

| 单位 | 参照 | 典型用途 |
|---|---|---|
| `px` | 绝对（CSS 像素，不等同物理像素） | 边框、阴影 |
| `em` | **当前元素的** `font-size` | 与字号联动的间距 |
| `rem` | **根元素**的 `font-size` | 全局间距、字号体系 |
| `%` | 包含块（宽度）或自身字号（当用于 `font-size` 时） | 栅格 |
| `vw` / `vh` | 视口宽 / 高的 1% | 全屏区块 |
| `ch` | 字符 `0` 的宽度 | 文本列宽 |

注意 `px` 那一行的措辞：**`px` 是 CSS 像素，不是物理像素**。两者的比值就是**设备像素比**（本章 §2.6）。

**`em` 的"层层放大"是有原因的**：它参照当前元素的 `font-size`。父元素 `font-size: 1.2em`、子元素也写 `1.2em`，就会逐层连乘。`rem` 恒定参照根元素，正是为了规避这一点——**这就是它被设计出来的理由**。

现代 CSS 还提供了取值函数，用来表达"中间尺寸"：

```css
h1 { font-size: clamp(1.5rem, 4vw, 2.5rem); }  /* 最小 1.5rem，最大 2.5rem，中间随视口 */
```

### 颜色：三套记法，各有用处

CSS Color 4 定义了多种记法：

| 记法 | 例子 | 何时用 |
|---|---|---|
| 关键字 | `red` `transparent` | 快速原型 |
| hex | `#1a73e8` | 从设计稿取色 |
| `rgb()` / `rgba()` | `rgba(26, 115, 232, .5)` | 需要透明度 |
| `hsl()` | `hsl(214 82% 51%)` | **手调色时**——色相、饱和度、亮度可独立调 |
| 现代色空间 | `oklch()` / `lab()` / `color()` | 感知更均匀的渐变与配色【待验证】各浏览器支持度持续变化，用前先查 |

**alpha 通道不等于 `opacity`**：`rgba()` 只影响该颜色本身；`opacity` 会让**整个元素及其子树**一起变透明——而且**它会创建层叠上下文**（本章 §2.5），这一点常被忽略。

### 与渲染管线的接点

| 改动 | 触发到管线哪一阶段 |
|---|---|
| 只改 `color` / `background-color` | 样式计算 → **绘制** |
| 改 `width` / `padding` / `font-size` | 样式计算 → **布局** → 绘制 |
| 只改 `transform` / `opacity`（已建层） | **合成**（可能完全跳过前两段） |

**判断方法**：问一句"这个属性会不会改变元素的**位置或尺寸**"。会 → 布局；不会但改变**可见效果** → 绘制；只改变**已有图层如何被摆放或混合** → 合成。D0 第 5 章会给出这张表的完整版本与测量方法。

## 2.3 Flexbox：一维布局的分配算法

### 它建立的是一种"格式化上下文"

**CSS Display** 的《Formatting Contexts》定义了各种布局模式各自的规则。`display: flex` 让容器**建立 flex 格式化上下文**——子元素成为 flex item，并按该上下文的规则排布。

**进入这个环境后，一批块级格式化上下文的规则会失效**——这是很多人"怎么不生效了"的根因：

| 老规则 | 在 flex 容器内 |
|---|---|
| `float` / `clear` | 无效果 |
| `vertical-align` | 无效果（改用 `align-items`） |
| 子项是块级还是行内 | 不再重要，统一变成 flex item |
| margin 折叠 | 不发生（本章 §2.2 的那张表） |

Flexbox 之前的水平排布方案——`float`、`display: inline-block`、`display: table`——都是**借别的机制来排版**，因此各自带着副作用。Flexbox 是**为布局而生的格式化上下文**。

### 主轴与交叉轴

Flex 是**一维**布局：它按一条轴分配空间。哪条是主轴由 `flex-direction` 决定，交叉轴与之垂直。

| `flex-direction` | 主轴 | `justify-content` 作用于 | `align-items` 作用于 |
|---|---|---|---|
| `row`（默认） | 水平 | 水平 | 垂直 |
| `column` | 垂直 | 垂直 | 水平 |

**理解这一点就能理解全部对齐属性**：`justify-*` 永远管主轴，`align-*` 永远管交叉轴，与"水平/垂直"没有绑定关系。

`align-content` 是第三个，只在**换行后有多行**（`flex-wrap: wrap`）时生效，管的是"多行之间的分布"。

### 空间分配算法：`flex-basis → grow → shrink`

CSS Flexible Box Layout Level 1 的《Flex Layout Algorithm》把确定一个 item 主尺寸的过程分成几步，简化后是：

```text
① 基准尺寸 = flex-basis（auto 则回退到 width / 内容尺寸）
② 剩余空间 = 容器主尺寸 − 所有 item 基准尺寸之和
③ 剩余为正 → 按 flex-grow 比例分配
   剩余为负 → 按 flex-shrink × 基准尺寸 加权收缩
④ 结果不低于 min-content（这是最容易踩的坑，见下）
```

`flex` 简写是这三个值的组合，最容易混淆的是 `flex: 1` 与 `flex: auto`：

| 写法 | 等价于 | 行为差异 |
|---|---|---|
| `flex: 1` | `1 1 0%` | 基准为 0，**完全按比例分**，内容多少不影响宽度 |
| `flex: auto` | `1 1 auto` | 先按内容尺寸做基准，**再分配剩余**，内容多的更宽 |

"两个盒子等宽"要用 `flex: 1`；"内容多的宽一些"才是 `flex: auto`。

### 坑：flex item 不会缩到内容以下

flex item 在主轴方向的 `min-width`（或 column 方向的 `min-height`）默认值是 **`auto`**，含义是：**它不会被压缩到小于内容的 min-content 尺寸。**

后果很典型——一个含长文本或长表格的行内布局会**撑破容器**，无论怎么调 `flex-shrink` 都没用。标准修法是显式放开这个下限：

```css
.item { min-width: 0; }        /* row 方向 */
.item { min-height: 0; }       /* column 方向 */
```

配合文本截断：

```css
.item { min-width: 0; }
.item > .text { overflow: hidden; text-overflow: ellipsis; white-space: nowrap; }
```

**这条坑的原理值得记住**：你遇到的不是"flex 不听话"，而是"`min-width: auto` 在按规范保护内容尺寸"。

### 与渲染管线的接点

Flex 布局发生在**管线的第 ④ 阶段（布局）**。所以：

- 改 `flex-basis` / `flex-grow` / 容器尺寸 → **必然触发布局**（比改颜色贵）。
- Performance 面板里的紫色 Layout 块，相当一部分来自这类改动（D0 第 5 章 §5.5）。
- 频繁改布局属性的动画天然昂贵——这也是"用 `transform` 做位移"的根本原因（本章 §2.5 会说明它为什么能跳过布局）。

> **动手**：做一个导航栏（左 logo、右菜单），分别用 `flex: 1` 与 `flex: auto` 写中间区域，观察不同内容长度下的差异。再把中间塞一段很长的英文单词，观察溢出，然后用 `min-width: 0` 修复。

## 2.4 Grid：二维布局

### 与 Flexbox 的分工

| | Flexbox | Grid |
|---|---|---|
| 维度 | 一维（一条主轴） | 二维（行与列同时定义） |
| 尺寸来源 | 内容与 flex 分配驱动 | **轨道定义驱动** |
| 适合 | 工具栏、导航、卡片内容排布 | 整页框架、卡片网格、仪表盘 |

两者建立的格式化上下文不同（CSS Display），**互补而非替代**。真实项目里常见的分层是：**Grid 搭页面骨架，Flexbox 排骨架内的行。**

### 显式网格与隐式网格

```css
.grid {
  display: grid;
  grid-template-columns: 200px 1fr;   /* 显式：定义了两列 */
  gap: 16px;
}
```

如果子项数量超出显式定义的行，Grid **不报错，而是自动创建"隐式"轨道**：

```css
grid-auto-rows: minmax(120px, auto);  /* 隐式行的尺寸规则 */
grid-auto-flow: row | column;          /* 自动填充方向 */
```

理解"显式 / 隐式"能解释一个常见困惑：**为什么只定义了两列，塞 10 个子项却排出了 5 行、而且行高不由我控制？** 因为那 5 行都是隐式行，受 `grid-auto-rows` 管辖。

### 轨道尺寸函数

| 写法 | 含义 |
|---|---|
| `200px` | 固定 |
| `1fr` | 剩余空间的 1 份 |
| `minmax(200px, 1fr)` | 最小 200px，最大分到剩余份额 |
| `auto` | 由内容决定（会吸收剩余空间） |
| `repeat(3, 1fr)` | 重复 3 次 |
| `repeat(auto-fill, minmax(200px, 1fr))` | **按容器宽度自动决定列数** |

最后一行是响应式网格的常用模式，也是"不用媒体查询就能自适应列数"的实现方式：

```css
.cards {
  display: grid;
  grid-template-columns: repeat(auto-fill, minmax(200px, 1fr));
  gap: 16px;
}
```

`auto-fill` 与 `auto-fit` 的差别在于"空轨道是否被折叠"：列数多于内容时，`auto-fill` 保留空列，`auto-fit` 把空列压掉、让现有内容摊开占满。

### `fr` 的分配机制，以及 `1fr` 为什么会被撑破

CSS Grid Layout Level 1 的《Track Sizing Algorithm》定义了轨道尺寸的求解过程。`fr` 的分配是**两段式**：

```text
① 先扣除固定轨道（px 等）与 gap
② 剩余空间按 fr 数量比例分配
```

关键在这里：**`1fr` 是 `minmax(auto, 1fr)` 的简写**——`fr` 的最小值隐含为 `auto`，而 `auto` 的最小值等于**内容的 min-content 尺寸**。所以：

```css
/* 一个含长英文单词或宽表格的网格项，会把列撑破 */
grid-template-columns: 1fr 1fr;

/* 标准修法：把最小值显式压到 0 */
grid-template-columns: minmax(0, 1fr) minmax(0, 1fr);
```

这与 本章 §2.3 的 `min-width: 0` 是**同一个机制**——"自动最小值保护内容，因此拒绝收缩"。记住这一点，大量响应式布局的溢出问题就能一眼定位。

### 与渲染管线的接点

Grid 与 Flex 同属**管线第 ④ 阶段（布局）**的不同布局模式。差别在于求解过程：Grid 要**同时**求解行与列（二维约束），所以在轨道数量多、约束复杂时，布局成本可能高于一维的 Flex。

> **动手**：用 Grid 做一个三栏页面骨架（头部 / 侧栏 + 主内容 / 页脚）。再做一个卡片网格，要求"容器变窄时列数自动减少"，且不得使用媒体查询。

## 2.5 定位与层叠上下文：脱离文档流之后

### 定位：CSS Positioned Layout 定义的参与方式

默认情况下，元素按 `display` 决定的方式参与**正常流**（normal flow）。`position` 的作用就是**改变元素在流里的参与方式**：

| `position` | 是否脱离正常流 | 偏移参照 |
|---|---|---|
| `static`（默认） | 不脱离 | 偏移属性无效 |
| `relative` | **不脱离**（原地占位） | 自身原位置 |
| `absolute` | **脱离**（不占位） | 最近的已定位祖先的内边距框 |
| `fixed` | **脱离** | 视口 |
| `sticky` | **不脱离**（原地占位） | 最近的滚动祖先 |

两个高频误解题：

**一、`relative` 没有"脱离"。** 它只是视觉上位移，原来占的位置仍然留着。所以"用 relative 调整布局"通常会留下空洞。

**二、`fixed` 的参照物不一定是视口。** 当祖先元素带有 `transform`、`filter`、`perspective`、`will-change`、`contain` 等属性时，该祖先会成为 `fixed` 的包含块。**这就是"固定定位突然不固定了"的原因**——通常来自某个祖先的动画或样式。

### `sticky` 为什么常常"不粘"

`sticky` 的规则是"滚动到阈值前保持原位，之后吸附"，但它有两个硬约束：

1. **需要滚动容器**——它相对最近的滚动祖先吸附。
2. **受父容器边界限制**——父容器滚出视口后，`sticky` 元素会被一起带走。

于是"设了 `sticky` 却不生效"的常见原因依次是：祖先链上某处有 `overflow: hidden`（把滚动容器换掉了）、元素高度等于父容器（没有可粘的空间）、父容器太矮。

### 层叠上下文：`z-index` 为什么有时不管用

这是 CSS 里最容易被误解的一处。核心事实是：

> **`z-index` 只在同一个层叠上下文内比较。不在同一个上下文里，`z-index` 数值大小毫无意义。**

**层叠上下文**由 CSS Positioned Layout 的《Stacking Contexts》定义。以下情形会**创建**它（常见项）：

| 触发条件 | 说明 |
|---|---|
| 根元素（`html`） | 全局根上下文 |
| `position` 为 `absolute` / `relative` **且** `z-index` 不是 `auto` | 经典组合 |
| `position: fixed` / `sticky` | 按现行定义无条件创建 |
| flex / grid item 且 `z-index` 不是 `auto` | 无需定位 |
| **`opacity` 小于 1** | 最容易"莫名其妙"的一条 |
| `transform` / `filter` / `clip-path` / `mask` 非 `none` | 动画经常触发 |
| `will-change` 指定了上述属性 | 为优化提前创建 |
| `isolation: isolate` | 显式隔离 |

**为什么调大 `z-index` 没用**：

```html
<div class="a">          <!-- z-index: 1，创建上下文 A -->
  <div class="a-child">  <!-- z-index: 9999 -->
</div>
<div class="b">          <!-- z-index: 2，创建上下文 B -->
</div>
```

`.a-child` 的 `9999` 只在**上下文 A 内部**有效。A 与 B 比较时用的是 `1` 与 `2`，所以 `.b` 依然盖住 `.a-child`。**子元素的 `z-index` 无法突破父级上下文的层级。**

同一个层叠上下文**内部**的绘制顺序（规范定义的绘制顺序，从下到上）：

```text
① 背景与边框（该上下文所属元素）
② 负 z-index 的子元素
③ 块级盒
④ 浮动盒
⑤ 行内盒 / 文本
⑥ z-index: auto 或 0 的定位元素
⑦ 正 z-index 的子元素
```

这就是"为什么文字总在背景之上""为什么负 `z-index` 的元素会跑到父元素背景下面"的答案。

### 与渲染管线的接点：层叠上下文 ≠ 合成层

这里必须澄清一个高频混淆：**层叠上下文与合成层（compositing layer）不是一回事。**

| | 层叠上下文 | 合成层 |
|---|---|---|
| 解决什么 | **绘制顺序**（谁在谁上面） | **合成阶段的独立处理单元** |
| 规范归属 | CSS Positioned Layout《Stacking Contexts》 | 浏览器内部实现 + CSS Transform / Compositing 相关规范 |
| 是否提升性能 | **不直接** | 是——独立层可只走合成，跳过布局与绘制 |

但两者有交集：`transform`、`opacity`、`will-change` 这些**既能创建层叠上下文、又常被浏览器用来提升为合成层**。所以"加 `transform` 做动画更流畅"成立，但原因不是"它创建了层叠上下文"，而是**它让改动只落在合成阶段**（D0 第 5 章 §5.1 的三种动画路径）。

**层不是越多越好**：每层都要内存与合成开销，滥用 `will-change` 反而更慢。

> **动手**：构造上文 `.a` / `.b` 的例子，验证子元素的 `z-index` 无法穿越父级上下文。再给 `.a` 加一个 `opacity: .99`，观察它是否也创建了上下文（提示：是的）。最后打开 DevTools 的 **Layer borders**，看它是否同时变成了合成层——**答案可能是"否"**，这正好说明两者不等价。

## 2.6 响应式：从设备像素到设计决策

### 三个视口与设备像素比

D0 第 1 章 §1.1 的 `viewport` 一行在此收尾。要分清三个"视口"：

| 概念 | 含义 |
|---|---|
| **布局视口** | CSS 中 `100%` 参照的宽度 |
| **视觉视口** | 用户当前看到的区域，可缩放 |
| **理想视口** | 布局视口等于设备宽度的那个状态（`width=device-width` 所设） |

以及一个关键比值（`devicePixelRatio` 定义在 **CSSOM View** 中）：

```text
设备像素比（DPR） = 物理像素 / CSS 像素
```

一台 DPR = 3 的手机上，1 个 CSS 像素由 3×3 个物理像素绘制。这解释了两件事：**为什么 `1px` 边框在高分屏上比期望粗**（它实际被渲染成 3 个物理像素）、**为什么需要按 `min-resolution` 之类的条件去换图**。

### 媒体查询：它是"求值"，不是"事件"

```css
@media (min-width: 768px) {
  .sidebar { display: block; }
}
```

媒体查询由 Media Queries Level 4 与 CSS Conditional Rules 定义。理解它的性质很重要：**它是样式表求值过程的一部分，浏览器在每次布局时重新判定**，不需要任何 JS 监听 `resize`。这带来两个好处：

- 页面在无 JS 时仍然响应式。
- 不存在"监听器没移除"之类的内存问题。

**但要注意它与管线的接点**：视口变化会让受影响的媒体查询重新求值 → **重新计算样式 → 重新布局 → 重绘**。这解释了"为什么 `resize` 很贵"，也解释了为什么D0 第 5 章会强调在 `resize` 回调里同步读几何属性是双重代价。

### 移动优先不是风格，是层叠规则的必然

CSS 的层叠规则是"**后写的覆盖先写的**"（在其余四步都相同时，即 本章 §2.1 的第 ⑥ 步）。所以样式表的组织顺序直接决定谁赢：

```css
/* 默认：面向小屏，不加任何查询 */
.card { padding: 12px; }

/* 屏幕变大时覆盖（注意用 min-width） */
@media (min-width: 768px) {
  .card { padding: 24px; }
}
```

这就是**移动优先**的机制解释：基础样式面向最小屏幕，用 `min-width` 逐级覆盖。反过来写（`max-width` 桌面优先）会不断"往下降级"，样式叠加顺序更容易失控。

| 写法 | 语义 | 效果 |
|---|---|---|
| `min-width: 768px` | "至少这么宽" | 移动优先，向上覆盖 |
| `max-width: 767px` | "最多这么宽" | 桌面优先，向后覆盖 |

### 断点应该由内容决定

不要让断点去凑设备型号（"iPhone 宽度是 375，那就断在 375"）。设备型号会过时，而**内容在什么宽度开始显得难看**是稳定信号。

做法是：把浏览器窗口从宽拖到窄，**观察内容在哪个宽度开始崩**，那个位置就是断点。

### 从"视口驱动"到"容器驱动"

媒体查询只能感知**视口**，无法感知**组件所在的容器**。同一个卡片组件放在窄侧栏和宽主区里，媒体查询给出的答案一样——这是长期存在的限制。**CSS Containment Level 3** 引入了**容器查询**：

```css
.card-container { container-type: inline-size; }

@container (min-width: 400px) {
  .card { grid-template-columns: 120px 1fr; }
}
```

它让组件按**容器**宽度自适应，从而真正可复用。【待验证】容器查询的浏览器支持度仍在演进，用前先查目标环境。

**注意它与管线的接点更细了**：容器尺寸变化只影响该容器子树内的样式求值，**不像媒体查询那样牵动全页**——这是它在工程上的真正价值。

### 逻辑属性与书写方向

多元语言场景下，`left` / `right` 是物理方向，会随书写方向出错。**CSS Logical Properties** 提供了替代：

| 物理属性 | 逻辑等价 |
|---|---|
| `margin-left` | `margin-inline-start` |
| `padding-top` | `padding-block-start` |
| `width` | `inline-size` |

新项目建议优先用逻辑属性，代价是必须理解"行内 / 块向"这对概念。（D0 第 7 章 §7.10 会补上 `dir="rtl"` 的场景。）

### 与渲染管线的接点

| 改动 | 管线阶段 |
|---|---|
| 视口尺寸变化 | 媒体查询重求值 → **样式计算 → 布局 → 绘制 → 合成** |
| 容器尺寸变化（容器查询） | 仅容器子树内 → 样式计算 → 布局 → 绘制 |
| 断点切换导致 `display` 变化 | 布局 + 绘制（可能整块子树） |

> **动手**：把 本章 §2.4 的卡片网格改成"移动优先 + 一个断点"的写法，并在浏览器里拖动窗口观察；再用 Performance 录制一次窗口拖动，**找出媒体查询重求值触发的那些紫色块**。

## 本章小结

**八条最该记住的结论**

1. **CSS 是"收集 → 排序 → 择一"的声明系统**。层叠排序由规范定义为**六步**：来源与重要性 → 上下文 → 内联样式 → 层 → 特异性 → 出现顺序。**特异性只是第五步。**
2. **特异性按位比较，不进位**。这条纠正了流传极广的"分数模型"。另外要区分"规范要求"与"实现优化"——反向匹配属于后者。
3. **样式计算是管线第 ③ 阶段**，输入是"层叠胜出的声明 + 继承 + 初始值"。改类名会触发重算样式，**但不一定触发布局**。
4. **`width` 的含义由 `box-sizing` 决定，而默认行为受解析模式影响**。`border-box` 是一次**取舍**，不是"更优写法"。
5. **`min-width: auto` 是布局溢出的头号来源**。Flex item 与 `1fr` 网格项都会"保护内容尺寸"，`min-width: 0` / `minmax(0, 1fr)` 是在显式解除这种保护。
6. **`z-index` 只在层叠上下文内比较**，而 `opacity` / `transform` 是最隐蔽的触发器。**层叠上下文 ≠ 合成层**——前者管绘制顺序，后者影响性能路径。
7. **移动优先是层叠规则的必然结果**，不是风格偏好；断点应由内容崩坏的宽度决定。
8. **媒体查询牵动全页管线（重求值 → 重算样式 → 布局 → 绘制），容器查询只影响容器子树**——这是后者在工程上的真正价值。
