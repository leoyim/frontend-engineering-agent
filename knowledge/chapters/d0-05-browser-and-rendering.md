## 5.1 从字节到像素：渲染管线的完整阶段

### 七个阶段，以及它们各自的产物

```text
① 解析 HTML → DOM 树
② 解析 CSS  → CSSOM 树
③ 样式计算  → 每个节点的一组「计算后样式」（computed style）
④ 布局 Layout → 每个盒的几何（位置与尺寸）
⑤ 绘制 Paint → 绘制指令（paint records）—— 不是像素
⑥ 光栅化 Raster → 像素
⑦ 合成 Composite → 最终画面
```

**第 ⑤ 步是最容易被误解的一环**：Paint 的产物是**指令列表**（"在坐标 (x,y) 画一个 200×40 的蓝色矩形"），不是什么位图。真正的像素化在第 ⑥ 步，由**光栅线程**完成。

### 谁在哪条线程上

| 阶段 | 执行者 | 说明 |
|---|---|---|
| 解析 HTML/CSS、样式计算、布局、绘制指令生成 | **主线程** | 与 JS、事件处理共享同一条线程 |
| 光栅化 | 光栅线程 | 把绘制指令变成像素 |
| 合成 | **合成线程** | 把已光栅化的图层拼成画面 |

**这张表是本章所有性能结论的源头**：主线程上任何环节被 JS 占住，前面几个阶段就排不上队；而只涉及合成线程的改动，可以在主线程忙碌时照常推进。

### 阻塞：为什么 CSS 会挡住首屏

解析阶段有三条不同的阻塞规则：

| 资源 | 是否阻塞 | 阻塞什么 |
|---|---|---|
| `<link rel="stylesheet">` | **阻塞渲染**（也阻塞脚本执行） | 浏览器必须等 CSSOM 就绪才能做样式计算 —— 否则没有样式可算 |
| `<script>`（无属性） | **阻塞解析** | 脚本可能改 DOM（甚至 `document.write`），浏览器必须停下来等它执行完 |
| `<script async>` | 不阻塞解析 | 下载完立即执行，**执行顺序无保证** |
| `<script defer>` | 不阻塞解析 | 在文档解析完成后、`DOMContentLoaded` 之前**按顺序**执行 |

由此得出一条常被忽略的实践结论：**首屏要求"关键 CSS 内联、非关键 CSS 延后"**，正是因为外部 CSS 会卡住整条渲染链。

### 三种"动画路径"，成本差一个数量级

改一个 CSS 属性会触发多长的管线，取决于该属性影响哪个阶段：

| 路径 | 触发阶段 | 典型属性 | 相对成本 |
|---|---|---|---|
| **改布局** | 布局 → 绘制 → 合成 | `width` `height` `top` `left` `margin` `padding` `font-size` | 最贵 |
| **改绘制** | 绘制 → 合成 | `color` `background-color` `border-color` `box-shadow` `visibility` | 中 |
| **只改合成** | 合成 | `transform` `opacity`（在已提升的图层上） | 最便宜 |

**这就是"用 `transform` 做动画"的全部理由**——不是风格偏好，而是它能跳过前两个阶段。

需要说明的是：**不是"写了 `transform` 就自动走合成"**。浏览器需要为它准备一个独立的**合成层**；`will-change: transform` 是一种**提前告知**（让浏览器早点建层），代价是常驻内存。

| 建层手段 | 副作用 |
|---|---|
| `will-change: transform` / `opacity` | 提前建层，可能长期占内存 |
| `transform: translateZ(0)`（历史手法） | 语义不清，现在应优先用 `will-change` |
| 3D 变换、`opacity` 动画 | 由浏览器自动判断 |

**层不是越多越好**：每层都要内存与合成开销，层数失控反而会卡——这是"滥用 `will-change`"的代价。

### 布局不是无条件全量

浏览器会为受影响的子树打上"需要布局"的标记，只在必要时重算——但**改动的传播范围决定成本**：

| 改动 | 传播范围 |
|---|---|
| 改一个叶子节点的 `color` | 该节点（仅重绘） |
| 改一个节点的 `width` | 该节点及其**后代与后续兄弟**（可能上行影响祖先） |
| 改根节点或容器尺寸 | 大面积甚至全量布局 |

这解释了"为什么给容器加动画会卡、给内部小元素加动画不卡"。

## 5.2 重排与重绘：触发条件与代价

### 会触发重排（布局）的操作

| 类别 | 例子 |
|---|---|
| 几何属性变更 | `width` `height` `margin` `padding` `border-width` `top` `left` |
| 内容变更 | 增删 DOM 节点、修改文本、换字体 |
| 查询几何属性（**强制同步布局**） | `offsetWidth` `offsetHeight` `getBoundingClientRect()` `scrollTop` `getComputedStyle()` 的部分值 |
| 窗口事件 | `resize`（必然引发大规模布局） |

最后一类"查询"最值得警惕：**它本身不改变任何东西，却因为"需要一个准确的几何读数"迫使浏览器提前清算布局**（D0 第 3 章 §3.5 的机制）。经典反模式是**在循环里交替读写**：

```js
// 反例：读→写→读→写…… 每一轮都可能触发一次强制布局
items.forEach((el) => {
  const h = el.offsetHeight;      // 读（可能强制布局）
  el.style.height = h + 10 + "px"; // 写（标记脏）
});

// 正例：先全部读，再全部写
const heights = items.map((el) => el.offsetHeight);
items.forEach((el, i) => { el.style.height = heights[i] + 10 + "px"; });
```

**"读写分离"这条规则的机制来源就在此**——不是编码风格建议，而是为了不让读取操作迫使浏览器反复清算。

### FastDOM 式批处理的规范依据

浏览器在每次 `update the rendering` 前会统一清算脏标记。所以**把同一帧内的多次写操作合并**，能让布局只算一次。这也是为什么"在 `requestAnimationFrame` 里写样式"优于"在事件回调里直接写"——前者落在渲染步骤内，后者可能落在任意任务里。

### 重绘不等于重排

| 改动 | 重排 | 重绘 | 合成 |
|---|---|---|---|
| `transform` / `opacity`（已建层） | 否 | 否 | 是 |
| `color` / `background-color` | 否 | 是 | 是 |
| `width` / `font-size` | **是** | 是 | 是 |

**判断方法**：问一句"这个属性会不会改变元素的**位置或尺寸**"。会 → 布局；不会但改变**可见效果** → 绘制；只改变**已有图层如何被摆放或混合** → 合成。

## 5.3 DevTools 四大面板：读数方法

工具的价值取决于"知不知道它显示的是什么"。逐面板对照机制：

### Elements —— 看的是"最终的 DOM 与生效的样式"

| 子面板 | 读什么 | 对应本章/前章机制 |
|---|---|---|
| DOM 树 | 解析后的真实结构（**含浏览器容错修复的结果**） | D0 第 1 章 §1.1 的容错解析 |
| Styles | 命中的规则，**被划掉的是被覆盖的声明** | D0 第 2 章 §2.1 的层叠与特异性 |
| Computed | 最终的计算值 | D0 第 2 章 §2.2 的单位与继承 |
| Layout（Grid / Flex 徽标） | 网格线与弹性轨道的实际分布 | D0 第 2 章 §2.3 / D0 第 2 章 §2.4 |
| Accessibility | **a11y tree** 与每个节点的 accessible name | D0 第 1 章 §1.2 / D0 第 1 章 §1.3 |

最后一行值得单独提示：**Elements 面板能直接看到 a11y tree**——这是验证"语义化到底生效了没有"最快的方式。

### Console —— 看的是"运行时的值"

| 用法 | 用途 |
|---|---|
| `$0` | 指向 Elements 中当前选中的节点 |
| `console.table(arr)` | 表格化数组/对象 |
| `console.time / timeEnd` | 粗粒度计时（精确计时用 Performance） |
| 实时表达式（Live Expression） | 持续观察某个值 |

### Network —— 看的是"请求的每个阶段花了多久"

瀑布图把每个请求拆成若干段：

| 阶段 | 含义 | 优化归属 |
|---|---|---|
| Queueing / Stalled | 排队与连接等待（并发上限、同域连接数） | D6（协议与 CDN） |
| DNS / TCP / TLS | 域名解析、建连、加密握手 | D0 第 6 章 §6.5（DNS/TCP/TLS） |
| **TTFB** | 请求发出到首字节返回（含服务端处理） | 服务端与缓存策略 |
| Content Download | 响应体传输 | 压缩、体积 |

**两个必须会用的开关**：**禁用缓存**（验证缓存策略是否真的生效）与**网络限速**（弱网才暴露真实首屏问题）。本地千兆网下"秒开"什么都证明不了。

### Application —— 看的是"浏览器替你存了什么"

| 存储 | 特点 |
|---|---|
| Cookie | 每次请求自动携带（这是它的关键代价），有大小与数量限制 |
| localStorage | 同步 API，**阻塞主线程**，容量约 5MB |
| sessionStorage | 同上，但标签页关闭即清 |
| IndexedDB | 异步、容量大、可存结构化数据 |
| Cache Storage | 配合 Service Worker 管理离线资源 |

这些存储的机制与取舍属于 `D0.L1.26`，在D0 第 6 章展开。这里只需记住：**Application 面板是"浏览器状态"的唯一真相来源**——排查"为什么登录态丢了""为什么缓存没更新"必须先看它。

### 另外三个面板，本章要用到

| 面板 | 用途 |
|---|---|
| **Performance** | 录制并分解主线程活动（本章 §5.5） |
| **Memory** | 堆快照与分配时间线（本章 §5.6） |
| **Rendering**（在 More tools 里） | Paint flashing / Layer borders / FPS meter —— **直接看见重绘与合成层** |

`Rendering` 面板是本节的"验证器"：打开 Paint flashing 后，**闪绿的区域就是真实重绘的范围**。这是把 本章 §5.1 的理论变成肉眼可见证据的手段。

## 5.4 断点调试：机制与手段

### 断点的本质

调试器的断点不是"暂停脚本"这么简单——它能工作的前提是浏览器向调试器暴露了**执行上下文与调用栈**（D0 第 4 章 §4.3 提到的执行上下文栈）。所以能设断点的地方，都是"执行上下文正在切换"的地方。

### 断点类型与适用场景

| 断点类型 | 在哪设 | 用于 |
|---|---|---|
| **行断点** | Sources 面板某一行 | 常规 |
| **条件断点** | 右键 → Add conditional breakpoint | 循环里只关心 `i === 500` |
| **日志断点** | Add logpoint | 不暂停、只打印（避免反复恢复） |
| **DOM 断点** | Elements 右键 → Break on | **属性修改 / 子树修改 / 节点移除**——找出"谁改了我的 DOM" |
| **事件监听器断点** | Sources → Event Listener Breakpoints | 找出"哪个处理器响应了这次点击" |
| **XHR / fetch 断点** | Sources → XHR/fetch Breakpoints | 按 URL 片段拦截请求发起处 |
| **异常断点** | Sources → Pause on exceptions | 勾选 "Pause on caught exceptions" 可追进被 `try` 吞掉的错误 |

**DOM 断点**是本章最值得掌握的技巧：它把"谁改的"这个问题从猜测变成直接定位——对应 D0 第 3 章 §3.5 讲的"修改 DOM 只是标记脏"，你能在**标记发生的那一刻**停下来。

### Scope 面板读的是词法环境

暂停时 `Scope` 面板显示的是**作用域链**（D0 第 3 章 §3.2 的词法环境）：

| 分组 | 含义 |
|---|---|
| Local | 当前函数的绑定 |
| Closure | **闭包捕获的环境**（D0 第 4 章 §4.3）——"这个变量是从哪来的"答案在这 |
| Script / Module | 模块作用域（D0 第 3 章 §3.8） |
| Global | 全局 |

### 异步调用栈

栈里出现 `<anonymous>`、`setTimeout`、`Promise.then` 这类帧时，说明**当前执行来自另一个任务或微任务**——这正是 D0 第 3 章 §3.7 讲的"调用栈已不同"的可视化证据。现代 DevTools 会尽量把跨异步的链路拼出来，但**链条的断点就是任务边界**。

## 5.5 Performance 面板：读一次录制

### 面板构成

| 区域 | 显示什么 |
|---|---|
| 顶部概览 | FPS（帧率）、CPU 占用、网络与主线程活动 |
| 火焰图（Main） | **主线程的调用栈随时间的层次**——宽度即耗时 |
| 底部摘要 | Summary / Bottom-Up / Call Tree / Event Log |

### 读数的四个关键信号

| 信号 | 含义 | 归属阶段 |
|---|---|---|
| **长任务**（超 50ms 的块，常有红色三角标记） | 主线程被连续占用，渲染与输入都被推迟 | D0 第 4 章 §4.4 |
| **紫色块（Recalculate Style / Layout）** | 样式计算与布局的耗时 | 本章 §5.1 |
| **绿色块（Rendering / Paint）** | 绘制指令生成 | 本章 §5.1 |
| **Layout Shift 记录** | 布局偏移事件 | D0 第 1 章 §1.3（CLS 的来源） |

**读法的顺序是固定的**：先看有没有长任务 → 再看长任务里占比最高的类别 → 再下钻到具体函数。**不要一开始就看函数级细节**——那会淹没在几千个条目里。

### 关于指标的诚实说明

Performance 面板给的是**实验室数据**（在你的机器、你的网络、你的操作路径下）。真实用户的表现要用 **RUM**（真实用户监控）采集——两者**不能互相替代**。这一点及 Core Web Vitals（LCP / INP / CLS）的完整讨论放在 D6 领域，本章只建立"读录制"的能力。

## 5.6 内存泄漏：识别与常见来源

### 首先要区分"内存高"与"内存泄漏"

**内存高不等于泄漏**。GC（垃圾回收）是惰性的：分配了但不再使用的对象会等下次 GC 才回收。所以判断泄漏的标准不是"占用多少"，而是：

> **反复做同一件事之后，"本该被回收的同类对象"数量是否持续增长。**

### 三快照法

Memory 面板的标准用法：

```text
① 快照 A：页面稳定后的基线
② 反复执行可疑操作 N 次（打开/关闭弹层、切换路由）
③ 手动触发 GC → 快照 B
④ 对比 A 与 B：看 "Objects allocated between" / 保留对象的增量
```

**关键在"手动触发 GC"**：Memory 面板有垃圾桶图标，不点它，看到的可能只是"还没回收"而不是"回收不掉"。对比时看的是 **Retained Size**（保留大小）——它表示"如果这个对象被回收，能释放多少"。

### 五类常见泄漏来源

| # | 来源 | 机制 |
|---|---|---|
| 1 | **未清理的定时器** | `setInterval` 持有回调，回调持有其闭包环境（D0 第 4 章 §4.3） |
| 2 | **未移除的事件监听器** | 尤其挂在 `window` / `document` 上的全局监听；被监听元素若还在 DOM 上，引用链不断 |
| 3 | **脱离文档的 DOM 引用（detached DOM）** | JS 里存着已从树中移除的节点，整棵子树无法回收 |
| 4 | **无上限的缓存 / 集合** | Map、数组持续增长且从不清理 |
| 5 | **未取消的异步操作** | 长轮询、未 `abort` 的请求、未取消的订阅（D0 第 4 章 §4.6 的 `AbortSignal` 正是治它） |

**第 1、2、5 类的共同点**：它们都把"某个外部引用"指向了本该回收的环境。所以泄漏排查的基本手法是——**问"谁还引用着它"**。堆快照里的 retainers（引用路径）链就是回答这个问题的工具。

## 5.7 动手

| 任务 | 验收 |
|---|---|
| 打开 Rendering 面板的 Paint flashing，分别改 `color` / `width` / `transform` | 说出三者触发的阶段差异，并用闪烁范围验证 |
| 打开 Layer borders，给一个元素加 `will-change: transform` | 指出它在哪一层，并说出建层的代价 |
| 在循环里交替读 `offsetHeight` 与写样式，用 Performance 录制 | **在火焰图里指出重复出现的 Layout 块** |
| 用 DOM 断点抓住"谁改了这个节点的 class" | 对比与"搜索代码"的时间差 |
| 在闭包中设断点，查看 Scope 面板的 Closure 分组 | 说出闭包环境里有哪些绑定（对应 D0 第 4 章 §4.3） |
| 在 `setTimeout` 回调里断点，观察 Call Stack | 指出任务边界在哪一帧（对应 D0 第 3 章 §3.7） |
| 用三快照法验证"打开再关闭弹层 10 次"是否泄漏 | 说出为什么必须先手动触发 GC |
| 复现一次 detached DOM 泄漏（保存已移除节点到全局数组） | 在快照里找到该节点，并说出引用链 |
| 用 Network 面板禁用缓存与限速，观察首屏 | 说出 TTFB 与 Content Download 各自的优化归属 |

**进阶挑战**：

1. 制造一次"层爆炸"（给上百个元素加 `will-change`），用 Layer borders 观察，并解释为什么层多反而更慢。
2. 在 `resize` 事件里同步读取几何属性，用 Performance 证明它与"读写分离"版本的耗时差距。
3. 用 Performance 录一次滚动，找出主线程最长的块，并把它切分到 50ms 以下。

## 本章小结

**七条最该记住的结论**

1. **渲染管线七个阶段、三条线程**。主线程做解析 / 样式 / 布局 / 绘制指令；光栅与合成在别的线程。所有"改什么会卡"的问题都归结为"改动走完了哪几个阶段"。
2. **Paint 产出的是指令，不是像素**。这一条澄清了大量关于重绘成本的误解。
3. **三种动画路径成本差一个数量级**（布局 → 绘制 → 合成）。`transform` / `opacity` 便宜，是因为它们能只走合成——但前提是存在**合成层**，而层有内存代价。
4. **"读几何属性"会强制布局**，所以"读写分离"有机制依据；`requestAnimationFrame` 写样式优于事件回调里直接写，因为前者落在渲染步骤内。
5. **DevTools 是"验证器"而非"摆设"**：Rendering 面板看重绘与图层，Application 看浏览器状态，Network 必须禁缓存 + 限速才有意义。
6. **DOM 断点把"谁改的"变成直接定位**；Scope 面板的 Closure 分组就是闭包环境的可视化。
7. **内存泄漏的判据是"反复操作后增量是否持续"**，前提是**先手动触发 GC**。五类来源的共同点是"外部引用未解除"。
