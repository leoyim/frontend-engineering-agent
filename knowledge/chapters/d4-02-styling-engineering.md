## 2.1 预处理器工程化：插件链的顺序就是语义

`D4.L3.01`。第 1 章已给出 `@use` 的五条差异。这一节讲**怎么把它们组织成一条不会互相踩的链**。

### 两段职责不同的链

```
Sass（模块系统 + 语法扩展）
   ↓
PostCSS（CSS → CSS 的插件链）
   ↓
压缩
```

**它们不是同一类工具**，这条分界值得再强调一次：

| | Sass | PostCSS |
|---|---|---|
| 官方自我描述 | 带模块系统的 CSS 预处理器 | **"A tool for transforming CSS with JavaScript"** |
| 输入 | `.scss` | **CSS** |
| 是否扩展语法 | ✅ 内置 | ❌ **靠插件** |

**PostCSS 的官方首页用四张"能力卡片"说明了它的职责范围**，而这四张卡恰好对应四类插件：

| 卡片 | 代表插件 | 职责 |
|---|---|---|
| 提升可读性 | **Autoprefixer** | 加浏览器前缀（数据源 **Can I Use**） |
| 提前用未来 CSS | **PostCSS Preset Env** | 把现代 CSS 转成多数浏览器能懂的（数据源 **cssdb**，**按 browserslist 目标决定 polyfill**） |
| 终结全局 CSS | **CSS Modules** | 类名自动哈希（官方示例 `.name` → `.Logo__name__SVK0g`） |
| 避免 CSS 错误 | **stylelint** | 静态检查 |

**⭐ 第一、二行的数据源不同，这是"为什么两个都要"的答案**：

| | 数据源 | 管什么 |
|---|---|---|
| Autoprefixer | **Can I Use** | **要不要加前缀** |
| Preset Env | **cssdb** | **要不要降级语法** |

**它们是两个不同的问题**（"能不能识别这个特性" vs "要不要写前缀"），**所以不能互相替代**。

### 顺序为什么是语义

**⚠️ 先说明一处缺口**：PostCSS 的**首页没有讲插件顺序**。所以下面这条是**机制推理**，不是该页原文：

> **插件按加入顺序依次处理同一棵 AST，所以顺序 = 处理的依赖顺序。**

**而这条推理可以直接被第 1 章已核验的 Vite 默认行为印证**：

> Vite 官方：**CSS 压缩在 PostCSS 之后运行**，并使用 `build.cssTarget`。

**"压缩在后"不是随便定的** —— 因为压缩会**改变源码形态**，它必须在所有"需要读懂源码"的插件之后。

**由此得出一条可复用的排序原则**：

| 阶段 | 做什么 | 例子 |
|---|---|---|
| **1. 语法层** | 把非 CSS 语法解析成 CSS | Sass 编译（在 PostCSS 之前） |
| **2. 内联层** | 把 `@import` 展开 | `postcss-import` |
| **3. 转换层** | 改写法（降级、前缀） | Preset Env、Autoprefixer |
| **4. 优化层** | 去重、合并、压缩 | 压缩器 |

**常见的踩坑是"2 与 3 顺序反了"**：如果先做降级（把嵌套展平），再做 `@import` 内联，那么**内联进来的文件不会被降级**。**症状是"引用的文件里语法没转换"** —— 而这个症状很难归因到"顺序"。

**另一条**：**Sass 必须在 PostCSS 之前**。因为 PostCSS 的输入是 **CSS**，不是 SCSS。**顺序反了就解析失败**（这个错误会明确报出来，属于"好查"的那类）。

### Sass 侧的"工程化"是什么

第 1 章给了 `@use` / `@forward` / `pkg:` 的机制。**把它们组织起来，就是一件事**：

> **让每个文件只 `@use` 它需要的东西，让每个包只有一个 `@forward` 出口。**

| 做法 | 效果 |
|---|---|
| **每个文件显式 `@use`** | 依赖可见（不用猜"这个变量哪来的"） |
| **包的入口文件只做 `@forward`** | **不转发即私有** —— 私有是结构事实，不是命名约定 |
| **包内跨文件用 `@use 'pkg:xxx'`** | 走包解析而不是相对路径（移动文件不破坏引用） |

**第二行是 Sass 相对旧方案最大的改进**。`@import` 时代"私有"靠 `_` 前缀约定，**约定可以被违反且不报错**；`@forward` 时代**不转发就是拿不到** —— 违反了会直接报错。

**这与 `D5` 第 3 章"门禁只有阻断与不卡两种形态"是同一个思路**：**让约束成为结构，而不是纪律。**

## 2.2 Design Token：值要能被换掉

`D4.L3.02`。第 1 章 §1.6 已经给出一个判据：**「值动态」与「规则动态」是两件事**。**Token 就是"值动态"的正式形态。**

### 定义：把值从规则里抽出来

```css
/* 没有 Token */
.card { padding: 16px; border-radius: 8px; }

/* 有 Token */
.card { padding: var(--space-4); border-radius: var(--radius-md); }
```

**差别不在写法，在"能换掉的范围"**：

| | 改一次值 | 影响 |
|---|---|---|
| 硬编码 | 改 N 处 | 漏改就出现"16px 和 15px 混着" |
| **Token** | **改 1 处** | 全局一致 |

### 三层结构，缺一层就不成立

| 层 | 例子 | 谁改它 |
|---|---|---|
| **① 原始值（primitive）** | `--blue-500: #0a84ff` | 几乎不改 |
| **② 语义（semantic）** | `--color-primary: var(--blue-500)` | **主题切换改这一层** |
| **③ 组件（component）** | `--button-bg: var(--color-primary)` | 组件级定制 |

**⭐ 为什么必须有第 ② 层**：因为**主题切换的本质是"同一个语义，换一个原始值"**。

```
主题 A：--color-primary → --blue-500
主题 B：--color-primary → --purple-500
```

**只有两层会怎样**：如果组件直接用原始值（`--blue-500`），**切主题必须改组件**；如果组件直接用十六进制（连原始值都没有），**连切的机会都没有**。

**所以第 ② 层是"可换"的唯一落点。** 而它有一个副作用：**语义层的名字必须描述"用途"，不能描述"外观"**。

| 名字 | 是否可换主题 |
|---|---|
| `--color-primary` | ✅ 换主题只改变量 |
| `--color-blue` | ❌ 主题换成紫色后，名字开始说谎 |
| `--color-danger` | ⚠️ 语义，但把"危险"绑死了颜色 —— **换成紫色主题时仍然说得通**（危险仍是红系） |

**第三行值得细想**：`--color-danger` 是**语义**（描述用途），但它天然绑定"红"这个视觉预期。**所以语义层要按"用途"命名，允许不同主题给出不同的具体颜色**。

### ⭐ 载体之争：Sass 变量做不了主题切换

这是本章最硬的一条判据。

| 载体 | 存在于什么时候 | 能否运行时切换 |
|---|---|---|
| **Sass 变量**（`$space-4`） | **构建期**（编译后消失） | ❌ **不能** |
| **CSS 变量**（`--space-4`） | **运行时**（浏览器里存在） | ✅ **能** |

**原因很直接**：Sass 变量在编译时就被替换成字面值了 —— **浏览器根本看不到它**。

**所以**：

> **"用 Sass 变量做 Token" 只能得到"编译期一致"，得不到"运行时可换"。**

**推论**：

| 需求 | 该用什么 |
|---|---|
| 只是避免硬编码（编译期一致即可） | Sass 变量够用 |
| **要主题切换 / 暗色模式 / 运行时换肤** | **必须 CSS 变量** |
| 既要 Sass 的运算能力，又要运行时 | **两者嵌套**：`$space: 4px` 生成 `--space-4: #{$space}` |

**第三行是实践里最常见的做法**，而它有一个必须理解的前提：**嵌套只发生在构建期**。运行时能换的只有**外层那个 CSS 变量**。

### `@property`：让变量有类型

CSS 变量本身是"任意文本替换"，**没有类型**。`@property` 给它加上类型（MDN，2026-05-01 修订，**Baseline 2024**，2024-07 起可用）。

**三个描述符**：

| 描述符 | 是否必填 | 说明 |
|---|---|---|
| `syntax` | **必填** | **带引号的字符串**，如 `"<color>"` / `"<length> \| <percentage>"` / `"*"`（任意） |
| `inherits` | **必填** | 布尔值。**没有可省略的默认值** —— 缺了整条规则无效 |
| `initial-value` | 视情况 | 当 `syntax` **不是 `"*"`** 时**必需**；且**必须是「计算独立」的值** |

**⭐ "计算独立"这条约束很值得记**：

| 值 | 能否作 `initial-value` | 为什么 |
|---|---|---|
| `10px` | ✅ | 不依赖任何上下文 |
| `2in` | ✅ | `1in` 始终等于 `96px`（MDN 明确举的例子） |
| **`3em`** | ❌ | **依赖父元素的 `font-size`** |

**这条约束的存在理由**：**初始值必须能在"还没有任何上下文"的时刻被确定**。`3em` 在那个时刻没有答案。

**另外三条容易踩的规则**（均为 MDN 明确）：

| 规则 | 后果 |
|---|---|
| **必须同时有 `syntax` 与 `inherits`** | 缺任一 → **整条规则无效并被忽略** |
| **同名多条 `@property`** | **样式表中最后一条生效** |
| **CSS 与 JS 同时注册同名属性** | **JS 注册优先**（`CSS.registerProperty()`） |

**注册之后能做什么**：MDN 的示例把 `--progress` 注册为 `"<percentage>"`，然后在 `@keyframes` 里从 `25%` 动画到 `100%` —— **类型化的自定义属性可以参与动画**。

**⚠️ 两处必须如实标注**：

1. **该页没有提性能优势**。所以"类型化后可避免重复计算/提升性能"这类说法**本章不给** —— 它可能成立，但**不是该页的信息**。
2. **该页也没有用"插值"这个词**。所以"可插值"不应被当作官方结论；能确定的是**动画示例存在**。

### Token 的治理判据

| 现象 | 判据 | 动作 |
|---|---|---|
| 主题切换要改组件 | **组件直接用原始值** | 补语义层 |
| 同一个间距出现 15px / 16px | **有硬编码混入** | 加 Lint 规则禁用魔法数字 |
| Token 名字带颜色名 | **命名按外观** | 改成按用途（`--color-primary`） |
| 暗色模式下某些元素不变 | **该值绕过了语义层** | 补齐链路 |

## 2.3 响应式：三种缩放基准

`D4.L3.03`。**这一节只讲基准的取舍。** 按已定的边界，不给 `clamp()` 与容器查询的语法。

### 三个基准，三种"跟随"

| 基准 | 单位 | 跟着什么缩放 |
|---|---|---|
| **设备无关** | `px` | **不缩放** |
| **根字号** | `rem` | **用户的字号设置**（以及你设定的根字号） |
| **视口** | `vw` / `vh` | **窗口尺寸** |

**⭐ 选型判据只有一句**：

> **你希望"什么变大时，它也变大"？**

| 想让什么变大时它也变大 | 选 |
|---|---|
| **用户调大字号**（无障碍需求） | **`rem`** |
| **屏幕变宽**（大屏要更"大"） | **`vw`** |
| **都不跟**（1px 边框、极细装饰） | **`px`** |

**这条判据把"用 rem 还是 vw"从审美问题变成了需求问题** —— 而两者的**用户含义完全不同**：

| | `rem` | `vw` |
|---|---|---|
| 尊重用户的字号偏好 | ✅ **是** | ❌ **不** |
| 大屏自动放大 | ❌ 不 | ✅ 是 |
| 手机横竖屏变化 | 不变 | **剧变** |

**第二、三行合起来说明一件事**：**`vw` 会忽略用户设置**。所以**正文排版用 `vw` 是有代价的** —— 用户在系统里调大字号，`vw` 的文字不会跟着变。

**这与 `D5` 第 2 章 §2.3 的"查询方式决定测试价值"是同一种思路**：**用一个技术选择，回答一个"用户能不能感知到"的问题。**

### rem 与 vw 混用为什么会失衡

**它们跟随的基准不同**，所以在极端宽度下比例会漂移：

| 场景 | 结果 |
|---|---|
| 根字号固定、尺寸用 `vw` | 大屏上文字不变、容器变大 → **留白越多越空** |
| 根字号用 `vw` 算、尺寸用 `rem` | 两者同步缩放 → **比例稳定**，但**用户字号设置被覆盖** |
| 两者混用且根字号另有一套规则 | **层叠出两个缩放系数** → 在某个宽度区间里"突然变大" |

**第三行是本章最值得警惕的一条**：**两层缩放叠加，效果是乘法而不是加法。**

**判断自己有没有这个问题，只需问一句**：

> **同一个元素的尺寸，最终被几个"跟随基准"的规则影响过？**

**答案 > 1，就存在失衡风险。** 这与 `D5` 第 4 章 §4.2 的"F 会自我放大"结构相同 —— **叠加的东西要按乘法理解，不能按加法理解。**

### 1px 问题：它是「物理像素 ≠ CSS 像素」的直接后果

**先说明来源**：**这一小节没有官方文档引用**，是从 CSS 像素与设备像素比（DPR）的定义**推导**出来的。

**机制**：

```
CSS 1px  →  DPR 个物理像素
```

| 设备 DPR | CSS `1px` 对应 | 想要"一根物理像素"的线 |
|---|---|---|
| 1 | 1 个物理像素 | `1px` 正好 |
| 2 | **2 个物理像素** | 需要 **0.5px** |
| 3 | **3 个物理像素** | 需要约 **0.333px** |

**所以"移动端 1px 看起来粗"不是渲染 bug** —— 它**精确地等于 1px × DPR**。

**三种应对，各有代价**：

| 做法 | 机制 | 代价 |
|---|---|---|
| 直接写小数（`0.5px`） | 让浏览器取整 | 部分环境下被取整成 0 或 1 |
| **`transform: scaleY()` 伪元素** | 先画 1px 再缩放 | 多一个元素，且位置要对齐 |
| **`box-shadow` / 渐变模拟** | 不依赖边框宽度 | 难以覆盖圆角等场景 |

**共性结论**：**"1px 问题"不是"怎么把线画细"，而是"你要不要精确控制物理像素"。**

**而它有一个更根本的答案**：**在多数设计里，你要的不是"一根物理像素"，而是"视觉上足够细"。** 所以**先问设计意图，再选实现** —— 这与 `D5` 第 4 章"先问是值动态还是规则动态"是同一个提问方式。

### 安全区：`env()` 与四个内缩量

**MDN（2026-10-08 修订，Baseline 广泛可用自 2020-01）**给的机制：

| 变量 | 含义 |
|---|---|
| `safe-area-inset-top` / `-right` / `-bottom` / `-left` | 四个内缩量，**构成一个矩形** |

**语义（官方原文要点）**：这四个值构成一个矩形，**在此矩形内放置内容不会被非矩形显示屏的形状裁切**。

| 情况 | 取值 |
|---|---|
| 视口是矩形，且没有特性（工具栏、动态键盘）占用空间 | **`0`** |
| 否则 | **大于 0 的 `px` 值** |

**⭐ 还有一组常被忽略的常量**：

| 变量 | 语义 |
|---|---|
| `safe-area-inset-*` | **随当前可见内容区变化** |
| **`safe-area-max-inset-*`** | 所有动态 UI 特性**收起**时的**静态最大值**（**常量**） |

**两者的用途不同**：**动态值用于"当前要让开多少"，最大值用于"布局需要预留多少"**。用错会在键盘弹出时跳动。

**退化值写法**（官方语法）：

```css
padding-bottom: calc(1em + env(safe-area-inset-bottom, 0px));
```

**⭐ 一个容易误判的行为**（MDN 明确）：

> `env()` 在**解析时**被视为合法；**在计算时**才被替换为实际值或退化值。
> 若替换后的值无效**且没有退化值**，**声明不会被忽略** —— 而是采用该属性的**初始值或继承值**。

**"不会被忽略"这一点很反直觉**：它意味着**你看到的是一个"看起来生效了但不是你以为的值"的结果**。**所以退化值不是可选项，是必需的。**

**⚠️ 一处必须如实标注**：**MDN 该页完全没有提 `viewport-fit=cover`**，也没有任何 `<meta name="viewport">` 的内容。所以"要让 `safe-area-inset-*` 变成非零值必须先设 `viewport-fit=cover`"这条**本章不作为官方断言** —— 它属于页面外知识，请以 viewport meta 相关文档为准。

**另一个官方警告（很实用）**：若同时设置了 `<meta name="text-scale" content="scale">` **又**使用 `env(preferred-text-scale)`，**缩放会被应用两次**：

```css
/* 会双重缩放 */
font-size: calc(2rem * env(preferred-text-scale));
```

**MDN 还建议优先用 `<meta>`**，因为跨平台支持更广、更简单。

**这条与 §2.3 开头的判据合起来，得到一条完整的规则**：

> **缩放系数只能有一个来源。** 根字号、`vw`、`env(preferred-text-scale)`、`<meta name="text-scale">` —— 每多叠一个，就多乘一次。

## 2.4 可维护性：废弃样式与体积

`D4.L3.04`。**CSS 的清理比 JS 难**，原因是结构性的。

### 为什么难

| 难点 | 原因 |
|---|---|
| **全局作用域** | 任何选择器可能命中任何元素 |
| **动态类名** | `class={`btn-${size}`}` 让静态扫描失效 |
| **状态类** | `:hover` / `:focus` / `is-active` 只在特定时刻生效 |
| **无"引用"概念** | HTML 里写 `class="a b"`，**不是 import**，没有引用计数 |

**第四行是根因**：**JS 的未使用代码可以靠 import 图判断，CSS 不能** —— 因为**类名的"使用"只发生在字符串里**。

**这与 `D3` 第 3 章 §3.4 的 Tree Shaking 是同一个问题**：**Tree Shaking 依赖静态可分析的模块图，而样式没有这张图。**

### 三条判据，可靠度递减

| 判据 | 怎么做 | 可靠度 |
|---|---|---|
| **① 类名无引用** | 在源码里搜索类名字面量 | 中（动态类名会漏判 → **误删**） |
| **② 规则被完全覆盖** | 分析同一元素上所有生效声明，找出从未生效的 | 高（但需要运行时信息） |
| **③ 选择器永不匹配** | 运行时遍历 DOM，统计选择器命中次数 | **最高**（但需要采集） |

**⚠️ 本章不引用任何具体工具的覆盖率 API**（未核验）。

**⭐ 但有一条判据比工具更可靠**：

> **"没有主人的样式"** —— 无法回答"谁在用它"的样式，应当删除。

**"主人"是什么**：能说出"这个类名由哪个组件/页面/状态产生"。**说不出来，它就没有主人。**

**这条判据的好处是**：**它不需要工具**，只需要问。而它**处理了动态类名这个最难的情况** —— 因为动态类名虽然静态搜不到，但**写它的人知道它在哪**。

**而它有一个前提**：**每条样式都应当有明确的所有者**（这正是第 1 章 §1.8 的"按变更传播范围分层"要解决的问题）。

### 体积监控

**CSS 体积的特殊性**：

| | JS | CSS |
|---|---|---|
| 压缩率 | 高（标识符可短） | **中**（选择器与属性名不能改） |
| 未使用部分的代价 | 解析 + 执行 | **解析 + 可能匹配** |
| 拆分的粒度 | 按模块 | **按 chunk（`build.cssCodeSplit`）** |
| 首屏影响 | 阻塞 | **阻塞渲染** |

**第四行是最要紧的**：**CSS 是阻塞渲染的资源**（而在 `D6` 第 4 章会看到，它直接影响 LCP/FCP）。**所以 CSS 体积的超标比 JS 更直接地伤害首屏。**

**监控的三条**（与 `D6` 第 4 章的性能预算接续）：

| 指标 | 为什么 |
|---|---|
| **首屏 CSS 的未使用比例** | 直接对应阻塞时间 |
| **单文件体积** | 超过阈值时压缩收益递减 |
| **选择器复杂度**（如嵌套深度） | 影响匹配成本（`D4` 第 3 章 §3.5 展开） |

**一条纪律**：**先把"从不生效的规则"删掉，再考虑压缩** —— 因为**压缩对"用不到的样式"完全无效**。这与 `D3` 第 3 章 §3.1 的"先转译后摇树"是同一种顺序意识。

## 2.5 CSS 提取与分包

`D4.L3.05`。**这一节的核心是一个取舍，不是一个配置。**

### 两种形态

| 环境 | CSS 在哪 | 机制 |
|---|---|---|
| **开发** | 注入 `<style>` | Vite 默认：`import './x.css'` → 注入并带 HMR |
| **生产** | **独立文件** | 由 **`build.cssCodeSplit`** 决定是否**按 chunk 拆** |

**⚠️ 一处提醒**：**从 Vite 5 起，对 `.css` 的默认/具名导入已移除**（第 1 章已核验）。要拿 CSS 字符串必须用 **`?inline`**。

### 三种分包策略与它们的取舍

| 策略 | 做法 | 好处 | 代价 |
|---|---|---|---|
| **跟随 chunk**（默认） | `cssCodeSplit` 开 | **首屏只加载用到的样式** | **请求数增加**；共享样式可能重复 |
| **全部合并** | `cssCodeSplit: false` | 一次请求 | **首屏加载用不到的全部样式** |
| **按入口拆** | 多页应用，每个入口一份 | 入口之间互不拖累 | 共享部分要单独提 |

**⭐ 取舍的本质是一句话**：

> **你在优化「请求数」还是「首屏字节数」？**

| 网络条件 | 倾向 |
|---|---|
| HTTP/1.1（连接数受限） | 合并 |
| **HTTP/2+（多路复用）** | **按需拆** —— 请求数不再是主要成本 |
| 首屏 LCP 敏感 | **按需拆** |

**这与 `D3` 第 3 章 §3.6 的"内联阈值"是同一类权衡**：**小文件合并省请求，但会让首屏多带用不到的内容。** 判据同样是**"它有没有可能不被用到"**。

### 一个必须处理的副作用：共享样式重复

**按 chunk 拆之后，被多个 chunk 引用的样式会怎样？**

| 情况 | 结果 |
|---|---|
| 同一个 CSS 被两个 chunk 引用 | **可能各自打包一份** → 重复下载 |
| 组件库的样式被所有 chunk 引用 | **重复量可能很可观** |

**处理方式与代码分割同构**（`D3` 第 3 章 §3.5）：**把它提取到公共 chunk**。

**而这里有一条顺序纪律**：

> **先确定"哪些样式是共享的"，再决定怎么拆。**

**因为"共享"是拆分的输入，不是输出。** 反过来做（先拆再发现重复）会陷入"每加一个页面就多一份重复"。

### 与组件库集成的三个问题

**这是实践里最容易出问题的地方**，而问题的形态很固定：

| 问题 | 机制 | 处理 |
|---|---|---|
| **样式全量引入** | 组件库的入口 CSS 引入了所有组件 | 按组件引入（若库支持）；否则**接受它，但把它算进预算** |
| **主题变量由谁提供** | 组件库用自己的变量前缀 | **把组件库的 Token 映射到你的语义层**（§2.2 的第 ② 层） |
| **类名冲突 / 优先级打架** | 两个来源的样式命中同一元素 | **`@layer` 或提高特异性**；**不要靠加载顺序** |

**⭐⭐ 第二行是本章最值得展开的一条**：

**组件库的变量不是你的 Token** —— 它有自己的命名与层级。**直接混用会导致"两套主题系统"**：

```
你的语义层:  --color-primary
组件库:      --ui-primary-color
```

**正确做法是建一层映射**：

```css
:root {
  --ui-primary-color: var(--color-primary);  /* 单向：库读你的 */
}
```

**⭐ 单向是关键**：**让组件库读你的语义层，而不是让你的代码读组件库的变量。** 因为前者在**换库时只需要改这一层映射**，后者要改所有使用点。

**这与 `D3` 第 6 章 §6.5 的"迁移成本在生态不在速度"、`X1` 第 1 章 §1.5 的"模板是复制、共享包是引用"是同一种结构**：**把"外部依赖的差异"收敛到一个可替换的边界上。**

**而第三行的"不要靠加载顺序"在第 1 章 §1.9 已经证明过**：**按需加载让顺序不可预测**。

## 2.6 治理动作：六个判定阈值

| # | 现象 | 判定阈值（起点值） | 动作 | 依据 |
|---|---|---|---|---|
| 1 | `@import` 进来的文件语法没被降级 | **顺序把"转换层"排在了"内联层"之前** | 内联必须在转换之前；Vite 里压缩在 PostCSS 之后是同一原则 | §2.1 |
| 2 | 切主题要改组件 | **语义层缺失或组件直接用原始值** | 补第 ② 层；命名改成按用途 | §2.2 |
| 3 | 暗色模式下个别元素不变 | **该值绕过了语义层** | 查出所有硬编码；加 Lint 禁用魔法数字 | §2.2 |
| 4 | 某个尺寸在特定宽度区间"突然变大" | **叠加了 > 1 个缩放基准** | 每个尺寸只允许一个基准来源；根字号与 `vw` 不并用 | §2.3 |
| 5 | 键盘弹出时底部按钮被遮 / 布局跳动 | **用了 `safe-area-inset-*` 而没留 `safe-area-max-inset-*`** | 布局预留用最大值，当前避让用动态值 | §2.3 |
| 6 | 想删样式但不敢删 | **无法回答"谁在用它"** | 用"没有主人就删"判据；动态类名问写它的人 | §2.4 |

### 三条使用说明

**① 阈值 1 是"沉默的顺序错误"。**

它不报错，只是**某些文件的语法没被转换** —— 而症状会在浏览器里表现为"某个属性不生效"。**归因到"顺序"的概率很低。**

**② 阈值 4 的排查方式与其他五条不同。**

它**不是找 bug，是数来源**：数一个尺寸被几个规则影响过。**数出来 > 1 就是问题**，不管当前是否看起来正常。

**③ 阈值 6 是最省工具成本的一条。**

它**不需要任何分析工具**，只需要一个问题。**而它能处理工具处理不了的动态类名。**

### 什么时候"不该做 Token"

| 情况 | 为什么 |
|---|---|
| **只有 1–2 个页面** | 三层的维护成本大于收益 |
| **设计尺度还没定** | 会得到一堆"每个组件一个 Token"的伪 Token |
| **没有主题切换需求且近期不会有** | 用 Sass 变量做编译期一致即可（§2.2 的判据） |

**第三行值得强调**：**Token 的价值在"值要能被换掉"。** 如果没有"换"的需求，**用 Sass 变量就够** —— 强行上 CSS 变量会得到一个"看起来准备充分但从不被换"的中间层。

## 2.7 动手

| 任务 | 验收 |
|---|---|
| 画出你项目的 CSS 处理链（谁在前谁在后） | 说出"内联"与"转换"哪个在前，以及顺序反了会怎样 |
| 查一次 Autoprefixer 与 Preset Env 是否都在 | 说出它们的数据源不同在哪（Can I Use vs cssdb） |
| 查一次你项目的 Sass 包出口 | 指出哪些成员靠"不转发"实现私有 |
| 列出你项目所有 Token，按三层分类 | 指出哪些是"按外观命名"的 |
| 查一次主题切换改的是哪一层 | 若改到了组件层，说出缺了哪一层 |
| 找出所有硬编码的间距与颜色 | 说出加一条 Lint 规则能否防住新增 |
| 数一次某个元素的尺寸被几个规则影响 | 若 > 1，说出叠加后是加法还是乘法 |
| 查一次你的响应式用 rem 还是 vw 还是混用 | 说出 `vw` 会忽略哪个用户设置 |
| 查一次安全区写法 | 指出"布局预留"与"当前避让"分别该用哪个变量 |
| 试一次去掉 `env()` 的退化值 | 说出结果是"报错"还是"用了初始值" |
| 对你项目的样式列表问"谁在用它" | 标出答不上来的（候选删除项） |
| 查一次生产 CSS 是几个文件 | 说出你优化的是请求数还是首屏字节数 |

**进阶挑战**（任选一项）：

1. **建一层组件库映射**：把组件库的变量单向映射到你的语义层。目标是**换库只改这一层**。
2. **做一次缩放基准审计**：列出所有影响尺寸的规则，标注每个的基准来源。目标：**每个尺寸只有一个基准**。
3. **按"有没有主人"清理一次样式**：优先处理动态类名（问写它的人）。目标是**删掉而不用回滚**。

## 2.8 本章常见误区

| # | 误区 | 纠正 |
|---|---|---|
| 1 | "PostCSS 是 Sass 的替代品" | 两者不同层：Sass 扩展**语法**，PostCSS 是 **CSS → CSS 的插件链**。官方自我描述是"用 JS 转换 CSS 的工具" |
| 2 | "Autoprefixer 和 Preset Env 装一个就行" | 数据源不同：Autoprefixer 用 **Can I Use**（管前缀），Preset Env 用 **cssdb**（管语法降级），**两个不同的问题** |
| 3 | "插件顺序无所谓" | **顺序 = 处理的依赖顺序**。Vite 官方"压缩在 PostCSS 之后"就是这条原则的实例 |
| 4 | "先降级再内联 `@import` 也行" | **会漏**：内联进来的文件不会被降级。症状是"引用的文件里语法没转换"，很难归因 |
| 5 | "PostCSS 能直接吃 SCSS" | PostCSS 的输入是 **CSS**。所以 Sass 必须在前，顺序反了会解析失败 |
| 6 | "Sass 变量就是 Design Token" | Sass 变量**编译后就消失** → **不能做运行时主题切换**。要换主题必须用 **CSS 变量** |
| 7 | "Token 只要两层就够" | **必须有语义层** —— 主题切换的本质是"同一语义换原始值"，语义层是唯一落点 |
| 8 | "Token 名字用颜色名更直观" | `--color-blue` 在换成紫色主题后**开始说谎**。语义层要按**用途**命名 |
| 9 | "`@property` 的 `initial-value` 随便填" | **必须是计算独立的值**：`10px` ✅、`2in` ✅（恒等 96px）、**`3em` ❌**（依赖父元素字号） |
| 10 | "`inherits` 可以不写" | **必填**。`syntax` 与 `inherits` 缺任一 → **整条 `@property` 无效并被忽略** |
| 11 | "`syntax` 不是 `"*"` 时也可以不写 `initial-value`" | **必需**；缺了整条规则无效 |
| 12 | "CSS 里注册的 `@property` 一定生效" | 与 JS 的 `CSS.registerProperty()` 同时注册同名属性时，**JS 优先** |
| 13 | "`@property` 能提升渲染性能" | **该 MDN 页没有提任何性能优势**。本章不给这个结论 |
| 14 | "`@property` 让变量可插值" | 该页**没有用"插值"这个词**。能确定的是**类型化后可参与动画**（有示例） |
| 15 | "用 vw 做字号会自动适配所有屏" | **它会忽略用户的字号偏好** —— 这在无障碍上是一个代价 |
| 16 | "rem 与 vw 混用更灵活" | **叠加是乘法**，不是加法。某个宽度区间可能"突然变大" |
| 17 | "移动端 1px 是渲染 bug" | 它**精确等于** `1px × DPR`。CSS 像素与物理像素本来就不是一回事 |
| 18 | "写 `0.5px` 就能解决 1px 问题" | 可能被取整成 0 或 1。伪元素 + `scale` 或阴影模拟各有代价 |
| 19 | "`env()` 不写退化值也没事" | **替换后无效且无退化值时，声明不会被忽略** —— 而是采用**初始值或继承值**。结果"看起来生效了但不是你以为的值" |
| 20 | "`safe-area-inset-*` 与 `safe-area-max-inset-*` 一样" | 前者**随可见内容区变化**，后者是**常量**（所有动态 UI 收起时的最大值）。布局预留该用后者 |
| 21 | "设了 `viewport-fit=cover` 才会让安全区生效" | **MDN 的 `env()` 页完全没提这一点**。本章不作官方断言，请以 viewport meta 文档为准 |
| 22 | "缩放系数多叠几个更保险" | **只能有一个来源**。`<meta name="text-scale">` + `env(preferred-text-scale)` 会**缩放两次**（官方警告） |
| 23 | "CSS 没有未使用代码问题" | 有，而且**更难清** —— HTML 里的 `class` 不是 import，**没有引用计数** |
| 24 | "静态搜类名就能判断有没有用" | **动态类名会漏判 → 误删**。可靠度：无引用 < 被完全覆盖 < 选择器永不命中 |
| 25 | "删样式要靠工具" | 更可靠的判据是**"有没有主人"**：答不出"谁在用它"就删。它还能处理工具处理不了的动态类名 |
| 26 | "CSS 合并成一个文件最好" | 那要看你在优化**请求数**还是**首屏字节数**。HTTP/2+ 下按需拆通常更优 |
| 27 | "按 chunk 拆就一定省" | 共享样式**可能重复打包**。要先把"共享"提取到公共 chunk |
| 28 | "组件库的变量可以直接当 Token 用" | 那会得到**两套主题系统**。应建**单向映射**：让库读你的语义层 |
| 29 | "样式冲突靠加载顺序控制" | 按需加载让顺序**不可预测**（第 1 章 §1.9）。要用 `@layer` 或特异性 |

> - **MDN `@property`（2026-05-01 修订，Baseline 2024，2024-07 起可用）**：三个描述符 **`syntax`（必填，带引号字符串）/ `inherits`（必填，无默认可省）/ `initial-value`**（`syntax` 非 `"*"` 时必需，且必须**计算独立**：`10px` ✅、`2in` ✅、**`3em` ❌**）；**缺 `syntax` 或 `inherits` 整条规则无效**；同名多条**最后一条生效**；**CSS 与 JS 同名注册时 JS 优先**；示例展示了**类型化属性参与动画**。
> - **MDN `env()`（2026-10-08 修订，Baseline 广泛可用自 2020-01）**：`env(<custom-ident>, <fallback>)`；**四个 `safe-area-inset-*` 构成矩形**，矩形内内容不会被非矩形屏幕裁切；视口为矩形且无遮挡时为 `0`，否则为**正 px 值**；另有 **`safe-area-max-inset-*`（常量，动态 UI 收起时的最大值）**；`env()` **解析时合法、计算时替换**，**替换后无效且无退化值时不忽略声明，而采用初始值或继承值**；**`<meta name="text-scale">` 与 `env(preferred-text-scale)` 叠加会缩放两次**（官方警告），且官方建议优先用 `<meta>`。
> - **Vite v8.3.4**（第 1 章已核，本章复用）：`@import` 内联靠 `postcss-import`；**压缩在 PostCSS 之后**、用 `build.cssTarget`。
>
> **五处如实标注的缺口**：① **PostCSS 首页未讲插件执行顺序、也未讲三阶段流程** —— §2.1 的排序原则标为**机制推理**，但被 Vite"压缩在 PostCSS 之后"的官方事实印证；② **MDN `@property` 页未提性能优势**，也**未使用"插值"一词**；③ **MDN `env()` 页完全未提 `viewport-fit=cover`**，故"安全区需配 viewport-fit"**不作为官方断言**；④ **`1px` 小节无官方引用**，为 DPR 定义推导；⑤ **本章不引用任何"CSS 覆盖率"工具的具体 API**（未核验）。
