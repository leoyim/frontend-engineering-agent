## 1.1 三个概念，不是一回事

"脚手架"这个词被用在三种完全不同的东西上，混起来会导致方案选型错误。

| 概念 | 做什么 | 粒度 | 生命周期 |
|---|---|---|---|
| **初始化器**（`create-*`） | 造出一个**新项目** | 整个项目 | **一次性** |
| **模板仓库**（template repo） | 提供**初始文件集合** | 整个项目 | 一次性（但可被再次拉取） |
| **代码生成器**（plop 等） | 造出**一个新文件/一组文件** | 单个模式（页面、组件、路由） | **持续**（每次新增都用） |

**三者的核心差别在"用几次"**：

- 初始化器与模板仓库：**一个项目只跑一次**；
- 代码生成器：**每天都在跑**。

**这条差别决定了一切后续设计** —— 一次性工具可以做得重（交互、装依赖、初始化 git），持续用的工具必须做得快（否则没人用）。

**而它们解决的是同一类问题的两个不同时刻**：

> **初始化器解决"第一个文件从哪来"；生成器解决"第 100 个文件怎么和第 1 个一样"。**

## 1.2 `npm create` 的真正机制：它只是语法糖

`X1.L2.01`。这一节是本领域最实用的一节，因为**几乎每个前端项目的第一步都是 `npm create xxx`，而它的机制常被误解。**

### 它做了什么

npm 官方的 `npm-init` 文档说得很清楚：

> `initializer` 实际上是一个名为 **`create-<initializer>`** 的 npm 包；该包由 **`npm-exec`** 安装，然后执行它的 **main bin**。

**官方直接给出了等价关系**：

> `npm init <package-spec>` 等价于 **`npx create-<package-spec>`**。

**所以 `npm create vite` 的真实含义是**：

```
npm create vite
  → npm exec create-vite
  → 安装并执行 create-vite 包的 bin
```

**⭐ 这条机制解释了一个常见困惑**：**`npm create xxx` 并不是 npm 内置了某个模板，它是"去 registry 找一个叫 `create-xxx` 的包并执行它"。**

**推论**：**任何一个发布到 registry 的 `create-*` 包，都可以用 `npm create` 调用** —— 包括你自己发的。

### 官方的命名转换表

| 你输入 | 实际转换成 |
|---|---|
| `npm init foo` | `npm exec create-foo` |
| `npm init @usr/foo` | `npm exec @usr/create-foo` |
| `npm init @usr` | `npm exec @usr/create` |
| `npm init @usr@2.0.0` | `npm exec @usr/create@2.0.0` |
| `npm init @usr/foo@2.0.0` | `npm exec @usr/create-foo@2.0.0` |

**注意第三行**：`npm init @usr` 转换成的包名是 **`@usr/create`**，**不是 `@usr/create-`**。这是唯一一个"没有子名"的特例。

### `npm create` 与 `npm init` 是同一个命令

官方 SYNOPSIS 写着 `aliases: create, innit`。

**所以**：**`npm create foo` ≡ `npm init foo` ≡ `npm exec create-foo`。**

**⚠️ 但有一个必须分清的分叉**：

| 命令 | 行为 |
|---|---|
| `npm init`（**不带参数**） | 走 **legacy 交互流程**，逐项问你 `package.json` 字段。**它不安装任何东西** |
| `npm create`（**不带参数**） | **没有意义** —— 它需要初始化器名 |

**这是最容易混淆的一处**：**裸 `npm init` 是最老的"创建 package.json"功能，与 `npm create` 完全是两件事。** 它们共享别名只是因为历史原因。

### 第一个坑：本机能跑，同事不能

官方文档写明：

> 如果本机**全局已安装** `create-<initializer>`，`npm init` 会**直接使用全局那个**；想要最新版或指定版本**必须显式写明**。

| 命令 | 实际用的版本 |
|---|---|
| `npm create vite` | **可能是本机全局的旧版本** |
| `npm create vite@latest` | 从 registry 拉最新 |
| `npm create vite@1.2.3` | 精确版本 |

**⭐ 这是"生成结果不一致"的头号原因**：一个人本机装过 `create-vite`，另一个人没有，于是**同一个命令生成了两套不同版本的模板**。

**纪律**：**在任何给别人的命令里，都写 `@latest` 或具体版本。** 裸写 `npm create xxx` 只在"确认自己没有全局安装"时安全。

### 第二个坑：给初始化器传参要多一个 `--`

官方原文：

> 任何额外选项都会被**直接传给**命令，所以 `npm init foo -- --hello` 会映射到 `npm exec -- create-foo --hello`。

**`--` 是 npm CLI 的参数分隔符**：

```
npm create vite@latest my-app -- --template vue
└─────── npm 消费的 ───────┘  └─ 透传给 create-vite ─┘
```

**官方在 Vite 的脚手架页里也明确标了这一点**：npm 7+ 需要额外的双横线，其他包管理器（yarn / pnpm / bun / deno）不需要。

**⚠️ 这意味着同一句命令在不同包管理器下写法不同** —— 复制粘贴时最容易失效的地方。

### 第三个坑：`--force` 会隐式打开 `--yes`

官方：`--force` 会**隐式地把 `--yes` 打开**，同时解除一堆安全保护。

**后果**：一条 `npm init --force` 可能在你没意识到的情况下**全部采用默认值**并覆盖策略性保护。**官方自己建议不清楚后果时不要用。**

### 裸 `npm init` 的默认值

`-y` / `--yes` 时全部采用默认值。官方列出的相关配置：

| 配置 | 默认 |
|---|---|
| `init-version` | `1.0.0` |
| `init-license` | `ISC` |
| `init-type` | `commonjs` |
| `init-private` | `false` |

**注意 `init-license` 默认 `ISC` 与 `init-type` 默认 `commonjs`** —— 这两项在今天的项目里**通常都不是想要的**。所以**裸 `npm init -y` 是一个会留下错误默认值的操作**，应当用你自己的初始化器，或者至少事后手动改掉。

## 1.3 模板仓库：把"版本"托管给谁

`X1.L2.01`。这一节回答一个在选型时几乎总被忽略的问题：**模板的版本，跟谁走？**

### 两条路线

| 路线 | 模板存在哪 | 版本由谁决定 |
|---|---|---|
| **A. 随包发布** | 打包进 `create-<x>` 这个 npm 包里 | **包的版本** |
| **B. 从 git 拉** | 放在一个 git 仓库（分支 / tag）里 | **分支或 tag** |

**这两条路线的后果完全不同**：

| | A. 随包发布 | B. 从 git 拉 |
|---|---|---|
| **改模板要发版吗** | **要** | 不要（提交即可） |
| **离线可用** | ✅ | ❌ 需要网络 |
| **版本可锁** | ✅ 包版本天然可锁 | ⚠️ 要显式指定 tag/commit |
| **"最新模板"含义** | 最新包版本 | **可能是某个分支的最新提交** |
| **可审计性** | 高（registry 不可变） | 中（分支可变） |

**⭐ 最关键的一行是"版本可锁"**：

> **走 git 分支的模板，如果不指定 tag 或 commit，那"模板"是一个会移动的目标。**

**而这意味着**：**同一句命令，今天和三个月后生成的项目可能不一样** —— 而且**没有任何记录告诉你差在哪**（除非你去 diff 两次的提交）。

### Vite 官方的处理方式（一个值得学的范式）

**Vite 把两类模板分开处理**（官方 Scaffolding 页）：

| 类型 | 官方路径 |
|---|---|
| **官方模板** | `npm create vite@latest` —— 由 **`create-vite`** 提供 |
| **社区模板** | 明确指向 **git 仓库**路径：`github.stackblitz.com/user/project`，或 **`npx tiged user/project my-project`** |

**这个分法的逻辑很清楚**：

> **官方模板要可控（随包发布、可锁版本）；社区模板要开放（走仓库、谁都能提）。**

**⚠️ 三处如实标注**：

1. **Vite 的 Getting Started 页没有说明官方模板是否随包发布** —— 它只说 `create-vite` 是"从基础模板快速启动项目"的工具。所以"官方模板打包在 `create-vite` 里"这一点，本章**按机制推断但不作为官方断言**。
2. **该页没有出现 `degit` 字样** —— 它推荐的是 **`tiged`**（`degit` 的社区活跃分支）。
3. **`degit` 自己的 README 两个源均抓取失败**，所以**本章不给 degit 的任何机制断言**（是否保留 `.git`、是否拉历史、支持哪些源、是否支持 tag 等，一律不写）。

### 脚手架的非交互能力：一个必查项

**一个脚手架能不能被 CI 用，取决于它有没有非交互模式。** Vite 的官方说明是一个好范例：

| 能力 | 官方写法 |
|---|---|
| 直接指定项目名与模板 | `npm create vite@latest my-vue-app -- --template vue` |
| **完全无交互** | `--no-interactive` 标志 |
| **在当前目录就地脚手架** | 项目名写 `.` |

**三条都是"可脚本化"的必要条件**：

| 缺了哪条 | 后果 |
|---|---|
| 不能指定模板 | CI 里没法选，只能吃默认 |
| 不能无交互 | CI 卡在等输入 |
| 不能就地生成 | 生成完还要 `mv`，且路径处理容易出错 |

**一条选型判据**：**如果一个脚手架只能交互运行，它就不能进 CI** —— 而"新项目初始化"恰恰是最该自动化的环节之一（它决定了所有项目的起点）。

### 官方模板清单的规模（一个参考量级）

Vite 的 `create-vite` 提供 **18 个模板**（官方清单）：vanilla / vue / react / react-compiler / preact / lit / svelte / solid / qwik，各自带 `-ts` 变体（React 额外有 `react-compiler` 与 `react-compiler-ts`）。

**这个数字有信息量**：**官方模板 ≈ 框架数 × 2（TS 变体）**。**它不是"模板越多越好"，而是"每个主流组合一个"** —— 因为模板的维护成本是乘法级的（每个模板都要跟着框架升级）。

**⚠️ 一条对照**：同一页的 StackBlitz 在线预设只有 **16 个**（少了 React Compiler 两个变体）。**同一份文档里两个清单的条目数不同** —— 说明"模板数量"这种数字必须指明出处。

## 1.4 代码生成器：与脚手架是两件事

`X1.L3.01`。这一节要讲清的是一句容易被忽略的话：**代码生成器解决的是"创建时对"，不是"之后一直对"。**

### plop 的自我定位

官方给了两层定义，都很有信息量：

> **"微生成器框架"**（micro-generator framework）

> 如果把它煮到核心，**它基本上就是 inquirer 提示与 handlebars 模板之间的胶水代码**。

**第二句是本章最诚实的一句工具自述**：**它没有魔法，就是"问几个问题 → 填模板 → 写文件"。** 知道这一点，就不会期待它有"检查能力"。

### 三个概念

| 概念 | 是什么 |
|---|---|
| **Generator** | `plop.setGenerator(name, config)` 注册；config 含 `prompts` 与 `actions` |
| **Prompt** | 用 **inquirer.js** 收集数据，`prompts` 数组原样传给 inquirer |
| **Action** | 描述"要做什么"，比如 `add` / `addMany` / `modify` / `append` / 自定义函数 |

**三者关系**：**Generator = prompts（问什么）+ actions（做什么）**，action 的输入数据来自 prompt 的答案。

### 几个值得记的机制细节

| 机制 | 官方事实 | 它解决什么问题 |
|---|---|---|
| **`add` 的 `path` 本身是模板** | 路径可写 `src/{{name}}.js`，渲染后才是真实路径 | 文件名也能按命名规范生成 |
| **`addMany` 的 `stripExtensions` 默认 `['hbs']`** | 批量加文件时自动去掉模板后缀 | 不用手动处理"模板后缀 vs 真实后缀" |
| **`modify` 的 `pattern` 默认匹配文件末尾** | 不写 `pattern` 时插在末尾 | 省掉最常见的"往末尾加一行" |
| **`append` 的 `unique` 默认 `true`** | 自动去重 | **重复跑生成器不会重复插入** ← 这一条很重要 |
| **`transform` 在写盘前执行** | 接收渲染后的字符串，返回字符串 | 生成后、落盘前做一次后处理（如格式化） |

**⭐ `unique` 默认 `true` 那条值得单独说**：它意味着**生成器可以被重复运行**（幂等）。而幂等是"生成器能不能进自动化流程"的前提 —— 一个会在重复运行时污染文件的工具，没人敢接进脚本。

### 它能非交互运行（这一点被严重低估）

**官方支持 bypass**：

| 写法 | 含义 |
|---|---|
| `plop component "some component name"` | 按**位置顺序**把值喂给 prompt |
| `plop component -- --name "my component" --type react` | 按**名字**传值 |
| `plop component _ react` | 用 `_` 占位跳过某个 prompt |

**这决定了它能不能被别的东西调用** —— 如果一个生成器只能交互跑，那它**无法在 CI、无法在 IDE 插件、无法在脚本里被复用**。

**一条判据**：**"有没有非交互模式"是判断一个生成器成熟度的第一条标准**，比它的模板多漂亮重要得多。

### ⭐ 最重要的一条：它不管"之后"

**这是本章的枢纽。** 官方文档对 plop 的定位反复围绕**新建成本**：

- "当你需要创建**一个新模式的新文件**时，**并不总能轻易找到**代码库里代表当前最佳实践的那些文件"
- "用 plop，你把'最佳实践'固化成代码"
- "它把'正确的方式'变成'**最容易的方式**'"
- 三条"为什么用生成器"的理由全部围绕新建成本：**每个 route/component/controller/test 省 5–15 分钟**

**而官方文档里没有任何 watch、diff 检查、漂移检测的能力。**

**所以定位是精确的**：

> **plop 在"创建环节"收敛一致性；它不负责"创建之后维持一致"。**

**这条推论直接决定它不能替代 Lint**：

| 问题 | 谁能发现 |
|---|---|
| 新建的组件不符合规范 | **生成器**（它生成的就是规范的） |
| 有人绕过生成器手写了组件 | **Lint**（生成器看不见） |
| 三个月后有人把生成的文件改坏了 | **Lint**（生成器不参与） |
| 生成器本身的模板过时了 | **没人**（见 §1.5 的结构性局限） |

**第二、三行是"为什么有了生成器还要 Lint"的答案。** 它们的判据完全不同：**生成器管"入口"，Lint 管"出口"。**

### 它与脚手架是组合关系，不是替代关系

**plop 官方文档里没有出现 "scaffold" 这个词**，反而演示了**把 plop 包装成脚手架**（"WRAPPING PLOP"）：

- 示例项目名 `create-your-name-app`、bin 名同名；
- 用 `node-plop` 做更细粒度控制（官方标注为"Thar be dragons"）。

**所以官方自己的立场是**：**plop 是内核，可以被外壳包成脚手架。**

**这也解释了它们的分工**：

| | 脚手架（`create-*`） | 生成器（plop） |
|---|---|---|
| 用几次 | 一次 | 每次新增文件 |
| 关心 | 整个项目的起点 | 单个模式的一致性 |
| 需要 | 装依赖、初始化 git、选框架 | 只写文件 |

**plop 刻意不内置 `git init` / `npm install`**（官方说明是为保持核心精简，改为在社区清单里维护）—— **这本身就是"我只做一件事"的表态。**

## 1.5 自研脚手架：三个必须自己做的决定

`X1.L4.01`。**这一节不讲怎么写代码，讲三个绕不过去的设计决定** —— 而第三个是真正的难点。

### 决定一：模板存在哪

| 方案 | 优点 | 代价 |
|---|---|---|
| **随包发布** | 可锁版本、离线可用、可审计 | 改模板要发版 |
| **git 仓库（tag）** | 改模板不用发版 | 依赖网络；**必须显式锁 tag** |
| **私有 registry** | 与内部包管理统一 | 需要维护 registry 权限 |
| **内网对象存储** | 大文件（图片、字体）也能放 | 需要自己的完整性校验 |

**判据**：**模板会不会经常改？**

- 一年改几次 → **随包发版**（顺带强制了 review）
- 每周都在改 → **git + tag**（但要接受"锁版本"需要自觉）

**无论选哪个，有一条底线**：**必须能回答"某个项目是用哪个版本的模板生成的"。** 做不到这一点，后面所有的升级与排查都无从下手。

### 决定二：交互还是参数

**答案不是二选一，是"两者都要"**：

| 使用者 | 需要什么 |
|---|---|
| **人** | 交互（不知道有哪些选项时要能浏览） |
| **CI / 脚本 / 其他工具** | 参数（必须有非交互模式） |

**Vite 的 `--no-interactive` 是一个好范式**：它不要求你记住所有参数，只提供一个"完全不问"的开关。

**而 §1.4 的 plop bypass 是另一个范式**：它让**同一个生成器**既能交互又能被脚本调用。

**一条纪律**：**非交互模式必须与交互模式走同一条代码路径。** 否则两者会分叉 —— CI 生成的与本地生成的不一致，而这个不一致**要等到很后面才会暴露**。

### 决定三：模板怎么升级（真正的难点）

**先看清一个结构性事实**：

> **脚手架生成的是「快照」，不是「引用」。**

**它的后果是刚性的**：

```
create-org-app v1.0 生成项目 A
                    ↓
create-org-app v1.2 改了模板（加了新的 lint 规则）
                    ↓
项目 A 完全不知道这件事 —— 它里面是 v1.0 的文件副本
```

**这不是 bug，是脚手架的固有属性。** 文件被复制出去之后，就与模板脱钩了。

**三种应对，效果差距极大**：

| 方案 | 做法 | 效果 | 风险 |
|---|---|---|---|
| **① 承认它是快照** | 生成后靠 **Lint / CI** 约束演进 | 中 | 规范要能表达成检查 |
| **② 提供升级脚本** | 把模板 diff 应用到已有项目 | 低–中 | **风险很高**：模板改动与项目改动会冲突 |
| **③ 把可变部分抽成共享包** | `@org/eslint-config`、`@org/tsconfig`、`@org/prettier-config` | **最高** | 需要包管理能力（`D1` 第 3 章） |

**⭐ 方案 ③ 的判断依据是本章最重要的一条**：

> **如果一个改进需要「在所有已存在的项目里生效」，它就不该放在模板里，而该放在共享包里。**

**因为两者的传播机制不同**：

| 载体 | 传播方式 | 升级方式 |
|---|---|---|
| **模板** | **复制**（一次性） | 无法传播 |
| **共享包** | **引用**（持续） | 改一处，全部生效（下次安装时） |

**这条判据可以直接拿去做分类**：

| 内容 | 该放哪 |
|---|---|
| 目录结构、示例代码、README 骨架 | **模板**（一次性即可） |
| ESLint / Prettier / TS 配置 | **共享包**（要能全局升级） |
| CI 工作流文件 | **模板**（但内容应尽量只引用共享配置） |
| 依赖版本约束 | **共享包**（或 `resolutions` / `overrides` 策略） |
| 构建配置（vite.config） | **共享包 + 少量模板内配置** |

**注意最后一行的写法**：**"共享包 + 少量模板内配置"** —— 现实里通常是**混合**的：可变的部分抽出去，项目特有的部分留在模板里。

**而混合的关键是**：**模板里要留一个明确的"这里可以改"的边界**。否则项目会把共享配置`抄`一份进来（因为"反正要改一点"），于是彻底失去升级能力。

### 团队落地的三个失败模式

| 失败模式 | 机制 | 症状 |
|---|---|---|
| **模板没人维护** | 它与业务 KPI 无关 | 半年后模板里的依赖全过时 |
| **模板只有一份，没人敢改** | 改动影响所有新项目 | 讨论三个月，最后由一个人硬改 |
| **每个项目都 fork 了模板** | 某个项目"就要改一点" | 模板失去意义，实际上有 N 个模板 |

**第三个是最常见的**，而它有一个精确的成因：**模板把"不该默认的东西"设成了默认**。项目要改，就只能 fork。

**所以模板设计的一条反向原则**：

> **模板里尽可能少放"有观点"的东西。有观点的东西放共享包，模板只负责组装。**

## 1.6 治理动作：六个判定阈值

| # | 现象 | 判定阈值（起点值） | 动作 | 依据 |
|---|---|---|---|---|
| 1 | 同一句命令，两个人生成的项目不一样 | **文档里写了裸 `npm create xxx`** | 改成 `@latest` 或具体版本 —— 本机全局安装会被优先使用 | §1.2 |
| 2 | 复制命令后参数没生效 | **缺 `--` 分隔符** | `npm create x@latest app -- --template vue`；npm 7+ 必须 | §1.2 |
| 3 | 新项目 `package.json` 里 license 是 ISC、type 是 commonjs | **用了裸 `npm init -y`** | 用自定义初始化器，或事后显式改掉 | §1.2 |
| 4 | 三个月前的项目与今天的同名模板生成结果不同 | **模板走 git 分支且未锁 tag** | 锁 tag/commit；并在项目里记录"由哪个版本生成" | §1.3 |
| 5 | 手写组件绕过生成器，风格不一致 | **生成器无 Lint 兜底** | 生成器管入口、Lint 管出口 —— **两者都要** | §1.4 |
| 6 | 模板改了，老项目全都没跟上 | **可全局生效的改进放在了模板里** | 抽成共享包（`@org/eslint-config` 等） | §1.5 |

### 三条使用说明

**① 阈值 1 与 2 都是"命令级"的问题，但它们的表现完全不同。**

第 1 条表现为**结果不一致**（很难归因）；第 2 条表现为**参数被忽略**（容易误判为"工具不支持这个参数"）。

**② 阈值 4 是最贵的一条。**

它的代价不是"多花了时间"，而是**"没人能回答老项目到底基于什么"** —— 于是所有升级、迁移、排查都失去起点。

**③ 阈值 6 的判据是本章的核心。**

**"这个改进需要让所有已存在的项目都生效吗？"** 答"是" → 放共享包；答"否" → 可以放模板。**这一问能解决 80% 的模板设计争议。**

### 什么时候"不该自研脚手架"

| 情况 | 为什么 |
|---|---|
| 只有 1–2 个项目 | 手工建一次比维护脚手架便宜 |
| 团队 < 5 人 | 模板 + 共享包已经够，自研 CLI 的维护成本摊不平 |
| 技术栈每半年换一次 | 脚手架会跟着重写，投入收不回来 |
| **真正痛的是"配置不一致"** | 那需要**共享包**，不是脚手架 |

**最后一行值得展开**：**很多"想自研脚手架"的需求，实际需求是"配置要能统一升级"。** 而那个问题的答案是共享包（§1.5 方案 ③），不是脚手架 —— **脚手架只能解决"起点一致"，解决不了"之后一致"。**

## 1.7 动手

| 任务 | 验收 |
|---|---|
| 用 `npm create xxx` 与 `npm create xxx@latest` 各生成一次 | 若结果不同，说出为什么（检查本机是否有全局安装） |
| 查一次 `create-<x>` 包在 registry 上的版本历史 | 说出"最新版"与"本机全局版"是否一致 |
| 试一次不给 `--` 就传参数 | 说出参数去哪了 |
| 查一次你项目的脚手架命令写在哪份文档里 | 判断它是否会在不同人机器上产生不同结果 |
| 找一个只支持交互的脚手架 | 说出它为什么不能进 CI |
| 用生成器生成同一个文件两次 | 观察是否重复插入（关注 `append` 的 `unique` 默认值） |
| 查一次你团队的生成器能否非交互运行 | 若不能，说出它失去了哪些复用场景 |
| 列出你模板里的全部内容，按 §1.5 的判据分类 | 标出哪些其实该搬到共享包 |
| 查一次某个老项目的 `package.json` | 能否回答"它由哪个版本的模板生成" |
| 数一下你团队有几个"模板的变体" | 若 > 1，说出每个变体为什么存在（是否本可避免） |

**进阶挑战**（任选一项）：

1. **做一次模板瘦身**：把模板里"所有项目都该有、且会不断更新"的部分抽成共享包。目标是**新建项目几乎不需要改配置**，且**配置升级能全局生效**。
2. **给脚手架加非交互模式**：要求与交互模式走同一条代码路径，并写一个脚本验证两种方式产出完全一致。
3. **建一份"模板来源记录"**：在每个生成的项目里留下"由哪个包版本 / 哪个 commit 生成"。目标：任意老项目都能被溯源。

## 1.8 本章常见误区

| # | 误区 | 纠正 |
|---|---|---|
| 1 | "`npm create xxx` 一定用最新版" | **本机全局装过 `create-xxx` 时会用全局那个** → 必须写 `@latest` 或具体版本 |
| 2 | "参数直接跟在后面就行" | 必须加 `--`：`npm create x@latest app -- --template vue`（npm 7+） |
| 3 | "`npm init -y` 出来的是个好起点" | 默认 `license: ISC`、`type: commonjs` —— 今天通常都不是想要的 |
| 4 | "`--force` 只是覆盖文件" | 它会**隐式打开 `--yes`** 并解除多项保护。官方建议不清楚后果时别用 |
| 5 | "模板放在 git 仓库更好维护" | 好处是改模板不用发版；**代价是"最新模板"会移动** —— 不锁 tag 就无法复现 |
| 6 | "模板随包发布太笨，改一点就要发版" | 那个"麻烦"换来的是**可锁版本、可审计、离线可用** |
| 7 | "脚手架只要好看好用就行" | **能否非交互运行**决定了它能不能进 CI —— 而新项目初始化是最该自动化的环节 |
| 8 | "模板越多越贴心" | 维护成本是**乘法级**（每个模板都要跟框架升级）。Vite 的 18 个 ≈ 框架数 × 2（TS 变体） |
| 9 | "同一份文档里的模板数一定一致" | Vite 同页的 StackBlitz 预设是 16 个、`create-vite` 是 18 个 —— **数字必须指明出处** |
| 10 | "代码生成器能保证代码规范" | 它只保证**生成时**规范。**手写的、以及之后被改坏的，它都看不见** |
| 11 | "有了生成器就不用 Lint" | **生成器管入口，Lint 管出口**。绕过生成器的手写文件只有 Lint 能发现 |
| 12 | "plop 是个脚手架" | 官方自我定位是**微生成器框架**（"inquirer 与 handlebars 之间的胶水"），且**文档里没有 scaffold 一词** |
| 13 | "生成器跑两次会重复插入" | `append` 的 `unique` **默认 `true`** —— 重复运行是安全的（幂等） |
| 14 | "生成器只能交互用" | plop 支持 **bypass**：位置参数、`--name x`、`_` 占位。**没有非交互模式的工具成熟度存疑** |
| 15 | "生成器能替代规范演进" | 它**不管"之后"** —— 官方文档无 watch / diff / 漂移检测 |
| 16 | "脚手架生成的项目会自动跟上模板改进" | **生成的是快照，不是引用**。文件复制出去就与模板脱钩了 |
| 17 | "写个升级脚本就能同步模板改动" | 风险很高：模板改动与项目改动会冲突。**优先级应低于"抽共享包"** |
| 18 | "模板里多放点配置，新项目省事" | 有观点的东西放模板 → 项目一改就得 fork → **模板退化成 N 个变体** |
| 19 | "配置都放模板里，反正会一起生成" | 若改进需要**在所有已存在的项目里生效**，它就不该在模板里，而该在**共享包**里 |
| 20 | "想统一配置就自研脚手架" | 很多这类需求的真实答案是**共享包** —— 脚手架只解决"起点一致"，不解决"之后一致" |
| 21 | "模板维护不是技术问题，加个人就行" | 它与业务 KPI 无关 → **半年后依赖全过时**。要靠"随包发版 + 必须有 reviewer"这类机制 |
| 22 | "团队小不需要脚手架" | 通常对 —— 但**"只有 1–2 个项目"与"技术栈半年一换"这两个条件更要紧** |

## 1.9 X1 领域收束

X1 只有一章，但它回答的是**全书的最上游问题**：

| 章 | 回答的问题 | 核心机制 |
|---|---|---|
| **§1.2** | 第一步命令到底做了什么 | **`npm create x` ≡ `npm exec create-x`**；全局安装优先 |
| **§1.3** | 模板的版本跟谁走 | **随包发布 vs git 分支** —— 后者不锁 tag 就无法复现 |
| **§1.4** | 怎么让第 100 个文件和第 1 个一样 | 生成器管**入口**，Lint 管**出口** |
| **§1.5** | 怎么让改进传到所有项目 | **模板是复制，共享包是引用** |

### 一条贯穿全书的收束

**X1 是"默认值"这一主题的终点。**

| 领域 | 与"默认值"的关系 |
|---|---|
| **D3 第 3 章** | 构建器的**默认值**决定产物 |
| **D5 第 3 章** | 工具的**默认值**决定覆盖率数字的含义 |
| **D6** | 流水线的**默认值**决定卡点位置 |
| **X1（本章）** | 脚手架的**默认值**决定一个新项目**从第一天起**是对的还是错的 |

**而 X1 的特殊之处在于**：**它改的不是某个项目的默认值，而是所有未来项目的默认值。**

**所以本章的判据可以压成一句话**：

> **能靠"改默认值"解决的，不要靠"写规范"解决；而改默认值的地方有两处 —— 模板（一次性）与共享包（持续）。分清这两处，脚手架才不会退化成 N 份副本。**
