## 1.1 选型的三个维度

"原生 CSS 好还是 Sass 好""要不要上 Tailwind"这类问题的争法，通常是把几个**不同维度**混在一起比。拆开之后，每个维度都有明确答案。

### 三个维度

| # | 维度 | 可能的取值 | 它决定什么 |
|---|---|---|---|
| **1** | **样式在什么时刻变成最终 CSS** | 浏览器解析 / 构建期预编译 / **运行时生成** | **运行时成本、可缓存性** |
| **2** | **类名是否唯一** | 全局共享 / **编译期重命名** / 运行时生成 | **冲突范围、可预测性** |
| **3** | **谁负责扩展 CSS 语法** | 浏览器（新特性）/ 预处理器 / PostCSS 插件 | **工具链复杂度、调试体验** |

**⭐ 三个维度里最重要的是第 1 个**，因为它是**唯一一个会给用户带来成本的**。另外两个只影响开发体验。

### 由此得到的方案定位

| 方案 | 生成时刻 | 类名 | 语法扩展者 |
|---|---|---|---|
| **原生 CSS**（含嵌套） | **浏览器解析** | 全局 | 浏览器 |
| **Sass / Less** | **构建期预编译** | 全局 | 预处理器 |
| **PostCSS** | 构建期（转换管线） | 取决于插件 | **插件** |
| **CSS Modules** | 构建期（重命名） | **编译期唯一** | 沿用 CSS / 预处理器 |
| **CSS-in-JS** | **可能运行时** | 运行时生成 | JS |
| **Tailwind** | **构建期生成** | 原子类（语义公用） | 由它生成的原子类 |

**这张表可以直接用来回答选型问题**：先问"能不能接受运行时成本"，再问"要不要类名隔离"，最后才问"语法要不要扩展"。

**而"哪个好"这个问法之所以无效**，是因为**三列可以任意组合** —— 例如 CSS Modules + Sass + PostCSS 三者共存，各自负责不同的列。

## 1.2 原生 CSS：它已经补上了两课

`D4.L2.01`。原生 CSS 近年最重要的变化是**嵌套** —— 它让"必须上预处理器"这条理由弱了很多。但同时有一条**硬边界**常被忽略。

### 嵌套：`&` 不是必需的

MDN 的说明很直接：**最基本的用法就是把子选择器写在父规则块内**，`&` 不是语法要求。

| 场景 | 能否省略 `&` | 解析结果 |
|---|---|---|
| **后代选择器** | ✅ 可以 | `.parent { .child {} }` → `.parent .child` |
| **组合器**（`+` `>` `~`） | ✅ 可以 | `h2 { + p {} }` 等价于 `h2 { & + p {} }` |
| **复合选择器** | ❌ **必须写** | 见下 |

**复合选择器为什么必须写 `&`**（MDN 原文要点）：

> 浏览器会在**没有 `&` 的选择器之间自动插入空格**。

所以：

```css
.a {
  .b  { }   /* → .a .b   （后代） */
  &.b { }   /* → .a.b    （复合，同一个元素） */
}
```

**这两行只差一个 `&`，语义完全不同** —— 而它们在 Sass 里也是这样，所以**这一条不是新知识**。

### ⭐ 硬边界：原生嵌套不能拼接

**这是本章最值得记的一条。** MDN 用一个小节专门强调：**CONCATENATION IS NOT POSSIBLE**。

```css
/* Sass 中可行，原生 CSS 中【无效】 */
.component {
  &__child-element { }   /* 不生效 */
}
```

**原因（官方）**：

> **不使用组合器时，嵌套选择器被当作「类型选择器」（type selector）。**

**后果非常具体**：

| 写法 | 原生嵌套下 |
|---|---|
| `&__element`（BEM 常见缩写） | **整块失效** |
| `.component__element`（写全） | ✅ 可以 |
| `element&`（类型选择器在前，复合） | ✅ 但解析成 `element.my-class` |

**而 `&__element` 恰好是 BEM 在 Sass 里最顺手的写法。** 于是：

> **采用原生嵌套，等于放弃 BEM 的 `&__` 缩写。**

**这不是"习惯问题"，是语法限制** —— 因为那条"无组合器即类型选择器"的规则是**类型选择器必须放在复合选择器最前**这条老规则的直接后果。

### 另外两处与 Sass 不同

| 差异 | 原生 CSS | Sass |
|---|---|---|
| **`&` 的特异性** | 类似 `:is()`，取**关联选择器列表中的最高特异性** | 无此语义 |
| **谁解析** | **浏览器** | 预处理器先编译 |

**第一行有一个实际后果**：如果 `&` 关联了多个选择器，**特异性按最高的那个算**。这意味着把选择器拆开写、合并写，特异性可能不同 —— **与 Sass 的心理模型不一致**。

### 一条容易踩的顺序陷阱

MDN 提到**嵌套声明规则**：CSS 规则**按书写顺序解析**。为了保持顺序，**嵌套之后出现的顶层声明**会被表示为 `CSSNestedDeclarations`。

```css
.foo {
  background-color: silver;
  @media screen {
    color: tomato;
  }
  color: black;   /* 顺序在后，会覆盖 @media 内的 color */
}
```

**所以"把声明放在嵌套之后"与"放在之前"结果不同** —— 而在更早的实现里，这个顺序还可能解析出错。

### 基线：不要凭记忆断言

**⚠️ 一处如实标注**：MDN 该页的正文**没有抓取到 Baseline 徽章**，所以本章**不给"Baseline 某年"的断言**。

**但可以引用一条已核验的事实**：**Vite v8.3.4 的浏览器目标基线日期是 2026-01-01**（来自 Vite Getting Started 页）。**用它作为"能不能直接用原生嵌套"的判据，比记一个年份可靠** —— 因为它是你这个项目**实际会遇到的解析器集合**（`D3` 第 3 章 §3.2 的 browserslist 机制）。

## 1.3 预处理器：Sass 的模块系统是一次断裂

`D4.L2.01`（为 `D4.L3.01` 铺底）。**Sass 近十年最重要的变化不是语法，是 `@use` 取代 `@import`** —— 而这次变化**会让一批老代码直接报错**。

### `@use` 与 `@import` 的五条差异

Sass 官方（Dart Sass 1.105.2）给了完整对照：

| 维度 | `@use` | `@import`（旧） |
|---|---|---|
| **作用域** | 变量 / 函数 / mixin **只在当前文件内可见**，官方原文：**"never adds them to the global scope"** | 注入**全局**作用域 |
| **加载次数** | **每个文件只加载一次**，CSS 只输出一次 | 可能重复加载、**重复输出 CSS** |
| **命名空间** | 默认 = URL 最后一段（去掉扩展名）；可 `as <ns>` 改名，**`as *` 取消命名空间** | 无命名空间 |
| **位置** | **必须在文件开头**，**不能嵌套在样式规则内** | 可嵌套 |
| **URL** | 每条**只能一个**，且**必须加引号** | —— |

### ⭐ "全局变量消失"的确切原因

这是从 Sass 迁移时最常见的报错，而官方给的解释很精确：

> **`@use` 只让变量、函数、mixin 在当前文件作用域内可用。它从不把它们加入全局作用域。**

**所以"变量找不到了"不是 bug，是设计目标。** 而官方还顺带解释了旧时代为什么变量名那么长：

> `@import` 时代**鼓励用户写 `$mat-corner-radius` 这种长名字来避免冲突**……

**而 `@use` 带来命名空间之后**，官方说**可以放心用 `$radius`、`$width` 这种简单名字**。

**⭐ 这条反过来印证了一个道理**：**变量命名长度的需求，来自"作用域被污染"这个前提。** 一旦有了命名空间，长名字的收益就消失了。这与 `D0` 的命名规范、`D1` 的约定设计是同一个机制 —— **当语言给了隔离，约定就不必再承担隔离的职责。**

### 三条结构约束

| 约束 | 后果 |
|---|---|
| **`@use` 必须置于文件开头**（除 `@forward` 外） | 想在 `@use` 前声明配置变量是**唯一例外** |
| **不能嵌套** | 旧的嵌套 `@import` 必须改写 |
| 每条只能一个 URL | 一次 `@use` 不能并列多个文件 |

**第二行的迁移路径（官方给的只有两条）**：

- 改成 **mixin 调用**；
- 或改用 **`meta.load-css()`**。

### 命名空间带来的另一个变化：`@forward`

`@forward` 的定位（官方）：

> 如果你想**一次加载多个文件的成员**，可以用 `@forward` 把它们的成员**从一个共享文件统一转发出去**。

**它解决的是"包的出口"问题**：

| 场景 | 手段 |
|---|---|
| 只想让某个变量在本文件可见 | `@use` |
| 想让整个包**对外**暴露一组成员 | **`@forward`**（包入口文件） |
| 想让某个成员**对整个包私有** | **不在任何入口 `@forward` 它**；甚至可以**只隐藏单个成员**而转发其余 |

**第三行是一个精妙的机制**：**"私有"不靠命名约定（如 `_` 前缀），靠"不转发"** —— 于是它是一个**结构事实**，而不是**纪律要求**。

### 跨包解析：`pkg:` 与 Node 解析器

**Dart Sass ≥ 1.71.0** 提供 **Node.js Package Importer**：

| 启用方式 | 写法 |
|---|---|
| JS API | `importers: [new NodePackageImporter()]` |
| Dart API | `NodePackageImporter()` |
| 命令行 | `--pkg-importer=node` |

**解析顺序（读 `package.json`，官方）**：

1. **`"exports"` 字段**，条件依次为 **`"sass"` → `"style"` → `"default"`**（官方推荐做法）；
2. `"sass"` 或 `"style"` 字段指向的文件 —— **仅当 `pkg:` URL 无子路径时生效**；
3. 包根目录的 index 文件 —— **同样仅当无子路径时**。

**⭐ 第 2、3 行的限定条件值得记**：`pkg:library/button` 会**直接取包根的 `button.scss`**，而不会走 `"sass"` 字段。**所以"有没有子路径"会改变解析分支** —— 这是排查"为什么引到了错误的文件"的关键。

### 两处如实标注

1. **该页没有给 `@import` 的弃用时间表**。它只说"`@use` 旨在取代旧的 `@import`"，并把 `@import` 放在站点的 **"Breaking Changes"** 分类下。**所以本章不给"某版本已移除"的断言。**
2. **该页没有"禁止混用 `@use` 与 `@import`"的明文**。混用的冲突可以按上面五条差异推导，但**那是推论，不是官方结论**。

## 1.4 PostCSS：它不是预处理器

`D4.L2.01`。**"PostCSS 是预处理器"是一个流传很广的错误定位** —— 而它会导致工具链配错。

### 它是什么

**PostCSS 是一条「CSS → CSS」的转换管线**：它把 CSS 解析成 AST，让**插件**修改，再序列化回去。

| | Sass / Less | PostCSS |
|---|---|---|
| 是否扩展**语法** | ✅ 内置（变量、嵌套、mixin…） | ❌ **本身不扩展**，靠插件 |
| 是否需要插件才能工作 | 不需要 | **插件就是全部** |
| 典型职责 | 语法扩展 | **兼容性降级、前缀、压缩、内联、语法糖** |

**所以在同一条链上，它们的位置是**：

```
Sass（扩展语法） → PostCSS（降级 / 前缀 / 优化） → 压缩
```

### Vite 的默认分工（官方）

Vite v8.3.4 的 CSS 一节给了明确的默认行为：

| 事实 | 官方内容 |
|---|---|
| **PostCSS 何时生效** | **不是必须配置，而是「有配置就自动生效」**："如果项目包含有效的 PostCSS 配置（`postcss-load-config` 支持的任何格式，如 `postcss.config.js`），它会**自动应用**到所有被导入的 CSS" |
| **执行顺序** | **CSS 压缩在 PostCSS 之后**运行，并使用 **`build.cssTarget`** 选项 |
| **生产压缩** | **默认用 Lightning CSS**；但**其余 CSS 处理仍走 PostCSS** |
| **`@import` 内联** | **靠 `postcss-import`**（预配置）；**Vite 别名在 `@import` 中同样生效**；**所有 `url()` 引用都会自动 rebase**（即使被导入文件在不同目录） |

**⭐ 第二、三行合起来排除一个常见误解**：

> **"Vite 用 Lightning CSS 处理 CSS"是错的。** 默认情况下 **Lightning CSS 只负责生产环境的「压缩」**，**转换仍由 PostCSS 承担**。

**而全量接管是显式且实验性的**：`css.transformer: 'lightningcss'`。

### 一条容易忽略的能力边界

**`@import` 内联、别名、`url()` rebase 这三件事，对 Sass / Less 同样适用，但 Stylus 不支持**（官方明确）。

**所以"换了预处理器，资源路径就错了"这一类问题，根因常常不是预处理器，而是这条链上的 rebase 行为**：

| 情况 | 结果 |
|---|---|
| 普通 `url()` | ✅ 自动 rebase |
| **以变量或插值开头的 `url()`** | ❌ **不支持 rebase**（官方标为 API 限制） |

**⚠️ 一处如实标注**：Vite 的 Features 页**没有覆盖 `css.preprocessorOptions`**（向 Sass 传 `additionalData` / `includePaths` 等）。所以本章**不给这些选项的默认值**。

### 该不该用 Lightning CSS 全量接管

| 判据 | 说明 |
|---|---|
| 官方标注为 **experimental** | 需要接受"行为可能与 PostCSS 不同" |
| **它绕过的可能是你正依赖的插件** | 例如 `postcss-import` 的 `@import` 内联 —— **官方没说明全量接管后它是否仍生效** |
| **它的强项是「降级 + 前缀」** | 那部分恰好可以只交给压缩阶段 |

**结论**：**默认路线（PostCSS 转换 + Lightning CSS 压缩）已经是"各取所长"的配置**，没必要为了"少一个依赖"去开实验开关。

## 1.5 CSS Modules：作用域是编译期的

`D4.L2.02`。它解决的是"类名冲突"，而解决方式**决定了它的成本**。

### 机制：编译期重命名

**它在构建时把类名替换成唯一标识**，组件里拿到的是一个**映射对象**：

```
源文件:  .title { ... }
编译后:  ._title_x7k2d { ... }
JS 侧:   import styles from './x.module.css'
         styles.title === '_title_x7k2d'
```

**因为它发生在编译期，所以运行时成本是零** —— 浏览器拿到的就是普通 CSS，没有额外的样式计算。

**这直接给出了它与 CSS-in-JS 的分界**（§1.6）：**同样是"作用域隔离"，一个在构建时完成，一个可能在运行时完成。**

### Vite 侧的具体规则（官方）

| 事实 | 官方内容 |
|---|---|
| **判定方式** | **任何以 `.module.css` 结尾的文件**即视为 CSS Modules 文件，导入返回模块对象（`classes.red`） |
| **配置项** | `css.modules` |
| **camelCase 具名导入** | 当 `css.modules.localsConvention` 设为 `'camelCaseOnly'` 等时可用（`.apply-color` → `applyColor`） |
| **与预处理器组合** | **在扩展名前加 `.module`**，如 `style.module.scss` |
| **Lightning CSS 下** | 改用 **`css.lightningcss.cssModules`**，而**不是** `css.modules` |

**⭐ 最后一行的坑值得单说**：**同一件事有两个配置入口，取决于用哪个 transformer。** 在 `css.transformer: 'lightningcss'` 下改 `css.modules` **不会生效** —— 而它**不会报错**。

**另一条**：`localsConvention` 是**双刃的**。开了 camelCase 之后，`.apply-color` 会被映射成 `applyColor`，于是**在 CSS 里写 `-`、在 JS 里写驼峰**，两边都要记住这条规则。

### ⚠️ 一处如实标注

**CSS Modules 的官方规范仓库文档抓取失败**（`raw.githubusercontent.com` 报错）。所以本章**不给 `:global` / `:local` 的确切语法、`composes` 的规则与限制** —— 这些都以官方规范为准。

**本章只主张能核验的部分**：**它是一种编译期的类名重命名机制，运行时零成本。**

## 1.6 CSS-in-JS：成本在运行时

`D4.L2.02`。这一节要给的是**成本结构**，而不是"该不该用"。

**⚠️ 先说清楚**：**本节无官方文档核验**（没有抓取任一 CSS-in-JS 库的官方说明）。以下内容是**机制层面的分析**，凡涉及具体库的实现，请以该库文档为准。

### 成本来自三处

| 步骤 | 什么时候发生 | 成本 |
|---|---|---|
| **① 序列化样式对象** | 组件渲染时 | 把 JS 对象转成 CSS 字符串（**每渲染一次可能重算**） |
| **② 计算唯一类名 / 哈希** | 同上 | 字符串哈希 |
| **③ 插入或更新样式表** | 同上 | 操作 CSSOM |

**关键在"什么时候发生"这一列**：**它在渲染路径上。** 而渲染路径上的每一点成本，都会乘以**渲染次数**。

**这也是为什么"作用域隔离"这件事，在编译期做和运行时做，代价差一个量级**：

| | CSS Modules | 运行时 CSS-in-JS |
|---|---|---|
| 类名计算 | **构建时一次** | **每次渲染** |
| 样式表插入 | 构建时已就绪 | 挂载时 |
| 服务端渲染 | 无额外成本 | 需要**收集并内联**样式 |

### 一条判据：什么情况下才真的需要运行时

**不是"要不要 CSS-in-JS"，而是"样式需不需要在运行时被计算"**：

| 需求 | 需要运行时吗 |
|---|---|
| 样式写在组件旁边（同文件） | ❌ 编译期方案也能（如 `.module.css` 同目录） |
| 类名不冲突 | ❌ CSS Modules 已解决 |
| **样式随 props 动态变化** | ✅ **这是真需求** |
| 主题切换 | ⚠️ **通常不需要** —— 见下 |
| 极致的设计系统约束（只允许某些值） | ❌ 编译期也能 |

### ⭐ 一条能省掉大量运行时的替代

**"随状态变化的样式"绝大多数可以落在 CSS 变量上**：

```js
// 运行时生成样式（每次渲染算一遍）
style={{ width: `${w}px`, color: active ? 'red' : 'gray' }}

// 只是把值传给浏览器（不算样式）
style={{ '--w': `${w}px`, '--state': active ? 'active' : 'idle' }}
```

**差别在"谁计算规则"**：

| 写法 | 谁把变量变成最终样式 |
|---|---|
| 生成新规则 | **你的 JS**（每次渲染） |
| **只设 CSS 变量** | **浏览器**（CSS 里已有规则） |

**所以本章的实用结论是**：

> **很多"必须上 CSS-in-JS"的需求，实际需求是"值要动态"。而「值动态」与「规则动态」是两件不同的事** —— 前者用 CSS 变量就够了。

**这也解释了 `D4.L3.02`（主题与 Design Token）为什么重要**：**Token 就是"把值抽出来"的那一步**，它让规则稳定、值可变。

## 1.7 Tailwind：成本被转移了

`D4.L2.03`。**v4 是一次范式变化**，而"收益与代价"的清单也随之变了。

### v4 的范式：CSS-first

**Tailwind 官方 Installation 页（v4.3）体现的新范式**：

| 事实 | 官方内容 |
|---|---|
| **入口写法** | 在 CSS 里写 **`@import "tailwindcss"`** |
| **`tailwind.config.js`** | **整个安装流程完全不涉及它**（官方六步里没有配置文件） |
| **官方推荐的集成方式** | **`@tailwindcss/vite` 插件** —— 原话："把 Tailwind 作为 **Vite 插件**安装是与 Laravel、SvelteKit、React Router、Nuxt、SolidJS 等框架集成**最无缝的方式**" |
| **PostCSS** | **仍作为可选项保留**，但**已非默认推荐** |
| **生成时刻** | **构建期，零运行时** |
| **类名来源** | **自动扫描**（无需声明 `content` 路径列表） |

**最后两行的官方原文很重要**：

> Tailwind 的工作方式是**扫描你所有的 HTML 文件、JS 组件与其他模板中的类名**，**生成对应的样式，然后写入一个静态 CSS 文件**。它快速、灵活、可靠 —— **且零运行时**。

**"零运行时"这四个字是它最硬的卖点**，而它**同时决定了下面那条限制**。

### ⭐ 类名拼接为什么不生效

**因为它是"扫描字符串"**。既然是静态扫描，那么：

```js
// ❌ 扫描不到：运行时才拼出来的完整类名
className={`bg-${color}-500`}

// ✅ 扫描得到：类名字面量在源码里完整出现
const map = { red: 'bg-red-500', blue: 'bg-blue-500' }
className={map[color]}
```

**这不是"框架不支持"，而是"零运行时"的必然代价**：

> **能在构建期生成，前提是"构建期能看见"。**

**这条推论还解释了另外两件事**：

| 现象 | 原因 |
|---|---|
| 从 CMS / 后端拿到的类名不生效 | 那串字符**不在源码里**，扫描不到 |
| 动态组合的类名需要"安全名单" | 要人为把组合写进源码，让扫描看见 |

**所以 Tailwind 的"动态"能力有一个明确的天花板**：**所有可能的类名组合，都必须在源码里出现过。**

### 收益与代价的转移

**原子化真正改变的不是"样式怎么写"，而是"成本落在谁身上"**：

| | 传统 CSS | 原子化 |
|---|---|---|
| **写样式** | 想一个名字 + 写规则 | **选一组类名** |
| **改样式** | 改规则（**可能影响别处**） | 改类名（**只影响这一处**） |
| **删样式** | 难判断还有没有人用 | **删掉类名就没了**（见 `D4.L3.04`） |
| **HTML 长度** | 短 | **长** |
| **类的语义** | 业务语义（`.card`） | **视觉语义**（`p-4 shadow`） |
| **设计一致性** | 靠纪律 | **靠可选值的集合** |

**⭐ 第四列与第六列是一对**：

> **HTML 变长，换来的是"样式不可能写到一半"** —— 因为你能写的类名是**有限的**（由设计尺度决定），而不是任意值。

**所以"原子化是否值得"的判据不是审美，而是**：

| 判据 | 倾向原子化 | 倾向传统 |
|---|---|---|
| 设计尺度是否明确 | ✅ 有明确的间距/字号阶梯 | ❌ 每页自由取值 |
| 样式复用方式 | 组件复用 | **CSS 类复用** |
| 团队规模 | 大（需要"不可能写错"的约束） | 小 |
| 动态主题 | **CSS 变量 + 原子类** | 变量替换 |

**⚠️ 一处如实标注**：该页**只有"fast, flexible, and reliable — with zero-runtime"这一句概括**，**没有任何体积或性能的量化数字**。所以本章**不给"能减少多少 KB"的断言**。

## 1.8 命名与组织：BEM 的边界被两件事改变了

`D4.L2.04`。BEM 常被当作"过时的规范"，但它的**原始职责**在今天有一半已经被接管了。

### BEM 在解决什么

`block__element--modifier` 的结构，有两个目的：

| 目的 | 手段 |
|---|---|
| **避免冲突** | 用长且结构化的名字降低碰撞概率 |
| **让类名可读** | 从名字读出"这个元素属于谁" |

**而这两件事在今天分别被两个东西接管了**：

| 目的 | 现在由谁负责 |
|---|---|
| **避免冲突** | **CSS Modules**（编译期重命名）/ 原子化（类名共用但语义无关） |
| **可读性 / 归属** | **仍然是 BEM**（或等价的结构化命名） |

### 被原生嵌套击穿的那一半

`D4.L2.01` 已经证明：**原生嵌套不能写 `&__element`**。

**所以 BEM 在原生嵌套下的写法只能是**：

```css
/* ❌ 失效 */
.card { &__title { } }

/* ✅ 必须写全 */
.card { }
.card__title { }
```

**而"必须写全"就丢掉了 BEM 在 Sass 时代最大的便利** —— 写一个类要敲两遍 block 名。

**于是实际选择变成三种**：

| 做法 | 代价 |
|---|---|
| **BEM + Sass**（用 `&__`） | 绑死预处理器 |
| **BEM + 原生嵌套**（写全名） | 冗长 |
| **CSS Modules + 短名** | 失去"从类名读归属"（编译后类名是哈希） |

**第三行的代价是真实的**：**编译后你在 DevTools 里看到的是 `_title_x7k2d`**，看不出它属于哪个组件。**缓解办法是配置类名模板**（把文件名/组件名编进去），但那是配置，不是默认。

### 更实用的组织判据：按「谁拥有」分

比"用什么命名法"更根本的问题是**样式放在哪**：

| 层级 | 内容 | 放哪 |
|---|---|---|
| **全局层** | reset、基础排版、CSS 变量 | 一个入口，**最先加载** |
| **共享层** | 设计系统组件、工具类 | 独立文件 / 包 |
| **组件层** | 单个组件的样式 | **与组件同目录** |
| **页面层** | 只属于某页的布局 | 页面目录 |

**⭐ 这条分层的判据是"变更范围"**：

> **问"这个样式改动会波及多少个地方"，答案决定它属于哪一层。**

- 波及全部 → 全局层（改动要最谨慎）
- 波及多个组件 → 共享层
- 只波及自己 → 组件层

**这与 `D3` 第 4 章 §4.3 的"chunk 是图的一次切分"、`D1` 第 3 章的"规范的层级"是同一个思路**：**按变更的传播范围来分层，而不是按文件的物理位置。**

### 一条常被忽略的规则

**样式加载顺序是有语义的**（CSS 的层叠依赖顺序）。所以：

> **"全局层最先加载"不是约定，是要求。**

**而按需加载（§1.9）会让这件事变复杂** —— 因为**动态导入的组件，其样式是后到的**。这直接引出下一节。

## 1.9 样式按需加载：与代码分割同一个机制

`D4.L2.05`。这一节与 `D3` 第 3 章 §3.5（代码分割）是同一件事的两面。

### 机制：样式跟着模块走

在 Vite 里，`import './x.css'` 默认会**注入 `<style>` 并带 HMR**；构建时由 **`build.cssCodeSplit`** 决定是否**按 chunk 拆 CSS**。

**所以"样式按需加载"不是一个单独配置，而是代码分割的自动结果**：

```
动态导入组件 → 它产生一个新 chunk → 这个 chunk 里的 CSS 也单独成文件 → 加载时一起到
```

**推论**：**只要用了动态导入（路由级懒加载），样式就已经在按需加载了** —— 不需要额外做什么。

### 需要额外处理的三种情况

| 情况 | 问题 | 处理 |
|---|---|---|
| **全局样式** | 它应该在**首屏**就有，不能被懒加载 | 放在入口同步导入 |
| **共享组件库的样式** | 被多个 chunk 引用 → 可能**重复注入** | 提取到公共 chunk（`D3` 第 3 章 §3.5 的分割策略） |
| **顺序依赖** | 懒加载的样式**后到**，可能覆盖掉先到的 | 用 **`@layer` / 特异性**控制，**不依赖加载顺序** |

**⭐ 第三行是本节最重要的一条**：

> **"按需加载"与"依赖加载顺序"是冲突的。**

因为**按需加载意味着顺序不可预测**（取决于用户点了什么）。所以：

| 做法 | 是否安全 |
|---|---|
| 靠"后加载的覆盖先加载的" | ❌ **不可靠** |
| 靠**特异性**分层（`@layer` / 更具体的选择器） | ✅ 可靠 |
| 靠 **CSS 变量**接受运行时值 | ✅ 可靠 |

**这条与 `D3` 第 3 章 §3.6 的"hash 必须在压缩之后算"是同一种思路**：**不要让正确性依赖于执行顺序无法保证的东西。**

### 一个必查项：`?inline`

Vite 官方有一条变更值得记：

> **从 Vite 5 起，对 `.css` 文件的默认导入与具名导入已被移除**（`import style from './foo.css'`）；**改用 `?inline` 查询**。

| 写法 | 行为 |
|---|---|
| `import './x.css'` | **注入**到页面 |
| `import s from './x.css?inline'` | 返回**处理后的 CSS 字符串**，**不注入** |

**所以"要把 CSS 当字符串拿到"这个需求，在 Vite 5 之后必须显式用 `?inline`** —— 老代码里的 `import style from './x.css'` 会直接失效。

## 1.10 治理动作：六个判定阈值

| # | 现象 | 判定阈值（起点值） | 动作 | 依据 |
|---|---|---|---|---|
| 1 | 原生嵌套下 `&__element` 不生效 | **出现一次即可确认** | 这是语法限制（无组合器即类型选择器），改成写全名或改用 Sass | §1.2 |
| 2 | 迁到 `@use` 后大量"变量未定义" | **报错集中在 `$` 变量** | 这是设计目标（`@use` 从不进全局作用域）；补 `@use` 或改用 `@forward` 统一出口 | §1.3 |
| 3 | 改了 `css.modules` 却不生效 | **项目开了 `css.transformer: 'lightningcss'`** | 该场景要用 `css.lightningcss.cssModules` —— **改错入口不会报错** | §1.5 |
| 4 | 渲染性能随组件数下降，且用了运行时 CSS-in-JS | **单次交互触发 > 100 次样式插入/更新** | 先查"值动态还是规则动态" —— **值动态改用 CSS 变量** | §1.6 |
| 5 | Tailwind 的某个类名不生效 | **类名是拼出来的** | 零运行时 = 构建期必须能看见；把组合写成字面量映射 | §1.7 |
| 6 | 懒加载后样式互相覆盖 | **同一元素被两个来源的样式命中** | 不要依赖加载顺序；用 `@layer` / 特异性 / CSS 变量 | §1.9 |

### 三条使用说明

**① 阈值 3 与 5 是"静默失效"类。**

它们**不报错**：配置写对了位置却没生效、类名生成了却没样式。**只有知道机制才能发现。**

**② 阈值 4 的排查顺序不能乱。**

先问"是值动态还是规则动态"（多数是前者），**再怀疑库**。反过来做会花很多时间去优化一个本不需要运行时的场景。

**③ 阈值 6 是最晚才暴露的一类。**

它在本地通常正常（加载顺序固定），**在生产环境偶发**（取决于用户路径）。这与 `D3` 第 5 章 §5.5 的"dev 正常 ≠ prod 正常"是同一类问题。

### 什么时候"不该换方案"

| 情况 | 为什么 |
|---|---|
| **现有方案没有具体痛点** | 换方案的收益是"理论上的"，成本是"确定的" |
| **团队还没统一设计尺度** | 上原子化会得到"任意值 + 原子类"的混合，比原来更差 |
| **只为消除类名冲突** | 先试 **CSS Modules**（增量最小），不要直接跳到 CSS-in-JS |
| **只因"原生嵌套出来了"** | 它不能拼接，**迁移成本可能高于收益** |

## 1.12 本章常见误区

| # | 误区 | 纠正 |
|---|---|---|
| 1 | "原生嵌套与 Sass 嵌套差不多" | 关键差异：**原生不能拼接**（`&__element` 失效），且 `&` 特异性类似 `:is()` |
| 2 | "BEM 的 `&__element` 在原生嵌套里也能用" | **整块失效** —— 无组合器时嵌套选择器被当作**类型选择器** |
| 3 | "原生嵌套能替代 Sass" | 不能拼接这一条就决定了：用原生嵌套要放弃 BEM 缩写 |
| 4 | "原生嵌套已经 Baseline 了，可以随便用" | 本章**未核验到 MDN 的 Baseline 徽章**。判断依据应当是**你项目的浏览器目标基线**（Vite v8 为 2026-01-01） |
| 5 | "变量名要长才安全" | 长名是 `@import` 时代**为绕开全局污染**的妥协（如 `$mat-corner-radius`）；有命名空间后可以用 `$radius` |
| 6 | "`@forward` 只是语法糖" | 它是**包的出口机制**：**不转发即私有** —— 私有成了结构事实，而不是命名约定 |
| 7 | "`pkg:` 总走 `"sass"` 字段" | **只有无子路径时**才走 `"sass"`/`"style"` 或 index；`pkg:library/button` 直接取包根的 `button.scss` |
| 8 | "`@import` 已经被移除了" | 该页**只给"旨在取代"的定位**，**未给弃用时间表**；本章不作"已移除"的断言 |
| 9 | "`@use` 和 `@import` 官方禁止混用" | 该页**没有这条明文**。混用的冲突是**可推导的**，但不是官方结论 |
| 10 | "Vite 用 Lightning CSS 处理 CSS" | 默认**只用于生产环境压缩**；**转换仍走 PostCSS**。全量接管要显式开 `css.transformer: 'lightningcss'`，且官方标为 **experimental** |
| 11 | "Vite 里 PostCSS 要手动配才能用" | **有配置就自动生效**（`postcss-load-config` 支持的任意格式） |
| 12 | "CSS 压缩在 PostCSS 之前" | **之后**，且使用 `build.cssTarget` |
| 13 | "`@import` 内联是 Vite 自己的实现" | 靠 **`postcss-import`**（预配置）；别名同样生效，`url()` 自动 rebase |
| 14 | "所有 `url()` 都会被 rebase" | **以变量或插值开头的 `url()` 不支持**（官方标为 API 限制）；**Stylus 也不支持** |
| 15 | "`.module.css` 只是命名习惯" | 在 Vite 里它是**判定方式**：任何以 `.module.css` 结尾即视为 CSS Modules 文件 |
| 16 | "改 `css.modules` 一定能配到 CSS Modules" | 若开了 `css.transformer: 'lightningcss'`，要用 **`css.lightningcss.cssModules`**，**改错入口不报错** |
| 17 | "开 `localsConvention` 没有代价" | 它把 `.apply-color` 映射成 `applyColor` —— **CSS 里写 `-`、JS 里写驼峰**，两边都要记 |
| 18 | "CSS-in-JS 的成本可以忽略" | 成本在**渲染路径上**：序列化、哈希、插入样式表，**每渲染一次都可能重算** |
| 19 | "动态样式必须上 CSS-in-JS" | **「值动态」与「规则动态」是两件事**。值动态用 **CSS 变量**就够了，规则由浏览器算 |
| 20 | "切换主题需要运行时 CSS-in-JS" | 通常不需要 —— 那是 CSS 变量换值，不是重新生成规则 |
| 21 | "Tailwind v4 还要配 `tailwind.config.js`" | **v4 是 CSS-first**：`@import "tailwindcss"`，官方安装流程**完全不涉及配置文件** |

> **本章核验到的官方事实（2026-10-17）**：
> - **Tailwind CSS v4.3（Installation）**：**CSS-first**（`@import "tailwindcss"`），**整个安装流程不涉及 `tailwind.config.js`**；官方推荐 **`@tailwindcss/vite` 插件**（"最无缝的方式"），PostCSS 仍可选但非默认；**构建期扫描类名 → 生成样式 → 写入静态 CSS，零运行时**；**自动类名扫描**（无需 `content` 数组）；**无任何体积/性能量化数字**。
> - **Sass / Dart Sass 1.105.2（`@use`）**：`@use` 与 `@import` **五条差异**（作用域 / 只加载一次 / 命名空间 / 必须置顶不能嵌套 / 单 URL 且必须加引号）；**`@use` "never adds them to the global scope"**；`@import` 时代**被迫写长名**（`$mat-corner-radius`）；`@forward` 是**包的出口**（**不转发即私有**，且可**只隐藏单个成员**）；**`pkg:` + NodePackageImporter（≥1.71.0）**，解析顺序 `"exports"`（`sass` → `style` → `default`）→ `"sass"`/`"style"` 字段 → index，**后两者仅在无子路径时生效**；嵌套 `@import` 的迁移路径为 **mixin** 或 **`meta.load-css()`**。
> - **Vite v8.3.4（Features·CSS）**：PostCSS **有配置就自动生效**；**压缩在 PostCSS 之后**，用 `build.cssTarget`；**生产默认用 Lightning CSS 压缩，其余处理仍走 PostCSS**；`css.transformer: 'lightningcss'` **全量接管为 experimental**；**`@import` 内联靠 `postcss-import`**，别名生效，**所有 `url()` 自动 rebase**（**变量/插值开头的不支持**；**Stylus 不支持**）；**任何 `.module.css` 结尾即 CSS Modules**，配置 `css.modules`，`localsConvention` 影响具名导入，**Lightning CSS 下用 `css.lightningcss.cssModules`**；**Vite 5 起移除 `.css` 的默认/具名导入，改用 `?inline`**。
> - **MDN（Using CSS nesting，2026-06-16 修订）**：`&` **非必需**（后代/组合器可省，**复合选择器必须写**）；浏览器在无 `&` 时**自动插入空格**；**`&` 特异性类似 `:is()`**；**不能拼接**（`&__child-element` 失效），原因是**无组合器时嵌套选择器被当作类型选择器**；嵌套声明按书写顺序，**嵌套后的顶层声明成为 `CSSNestedDeclarations`**；无效嵌套只丢弃该块。
