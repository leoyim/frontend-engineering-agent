## 3.1 规模化的三个新问题

前两章结束时，团队已经有了一条能跑的本地门禁链和一套提交规范。这一章要处理的是**量变引起的三个质变**：

| 质变 | 症状 | 本质 |
|---|---|---|
| **存量** | 老项目一接规则就有几千条报错 | 规则集是按**新代码应该长什么样**设计的 |
| **耗时** | 全量 lint 从秒变成分钟，门禁成了负担 | 检查成本与代码量成正比，但**每次变更只涉及很小一部分** |
| **一致性** | N 个仓库 = N 份配置，规范开始分叉 | 规范是**文档**，文档没有版本号、不能升级 |

**注意它们的共同点**：三个问题的解法方向都是同一个 —— **把判定对象从"全量"换成"变化量"**。

- 存量 → 判"新增的违规"而不是"所有违规"
- 耗时 → 判"变了的文件"而不是"所有文件"
- 一致性 → 判"配置的版本"而不是"配置的内容"

这个统一视角是本节的骨架。**每一种"换成变化量"的做法都会引入一类新的失效模式**，本章逐条讲清它们的边界。

## 3.2 存量接入：三种容忍策略与各自的代价

### 先纠正期望值

"一开规则就几千条报错"**不是配置故障**。

规则集的设计前提是"新代码应该长什么样"。一个跑了五年的仓库没有长成那个样子，是因为它是在**没有任何规则**的条件下长出来的。所以报错数的量级反映的是**历史跨度**，不是**违规严重性**。

认清这一点很重要 —— 因为错误的心智模型会导向错误的解法：以为"配置有问题"，于是去调配置；实际要做的是**设计一条还债路径**。

### 官方给的渐进依据：`"warn"`

ESLint 官方对规则级别的文档里，藏着对"渐进式接入"最接近的表述：

> 如果你不想强制合规、但仍希望 ESLint 报告该规则的违规，就把严重级别设为 `"warn"`。这**典型用于引入一条最终会被设为 `"error"` 的新规则**……或规则可能误报需要人工复核。

**要如实说明的是**：官方文档**没有**名为"渐进式接入"的专门章节。上面这句话是**唯一的官方依据**，它给的是一条使用场景，不是一套方法论。

### 三种策略，按"谁来还债"划分

| 策略 | 做法 | 谁来还债 | 代价 |
|---|---|---|---|
| **warn 起步** | 新规则先设 `warn`，观察后升 `error` | 部分靠新代码自然稀释 | 需要有人负责"升级"这个动作；`warn` 长期停留会失去意义 |
| **分区（按路径分级）** | 用带 `files` 的配置对象给不同目录配不同 severity | **新代码**：老目录降级，新目录全开 | 配置复杂度上升；"新代码写进老目录"仍会漏 |
| **抑制（suppressions）** | 一次性记录所有现存违规，之后只报新增 | **无人还债** —— 除非额外机制逼着还 | 抑制记录会变成永久免责清单（有机制应对，见下） |

**这三种不是互斥的。** 真实项目的常见组合是：**主体用抑制（一次性止血）+ 分区（给新目录全开）+ warn（用于新引入的规则试点）**。

### 分区策略的机制细节

官方给的按文件配置示例：先在全局把某规则设为 `"error"`，再用**后续的配置对象**配合 `files` 把测试文件的该规则改为 `"off"`。同一机制反向用，就是把老目录降级。

三个必须知道的合并语义（都来自官方文档）：

| 语义 | 说明 |
|---|---|
| **后者覆盖前者** | 多个配置对象指定同一规则时，后面的覆盖前面的 |
| **只写级别会与前面的选项合并** | 前面写了 `semi: ["error", "never"]`，后面只写 `semi: "warn"`，最终是 **`["warn", "never"]`** —— 选项被保留了。这是个不容易注意到的行为 |
| ⚠️ **内联注释优先级最高** | 内联注释（配置注释）在**所有配置文件之后**应用 —— 所以配置文件改不动一条已经带注释的行 |

最后一行解释了一个常见困惑：**"我在配置里把规则降级了，为什么这个文件还报？"** —— 去看那个文件里有没有内联注释。

### 抑制机制：存量接入最有力的工具

这是 ESLint 提供的一套**专门的存量接入机制**，很多人不知道它存在。

**`--suppress-all`**（官方原文）：

> 抑制现存违规，使它们在后续运行中不被报告。**它让你可以启用一条或多条 lint 规则，并只在新违规出现时被通知。** 抑制默认存储在 `eslint-suppressions.json` 中，除非用 `--suppressions-location` 另行指定。文件会被更新以加入新的抑制记录。

**这句话的分量在于"只在新违规出现时被通知"** —— 它把"检查全量"换成了"检查变化量"，而且**不需要改任何规则配置**。

相关选项：

| 选项 | 作用 |
|---|---|
| `--suppress-rule <ruleId>` | 只抑制特定规则（可多次传参） |
| `--suppressions-location` | 抑制文件位置（文件或目录；目录模式下文件名基于 **CWD 的哈希**） |
| `--prune-suppressions` | 清理不再需要的抑制项。官方原文："**当你想解决掉一条或多条被抑制的违规后，这个选项有用**" |
| `--pass-on-unpruned-suppressions` | 忽略未使用的抑制项（**默认不忽略**，见下） |

### 抑制机制最聪明的一处设计

`--pass-on-unpruned-suppressions` 的官方说明：

> 忽略未使用的抑制项。**默认情况下，如果抑制文件里存在未使用的抑制项，ESLint 会以退出码 2 退出并显示错误消息。**

**把这条和 §3.1 的框架对起来看，就能看出它为什么重要。**

抑制策略最大的风险是**只增不减** —— 记一次账就永久免责。而 ESLint 的默认行为恰好把它堵住了：

- 一个抑制项**已经不再对应任何违规**，意味着**这笔债已经还完了**（有人改了代码、或者规则本身改了）；
- 此时 ESLint **不会静默接受**，而是**以退出码 2 报错** —— 提醒你"账本该划掉了"。

**"未使用的抑制项"就是"已还完但没划账的债"。** 这条默认行为把抑制文件从"免责清单"变成了**一份需要维护的债务台账** —— 而且是**由工具强制维护**的。

注意退出码的选择也很讲究：它是 **2**（配置或工具问题），不是 1（代码有问题）。第 1 章 §1.5 讲过这两个码的责任方不同 —— **这条错误该通知规范维护者，不是通知提交者**。

**一处诚实的缺口**：该页面**未给出 `eslint-suppressions.json` 的 JSON 结构**，只说明默认文件名与"文件会被更新"。格式细节指向另一页（Bulk Suppressions）。若需要直接读写该文件，请以该页为准。

## 3.3 内联禁用注释：为什么官方说"谨慎使用"

内联注释是绕过规则的**最后一道**、也是最容易滥用的一道手段。

### 三种形式与两个语言细节

| 形式 | 作用范围 |
|---|---|
| `eslint-disable` / `eslint-enable` | 块级，可作用于文件一部分或整个文件（顶部写即整文件） |
| `eslint-disable-line` | 当前行 |
| `eslint-disable-next-line` | 下一行 |

两个容易踩的语言细节：

**其一，`/* eslint-enable */` 不带任何规则名时，会重新启用所有被禁用的规则。** 官方明确警告了这一点。若某规则希望"永不被启用"（不受后续 enable/disable 影响），写法是 `/* eslint no-alert: "off" */`。

**其二，注释可以让 ESLint 不报告违规，但不能让代码变得合法。** 官方 Tip 原文：被禁用的代码**仍需是语法合法的 JavaScript** —— ESLint **仍会解析整个文件**。所以"用注释屏蔽一段坏代码"在多数情况下不管用（解析错误不是规则违规）。

另外，注释可以附说明文字，须位于配置之后、**由两个及以上连续的 `-`** 分隔：

```js
// eslint-disable-next-line no-console -- 构建脚本需要直接输出到 stderr
```

### 官方的"谨慎使用"五条

官方在文档里给了一组明确的使用建议，值得原样列出：

1. **谨慎使用** —— 内联禁用应受限，仅在理由明确且正当的场景使用；**不应成为解决 lint 报错的默认手段**。
2. **记录原因** —— 在 `--` 之后写明禁用该规则的原因。
3. **临时方案要建后续任务** —— 若禁用只是临时应急，应创建后续任务妥善解决底层问题。
4. **靠代码评审发现** —— 鼓励团队成员定期互审，识别禁用注释背后的原因。
5. **优先用配置文件** —— 尽可能用配置文件替代禁用注释，以保持一致的项目级规则处理。

第 5 条最重要：**内联注释是"逐处例外"，配置文件是"整体策略"。** 例外多了以后，规则的实际效力就由注释数量决定了 —— 而没人知道这个数字。

### 执行机制：`reportUnusedDisableDirectives`

这套约定不是靠自觉执行的，ESLint 给了一个对应的检查：

> 报告**未被使用的 `eslint-disable` 注释** —— 即那些"禁用了在对应行本来就不会报错"的规则的注释。

**默认值是 `"warn"`。** 对应的 CLI 选项是 `--report-unused-disable-directives` 与 `--report-unused-disable-directives-severity`。

**"未使用的禁用注释"就是"过期豁免"** —— 规则早就改了、或者那行代码早就重写了，但豁免还挂在那里。它与 §3.2 的"未使用抑制项"是同一类腐化，只是粒度更细（行级 vs 文件×规则级）。

一个相邻但不同的设置容易混：**`reportUnusedInlineConfigs`** 报告的是**未生效的内联配置注释**（即没有改变既有配置的注释），默认 `"off"`，CLI 选项是 `--report-unused-inline-configs`。

## 3.4 提速：三层手段，三层失效边界

### 先纠正一个默认认知

ESLint 的并发**默认是关闭的**。

官方对 `--concurrency` 的说明：

> 该选项控制用于 lint 文件的 **worker 线程数**。

| 取值 | 含义 |
|---|---|
| **`off`（默认）** | **所有文件在主线程中 lint** |
| `auto` | 尝试自动决定最佳设置 |
| 一个正整数 | 使用指定数量的线程 |

**所以"ESLint 变慢了"的第一件事不是优化规则，而是确认这个开关有没有打开。** 这是一条零成本的改动 —— 而它的默认值之所以是 `off`，大概是因为并发会带来内存开销与行为差异，官方选择让使用者显式承担。

### 四层手段对照

| 手段 | 压缩的"量" | 机制 | 边界 |
|---|---|---|---|
| **lint-staged** | 单次提交的差异 | 第 1 章 §1.10：输入是 git index 里的路径 | 只覆盖这次提交；**不能替代全量检查** |
| **`--cache`** | 跨运行的文件级差异 | 按文件自身 + 配置判断缓存有效性 | 不跟踪文件间依赖；**被 autofix 的文件不进缓存**；不带 `--cache` 跑会删缓存文件 |
| **`--concurrency`** | 单次运行的墙钟时间 | worker 线程 | **不解决任何正确性问题**，只是更快地算错 |
| **monorepo 任务编排** | 仓库 × 任务的差异 | 见 §3.4 后半 | 需要任务**真的确定性** |

前三项在第 1 章 §1.5 与 §1.10 已经讲过机制。这里补上两个细节与第四项。

### 缓存的两个细节

**`--cache-strategy` 的取值与一个真实场景**

| 取值 | 含义 |
|---|---|
| `metadata`（**默认**） | 按文件的元数据（如修改时间）判断变化 |
| `content` | 按文件内容判断 |

官方对 `content` 的使用场景说明：

> `content` 策略在**文件修改时间变了但内容没变**的情况下有用。例如，**这会在 `git clone` 这类 git 操作中发生，因为 git 不跟踪文件修改时间**。

**`--cache-location` 的一个路径陷阱**

默认位置是 `.eslintcache`（在执行 eslint 命令的目录中）。若指定**目录**，缓存文件名会**基于当前工作目录的哈希**（如 `.cache_hashOfCWD`）。

官方给了一条容易漏掉的注意事项：

> 如果缓存的目录不存在，请确保在 *nix 系统上加尾部的 `/`，在 Windows 上加 `\`。**否则该路径会被当成文件。**

**这条与第 1 章 §1.4 的 glob 求值基准属于同一类坑**：缓存与配置的路径语义**都依赖"命令从哪个目录跑"**。这也是为什么 CI 上"本地能命中、CI 命中不了"经常不是缓存坏了，而是**跑命令的目录不同**。

### monorepo 的任务编排：以 Turborepo 为例

单仓库里 lint 的提速手段到此为止；多仓库/多包里多了一层新问题：**任务之间还有依赖**（`@app/web` 的 lint 与 `@pkg/ui` 的 lint 是两个任务，但它们的输入有交集）。

Turborepo 的机制是**双哈希**：

> Turborepo 会创建**两个哈希：一个 global hash 与一个 task hash**。任一哈希变化，该任务就会 miss cache。

| 哈希 | 输入项（官方表格择要） |
|---|---|
| **global hash** | 根与包级 `turbo.json` 解析后的任务定义 · 影响**根 workspace** 的 lockfile 变更 · **根 workspace 所用内部包的源文件** · `globalDependencies` 列出的文件内容 · `globalEnv` 列出的变量**值** · 影响运行时的 flag · **任意透传参数** |
| **task hash** | 该包的配置变更 · 影响该包的 lockfile 变更 · 包的 `package.json` · **默认是该包目录下所有受源码管理的文件**（可用 `inputs` 配置） |

**global hash 里最容易被忽略的一项是"根 workspace 所用内部包的源文件"。** 官方解释：Turborepo 会把根 `package.json` 直接或传递依赖的**所有内部 workspace 包的源文件**纳入 global hash —— 也就是说，**改一个被根依赖的共享包，会让所有任务 miss cache**。这不是 bug，而是保守的正确性选择（那个包可能影响任何任务的运行）。

**"透传参数"也算输入**同样值得注意：`turbo build -- --arg=value` 与 `turbo build` 的哈希不同 —— 包括**没有收到该参数的依赖项**。

### 缓存的三条硬边界

**① 官方前提：任务必须是确定性的。**

> Turborepo **假定你的任务是确定性的**。如果一个任务在 Turborepo 已知的输入集合下能够产生不同输出，缓存可能不会按预期工作。

这条对 lint 的含义很直接：**如果 lint 的结果依赖了 Turborepo 不知道的东西**（比如某个未被列入 `globalEnv` 的环境变量、或从网络拉取的规则集），缓存就可能给出过期结果。这与第 1 章 §1.5 里 `--cache` 的"不跟踪跨文件依赖"是同一类问题，只是**层数更深**（文件层、任务层、仓库层都要各自维护正确的输入集合）。

**② `outputs` 的默认行为对 lint 恰好是合适的。**

官方原文：

> Turborepo 会缓存任务在 `turbo.json` 的 `outputs` 键中定义的**文件产物**。命中缓存时，它会从缓存中恢复这些文件。
>
> **如果你不为一个任务声明文件产物，Turborepo 就不会缓存它们。这对某些任务是没问题的（比如 linter）** —— 但很多任务会产生你希望被缓存的文件。

注意这里的措辞：不声明 `outputs` **不等于**任务完全不缓存 —— **日志仍会被捕获与回放**（官方："Turborepo 总是捕获你任务的终端输出，并从任务首次运行时的记录把日志恢复到你的终端"）。所以 lint 任务即便没有文件产物，也能享受"命中缓存 → 立刻打印上次的日志"的效果。

**③ `--force` 的语义有一处精确性值得记。**

> 如果你想强制 turbo 重新执行一个已被缓存的任务，使用 `--force`。**注意它禁用读取缓存，而不是写入。**

**"禁读但不禁写"** —— 很多人以为 `--force` 是完全绕过缓存。实际行为是：这次重新执行，并且把新结果写回缓存。

### 三个"缓存反而更慢"的场景

官方明确列出了三种应当考虑关闭缓存的情况：

1. **执行极快的任务** —— 可能慢于一次远程缓存的网络往返；
2. **产物极大的任务**（如完整 Docker 容器）—— 上传/下载比重新生成更慢；
3. **任务自身已有缓存机制** —— 两套缓存配合容易使配置复杂化。

这三条对"要不要给 lint 开缓存"是有用的判据：**如果一次全量 lint 只要 2 秒，配缓存与调 `inputs` 的成本很可能高于收益。**

关闭方式有两种粒度：任务级 `"cache": false`（永久），或整次运行用 `--cache <options>`。

排障手段：**`--dry`**（预演将要执行什么，不真正执行）与 **`--summarize`**（输出任务的 inputs / outputs 等总览 —— **对比两次 summary 可以定位哈希差异的原因**）。后者是排查"为什么缓存不命中"的直接工具。

## 3.5 共享配置：把规范做成可版本化的制品

### 这一步为什么是"治理"而不是"打包"

前两章的规范都活在**各自仓库的配置文件里**。仓库一多，就有 N 份配置 —— 而它们会**缓慢分叉**：A 仓库为了过一个紧急需求把某条规则关了，B 仓库的主版本升级了但 ESLint 配置没跟上。

**共享配置的作用是把规范从"文档"变成"依赖"。** 依赖有版本号、能升级、能被审计、能在锁文件里留痕 —— **这是阻止分叉的唯一有效机制**：不是靠约定"大家要统一"，而是靠**版本号让不统一变得可见**。

### 命名约定

官方**推荐**（非强制）的命名：

| 类型 | 推荐命名 | 示例 |
|---|---|---|
| 普通包 | 以 `eslint-config-` 开头 | `eslint-config-myconfig` |
| npm scoped 包 | 命名为或前缀为 `@scope/eslint-config` | `@scope/eslint-config`、`@scope/eslint-config-myconfig` |

官方原话是"你可以随意命名包"，但这对**识别**没有帮助 —— 约定存在的意义是让人一眼能认出这是个 ESLint 共享配置。

### 与 eslintrc 时代的根本差别：没有短名简写

这是 flat config 迁移里一个容易被漏掉的点。

eslintrc 时代写 `extends: "airbnb"`，ESLint 会自动补全成 `eslint-config-airbnb`。**flat config 的官方共享配置文档里完全没有提到这种短名简写。** 现在的链路是：

```js
// eslint.config.js
import { defineConfig } from 'eslint/config';
import myconfig from 'eslint-config-myconfig';

export default defineConfig([
  {
    files: ['**/*.js'],
    extends: [myconfig],
  },
]);
```

**这个变化的意义超过了写法**：共享配置从"一个字符串名字"变成了**一个真实的模块依赖**。好处是类型信息与跳转可用（能直接看到配置对象长什么样），代价是**配置不再是纯声明式的** —— 它现在是一个会被执行的 JS 模块。

### 导出形式：直接导出配置本身

- 从包的主入口**直接 `export default`**；
- 官方提示**多数情况下应导出配置对象数组**，也可以导出单个配置对象；
- 因为入口就是 JavaScript，**可以从文件读取设置或动态生成**。

**一处必须说清的区分**：官方文档中**未出现 `configs` 字段**，也没有要求用它来承载共享配置。也就是说：

| 包类型 | 导出什么 | 怎么被引用 |
|---|---|---|
| **共享配置**（`eslint-config-*`） | **直接导出配置对象/数组** | `import` 后在 `extends` 数组里用 |
| **插件**（`eslint-plugin-*`） | 导出插件对象（含 `rules`、`configs` 等） | 注册到 `plugins`，或通过 `configs.xxx` 取用其预制配置 |

**混用这两种形态是配置类问题的高频来源。** 一个包如果想同时是共享配置与插件，应当导出两个入口。

### 依赖声明有明确分工

官方给了两条互补的规则，它们的逻辑恰好对称：

| 什么 | 声明在哪 | 官方原话 |
|---|---|---|
| **ESLint 自身** | **`peerDependencies`** | 推荐用 `peerDependencies: { "eslint": ">=10.0.0" }` —— **用 `>=` 范围加最低所需版本，以保障向前兼容** |
| **配置依赖的插件或自定义 parser** | **`dependencies`** | "如果你的共享配置依赖某个插件或自定义 parser，你应当在 `package.json` 中把**这些包声明为 dependencies**" |

这个分工的逻辑是：**eslint 是"宿主提供的"（同一份 eslint 服务所有配置），插件是"配置自带的能力"（跟着配置版本走）。** 搞反了的后果不同 —— eslint 写成 dependency 会导致多份 ESLint 实例；插件写成 peerDependency 会让使用者必须自己再装一遍。

### 两条必须记住的限制

**① 共享配置无法与 CLI 的 `--config` 标志一起使用。**

官方明确警告了这一点。实际影响：**排查配置问题时常用的 `eslint --config ./some-config.js` 手法，对共享配置不适用。** 这也与第 1 章 §1.4 的"用 `--config` 会让 glob 相对于 cwd 求值"叠加 —— 两个坑会一起出现。

**② 一个包可以导出多个配置，用子路径引入：**

```js
import mySpecialConfig from 'eslint-config-myconfig/my-special-config.js';
```

官方还强烈建议**始终提供 default export**，避免使用者困惑。

发布时的其他建议：加 `eslint` 与 `eslintconfig` 两个关键词便于检索。

## 3.6 度量与腐化治理：让"欠债"自动报警

### 治理的核心难处

规范一旦变成"差不多了就行"，就会**反向腐化**：**每一条被容忍的例外，都在示范"这条规则可以破"。**

所以治理的关键不是"多写几遍规范"，而是**让欠债这件事可见**。而"可见"有一个质量分级：

| 级别 | 形态 | 结局 |
|---|---|---|
| 最差 | 没人知道欠多少 | 腐化不可逆 |
| 中 | 有人能查出来（报表、仪表盘） | **需要有人定期看** —— 三个月后没人看了 |
| 最好 | **工具自己会以退出码报警** | 想忽略也忽略不掉 |

**要选第 3 种。** 这与第 1 章 §1.1 的判据是同一条：**能被自动化报警的度量才会活下来。**

### 可用的度量机制

| 机制 | 官方说明 | 能测什么 |
|---|---|---|
| **`--format json`** | 内置 formatter，输出结构化结果 | 违规的规则 ID、文件、行列 —— **按规则/文件统计存量的原始数据** |
| **`--stats`** | "把一系列详细的性能统计（**解析时间、修复时间、按规则的 lint 时间**）加到传给 formatter 的结果对象上" | 耗时分布；官方说明它"**intended for use with custom formatters**"，也可与内置 `json` formatter 一起用 |
| **`TIMING=1`** | 环境变量（第 1 章 §1.2 已提） | 显示耗时最长的 10 条规则及占比；`TIMING=50` / `TIMING=all` 可看更多 |
| **`--max-warnings n`** | 第 1 章 §1.5 已讲：警告数**严格大于** n 时以退出码 1 失败 | **"存量违规不许增加"的廉价卡点** —— 设成当前值，新问题就会顶破它 |
| **`reportUnusedDisableDirectives`** | 默认 `"warn"`，报告过期豁免 | 豁免密度与过期率 |
| **`--suppress-all` 的默认退出码 2** | 抑制文件里有未使用项即报错 | **债已还完但账没划** |

### 把度量分成四类

| 度量 | 问的问题 | 用什么 | 是否自动报警 |
|---|---|---|---|
| **存量规模** | 一共欠多少 | `--format json` 统计规则/文件维度 | 否（需人看） |
| **变化量** | 这次新增了多少 | 抑制机制 + `--max-warnings` | **是**（退出码 1） |
| **豁免过期** | 有多少失效的豁免还挂着 | `reportUnusedDisableDirectives`（默认 `warn`） | **是**（默认即警告） |
| **债务划账** | 还完了的债有没有销账 | 未使用抑制项 → **默认退出码 2** | **是** |
| **耗时分布** | 时间花在哪条规则/哪个文件 | `--stats` + `TIMING` | 否（需人看） |

**第一类与第五类需要人看，所以一定会荒废。** 实际做法是：**把它们接到 CI 的输出里，但不要指望它驱动行动**；真正驱动行动的是**第 2、3、4 类** —— 它们由 ESLint 自己以退出码或警告形式推给每次运行。

这里有一个**判断力上的细节**：`--max-warnings` 的阈值**必须进版本控制**，否则它会变成"每次被调大一点点"的橡皮筋。

### 腐化的四种形态与各自的检出机制

这是本节的收束 —— 把"腐化"从模糊感受变成可检出的现象：

| 腐化形态 | 具体表现 | 机制上的检出方式 |
|---|---|---|
| **豁免过期** | 某行早就不报错了，`eslint-disable-next-line` 还挂着 | `reportUnusedDisableDirectives`（默认 `warn`） |
| **债务划账** | 抑制项已无对应违规，还在文件里 | 默认**退出码 2** 报错 → `--prune-suppressions` 划账 |
| **规范分叉** | 各仓库配置各改各的，没人知道总共有几份 | 共享配置的**版本号** —— 锁文件里能看到各仓库用的是哪个版本 |
| **卡点失效** | `--max-warnings` 被"临时"调大后没调回来 | 该值进版本控制 + 变更走评审（**过程机制，非工具机制**） |

**注意最后一行是唯一没有工具机制的。** 这不是巧合：**所有"调大阈值"类的腐化都很难被工具自动发现**，因为它在外观上就是一个合法的配置改动。

对这一类，唯一的对策是**把它变成需要别人同意的事** —— 这与 §2.6 里 CODEOWNERS 的思路一致：**关键配置必须被另一个门禁保护。**

## 3.7 实战：规范在规模化中腐化的六种方式

> **说明**：与第 1 章 §1.12、第 2 章 §2.7 同一性质 —— 这是一条**构造示例**，每一步的现象与成因都能在本章找到对应机制。

### 阶段一：老项目第一次接入

**现象**：把共享配置接上，`eslint .` 打出 4,000 多条。

**错误反应**：开始一条条改配置、关规则 —— **这是在改"期望值"，不是在解决"存量"**。

**正确反应**（按 §3.2）：先判断存量规模（`--format json` 统计），再选策略组合：

```shell
# 一次性把现存违规全部记账，之后只报新增
npx eslint "src/**/*.js" --suppress-all
```

**一句话说清这个动作的性质**：它没有让代码变合规，**它把"存量"和"新增"分开了**。而"新增"才是从今天起能被门禁管住的部分。

### 阶段二：抑制文件只增不减

**现象**：半年后 `eslint-suppressions.json` 比一开始还大，团队觉得"这个文件是个摆设"。

**排查**：文件里有多少抑制项**已经不再对应任何违规**？

**机制上它会被自动发现**（§3.2）：

```
✖ Unused suppressions found ...
   ESLint exits with exit code 2 ...
```

**修法**：

```shell
npx eslint "src/**/*.js" --prune-suppressions
```

**这一步的价值在于"划账"这个动作本身**：它把一个"还完了的债有没有销账"的问题，变成了**每次 CI 都会提醒的事**。如果团队从来没执行过 `--prune-suppressions`，说明他们大概也用了 `--pass-on-unpruned-suppressions` 把它关掉了 —— **那就是主动把台账机制拆了**。

### 阶段三：CI 变慢，有人提议"关掉 lint"

**现象**：全量 lint 要 4 分钟，PR 反馈变慢，有人在群里说"lint 太耽误事了"。

**排查顺序**（按"零成本 → 有成本"排）：

1. **`--concurrency` 开了吗？** 默认是 `off` —— 也就是**所有文件在主线程 lint**。这是一条零成本改动；
2. **CI 上用了 `--cache` 吗？** 用了的话缓存能命中吗（同一个目录跑？`--cache-strategy` 是 `metadata` 还是 `content`）？
3. **是不是每次都全量？** 本地已有 lint-staged，CI 是否需要全量（需要，但可以考虑**只对变更的包跑**，见阶段四）。

**这一阶段最值得说的一层**：第 1 章 §1.5 说过 `--cache` 是**用正确性换速度**的开关。所以第 2 步的正确问法不是"能不能开缓存"，而是"**这个仓库有类型感知规则或跨模块 import 规则吗**" —— 有的话，CI 上开缓存会漏报跨文件问题。

### 阶段四：monorepo 里 lint 缓存命中率异常

**现象**：改了 `packages/ui` 的一个组件，结果**所有包的 lint 任务都 miss cache**。

**这一条在官方文档里有明确解释**（§3.4）：Turborepo 会把**根 `package.json` 直接或传递依赖的所有内部 workspace 包的源文件**纳入 **global hash**。如果 `packages/ui` 正好在根依赖闭包内，改它就会让所有任务 miss。

**第二现象**：PR 里只改了一个应用，但 lint 任务跑了全部包。

**排查**：`inputs` 有没有配？默认情况下 task hash 的输入是"**该包目录下所有受源码管理的文件**" —— 这个默认值是保守的（正确但慢）。

**第三现象**：本地缓存命中、CI 不命中。

**排查**：有没有用到**透传参数**（`turbo lint -- --fix` 与 `turbo lint` 的哈希不同），或者 `globalEnv` 里列了某个 CI 上取值不同的变量。

**工具**：`--dry` 预演、**`--summarize` 对比两次 summary 定位哈希差异** —— 后者是官方给的这个问题的直接手段。

### 阶段五：共享配置分叉

**现象**：五个仓库用了五个版本的 `@org/eslint-config`，没人知道差在哪里。

**成因**：共享配置**没有"统一升级"这个动作** —— 每个仓库各自 `npm update` 的结果自然不同。

**修法**（三条合起来用）：

1. **`peerDependencies: { "eslint": ">=10.0.0" }`** —— 官方推荐的范围写法，保证向前兼容；
2. **在仓库名册/仪表盘上按锁文件列出各仓库的共享配置版本** —— 让分叉**可见**（这一步是"存量规模"类的度量，需人看，因此要接进已有流程而不是新开一个）；
3. **把共享配置的升级变成一次有计划的批量动作**（配合 D2 领域讲过的 monorepo 任务编排），而不是等各仓库自然漂移。

**注意排查顺序里的一个坑**：想调试共享配置时，**不能用 `--config`**（§3.5，官方明确共享配置无法与 `--config` 一起使用）。可行的替代是把配置内容临时 `import` 进本地的 `eslint.config.js`。

### 阶段六：跨仓库的"新代码"定义不一致

**现象**：A 仓库的老目录全降级了、B 仓库没降级，于是同一个组件在两边报不同的错。

**成因**：**"新代码"是一个人为划定的边界**，它必然带主观性。A 仓库选的是"按目录分区"，B 仓库选的是"抑制一切现存违规"—— **两种策略对"哪些算新代码"的定义不同**。

**这一条没有工具能解决。** 它是 §3.2 三种策略的**语义差异**：抑制策略下，"新代码"指的是"抑制记录之后新增的违规"；分区策略下，"新代码"指的是"写在新目录里的代码"。二者不等价。

**修法**：**跨仓库统一时，统一的不是配置内容，而是策略选择。** 各仓库可以有不同版本的共享配置（版本号让差异可见），但**容忍策略应当一致** —— 否则"统一规范"这句话在跨仓库评审时无从执行。

### 反过来看：这一章该放进运维手册的几条

| 现象 | 先查什么 | 对应机制 |
|---|---|---|
| 一开规则几千条报错 | 不是配置错，是历史跨度 | §3.2 期望值 |
| 抑制文件越滚越大 | 有没有跑过 `--prune-suppressions` | §3.2 退出码 2 的默认行为 |
| 配置里降级了但某个文件还报 | 该文件里有内联注释 | §3.3 内联注释优先级最高 |
| 注释里 `eslint-enable` 之后全都不报了 | 不带规则名的 enable 会重启用**所有**规则 | §3.3 |
| 想去掉一段坏代码的报错 | 注释不改语法合法性 | §3.3 |
| lint 慢 | `--concurrency` 默认是 `off` | §3.4 |
| 本地缓存命中、CI 不命中 | 跑命令的目录、`--cache-location`、透传参数 | §3.4 |
| monorepo 改一个包所有任务都 miss | 它在不在根依赖闭包内 | §3.4 global hash |
| `--force` 之后还是有缓存 | `--force` **禁读不禁写** | §3.4 |
| 调共享配置调不动 | 共享配置**不能与 `--config` 一起用** | §3.5 |
| 共享配置装了两份 ESLint | eslint 应声明为 `peerDependencies` | §3.5 |
| `--max-warnings` 越调越大 | 该值是否进版本控制、变更是否走评审 | §3.6 卡点失效 |

## 3.8 动手

**每一项都要求说出理由**：

| 任务 | 验收 |
|---|---|
| 在一个有现存违规的仓库跑 `--suppress-all`，再新增一处同类违规 | 说出两次运行分别报了什么，以及"只在新违规出现时被通知"这句话对应哪个选项 |
| 手工删掉一条违规代码（使某个抑制项失去对应） | 记录退出码，说出**为什么它是 2 而不是 1**，以及正确的处理动作 |
| 用 `--pass-on-unpruned-suppressions` 再跑一次 | 说出这个选项在治理意义上**关掉了什么** |
| 给某文件加一条 `/* eslint-disable-next-line no-alert */`，但该行本来就不报错 | 说出默认哪个选项会报告它、默认级别是什么 |
| 写一段 `/* eslint-disable no-alert */ ... /* eslint-enable */ ... alert('x')` | 说出为什么最后的 `alert` 仍然被报（或不被报），依据是哪一条 |
| 在配置里把某规则降级为 `warn`，但该文件仍报 `error` | 说出原因与优先级规则 |
| 对比 `semi: ["error","never"]` 之后写 `semi: "warn"` 与写 `semi: ["warn","never"]` | 说出两者是否等价，依据是哪一条合并语义 |
| 用默认设置跑一次 lint 计时，再加 `--concurrency auto` 对比 | 说出默认值是什么、这一改动**解决**与**不解决**什么问题 |
| 把 `--cache-location` 指向一个不存在的目录（不加尾部斜杠） | 记录现象，说出官方给的注意事项 |
| 在一个 `git clone` 出来的仓库里用 `--cache` | 说出哪种 `--cache-strategy` 更适合这个场景、为什么 |
| 用 `--format json` 统计违规次数最多的三条规则 | 说出这份数据属于本章四类度量中的哪一类、为什么它**不会自己驱动行动** |
| 用 `--stats` 输出一次结果 | 说出它加进去的三类时间是什么、官方建议配合什么使用 |
| 建一个最小的共享配置包并用它 | 说出为什么**不能**用 `--config` 调它 |
| 在共享配置的 `package.json` 里把 eslint 写成 `dependencies` | 说出后果，以及官方推荐写在哪个字段、用什么范围 |
| 在 monorepo 里改一个**被根依赖的内部包**的源码，跑两次 lint | 记录命中情况，说出它命中/未命中 global hash 还是 task hash 的哪一项 |
| 用 `--summarize` 对比两次运行的 summary | 说出这个方法用来定位什么问题 |
| 对一个"只要 2 秒"的 lint 任务配缓存 | 说出官方列的三个"缓存反而更慢"场景里，它属于哪一个 |

**进阶挑战**（任选一项）：

1. 给一个真实存量项目设计一套**完整的还债路径**：写清用哪几种容忍策略的组合、每种策略的退出条件是什么、谁负责哪个动作。**要求每一项都有一个"会自动报警"的机制对应**，没有对应机制的项目要显式标为风险。
2. 用 `--format json` + `--stats` 出一份**该项目的规范健康报表**，至少包含：存量规模（按规则 Top 10）、豁免密度（禁用注释数/千行）、债务划账状态（未使用抑制项数）、耗时分布（Top 3 慢规则）。然后判断：这四项里哪几项**能自动化**、哪几项**必须人工看**。
3. 拿一个 monorepo，用 `--summarize` 找出**一次缓存未命中的真实原因**，并用官方文档里的输入项表逐项排除。

## 3.9 本章常见误区

| # | 误区 | 纠正 |
|---|---|---|
| 1 | "把规则都关了，然后慢慢开" | 关掉规则等于**门禁失效**；`--suppress-all` 是把**存量与新增分开**，不是关规则。两者性质不同 |
| 2 | "官方有专门的渐进式接入指南" | 官方**没有**专章。唯一的依据是规则级别文档里那句"**典型用于引入一条最终会被设为 `error` 的新规则**" |
| 3 | "抑制文件记一次就永久免责" | 官方**默认**：抑制文件里存在**未使用的抑制项**时，ESLint **以退出码 2 退出并报错** —— 它逼你划账 |
| 4 | "未使用的抑制项报错是 bug" | 它是刻意的：**未使用的抑制项 = 已还完但没划账的债**。用 `--prune-suppressions` 处理 |
| 5 | "抑制项报错用退出码 1" | 是 **2**（配置或工具问题）。责任方是**规范维护者**，不是提交者 |
| 6 | "`--pass-on-unpruned-suppressions` 只是个方便的开关" | 它**关掉了抑制机制的核心**：抑制文件因此变成只增不减的永久免责清单 |
| 7 | "内联禁用注释是解决报错的常规手段" | 官方明确"**不应成为解决 lint 报错的默认手段**"，并列了五条谨慎使用建议 |
| 8 | "配置里把规则降级就一定能压住报错" | **内联注释优先级最高**，在所有配置文件之后应用 |
| 9 | "`/* eslint-enable */` 只重启用之前 disable 的那些" | **不带规则名时会重新启用所有被禁用的规则**（官方警告） |
| 10 | "可以用注释屏蔽语法错误的代码" | 官方 Tip：被禁用的代码**仍需是语法合法的 JavaScript** —— ESLint 仍会解析整个文件 |
| 11 | "批量豁免只能靠人工加注释" | 用 `--suppress-all` / `--suppress-rule` 批量记录，落在 `eslint-suppressions.json` |
| 12 | "ESLint 默认会多线程跑" | **`--concurrency` 默认是 `off`** —— 所有文件在主线程 lint |
| 13 | "开了并发就没有正确性问题了" | `--concurrency` **只影响墙钟时间**，不解决任何缓存的过期问题 |
| 14 | "`--cache` 只是更快" | 第 1 章已讲的三条仍在：不带 `--cache` 跑会删缓存文件、被 autofix 的文件不进缓存、**不跟踪跨文件依赖** |
| 15 | "`--cache-strategy` 用默认的就行" | 默认是 `metadata`。**`git clone` 后修改时间会变而内容没变**，官方建议这时用 `content` |
| 16 | "`--cache-location` 指向不存在的目录也没关系" | 官方明确：*nix 上要加尾部 `/`、Windows 上 `\`，**否则该路径会被当成文件** |
| 17 | "monorepo 缓存不命中就是缓存坏了" | 官方解释了原因之一：**根 workspace 所用内部包的源文件**纳入 global hash，改它会让**所有任务** miss |
| 18 | "透传参数不影响缓存" | `turbo build -- --arg=value` 与 `turbo build` 哈希不同，**且含未收到该参数的依赖项** |
| 19 | "`--force` 会完全绕过缓存" | 官方原文：**它禁用读取缓存，而不是写入** |
| 20 | "给 lint 任务配缓存总是划算的" | 官方列了三个"缓存反而更慢"的场景：**执行极快的任务**、产物极大、任务自身已有缓存机制 |
| 21 | "不声明 `outputs` 就是完全不缓存" | 不声明文件产物 ≠ 任务完全不缓存 —— **日志仍会被捕获并回放**。官方也说这对 **linter 这类任务没问题** |
| 22 | "任务缓存不需要任务有确定性" | 官方前提：Turborepo **假定任务确定性**。输出依赖它不知道的输入时，缓存会给出过期结果 |
| 23 | "共享配置可以用 `--config` 调" | 官方明确警告：**共享配置无法与 CLI 的 `--config` 标志一起使用** |
| 24 | "共享配置应该导出 `configs` 字段" | 官方文档**未出现 `configs` 字段** —— 共享配置是**直接导出配置对象/数组**。`configs` 是**插件**的形态 |
| 25 | "flat config 还支持 `extends: 'airbnb'` 这种短名" | 官方共享配置文档**完全没有提到短名简写**；现在是 `import` 拿到对象后放进 `extends` 数组 |
| 26 | "共享配置里 eslint 应该写进 `dependencies`" | 官方推荐 **`peerDependencies`**，并用 `>=` 范围加最低所需版本以保障向前兼容 |
| 27 | "共享配置依赖的插件也该是 peerDependency" | 相反：**插件与自定义 parser 应声明为 `dependencies`**。分工是"eslint 宿主提供、插件配置自带" |
| 28 | "`--max-warnings` 调大一点是小事" | 它是**唯一没有工具机制**能自动发现的腐化形态。对策是**该值进版本控制 + 变更走评审** |
| 29 | "内联禁用注释的数量不重要" | 它是"**豁免密度**"这个度量。例外多了以后，规则的实际效力由注释数量决定 —— 而没人知道这个数字 |

## 3.10 D1 领域收束

三章、13 个节点到此收束。**D1 回答的是一个组织性问题**：

> **一个人的正确，怎么变成一群人的默认？**

| 章 | 回答什么 | 核心机制 |
|---|---|---|
| **第 1 章** | 写法怎么统一并自动生效 | **检查工具的执行模型与配置解析**（"哪个环节在什么条件下失效"） |
| **第 2 章** | 变更怎么进入仓库并被接受 | **提交 → 评审 → 门禁**的链路 |
| **第 3 章** | 规则怎么分工与演进 | **规范的分层**与度量 |

### 一条贯穿 D1 的判据

> **这条规范能不能被机器执行？**

| 规范形态 | 能执行吗 | 长期结果 |
|---|---|---|
| 写在文档里 | ❌ | **会衰减**（新人不读、老人忘） |
| 写在评审清单里 | ⚠️ 靠人 | 疲劳后失效（`D5` 第 4 章的"假红率"机制） |
| **写成可执行的检查** | ✅ | **会一直生效** |

**⭐ 这条判据解释了 D1 为什么把"自动生效"放在第 1 章**：**能自动执行的约定才叫默认值，其余只是建议。**

**而它与 `D5` 第 3 章 §3.4 的"门禁四条准入判据"是同一件事的两端**：**D1 决定"要不要写成检查"，D5 决定"写成的检查能不能当门禁"**。

### D1 与 X1 的分界

| | D1 负责 | X1 负责 |
|---|---|---|
| 对象 | **约定本身**（写法、提交、评审） | **把约定变成默认值的载体**（模板、共享包、脚手架） |
| 判据 | "能不能被机器执行" | "改进需不需要在所有已存在项目生效"（`X1` 第 1 章 §1.5） |

**一句话记住边界**：**D1 写下规则，X1 让规则出现在第一个文件里。**
