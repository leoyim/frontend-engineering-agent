## 2.1 依赖树是怎么被摊平的：提升与硬链接

### 先明确一个前提：依赖树是"求解"出来的

`package.json` 里写的是**版本范围**（约束），而磁盘上必须是**确定的版本组合**。所以安装这件事的本质是：

```text
输入：一棵由许多包各自声明范围构成的约束集合
求解：找到一组满足全部约束的版本组合，并决定它们在磁盘上的布局
输出：node_modules 目录树 + lockfile（求解结果的记录）
```

**"布局"是一个独立的设计选择**——同样一组版本，可以有完全不同的磁盘形态。而**绝大多数"包管理玄学问题"都源于布局与声明关系的错位**。

### 三代布局策略

| 代 | 代表 | 布局机制 | 代价 |
|---|---|---|---|
| 嵌套 | 早期 npm | 每个包自带一份 `node_modules`，依赖层层嵌套 | 大量重复（同一个包存很多份）、路径超长 |
| **提升（hoisting）** | npm 3+ / yarn classic | 尽量把依赖**提到最顶层**，只有版本冲突时才嵌套 | 顶层目录里出现大量"你没声明过"的包 → 幽灵依赖 |
| **内容寻址 + 链接** | pnpm | 全局 store 存一份内容（用**内容哈希**寻址），项目中用**硬链接 + 符号链接**组织 | 兼容性要求（部分工具不认符号链接） |

### 提升的机制：为什么顶层会"多出"很多包

```text
你声明：A@^1.0.0
A 声明：B@^2.0.0
结果：
  node_modules/A
  node_modules/B      ← 你没声明过它，但它被"提"到了顶层
```

**提升的目的是去重**：把 `B` 放在顶层，其他也依赖 `B` 的包就能共用一份。但如果另一个包依赖 `B@^1.0.0`，顶层只能放一个版本，于是：

```text
node_modules/B            ← 被提升上来的那个版本
node_modules/C/node_modules/B   ← 版本冲突时嵌套在消费者里面
```

**这就是"我明明只装了一个 React"却经常在 `npm ls react` 里看到两三个版本的原因**（回链 D2 第 1 章 §1.7 的双包危害）。

### pnpm 的机制：内容寻址 + 两层结构

```text
~/.pnpm-store/…            ← 全局内容库：同一份内容只存一次
node_modules/.pnpm/        ← 虚拟 store：所有包的真实位置
node_modules/A  →  符号链接到 .pnpm/A@1.0.0/node_modules/A
```

两件事因此成立：

| 结论 | 机制 |
|---|---|
| **磁盘占用大幅下降** | 同一内容在全局只存一份，项目里是**硬链接**（不是复制） |
| **依赖关系变得严格** | 顶层 `node_modules` 只放**你直接声明**的包（符号链接），传递依赖藏在 `.pnpm` 里——**Node 的解析算法从代码所在目录向上找，找不到"没声明的包"** |

**第二行是关键**：pnpm 的严格性不是"额外加的检查"，而是**布局变化导致的自然结果**。

### 对照表（选型的实际依据）

| 维度 | npm（提升） | yarn classic（提升） | pnpm（链接） |
|---|---|---|---|
| 磁盘占用 | 高 | 高 | **低** |
| 安装速度 | 中 | 中 | 快（store 命中时极快） |
| 依赖严格性 | 弱（可访问未声明依赖） | 弱 | **强** |
| 老工具兼容性 | 好 | 好 | 偶有问题（不认符号链接） |
| 迁移成本 | — | — | 迁入时**会暴雷**（把它当"bug"其实是修正） |

### 排查工具

| 工具 | 用途 |
|---|---|
| `npm ls <pkg>` / `pnpm why <pkg>` | 看某包为什么被装、装了几个版本 |
| `npm ls --all` | 完整依赖树（大项目慎用） |
| `node_modules/.pnpm` 目录 | pnpm 下确认真实布局 |
| `require.resolve("pkg")` | **运行时**看实际解析到哪个文件——比看目录更准 |

最后一行值得强调：**"它到底加载了哪一份"这个问题，应该用运行时答案，而不是猜**。

## 2.2 幽灵依赖：能跑，但没资格跑

### 定义与机制

```js
// src/index.js
import _ from "lodash";     // ← 能跑
```

```json
// package.json
{ "dependencies": { "axios": "^1.0.0" } }   // ← 从没声明 lodash
```

它为什么能跑？因为 本章 §2.1 的**提升**把某个传递依赖的 `lodash` 放到了顶层，而 Node 的模块解析算法是**从代码所在目录逐级向上查找 `node_modules`**——顺路就找到了。

**幽灵依赖（phantom dependency）** 指的就是这种"实际用了、但没声明"的依赖。

### 危害：三层

| 层次 | 表现 |
|---|---|
| **脆弱** | 依赖树一变（上游升级、换包管理器）它就消失 → 报 `Cannot find module` |
| **版本失控** | 你用的版本由**上游**决定；上游一变，你的运行行为跟着变 |
| **事实失真** | `package.json` 不再是"这个包需要什么"的准确描述，别人（与工具）无法据此判断 |

**"从 npm 迁到 pnpm 时大面积报错"就是这一条**：pnpm 的布局让未声明的包**真的找不到**，于是所有幽灵依赖同时暴露。**这不是 pnpm 的 bug，而是它把一直存在的错误显性化了。**

### 检测与修复

| 手段 | 说明 |
|---|---|
| 用 pnpm（或任何严格布局）跑一次构建 | 最有效的被动发现方式 |
| 专用检查工具 | 扫描源码里的 import 与 `package.json` 做比对 |
| lint 规则 | 禁止导入未声明依赖 |
| **修复** | **显式声明**——即使上游也依赖它，你用了就该写 |

## 2.3 SemVer 与版本范围：声明的是"可接受区间"

### SemVer 的三段与它的承诺

```text
MAJOR . MINOR . PATCH
  1   .   2   .   3
  不兼容  新增功能  修 bug
```

**1.0.0 之前不适用这套承诺**——`0.x` 表示"接口可能随时变"：

| 范围 | 实际允许 |
|---|---|
| `^1.2.3` | `>=1.2.3 <2.0.0` |
| `^0.2.3` | `>=0.2.3 <0.3.0`（**只允许 MINOR 位不动**） |
| `^0.0.3` | `>=0.0.3 <0.0.4`（**只允许 PATCH**） |

**`^` 的规则是"不允许修改最左侧的非零位"**——所以 `0.x` 包的实际升级幅度比你以为的小得多。这是"我的 `^0.1.0` 依赖为什么从不自动升级"的答案。

### 常见范围写法

| 写法 | 含义 | 何时用 |
|---|---|---|
| `1.2.3` | 精确 | 极少（想锁死时用 lockfile 更合适） |
| `^1.2.3` | 允许 MINOR 与 PATCH | **默认选择**（库作者友好） |
| `~1.2.3` | 只允许 PATCH | 对上游不太信任时 |
| `>=1.2.3 <2` | 显式区间 | 表达特殊约束 |
| `1.2.x` / `*` | 宽松到几乎任意 | 危险 |
| `a \|\| b` | 并集 | 跨大版本的兼容区间 |

### 一条常被忽略的规则：预发布版本默认不匹配

```text
1.3.0-beta.1  不满足  ^1.2.3
```

**预发布版本只有在该范围的同一 `[major, minor, patch]` 上显式包含预发布标识时才会被选中**。所以"能不能自动升到 beta"这件事，默认答案是"不能"。

### 范围与可复现性的张力

| 概念 | 回答的问题 |
|---|---|
| **版本范围**（`package.json`） | "我能接受哪些版本" |
| **lockfile** | "我实际用了哪个版本" |
| **integrity 哈希** | "我用的内容没被改过吗" |

三者缺一不可：**只写范围 → 不同时间装出不同结果；只锁版本 → 无法表达兼容策略**。这条张力就是下一节 lockfile 的存在理由。

## 2.4 lockfile：它记录什么、形状由谁决定

> D0 第 7 章 §7.7 已给基础结论（三层关系、`npm install` 会改写而 `npm ci` 不会、必须提交）。本节只讲机制层。

### 它记录的不是"版本列表"，而是"整棵树"

| 字段 | 作用 |
|---|---|
| 包标识 | registry 路径或**本地链接**（workspace 场景会出现 `link:` / `file:`） |
| 精确版本 | 求解结果 |
| **integrity** | **SRI 格式的哈希**（如 `sha512-…`）——校验"下载到的字节"，而不是"包名对不对" |
| 依赖声明 | 该包自己的 `dependencies` / `peerDependencies` |
| engines / os / cpu 等 | 环境约束 |

**integrity 值得单独记住**：它防的是"注册表被投毒/传输被篡改"这一层。**它挡不住"这个版本本身就是恶意提交"**——那是 本章 §2.9 的问题。

### 形状受布局策略影响，因此不可跨包管理器互换

同一组依赖，npm 与 pnpm 生成的 lockfile **结构不同**（提升布局与链接布局的树形不一样）。

**推论**：把一个项目从 npm 换成 pnpm，**不能沿用旧 lockfile**，必须重新生成并重新验证。这也是迁移时"必须跑一次完整 CI"的原因。

### `npm ci` 的校验逻辑

```
前提：必须存在 lockfile
行为：删除 node_modules → 严格按 lockfile 安装 → 不解析、不改写
校验：若 lockfile 与 package.json 不同步 → 直接失败（退出码非 0）
```

**最后一行是关键**：在 CI 里它表现为**构建失败**，而失败原因写的是"lock 与 package.json 不一致"——这正是它要拦的情况（有人只提交了其中一个）。

**各包管理器的冻结模式：**

| 包管理器 | 命令 | 语义 |
|---|---|---|
| npm | `npm ci` | 只按 lockfile 安装 |
| pnpm | `pnpm install --frozen-lockfile` | 同上 |
| yarn | `yarn install --immutable` | 同上 |

### lockfile 冲突的处理原则

**不要手改。** 理由不是"怕乱"，而是它**同时承载了版本、integrity 与树结构**，手工合并几乎一定会产出"结构自洽但哈希对不上"的结果。正确做法是删掉冲突标记后用命令重新生成，再跑一次完整安装验证。

## 2.5 `peerDependencies`：把版本决定权交还给宿主

### 语义："由宿主提供"

| 字段 | 语义 | 谁控制版本 |
|---|---|---|
| `dependencies` | 我**自己需要**它 | 我 |
| `devDependencies` | 我**开发时**需要它 | 我 |
| **`peerDependencies`** | **宿主必须提供它** | **消费者** |

**组件库与插件必须用 peer 的原因有两个**：

1. **避免重复实例**——如果组件库把 React 写进 `dependencies`，消费者就很可能装出两份 React（回链 D2 第 1 章 §1.7 的双包危害），Hooks 直接报错。
2. **版本由宿主决定**——库不该替应用决定"用哪个版本的框架"。

### npm 7+ 的行为变化改了常见成因

| 版本 | 行为 |
|---|---|
| npm 6 及以前 | peer 不满足只**警告**，不装 |
| **npm 7+** | **自动安装** peer 依赖 |

这条变化带来一个反直觉结果：**"漏写 peer"与"写错 peer"的后果变得更严重了**——以前只是警告，现在可能真的装出一个你不期望的版本，或者直接抛 `ERESOLVE` 冲突错误。

处理手段：

| 手段 | 用途 |
|---|---|
| `overrides`（npm）/ `resolutions`（yarn）/ `pnpm.overrides` | **强制统一**某依赖的版本 |
| `--legacy-peer-deps` | 退回旧行为（**临时手段，会引入隐患**） |
| 升级到兼容版本 | 真正的解法 |

### 怎么验证"有没有重复实例"

```bash
npm ls react          # 看装了几个版本、分别被谁要求
pnpm why react
```

**判据**：理想情况是**只有一个版本**。出现多个时，看它们是否是同一包的**不同副本**——是则说明存在重复实例风险。

### 什么时候该用 `dependencies` 而不是 peer

| 场景 | 选择 |
|---|---|
| 组件库、插件、框架适配层 | **`peerDependencies`** |
| 纯工具函数库（lodash 这类） | `dependencies`（多份也无害） |
| 构建工具、编译器 | **`devDependencies`**（属构建期） |

## 2.6 私有 registry 与发布流程

### registry 是一个 HTTP API

npm registry 不是"npm 客户端的一部分"，它就是一个约定格式的 HTTP 服务：

| 端点类型 | 作用 |
|---|---|
| packument | 包的元数据（版本列表、dist 信息） |
| tarball | 包内容的压缩包 |

**这条认知的价值**：私有 registry 只是"另一台实现了同一套接口的服务器"——自建（Verdaccio / Nexus / Artifactory）、托管（GitHub Packages、云厂商制品库）都成立。

### 认证与 scope 绑定

```ini
# .npmrc
@myorg:registry=https://npm.example.com/
//npm.example.com/:_authToken=${NPM_TOKEN}
```

两行各有作用，缺一不可：

| 行 | 作用 |
|---|---|
| `@myorg:registry=…` | **把 scope 绑定到私有源**——这条防的是 **dependency confusion**（见 本章 §2.9） |
| `//host/:_authToken=…` | 认证凭据。**用环境变量而非明文**，CI 里尤其重要 |

### 发布流程与它的两条铁律

```bash
npm version patch          # 升版本并打 tag
npm run build               # 产出构建物
npm publish                 # 发布
```

| 铁律 | 原因 |
|---|---|
| **已发布的版本不能覆盖** | 版本号是"不可变标识"，覆盖会破坏所有消费者的 integrity 校验 |
| **撤回（unpublish）是破坏性操作** | 有严格的时间与条件限制；撤回会让依赖它的项目**无法安装** |

### 包里带什么：`files` 与 `.npmignore`

| 字段 | 语义 |
|---|---|
| `files` | **白名单**——只打这些（推荐） |
| `.npmignore` | 黑名单（`files` 存在时优先级更低） |

**包体积治理从发布前开始**：忘了配置会把源码、测试、构建缓存一起发上去。检查手段是打包前的干跑（`npm pack --dry-run`）看清单。

### 生命周期脚本与构建产物

| 脚本 | 时机 |
|---|---|
| `prepare` | 本地安装与发布前都会跑（常用于构建） |
| `prepublishOnly` | 只在 `npm publish` 前跑（常用作发布前校验/构建） |

**注意 `prepare` 会在"作为依赖被安装"时也可能触发**——所以它里面不要放有副作用的重操作。

【待验证】**provenance / 发布签名**这类供应链溯源能力在各 registry 的支持度仍在演进，用前查目标 registry 的文档。

## 2.7 Monorepo：为什么用、怎么选

### 与多仓库（Polyrepo）的对照

| 维度 | Monorepo（单仓库多包） | Polyrepo（多仓库单包） |
|---|---|---|
| 跨包改动 | **一次提交**，原子 | 多次提交 + 版本协调 |
| 本地联调 | 直接链接，改完即生效 | 需要 `link` / 发包 / 本地覆盖 |
| 工具与规范 | 一套配置，容易统一 | 每仓库各自漂移 |
| CI | **需要"只跑受影响的包"**，否则全量跑 | 天然只跑本仓库 |
| 版本管理 | 需要专门的版本工具（本章 §2.8） | 各自独立 |
| 仓库规模 | 会持续变大 | 分散 |

**Monorepo 的收益集中在"协作成本"，代价集中在"工具复杂度"**——所以它不是一个"更好"的默认选项，而是一个有明确适用面的选择。

### workspace 协议：本地包的引用方式

```json
// packages/app/package.json
{ "dependencies": { "@myorg/ui": "workspace:*" } }
```

`workspace:*` 的语义是**两段式**：

| 时刻 | 行为 |
|---|---|
| 本地开发 / 安装 | 解析为**本地目录的符号链接**（不是去 registry 下载） |
| **发布时** | 由发布工具**替换成真实版本号**（如 `^1.2.0`） |

**第二行是它安全的原因**：发布出去的包不会带 `workspace:*`（那对消费者无意义）。**"忘了替换"是自定义发布脚本最常见的坑**——这也是下面那类工具存在的理由。

### 三种主流方案与它们的层次

**关键认知：它们不在同一层，因此不互斥。**

| 工具 | 层次 | 机制 |
|---|---|---|
| **pnpm workspace** | 包管理层 | 内容寻址 store + 硬链接；`pnpm-workspace.yaml` 声明包目录；严格布局天然防幽灵依赖 |
| **Turborepo** | 任务编排层 | 声明任务之间的依赖与输入输出 → **按输入哈希命中缓存**（可远程共享） |
| **Nx** | 任务编排 + 项目图 | 构建**项目依赖图** → 支持"只跑受影响的项目" + 计算缓存 |

典型组合是：**pnpm workspace 管依赖，Turborepo 或 Nx 管任务与缓存。**

### "受影响（affected）"是怎么算出来的

```text
① 构建项目依赖图（哪个包 import 了哪个包）
② 对比本次改动涉及的文件 → 映射到包
③ 沿依赖图向下/向上求闭包 → 得到"需要重跑"的集合
④ 对未受影响的包直接跳过或命中缓存
```

**注意第 ① 步与 D3 的依赖图是同一类东西**——只是粒度为"包"而不是"模块"。这也解释了为什么 Monorepo 的编排能力依赖包之间**有显式的依赖声明**（幽灵依赖会直接让"受影响分析"失效）。

### 选型维度

| 维度 | 要问的问题 |
|---|---|
| 包管理需求 | 是否要严格布局（防幽灵依赖）？是否已有 pnpm 经验？ |
| 任务编排需求 | 是否需要"只跑受影响"与远程缓存？ |
| 生态与学习成本 | 团队能否接受一份新的配置与心智模型？ |
| 与 CI 的集成 | 缓存能否跨机器共享？ |
| 迁移成本 | 现有仓库结构与脚本要改多少？ |

## 2.8 Monorepo 治理：版本、发布与边界

### 版本策略：统一 vs 独立

| 策略 | 做法 | 适合 |
|---|---|---|
| **统一版本（fixed）** | 所有包共用一个版本号，一起升 | 包之间耦合紧、总是一起发布 |
| **独立版本（independent）** | 每个包各自升 | 包对外独立消费、发布节奏不同 |

**取舍点**：统一版本省心但会"无谓地升一堆包"；独立版本精确但需要工具支撑版本计算。

### Changesets 的工作流（解决"版本与 CHANGELOG 从哪来"）

```text
① 改代码时，顺手写一个 changeset 文件（说明：哪个包、什么级别的变更、说明文字）
② 汇聚所有 changeset → 生成一份版本计划
③ 执行升版本：批量改 package.json + 生成各自的 CHANGELOG
④ 发布：把需要发布的包推上去
```

**它的核心价值是"把版本决策从发布时提前到改动时"**——改的人最清楚这次改动是 patch 还是 breaking，而不是等到发布前靠猜。

### 依赖边界：用 `exports` 封住内部路径

```js
import { x } from "@myorg/ui/src/internal/helper";   // ✗ 深层引用
import { x } from "@myorg/ui";                        // ✓ 只走公开入口
```

**回链 D2 第 1 章 §1.4**：`exports` 字段一旦声明就会**封住内部路径**——这正是 Monorepo 里强制边界的机制，不是靠约定，而是靠**消费者根本解析不到**。

**深层引用的危害**：它让包的内部重构变成 breaking change；也让"受影响分析"无法通过公开入口判断依赖。

### 依赖版本一致性

同一个第三方依赖（如 TypeScript、React）在多个包里保持同版本，否则会出现：类型不兼容、多份实例、构建结果不一致。

| 手段 | 说明 |
|---|---|
| 在各包统一写同一范围 + 单一 lockfile | Monorepo 通常共用根 lockfile |
| `overrides` / `pnpm.overrides` | 强制统一传递依赖 |
| 在 CI 加校验 | 检测跨包的同依赖版本漂移 |

### 与 CI 的接线

Monorepo 的 CI 必须解决"**别全量跑**"：

```text
受影响分析（本章 §2.7）→ 只对受影响的包跑 lint / 类型检查 / 测试 / 构建
                  → 对命中缓存的直接复用产物
```

`D1.L3.04`（Lint 提速：monorepo 中的编排）会回链到本节；`D6` 领域的 CI/CD 也会回链。

## 2.9 依赖安全与供应链治理

> **域外依赖（已闭合）**：本节需要"依赖安全扫描（SCA）"的背景，完整机制见 **`D5` 第 1 章 §1.5**（含"SCA 是供应链最小防线，不是安全审计"）。此处就地简要交代。

### 【补充背景】SCA 在做什么

**SCA（Software Composition Analysis，软件成分分析）** 是把你的**依赖清单与已知漏洞库比对**，报告"你用了哪些有已知问题的版本"。要记住它的两个边界：

- 它只能发现**已公开**的问题；
- 它**不判断你的代码是否真的受影响**（那需要额外分析调用路径）。

### 供应链的真实威胁面

| 威胁 | 机制 |
|---|---|
| **恶意提交** | 维护者账号被劫持，或恶意接管废弃包 → 发一个新版本，里面直接跑恶意代码 |
| **`postinstall` 脚本** | 安装时**能执行任意代码** —— 这是最主要的执行载体 |
| **抢注包名（typosquatting）** | 用形近名（如 `crossenv` vs `cross-env`）诱骗手误 |
| **依赖混淆（dependency confusion）** | 公司内部包名是公开的 → 攻击者在公共源发一个**同名且版本更高**的包 → 解析时命中公共源 |
| **传递依赖失控** | 你自己的依赖没问题，它依赖的依赖出问题 |

### 各威胁的对应手段

| 威胁 | 手段 |
|---|---|
| 恶意提交 / 篡改 | **lockfile + integrity**（保证"内容没变"，但不保证"内容安全"） |
| `postinstall` | 评估是否使用 `--ignore-scripts`；**代价是部分包需要它的构建步骤才能用** |
| 抢注 | 依赖数量治理（能不加就不加）、代码评审、自动化检查 |
| **依赖混淆** | **把内部 scope 绑定到私有源**（本章 §2.6 的 `@myorg:registry=…`）——这是最直接的对策 |
| 传递依赖 | 依赖数量与深度治理；定期审计 |
| 发布者凭据泄露 | **最小权限 token**（限定 scope 与操作）、CI 中不落明文 |

### 一条诚实的判断

**`npm audit` 报告 ≠ 必须立即修**。它的输出常包含：

- 只影响开发依赖的漏洞；
- 需要特定调用方式才触发的问题；
- 修复它导致的 breaking 升级成本高于风险。

所以**治理的正确姿势是"分级 + 门禁"，而不是"零告警"**：把"高危且影响运行时的漏洞"设为阻断项，其余进入跟踪队列。完整的门禁设计属于 D5 与 D6。

## 2.10 动手

| 任务 | 验收 |
|---|---|
| 在一个项目里 `npm ls` 一个传递依赖 | 说出它为什么在顶层、以及提升的目标是什么 |
| 用 pnpm 重装同一个项目 | **记录哪些 import 开始报错**，说明这些就是幽灵依赖 |
| 构造一次版本冲突（两个包要同一依赖的不同大版本） | 指出磁盘上出现了嵌套的 `node_modules`，并解释为什么 |
| 给一个假想的组件库分别用 `dependencies` 与 `peerDependencies` 声明 React | 说出两种情况下消费者会装出几份实例 |
| 手工制造锁文件与 `package.json` 不一致 | 用 `npm ci` 复现失败，**记录退出码与报错文本** |
| 用 `npm pack --dry-run` 看一个包的发布清单 | 指出不该被打进去的文件，并用 `files` 修掉 |
| 建一个含两个包的 pnpm workspace，用 `workspace:*` 互相引用 | 说出发布时这个字段会发生什么；用 `pnpm pack` 验证 |
| 给 Monorepo 配一条"只跑受影响包"的脚本（任一工具） | 说出它是靠什么信息算出"受影响"的 |
| 在 CI 里只提交 `package.json` 不提交 lockfile | 复现冻结模式下的失败，并说明它拦住了什么问题 |
| 检查一个项目的依赖里是否有 `postinstall` 脚本 | 说出它为什么是供应链攻击的主要载体 |

**进阶挑战**：

1. 把 `resolve.alias` 式的"内部路径深层引用"改为 `exports` 封边界，验证消费者是否真的解析不到。
2. 用 `overrides` / `resolutions` 消除一次重复实例，并用 `npm ls` 前后对比。
3. 写一个 changeset 流程的最小示例（两个包、一次 patch、一次 minor），跑完全流程。

## 2.11 本章常见误区

| # | 误区 | 事实 |
|---|---|---|
| 1 | "`^0.1.0` 会自动升到 `0.2.0`" | `^` 不允许修改最左侧非零位；`^0.1.0` 实际是 `>=0.1.0 <0.2.0` |
| 2 | "预发布版本会被自动选中" | 默认**不匹配**；只有范围在同一 `[major,minor,patch]` 上显式包含预发布才会被选中 |
| 3 | "lockfile 只是版本列表" | 它还含 **integrity（SRI 哈希）**与完整依赖声明——手工合并几乎必然破坏自洽性 |
| 4 | "integrity 能防住恶意包" | 它只保证"内容与记录一致"，**不判断内容是否安全** |
| 5 | "`npm ci` 和 `npm install` 只是在 CI 里更合适" | `ci` 严格按 lockfile 安装且**不一致即失败**，这是可复现性的硬约束 |
| 6 | "peer 不满足只是警告，无所谓" | **npm 7+ 会自动安装 peer**，行为已变；写错可能直接抛 `ERESOLVE` |
| 7 | "组件库把 React 写进 `dependencies` 更省事" | 会造成**重复实例**，引发 Hooks 报错与单例失效（回链 D2 第 1 章 §1.7） |
| 8 | "`--legacy-peer-deps` 是标准解法" | 它只是退回旧行为并掩盖冲突，会带入隐患 |
| 9 | "已发布版本可以覆盖" | 版本号是不可变标识；覆盖会破坏所有消费者的 integrity 校验，撤回也是破坏性操作 |
| 10 | "包体积不用管" | 忘记配置 `files` 会把源码、测试、缓存一起发上去；用 `npm pack --dry-run` 检查 |
| 11 | "`workspace:*` 会原样发布出去" | 发布工具会把它替换成真实版本；但**自定义发布脚本常常忘了这一步** |
| 12 | "Turborepo 与 pnpm workspace 是竞品" | 它们不在同一层：前者管任务与缓存，后者管依赖与布局，典型做法是组合使用 |
| 13 | "受影响分析是看文件时间戳" | 它靠**项目依赖图 + 改动映射**求闭包；幽灵依赖会让这个分析失效 |
| 14 | "用 `exports` 封边界只是规范问题" | 它是**机制**：消费者根本解析不到内部路径，约定因此变成强制 |
| 15 | "`npm audit` 有告警就得立刻升" | 报告不等于风险；治理应"分级 + 门禁"，而非追求零告警 |
| 16 | "内部包名很独特，不会被抢注" | 依赖混淆正是利用"内部包名是公开的"这一点——对策是把 scope **绑定到私有源** |
| 17 | "`postinstall` 只是构建步骤" | 它**能执行任意代码**，是供应链攻击的主要载体；`--ignore-scripts` 是取舍而非免费选项 |

## 本章小结

**八条最该记住的结论**

1. **依赖安装 = 约束求解 + 布局决策**。三代布局（嵌套 / 提升 / 内容寻址链接）决定的不只是性能，还有**依赖关系的严格程度**。
2. **提升的代价是"顶层 ≠ 你声明的"**——这就是幽灵依赖的根。**pnpm 的严格性来自布局，不是额外检查**，所以迁移时的报错是在修正而非制造问题。
3. **版本范围表达"可接受区间"**：`^` 不允许修改最左侧非零位（所以 `^0.1.0` 升不上去），预发布版本默认不匹配。**锁定实际版本的是 lockfile。**
4. **lockfile 承载版本 + integrity + 树结构**，形状受布局策略影响，**不可跨包管理器复用**；`npm ci` 的一致性校验在 CI 里表现为"构建失败"——那正是它要拦的情况。
5. **`peerDependencies` 的语义是"由宿主提供"**，它是避免重复实例的主要机制；而 **npm 7+ 会自动安装 peer**，改变了冲突的常见形态。
6. **私有源的 scope 绑定是防依赖混淆的直接手段**；已发布版本不可覆盖；包内容用 `files` 白名单治理。
7. **Monorepo 的三种工具不在同一层**：包管理层（pnpm workspace）与任务编排层（Turborepo / Nx）是组合关系。`workspace:*` 在发布时会被替换成真实版本。
8. **供应链治理是分层的**：integrity 防篡改、`peerDependencies` 防重复、scope 绑定防混淆、最小权限 token 防凭据泄露，而 `npm audit` 只是其中一环——**治理目标是"分级 + 门禁"，不是零告警**。
