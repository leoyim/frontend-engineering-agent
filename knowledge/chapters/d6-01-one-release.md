# D6 第 1 章 · 一次发布：从产物到线上

> **本章定位**：D6 领域第 1 章。D3 讲的最后一步是"产出一个文件"，本章从**那个文件之后**接上：它怎么变成一群用户真正用到的东西。整章为【补充背景】。
>
> **对应地图节点**：`D6.L2.01`（静态资源部署与一次完整的发布流程）· `D6.L2.02`（环境概念：dev / staging / prod 与配置差异）· `D6.L4.02`（build once, deploy many：运行期注入与环境配置管理）· `D6.L4.03`（制品成套：产物 + sourcemap + 版本号 + 构建元信息）
>
> **前置**：`D3.L2.02`（开发/生产两套目标）· `D3.L4.03`（缓存三层结构）· `D0.L2.09`（HTTP 缓存语义）。
>
> **来源约定（本章及整个 D6）**：**只引通用协议与平台无关机制** —— RFC 9110 / 9111 / 8246 / 5861、WHATWG 规范、浏览器行为。**厂商差异只做定性描述，不写控制台步骤与价格**（理由见本章尾注）。凡属本书的机制推导，均显式标注。
>
> **读过 D3 的人会看到一条主线被接上**：D3 第 8 章讲"文件名带 hash 之后三层缓存就成立了"，本章讲**"为什么光有 hash 还不够"** —— 因为发布这件事本身，需要一个**原子切换点**。
>
> **读完能做到**：说出发布的最小原子单位是什么、为什么不是文件；判断一次发布能不能回退、回退是否需要重新构建；说清 build once deploy many 的**代价**在哪；列出制品必须成套的四样东西。

## 1.1 发布的四个动作

先把"发布"这个词拆开。它不是一个动作，是**四个**：

| # | 动作 | 回答的问题 | 失败的后果 |
|---|---|---|---|
| 1 | **产出制品** | 这次要发的东西是什么（一整套文件） | 说不清线上是哪个版本 |
| 2 | **上传** | 把它们放到能被取到的位置 | 用户拿不到 |
| 3 | **切换** | 让用户**开始**拿到新的 | 发了但没生效 |
| 4 | **可回退** | 出问题时能退回去 | 只能"往前修"，修不回来就持续故障 |

**大多数人只把第 2、3 步当发布**，于是第 1 步做得很随意（没有版本号、没有 sourcemap）、第 4 步根本没有（覆盖式上传）。**而故障时最能救命的是 1 和 4。**

**本章的骨架就是这四步的展开**：§1.2 讲 2–4 的完整流程，§1.3 讲"切到哪个环境"，§1.4 讲一个让 1 与 3 解耦的约束（build once），§1.5 讲 1 到底该包含什么。

## 1.2 一次完整的发布流程

### 六步

| 步 | 动作 | 关键点 |
|---|---|---|
| 1 | **构建** | 产出**文件名带内容 hash** 的产物（`D3` 第 8 章 §8.2） |
| 2 | **打包制品** | 产物 + sourcemap + 版本号 + 构建元信息（§1.5） |
| 3 | **上传** | **按版本目录上传，不覆盖旧版本** |
| 4 | **分发** | 让边缘节点有副本（预热可按需） |
| 5 | **切换索引** | 让"当前版本"指向新目录 —— **这是发布真正生效的一刻** |
| 6 | **观察与回退** | 看指标，不对就把索引切回去 |

### 核心洞察：发布的最小原子单位是"索引"，不是"文件"

这一条是本章最重要的判断，而且**直接由 D3 的 hash 机制推出来**：

> **既然文件名带内容 hash，那么"文件内容不变"就等于"文件名不变"。**
> **所以上传一个新版本，完全不需要动旧版本的文件。**

于是"发布"这件事可以被压缩成**一次引用替换**：

```
版本目录式（推荐）                覆盖式（不推荐）
─────────────────                ─────────────────
/static/v1.4.2/...   ← 旧        /static/...   ← 被新文件覆盖
/static/v1.4.3/...   ← 新
/index.html          ← 指向谁    /index.html  ← 只能指向"当前"
```

**这个差别决定了三件事**：

| 能力 | 版本目录式 | 覆盖式 |
|---|---|---|
| **回退** | **切索引，秒级，不重新构建** | **必须重新构建旧版本**，或根本退不回去 |
| **灰度 / 分批** | 天然支持（不同用户拿不同索引） | 做不到 |
| **旧页面兼容** | 旧 HTML 仍指向旧目录，**不会 404** | 旧文件被覆盖 → 旧页面可能加载到混版 |

**第三行值得单独说**：这正好是 D3 第 8 章 §8.1 讲的"发版后部分用户白屏"。**白屏的根因不是 hash 没做好，而是"旧 HTML 指向的旧产物被删了"**。版本目录式从结构上消除了这个可能 —— 旧目录还在，旧 HTML 依然能取到它引用的每一份文件。

### 索引本身怎么才能"瞬时切换"

索引通常是 `index.html`（或一份 manifest）。**它必须满足两个条件**：

| 条件 | 为什么 |
|---|---|
| **不被长缓存** | 否则用户手里的是旧索引（`D3` 第 8 章 §8.1：Vite 官方建议对 HTML 设 `Cache-Control: no-cache`） |
| **切换是原子的** | 否则会出现"一半用户拿新、一半拿旧"之外的第三种状态：**拿到半新半旧的索引** |

**第二条的机制**：一次切换如果在存储层不是原子的（例如分多次写入同一个文件），那么在写入过程中被读取，就会读到**不完整的索引**。所以索引应当**整体替换**（写新对象 + 改指针），而不是**原地编辑**。

**⚠️ 一处如实标注**：具体的"原子替换"由存储层提供（对象存储的覆盖写、CDN 的缓存清除、或符号链接切换），**各家实现不同**。本章按"**替换指针**"这个抽象描述，**不给出具体产品操作**（符合本章的来源约定）。

### 观察与回退：回退速度是设计出来的

**回退的代价，在发布设计时就决定了**：

| 设计 | 回退动作 | 耗时 |
|---|---|---|
| 版本目录式 + 索引切换 | 把索引指回上一版 | **秒级** |
| 覆盖式 | 重新构建旧 commit + 重新上传 | **分钟到小时** |
| 只有一个环境、只保留最新一版 | **退不回去** | —— |

**所以"能不能回退"不是运维能力问题，是发布流程的设计问题。** 而它必须在第一次发布之前定下来 —— 事后补，往往要重构整个上传路径。

### 一条容易被忽略的观测要求

发布完成后，需要能回答"**现在到底有多少人还在用旧版本**"。这要求：

| 要求 | 为什么 |
|---|---|
| 前端上报**自己的版本号** | 否则你只知道"服务器上是什么"，不知道"用户手里是什么" |
| 上报里有**版本维度** | 否则无法区分"新版本引入的错误"与"全量都在错" |

**这条与 §1.5 直接相关**：**版本号必须进产物**，而且必须是**可被前端读到**的形式（不只是文件名或注释）。

## 1.3 环境：dev / staging / prod 差在哪

`D6.L2.02`。这个节点最容易被写成"三套配置文件的对照表"，但那不是它的实质。

### 差异分五类，只有四类应该有

| 维度 | 该不该有差异 | 说明 |
|---|---|---|
| **目标环境**（浏览器矩阵） | **可以**（但见下方警告） | 理论上 staging 可以用更窄的矩阵加速，但**推荐保持一致** —— 见下 |
| **外部依赖地址**（API 域名、第三方 key） | **应该** | 必须与 prod 隔离 |
| **数据** | **应该** | staging 必须是假数据或脱敏数据 |
| **权限与凭证** | **应该** | **绝不能与 prod 共用** |
| **观测**（采样率、告警阈值） | **应该** | staging 的告警不该叫醒人 |
| **代码路径** | ❌ **不应该** | **这是本章的核心纪律** |

### 核心纪律：环境差异只能落在"配置与数据"上，不能落在"代码路径"上

**反例**：

```js
if (import.meta.env.MODE === 'staging') {
  // 只有在 staging 才走的分支
}
```

**为什么这是错的**：**staging 通过不能证明 prod 会通过** —— 因为你测的是**另一条路径**。

| 你以为 | 实际 |
|---|---|
| "staging 跑通了，prod 应该也没问题" | prod 走的是**另一条代码路径**，从未被执行过 |
| "环境分支只是一点小差别" | 它把测试的有效性**归零**了，而不是降低了 |

**这条与 D3 第 5 章 §5.5 的"dev 正常 ≠ prod 正常"是同一族问题**，只是那一条的成因是**构建模式**，这一条的成因是**运行环境**。

**正确的替代**：如果 staging 需要特殊行为，用**配置值**表达，而不是用分支：

```js
if (config.enableMockApi) { ... }   // ✅ 配置驱动，prod 里这个值恒为 false
if (env === 'staging') { ... }      // ❌ 环境驱动，prod 里这条分支永不被执行
```

**两者的区别看起来微小，实质完全不同**：前者**在 prod 里仍是一段会被读到并判定的代码**，后者**在 prod 里是一段被跳过的代码**。前者能通过"把开关打开"来测；后者不能。

### 环境的数量不是越多越好

每多一个环境，就多**一份可能与 prod 漂移的配置**：

| 漂移形态 | 表现 |
|---|---|
| 配置项只在某个环境存在 | 新加到 prod 的配置，staging 没加 → staging 测不出问题 |
| 某个环境长期不重建 | 依赖版本、构建器版本与 prod 不同 → 构建行为都不同 |
| 环境间的凭证混用 | 一旦误操作，影响面跨环境 |

**dev / staging / prod 三个是常见配置，不是硬性要求。** 小团队两个（dev + prod）就够；关键在于**每个环境的差异都被显式声明**，而不是"大家心里知道"。

### 一条与构建有关的警告

**目标浏览器矩阵（browserslist）不应该按环境分叉。**

理由在 D3 第 3 章 §3.2：`browserslist` 被**多个工具共享**（转译、autoprefixer、lint）。如果 staging 用一套、prod 用另一套，那么**staging 测到的产物与 prod 的产物不是同一份转译结果** —— 这又回到了"测的不是要发的东西"。

**所以**：浏览器矩阵属于"**产品决策**"，不属于"环境配置"。它应当只有一份。

## 1.4 build once, deploy many

`D6.L4.02`。这是本章最需要"知其代价"的一条。

### 问题：如果每个环境各构建一次

假设 dev / staging / prod 各跑一次 `npm run build`，那么：

| 环节 | 事实 |
|---|---|
| staging 测的产物 | 由 staging 的构建产生 |
| **prod 上线的产物** | 由 prod 的构建产生 —— **一份从未被任何人打开过的文件** |
| 两者的关系 | 源码相同，但**构建时间、构建机器、环境变量注入结果都可能不同** |

**"测过的没发，发的没测过"** —— 这就是问题的准确描述。

**注意这不只是理论风险**：D3 第 8 章 §8.2 已经证明，**构建本身可以不确定**（四个 hash 不稳的成因）。所以"同一份源码构建两次得到相同字节"是需要**刻意保证**的，不是默认成立的。

### 定义

> **构建一次，得到一份字节，把这一份字节部署到所有环境。**

| 好处 | 机制 |
|---|---|
| staging 测的就是线上要跑的 | 同一份字节 |
| 回退可直接复用历史制品 | 制品按版本归档 |
| 构建次数与环境数解耦 | 构建一次，部署 N 次 |

### 代价：所有"环境相关的值"必须从构建期移到运行期

这是本节的核心，也是 `L4.02` 名字里"运行期注入"的由来。

**因为**：构建期的值会被**烧进产物**。一旦烧进去，同一份字节就无法在不同环境表现不同。

### 两种注入时机，只有一种能 build once

| 方式 | 时机 | 典型机制 | 能否 build once |
|---|---|---|---|
| **构建期替换** | 构建时 | `import.meta.env.*`、DefinePlugin 常量替换 | **不能** |
| **运行期读取** | 页面加载 / 请求时 | 独立配置文件、服务端渲染时注入、接口获取 | **能** |

**这里有一条已核验的关键约束**（D3 第 2 章 §2.3 / 第 3 章 §3.5）：**`import.meta.env.*` 是静态替换** —— 它在构建时就被替换成字面量，产物里**不再有"读取环境"这个动作**。

**所以 `import.meta.env` 不能承担运行期注入。** 这不是配置技巧问题，是机制决定的。

**混淆的症状**（很典型）：改了服务器上的环境变量，重新加载页面，**毫无变化** —— 因为产物里的值早在构建时就定死了，服务器上的变量只影响"下一次构建"。

### 运行期注入的三种形态（本书的机制归纳）

本章不给具体产品实现，但三种形态的**结构差别**值得说清：

| 形态 | 机制 | 代价 |
|---|---|---|
| **独立配置对象** | 页面先加载一个**不带 hash、不缓存**的小文件（或内联脚本），把配置挂在全局对象上，业务代码运行时读它 | 多一次请求或一点内联体积；**配置泄漏风险**（能看到就能改？不，能看≠能改，但会暴露内部地址） |
| **服务端注入** | 返回 HTML 时把配置写进文档 | 要求 HTML 由服务端产生（纯静态托管做不到） |
| **接口获取** | 启动时请求一个配置接口 | 多一次往返；首屏要等它 |

**⚠️ 一条共同的风险**：**运行期注入让产物不再自解释。**

| | 构建期注入 | 运行期注入 |
|---|---|---|
| 拿到一个 JS 文件，能知道它在哪个环境跑吗 | **能**（值在里面） | **不能**（值是外部给的） |
| 排查"为什么这个环境行为不对" | 看产物 | 还要看**配置有没有正确下发** |

**缓解办法只有一条**：**把"本产物期待哪些运行期配置"记录进制品的构建元信息**（§1.5）。这样出问题时能先排除"配置没给对"这一类。

### 混用是最坏的情况

**同一份代码里既有构建期替换、又有运行期注入**，会产生一类极难查的 bug：

| 现象 | 根因 |
|---|---|
| 改了 A 配置生效，改了 B 配置不生效 | A 走运行期，B 走构建期 |
| 本地开发正常、部署后失效 | 本地 dev server 会**在每次请求时重新替换** `import.meta.env`，所以"改了就生效"；而生产是**构建时定死** |

**第二行值得注意**：**开发环境的行为会主动掩盖这个错误** —— 因为 dev server 每次请求都重新处理，看起来"改环境变量就生效"。这正是 D3 第 5 章那条"dev 正常 ≠ prod 正常"的又一处体现。

### 一条纪律：注入的值要能被验证

无论哪种形态，都应当有**至少一处**能回答"这份产物这次实际拿到了什么配置"。最小做法：

- 把配置的**键名与来源**（不是值，避免泄漏敏感信息）打进构建元信息；
- 前端上报版本号时，一并上报**配置的指纹**（例如键集合的 hash）。

**这样"配置错"与"代码错"就能被分开定位** —— 否则所有线上问题都会先被怀疑成代码问题，浪费大量时间。

## 1.5 制品成套：产物之外还要交什么

`D6.L4.03`。这一节回答的问题很朴素：**出故障时，你需要手上有哪些东西才能查**。

### 三个必答问题

任何一次线上故障，最先要回答的是：

| 问题 | 需要什么 |
|---|---|
| **是哪个版本？** | 版本号（进产物、可被前端读到） |
| **对应哪份源码？** | sourcemap + commit 标识 |
| **谁、用什么构建的？** | 构建元信息（构建器版本、依赖锁、时间、CI 任务号） |

**三样缺任何一样，排查都会退化成猜。**

### 制品清单

| 组成 | 用途 | 缺了会怎样 |
|---|---|---|
| **产物**（带 hash 的 JS / CSS / 资源） | 正常运行 | —— |
| **sourcemap** | 把线上堆栈还原到源码 | 报错只能定位到压缩后的位置（`D3` 第 3 章 §3.6） |
| **版本号** | 回答"线上是哪个版本" | 无法区分"新版本引入"与"全量都在错" |
| **构建元信息** | 回答"这份产物怎么来的" | 无法复现、无法判断是否受依赖变更影响 |
| **清单**（manifest：未 hash → hash 的映射） | 由索引/服务端解析引用 | 服务端渲染或动态加载时找不到文件名 |

**清单那一行值得单独确认**：Vite 官方对 `build.manifest` 的定义是"**未哈希资源文件名到其哈希版本的映射**"（D3 第 3 章 §3.6 已引）。**它就是"索引"的另一种形态** —— 服务端要靠它把"逻辑名"翻译成"带 hash 的文件名"。

### sourcemap 不是调试附件，是排障的必要条件

这一点需要在 D6 里再强调一次，因为它的**部署方式**与产物完全不同：

| 项 | 产物 | sourcemap |
|---|---|---|
| 谁需要它 | 用户的浏览器 | **只有你的排障工具** |
| 该不该公开 | 必须公开 | **不该** |
| 缓存策略 | 长缓存（带 hash） | 不参与用户侧缓存 |

**官方对三种带 map 配置的警告**（`D3` 第 3 章 §3.6 已引，这里给出后果）：

| 配置 | 官方警告 | 实践含义 |
|---|---|---|
| `source-map` | "应当**配置服务器禁止普通用户访问** Source Map 文件" | 默认就是公开的，必须额外挡 |
| `hidden-source-map` | "**不应把 Source Map 文件部署到 web 服务器**，只用于错误上报工具" | 生成但不写引用注释，**单独上传给平台** |
| `nosources-source-map` | "仍暴露文件名与结构，可用于反编译，但不暴露原始代码" | 可对外的折中档 |

**"hidden"隐藏的是引用注释，不是文件**（`D3` 第 3 章 §3.6 的对照表）。所以选 `hidden-source-map` 时，**制品里仍然有 `.map` 文件** —— 它该进"排障包"而不是"公开目录"。**这两者在制品打包时就要分开，不能等到部署时人工挑。**

### 构建元信息该记什么

**判据是"能不能复现"**：

| 项 | 为什么 |
|---|---|
| **commit 标识** | 定位源码 |
| **依赖锁文件的指纹** | D2 讲过 lockfile 的边界：同一份 `package.json` 不等于同一份依赖树 |
| **构建器与大版本** | 换过打包器/转译器时，"同样的源码不同产物"是正常的 |
| **构建时间** | 与发布记录、故障时间对齐 |
| **构建发起者 / CI 任务号** | 谁触发、能不能回看日志 |
| **运行期配置的键名清单** | §1.4：运行期注入让产物不自解释，这是唯一的补丁 |

**⚠️ 一条纪律：构建元信息不要写进产物本身的可执行部分。**

理由在 D3 第 8 章 §8.2 的四个 hash 成因：**构建时间戳进了产物，hash 就每次都变**，三层缓存全部作废。**元信息应当是独立文件**（或写进清单），与产物**分离**。

### 制品必须不可变

> **同一个版本号，永远指向同一份字节。**

这条不成立时会发生什么：

| 破坏方式 | 后果 |
|---|---|
| 用同一个版本号重新发布 | 用户侧缓存命中旧字节、服务端认为是新字节 → **行为不可预测** |
| 发布后"打个补丁"改制品 | 出问题时无法判断"线上那份到底是什么" |
| 版本号由时间戳生成且在分钟级重复 | 两次发布可能撞号 |

**所以版本号应当来自"内容"或"单调递增的发布序号"，而不是"什么时候构建的"。**

## 1.6 治理动作：六个判定阈值

与前几章同体例。**全部是起点值，需按项目校准。**

| # | 现象 | 判定阈值（起点值） | 动作 | 依据 |
|---|---|---|---|---|
| 1 | 发版后仍有用户在用旧版本 | **发版 30 分钟后仍有 > 1% 的旧版本请求** | 查索引（HTML）是否 `no-cache`；查是否有 CDN 侧缓存了 HTML | §1.2 |
| 2 | 发版后部分用户白屏 / 资源 404 | **出现任何一次资源 404** | 检查是不是覆盖式上传删了旧文件；启用版本目录式 | §1.2 |
| 3 | 回退需要重新构建 | **回退耗时 > 5 分钟** | 改为"保留历史目录 + 切索引" | §1.2 |
| 4 | 无法回答"线上是哪个 commit" | **任意一次故障排查中答不出** | 把 commit 与版本号写进构建元信息，并由前端上报 | §1.5 |
| 5 | 两个环境行为不同但配置看起来一样 | **任意一次"staging 好、prod 不好"** | 查代码里有没有 `if (env === ...)` 分支 | §1.3 |
| 6 | 改了服务器环境变量，页面没变 | **任意一次"改配置无效"** | 查该配置是否走了 `import.meta.env`（构建期静态替换） | §1.4 |

### 三条使用说明

**① 阈值 1 与 2 是"正确性"问题，优先级高于其余四条。**

用户拿到旧代码或白屏，**功能就是坏的**，不是"体验差一点"。

**② 阈值 3 与 4 是"能不能查"的问题。**

它们不影响正常运行，但**决定故障时能不能快速定位**。而这两条的修复成本随项目年龄**上升** —— 越晚做越贵。

**③ 阈值 5 与 6 是同一类错误的两个面。**

都属于"**你以为在测/改 A，实际在测/改 B**"：

- 阈值 5：以为在测同一条路径，实际是两条；
- 阈值 6：以为在改运行期配置，实际改的是构建期输入。

**这类问题的共同特征是"不报错、只是结果不对"**，所以只能靠纪律（不在代码里分环境、不用 `import.meta.env` 做运行期配置）来预防。

### 什么时候"不该做 build once"

这条要留出余地。以下情况，**每环境各构建一次是可接受的**：

| 情况 | 为什么 |
|---|---|
| 产物里**没有**任何环境相关的值 | 那么各环境构建出的字节本来就相同，build once 只是形式 |
| 环境数量 = 1 | build once 没有意义 |
| 团队还做不到"运行期注入" | 强行做会引入更难查的问题（§1.4 的混用） |

**判据很简单**：**先问"产物里有环境相关的值吗"。** 没有 → 不必刻意做；有 → 必须做，否则"发的东西没测过"。

## 1.7 动手

**每一项都要求说出理由**：

| 任务 | 验收 |
|---|---|
| 画出你项目当前的一次发布流程，标出六个步骤分别是什么 | 指出哪一步是"发布真正生效的一刻" |
| 查一次你的上传方式：是覆盖式还是版本目录式 | 说出如果是覆盖式，回退需要多少时间、是否需要重新构建 |
| 查一次 `index.html` 的响应头 | 说出它是否 `no-cache`；若不是，发版后会发生什么（§1.6 阈值 1） |
| 手工模拟一次回退（不重新构建） | 记录耗时，并说出这个耗时是由什么设计决定的 |
| 列出你项目所有的环境，以及每个环境与 prod 的差异项 | 逐项标注属于"配置/数据/权限/观测"还是"代码路径" |
| 全局搜索 `env ===` / `MODE ===` 一类分支 | 说出哪些应改为配置驱动、为什么（"prod 不会执行那条分支"） |
| 检查 `import.meta.env.*` 的使用点 | 区分哪些是"构建期就该定死"的、哪些被误当成运行期配置 |
| 列出你制品里包含的文件 | 对照 §1.5 的五项清单，标出缺哪几项、缺了会导致什么问题 |
| 检查 `.map` 文件是否被部署到公开目录 | 说出 `hidden-source-map` 下 `.map` 该去哪、为什么"hidden"不等于"没有" |
| 查一次能否回答"线上是哪个 commit" | 若不能，说出最少需要补哪几样东西 |
| 检查构建元信息里有没有时间戳被写进**产物** | 说出它会让第 8 章哪一个 hash 成因成立 |

**进阶挑战**（任选一项）：

1. **把发布改成版本目录式 + 索引切换**，并验证"回退不重新构建"。要求记录回退耗时、旧页面是否仍能正常加载。
2. 给你的制品做一份**"故障时可查性"清单**：三个必答问题（版本 / 源码 / 构建者）各由哪个文件回答、怎么取到。要求别人拿这份清单能独立完成一次排查。
3. 把 §1.3 的五类差异 × 你项目的实际环境做成矩阵，标出**每一处差异被声明在哪里**（配置文件 / CI 变量 / 代码分支）。发现"只在大家心里"的差异，就是这次的最大收获。

## 1.8 本章常见误区

| # | 误区 | 纠正 |
|---|---|---|
| 1 | "发布就是把文件传上去" | 发布有**四个动作**：产出制品 / 上传 / 切换 / 可回退。少任何一个都不完整 |
| 2 | "发布的最小单位是文件" | **是索引**。因为 hash 文件名不变内容就不变，所以发布 = 一次引用替换 |
| 3 | "旧版本可以随手删" | 旧 HTML **仍指向旧产物**。删了就是 404 / 白屏（§1.2） |
| 4 | "回退就是重新构建上一版" | 版本目录式下回退是**切索引，秒级**。需要重新构建说明设计有问题 |
| 5 | "能不能回退是运维的事" | 它由**发布设计**决定，必须在第一次发布前定下来 |
| 6 | "环境就是三套配置文件" | 环境差异分五类（目标 / 外部依赖 / 数据 / 权限 / 观测），**代码路径不该有差异** |
| 7 | "环境越多越严谨" | 每多一个环境就多一份漂移机会。关键是差异**被显式声明** |
| 8 | "各环境用不同的 browserslist 更灵活" | **会破坏测试有效性** —— staging 的转译结果与 prod 不是同一份。浏览器矩阵属产品决策 |
| 9 | "每个环境各构建一次更简单" | 于是**"测过的没发，发的没测过"** —— prod 上线的是从未被打开过的文件 |
| 10 | "build once 是个优化技巧" | 它是一个**约束**，代价是所有环境相关的值必须移到运行期 |
| 11 | "用 `import.meta.env` 做运行期配置就行" | **它是静态替换**，构建时即定死，产物里没有"读取环境"这个动作 |
| 12 | "本地改了环境变量就生效，说明配置没问题" | **dev server 每次请求都重新替换**，会主动掩盖这个错误。这又是一处"dev 正常 ≠ prod 正常" |
| 13 | "运行期注入没有任何代价" | 代价是**产物不再自解释** —— 拿到一个 JS 文件无法知道它在哪个环境跑 |
| 14 | "制品就是产物" | 制品 = 产物 + sourcemap + 版本号 + 构建元信息（+ 清单）。缺一样，排查就退化成猜 |
| 15 | "`hidden-source-map` 就不会有 `.map` 文件了" | "hidden" 隐藏的是**引用注释**，文件仍在制品里。它该进排障包而非公开目录 |
| 16 | "构建元信息写进产物里最方便" | **时间戳进了产物会让 hash 每次都变**（第 8 章 §8.2 成因 3），三层缓存全部作废 |
| 17 | "同一个版本号修修补补没关系" | **制品必须不可变**：同一版本号永远同一份字节。否则"线上那份到底是什么"无法回答 |
| 18 | "版本号用构建时间戳就行" | 分钟级重复会撞号，且它不表达"内容"。应用内容或单调递增的发布序号 |
| 19 | "发布完就结束了" | 还要能回答"**现在有多少人还在用旧版本**" —— 这要求版本号进产物且可被前端上报 |
