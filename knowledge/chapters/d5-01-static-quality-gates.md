## 1.1 四类检查，问的是四个不同的问题

先把"静态检查"这个笼统说法拆开。它们查的**对象**根本不同：

| 类别 | 查什么 | 代表工具 | 典型问题 |
|---|---|---|---|
| **语法与风格** | **你写的写法** | ESLint（JS/TS）、Stylelint（CSS） | 未使用变量、`==` 误用、选择器重复 |
| **类型** | **值之间的类型关系** | `tsc --noEmit` | 传错参数类型、可能为 `undefined` |
| **结构深度** | **代码的结构与坏味道** | SonarQube 一类 | 圈复杂度、重复块、安全热点 |
| **依赖** | **你引用的别人的代码** | `npm audit`、Snyk、Dependabot | 依赖的某个版本有已知漏洞 |

**这张表最有用的地方在最后一行的"对象"**：

> **前三类查"你写的代码"，第四类查"你没写的代码"。**

**这条区分决定了它们的运行节奏完全不同**（§1.6）：前三类是**变更驱动**的（你改了代码才需要查），第四类是**时间驱动**的（你没改任何东西，昨天安全的依赖今天可能有漏洞了）。

## 1.2 分工的边界

### 一条被官方明确下来的分界：linter vs pretty printer

Stylelint 官方对"要不要格式化"给了一条很干脆的立场：

> 我们推荐**搭配 Prettier 这类 pretty printer 一起使用** Stylelint。**Linter 与 pretty printer 是互补工具**，协同帮你写出 consistent 且无错的代码。

**这条把一整类争论解决了**：

| 归谁 | 管什么 | 判据 |
|---|---|---|
| **linter**（ESLint / Stylelint） | **对不对**（错误 + 约定） | 有"对错" |
| **pretty printer**（Prettier） | **长什么样**（空白、引号、换行） | **没有对错，只有一致** |

**"没有对错，只有一致"是这条分界的关键**：缩进用 2 空格还是 4 空格，**不存在正确答案** —— 所以它不该由 linter 的规则来表达（否则每条规则都要争论"哪个才对"），而该由格式化器**统一**。

**这也是 D1 第 1 章"职责边界"的延续**：那一章讲"为什么不该用 prettier 当 lint 规则"，这里给出它的一般形式。

### 一条必须如实说明的缺口

**"CSS 归 Stylelint、JS 归 ESLint"这个分工，并不是 Stylelint 官方声明的。**

本次核验的 Stylelint 官网首页**全文未提及 ESLint 一词** —— 它只对比了 Prettier。所以：

| 说法 | 依据 |
|---|---|
| "linter 与 pretty printer 互补" | ✅ 官方原文 |
| "CSS 由 Stylelint 管、JS 由 ESLint 管" | ⚠️ **按语言边界推出来的常识分工，没有官方背书** |

**为什么要标这一条**：因为**边界重叠是真实存在的** —— CSS-in-JS、Vue/Svelte 单文件组件、`<style>` 块里的样式，**都同时落在两个工具的语言范围内**。这时"谁管"不是一个理论问题，而是一个**必须显式配置**的问题（下面 §1.3 讲重叠）。

### Stylelint 的能力边界（官方）

| 项 | 官方内容 |
|---|---|
| **定位** | "一个强大的 CSS linter，帮你**避免错误**并**强制执行约定**" |
| **"避免错误"的例子** | 非法写法（格式错误的 grid area）、合法但有问题的写法（重复选择器）、未知内容（属性名拼错） |
| **"强制约定"的例子** | 禁止某些写法（特定单位）、强制命名模式（自定义属性）、设定上限（ID 选择器数量）、规定记法（现代 color 函数） |
| **规则规模** | **100+ 内置规则**，支持插件（自定义规则）与可共享配置 |
| **语法支持** | 原生 CSS；可**扩展**到 SCSS / Sass / Less / SugarSS；可**从 HTML / Markdown / CSS-in-JS 模板字符串中提取**内嵌样式 |
| **能否格式化** | **不能，官方明确交给 Prettier**；但"**尽可能自动修复问题**"的能力存在 |

**两处要留意的措辞**：

1. **"可扩展（can be extended to）"** —— SCSS / Less 等支持依赖 **custom syntax 插件**，不是内核自带。
2. **首页未出现 `--fix` 标志**，只说"automatically fixes problems where possible"。所以"Stylelint 能自动修复"成立，**但具体命令形式本章不给**（需查 CLI 页）。

**版本**：首页导航的迁移指南列到 **17.0.0**，据此可推断当前主版本为 **v17** —— 但**页面本身没有直接写"最新版是 17"**，这是推断。

## 1.3 三类静态检查为什么不能互相替代

### 各自能发现什么，不能发现什么

| 检查 | **能**发现 | **不能**发现 |
|---|---|---|
| **ESLint / Stylelint** | 语法模式、可疑写法、命名约定、禁用 API | **语义错误**（逻辑对不对）、类型错误 |
| **`tsc`** | 类型不匹配、可能为 `undefined`、接口不符 | **逻辑正确性**（类型全对但算错了）、运行时行为 |
| **SonarQube 一类** | 结构问题（复杂度、重复）、安全热点、坏味道 | **"这一行具体错在哪"** —— 它给的是**度量与位置**，不是精确修复 |

**第二行最容易被高估**：**类型全对 ≠ 程序正确**。一个 `add(a: number, b: number): number` 写成 `return a - b`，类型完美、行为错误 —— **三条静态检查都发现不了**。这类问题只能靠**测试**（D5 后续章节）。

### 重叠区：同一类问题被两个工具报

**真实存在的三处重叠**：

| 重叠 | 表现 |
|---|---|
| **ESLint 与 `tsc`** | 未定义变量、未使用变量、`any` 的传递 |
| **ESLint 与 Stylelint** | CSS-in-JS、SFC 里的 `<style>` |
| **SonarQube 与 ESLint** | 复杂度、重复代码、部分安全规则 |

**处理原则**：

> **同一类问题只应由一个工具报告。**

**为什么这条重要**：不是"重复很烦"，而是 **重复会让"总数"失去意义** —— 一个 100 条的报告里如果有 40 条是重复的，你就无法用"这次新增了几条"来判断质量变化。

**三种处理方式与代价**：

| 做法 | 代价 |
|---|---|
| **关掉其中一边的规则** | 需要知道两边规则的重叠清单（这本身就是维护负担） |
| **接受重复，但在汇总层去重** | 需要一个汇总层（SonarQube 一类可以承担） |
| **只保留一边** | 可能丢掉另一边的独特能力 |

**⚠️ 一条与工具版本有关的提醒**：ESLint 与 Stylelint 都在历史上**把"风格类规则"逐步移出**（交给格式化器）。所以"某个规则现在归谁"**会随主版本变化** —— 这也是本章不列具体规则清单的原因。

## 1.4 质量门：从"发现问题"到"阻止合并"

`D5.L2.02`。这是本章最容易误解的一节。

### 定义：质量门是"一组条件"，不是一个检查

SonarQube 官方定义（原文）：

> **质量门使用一组条件（sets of conditions）**，在分析过程中对你的代码进行度量。**根据结果，代码通过或失败**。

而每个条件的构成，官方给得很具体：

> **每个质量门条件是一个组合：一个度量（metric）/ 一个比较符 / 一个错误阈值（error value）**。

官方举的例子：度量 = 可靠性问题数、比较符 = `>`、阈值 = `0`（含义是"没有可靠性问题"）。

**失败规则也是明确的**：

> **只要其中一个条件被满足，质量门就失败。**

### ⭐ 关键事实：质量门默认**不阻断**任何东西

这是本节最重要的一条，而且**只能用官方措辞证明**。看它用的是**情态动词**：

| 官方原文 | 关键词 |
|---|---|
| "PR 装饰……**can be used to** block the merge of the pull request if the quality gate fails" | **can be used to** |
| "质量门状态**can be reported to** your CI pipeline. It **can be used to** fail your CI pipeline" | **can be used to** |

**"可被用来"不等于"默认会"**。官方把真正的执行权交给了外部系统：

| 想做的是 | 需要额外接上 |
|---|---|
| **阻止合并** | **仓库平台的分支保护规则**（把质量门状态设为必需检查） |
| **让流水线失败** | **CI 侧的集成**（Jenkins / GitHub Actions / GitLab CI 等） |

**所以"我配了质量门"这句话的真实含义是**：**我有了一个判决，但还没有执行者。**

**⚠️ 一处必须说明的缺口**：官方这两页**完全没有提到** `sonar.qualitygate.wait` 这类 Scanner 参数，**也没有提到 Webhook**。所以"分析完同步等待门结果"或"Webhook 回调触发失败"的具体用法，**本章不给** —— 需查 CI-based analysis 章节。

### New Code：质量门真正在卡的东西

**先看定义**（官方原文）：

> **新代码是你最近新增或修改的代码。**

而它的**计算方式**值得看清，因为它解释了"为什么同一个项目两次分析的门状态可能不同"：

> SonarQube Cloud 计算出一个**含开始日期与结束日期的新代码周期**。位于**你上次分析日期与起始日期之间**的代码被视为新代码。

**即：新代码不是一个"代码集合"，而是一个"时间窗口内的代码"。**

**四种定义方式**（SonarQube Cloud）：

| 方式 | 起始日期怎么定 | 可配层级 |
|---|---|---|
| **Previous version** | 当前项目版本**首次分析**的日期（版本由 `sonar.projectVersion` 定义） | 组织级 / 项目级 |
| **Number of days** | 当前日期 − X 天；**默认 30，上限 90** | 组织级 / 项目级 |
| **Specific version** | 指定版本**首次分析**的日期 | **仅项目级，且只能通过 Web API** |
| **Specific date** | 直接指定日期 | **仅项目级，且只能通过 Web API** |

**⚠️ 一处版本差异**：**SonarQube Cloud 的这一页里没有 "reference branch"（参考分支）这个选项** —— 它与 SonarQube Server 的可选项不同。所以"新代码 = 相对参考分支的变更"这句话，**只在 Server 侧成立**，本章不外推到 Cloud。

**还有一条与时间窗口直接相关的机制**：

> 新代码问题若 **30 天内未处理**，该问题**就会变成总体代码的一部分**。

**这条的意义**：**"新代码"是一个会过期的状态。** 一个永远不修的问题不会一直"属于新代码"—— 它会**沉入总体代码**，从此不再被默认质量门卡住。**这是"债务会沉淀"的机制化体现。**

### 为什么以新代码为主

官方给的理由不是"新代码更重要"，而是一条**杠杆**：

> 当你给项目新增代码时，**你通常会顺带触碰一部分旧代码**。因此，**分析并清理新代码，会让你同时修复旧代码中的问题，从而逐步提升代码库的整体质量**。

**这条理由的巧妙之处**：它不要求"偿还历史债务"，而要求"**顺手清理**"。因为**改造旧代码的风险与成本远高于改新代码** —— 于是策略变成"用增量带动存量"，而不是"先清债再开发"。

**一条佐证**：内置的 **Sonar way 质量门只对新代码设置条件**。

**一处诚实标注**：这一页**正文没有出现 "Clean as You Code" 这个术语**（虽然上面那段话在语义上正是它的表述）。所以本章**不用这个术语当官方概念**。

### 两个会让人"以为门坏了"的机制

| 机制 | 官方内容 | 症状 |
|---|---|---|
| **Fudge factor（宽容系数）** | 覆盖率与重复率相关条件，在**新代码行数少于 20 行时被忽略**（默认开启，组织级；项目管理员可覆盖） | 改了三行代码，覆盖率明明掉了，门却过了 |
| **Not computed** | ① 只做过**一次**分析（门在**第二次**分析后才计算）；② 项目**未设置 new code definition** | 门状态显示 "Not computed"，CI 里"等待门结果"的逻辑无从判断 |

**第二条对 CI 门禁是致命的**：如果门状态是 `Not computed`，那么"等它通过"的流水线**永远等不到结论**。

### Sonar way 的六条条件（以及一处文档不一致）

内置默认门 **Sonar way** 的条件，官方列的是：

| # | 条件 |
|---|---|
| 1 | 可靠性评级 = A（无新增 Bug） |
| 2 | 安全性评级 = A（无新增漏洞） |
| 3 | 可维护性评级 = A（新代码技术债有限） |
| 4 | 所有新增 Security Hotspot 均已评审（100%） |
| 5 | 新代码测试覆盖率 **≥ 80.0%** |
| 6 | 新代码重复率 **≤ 3.0%** |

**⚠️ 一处文档自身的不一致**：官方原文说它是 "**four conditions**"，但**紧接着列了 6 条**。本章按**实际列出的 6 条**记录，并注明这个矛盾 —— **引用时不要照抄"four"这个数字**。

**另一条可用信息**：**自定义质量门仅 Team 与 Enterprise 计划可用**。小团队只能用内置门 —— 这一点会直接影响"能不能按自己的标准设阈值"。

## 1.5 SCA：查的是"别人的代码"

`D5.L2.03`。这一类的机制与前三条**根本不同**，而差别决定了它怎么用。

### 根本区别：它不看你写的代码

**`npm audit` 的机制**（官方文档）：

> 它会把项目里**配置的依赖描述**提交给默认 registry，请求一份**已知漏洞报告**；如果发现漏洞，会计算影响和适当的修复方案。

具体流程（官方）：

| 步 | 内容 |
|---|---|
| 1 | 以 `package-lock.json` / `npm-shrinkwrap.json` 里的**依赖树**为依据（**默认必须有 lockfile**） |
| 2 | 生成**包含包名与版本列表**的 JSON，POST 到 registry 的 `/-/npm/v1/security/advisories/bulk` |
| 3 | 拿返回的 **advisory（安全公告）** 与依赖版本匹配 |
| 4 | 失败时回退到较慢的 **Quick Audit** 接口，并附上 `npm_version` / `node_version` / `platform` / `arch` / `node_env` 等元数据 |

**⚠️ 本章的一条重要结论（据机制推出，非官方原句）**：

> 它本质上是**"包版本 × 漏洞公告库"的匹配**，**不是扫描你的源代码或运行时行为**。

**"已知漏洞"这个词是官方定义里就有的**（"known vulnerabilities"）。所以：

| 它能发现 | 它不能发现 |
|---|---|
| registry 已收录的、**你依赖的版本范围内**的已知漏洞 | 你**自己代码**里的漏洞（如 XSS 写法） |
| 传递依赖带来的漏洞（因为它算的是完整依赖树） | **尚未公告**的漏洞、零日 |

**这条给了一个清晰的定位**：**SCA 是"供应链的最小防线"，不是"安全审计"。** 把它当成后者，会漏掉整整一类问题（自家代码的安全缺陷）。

**一条附带机制**：npm 会计算 **meta-vulnerability（元漏洞）** —— 某个包本身未必直接有漏洞，但它**依赖了有漏洞的包**，因而间接脆弱。这解释了"为什么漏洞列表里的包名，我没直接安装过"。

### severity 五级与退出码：一个常被误解的开关

**severity 等级**（由低到高）：**`info` → `low` → `moderate` → `high` → `critical`**。

**退出码语义**（官方）：

| 命令 | 何时返回 0 |
|---|---|
| `npm audit` | **没有发现漏洞** |
| `npm audit fix` | 没有漏洞，**或所有漏洞都被成功修复** |
| 发现漏洞时 | **取决于 `audit-level` 配置**：**默认只要发现任意漏洞就返回非零** |

**⭐ 一个极易误解的细节**（官方明确）：

> `--audit-level` 用来指定"**最低多少级漏洞才导致命令失败**"。它**不会过滤报告输出**，**只改变失败门槛**。

**这条的实践含义**：

```
npm audit --audit-level=high
```

- `high` / `critical` → **退出码非零**（流水线失败）
- `info` / `low` / `moderate` → **仍然出现在报告里**，但**不导致失败**

**所以"加了 `--audit-level=high` 就等于不管 low 级漏洞了"是错的** —— 它只是**不因此失败**，报告里依然有。**这两件事的差别，在"有人看报告"与"没人看报告"的团队里会得出完全不同的结果。**

### `audit fix` 与 `--force`：一条安全分界线

| 命令 | 行为（官方） |
|---|---|
| `npm audit fix` | 按计算出的修复方案自动修，底层执行完整 `npm install`；**不会为了修复而突破 `package.json` 中声明的依赖范围** |
| `npm audit fix --force` | 允许安装**超出声明范围**的模块，**包括 SemVer-major 变更** |

**官方对 `--force` 的警告很重**：它是一个**全局性的"解除保护"开关**（不只影响 audit fix），"**如果没弄清自己要做什么，强烈不建议使用**"。

**这条把 SCA 与 D2 的 SemVer 知识接上了**：`--force` 之所以危险，正是因为它**允许跨大版本**（`D2` 第 2 章 §2.5 已讲"最左侧非零位"规则）—— 而大版本变更按定义就是破坏性的。

**两个更安全的替代**（官方）：`--package-lock-only`（只更新 lockfile，不动 `node_modules`）、`--only=prod`（跳过 devDependencies）。

### 第二种做法：让机器持续开 PR

`npm audit` 是**跑一次查一次**。而漏洞是**持续被发现**的 —— 于是有了第二类工具：**持续监控 + 自动开 PR**。

**Dependabot 有两种更新，机制完全不同**（官方原文对比）：

| 维度 | **security updates** | **version updates** |
|---|---|---|
| 目的 | 更新**存在已知漏洞**的依赖 | 保持依赖为最新，**即使没有任何漏洞** |
| 触发 | 依赖图中出现 **Dependabot alert**（且有可用补丁） | 检测到依赖**已过时**（按 `schedule`） |
| 版本目标 | **含补丁的最低版本** | manifest 中依赖的**最新版本** |
| 需要 `dependabot.yml` 吗 | **不需要** | **必须** |
| 一句话 | **事件驱动（漏洞驱动）** | **时间驱动（计划驱动）** |

**⭐ 官方还有一条很容易误解的说明**：

> **`dependabot.yml` 文件里的设置与 Dependabot security alerts 之间没有任何交互**（唯一例外：合并安全更新 PR 会关闭相关 alert）。

**所以"我在 `dependabot.yml` 里配了忽略规则，安全更新就不会来了"是错的** —— 两者不通。如果想只对部分 alert 开 PR，官方建议**保持 security updates 关闭**，改用 **auto-triage rules**。

### 三个容易踩的具体坑（均来自官方）

| # | 坑 | 官方依据 |
|---|---|---|
| **1** | **alert 覆盖完整依赖图，但 security updates 只对 manifest / lockfile 中声明的依赖触发** | 原文明确限定 |
| **2** | **npm 生态可以连带更新父依赖；其他生态若必须更新父依赖，则无法完成**（会在 alert 上报错） | 原文按生态区分 |
| **3** | **兼容性评分不是本仓库的 CI 结果** | 原文：评分 = **其他公共仓库**针对同一更新所运行 CI 的通过百分比 |

**第 1 条最反直觉**：你会看到一条 alert（传递依赖有漏洞），但**没有对应的 PR** —— 因为它不在你"声明的依赖"里。**这不是 bug，是设计。**

**第 3 条也值得单独记**：兼容性评分看起来像"CI 通过率"，实际是**跨仓库的历史统计**，**是参考性提示，不是本仓库的门禁**。

**另有一条运维细节**：**当维护者不再与 Dependabot PR 交互时，它会临时暂停更新并通知你** —— 这解释了"为什么 PR 突然不来了"。

## 1.6 三类检查的协同：一条按"反馈成本"排的顺序

### 顺序

| 位置 | 检查 | 反馈延迟 | 为什么在这 |
|---|---|---|---|
| 1 | **编辑器内**（ESLint / Stylelint / `tsc`） | **秒级** | 问题刚产生就可见 |
| 2 | **提交前**（lint-staged） | 秒级 | 只查改动的文件（`D1` 第 1 章） |
| 3 | **CI 内**（全量 lint + 类型 + 测试） | 分钟级 | 兜住"本地没跑"的情况 |
| 4 | **质量门**（SonarQube 一类） | 分钟级 | 在合并前给出**判决** |
| 5 | **依赖扫描**（`npm audit` / Dependabot） | **定时 + 事件** | **不随你的变更节奏** |

**前四行是同一条逻辑**（`D3` 第 9 章 §9.3 已给过一般形式）：**能在更早发现的问题，不该推到更晚。**

### 第五行为什么特殊

**因为 SCA 的两个输入里，有一个不由你控制**：

| 输入 | 谁决定 | 什么时候变 |
|---|---|---|
| 你的依赖树 | **你** | 你改 `package.json` 时 |
| **漏洞公告库** | **别人** | **随时** |

**所以 SCA 不能只放在 CI 的 PR 检查里** —— 因为**一个没改任何依赖的 PR，也可能突然"变红"**（某个依赖昨天还没被公告漏洞）。这会带来一个具体后果：

> **PR 检查会因为"与你无关的原因"失败。**

**治理上的处理**（本章的建议）：**把"变更驱动的 SCA"与"时间驱动的 SCA"分开**。

| 类型 | 放在哪 | 目的 |
|---|---|---|
| **变更驱动** | PR 检查（只检查**本次新增/升级的依赖**） | 不引入**新的**已知漏洞 |
| **时间驱动** | 定时任务（全量扫描）+ Dependabot 类持续监控 | 发现**存量**依赖的新披露漏洞 |

**这条区分的价值**：**它把"你的 PR 为什么红了"变成一个可解释的问题** —— 要么你引入了新漏洞（该修），要么是存量漏洞被公告了（走定时流程，不阻塞无关 PR）。

**⚠️ 一条与第 4 行有关的提醒**：质量门的 `Not computed` 机制（§1.4）会让"等门通过"的逻辑失效。**流水线里"等门"的步骤必须先判状态可计算，再判是否通过。**

## 1.7 治理动作：六个判定阈值

与前几章同体例。**全部是起点值，需按项目校准。**

| # | 现象 | 判定阈值（起点值） | 动作 | 依据 |
|---|---|---|---|---|
| 1 | 质量门配了，但坏代码照样合进来 | **任意一次"门失败但 PR 被合并"** | 检查有没有把门状态设成**必需检查**（分支保护）—— 官方措辞是 "**can be used to**"，默认不阻断 | §1.4 |
| 2 | 门状态一直是 `Not computed` | **任意一次 `Not computed` 卡住流水线** | 查两个原因：只分析过一次（第二次才计算）/ 未设 new code definition | §1.4 |
| 3 | 改了几行代码，覆盖率掉了但门过了 | **新代码 < 20 行** | 这是 **fudge factor**（默认开启），不是 bug | §1.4 |
| 4 | 报告里同一问题出现两次 | **同一类问题被 ≥2 个工具报告** | 关掉一边，或在汇总层去重。重复会让"总数"失去意义 | §1.3 |
| 5 | 加了 `--audit-level=high` 后以为不管低级漏洞了 | **报告里仍有 low / moderate 条目** | `--audit-level` **只改失败门槛，不过滤输出** | §1.5 |
| 6 | 看到 alert 却没有对应 PR | **传递依赖有 alert 但无 PR** | 官方：alert 覆盖完整依赖图，但 **security updates 只对 manifest/lockfile 声明的依赖触发** | §1.5 |

### 三条使用说明

**① 阈值 1 是本章最重要的一条。**

它不报错、不告警 —— 质量门会正常产出 `Failed`，PR 也会正常被合并。**只有去核对"分支保护里有没有它"才能发现。**

**② 阈值 4 的代价被系统性低估。**

重复报告的直接成本是"烦"，真实成本是**"总数"这个指标失效** —— 而"新增了几条问题"是判定质量变化最常用的口径。

**③ 阈值 5 与 6 都属于"以为工具在做 X，实际它在做 Y"。**

这类误解的特点是：**它们不导致报错，只导致错误的安全感。**

### 什么时候"不该加检查"

| 情况 | 为什么 |
|---|---|
| **没有能力处理报出来的问题** | 会训练出"忽略"（`D6` 第 4 章 §4.6 的告警同源问题） |
| **检查项与会话内的反馈重复** | 编辑器已经报过，CI 再报一遍只增加噪声 |
| **规则与团队实际写法长期冲突** | 要么改规则，要么改代码；**长期红色等于没有规则** |
| **还没解决"门不阻断"的问题** | 加更多检查只是让"看得见但不生效"的判决更多 |

## 1.8 动手

**每一项都要求说出理由**：

| 任务 | 验收 |
|---|---|
| 列出你项目里所有静态检查工具，标注各自"查什么对象" | 用 §1.1 的四类归类；指出哪些是"查你写的"，哪些是"查别人的" |
| 找出一处被两个工具重复报告的问题 | 说出你选了哪边保留、为什么（§1.3 的三种做法各有什么代价） |
| 查一次 Stylelint 能否格式化 | 说出官方把它交给了谁、依据是哪个词（"complementary"） |
| 查一次你的质量门状态是否被设为"必需检查" | 若没有，说明"配了门"与"门生效"差在哪一步 |
| 查一次你的 new code definition 是哪种 | 说出若用 Number of days，默认多少天、上限多少天 |
| 构造一次 `Not computed`（只分析一次） | 记录现象，说出它为什么会让"等门"的流水线卡死 |
| 改 10 行以内的代码，观察覆盖率条件 | 说出这是 fudge factor 还是真的过了 |
| 跑 `npm audit --audit-level=high` | 说出它改变了什么、没改变什么 |
| 查一次你项目里有没有"传递依赖有 alert 但无 PR"的情况 | 用 §1.5 的第 1 个坑解释 |
| 查看一个 Dependabot PR 的兼容性评分，判断它来自哪 | 说出它为什么不是"本仓库 CI 通过率" |
| 检查你的 `dependabot.yml` 里有没有 ignore 规则 | 说出它对 security updates **有没有**作用、依据是哪句原文 |

**进阶挑战**（任选一项）：

1. **做一次"重复报告审计"**：把 ESLint / Stylelint / `tsc` / 质量门四条流水线的报告合并，统计重复率。目标是把"总数"恢复成可用指标。
2. **把 SCA 拆成"变更驱动 + 时间驱动"两条流水线**：PR 里只查新增/升级的依赖，定时任务做全量。要求说明这样拆分后，"PR 为什么红了"如何变得可解释。
3. **验证一次"质量门到底能不能拦住合并"**：故意提交一个必然失败的门状态，看 PR 是否真的被阻止。**这一步能一次性暴露所有"配了但没接上"的情况。**

## 1.9 本章常见误区

| # | 误区 | 纠正 |
|---|---|---|
| 1 | "前三类与 SCA 是同类" | **前三类查你写的代码，SCA 查你没写的代码**。这条差别决定运行节奏（变更驱动 vs 时间驱动） |
| 2 | "CSS 归 Stylelint、JS 归 ESLint 是官方说的" | **不是**。Stylelint 首页**全文未提 ESLint**，它只对比了 Prettier。语言边界是**常识分工，无官方背书** |
| 3 | "类型检查通过就说明代码正确" | 类型全对但 `return a - b` 写成 `return a - b` 之外的逻辑错误，**三条静态检查都发现不了**。那要靠测试 |
| 4 | "多个工具报同一问题只是烦" | 真实成本是**"总数"这个指标失效** —— 你无法用"新增几条"判断质量变化 |
| 5 | "质量门会自动拦住合并" | **不会**。官方措辞是 "**can be used to**" block / fail。执行权在**分支保护**或 **CI 集成** |
| 6 | "配了质量门就有了门禁" | 你只得到了**判决**，还没得到**执行者**（§1.7 阈值 1） |
| 7 | "新代码 = 最近提交的那些文件" | 它是一个**含起止日期的时间窗口**内的代码；起始日期由 new code definition 决定 |
| 8 | "新代码定义随便选一个" | **Cloud 版没有 reference branch**（与 Server 不同）。选项差异会直接影响门的严格度 |
| 9 | "新代码问题会一直是新代码" | **30 天内未处理就会沉入总体代码**。这是"债务沉淀"的机制化 |
| 10 | "门显示 Not computed 是数据延迟" | 两个真实原因：**只分析过一次**（第二次才计算）/ **未设 new code definition** |
| 11 | "覆盖率没达标但门过了，一定是配错了" | 可能是 **fudge factor**：新代码 **< 20 行**时覆盖率与重复率条件被忽略（默认开启） |
| 12 | "Sonar way 有四个条件" | 官方原文说 "four conditions" **但紧接着列了 6 条**。按 6 条记，**别照抄那个数字** |
| 13 | "自定义质量门谁都能建" | 官方：自定义门**仅 Team 与 Enterprise 计划可用** |
| 14 | "`npm audit` 会扫描我的源码" | **不会**。它是"**包版本 × 漏洞公告库**"的匹配，机制上不读你的源码 |
| 15 | "`npm audit` 能发现零日漏洞" | 只能覆盖**已收录的已知漏洞**（官方定义用 "known vulnerabilities"） |
| 16 | "`--audit-level=high` 就不管 low 级了" | 它**只改失败门槛，不过滤输出**。低级别漏洞仍在报告里 |
| 17 | "`npm audit fix` 会顺带升大版本" | **不会**，它不突破 `package.json` 声明的范围。`--force` 才会（**可能引入破坏性变更**） |
| 18 | "`--force` 只是个 audit 参数" | 它是**全局性的"解除保护"开关**，官方"强烈不建议"在没弄清时使用 |
| 19 | "Dependabot 的两种更新是一回事" | **security = 事件驱动（漏洞驱动），version = 时间驱动（计划驱动）**。目标版本也不同 |
| 20 | "`dependabot.yml` 能管安全更新" | 官方明确：**`dependabot.yml` 的设置与 security alerts 之间没有交互**（唯一例外是合并 PR 关闭 alert） |
| 21 | "有 alert 就一定有 PR" | **security updates 只对 manifest / lockfile 中声明的依赖触发**；传递依赖可能只报警不开 PR |
| 22 | "Dependabot 的兼容性评分是本仓库 CI 结果" | 它是**其他公共仓库**针对同一更新的 CI 通过百分比，**是参考提示，不是门禁** |
| 23 | "Dependabot PR 不来了是配置坏了" | 官方：**维护者长期不交互时，它会临时暂停更新并通知你** |
| 24 | "SCA 应该全放在 PR 检查里" | 漏洞库变化**不由你控制**，会让无关 PR 变红。应拆成**变更驱动 + 时间驱动**两条 |
