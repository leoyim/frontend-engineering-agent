# D3 第 9 章 · 深度定制、选型与迁移

## 9.1 定制的三个层次：先确认真的需要写代码

`D3.L4.08` 的名字是"深度定制"，但治理层的第一课是**先排除不需要定制的情况**。

| 层次 | 手段 | 成本 | 什么时候停在这一层 |
|---|---|---|---|
| **0. 不用动** | 现有配置项、现有插件 | 最低 | 有现成方案能覆盖 90% |
| **1. 写配置** | 组合已有 loader / plugin / 选项 | 低 | 只需改变行为参数 |
| **2. 写扩展** | 自定义 loader / plugin | **中到高** | 需要新的**转换**或新的**构建期动作** |
| **3. 改链路** | 替换工具、改构建架构 | **最高** | 现有工具的能力边界到了（§9.4） |

**一条判断顺序**：**从 0 往上走，每一层先问"上一层能不能做到"**。跳过这一问的后果，是项目里积累一堆"只做了一件小事"的自研插件 —— 而它们**每一个都是迁移时的钉子**（§9.3）。

### 为什么自研扩展的成本被系统性低估

因为它的成本**不在写的时候，在维护与迁移的时候**：

| 成本 | 什么时候付 |
|---|---|
| 写 | 一次性 |
| 跟随上游 API 变化 | **每次工具大版本升级** |
| 迁移到新工具 | **一次全部**（自定义插件几乎不可能平移 —— 第 6 章 §6.5 的判据） |
| 交接 | 作者离开后 |

**最后一条最容易被忽略**：一个只有原作者能改的构建插件，会成为**团队的结构性风险**。

## 9.2 写扩展必须守住的四个边界

这四条全部来自第 4 章已核验的机制。它们不是"最佳实践"，而是**写错了会静默失效**的地方。

### 边界一：位置 —— loader 只管一个文件，plugin 才跨阶段

**判据**（第 4 章 §4.4–§4.5）：

| 你要做的事 | 用哪个 |
|---|---|
| 把某种文件转成合法模块 | **loader**（`test` + `use`） |
| 跨文件/跨阶段（读全局信息、生成产物、改配置） | **plugin** |

**这条的硬性依据**：loader 的作用域是"一个文件进、一个模块出"，且**链尾必须返回匹配模块类型的内容**（第 4 章 §4.4）。**任何需要"看到别的文件"的逻辑，loader 都做不到** —— 强行去做会得到"顺序依赖"的隐性 bug。

### 边界二：阶段 —— 改产物必须用 `processAssets` + stage

**这是本章最硬的一条。** 官方把"在 `emit` 里写产物文件"列为**常见错误并报告为已废弃**（**官方原文见第 4 章 §4.5**）。

**为什么 `emit` 不行，一句话**：它跑在 compilation **封口之后**，所以写出的文件**跳过了压缩、sourcemap、hash 这一整段**，**而且别的插件看不到它** —— 产物里有它，链路上没有它。

**正确做法**：`compilation.hooks.processAssets` + 按工作性质声明 stage（新增文件用 `PROCESS_ASSETS_STAGE_ADDITIONAL`，压缩用 `PROCESS_ASSETS_STAGE_OPTIMIZE_SIZE`）。

**为什么 stage 重要**：官方明说它的存在是为了「**让插件自动组合，而不必在配置里手工排序**」。**声明式的位置 vs 命令式的顺序** —— 后者在多人协作里必然被重排。

### 边界三：状态 —— compiler 还是 compilation

**判据**（**官方区分见第 4 章 §4.5**）：

**状态该挂在哪，看它要活多久。** watch 模式下每次重建都会产出**新的 Compilation**，而 **Compiler 始终是那一个**。于是：

| 状态 | 挂哪 | 例子 |
|---|---|---|
| **要跨重建留住** | `compiler` | 缓存、统计计数、已处理文件集合 |
| **只属于本次构建** | `compilation` | 本次的产物清单、本次的错误集合 |

**放错的症状是"增量构建结果不对、全量构建正常"** —— 极难查，因为它只在第二次构建出现。

### 边界四：确定性 —— 插件不能把"非内容的输入"写进产物

这一条是第 8 章 §8.2 的直接应用。**四个 hash 不稳的成因里，有两个是插件最常引入的**：

| 成因 | 插件里的典型写法 |
|---|---|
| **构建元信息进产物** | 在产物头部注入 `new Date().toISOString()`、版本号、随机 id |
| **绝对路径进产物** | 把 `__filename` / `path.resolve(...)` 写进生成的内容 |

**这两条的共同性质**：**它们在开发时完全无害，只在"发版后用户要重下全部"时体现** —— 也就是说，**代价被推迟到最不该出现的时候**。

**治理动作**：任何自研插件在注入内容前，先问一句 **"这个东西在同样输入下会不会变"**。会变 → 不要进产物（放进单独的、不缓存的元信息文件）。

### 附带一条：dev 与 build 的一致性

第 4 章 §4.6 已核验 Vite 侧的两个"dev 期不调用"：

| 钩子 | dev 期 |
|---|---|
| `moduleParsed` | **不调用**（为避免全量 AST 解析） |
| Output Generation Hooks | **不调用**（`closeBundle` 除外） |

**推论**：如果插件逻辑依赖 `moduleParsed` 或 output 钩子，它**在 dev 下不会生效** —— 而 `transform` / `load` / `resolveId` 是**每次模块请求都调用**的。

**写之前先看一眼官方那张"钩子调用频次表"**（第 4 章 §4.6），比写完再调试便宜。

## 9.3 构建链路改造：什么时候值得写插件

### 判据表

| 判据 | 倾向"写" | 倾向"不写" |
|---|---|---|
| **使用范围** | 多个项目复用 | 只有本项目用一次 |
| **生命周期** | 长期（一年以上） | 一次性（做完就不再改） |
| **是否有更合适的层** | 只能构建期做 | **lint / 类型系统 / 测试能做** |
| **上游是否已有** | 官方或主流生态无方案 | 有现成插件，只是配置麻烦 |
| **性能敏感度** | 不敏感（低频、小范围） | 敏感（每次构建都跑、遍历全图） |

### 三条最常被违反的纪律

**① 不要把"代码质量"塞进构建。**

构建期的插件**跑得晚、报得晚、且不能增量反馈**。而 lint 与类型检查能在**编辑器里实时**给出反馈（`D1` 领域）。

| 想在构建期做的事 | 更合适的层 |
|---|---|
| 禁止某些 API | **ESLint 规则**（`D1` 第 1 章） |
| 检查类型 | `tsc --noEmit`（`D2` 第 3 章的"检查与产出分离"） |
| 检查依赖方向 | 静态分析（`import/no-cycle` 一类） |
| 检查产物是否合规 | **产物层的独立检查脚本**（不必进构建） |

**判据**：**如果一件事能在"写代码时"发现，就不该推迟到"构建时"。**

**② 不要用插件弥补"设计问题"。**

例：为了兼容某个只导出 CJS 的库而写一个"自动加 `default` 的插件"。**可能的根因是依赖选择问题** —— 而插件把这个决策**固化进了构建流程**，让换库变得更贵。

**③ 插件是迁移时最贵的一项。**

第 6 章 §6.5 的三条判据里，第一条就是「**看插件，不看 loader**」：**loader 语义局部、易平移；plugin 与 hook 模型强绑定，最难搬。**

**所以每写一个插件，都在为未来的迁移增加成本。** 这条不是"别写"，而是"**写之前算清这笔账**"。

### 一个可以让插件更便宜的做法

**把插件写成"薄的一层"**：真正的逻辑放在**不依赖构建工具的纯函数模块**里，插件只做"取数据 → 调纯函数 → 放回去"。

| 好处 | 为什么 |
|---|---|
| 可单测 | 纯函数不需要跑构建 |
| 可复用 | 换工具时逻辑还在，只重写外壳 |
| 可审查 | 逻辑与 hook 样板分离，评审看得清 |

**这是本章对 `D3.L4.08` 最实用的一条工程建议**：**让插件薄，让逻辑厚。**

## 9.4 选型决策矩阵

`D3.L4.09`。第 6 章 §6.6 给的是"投入建议"（分三档），本节给的是**决策流程** —— 因为选型失败通常不是"选错了工具"，而是**顺序错了**。

### 正确的顺序：约束 → 层次 → 工具

**大多数人从"工具"开始**（"Rspack 和 Rolldown 哪个好"），于是**先锁定了答案，再去找理由**。正确的顺序是三层：

| 层 | 问题 | 输出 |
|---|---|---|
| **① 约束** | 团队会什么？现有生态是什么？平台限制是什么？ | **一份排除清单** |
| **② 层次** | 我只需要换转译压缩，还是整个打包器？ | **A / B / C / D / E 档**（第 6 章 §6.1） |
| **③ 工具** | 在这个档次里，哪个满足约束？ | 具体工具 |

**先做第 ① 层的原因是**：**约束是硬的，工具是软的。** 一个不符合约束的最优工具，在你的项目里就是最差的。

### 第 ① 层：约束清单

| 约束 | 为什么它是硬的 |
|---|---|
| **团队技能** | 只有一人会的工具 = 单点风险 |
| **现有插件/loader 存量** | 决定迁移成本下限（第 6 章 §6.4 的"兼容对象"那一列） |
| **构建期执行 JS 的依赖** | 一旦有，某些原生架构**搬不过去**（第 6 章 §6.5 的 `sassOptions.functions`） |
| **包管理器** | 如 Yarn PnP 在 Turbopack 是 **"Not planned"**（第 6 章 §6.5） |
| **框架绑定** | 如 Next.js 与 Turbopack 是内置关系 |
| **有没有视觉回归** | 没有的话，任何会改变行为细节的迁移都是盲赌 |

**这张表的作用是产出"排除项"**。**排除到最后只剩一个候选，选型就结束了** —— 而且这个结论**很难被推翻**，因为它建立在硬约束上。

### 第 ② 层：先定层次，再定工具

这是最容易被跳过的一层，也是最省钱的一层。

| 层次 | 判断依据 | 收益上限 |
|---|---|---|
| **A. 只换转译与压缩** | 转译+压缩占总耗时 > 40%（第 7 章 §7.5 阈值 4） | **就是这个占比** |
| **B/C/E. 换打包器但兼容旧 API** | 瓶颈在 linking / 增量重建 | **受串行占比约束**（第 7 章 §7.3） |
| **D. 换架构** | 需要结构性改进（函数级增量等） | 高，但**行为风险也高** |

**关键认知**（第 6 章 §6.6）：**A 档是"纯收益"** —— 同样的输入、同样的输出，只是更快；**换打包器则可能改变产物语义**。

**所以第 ② 层的默认答案是 A 档。** 只有在"换完 A 档还慢"时，才进入 B/C/E 或 D。

### 第 ③ 层：候选比较矩阵

进入这一层时，候选通常只剩 2–3 个。**比较的维度应当是"约束的满足度"，而不是"速度"**：

| 维度 | 权重来源 | 怎么核验 |
|---|---|---|
| **兼容对象** | 你的现有生态（webpack / Rollup / Vite / 无） | 第 6 章 §6.4 的表 |
| **插件可用率** | 你的插件清单 | **自己盘一遍**（Rspack 官方只给"头部 50 个 > 85% 可用或有替代"） |
| **架构性不可为项** | 你是否有构建期执行 JS 的依赖 | 查官方"Unsupported and unplanned"清单 |
| **成熟度** | 你的风险容忍度 | **只看官方可核验信号**（第 6 章 §6.6 的矩阵） |
| **官方是否给基准** | 你是否需要自证收益 | **多数工具没给**（第 6 章 §6.6 最后一列） |

**⚠️ 最后一行值得展开**：**如果官方没给基准，你就必须自己量** —— 而这需要第 7 章 §7.4 的六步法。**"选型"与"验证"是同一件事的两半**，缺一半就只能靠"感觉快了"。

### 一条反常识的结论

**选型的第一问不是"哪个快"，而是"我能接受多大迁移成本"。**

理由：**速度收益是可量化的、有上限的**（第 7 章 §7.3 的串行占比约束）；而**迁移成本是不可逆的**（一旦换了，回退要再付一次）。**两个不可逆的决策里，先算那个回不了头的。**

## 9.5 迁移评估：一页纸模板

`D3.L4.10`。一页纸的意义不是"简短"，而是**强迫你把不确定的地方暴露出来**。

### 模板（七个字段）

| # | 字段 | 填什么 | 不填会怎样 |
|---|---|---|---|
| **1** | **动机** | 一个指标 + 当前值 + 目标值 | "想换新工具"不是动机 |
| **2** | **范围** | 换哪一层（A/B/C/D/E）+ 涉及几个项目 | 范围不清 → 工期与风险都估不出 |
| **3** | **兼容清单** | 插件 / loader / 构建期 JS 依赖，逐项标"可用 / 有替代 / 无解" | 这是**最容易低估**的一项（第 6 章 §6.5） |
| **4** | **行为风险** | 可能变化的行为细节 + 现有回归手段 | 没有视觉回归 = 盲赌 |
| **5** | **回退方案** | 出问题时怎么退、退的代价 | 没有回退 = 不能尝试 |
| **6** | **验收标准** | 用哪个指标、达到多少、怎么量 | 无法证明成功，也无法证明失败 |
| **7** | **时间盒** | 最迟什么时候判定"不做" | 迁移常变成无期限的并行状态 |

### 空模板

```markdown
## 迁移评估：<项目/团队>

**1. 动机**
- 指标：<冷启动 / 首次可见 / 增量重建 / HMR 更新 —— 选一个>
- 当前值：<数字>（机器：<>；缓存状态：<>；样本：<>）
- 目标值：<数字>

**2. 范围**
- 换哪一层：<A 只换转译压缩 / B 兼容 Rollup / C 兼容 webpack / D 重设计 / E 兼容 Vite>
- 涉及项目：<n> 个

**3. 兼容清单**
| 项 | 类型 | 状态 | 处置 |
|---|---|---|---|
| <插件名> | plugin | 可用 / 有替代 / 无解 | <改法或替代物> |
| <loader 名> | loader | 可用 / 有替代 / 无解 | <改法> |
| <构建期执行 JS 处> | 代码 | 可用 / 无解 | <评估> |

**4. 行为风险**
- 可能变化：<CSS 顺序 / 小数精度 / chunk 边界 / 其它>
- 回归手段：<视觉回归 / 端到端 / 人工基线 / 无>

**5. 回退方案**
- 怎么退：<保留旧配置 / 分支 / 开关>
- 退的代价：<重建时间 / 重测范围>

**6. 验收标准**
- 指标：<>；达标线：<>；测量方式：<>

**7. 时间盒**
- 判定日：<日期>
- 到点未达标则：<放弃 / 缩范围>
```

### 三条填写纪律

**① 第 3 项必须逐项列，不能写"大致兼容"。**

Rspack 官方的口径是「头部 50 个插件 **> 85% 可用或有替代**」（第 6 章 §6.4）—— **这个数字对你的项目没有意义**，因为你的插件可能全在那 15% 里。**只有逐项盘自己的清单才有效。**

**② 第 4 项如果填"无回归手段"，这项评估就已经有结论了。**

第 6 章 §6.5 的反直觉结论：**迁移最大的风险不是构建失败，而是"构建成功但行为微变"**（CSS Module 排序、CSS 小数精度 5 位 vs 10 位）。**没有回归手段意味着你会在上线后才发现。**

**③ 第 7 项的存在是为了避免"永久迁移中"。**

迁移最常见的失败形态不是"换失败了"，而是**"两套配置长期并存"** —— 团队一半人用旧的、一半人用新的，两边的行为差异无人说得清。**时间盒强制做出二选一。**

### 判据：填不满的表就是不该迁的信号

| 空缺 | 含义 |
|---|---|
| 第 1 项填不出"一个指标" | 你还没有 §7.4 第 1 步，先别迁 |
| 第 3 项列不出来 | 你不知道自己的依赖面，风险不可估 |
| 第 4 项是"无" | 你不知道行为会不会变 |
| 第 5 项是"无" | 你不能试，只能赌 |
| 第 7 项填不出来 | 这件事没有终点 |

**这张表最大的价值是"劝退"** —— 它让"想换新工具"这个冲动，先在纸上过一遍。

## 9.6 治理动作：六个判定阈值

与第 7、8 章同体例。**全部是起点值，需按项目校准。**

| # | 现象 | 判定阈值（起点值） | 动作 | 依据 |
|---|---|---|---|---|
| 1 | 想写一个构建插件 | **现有配置 + 现成插件能满足 ≥ 90% 需求** | 先不写，把 90% 做好、剩下 10% 接受或换方案 | §9.1 |
| 2 | 已经写了插件，但只在 build 生效 | **dev 下完全不生效** | 查钩子：`moduleParsed` / Output Generation Hooks **dev 期不调用** | §9.2 |
| 3 | 插件生成的产物没被压缩 / 没加 hash | **任意一个产物文件绕过压缩或 hash** | 把 `emit` 改成 `processAssets` + 合适的 stage | §9.2 |
| 4 | 增量构建结果与全量不一致 | **同一份源码，增量与全量产物不一致** | 查插件状态挂 compiler 还是 compilation | §9.2 |
| 5 | 发版后用户要重下全部 | **改一行导致 > 5 个文件失效** | 先查 hash 稳定性（第 8 章 §8.2 的四个成因），尤其插件注入的元信息/绝对路径 | §9.2 |
| 6 | 准备迁移，但评估表填不满 | **七个字段缺任意一个** | 先补齐，再决定；尤其缺"行为风险"与"回退方案"时**不要开始** | §9.5 |

### 使用说明

**阈值 1 是本章的第一道闸。** 它不判断"插件写得好不好"，只判断**"该不该写"** —— 而后者决定的是你未来三年的迁移成本。

**阈值 2 与 3 是"静默失效"类**：不报错、有产物、看起来正常，但**少了一层加工**或**根本没跑**。这类问题只能靠"知道有这回事"来发现。

**阈值 6 是本章唯一一条"可以阻止项目启动"的阈值。** 它的正当性来自 §9.5 的结论：**填不满的表，说明你还没准备好，而不是说明工具不好。**

### 什么时候"不该定制、不该迁移"

| 情况 | 为什么 |
|---|---|
| 需求是"一次性"的 | 插件成本在维护与迁移，不在写（§9.1） |
| 需求能在 lint / 类型 / 测试层解决 | 那三层反馈更早、更便宜（§9.3） |
| 团队里只有一个人能改这套构建 | 结构性单点风险 |
| 没有行为回归手段 | 迁移是盲赌（§9.5 第 3 条纪律） |
| 动机填不出一个指标 | 你还没有基线，先做第 7 章 |

## 9.7 动手

**每一项都要求说出理由**：

| 任务 | 验收 |
|---|---|
| 把你项目里的自研构建扩展列出来，逐个标注属于三个层次中的哪一层 | 说出哪几个其实可以用配置或现成插件替代 |
| 取其中一个插件，判断它"薄"还是"厚" | 说出能否把逻辑抽成不依赖构建工具的纯函数 |
| 检查你项目里所有 loader，确认没有跨文件逻辑 | 说出为什么 loader 做不到跨文件（链尾必须匹配模块类型） |
| 全局搜索项目里有没有在 `emit` 钩子里写文件的代码 | 若命中，说出它跳过了哪些阶段 |
| 检查自研插件有无注入时间戳 / 版本号 / 绝对路径 | 说出这分别对应第 8 章 §8.2 的哪两个成因 |
| 取一个插件，确认它在 dev 下是否真的生效 | 用第 4 章 §4.6 的钩子频次表解释结果 |
| 按 §9.4 的三层顺序，为你的项目写一份选型结论 | 说出第 ① 层排除了哪些候选、依据是哪条硬约束 |
| 盘一次你的插件清单，逐项标"可用 / 有替代 / 无解" | 说出"有替代"那一项需要多少改造工作量 |
| 用 §9.5 的空模板填一遍（哪怕最后结论是"不迁"） | 说出哪一格最难填、为什么 |
| 为你准备做的迁移写一条"时间盒 + 到点动作" | 说出为什么没有时间盒会变成"永久迁移中" |

**进阶挑战**（任选一项）：

1. **把一章插件变薄**：把一个自研插件的逻辑抽成纯函数 + 薄壳，补上纯函数的单测。要求说明"换成另一个打包器时，哪部分可以留用"。
2. 给团队做一份**迁移评估模板的填写样例**（用一个真实或构造的项目填满七格），重点展示第 3、4 项的写法 —— 这两项最容易写成空话。
3. 把 §9.4 的三层顺序 × 第 6 章 §6.6 的三档投入 × 第 7 章 §7.4 的六步法做成一张流程图：**从"构建慢"到"决定动不动"的完整决策路径**。这张图的价值在于：**它把三章的内容接成了一条可执行的路**。

## 9.8 本章常见误区

| # | 误区 | 纠正 |
|---|---|---|
| 1 | "有问题就写个插件" | 先走"配置 → 现成插件 → 自研"三层。**自研的成本在维护与迁移，不在写** |
| 2 | "loader 和 plugin 差不多，能跑就行" | **loader 只管单文件，链尾必须匹配模块类型**。跨文件逻辑 loader 做不到 |
| 3 | "在 `emit` 里写产物文件也能跑" | 官方列为**常见错误并报告为已废弃**：会跳过压缩 / sourcemap / hash，且**其他插件看不到它** |
| 4 | "插件顺序在配置里排好就行" | 应用 **`processAssets` + stage**。官方明说 stage 的存在是为了**让插件自动组合、不必手工排序** |
| 5 | "插件状态放哪都行" | **要跨重建保留的挂 compiler，单次构建的挂 compilation**。放错的症状是"增量结果不对、全量正常" |
| 6 | "产物里加个构建时间戳只是方便排查" | 它会让 **hash 每次都变** → 三层缓存全部作废（第 8 章 §8.2 成因 3） |
| 7 | "产物里写绝对路径无所谓" | 换机器/换目录就变 → hash 不稳，且与 CI 缓存失效同源（第 8 章 §8.2 成因 4） |
| 8 | "插件在 build 下能用就够了" | dev 下 `moduleParsed` 与 Output Generation Hooks **不调用**。不看频次表会白写一遍 |
| 9 | "代码规范检查放构建期最保险" | 构建期**跑得晚、报得晚、不能增量反馈**。lint 与类型检查能在编辑器里实时给（D1 / D2） |
| 10 | "选型就是比哪个工具快" | 顺序应当是**约束 → 层次 → 工具**。先比速度等于先锁答案再找理由 |
| 11 | "直接从换打包器开始最省事" | **A 档（只换转译压缩）是纯收益**：输入输出不变，只是更快。应先做这一档 |
| 12 | "Rspack 说 85% 插件可用，所以我大概也没问题" | 那个数字是**头部 50 个插件**的统计。**你的插件可能全在那 15% 里**，必须自己盘 |
| 13 | "官方有基准，我不用自己量" | **多数工具没给基准**（第 6 章 §6.6 最后一列）。没给就必须用第 7 章六步法自量 |
| 14 | "迁移评估表可以只填关键的几项" | **七格缺一格就该停下**。尤其缺"行为风险"与"回退方案"时不要开始 |
| 15 | "构建成功就说明迁移成功了" | 最大风险是**构建成功但行为微变**（CSS 顺序、小数精度）。要靠视觉回归发现 |
| 16 | "自研插件和迁移是两件不相干的事" | 它们是最强相关的一对：**插件是迁移时最贵的一项**（第 6 章 §6.5 判据第一条） |

## 9.9 D3 领域收束

九章、35 个节点到此收束。回顾一下这条主线：**它一直在回答同一个问题的不同层次**——**"那个文件是怎么来的"**。

| 章 | 回答的层次 | 一句话结论 |
|---|---|---|
| **第 1 章** | 定位 | 构建的边界是"源码 → 可在目标环境运行的静态产物"；`mode` 从不承诺删 console |
| **第 2 章** | 配置 | 默认值有出处；`mode` 与 `NODE_ENV` 是两个旋钮 |
| **第 3 章** | 产物 | **五个决策点顺序不可交换**；语法与 API 是两件事；摇树 = 标记 + 剪枝 + 压缩 |
| **第 4 章** | 世界模型 | **图是从入口可达的子图**；改产物用 `processAssets` 而不是 `emit` |
| **第 5 章** | 开发期 | **"快"是四个指标**；HMR 的边界决定更新代价；三层"快"不能互相替代 |
| **第 6 章** | 实现语言 | **并行度决定难度**；linking 天然串行，是收益天花板 |
| **第 7 章** | 治理（性能） | **没有基线的优化不算优化**；三类耗时来源要用对手段 |
| **第 8 章** | 治理（缓存） | 三层缓存共用"URL 与内容绑定"这一个前提；**Hash 稳定性是地基** |
| **第 9 章** | 治理（决策） | **约束 → 层次 → 工具**；填不满的评估表就是不该迁的信号 |

**三条贯穿全领域的判据**（可以单独带走）：

1. **先分类，再优化。** 慢分四类指标（第 5 章）、耗时分三类来源（第 7 章）、工具分五档（第 6 章）—— **分类错了，动作一定错。**
2. **区分"不变"与"会变"。** 语法与 API 要分开（第 3 章）、dev 与 prod 的行为要分开（第 5 章）、哈希与内容要绑定（第 8 章）—— **把会变的东西当初不变，是所有缓存事故的根源。**
3. **成本常常被推迟，而不是被消除。** 自研插件的成本在迁移时付（第 9 章）、hash 不稳的代价在发版后付（第 8 章）、跳过 `mode` 默认值的代价在线上付（第 5 章）。
