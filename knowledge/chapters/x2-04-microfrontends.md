## 4.1 什么时候不该上微前端

`X2.L3.04`。**这一节放在最前面，因为微前端的成本远高于它的收益 —— 而它常被当成"技术先进"的标志。**

### 连方案自己都在劝退

single-spa 的官方文档里有一段几乎不带修饰的话：

> **这是一个「高级架构」，与前端应用通常的做法不同。它需要改变现有的范式，并理解底层工具。**
>
> **如果你不是从零开始做应用，你就必须把你的 SPA 迁移成 single-spa 应用。**

**"高级架构"、"需要改变现有范式"、"必须迁移"** —— 这不是竞品说的，是**方案自己的文档**说的。

**⭐ 这句话的价值在于它承认了一件事**：

> **微前端的成本主要不在技术，在「迁移」与「范式改变」。**

### 它真正解决的是什么

**微前端解决的是组织问题**：

| 问题 | 微前端能解吗 |
|---|---|
| **多个团队要独立发布，互不阻塞** | ✅ **这正是它存在的理由** |
| 存量系统要渐进替换（新框架写新代码） | ✅ 能（single-spa 明确列为收益） |
| 首屏加载慢 | ❌ **不是性能方案**（见下） |
| 项目太大不好维护 | ⚠️ **模块化/分层更合适** |
| 技术栈太旧想升级 | ⚠️ 可能，但成本可能高于重写 |

**⭐ 第三行必须强调**：**微前端不是性能优化手段。**

single-spa 确实把"懒加载代码，改善首屏加载时间"列为收益，**但那是"按需加载子应用"的副产品** —— 而**同一个效果用路由级代码分割（`D3` 第 3 章 §3.5）就能拿到**，不需要引入微前端的全部复杂度。

**所以判据是**：

> **如果"独立发布"这个需求不存在，微前端就没有理由。**

**而"独立发布"是一个组织事实，不是技术事实** —— 它取决于**团队边界**，而不是代码边界。

### 三个"看起来需要但其实不需要"的场景

| 场景 | 看起来像 | 实际该用什么 |
|---|---|---|
| **一个大仓库、多个团队** | 需要微前端 | **monorepo + 独立发布流水线**（`D3` 第 9 章 §9.3 的 monorepo 判据） |
| **页面里要嵌别人的页面** | 需要微前端 | **iframe**（最彻底、最便宜，代价是集成体验） |
| **子应用要独立部署但同属一个团队** | 需要微前端 | **独立的包 + 版本管理**（`X1` 第 1 章 §1.5 的"共享包是引用"） |

**第一行是最高频的误判**：**"多个团队"与"多个构建"不是一回事**。**monorepo 里多个团队各发各的包，同样能做到"互不阻塞"** —— 而且**没有运行时组装的那一层复杂度**。

**第三行同样高频**：**同一个团队内部的"独立部署"，用包版本管理就够了** —— 因为**没有"我必须在你不知道的时候发版"这个需求**。

### 成本清单：它换走了什么

**微前端带来的是"独立发布"，换走的是这些**：

| 代价 | 具体表现 |
|---|---|
| **依赖重复** | 每个子应用一份 React/Vue；不放共享则体积翻倍，放共享则版本要协商（§4.3） |
| **运行时装配** | 主应用要在运行时加载、初始化、挂载别人（§4.4） |
| **样式与全局冲突** | 全局变量、CSS、事件监听都可能打架（§4.5） |
| **路由归属不清** | 谁拥有哪个路径？主应用与子应用都可能想改 URL |
| **调试链路变长** | 一个 bug 要跨 3 个仓库、3 套 sourcemap（`D6` 第 4 章 §4.3 的"堆栈还原失败"会成倍出现） |
| **版本协调** | "子应用 A 的新版本要求主应用升级" —— 独立发布的对偶问题 |
| **信任边界模糊** | **远端脚本就是任意代码执行**（§4.3） |

**⭐ 最后一行最容易被忽略，而它是最严重的**：**加载一个 remote 等于执行一段你无法审计的代码**，而它跑在**你的域名、你的用户的浏览器里**。

**这条在 webpack 的官方页里没有被讨论**，但**它是机制的必然结果**：`remotes` 最终注入一个 `<script>`（`remoteType: 'script'`），**script 执行即刻获得页面上的全部权限**。

**所以微前端有一个安全问题，而不是一个性能问题**：**谁能发布子应用？他们能改什么？**

## 4.2 三种方案不在同一层

`X2.L3.04`。它们常被并列成"三个竞品"，但**它们切的位置完全不同**。

### 一个关键区分

| 方案 | 切在哪一层 | 它假设什么 |
|---|---|---|
| **Module Federation** | **模块层**（构建产物的模块） | 大家**愿意共享同一个运行时** |
| **single-spa** | **应用生命周期层**（编排） | 各应用**各跑各的**，由它决定何时挂载 |
| **qiankun** | 应用层 + 隔离（**基于 single-spa**） | 各应用各跑各的，**且要互相看不见** |

**⭐ "假设"这一列才是真正的差别**：

**Module Federation 的方向是「共享」** —— 它让多个构建**共用一份依赖、互相消费模块**。
**single-spa / qiankun 的方向是「隔离」** —— 它们让多个应用**互不干扰地共存**。

**共享与隔离是相反方向。** 所以它们**不是竞品，而是回答了两个不同的问题**：

> **Module Federation 问：怎么让多个构建共用一份东西？**
>
> **single-spa 问：怎么让多个应用同时活着且不打架？**

**而 qiankun 是在第二个问题之上加了"看不见"**（沙箱 + 样式隔离 + HTML 入口）。

### 从官方定位能直接读出来

| 方案 | 官方自我定位 |
|---|---|
| **Module Federation** | "多个独立构建应当组成**一个应用**。这些独立构建**像容器一样**，可以互相暴露与消费代码" |
| **single-spa** | "一个用于在同一个前端应用中**汇聚多个 JavaScript 微前端**的框架" |
| **qiankun** | "微前端的一种实现，**基于 single-spa**，目标是让「生产可用」的微前端架构更容易" |

**注意 qiankun 那句"基于 single-spa"**：**它不是一个独立方案，而是一层封装**。所以：

> **"qiankun vs single-spa"不是"两种方案的对比"，而是"底座 vs 底座 + 隔离层"。**

## 4.3 Module Federation：版本协商是核心

`X2.L4.01`。webpack 的官方页给了一份很细的机制说明，而**它是本章最有价值的部分** —— 因为它给出了**具体的行为**，而不只是"I can do micro frontends"。

### 官方定义与一个必须纠正的术语

官方：

> **多个独立的构建应当组成一个应用。这些独立构建像容器一样，可以互相暴露与消费代码，形成一个统一的整体。**
>
> **这通常被称为微前端，但不限于此。**

**⚠️ 术语校正**：页面**没有**把 host / remote 定义成两种项目类型。原文是：

> **每个构建都既是容器，也消费其他构建作为容器。**

**所以准确的说法是"两种能力"，不是"两种角色"**：

| 配置 | 该构建获得的能力 |
|---|---|
| **`exposes`** | 产出 container entry（**对外暴露模块**）→ 此时被当作 remote |
| **`remotes`** | 引用其他 container（**消费远端模块**）→ 此时被当作 host |
| 两者都配 | **双向**（官方在排错里称 "omnidirectional host"） |

**这条校正很重要**：**"我们是 host，他们是 remote"这个说法会让人误以为有两类项目** —— 而实际是**一份构建上的两个开关**。

### 机制：构建期拆分 + 运行时组装

**官方明确它不是代码分割**：**这是"构建期拆分 + 运行时组装"**。

**而它有一条硬性约束**：

> **加载远端模块是异步操作。……没有 chunk loading 操作就不可能使用远端模块。**

**所以官方强烈推荐把入口拆开**：

```js
// ❌ 入口直接消费远端 → 会报
// "Shared module is not available for eager consumption"

// ✅ 拆成 bootstrap
import('./bootstrap')
```

**⭐ 这条约束的实质是**：**远端的模块在"你的代码开始跑"时还不存在。** 所以**入口必须留出一个"等它到"的缺口** —— 而那个缺口就是 `import()`。

**这与 `D3` 第 3 章 §3.5 的"`import()` 是唯一稳定的分割点"是同一个机制**，只是这里**分割的对象变成了"另一个构建"**。

### `shared`：每一条都既「提供」也「消费」

官方机制：`shared` 由两个插件组成：

| 插件 | 作用 |
|---|---|
| **`ProvideSharedPlugin`** | 把本构建的副本**注册进 scope** |
| **`ConsumeSharedPlugin`** | **优先从 scope 查**；**scope 里没有满足条件的版本时，回退到本地副本** |

**⭐ 所以"只写 `shared` 却同时具备提供与消费两种行为"是设计使然** —— **每一条 shared 条目都既被 provide 也被 consume。**

**scope 的数据形状也值得记**（它是"以模块名为 key、以版本号为二级 key"的普通对象）：

```js
const shareScope = {
  react: {
    "18.3.1": { get, from: "host", eager: false },
  },
};
```

### ⭐ 版本协商：允许多个 major 并存

**这是 Module Federation 最核心也最容易被误解的一条。** 官方原文：

> 当多个构建注册同一个模块时，**`requiredVersion` 决定**：消费者拿到的是 **scope 中满足它范围的「最高版本」** —— 这正是**让两个需要不同 major 的构建可以共存**的原因。

| 情形 | 行为 |
|---|---|
| scope 中有满足 `requiredVersion` 的版本 | 取**满足范围的最高版本**，不打包本地副本 |
| **多个不同 major 并存** | **允许**，各消费者按自己的范围取所需 |
| **scope 中无满足版本** | **回退到本地副本**（**不是报错**） |
| 两个构建注册**同一版本** | 运行时用 **`output.uniqueName`** 打破平局 |
| 某版本已被加载 | **已加载的版本永不替换** |
| 已用过的共享模块又被新容器提供 | **静默忽略**（不告警） |

**⭐ 这张表里有两行必须单独讲**：

**第二行**：**"允许多个 major 并存"是特性，不是妥协。** 所以**"我们统一升级 React"这个需求，在 Module Federation 里不是必须的** —— 但**代价是页面上可能同时跑着两个 React**。

**第三行**：**没有满足版本时回退本地副本，而不是报错。** 这意味着**"共享失败"是静默的** —— 你以为在共享，实际在用自己的副本。**体积变大了，但没有任何提示。**

### 三条静默行为（本节最实用）

| 静默行为 | 后果 |
|---|---|
| **`uniqueName` 冲突** | 两个构建共享同一个全局 chunk 加载数组 → **静默冲突**（官方说共享模块靠 uniqueName 判定"谁的副本胜出"） |
| **后提供的共享模块** | **静默忽略**，不告警 |
| **无满足版本** | **静默回退**到本地副本 |

**⭐ 三条都是"不报错、但行为与你以为的不同"** —— 这与 `D5` 第 2 章 §2.2 的"`cache-hit` 只表示精确匹配"、`D4` 第 2 章 §2.3 的"`env()` 替换失败时采用初始值"是同一类陷阱：**系统的默认行为让它看起来是对的。**

**而 `uniqueName` 那条有一个具体的成因**：**它默认从 `package.json` 的 `name` 推导** —— 所以**从主应用里拆出一个子应用时，极容易忘了改 name，于是两个构建同名。**

### `eager: true` 的代价

官方排错章节明确：**`eager: true` 时"所有 provided 与 fallback 模块都会总是被下载"**，因此建议**只在一个点（如 shell）提供**。

**所以"共享"不是免费的**：**它减少重复下载，但 eager 会让它变成"总是全下载"。**

### 五处官方未覆盖的空白

**webpack 该页没有讨论以下内容**（本章据此不给断言）：

1. **样式 / CSS 隔离**
2. **SSR**
3. **跨容器的类型安全**
4. **部署版本管理与回滚**
5. **安全（远端脚本的信任边界）**

**⚠️ 第 5 条值得再强调一次**：**它不在文档里，但它是机制的必然结果** —— `remotes` 会注入 `<script>`（`remoteType: 'script'`），**加载即执行**。**所以"谁能发布 remote"是一个安全问题，而文档没有回答它。**

**⚠️ 还有一条容易误传的**：**该页从未声称"可跨构建工具使用"。** 它说 "concept should be **environment-independent**" —— 那是**运行时环境**（web / Node.js），**不是构建工具**。**所有实现入口都是 webpack 5 插件。**

## 4.4 编排与隔离：single-spa 与 qiankun

`X2.L3.04`。这两个方案的关系是"底座与封装"，而**它们对隔离的承诺比想象中少**。

### single-spa：把生命周期上提到「应用级」

**官方定义**：

> 一个用于在同一个前端应用中**汇聚多个 JavaScript 微前端**的框架。

**⭐ 它最漂亮的一个概念是生命周期的类比**（官方原文）：

> single-spa 从现代框架的**组件生命周期**中获得灵感，**把生命周期抽象到「整个应用」这一级**。

| 组件级 | 应用级 |
|---|---|
| `mount` / `unmount` | **`bootstrap` / `mount` / `unmount`** |

**而它有一个硬要求**：**inactive 时必须「完全从 DOM 中移除」**（官方用词 "totally removed from the DOM"，不是隐藏）。

**这条比看起来严格**：**它意味着子应用不能靠 `display: none` 保活** —— 而这**恰恰是"不打架"的前提**：**不在 DOM 里，就不会抢事件、抢样式。**

### single-spa 的其它机制

| 概念 | 作用 |
|---|---|
| **Root Config** | 渲染 HTML 页面 + 注册应用（**注册中心**） |
| 注册时的三样东西 | **name** / **加载该应用代码的函数** / **判定 active 的函数** |
| **import map** | 把模块名映射到 URL；**`orgName` 作为命名空间，所有应用必须一致** |
| **共享依赖** | 也通过 import map 共享（如 React 指向 CDN ESM 地址） |

**⭐ import map 这条路值得注意**：**它靠浏览器原生的模块解析**，而不是打包器的运行时。**所以它对构建工具有更少的假设**（官方也说"works with ES5, ES6+, TypeScript, Webpack, SystemJS… 或任何构建系统"）。

### ⚠️ single-spa 不做隔离

**该页完全没有提及** JS 沙箱、CSS 样式隔离、Shadow DOM、全局变量污染 —— **任何隔离机制都没有。**

**它能确认的只有"约定式隔离"**：

| 手段 | 依赖什么 |
|---|---|
| 各应用自己实现 bootstrap/mount/unmount | **子应用的自觉** |
| inactive 时完全移出 DOM | **框架的执行** |
| 应用不能各自独占页面 | **约定** |

**所以 single-spa 的定位是「编排层/底座」** —— 它管"何时加载、何时挂载、何时卸载"，**不管"它们会不会打架"**。

### qiankun：在底座之上加隔离

**官方定位**：

> 微前端的一种实现，**基于 single-spa**，目标是让构建"生产可用"的微前端架构更容易、少踩坑。

**它加的三样东西**（官方 Features 列表）：

| 能力 | 官方表述 |
|---|---|
| **JS 沙箱** | "确保子应用之间的**全局变量 / 事件**不发生冲突" |
| **样式隔离** | "确保样式**互不干扰**" |
| **HTML Entry** | "让你**像使用 iframe 一样**接入子应用" |

**⭐ 而 §4.2 那句判断在这里被印证了**：**qiankun = single-spa（编排）+ 沙箱 + 样式隔离 + HTML 入口。**

**"像用 iframe 一样"这个说法也说明了它想解决的问题**：**iframe 的隔离最彻底，但集成体验最差**（路由、弹窗、通信都受限）。**qiankun 想拿 iframe 的隔离感 + 非 iframe 的集成度。**

### ⚠️ 一个必须如实说明的关键缺口

**qiankun 官方文档的该页（Introduction）里，「How Does Qiankun Works」一节的内容是 `TODO`（未撰写）。**

**后果很直接**：

| 想知道 | 能核到吗 |
|---|---|
| 它有 JS 沙箱吗 | ✅ **有一句能力声明** |
| **沙箱怎么实现的**（Proxy？快照？） | ❌ **不能** |
| 沙箱**有什么限制**（哪些情况会失效） | ❌ **不能** |
| 样式隔离有几种方案、各自边界 | ❌ **不能** |
| 该页有"已知问题/限制"章节吗 | ❌ **没有** |

**所以本章只能写"它声称有沙箱与样式隔离"，不能写"它怎么做的、在什么情况下会失效"。**

**⚠️ 这本身是一个值得记住的方法论**：**遇到"某方案宣称解决了 X"时，要问"它有没有写清 X 的实现与边界"** —— 如果没有，**"宣称"与"能用"之间有一个未知的差距**。

### single-spa 与 qiankun 的对照（只写能核到的）

| 维度 | single-spa | qiankun |
|---|---|---|
| **定位** | 编排层 / 底座 | **基于 single-spa 的封装** |

| **inactive 时** | **完全移出 DOM** | 沿用（同一底座） |

| **样式隔离** | ❌ **该页未提** | ✅ **有（仅能力声明）** |
| **入口形态** | 模块 + import map | **HTML Entry** |
| **跨框架** | ✅ 明确（React / AngularJS / Angular / Ember） | ✅ 明确（React / Vue / Angular / jQuery） |

## 4.5 隔离的代价：一条判据

`X2.L4.01`。**这一节是机制推导**（官方三页都没有系统讨论隔离代价），所以不给数字，只给判据。

### 三种隔离手段，代价递增

| 手段 | 隔离什么 | 集成难度 |
|---|---|---|
| **约定**（single-spa 的做法） | **什么都不隔离**，靠"各应用守规矩" | **最低** |
| **JS 沙箱 + 样式隔离**（qiankun 的做法） | 全局变量、事件、CSS | 中 |
| **iframe** | **全部**（含 DOM、样式、JS、路由） | **最高** |

**⭐ 一条判据**：

> **隔离越彻底，集成越难。**

**因为"隔离"的本质是"切断共享"** —— 而**集成需要共享**（共享路由、共享登录态、共享 UI 上下文、共享弹窗层级）。

| 被切断的共享 | 要额外做什么 |
|---|---|
| 路由 | 手动同步 URL（子应用的路由变化要通知主应用） |
| 登录态 | 显式传递（iframe 里拿不到父页面的内存） |
| 弹窗层级 | 无法跨应用居中（iframe 里被裁在框内） |
| 样式 | 子应用的主题变量要注入进去 |

**所以"要用 iframe 好不好"这个问题，答案是**：

> **看你要切断哪些共享。** 切得越多，隔离越强，集成越难。

**这与 `D4` 第 3 章 §3.1 的"暴露值不暴露结构"是同一个权衡的两面**：**想让别人改得少（隔离），就得自己提供足够的接口（集成）。**

### 而 Module Federation 是反方向

**它不做隔离，它做共享。** 所以它面对的是**相反的一类问题**：

| 方向 | 收益 | 风险 |
|---|---|---|
| **隔离**（single-spa / qiankun / iframe） | 互不干扰 | **集成难**；体验割裂 |
| **共享**（Module Federation） | 依赖去重、模块复用 | **版本协商**；**静默冲突**（§4.3 三条） |

**⭐ 这条对照能直接用来做选型**：

| 你的主要痛点是 | 方向 |
|---|---|
| "子应用互相污染全局/CSS" | **隔离** |
| "每个子应用都打包一份 React，体积翻倍" | **共享** |
| **"团队要独立发布"** | **两个方向都能做，先看隔离还是共享更痛** |

**第三行才是根本需求** —— 而**前两行是选型的技术依据**。

## 4.6 治理动作：六个判定阈值

| # | 现象 | 判定阈值（起点值） | 动作 | 依据 |
|---|---|---|---|---|
| 1 | 想上微前端但说不出"谁要独立发布" | **答不出具体的团队名** | 那是组织需求缺失 → 用 monorepo 或共享包代替 | §4.1 |
| 2 | 用微前端解决"首屏慢" | **首屏指标是主要目标** | 它不是性能方案；用路由级代码分割（`D3` §3.5） | §4.1 |
| 3 | 页面上出现两个 React | **`shared` 未配 singleton，或 major 不同** | Module Federation **允许多个 major 并存**，取"满足范围的最高版本" | §4.3 |
| 4 | "共享了，但体积没降" | **无满足版本时静默回退本地副本** | 检查 `requiredVersion` 与实际注册版本；**它不报错** | §4.3 |
| 5 | 两个子应用的 chunk 互相干扰 | **`output.uniqueName` 重复** | 它默认从 `package.json` 的 `name` 推导 → **拆子应用时最易同名** | §4.3 |
| 6 | 体积翻倍且找不到原因 | **`eager: true`** | 官方：**所有 provided 与 fallback 模块都会总是被下载** → 只在 shell 一处提供 | §4.3 |

### 三条使用说明

**① 阈值 1 是唯一一个"应该退回去"的阈值。**

其余五条都是"已在微前端里，怎么修"。**而第 1 条是"要不要进来"** —— 它的成本（§4.1 那张清单）远高于它可能带来的收益，**除非有明确的组织需求**。

**② 阈值 3 与 4 都是"静默"类。**

一个是**允许多份共存**（设计如此），一个是**静默回退**（不报错）。**它们都不会让构建失败。**

**③ 阈值 6 与 `D3` 第 3 章的"内联阈值"是同一类权衡。**

**"共享"减少重复下载，但 eager 让它变成"总是全下载"** —— **优化动作的方向取决于什么时候需要它。**

## 4.7 动手

| 任务 | 验收 |
|---|---|
| 回答一次"哪两个团队需要独立发布" | 若答不出团队名，说出该用什么替代 |
| 查一次微前端是否被当成性能方案 | 若是，说出用代码分割能拿到多少同样的收益 |

| 查一次 `shared` 配置 | 说出页面上会不会出现两份 React，为什么 |
| 查一次 `output.uniqueName` | 若未显式配置，说出它从哪里推导、有没有重名风险 |
| 查一次有没有 `eager: true` | 若有，说出体积代价 |
| 查一次谁能发布 remote / 子应用 | 说出"远端脚本 = 任意代码执行"在你的流程里意味着什么 |
| 查一次跨应用的路由同步方式 | 说出它靠什么机制（约定？框架？） |
| 查一次子应用 inactive 时是否真的移出 DOM | 若是 `display:none`，说出会有什么冲突风险 |

**进阶挑战**（任选一项）：

1. **做一次"微前端必要性评审"**：按 §4.1 的成本清单逐项估算你项目的代价，与"独立发布"的收益对比。目标是给出**一个可被反驳的结论**（而不是"感觉值得"）。
2. **验证一次共享是否真的生效**：从一个子应用里打印实际用的 React 版本，验证它是"共享来的"还是"本地副本"。目标是**亲手触发一次静默回退**。
3. **给 remote 建立信任边界**：列出所有能发布 remote 的人与流程，评估"如果他发了一段坏代码会怎样"。目标是**把安全问题从"没想过"变成"有答案"**。

## 4.8 本章常见误区

| # | 误区 | 纠正 |
|---|---|---|
| 1 | "多个团队就该上微前端" | **"多个团队"与"多个构建"不是一回事**。monorepo + 独立发布流水线也能做到互不阻塞 |
| 2 | "子应用要独立部署就需要微前端" | 同一团队内用**包版本管理**就够（`X1` §1.5"共享包是引用"） |
| 3 | "页面里要嵌别人的页面就上微前端" | **iframe 最彻底、最便宜**，代价只是集成体验 |
| 4 | "微前端的成本主要是技术" | 主要是**迁移**与**范式改变**（官方原话） |
| 5 | "Module Federation / single-spa / qiankun 是三个竞品" | **它们不在同一层**：模块层 / 应用编排层 / 编排 + 隔离 |
| 6 | "qiankun 和 single-spa 是两种可选方案" | qiankun **基于 single-spa** —— 是**底座 vs 底座 + 隔离层**的关系 |
| 7 | "Module Federation 和 single-spa 解决同一个问题" | **方向相反**：MF 是**共享**，single-spa/qiankun 是**隔离** |

| 9 | "Module Federation 就是代码分割" | 它是**构建期拆分 + 运行时组装**；代码分割是同一构建内部的事 |
| 10 | "远端模块可以直接在入口同步 import" | **不行**：官方"没有 chunk loading 操作就不可能使用远端模块" → 必须 `import('./bootstrap')` |

| 17 | "Module Federation 可以跨构建工具用" | **webpack 该页从未这样声称**。"environment-independent" 指**运行时环境**（web/Node），**不是构建工具** |
| 18 | "Module Federation 解决了样式隔离" | **webpack 该页完全没有讨论 CSS/样式隔离**（同类的空白还有 SSR、类型安全、版本回滚、**安全**） |
| 19 | "加载 remote 没有安全风险" | **`remotes` 最终注入 `<script>`，加载即执行**。它跑在你的域名、你的用户浏览器里 → **信任边界问题**（官方页未讨论，但这是机制必然） |
| 20 | "single-spa 提供沙箱" | **该页完全没有提及沙箱或样式隔离**。它只有"约定式隔离"（各应用自己守规矩 + inactive 时移出 DOM） |
| 21 | "inactive 时隐藏就行" | 官方要求**完全从 DOM 移除**（"totally removed from the DOM"），不是 `display:none` |
| 22 | "qiankun 的沙箱机制文档里有" | **该页「How Does Qiankun Works」是 `TODO`** → **只有能力声明，没有实现与限制** |

## 4.9 X2 领域收束

X2 四章到此收束。**它们回答的是同一个问题的四个层次**：

| 章 | 回答的问题 | 核心机制 |
|---|---|---|
| **第 1 章** | HTML 何时算出来？ | **一个变量：生成时刻**；`revalidate` 是**请求驱动**的节流 |
| **第 2 章** | 算完之后怎么接管？ | **同构是一条约束**（输入不同、输出必须相同）；`cacheHandler` 反读出"默认缓存在进程内" |
| **第 3 章** | 服务端跑在哪里？ | **配额决定架构**；**默认单区域 → Serverless ≠ 边缘** |
| **第 4 章** | 一个应用由多个构建组成？ | **共享与隔离是相反方向**；三种方案**不在同一层** |

### 一条贯穿四章的主线

**四章反复出现的是同一个判据**：

> **这个选择，把复杂度放在了哪一侧？**

| 章 | 复杂度被放到哪 |
|---|---|
| 第 1 章 | SSR 把成本放到**每次请求**；SSG 把成本放到**构建**；ISR 把它放到**缓存管理** |
| 第 2 章 | 同构把"两端一致"的责任**交给代码**；两阶段渲染把它换成**确定的性能成本** |
| 第 3 章 | Serverless 把复杂度换成**配额适应**；边缘把它换成**更紧的配额**换地理收益 |
| 第 4 章 | 微前端把"独立发布"的收益，换成**依赖/样式/路由/信任边界**的持续成本 |

**所以 X2 全领域的判据可以压成一句话**：

> **架构不消除复杂度，它只决定复杂度由谁承担、什么时候承担。**

**而"看起来更现代"的选项，通常只是把复杂度搬到了一个更晚才暴露的位置。**

### 与相邻领域的分界

| 领域 | 它负责的部分 |
|---|---|
| **X2（本领域）** | **形态**：HTML 何时生成、谁接管、服务端在哪、由几个构建组成 |
| **D3** | **产物**：形态确定后，怎么把它真正打出来 |
| **D6** | **交付与运行**：部署、缓存、可观测性 |
| **D4** | **样式**：在任一形态下的样式工程 |
| **D5** | **验证**：形态变化如何被测试发现（视觉回归 + E2E） |

**⭐ 一句话记住边界**：**X2 决定"东西长什么样"，D3 决定"怎么做出来"，D6 决定"怎么送出去并知道它好不好"。**
