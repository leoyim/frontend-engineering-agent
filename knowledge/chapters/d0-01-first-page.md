## 1.1 五行骨架：为什么是这五行

```html
<!DOCTYPE html>
<html lang="zh-CN">
  <head>
    <meta charset="UTF-8" />
    <meta name="viewport" content="width=device-width, initial-scale=1" />
    <title>我的第一个页面</title>
  </head>
  <body>
    <h1>你好，世界</h1>
    <p>这是我写的第一个页面。</p>
  </body>
</html>
```

这十行里，**只有五行是"结构"，其余都是"为什么"**。逐个拆开看机制。

### 浏览器拿到这段文本后做了什么：解析是两个阶段

HTML Standard 的《Parsing》把解析拆成**两个阶段**：

```text
阶段一 · 分词（tokenizer）：字节 →（按编码解码）→ 字符 → 标签、属性、文本、注释
阶段二 · 建树（tree construction）：按「插入模式」把 token 组装成 DOM 树
```

理解这两级划分，就能理解三条支配 HTML 的规则：

| 规则 | 机制来源 |
|---|---|
| **它是树，不是序列** | 建树阶段按嵌套关系组装父子结构 |
| **它容错，不抛错** | 规范为异常输入定义了恢复行为。产生的 **parse error 是给实现者看的，不暴露给页面** |
| **编码必须先确定** | 字符流要先解码才能分词——所以编码声明的位置有硬约束 |

**第二行是"HTML 比 JS 难调试"的根源**：JS 语法错误会抛 `SyntaxError`（D0 第 3 章 §3.7），而 HTML 写错了**只会静默变形**——标签被自动闭合、错误嵌套被"猜"着修正，页面照常渲染，只是结构和你以为的不一样。所以 HTML 的正确性**要靠规范写法与工具检查，不能靠"跑起来看看"**。

### 先建立"渲染管线"的整体图：解析只是第一步

这是本章最重要的机制锚点。浏览器要把这段文本变成屏幕上的像素，必须走完一条固定管线：

```text
① 解析 HTML → DOM 树
② 解析 CSS  → CSSOM 树
③ 样式计算 → 每个节点的计算后样式（computed style）
④ 布局 Layout → 每个盒的几何（位置与尺寸）
⑤ 绘制 Paint → 绘制指令
⑥ 光栅化 → 像素
⑦ 合成 Composite → 最终画面
```

关键点有三条：

| 结论 | 机制 |
|---|---|
| **DOM 与 CSSOM 是两条并行产物** | 解析 HTML 时若遇到 `<link rel=stylesheet>`，浏览器会同时去取 CSS；但**必须两者都就绪才能进入第 ③ 步** |
| **所以 CSS 是"渲染阻塞资源"** | 没有 CSSOM 就没有"计算后样式"，第 ③ 步无法开始 |
| **第 ① 步完成 ≠ 页面可见** | 真正决定首屏的是第 ③–⑦ 步，它们共享主线程（D0 第 5 章 §5.1 展开，D0 第 3 章 §3.6 讲过主线程与事件循环的关系） |

**这条链条解释了本章后面所有"为什么要这么写"**：语义化、`alt`、宽高、关键 CSS 的位置——都不是风格问题，而是**为了让管线走得又对又快**。

### `<!DOCTYPE html>` 不是"声明"，是"开关"

它最常见的解释是"告诉浏览器这是 HTML5"。更准确的说法来自 HTML Standard 的《The DOCTYPE》条款：**它的作用是让浏览器在三种解析模式中选择一种。**

| 模式 | 触发条件 | 盒模型行为 |
|---|---|---|
| **no-quirks**（标准模式） | 文档开头是 `<!DOCTYPE html>` | 按现行规范：`width` 指**内容区**宽度 |
| **limited-quirks**（近乎标准） | 部分旧 DOCTYPE | 少数行为偏离标准 |
| **quirks**（怪异模式） | 缺少或写错 DOCTYPE | 退回 1990 年代实现：`width` 指**内容 + 内边距 + 边框** |

同一份 CSS 在两种模式下算出的实际宽度不同。**怪异模式存在的唯一目的是不让 1990 年代的老页面突然错版**——它是兼容性包袱，不是可选风格。

> 你在网上看到的"加个 `box-sizing: border-box` 就好了"，本质上是用 CSS 手动找回怪异模式的盒模型。这个取舍D0 第 2 章正面讨论。

### `meta charset`：位置是硬约束

编码由 **Encoding Standard** 规定：浏览器在收到字节流时先做**编码嗅探**，而 `<meta charset>` 只有出现在文档**前 1024 字节内**才会被采信；否则回退到启发式猜测。

于是"中文乱码"有一个很典型的成因：文件在编辑器里看着完全正常，**问题出在传输与解码环节**——文件本身的字节没错，只是浏览器用错了编码去解它。

### `lang`：它不是标注，是给决策系统用的输入

HTML Standard 定义了 `lang` 属性（《The `lang` and `xml:lang` attributes》），它**可以挂在任意元素上**（不只在 `<html>`）。这个属性实际参与四类决策：

| 决策 | 影响 |
|---|---|
| 屏幕阅读器发音 | 用错语言 → 用错误的音素规则朗读 |
| 断行与标点挤压 | 与字体回退链一起决定排版 |
| 字形选择 | `zh-CN` 与 `zh` 会影响部分汉字的写法差异 |
| 翻译工具判定 | 判断是否需要翻译 |

### `viewport`：两个视口的分工

不加这一行，手机浏览器会进入兼容策略：**假装自己有一个默认宽度的布局视口**，把页面按它排好再整体缩小。要理解它，先分清两个概念：

| 概念 | 含义 |
|---|---|
| **布局视口**（layout viewport） | CSS 中 `width: 100%` 参照的那个宽度 |
| **视觉视口**（visual viewport） | 用户当前实际看到的区域，可缩放 |

`width=device-width` 的作用是**把布局视口设成设备的 CSS 像素宽度**，让 `100%` 等于屏幕宽；`initial-scale=1` 把初始缩放设为 1。D0 第 2 章 §2.6 会补上第三个数：**理想视口**，以及设备像素比（DPR）。

### 标签语法：三条规则就够

```html
<!-- 注释 -->

<p>有开有闭</p>
<img src="photo.jpg" alt="" />   <!-- void 元素：无内容，不需闭标签 -->
<a href="#top" class="link">属性写在开标签里</a>
```

- **void 元素**（`img` `br` `hr` `input` `meta` `link`）没有内容，写成 `<img>` 或 `<img />` 均可。
- **布尔属性**（`required` `disabled` `checked`）出现即为真，`required` 与 `required="required"` 等价。
- **嵌套必须正确闭合**。写错了不会报错，只会被建树阶段的恢复行为"猜"——而猜的结果通常不是你想要的。

缩进不影响渲染（连续空白会被折叠成一个空格），但它是给**人**看的。

## 1.2 语义化：浏览器暴露给机器的第二棵树

### 关键机制：DOM 之外还有一棵树

解析完 DOM 之后，浏览器还会构建一棵**可访问性树**（accessibility tree，简称 a11y tree），交给屏幕阅读器、语音控制、自动化测试等辅助技术。

a11y tree 的每个节点带三个要素：

| 要素 | 内容 |
|---|---|
| **role（角色）** | 这是什么——按钮、标题、导航区域 |
| **name（可访问名）** | 它叫什么——"提交""第三章" |
| **state / property** | 它当前的状态——展开、选中、禁用 |

### role 是从哪来的：一份规范化映射表

这是本节最关键的一点：**role 不是浏览器随意起的名字，而是由规范规定的映射。**

**HTML-AAM**（HTML Accessibility API Mappings）逐一对每个 HTML 元素规定了它映射到哪个 role、以及它的可访问名从哪来。所以：

| 你写的标签 | a11y tree 里的 role | 屏幕阅读器怎么念 |
|---|---|---|
| `<h1>` | `heading`（带 level） | "一级标题，你好世界" |
| `<nav>` | `navigation` | "导航区域" |
| `<button>` | `button` | "按钮，提交" |
| `<a href>` | `link` | "链接，查看详情" |
| `<ul>` / `<li>` | `list` / `listitem` | "列表，3 项" |
| `<div>` | `generic` | （不播报，等于空气） |

这就把"语义化"从一句口号变成了可验证的事实：**`class="title"` 只存在于你的脑子里；`<h1>` 存在于浏览器交给辅助技术的那棵树里。** 而验证方法在D0 第 5 章：**DevTools 的 Accessibility 面板会直接展示这棵树**。

### 为什么 `<div onclick>` 键盘用不了：可聚焦性的来源

这不是"语义"这种抽象问题，而是可聚焦性的具体机制。HTML Standard 的《Focus》定义了 **focusable area**（可聚焦区域），而 tab 序列由 **sequential focus navigation order** 定义。

可聚焦性的来源只有三类：

| 来源 | 例子 |
|---|---|
| 元素本身在规范的可聚焦列表里 | `<a href>` `<button>` `<input>` `<select>` `<textarea>` |
| 显式声明 | `tabindex="0"` / `tabindex="-1"` |
| 内建键盘行为 | `<a>` 响应 Enter；`<button>` 响应 Enter 与 Space |

于是 `<div onclick="submit()">提交</div>` 同时缺三样东西：

1. **不在 tab 序列里** → 键盘用户根本走不到它。
2. **role 是 `generic`** → 屏幕阅读器念不出"这是个按钮"。
3. **没有内建键盘响应** → 即使手动加 `tabindex="0"`，Enter 也不会有反应，还得自己监听 `keydown` 并处理 Space。

用 `<button>` 则三样全由浏览器按规范提供。**这不是风格问题，是功能缺失。**

### `<a>` 与 `<button>`：判断标准只有一条

| 点击后的结果 | 用哪个 | 浏览器提供什么 |
|---|---|---|
| 跳转到另一个地址 | `<a href="…">` | 右键"在新标签打开"、复制链接、被爬虫跟随、Enter 触发 |
| 在当前页执行一个动作 | `<button>` | Enter / Space 触发、`type` 决定是否提交表单 |

用 `<a href="#">` 冒充按钮会丢掉按钮的键盘行为；用 `<button>` 冒充链接会丢掉"新标签打开"等链接原语。**两者不可互换的原因是它们的内建行为不同。**

### 标题层级：它是导航结构，不是字号

在 a11y tree 里，`heading` 节点带层级信息，屏幕阅读器用户可以**按标题在页面内跳转**——这是视障用户浏览长文档的主要方式。由此得出三条硬规则：

- 一页只用一个 `<h1>`（页面主题）。
- 层级不跳（`h1` 直接到 `h4` 会让依赖标题导航的用户失去方位感）。
- 想要小字就用 CSS，**永远不要为了字号去改标题级别**。

### `div` 不是禁用词

`<div>` 与 `<span>` 的 role 是 `generic`——**它们的用途正是"这里需要容器，但没有任何语义可用"**。典型场景是纯为 CSS 布局或 JS 钩子套一层。

判断方法很简单：写完一段结构后回看，问一句"这个 `div` 的 `class` 名，能不能换成某个标签？"。`<div class="post-title">` 应该是 `<h2>`；`<div class="btn">` 应该是 `<button>`。

## 1.3 媒体：`alt` 与宽高为什么是硬要求

### `alt` 在 a11y tree 里的位置

图片在 a11y tree 里是一个 `image` 节点，**它的可访问名按 HTML-AAM 的映射规则来自 `alt`**。于是三种写法对应三种完全不同的结果：

| `alt` 写法 | a11y tree 结果 | 屏幕阅读器 |
|---|---|---|
| `alt="2024 年构建耗时对比：Rspack 比 Webpack 快 4 倍"` | 有名字，且携带信息 | 念出这句描述 |
| `alt=""` | 节点被标记为**装饰性** | **直接跳过**，不念 |
| **没有 `alt` 属性** | 名字缺失 | 回退念文件名（如 `IMG_2031.jpg`） |

第三行是关键：**漏写 `alt` 与写 `alt=""` 是两件完全不同的事**。前者是信息缺失，后者是明确声明"这图无信息、请跳过"。

由此得出三种判据：

| 图片类型 | 判据 | 写法 |
|---|---|---|
| **信息性** | 去掉它，用户就少了一条信息 | 描述**图里的信息**，而不是"这是张图" |
| **装饰性** | 去掉它，理解不受影响 | `alt=""`（**属性必须保留**） |
| **图注型** | 图外有独立说明 | `alt` 写简短标识，说明放 `<figcaption>` |

`alt="图片"` 是最糟的写法：既占用了播报时间，又不提供任何信息。

**还有一条容易被忽略的规则**：凡是"缺了它就读不懂"的图，必须用 `<img>`，不能用 CSS `background-image`。背景图不进 a11y tree，也不被搜索引擎索引。

### `width` / `height` 为什么必须写：CLS 的完整公式

这不是"最佳实践"，是**渲染时序的硬约束**。

浏览器解析是流式的：拿到 `<img>` 时图片字节还在网络上。要排版后续内容，就必须先知道"给这张图留多大地方"：

1. 有 `width`/`height` 属性 → **立刻算出占位尺寸**，继续排版。
2. 只有 CSS 尺寸 → 能用，但响应式场景下高度常依赖图片固有比例，仍可能要等图片元数据。
3. 什么都没有 → **先按 0 高度排版**，等图片下载完成后重排。

第 3 种造成的就是**布局偏移**。它由 **Layout Instability API** 定义并计算：

```text
单次偏移分数 = impact fraction × distance fraction
             （受影响区域占视口的比例）×（元素移动距离占视口的比例）

CLS 分数 = 一个会话窗口内所有偏移分数之和的最大值
           会话窗口：两次偏移间隔 < 1 秒，且窗口总长 ≤ 5 秒
```

**两个因子相乘**这件事值得琢磨：**移动得越远、波及面积越大，分数越高**。所以一张没写宽高的头图加载完成、把整篇正文推下去几百像素，是 CLS 分数最主要的来源之一。

正确写法是"属性负责比例，CSS 负责约束"：

```html
<img src="cat.jpg" alt="一只橘猫趴在键盘上睡觉" width="800" height="600" />
```

```css
img { max-width: 100%; height: auto; }
```

`width`/`height` 让浏览器提前知道 800:600 这个比例，`max-width` 保证不超出容器，`height: auto` 让高度按比例跟随。

### 图片解码：发生在哪条线程

光栅化阶段（本章 §1.1 的第 ⑥ 步）需要把图片字节变成像素，这一步叫**解码**。解码可以**异步**进行，从而不阻塞主线程上的布局与绘制。

```html
<img src="hero.jpg" alt="…" decoding="async" />
```

| `decoding` | 含义 |
|---|---|
| `sync` | 与渲染同步解码（可能阻塞） |
| `async` | 允许异步解码（可能先显示空白再出图） |
| `auto` | 交给浏览器决定（默认） |

**取舍在于"卡顿"与"闪白"之间**。这条属性属于调优手段，不是必需品；但知道它存在，就能解释"为什么同样的图有时会先空一下"。

### 视频与音频：三个属性决定可用性

```html
<video controls width="640" poster="cover.jpg">
  <source src="demo.webm" type="video/webm" />
  <source src="demo.mp4" type="video/mp4" />
  <track kind="captions" src="demo.zh.vtt" srclang="zh" label="中文字幕" />
  你的浏览器不支持 video，<a href="demo.mp4">点此下载</a>。
</video>
```

| 元素 / 属性 | 作用 | 不写会怎样 |
|---|---|---|
| `controls` | 显示播放控件 | 用户无法播放（除非用 JS 自建控件） |
| 多个 `<source>` | 让浏览器按支持度自选格式 | 单一格式在不支持的浏览器上完全不可用 |
| `track` | 字幕 / 描述轨 | **听障用户被直接排除** |

回退文本（标签之间的文字）只在浏览器不认识 `<video>` 时显示，对老旧设备与爬虫仍有意义。

## 1.4 表单：原生校验背后发生了什么

### 一个能用的表单

```html
<form action="/subscribe" method="post">
  <fieldset>
    <legend>订阅更新</legend>
    <p>
      <label for="email">邮箱地址</label>
      <input type="email" id="email" name="email" required autocomplete="email" />
    </p>
    <p>
      <input type="checkbox" id="agree" name="agree" required />
      <label for="agree">我已阅读并同意服务条款</label>
    </p>
    <button type="submit">订阅</button>
  </fieldset>
</form>
```

### 提交链路：一次点击之后发生了什么

HTML Standard 的《Form submission algorithm》定义了完整流程，简化后是四步：

```text
点击 submit → ① 约束校验 → ② 收集并序列化字段 → ③ 按编码方式编码 → ④ 按 method 发出请求
```

### 第 ① 步就是"原生校验"的本体

它的规范名字是 **Constraint Validation**（HTML Standard 的《Constraint validation》条款）。关键机制：**校验发生在 `submit` 事件之前**。只要有控件不满足约束，浏览器就：

1. **阻止提交**（不发请求）；
2. 对该控件触发 `invalid` 事件；
3. 聚焦到它并弹出提示。

由此可推出三件常被误解的事：

| 结论 | 机制 |
|---|---|
| 原生校验**不是"额外的 JS"** | 它是浏览器的内建流程，所以不写一行 JS 也能挡住格式错误 |
| 它**可以被绕过** | `novalidate` 属性或 JS 里 `preventDefault()` 都能跳过 |
| 所以它**不能作为安全措施** | 用户可以改前端代码、也可以绕过浏览器直接发请求——**校验必须在服务端重做一遍** |

### `method` 与编码方式

| 属性 | 可选值 | 机制差异 |
|---|---|---|
| `method` | `get` / `post` | `get` 把字段拼进 URL 查询串；`post` 放进请求体 |
| `enctype` | `application/x-www-form-urlencoded`（默认）/ `multipart/form-data` / `text/plain` | 决定第 ③ 步怎么编码 |

两条实用结论：

- **密码等敏感字段绝不能用 `get`** —— URL 会进浏览器历史、代理日志、Referer 头。
- **有文件上传必须用 `multipart/form-data`** —— 默认编码无法承载二进制。

`get` 还隐含一层语义：**GET 应当是安全且幂等的**（D0 第 6 章 §6.2 展开）。用 GET 提交"删除"这类操作，会被浏览器预取、爬虫抓取而误触发。

### `label` 与可访问名的计算顺序

```html
<label for="email">邮箱</label>
<input type="email" id="email" />
```

`for` 指向控件的 `id` 后，发生两件事：

1. **控件获得可访问名**。表单控件的 name 计算遵循 W3C 的《**Accessible Name and Description Computation**》——而**关联的 `label` 在该计算里优先级很高**（D0 第 7 章 §7.9 会给出完整的五步顺序）。没有它，屏幕阅读器只念"编辑框"，用户不知道要填什么。
2. **label 成为点击目标**。点击文字即聚焦控件——对触屏与手部不便的用户，这个小方框太难点了。

**`placeholder` 不能替代 `label`**，理由是机制层面的：它在输入开始后就消失，用户回头无法确认字段含义；它的默认对比度通常达不到 WCAG 要求；它在可访问名计算中的回退支持在各实现间不一致。**`placeholder` 只用来给格式示例。**

### `input` 的 `type` 决定了什么

`type` 不只是校验开关，它同时影响三件事：

| 影响面 | 例子 |
|---|---|
| **键盘类型**（移动端） | `type="email"` 弹出带 `@` 的键盘；`type="tel"` 弹数字键盘 |
| **原生校验** | `type="email"` 自动校验格式；`type="url"` 校验协议 |
| **语义与 UI** | `type="date"` 出现日期选择器；`type="checkbox"` 有勾选框 |

常用值：`text` `email` `password` `tel` `url` `number` `date` `time` `range` `search` `checkbox` `radio` `file` `color` `hidden`。

其他约束属性：`required`、`minlength` / `maxlength`、`min` / `max` / `step`、`pattern`（正则）。

### `fieldset` / `legend`：分组不是装饰

单选按钮组、复选组这类"一题多选"的结构，如果没有分组，屏幕阅读器用户听到的是一串孤立控件，无法知道"这一组在问什么"。`<fieldset>` + `<legend>` 正是为此存在的语义结构——`<legend>` 还会成为组内控件的**可访问名来源之一**。

## 1.5 可访问性：从"能用"到"可判定"

可访问性（a11y）常被当成道德题，其实它更是一个**可测量的工程题**：**WCAG**（Web Content Accessibility Guidelines，现行为 2.2）把要求写成了可判定的**成功准则**（Success Criterion，简称 SC），并分 A / AA / AAA 三个符合等级。业界通常以 **AA** 为目标线。

### 谁会受益：一个更宽的答案

视障（屏幕阅读器）、色盲、听障、运动障碍（无法精确使用鼠标）、认知障碍用户；**以及临时受伤的人**（手骨折、眼疾）、**用旧设备或弱网的人**、**在强光下看屏幕的人**。

这不是"少数人的需求"——**每个人一生中都会经历"暂时不便"的阶段**。

### 门槛一：对比度不是审美，是一条公式

WCAG 2.2 的准则 **Contrast (Minimum)**（AA 级）要求：**正文文字对比度 ≥ 4.5:1，大号文字 ≥ 3:1**。

这个比值是按公式算出来的，不是主观判断：

```text
对比度 = (L1 + 0.05) / (L2 + 0.05)

其中 L 为相对亮度，计算过程：
① 把 sRGB 各通道值除以 255
② 对每个通道做「线性化」（gamma 还原）
③ 按 0.2126 R + 0.7152 G + 0.0722 B 加权求和
```

理解这一点就能明白：**"我觉得挺清楚的"不是判据**——因为它无法解释"为什么 `#767676` 在白色背景上刚好达标"。浅灰文字配白底之所以是常见缺陷，正是因为它在公式上过不了线。

### 门槛二：焦点可见性的启发式

```css
/* 灾难写法 */
*:focus { outline: none; }
```

焦点框是键盘用户**唯一的位置指示**。去掉它，键盘用户按 Tab 之后完全不知道焦点在哪。

那为什么很多人都想去掉它？因为鼠标点击时它也会出现，看起来多余。于是 CSS Selectors Level 4 定义了 **`:focus-visible`**——它的定义里包含**由用户代理启发式判断"用户是否可能用键盘"**：

| 交互方式 | `:focus` | `:focus-visible` |
|---|---|---|
| 鼠标点击按钮 | 匹配 | 不匹配 |
| 键盘 Tab 到按钮 | 匹配 | 匹配 |

所以正确做法是**换掉它，而不是删掉它**：

```css
:focus-visible {
  outline: 2px solid #1a73e8;
  outline-offset: 2px;
}
```

### 门槛三：ARIA 的边界

**WAI-ARIA** 是一组用来补充语义的属性：

```html
<button aria-expanded="false" aria-controls="menu">菜单</button>
<ul id="menu" hidden>…</ul>
```

它有两条规范层面的约束：

> **一、能用原生语义表达的，不要用 ARIA 表达。**
> **二、ARIA 可以覆盖原生语义，所以覆盖必须是有意的。**

第一条的原因在**优先级**：浏览器内建行为负责键盘响应、焦点管理、播报——这些是原生元素的"出厂配置"。而 `role="button"` 只是给 a11y tree 贴了个标签，**不带来任何键盘行为**，全部要自己用 JS 补齐，漏一条就是一个可用性缺陷。

第二条的原因在**可覆盖性**：给 `<h2 role="presentation">` 会让标题在 a11y tree 中消失。所以 ARIA 是补丁，不是地基。（D0 第 7 章 §7.9 会给出 ARIA 的五条使用规则与 `inert` 这个更可靠的替代方案。）

### 一条可执行的验收流程

```text
1. 全程只用键盘（Tab / Shift+Tab / Enter / Space）走完主要流程
2. 每一步都能明确看到焦点位置
3. 把所有图片 src 改错，看 alt 是否完整表达原意
4. 用 DevTools 的 Accessibility 面板读 a11y tree，确认 role / name 都正确
5. 用 Lighthouse 或 axe 扫一遍「可判定」的部分
```

**第 5 步必须配一个说明**：自动化工具**只能覆盖约三分之一**的可访问性问题（缺名、对比度、标签关联这类可判定的）。键盘流程是否顺畅、语义是否合理、屏幕阅读器体验如何——**只能人工验证**。

## 1.6 SEO：爬虫看到的和你看到的不一样

搜索引擎看到的是 **HTML**，不是你的设计稿。而且——**它看到的时间点也可能和你不一样**。

### 关键机制一：关键渲染路径

回看 本章 §1.1 的管线，把"从请求页面到首屏可见"这一段单独拎出来，就是**关键渲染路径**（critical rendering path）：

```text
请求 HTML → 解析 HTML → （遇到 link/script 时发起子请求）
           → 构建 DOM + CSSOM → 样式计算 → 布局 → 绘制 → 合成 → 首屏可见
```

两点直接影响首屏：

| 资源 | 阻塞什么 | 为什么 |
|---|---|---|
| CSS（`<link rel=stylesheet>`） | **渲染** | 没有 CSSOM 就无法做样式计算（本章 §1.1） |
| 无属性的 `<script>` | **解析** | 脚本可能改 DOM，浏览器必须停下来等它执行完 |

所以"关键 CSS 内联、非关键 CSS 延后"不是优化技巧，而是**对阻塞规则的正确应对**。

### 关键机制二：抓取与渲染是两个阶段

```text
① 抓取（crawl）：下载 HTML 原文 → 提取链接 → 加入待抓队列
② 渲染（render）：把 HTML 交给无头浏览器执行 JS → 得到最终 DOM → 建立索引
```

两个阶段之间存在**队列延迟**。这带来一个真实后果：**纯由 JS 在客户端渲染出来的内容，索引时机不确定。**

【待验证】各搜索引擎对 JS 渲染的支持度与队列策略持续变化，**本书不给确定性结论**。稳妥的工程取舍是：**关键内容放进 HTML**（服务端渲染或静态生成），JS 负责增强交互。这个取舍直接对应 X2 领域的 SSR / SSG。

### 三项基本动作

```html
<head>
  <title>如何系统学习前端工程化 | 我的技术笔记</title>
  <meta name="description" content="一份从零基础到精通的前端工程化学习路线，覆盖构建、样式、测试、交付与架构模式。" />
</head>
```

| 项 | 作用 | 常见错误 |
|---|---|---|
| `<title>` | 标签页标题 + 搜索结果的标题行 | 全站都叫"首页" |
| `meta description` | 常被用作搜索结果摘要 | 留空；或写成与内容无关的推广语 |
| `lang` | 语言判定（同时影响 a11y 与索引，本章 §1.1） | 漏写或写错 |

### 结构本身就是信号

- **标题层级**被用来判断页面主题与内容优先级。
- **`a` 的链接文字**被用来理解被链接页面——写"点这里"等于浪费一次说明机会。
- **`alt`** 是图片搜索的信息来源。

这解释了 本章 §1.2 与 本章 §1.3 的重要性：**语义化 + `alt` + 标题层级，是可访问性与 SEO 的共同基本盘**，不是两件事。

### 结构化数据：额外给机器一份声明

```html
<script type="application/ld+json">
{
  "@context": "https://schema.org",
  "@type": "Article",
  "headline": "如何系统学习前端工程化"
}
</script>
```

它用的是 **JSON-LD**（W3C 规范）配合 schema.org 的词表，作用是让搜索结果出现更丰富的展示形式。它是**补充说明**，不是必需项。

### 一条诚实的提醒

**堆关键词无效。** 关键词密度作为排序信号早已被弃用，过度堆砌会被判定为垃圾内容。有效策略只有一个：**把内容本身写清楚**。

## 1.7 动手：做出你的第一个页面

从空白文件写 `about.html`，并**为每个选择写一句理由**（理由比结果重要）。

| 要求 | 验收方式 |
|---|---|
| 完整骨架（doctype / `lang` / `charset` / `viewport` / `title`） | 删掉任意一行，说出会发生什么；**说出 DOCTYPE 影响的是哪种解析模式** |
| `<header>` + `<nav>` + `<main>` + `<article>` + `<footer>` | `Ctrl+F` 搜 `<div`，确认剩下的都不是"本该用语义标签"的 |
| 一个 `<h1>`，至少两级标题且不跳级 | 说出为什么不能用 `h4` 来"让字变小" |
| 一张信息性图片（`alt` 描述信息）+ 一张装饰性图片（`alt=""`） | 把图片路径改错，`alt` 能否替代原意；**说出漏写 `alt` 与 `alt=""` 的区别** |
| 所有 `<img>` 带 `width` / `height` | 说出它与 CLS 公式两个因子（impact fraction / distance fraction）的关系 |
| 一个表单：姓名 / 邮箱 / 留言，含 `<label>`、两种原生校验、`<fieldset>` 分组 | 只用键盘走完并提交；**说出校验发生在 `submit` 之前还是之后** |
| 一份 `<title>` 与 `meta description` | 不看页面内容也能知道这页讲什么 |

**进阶挑战**（任选一项）：

1. 打开 DevTools 的 **Accessibility 面板**，对照 HTML-AAM 的映射，检查你写的每个元素 role 是否正确。
2. 故意把 `<!DOCTYPE html>` 删掉，写一条能观察出怪异模式差异的 CSS（用同一个 `width` + `padding` 对比实际占位宽度），记录现象。
3. 给表单加一个只有 `placeholder` 没有 `label` 的字段，用 Accessibility 面板观察该控件**名字是否为空**。

## 本章小结

**六条最该记住的结论**

1. **HTML 解析分两阶段**（分词 → 建树），且**容错不抛错**——错误被静默修复。所以规范写法与工具检查比"跑起来看看"更重要。
2. **渲染是一条七阶段管线**：解析 → DOM / CSSOM → 样式计算 → 布局 → 绘制 → 光栅化 → 合成。**DOM 与 CSSOM 都就绪才能进入样式计算**，这就是 CSS 阻塞渲染的机制原因；而真正决定首屏的是后几个阶段。
3. **浏览器给机器的是两棵树**：DOM 树给脚本，**a11y tree 给辅助技术**，其 role 由 **HTML-AAM** 规范化映射。`class` 名在第二棵树里不存在。
4. **可聚焦性来自规范定义**（HTML Standard《Focus》），不来自"能点"。这是 `<div onclick>` 不可用的根本原因，也是 `a` / `button` 不可互换的原因。
5. **`alt` 与 `width`/`height` 是硬要求，各自有机制**：前者按 HTML-AAM 成为可访问名，后者让浏览器在图片到达前算出占位——直接关系到 **CLS 公式**（impact fraction × distance fraction）。
6. **前端校验是体验，不是安全**。Constraint Validation 发生在 `submit` 之前，可被绕过，**必须在服务端重做**。这条结论在 D5 与 X2 领域反复出现。
