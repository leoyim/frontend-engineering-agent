## 6.1 先给谱系：它们换的不是同一层

"新一代构建工具"是一个含混的说法。按**替换掉哪一层 + 借谁的生态**来分，它们其实分属**五个档次**：

| 档次 | 工具 | 实现语言 | 生态策略 | 接管了什么 |
|---|---|---|---|---|
| **A. 只换转译与压缩** | **esbuild** | Go | 不接管打包 | 语法降级、minify |
| | **SWC** | Rust | 同上（Babel 替代） | 同上 |
| | **Oxc** | Rust | 同上 | 同上 |
| **B. 换打包器，兼容 Rollup API** | **Rolldown** | Rust | 官方自称 "Rollup-compatible API" | 整个打包与产物 |
| **C. 换打包器，兼容 webpack API** | **Rspack** | Rust | 官方自称 "modernizes the webpack API" | 整个打包与产物 |
| **D. 换打包器，重设计架构** | **Turbopack** | Rust | 官方明确"取代 webpack"，配置不兼容 | 整个打包与产物 |
| **E. 换打包器，借 Vite 插件生态** | **Farm** | Rust | 官方自称 "Support **Vite plugins** out of box" | 整个打包与产物 |

**这张表的意义在第 4 层**：A 档工具**不改变依赖图、不改变 chunk 划分、不改变插件模型** —— 它只是把流水线上两段最耗 CPU 的活换了个实现。B/C/D 档则**改变整个下游**，包括构建成功之后的行为细节。

**所以"要不要上 Rust 工具"不是一个问题，而是四个问题。** 本章 §6.2 讲为什么原生化有收益（以及收益上限在哪），§6.3 讲 A 档，§6.4 讲 B/C/D 三档的分野，§6.5 讲迁移的真实成本，§6.6 收成一张决策矩阵。

## 6.2 为什么原生化：并行度决定难度

### 一个流行的错误理由

最常见的说法是"Rust / Go 比 JavaScript 快"。

**这句话本身没有解释力**：JS 的 JIT 在**稳态**下非常快，很多算法的 JS 实现并不比原生慢多少。真正的原因要具体得多，esbuild 官方 FAQ 把它拆成了四条：

> 几个原因：
> - 它是用 **Go** 写的，编译为**原生代码**。
> - **并行被大量使用**。
> - esbuild 里的**一切都是从零实现的**。
> - **内存被高效使用**。

### 理由一：命令行工具是 JIT 的最差场景

这是最容易被忽略、但机制最干净的一条。官方原文：

> 大多数其他打包器是用 JavaScript 写的，但**一个命令行应用对 JIT 编译语言来说是最差的性能场景**。每次你运行打包器，**JavaScript VM 都是第一次看到你的打包器代码，没有任何优化提示**。**当 esbuild 忙着解析你的 JavaScript 时，node 正忙着解析你的打包器的 JavaScript。** 等到 node 解析完你的打包器代码，esbuild 可能已经退出，而你的打包器还没开始打包。

**"没有优化提示"是关键词**：JIT 的优势来自**热点代码反复执行**，而一个跑几秒就退出的 CLI 进程**永远处在预热阶段**。

**这条的推论很硬**：**构建这种"短命进程 + 大量一次性计算"的任务，天然不适合 JIT。** 这不是"JS 慢"，而是"JS 的快法用不上"。

**注意它与 dev server 的差别**：dev server 是**长命进程**，JIT 有预热时间 —— 所以这条理由**并不能**解释"为什么 Rust 的 dev server 也更快"。后者要靠下一条。

### 理由二：并行度 —— 这是本章的核心

官方对 Go 与 JS 的并行能力对比，是本章最关键的一段：

> 此外，**Go 从核心上就是为并行设计的，而 JavaScript 不是**。**Go 在线程间共享内存，而 JavaScript 必须在​线程间序列化数据**。两者都有并行的垃圾回收器，但 **Go 的堆在所有线程间共享，而 JavaScript 每个线程有独立的堆**。根据我的测试，这似乎把 JavaScript worker threads 可能的并行度**砍掉了一半**，大概是因为**一半的 CPU 核心在忙着为另一半回收垃圾**。

拆成三个具体差异：

| 差异 | Go | JavaScript |
|---|---|---|
| 线程间数据 | **共享内存** | **必须序列化**（`postMessage` / `SharedArrayBuffer` 属特例） |
| 堆 | **全线程共享** | **每线程独立堆** |
| 并行度上限 | 接近核心数 | 官方称"**约砍半**"（一半核心在为另一半做 GC） |

**第三条是本节最锋利的观察**：**多线程在 JS 里不只"难写"，它还有结构性开销** —— 你申请 8 个 worker，实际有效算力可能只相当于 4 个核，因为另外 4 个在各自回收垃圾。

### 理由三：不是所有阶段都能并行

这一条决定了"原生化能带来多少收益"，也是本章标题的来源。官方原文：

> esbuild 内部的算法**被精心设计为在可能时完全吃满所有可用的 CPU 核心**。大致有**三个阶段：解析、链接、代码生成**。**解析与代码生成占了大部分工作量，且完全可并行**（**链接在大多数情况下是天然串行的任务**）。由于所有线程共享内存，当打包多个入口、而它们导入了同一批 JavaScript 库时，**工作可以很容易地被共享**。

**三个阶段的可并行性差异，就是"难度"所在**：

| 阶段 | 做什么 | 可并行性 |
|---|---|---|
| **解析（parsing）** | 读文件、词法、语法、作用域 | **完全可并行**（文件之间独立） |
| **代码生成（codegen）** | 输出代码、sourcemap | **完全可并行**（输出单元之间独立） |
| **链接（linking）** | 合并模块、解析跨模块引用、划分 chunk | **天然串行**（要先知道全局） |

**这就是本章的核心命题**：

> **原生化的收益上限，由"这个阶段有多少可并行的工作"决定。不是由"语言有多快"决定。**

**由此可以推出一个非常实用的判断**：

- 一个**只做转译与压缩**的工具（A 档），它处理的恰好是**"完全可并行"的两段** → **收益直接、且可预测**；
- 一个**接管打包**的工具（B/C/D 档），它必须处理 **linking** → **串行部分是天花板**，收益要靠"减少串行工作量"（更好的增量、更细的缓存粒度）来拿，而不是靠"更快地跑串行代码"。

**这解释了 §6.3 与 §6.4 的差别**：A 档是"拿走容易拿的那部分"，B/C/D 档是在**难的那部分**上做文章 —— 所以后者的技术路线才会出现"增量计算""惰性打包"这些**结构性**手段（§6.4）。

### 理由四：减少遍历与中间表示转换

官方第三条理由是"全部从零实现"，理由是：

> 自己实现一切、而不是用第三方库，有很多性能好处。你可以**从一开始就把性能放在心上**，可以**确保所有东西使用一致的数据结构以避免昂贵的转换**，也可以在必要时做**大范围的架构改动**。代价当然是工作量大。

**"避免昂贵的转换"这一句，直接连到 §6.3 那条被广泛误传的说法。**

### 一条诚实的边界

**本章不给跨工具的"倍率"结论。** 官方页面上确实有基准数字（§6.3 会引用并附上测试条件），但它们是**特定机器、特定项目、无缓存**下的结果 —— 换到你的项目上，这些数字的**排序可能不变，倍数一定不同**。

## 6.3 esbuild 与 SWC：只换转译与压缩层

### 一条必须纠正的说法：esbuild 并非"不用 AST"

流传最广的一条技术说法是"esbuild 之所以快，是因为它不用 AST，直接流式处理字符串"。

**本次核验的官方 FAQ 里没有这个说法，而且原文恰好相反**：

> 例如，**esbuild 只完整触碰 JavaScript AST 三次**：
>
> 1. 一趟做词法、解析、作用域建立与符号声明
> 2. 一趟做符号绑定、语法压缩、JSX/TS 转 JS、ESNext 转 ES2015
> 3. 一趟做标识符压缩、空白压缩、代码生成与 source map 生成

**所以准确的说法是：esbuild 使用 AST，但自己做 parser，并把处理压到三次遍历。**

### 那"快"到底来自哪

官方对"为什么只遍历三次能更快"的解释，是本节最有价值的一段：

> 这**最大化了 AST 数据的复用，趁它还热在 CPU 缓存里**。其他打包器**把这些步骤放在分开的遍历里，而不是交错进行**。它们还可能在**多种数据表示之间转换，以便把多个库粘在一起**（例如 **string→TS→JS→string，然后 string→JS→更旧的 JS→string，然后 string→JS→压缩后的 JS→string**），这会**用更多内存并拖慢速度**。

**这段话给出了一个可迁移的判据**：

| 做法 | 代价 |
|---|---|
| **交错处理**（一趟里做完多件事） | 数据在 CPU 缓存里还是热的 |
| **分开遍历**（每步一趟） | 每趟都要重新读一遍数据，缓存已冷 |
| **多次表示转换**（string→AST→string→AST→…） | **最贵**：每次转换都要分配新内存 |

**注意官方举的那条链**：`string→TS→JS→string→JS→更旧的 JS→string→JS→压缩后的 JS→string`。**这是"用多个独立工具串起来"的必然结果** —— 每个工具只接受文本、只输出文本。**这就是"自己实现一切"的性能意义：可以在内存里一次走完，不必来回序列化。**

### 官方基准（附测试条件）

官方 FAQ 的 "Benchmark details" 给了两组数字。**引用时必须带上条件**：

**JavaScript 基准**（three.js 复制 10 份、从零构建单一 bundle、无缓存）：

| 工具 | 时间 | 相对 | 速度 |
|---|---|---|---|
| **esbuild** | **0.39s** | 1x | 1403.7 kloc/s |
| parcel 2 | 14.91s | 38x | 36.7 kloc/s |
| rollup 4 + terser | 34.10s | 87x | 16.1 kloc/s |
| webpack 5 | 41.21s | **106x** | 13.3 kloc/s |

**TypeScript 基准**（旧 Rome 代码库）：

| 工具 | 时间 | 相对 |
|---|---|---|
| **esbuild** | **0.10s** | 1x |
| parcel 2 | 6.91s | 69x |
| webpack 5 | 16.69s | **167x** |

**测试条件（官方给出）**：每个时间取三次运行中最好的一次；**6 核 2019 MacBook Pro、16GB RAM**；关闭 macOS Spotlight。

**必须点明的三点**：

1. **这是"无缓存"的冷构建** —— 所以它量的是**指标 1 与指标 3 的混合**（第 5 章 §5.1），不是 HMR；
2. **这是 esbuild 自己选的项目与机器**；
3. **`rollup 4 + terser` 那一行很关键**：Rollup 本身很快，慢在 **terser**（串行、JS 实现）。**这正是"只换压缩层"能拿到收益的直接证据**。

### 一条关于 TypeScript parser 的官方发现

官方在解释"为什么不借用现成的 parser"时，写了这么一段：

> 例如，**很多打包器用官方 TypeScript 编译器作为 parser**。但它**是为服务 TypeScript 编译器团队的目标而构建的，他们没有把性能作为首要优先级**。他们的代码**大量使用多态对象形状与不必要的动态属性访问**（两者都是众所周知 JavaScript 的减速带）。而且**TypeScript 的 parser 似乎在关闭类型检查时仍然运行类型检查器**。

**最后半句值得单独记**：**"关掉类型检查"可能只是关掉了报告，没关掉计算。** 这条对任何"我明明关了 `typeCheck` 为什么还慢"的排查都有用。

### Oxc：不是"一个工具"，是"一套底座"

官方定位（原文）：

> **一套用 Rust 编写的高性能 JavaScript 工具集合。**

页面主标题是 **"THE JAVASCRIPT OXIDATION COMPILER"**，另一句定位是 **"现代 JavaScript 工具链的基石"**。

**"集合"这个定位是它与 esbuild / SWC 的根本差别。** 它把能力拆成六个可独立消费的组件：

| 组件 | 做什么 | 官方宣称 | 成熟度 |
|---|---|---|---|
| **Oxlint** | Linter | ESLint 兼容；比 ESLint 快 **50~100 倍**；**800+ 条规则**；由 **tsgo** 驱动的类型感知检查 | 未标注 |
| **Oxfmt** | Formatter | Prettier 兼容；比 Prettier 快 **30 倍**；比 Biome 快 **3 倍** | **Beta** |
| **oxc-parser** | 解析 | 比 SWC 快 **3 倍**；通过全部 Test262 stage-4 | 未标注 |
| **oxc-transform** | 转换 | TS & JSX；语法降级到 ES2015；Isolated Declarations（DTS 生成） | 未标注 |
| **oxc-resolver** | 模块解析 | 与 Node.js 兼容的 CJS / ESM；行为对齐 `enhanced-resolve`；比它快 **28 倍** | 未标注 |
| **oxc-minify** | 压缩 | 死代码消除、语法缩短、空白移除、变量名混淆 | **Alpha** |

**官方的 parser 基准**（解析 `typescript.js`，MacBook Pro M3 Max）：**Oxc 26.3 ms / SWC 84.1 ms / Biome 130.1 ms**。

**这张表最有价值的不是那些倍数，而是"拆分方式"**：

| | esbuild / SWC | **Oxc** |
|---|---|---|
| 形态 | 一个 CLI / 一个平台 | **一套可独立引用的组件** |
| 谁在用 | 终端用户、打包器内部 | **lint / format / 打包器都能从同一份实现里取用** |

**这正好把 §6.2 的理由四推到极致**：esbuild 的快来自"在一个进程内把多步交错进三次遍历"；而 Oxc 的快多了一层 —— **如果多个工具共享同一套 parse / transform / minify 实现，工具之间那条 `string→AST→string→AST→…` 的转换链就根本不存在**。

**⚠️ 一条必须说明的边界**：**Oxc 首页通篇没有出现 "Rolldown" 或 "Vite" 字样**，也没有任何"被 XX 用作底层"的表述。所以"Rolldown 的解析/转换/压缩由 Oxc 提供"这一点，**在 Rolldown 与 Oxc 两个官方首页上都无法证实**（见 §6.4）。本章不把它当作结论。

**另一条边界**：**Oxc 首页没有给出任何语义化版本号**，只在两个组件上标了 **Beta（Oxfmt）** 与 **Alpha（oxc-minify）**。**这两个标记本身是有信息量的** —— 它说明这套底座的格式化与压缩部分还在早期。

**一个跨领域的观察**：Oxc 的 **Oxlint** 属于 **D1（规范与质量）** 领域的工具，而不是 D3 的。**同一个 Rust 底座同时服务 lint 与构建两件事** —— 这是"原生化"在工具链层面的一个自然结果，也提示我们：**D1 与 D3 在底层实现上正在合流**（Oxlint 兼容 ESLint，而 ESLint 是 D1 第 1 章的主题）。

### 这一档的收益上限在哪

回到 §6.2 的核心命题：esbuild / SWC / Oxc 处理的是**解析与代码生成** —— 恰好是"完全可并行"的两段。

**所以它们的收益有三个特征**：

| 特征 | 含义 |
|---|---|
| **直接** | 不需要改依赖图、不需要改插件，配置层面替换即可 |
| **可预测** | 收益 ≈ 这两段在总耗时中的占比 |
| **有上限** | **拿不到 linking 那一段的收益**；产物结构、chunk 划分、插件模型**完全不变** |

**推论**：**如果你的瓶颈在 linking（大项目的图合并、chunk 优化），换转译器不会有帮助** —— 因为那部分根本不在它管的范围里。

### 三个工具的共同边界

**A 档三者（esbuild / SWC / Oxc）都不做类型检查。** 这条在第 3 章 §3.2 已按"检查与产出分离"讲过，这里只需强调：**换哪个都一样，`tsc --noEmit` 永远是独立的一步。**

### SWC：Babel 的 Rust 替代

官方定位（原文）：

> **SWC 是一个可扩展的、基于 Rust 的、面向下一代快速开发工具的平台。**

页面标题另含 **"Speedy Web Compiler"**，作者署名为 **kdy1**。

**能力清单**（官方首页）：编译 / 转译 JS 与 TS、**压缩（Minification）**、**打包（bundling）**、WebAssembly 转换、`swc-loader`（用于 **webpack 与 Rspack**）、`@swc/jest`、自定义插件；入口包为 `@swc/cli` 与 `@swc/core`。

**使用方**（官方列出）：工具侧 **Next.js、Parcel、Deno**；公司侧 **Vercel、字节跳动、腾讯、Shopify、Trip.com**。

**官方基准主张**：

> **SWC 在单线程上比 Babel 快 20 倍，在四核上快 70 倍。**

**⚠️ 但页面没有给出测试方法、硬件配置或基准细节。** 引用这个数字时必须带上这句限定 —— 否则它就是一个不可复现的断言（对照 §6.3 开头 esbuild 那组给出了完整条件的基准）。

**两条必须纠正的印象**：

| 常见说法 | 官方实际 |
|---|---|
| "SWC 是 Babel 的 drop-in 替代" | 首页**把 Babel 作为性能对比对象**，但**没有出现 "drop-in replacement" 的表述**。这是社区说法，不是官方承诺 |
| "SWC 只做转译" | 官方明确它能**压缩**也能**打包**（bundling） |

**第二条更有意思**：SWC **具备打包能力**，但它没有成为主流打包器的替代品 —— 而是**成为了别的工具内部的转译层**（Next.js / Parcel / `swc-loader`）。

**这正是 §6.2 判据的一次自然验证**：SWC 的落点是**可完全并行的解析与代码生成**，而**打包器最难的 linking 段它没有去碰**。工具的市场位置，往往就是它选的战场。

## 6.4 借生态还是换架构：三条路线

B/C/D 三档都要接管整个打包过程。它们的分野**不在语言**（都是 Rust），而在**对旧生态的态度**。

### 路线一：Rolldown —— 兼容 Rollup API

官方首页的定位原文：

> **极速的、基于 Rust 的 JavaScript 打包器**，**具备 Rollup 兼容的 API 与 esbuild 的功能对标**。

以及一句关于归属的表述：

> **驱动 Vite 8+ 的统一打包器。**

和一句规模主张：「Rolldown 处理数万个模块不费吹灰之力。」

**生态策略**：首页把 "**ROLLUP COMPATIBLE**" 单列成一个特性块，副文案是"**熟悉的 API 与配置项，以及丰富的插件生态**"。

**官方基准**（19k 模块 = 10k 个 React JSX 组件 + 9k 个 iconify JS 文件，**开启压缩与 source map**）：

| 工具 | 耗时 |
|---|---|
| **Rolldown** | **1.61s** |
| esbuild | 1.70s |
| rspack | 4.07s |
| Rollup + esbuild | **40.10s** |

**这组数字最有信息量的是最后一行**：`Rollup + esbuild` 要 40 秒 —— 而 Rolldown 只要 1.61 秒。**同一个"用 Rust/Go 加速过"的生态，换成一体化实现后差了 25 倍。** 这印证了 §6.2 的理由四：**真正的开销在"多个工具之间来回序列化"，而不在单个工具的速度。**

**⚠️ 三条必须如实标注的边界**：

1. **"Rolldown 用 Oxc 做 parse / transform / minify" 在两个官方首页都没有得到证实。** 本次**双向核验**过：Rolldown 首页把 `transforms` / `define` / `inject` / `minify` 描述为**内建能力**，但**没有交代底层由谁实现**；而 **Oxc 首页通篇没有出现 "Rolldown" 或 "Vite" 字样**，只列了自家六个组件。所以这不是"官方说了我没查到"，而是**两边首页都没说**。本章据此**不把它当作结论**（详见 §6.3 的 Oxc 一节）。
2. **首页没有给出 Rolldown 自身的版本号**，也没有 beta/RC 字样。最强的成熟度信号是它"驱动 Vite 8+"。
3. **首页未提及增量构建、并行、chunk 分割**等能力 —— **这不代表它不支持**，只代表这些不在首页。

### 路线二：Rspack —— 兼容 webpack API

官方定义：

> Rspack 是一个**面向 Web 的、快速的、基于 Rust 的打包器**。它**现代化了 webpack 的 API**，以**实现对 webpack 的无缝替换**，同时带来**极快的构建速度**。

**"无缝替换"是目标表述，官方紧接着给的是量化区间** —— 这一点很重要，值得完整引用：

| 维度 | 官方原文 |
|---|---|
| API / 配置 | 覆盖 **"webpack 的大部分 API 与特性"** |
| **Loader** | **"目前与社区里几乎所有的 loader 兼容"** |
| **Plugin** | **"对于下载量最高的 50 个 webpack 插件，超过 85% 可以在 Rspack 中使用，或者有替代方案"** |

**⚠️ "或者有替代方案"这半句是整段的关键。** 它意味着：**那 85% 里有相当一部分不是 drop-in，而是要换一个实现。** 所以准确理解是：

> **loader 层基本可平移；plugin 层是"大部分可用 + 一部分要换"；配置层官方只说"大部分"。**

**官方给的四条优势**（"Compared with webpack" 段）：

1. **Rust 语言的效率** —— 并顺带提到 Rust 有"编译器级的安全防护"（对比 C++ 等原生语言）；
2. **高度并行化的架构** —— 官方指出 webpack 受限于 JS 薄弱的​多线程支持；
3. **关键打包能力的内建实现** —— 这条的论证很值得看：webpack 的 hook 体系催生了大量第三方 loader/plugin，但**这些包常成为性能瓶颈**，原因是「**作者不熟悉内部机制**」以及「**hook 机制本身限制了算法交互**」。所以 Rspack 把关键特性做成**内建插件**；
4. **优化的 HMR** —— 采用**专门的增量编译策略**，理由是「HMR 对构建速度的要求比普通打包更苛刻」。

**第 3 条是本章一个重要的判断依据**：**第三方插件不只是"生态财富"，它也是"性能上限"的来源。** 因为插件作者只看得到 hook 边界，看不到全局优化机会 —— 而内建实现可以跨 hook 优化。

**动机数据（官方给的，很具体）**：字节跳动的大型单体应用，生产构建**曾达 10 分钟甚至半小时**，冷启动**可超数分钟**；官方给出的目标指标是 **`npm run dev` 启动控制在 10–15 秒内**。

**注意：官方在这里没有给"Rspack 比 webpack 快 N 倍"的倍数** —— 只给了"webpack 侧有多慢"与"目标有多快"。

**成熟度（官方可核验的）**：**2024 年 8 月发布 Rspack 1.0，官方视其为生产可用（production-ready）**。文档侧栏另已出现 "Upgrading from v1 to v2"，但**正文未给出 v2 的状态说明**。

**一个有用的生态分层**：官方明确说，如果你想要 **Vite 那样开箱即用**的体验，应该用 **Rsbuild**（"一个由 Rspack 驱动的构建工具"）。分工是：**Rspack 偏底层、面向框架与上层工具；Rsbuild 偏开箱即用。**

### 路线三：Turbopack —— 重设计架构

官方定义：

> Turbopack 是一个**为 JavaScript 与 TypeScript 优化的增量式打包器，用 Rust 编写，内建于 Next.js**。

**官方给的四个设计要点**，第一个就与本章主线直接相关：

| 设计要点 | 官方内容 |
|---|---|
| **Unified Graph（统一图）** | Next.js 有多个输出环境（client / server）。多编译器 + 拼接 bundle 很繁琐；Turbopack **对所有环境使用单一统一图** |
| **Bundling vs Native ESM** | **明确拒绝"dev 期不打包、靠浏览器原生 ESM"的方案** —— 小应用可行，**大应用会因过多网络请求变慢**；Turbopack **在 dev 阶段仍然打包，但以优化方式进行** |
| **Incremental Computation（增量计算）** | **跨核心并行**；**缓存粒度细到函数级（down to the function level）**；**已完成的工作不会重做**；**结果持久化到磁盘，跨多次运行保留** |
| **Lazy Bundling（惰性打包）** | **只打包 dev server 实际请求到的内容**，从而降低首次编译时间与内存占用 |

**第二条是本章最重要的跨章呼应。** 第 5 章 §5.2 我们记下了 Vite 官方那句"**Rolldown 改变了这一点**"（探索 dev 期打包）；这里 Turbopack 是**从另一个方向、早得多地**得出了同一个结论：**未打包 dev 在大项目上会被请求数压垮。**

**两个独立项目收敛到同一结论**，这本身就是一个可以下判断的信号：**"dev 不打包"是一个特定规模下的最优解，不是普适原则。**（第 5 章 §5.9 误区 4）

**第三条的"函数级缓存粒度"值得单独想一遍**：它比"文件级缓存"细一档，所以**一个文件里改一行，只有依赖那一行的计算失效**。这是"减少串行工作量"的具体做法 —— 正好对应 §6.2 说的"linking 是天花板，只能靠减少工作量来突破"。

**成熟度（官方版本表）**：

| 版本 | 变化 |
|---|---|
| **v15.0.0** | **dev 支持稳定（stable）** |
| v15.3.0 | build 支持 **experimental** |
| v15.5.0 | build 支持 **beta** |
| **v16.0.0** | **build 支持稳定**；**Turbopack 成为 Next.js 默认打包器** |

**所以"Turbopack 还只是实验品"这个印象已经过期了**：dev 自 15.0 稳定，build 自 16.0 稳定并成为默认。

**⚠️ 但官方页面上没有给出任何基准数字** —— 没有耗时、没有倍率。只有 "a much faster local development experience" 这类定性表述。**本章据此不给 Turbopack 的速度结论。**

### 路线四：Farm —— 借 Vite 的插件生态

官方定位（原文）：

> **用 Rust 编写的极速 Web 构建工具。**
>
> **Farm 是一个基于 Rust 的 Web 构建引擎**，用于辅助你的 Web 程序与 JavaScript 库。

**它最值得记的一条是生态策略**，官方在首页明写：

> **开箱即用地支持 Vite 插件。**

**这是"借生态"的第四种借法** —— 不是借 Rollup 的插件 API（Rolldown），也不是借 webpack 的（Rspack），而是**借 Vite 插件**。

**为什么这一招聪明**：按第 4 章 §4.6 的结论，**Vite 插件接口本身扩展自 Rolldown / Rollup 的钩子模型**。所以**兼容 Vite 插件，约等于一次性吃到了"Vite + Rollup 那一系"的生态** —— 用一次兼容性投入换两代插件存量。

**⚠️ 边界**：官方首页只说了**插件层面**兼容，**配置层面（`vite.config` 能否直接平移）未提及**。所以"Farm 能直接跑我的 Vite 项目"这句话目前**没有官方依据**。

**官方强调的两个核心机制**：

| 机制 | 官方原文 |
|---|---|
| **Partial Bundling（部分打包）** | "把你的项目打成**少量合理的 bundle**，**加快资源加载**的同时**不牺牲缓存粒度**" |
| **增量构建 + 持久化缓存** | "支持持久化缓存，**模块级缓存默认开启**，任何模块在被修改前不会被二次编译" |

**"Partial Bundling" 这个概念值得单独想一遍**，因为它是对第 5 章那个两难的一次正面折中：

| 方案 | 请求数 | 缓存粒度 |
|---|---|---|
| **完全不打包**（dev server 按需） | **多**（每模块一请求） | 最细 |
| **完全打包**（传统 build） | 少 | **粗**（改一个模块，整个 bundle 失效） |
| **部分打包（Farm）** | **"少量合理"** | **"不牺牲"** |

**这与 Turbopack 的"dev 也打包"、Vite 的 full bundle mode 探索，是同一个方向上的三种解法**：都在回答"**请求数与缓存粒度之间，最优点在哪**"。而三者的答案一致：**不在两个端点，在中间。**

**成熟度**：官方站点的版本选择器已列出 **1.0.0**（并注明 1.0 之后**继续发布 nightly 版本**）。基准方面只给了量级表述（"毫秒级启动"、"多数场景 HMR 更新在 **10ms** 内"），**具体数值需查页外的 benchmark 详情**。

**⚠️ 一处缺口**：**Farm 首页完全没有提到 webpack** —— 没有对比、没有迁移说明。所以"Farm 是 webpack 替代品"这个说法在本页**无据**。

### 四条路线的代价对照

| 工具 | 兼容对象 | 配置迁移量 | 插件生态 | 成熟度信号 | 主要卖点 |
|---|---|---|---|---|---|
| **Rolldown** | **Rollup** | 低（若本来用 Rollup / Vite） | Rollup 插件生态 | "驱动 Vite 8+"（首页无版本号） | 一体化（消除工具间序列化） |
| **Rspack** | **webpack** | 低（若本来用 webpack） | webpack 插件（**>85% 可用或有替代**） | **v1.0（2024-08）生产可用** | 借 webpack 生态 + 内建关键能力 |
| **Turbopack** | **无**（重设计） | **高**（配置键都换了） | **支持 webpack loaders，不支持 plugins** | **dev 15.0 稳定 / build 16.0 稳定并默认** | **增量计算（函数级）+ 统一图** |
| **Farm** | **Vite 插件** | **未核验** | **官方自称"开箱即用支持 Vite 插件"** | **1.0.0**（另持续发 nightly） | **Partial Bundling + 模块级缓存默认开启** |

**看这张表的一个方法**：**先看"兼容对象"那一列，它决定了你的迁移成本下限。** 如果你本来用 webpack，Rspack 是唯一"配置基本能留"的选项；如果你本来用 Vite / Rollup，Rolldown 与 Farm 都在射程内；只有 Turbopack 要求你接受一次完整的配置重写。

## 6.5 迁移的真实成本：不在速度，在生态

### 一张"搬不过去"的清单

`D3.L3.12` 想回答"该不该换"。而回答这个问题，先得知道**换过去会丢什么**。Turbopack 的官方文档难得地把这件事列得很细：

| 项 | 官方状态 |
|---|---|
| **webpack loaders** | **支持** |
| **webpack plugins** | **不支持**（依赖插件系统的第三方工具需找替代方案，或继续用 webpack） |
| `next.config.js` 的 `webpack()` 配置 | **不会被识别**（改用 `turbopack` 键：`rules` / `resolveAlias` / `resolveExtensions` / `ignoreIssue`） |
| **Yarn PnP** | **明确 "Not planned"** |
| `sassOptions.functions` | **不支持** —— 官方理由：**Rust 架构无法执行 JS 函数** |
| 旧式 CSS Modules 特性 | **不支持且无计划**：独立 `:local` / `:global` 伪类、`@value`、`:import` / `:export` ICSS、在 `.module.css` 里 `composes` / `@import` 普通 `.css` |
| `experimental.urlImports` / `experimental.esmExternals` | 不支持 |
| 项目根目录外的文件 | 不再解析（`npm link` / `pnpm link` 场景需额外配置） |

**这张清单里最有代表性的一行是 `sassOptions.functions`**：**"Rust 架构无法执行 JS 函数"** —— 这不是"还没做"，而是**架构性不可为**。原生化的代价之一，就是**丢失"在构建期执行任意 JS"这个能力**。

**另一行是 Yarn PnP 的 "Not planned"**：**生态兼容不是"时间问题"，有时是"不打算做"。**

### 一个反直觉结论：最大的风险不是构建失败

对比下面两类迁移事故：

| 类型 | 表现 | 排查难度 |
|---|---|---|
| **构建失败** | 立刻报错，装不起来 | **低** —— 你马上就知道了 |
| **行为微变** | 构建成功、产物正常、**渲染有细微差异** | **高** —— 可能上线后才被发现 |

**Turbopack 官方列出了三个"构建成功但行为变了"的具体例子**：

| 差异 | 官方内容 |
|---|---|
| **CSS Module 排序** | 严格按 **JS import 顺序**输出（webpack 有时会忽略 JS 推断的顺序） |
| **Sass `~` 前缀** | **不支持**旧式 `@import '~bootstrap/...'`，可去掉 `~`，或用 `resolveAlias: { '~*': '*' }` 兼容 |
| **CSS 小数精度** | **Lightning CSS 保留 5 位，webpack 为 10 位**（如 `25/17` → `1.47059` vs `1.4705882353`） |

**"CSS 小数精度"这一条值得停一下**：`1.47059` 与 `1.4705882353` 的差别，会让 `line-height`、`letter-spacing` 这类属性的**实际渲染位置**差零点几个像素。

**这就是迁移的真实成本所在**：它不体现在"能不能构建"，而体现在"**视觉回归测试能不能覆盖到**"。**如果你的项目没有视觉回归，任何一次打包器替换都是一次盲赌。**

### 三条可以带走的判据

| 判据 | 内容 |
|---|---|
| **看插件，不看 loader** | loader 是"单文件转换"，语义局部、易平移；**plugin 是"全流程干预"，与 hook 模型强绑定**，最难搬 |
| **看"构建期执行 JS"的依赖** | 一旦有（如 Sass 自定义函数、自定义 loader 里跑 Node API），**原生化架构就搬不过去** |
| **看有没有视觉回归** | 没有视觉回归的项目，**不该**在没有人工基线的情况下换打包器 |

## 6.6 成熟度矩阵与投入建议

### 矩阵

**成熟度一列只写官方可核验的信号**，不写主观判断：

| 工具 | 语言 | 换哪一层 | 生态策略 | **成熟度（官方信号）** | **官方是否给基准** |
|---|---|---|---|---|---|
| **esbuild** | Go | 转译 + 压缩 | 不接管打包 | 首页未给版本信息（本次未取） | **是**（两组，附完整测试条件） |
| **SWC** | Rust | 转译 + 压缩（**官方也称可打包**） | **做别的工具内部的转译层**（Next.js / Parcel / Deno / `swc-loader`） | **首页无版本号、无稳定标记** | **是**（20x 单线程 / 70x 四核，**但无测试条件**） |
| **Oxc** | Rust | 转译 + 压缩 + **lint/format/解析** | **工具集底座**（六个可独立消费的组件） | **Oxfmt = Beta、oxc-minify = Alpha**；其余未标注；**无版本号** | **是**（parser 单项，附硬件） |
| **Rolldown** | Rust | 整个打包器 | **兼容 Rollup API** | **"驱动 Vite 8+"**（首页无版本号） | **是**（19k 模块） |
| **Rspack** | Rust | 整个打包器 | **兼容 webpack API** | **v1.0（2024-08）生产可用** | **否**（只给 webpack 侧痛点） |
| **Turbopack** | Rust | 整个打包器 | **重设计，内置 Next.js** | **dev 15.0 稳定 / build 16.0 稳定并默认** | **否**（仅定性） |
| **Farm** | Rust | 整个打包器 | **兼容 Vite 插件**（"out of box"） | **1.0.0**（另持续发 nightly） | **否**（仅"毫秒级"/"10ms 内"量级表述） |

### 投入建议：按"你要换哪一层"分三档

**第一档：换转译与压缩（esbuild / SWC / Oxc）**

| 项 | 判断 |
|---|---|
| 收益 | **直接、可预测**（收益 ≈ 这两段在总耗时中的占比） |
| 风险 | **低** —— 不改依赖图、不改 chunk、不改插件模型 |
| 前提 | 必须**另配类型检查**（三者都不做） |
| 建议 | **如果只能做一件事，先做这件** |

**第二档：换打包器但兼容旧 API（Rolldown / Rspack）**

| 项 | 判断 |
|---|---|
| 收益 | **中等偏高**（能拿到 linking 段的改进，但要靠增量与缓存，不靠语言） |
| 风险 | **中** —— 插件层要盘一遍（Rspack：>85% "可用或有替代"） |
| 前提 | 你本来就用的 Rollup（→ Rolldown）或 webpack（→ Rspack） |
| 建议 | **先把插件清单列出来**，逐个标"可用 / 有替代 / 无解"，再决定 |

**第三档：换架构（Turbopack 一类）**

| 项 | 判断 |
|---|---|
| 收益 | **可能最高**（函数级增量、统一图、惰性打包都是结构性改进） |
| 风险 | **高** —— 配置键、插件模型、甚至 CSS 精度都会变 |
| 前提 | **有视觉回归**；且能接受"某些能力架构性不可为" |
| 建议 | **只在你能覆盖行为差异时才做** |

### 一条反常识的建议

**先换"不影响产物语义"的那一层，再考虑换打包器。**

原因很直接：

| 层次 | 产物语义是否变化 |
|---|---|
| 转译 + 压缩 | **不变**（同样的输入，同样的输出，只是更快） |
| 打包器 | **可能变**（chunk 划分、CSS 顺序、精度、插件行为） |

**所以第一档是"纯收益"，第二三档是"收益 + 一次行为审计"。** 把这两件事**拆成两次变更**，任何一次出问题都能立刻定位到是哪一层。

**这是本章最实用的一条工程建议**，也是最容易被"一次性升级到全家桶"的冲动盖过去的一条。

### 一条关于"该不该等"的判断

**"等它稳定"这个策略，在 2026 年已经部分失效**：

| 工具 | 已经稳定了 |
|---|---|
| Turbopack | dev（15.0）、build（16.0，且已默认） |
| Rspack | v1.0（2024-08） |
| Rolldown | 已被 Vite 8+ 采用为底层 |

**"还不稳定"不再是一个通用的推迟理由。** 真正的理由应该更具体：**"我的插件里有几个搬不过去"**、**"我没有视觉回归"**、**"我用 Yarn PnP"**。**能说出具体理由，才叫判断；说不出，只是拖延。**

## 6.7 实战：迁移里的六个现场

> **说明**：构造示例，不是真实项目经历。每一步的成因都能在本章或前五章找到对应机制。

### 场景一：换了 esbuild 转译，构建没快多少

**现象**：把 Babel 换成 esbuild 做转译，构建时间只降了 10%。

**成因**（§6.2 / §6.3）：**A 档工具只接管"解析 + 代码生成"两段**，拿不到 **linking** 的收益。如果你的项目耗时主要在图合并、chunk 优化、插件遍历上，换转译器的收益自然小。

**诊断**：先量"转译占总耗时多少"。**这个占比就是收益上限。**

### 场景二：以为 esbuild 不用 AST，据此做了个错误的技术判断

**现象**：团队文档里写"esbuild 不用 AST，所以比 X 快"，后来在讨论"我们能不能也跳过 AST"时被带偏。

**成因**（§6.3）：**官方原文恰好相反** ——"esbuild 只完整触碰 JavaScript AST **三次**"。

**正确理解**：快来自**减少遍历次数 + 避免多次表示转换**（官方举的那条 `string→TS→JS→string→…→压缩` 的链），而不是"没有 AST"。

### 场景三：换到 Turbopack，构建成功但页面视觉有偏移

**现象**：迁移后一切正常，只有某些段落的行高看起来"差一点点"。

**成因**（§6.5）：官方明列的 **CSS 小数精度差异** —— **Lightning CSS 保留 5 位，webpack 保留 10 位**。`line-height` 这类属性会受影响。

**这条的意义**：**它不会被任何"构建是否成功"的检查发现**。只有视觉回归能发现。

### 场景四：某个 webpack 插件在新工具里找不到对应物

**现象**：`npm ls` 里有个只做"构建时生成文件"的插件，新工具没有等价物。

**成因**（§6.5）：**新工具普遍支持 loader，但不支持 webpack plugin**（Turbopack 官方明确）。原因在第 4 章 §4.5：plugin 依赖 **hook 模型**，而不同工具的 hook 模型不兼容。

**修法**：多数"生成文件"类插件可以用新工具自己的钩子重写（第 4 章 §4.6 的 `generateBundle` / `processAssets`）。**真正搬不过去的是"深度依赖 webpack 内部对象"的插件。**

### 场景五：Sass 自定义函数搬不过去

**现象**：项目用 `sassOptions.functions` 在构建期算出一批颜色值，新工具不支持。

**成因**（§6.5）：官方理由非常干脆：**Rust 架构无法执行 JS 函数**。

**这条是"架构性不可为"的典型**：不是"还没做"，而是"这种架构里没有这个位置"。**修法是换实现**（把计算挪到 Sass 层，或先生成变量文件）。

### 场景六：Yarn PnP 项目无法迁移

**现象**：项目用 Yarn PnP，新工具官方标注 "Not planned"。

**成因**（§6.5）：**生态兼容不是"时间问题"**。有些是"优先级低"，有些是"明确不做"。

**这一条改变的是决策性质**：**如果你在"等它支持"，可能永远等不到。** 唯一的办法是改包管理器，或留在原工具。

### 反过来看：本章机制该放进决策文档的哪几句

| 问题 | 怎么答 | 对应机制 |
|---|---|---|
| 换转译器能快多少 | 转译占总耗时多少，就是上限 | §6.2 阶段可并行性 |
| 为什么 Rust 工具更快 | 并行度 + 消除工具间序列化 + JIT 冷启动 | §6.2 四条理由 |
| esbuild 是不是不用 AST | **不是**，它只遍历 AST 三次 | §6.3 官方原文 |
| 该换哪一层 | 先换不影响产物语义的层 | §6.6 一条反常识的建议 |
| 换打包器会丢什么 | loader 基本可平移，**plugin 最难搬** | §6.5 三条判据 |
| 迁移最大风险是什么 | **构建成功但行为微变**（CSS 精度、排序） | §6.5 反直觉结论 |
| 现在稳不稳定 | Turbopack dev 15.0 / build 16.0；Rspack v1.0；Rolldown 驱动 Vite 8+ | §6.6 矩阵 |
| 该不该等 | 能说出具体理由才算判断 | §6.6 关于"该不该等" |

## 6.8 动手

**每一项都要求说出理由**：

| 任务 | 验收 |
|---|---|
| 在一个项目里分别量：总构建时间、转译段耗时、压缩段耗时 | 说出"换 A 档工具"的收益上限是多少，依据是 §6.2 的阶段划分 |
| 把 esbuild 的"为什么快"按四条理由各写一句 | 说出哪一条解释了 **CLI 冷构建**、哪一条解释了 **dev server 也可能更快** |
| 查一次你所用工具是否用官方 TypeScript 编译器作 parser | 说出官方那句"关掉类型检查仍运行类型检查器"的发现意味着什么 |
| 用 §6.3 的三次遍历内容，画出 esbuild 的处理流水线 | 说出"减少遍历"与"减少表示转换"各自省掉了什么 |
| 复现官方那条 `string→TS→JS→string→…` 的表示转换链 | 说出多工具串联为什么必然产生这条链（提示：工具间的接口是文本） |
| 查一次你项目里的 webpack（或 Rollup）插件清单 | 按 §6.5 的判据标注：可用 / 有替代 / 无解，并统计比例 |
| 找出项目里所有"构建期执行 JS"的地方（Sass 函数、自定义 loader） | 说出这一类为什么在原生化架构里搬不过去 |
| 在项目里跑一次视觉回归（没有就先用截图对比） | 说出"为什么没有视觉回归就不该换打包器" |
| 查一次你用的框架/工具链，确认它底层是哪个打包器 | 说出它在 §6.1 的谱系表里属于哪一档 |
| 对比 Rolldown 官方基准里的 `Rollup + esbuild` 与 `Rolldown` 两行 | 说出 40.10s vs 1.61s 的差距说明了什么（提示：不是"语言快"） |
| 读一次 Turbopack 的 "Bundling vs Native ESM" 与 Vite 的 "Rolldown 改变了这一点" | 说出两者为什么独立收敛到同一结论 |
| 把 §6.6 的矩阵填成你自己项目的版本（加一列"我用不用"） | 说出你的第一档迁移动作是什么、为什么不是第三档 |

**进阶挑战**（任选一项）：

1. **做一次"两阶段迁移"**：先把转译与压缩换成 A 档工具（产物语义应不变），验证产物 diff 为空；再单独评估是否换打包器。要求记录两次变更各自的耗时变化与风险。
2. 拿一个真实项目，列出**迁移会丢的能力清单**（按 §6.5 的三条判据），并给每一项标"可替代 / 需改实现 / 无解"。**这份清单比"快多少"更能决定该不该迁。**
3. 把 §6.2 的"三阶段可并行性"与 §5.1 的"四个指标"叠加成一张表：**每个指标主要落在哪个阶段、能不能靠并行改善**。这张表的价值在于：**它能解释为什么"某工具在某指标上更快"不自动推广到其他指标。**

## 6.9 本章常见误区

| # | 误区 | 纠正 |
|---|---|---|
| 1 | "Rust / Go 比 JS 快，所以原生工具更快" | 解释力不足。真正的理由是：**JIT 冷启动劣势 + 并行度（共享内存 vs 序列化 + 独立堆）+ 减少遍历与表示转换** |
| 2 | "esbuild 快是因为不用 AST" | **错，官方原文相反**：esbuild "只完整触碰 JavaScript AST **三次**" |
| 3 | "esbuild 快是因为用 Go 重写了 Babel" | 它**从零实现**（含自己的 TS parser），并**把多步处理交错进三次遍历**以减少缓存失效与表示转换 |
| 4 | "JS 多线程只是写起来麻烦" | 还有**结构性开销**：线程间必须序列化、每线程独立堆。官方称这会把并行度**砍掉约一半** |
| 5 | "关掉类型检查就真的不跑类型检查器了" | 官方发现：**TypeScript 的 parser 似乎仍在运行类型检查器**（即使类型检查被关闭） |
| 6 | "A 档工具会顺便做类型检查" | **都不做**（esbuild / SWC / Oxc）。`tsc --noEmit` 必须独立跑 |
| 7 | "Rolldown 是 Rollup 的替代品，随便换" | 官方只说 **"Rollup-compatible API"**；**兼容度细节首页未给**，需查迁移文档 |
| 8 | "Rolldown 首页提到了 Oxc，所以 Oxc 是它的内核" | **本次抓取的首页完全没有提到 Oxc**。transforms / minify 被描述为"内建能力"，但**底层实现未交代** |
| 9 | "Rolldown 已经有正式版本号了" | **首页未标注自身版本号**。最强成熟度信号是"驱动 Vite 8+" |
| 10 | "Rspack 能无缝替换 webpack" | 官方用的是量化区间：**"大部分" API**、**"几乎所有的" loader**、头部 50 个插件 **">85% 可用或有替代"** |
| 11 | "85% 意味着 85% 可以直接用" | **"或有替代"这半句意味着相当一部分不是 drop-in**，要换实现 |
| 12 | "第三方 loader/plugin 越多越好" | Rspack 官方反过来论证：**它们常成为性能瓶颈**（作者不熟悉内部机制 + hook 限制算法交互），所以关键能力要做成内建 |
| 13 | "Turbopack 还是实验品" | **dev 自 15.0.0 稳定；build 自 16.0.0 稳定并成为 Next.js 默认打包器** |
| 14 | "dev 期不打包是先进做法" | **Turbopack 官方明确拒绝**：小应用可行，**大应用会因请求数变慢**。而 Vite 也在探索 dev 期打包（第 5 章） |
| 15 | "Turbopack 的缓存是文件级的" | 官方说**粒度细到函数级**，且结果**持久化到磁盘、跨多次运行保留** |
| 16 | "Turbopack 支持 webpack 生态" | **支持 webpack loaders，不支持 webpack plugins** |
| 17 | "迁移失败会报错，所以能马上发现" | **最大风险是"构建成功但行为微变"**：CSS Module 排序、CSS 小数精度（5 位 vs 10 位）都要靠视觉回归发现 |
| 18 | "某个 Sass 函数不支持，等他们做就好了" | 官方理由：**Rust 架构无法执行 JS 函数** —— 这是**架构性不可为**，不是待办 |
| 19 | "Yarn PnP 以后会支持" | Turbopack 官方标注 **"Not planned"**。有些兼容不是时间问题，而是决定不做 |
| 20 | "Rolldown 快是因为 Rust 编译器好" | 官方基准里 `Rollup + esbuild` 40.10s vs Rolldown 1.61s —— **差距主要来自消除工具间串联**，不是单个工具的语言 |
| 21 | "等所有工具都稳定了再动" | 三个主要工具都已稳定（Turbopack 16.0 默认 / Rspack v1.0 / Rolldown 驱动 Vite 8+）。**该不该动要有具体理由，不能只说"还不稳"** |
| 22 | "本章给的那几个工具的速度可以直接比" | **不能**。Turbopack 与 Rspack 的官方页面**都没有给出速率基准**；esbuild 与 Rolldown 的基准**测试条件不同** |
| 23 | "SWC 是 Babel 的 drop-in 替代" | 官方首页**只把 Babel 作为性能对比对象**，**没有 "drop-in replacement" 的表述**。这是社区说法 |
| 24 | "SWC 只做转译" | 官方明确它也能**压缩**、也能**打包**。但它没有成为主流打包器替代品，而是**做了别人的转译层**（Next.js / Parcel / Deno） |
| 25 | "SWC 比 Babel 快 20 倍 / 70 倍"可以直接引用 | 官方这句**没有给测试方法、硬件配置或基准细节**。引用必须带这个限定（对照 esbuild 那组给了完整条件） |
| 26 | "Rolldown 的 parse/transform/minify 由 Oxc 提供" | **在两个官方首页都无法证实**：Rolldown 首页未提 Oxc，**Oxc 首页也未提 Rolldown 或 Vite**。本章不把它当结论 |
| 27 | "Oxc 是又一个 esbuild 那样的工具" | 它定位是**"一套工具集合 / 工具链基石"**，六个组件可独立消费（lint / format / parser / transform / resolver / minify）。**"底座"与"工具"是两种形态** |
| 28 | "Oxc 已经全稳定了" | 官方自标：**Oxfmt = Beta、oxc-minify = Alpha**；且**未给任何版本号** |
| 29 | "Farm 能直接跑我的 Vite 项目" | 官方只说**插件层面 "out of box" 支持 Vite 插件**，**配置层面（`vite.config` 能否平移）未提及** |
| 30 | "Farm 是 webpack 替代品" | **Farm 首页完全没有提到 webpack** —— 无对比、无迁移说明。此说法在本页无据 |
| 31 | "Partial Bundling 只是营销词" | 它是对第 5 章那个两难的**正面折中**：在**请求数与缓存粒度**之间取中间点，与 Turbopack「dev 也打包」、Vite 的 full bundle mode 同向 |
