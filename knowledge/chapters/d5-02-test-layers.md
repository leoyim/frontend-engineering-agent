## 2.1 测试分层的真实含义

"测试金字塔"是一个被说烂的图。但它**真正的依据**往往没被讲清 —— 于是"为什么多写单元测试"变成了一条教条。

### 分层依据：反馈成本 × 真实度

| 层 | 真实度 | 反馈速度 | 单次成本 | 失败原因的数量 |
|---|---|---|---|---|
| **单元测试** | 低（只测一个函数/模块） | **毫秒级** | 极低 | **少**（基本只有"逻辑错了"） |
| **组件测试** | 中（真实渲染，但依赖被替身） | 秒级 | 低 | 中 |
| **集成测试** | 较高（多模块协作） | 秒级–十秒级 | 中 | 较多 |
| **E2E** | **最高**（真实浏览器 + 真实服务） | **分钟级** | 高 | **最多** |

**这张表最关键的是最后一列。**

**E2E 失败的原因远多于"代码错了"**：

| E2E 可能因为什么失败 | 与代码正确性有关吗 |
|---|---|
| 服务没起来 / 网络抖动 | **无关** |
| 元素还没渲染出来（时序） | **无关** |
| 元素被遮挡、动画未停 | **无关** |
| 第三方服务超时 | **无关** |
| **断言不成立** | **有关** |

**所以"多写单元、少写 E2E"的真正理由不是"单元更便宜"，而是**：

> **E2E 的失败信号里，真正指向"代码错了"的比例很低。**

一个 90% 时间在报"时序问题"的 E2E 套件，**不是在保护质量，而是在训练团队忽略红色**。这与 `D5` 第 1 章 §1.7 那条"没有能力处理的问题会训练出忽略"、以及 `D6` 第 4 章 §4.6 的"告警数与健康度负相关"是同一个机制。

### 三种成本，只有一种在增长

| 成本 | 什么时候付 | 随什么增长 |
|---|---|---|
| **写** | 一次 | 与真实度**正相关** |
| **跑** | 每次 CI / 每次提交 | 与真实度**强正相关** |
| **维护** | **持续** | 与真实度**强正相关**，且**随被测系统的外部依赖变化而变化** |

**第三行是最容易被低估的**：单元测试的维护成本几乎只随"逻辑变化"增长；而 E2E 会因为你**没有改任何代码**而失效（第三方页面改了、接口字段变了、证书过期了）。

**这解释了"测试套件越老越慢越红"的现象**：不是团队变懒了，而是**维护成本的结构性差异**在高龄套件上兑现了。

### 一条判据：这个测试应该放在哪一层

不是按"重要性"分层，而是按**"你想锁定什么不变"**：

| 想锁定 | 放哪层 | 例子 |
|---|---|---|
| **一个纯逻辑的输入输出关系** | 单元 | 价格计算、日期格式化、状态机转移 |
| **组件的可访问性与交互** | 组件 | 表单校验提示、按钮禁用态、键盘可达 |
| **多个模块的契约** | 集成 | 请求层 → 状态层 → 渲染 |
| **关键用户路径能走通** | E2E | 登录 → 下单 → 支付（**只测 3–5 条主路径**） |
| **外观没有意外变化** | 视觉回归 | 设计系统组件、关键页面 |

**第三、四行是"少而精"的典型**：E2E 的数量应当**等于"业务上绝不允许坏掉的路径"的数量**，而不是"尽可能多覆盖功能"。

## 2.2 单元测试：Vitest 与 Jest 的分工

`D5.L2.04`。这两个工具常被并列讨论，但**它们与构建工具的关系完全不同** —— 而这决定了该选哪个。

### ⭐ 一条来自 Jest 官方的硬事实

本次核验的 **Jest 官方 Getting Started 页**里，有一段明确写着：

> **Vite 不受支持**（与 Vite 插件系统不兼容；`vite-jest` 不兼容 Vite > 2.4.2）；**替代方案是 API 兼容 Jest 的 Vitest**。

**这条的价值在于它出自 Jest 自己的文档** —— 不是"Vitest 的宣传"，而是"另一个工具的官方推荐"。

**所以在一个 Vite 项目里，"要不要用 Jest"这个问题已经有官方答案了。**

### Vitest 的机制：复用 Vite 的配置

Vitest 的官方定位：

> **下一代测试框架，由 Vite 驱动。**

它的机制关键在配置层（官方）：

| 事实 | 官方内容 |
|---|---|
| **默认读取 `vite.config.*`** | 因此"**你现有的 Vite 插件与配置可以开箱即用**" |
| 可另建 `vitest.config.*` | 但**前者存在时，`vite.config.*` 的所有选项会被忽略** |
| 环境要求 | **Vite >= v6.4.0**，**Node >= v22.12.0** |
| 测试文件命名 | 默认需含 `.test.` 或 `.spec.` |
| 单次运行 | `vitest run`（不带 `run` 是 watch 模式） |

**第二行是本章最实用的一条**：**两个配置文件同时存在时，不是"合并"，而是"后者整体被忽略"。** 很多人以为 `vitest.config.ts` 会覆盖/补充 `vite.config.ts`，实际是**直接替换**。所以如果你在 `vitest.config.ts` 里只写了 `test` 字段，**`vite.config.ts` 里的 `resolve.alias` 会全部失效** —— 症状是"测试里 import 路径解析不到，但构建正常"。

**⚠️ 一处如实标注**：Vitest 的 Getting Started 页只说"配置与插件复用"，**没有展开说它是否复用 Vite 的转换管道**。所以"测试与构建的转换行为完全一致"这句话，本章**不外推**（且 `D3` 第 5 章已证明 dev 与 prod 的转换行为本来就有差异）。

### 覆盖率：口径比数字重要

`D3` 第 3 章讲过"覆盖面由测试范围决定"，这里给出工具侧的机制。

**Vitest 的覆盖率默认值**（官方）：

| 配置 | 默认值 | 含义 |
|---|---|---|
| `coverage.enabled` | **`false`** | **默认不采集**，必须显式打开 |
| `coverage.provider` | **`'v8'`** | 可选 `'v8' \| 'istanbul' \| 'custom'` |
| `coverage.include` | **「测试运行期间被导入的文件」** | ← **这条最容易造成"覆盖率虚高"** |
| `coverage.reportsDirectory` | `./coverage` | 且 `coverage.clean` 默认 `true`，**跑测试前会删掉该目录** |
| `coverage.reporter` | `['text', 'html', 'clover', 'json']` | —— |

**⭐ `include` 的默认值是最值得记的一条**：

> **默认只统计"被测试导入过的文件"。**

**后果**：一个**从未被任何测试 import 的模块**，根本不会出现在分母里 —— 于是覆盖率可能显示 95%，而实际上有大量代码**一行都没跑过**。

**这不是 bug，是默认口径的选择。** 要得到"全量口径"，必须显式把 `coverage.include` 设成源码目录（如 `src/**`）。

**四种子阈值与一个巧妙的负数语义**（官方）：

| 子阈值 | 正数含义 | **负数含义** |
|---|---|---|
| `lines` / `functions` / `branches` / `statements` | **最低覆盖率百分比** | **允许的未覆盖条数上限** |

官方例子：`lines: 90` → 行覆盖不得低于 90%；`lines: -10` → **未覆盖行数不得超过 10 行**。

**这个负数语义很有用**：**对"代码量小但每条都重要"的模块，用"未覆盖条数"比用百分比更合理** —— 因为 10 行里漏 1 行就是 90%，而 1000 行里漏 10 行是 99%，两者的严重性其实相反。

**另外两条**：

- **glob 分组不继承顶层阈值**（官方明确）—— 分组是"独立设定"，不是"覆盖"。
- `coverage.thresholds.perFile` 默认 `false`，**即默认只看聚合值** —— 这允许"某些文件 0%、另一些 100%"而总体达标。

**⚠️ 一处缺口**：Vitest 的 Coverage 配置页**没有给出 v8 与 istanbul 的优劣对比**（只标了各自的专属选项）。所以"该选哪个 provider"本章**不给建议**。

### Jest 需要什么配置

| 场景 | 官方内容 |
|---|---|
| **纯 JS（CommonJS）** | **零配置** |
| 有 Babel 配置时 | `babel-jest` 在安装 Jest 时**自动安装**，会自动转换文件；想关闭用 `transform: {}` |
| **TypeScript** | 两条路：经 **Babel**（`@babel/preset-typescript`）或 **`ts-jest`** |
| **⚠️ 经 Babel 的路径** | 官方明确：**纯转译，不做类型检查**（需要类型检查要用 ts-jest 或单独跑 `tsc`） |

**最后一行与 `D2` 的"检查与产出分离"完全一致**：Babel 路径下，**类型错误不会让测试失败**。这会造出一个危险的假象：**测试全绿，但代码有类型错误。**

**⚠️ 两处如实标注**：Jest 的 Getting Started 页**完全没有提及 ESM**（示例一律 CommonJS），也**没有 `testEnvironment` 与 snapshot testing**。所以本章**不给 ESM 现状判断，也不给 `testEnvironment` 默认值**。

**版本**：Jest 文档当前展示 **30.5**（最后更新 2026-08-28）；Vitest **v5.0.5**。

## 2.3 组件测试：查询方式决定了测试的价值

`D5.L2.05`。这一节的核心不是"怎么用 Testing Library"，而是**"为什么查询方式本身就是设计决策"**。

### 核心理念：一句话

官方引言（全站的核心论点）：

> **你的测试越接近软件被使用的方式，它能给你的信心就越多。**

配套的定位是"以**用户为中心**的方式测试 UI 组件"。

**而它要避免的东西，官方列得很具体** —— 四类**实现细节**：

| # | 应当避免测的东西 |
|---|---|
| 1 | 组件的**内部 state** |
| 2 | 组件的**内部方法** |
| 3 | 组件的**生命周期方法** |
| 4 | **子组件** |

**为什么这四类不能测**：因为**它们会在"重构但不改功能"时变化**。测了它们，测试就会在正确的重构中变红 —— 而频繁的假红会让人**不再相信测试**（同 §2.1 的机制）。

### 查询优先级：三个等级

官方把查询分成三层，**顺序本身就是判据**：

| 等级 | 官方描述 | 查询 |
|---|---|---|
| **1. 对所有用户可及** | "反映视觉/鼠标用户**以及**使用辅助技术的用户的体验" | `getByRole` → `getByLabelText` → `getByPlaceholderText` → `getByText` → `getByDisplayValue` |
| **2. 语义查询** | "符合 HTML5 与 ARIA 的选择器，但**跨浏览器与辅助技术的体验差异很大**" | `getByAltText` → `getByTitle` |
| **3. Test ID** | —— | `getByTestId` |

**`getByRole` 排第一的官方理由**（原文）：

> **这应当是你在几乎所有场景下的首选偏好。** 用它几乎没有取不到的东西（**如果取不到，那可能是你的 UI 存在无障碍问题**）。

**⭐ 这条后半句是本节的枢纽**：

> **用 `getByRole` 查不到，不一定是测试写错了 —— 可能是组件本身对辅助技术不可见。**

**于是组件测试顺带成了一道无障碍检查。** 这不是附加好处，而是"按用户方式查询"这条原则的**数学后果**：你按"用户能找到的方式"查，查不到就意味着"有用户找不到"。

**另外三条官方结论**：

| 查询 | 官方立场 |
|---|---|
| `getByLabelText` | "对表单字段**非常好**"；表单场景应为**首选**（用户是靠 label 文本找表单的） |
| `getByPlaceholderText` | "**placeholder 不是 label 的替代品**。但如果那是你唯一的办法，它比别的选择好" |
| `getByTitle` | "**title 属性不被读屏器一致地读取**，并且对明眼用户**默认不可见**" |
| `getByTestId` | "**用户看不到（也听不到）这些**" → 只在无法用 role/文本匹配时用 |

**一句话总结查询优先级**：

> **优先级 = 这个属性"有多少真实用户能感知到"。**

`role` + 可访问名称 是所有用户都能感知的（包括读屏器）；`testid` **没有任何用户能感知** —— 所以它最后。

### `get` / `query` / `find`：三个动词，三种语义

这是最容易混的一组，而官方给了一张完整的表：

| 方法 | 0 个匹配 | 1 个匹配 | **>1 个匹配** | 会重试吗 |
|---|---|---|---|---|
| `getBy...` | **抛错** | 返回元素 | **抛错** | 否 |
| `queryBy...` | **返回 `null`** | 返回元素 | **抛错** | 否 |
| `findBy...` | **抛错** | 返回元素 | **抛错** | **是** |
| `getAllBy...` | 抛错 | 返回数组 | 返回数组 | 否 |
| `queryAllBy...` | **返回 `[]`** | 返回数组 | 返回数组 | 否 |
| `findAllBy...` | 抛错 | 返回数组 | 返回数组 | **是** |

**这张表里有三条设计意图值得单独看**：

**① `>1 个匹配` 一律抛错**（除 `*AllBy*`）。

**这条把"查询"变成了"断言"**：如果一个角色为 `button` 的元素本该只有一个，那么"查到两个"就是**明确的错误**，而不是"随便返回第一个"。**它强迫你面对歧义** —— 这在组件组合、列表渲染时特别有用。

**② `queryBy` 是唯一"找不到不报错"的**。

**所以它的用途是"断言不存在"**：`expect(screen.queryByText('错误提示')).toBeNull()`。**用 `getBy` 断言不存在会抛错，导致测试"失败得莫名其妙"。**

**③ `findBy*` 会重试，且默认 1000ms 超时**（官方）。

**它本质上是 `getBy*` + `waitFor` 的组合** —— 官方说明可以把 `waitFor` 的选项作为**最后一个参数**传进去。

**⭐ 由此得出一条纪律**：

> **需要等待时用 `findBy*`，不要手写 `waitFor` + `expect(getBy...)`。**

**因为手写的版本会在超时后抛出"找不到元素"，而 `findBy` 抛的是"等待超时"** —— 前者的错误信息会误导你去查查询条件，后者直接告诉你"等太久了"。**错误信息的质量决定了排查时间。**

### `screen`：为什么官方推荐它

官方明确建议：**"使用 `screen` 是推荐的"**。

**原因**：它是**预绑定 `document.body`** 的查询集合，省掉从 `render()` 返回值解构的麻烦，并且在 debug 输出与 `waitFor` 场景下更好用。

**另一个必须知道的限制**（官方）：用 `screen` 需要**全局 DOM 环境** —— 例如 Jest 要配 `testEnvironment: jsdom`。

**另两条实用默认值**（官方）：

| 项 | 默认行为 |
|---|---|
| `exact` | **默认 `true`**（完整匹配、区分大小写）；`false` 时子串且不区分大小写；**对正则/函数参数无效** |
| **空白归一化** | 默认**裁剪首尾空白 + 把内部连续空白折叠为单个空格** |

**第二条解释了一个常见困惑**："我明明写的是两个空格，为什么匹配失败？" —— 因为**归一化先把它们折叠了**。

### 分层：它不是一个框架

官方的 **"What this library is not"** 说得很清楚：

| 不是 | 说明 |
|---|---|
| **不是 test runner / 测试框架** | 它只提供查询与交互 |
| **不绑定特定测试框架** | 可与 Jest、Mocha + JSDOM、或真实浏览器配合 |

**它的分层**：

```
DOM Testing Library（核心，查询 + 交互）
   ├── React / Vue / Angular 适配（render 时预绑定查询）
   ├── React Native 实现
   └── Cypress 插件（复用同一套查询）
```

**这条分层的意义**：**"按用户方式查询"这个原则是与框架无关的**。所以换框架时，**测试的写法几乎不变** —— 这与 §2.2 的"换测试运行器和换断言库是两件事"是同一个道理。

## 2.4 集成与 E2E：自动等待解决的是"时序"不是"正确"

`D5.L3.01`。这一节要讲清一件事：**E2E 框架的自动等待，解决的是"什么时候操作"，不是"操作对不对"**。

### Playwright 的定位与一体化

官方定位：

> **一个面向现代 Web 应用的端到端测试框架。它把测试运行器、断言、隔离、并行与丰富的工具链打包在一起。**

**"打包在一起"这一条是它的关键差异** —— 官方列举的四个卖点里，前三个都是"你不用自己拼装"：

| 卖点 | 官方内容 |
|---|---|
| 一体化 | runner + assertions + isolation + parallelization + tooling |
| 跨引擎 | **Chromium / WebKit / Firefox**，三个平台（Windows / Linux / macOS） |
| 默认行为 | **headless + 三个引擎并行** |
| 移动端 | 原生模拟 Chrome(Android) 与 Mobile Safari |

**⚠️ 一处与 Cypress 的对照缺口先说**：Cypress 官方"为什么不支持 Safari/WebKit"这件事，在本次核验的页面上**完全没有提及**。所以本章**不断言 Cypress 支持或不支持 WebKit**（详见下）。

### auto-waiting：五项可操作性检查

官方定义：

> Playwright 在**执行操作前**对元素做一系列**可操作性检查（actionability checks）**，以确保操作按预期生效。它**自动等待所有相关检查通过**，然后才执行请求的操作。**若在给定超时内检查未通过，操作失败并抛出 `TimeoutError`。**

**五项检查（官方定义）**：

| 检查 | 官方定义 | 常见误解 |
|---|---|---|
| **Visible** | 元素有**非空边界框**，且计算样式**不是 `visibility:hidden`** | **`opacity: 0` 仍算可见**；零尺寸**不算**；`display:none` 不算 |
| **Stable** | 元素在**至少两个连续动画帧**中保持相同边界框 | 这是"动画期间点不到"的机制解释 |
| **Enabled** | 未被禁用（含**位于带 `[disabled]` 的 `<fieldset>` 中**、是带 `[aria-disabled=true]` 元素的后代） | 禁用不只看元素自身 |
| **Editable** | 已启用且**不是只读**（含 `<select>`/`<input>`/`<textarea>` 带 `[readonly]`、或 ARIA role 支持只读的 `[aria-readonly=true]`） | 只读与禁用是两件事 |
| **Receives Events** | 元素是**操作点处指针事件的命中目标**，即**没有被其他元素遮挡** | 这是"遮罩层导致点击失败"的机制解释 |

**`opacity: 0` 算可见** 这条特别值得记：它意味着**一个完全透明的元素仍可被点击**（只要没被遮挡）。所以"把它透明掉"不是"隐藏它" —— 那是 `visibility: hidden` 或 `display: none` 的语义。

### 不同操作要做的检查不一样

官方给了完整对照表：

| 操作 | Visible | Stable | Receives Events | Enabled | Editable |
|---|:-:|:-:|:-:|:-:|:-:|
| `click()` `check()` `dblclick()` `tap()` | ✓ | ✓ | ✓ | ✓ | — |
| `hover()` `dragTo()` | ✓ | ✓ | ✓ | — | — |
| `screenshot()` | ✓ | ✓ | — | — | — |
| `fill()` `clear()` | ✓ | — | — | ✓ | ✓ |
| `selectOption()` | ✓ | — | — | ✓ | — |
| `press()` `focus()` `dispatchEvent()` | — | — | — | — | — |

**这张表解释了三个现象**：

| 现象 | 原因 |
|---|---|
| `fill()` 不需要 Stable，但 `click()` 需要 | 填值不依赖坐标命中；点击依赖"这一帧元素在哪" |
| `screenshot()` 需要 Stable | 否则会截到动画中间态 |
| `press()` 什么检查都不做 | 键盘事件**不依赖元素位置与可见性** |

**第三行是个重要提示**：**用 `press()` 绕过了可见性与遮挡检查** —— 于是"键盘能操作"≠"鼠标能操作"。**如果把测试都写成 `press()`，你会漏掉一整类"点不到"的问题。**

### `force` 的代价

官方说明：部分操作支持 `force` 选项，**关闭非必要的可操作性检查**（例如给 `click()` 传 `force` 就不再检查"是否接收点击事件"）。

**它的代价是精确的**：**你放弃了"这个元素真的能被用户点到"这个保证。** 而这条保证恰好是 E2E 相对单元测试的**主要价值**。所以 `force` 只应当用于"已经确认过原因"的场景（例如确实有个覆盖层，但业务上允许穿透）。

### 断言也是自动重试的

官方原文：

> Playwright 包含**自动重试断言**，它通过**等待条件满足**来**消除 flakiness**，机制与操作前的 auto-waiting 类似。

**⚠️ 一处措辞如实标注**：这一页用的术语是 **"auto-retrying assertions"**，**没有用 "web-first assertions"**（后者只在安装页的"下一步"里被提了名字，没有定义）。

**这条区分的实践含义**：

| 断言类型 | 行为 |
|---|---|
| **自动重试的断言**（如 `toHaveText` / `toBeVisible`） | 会等待并重试，直到超时 |
| **普通断言**（如 `expect(2).toBe(2)`） | **立即判定**，不等待 |

**所以"把自动重试断言换成普通断言"是 E2E 变 flaky 的一条常见路径**：例如先取文本再用 `toBe` 比较，就丢掉了等待能力。

**⚠️ 一处缺口**：**Playwright 的 actionability 页没有给出默认超时的具体数值**。所以本章**不给秒数**。

### Cypress：架构差异才是重点

Cypress 的官方定位与 Playwright 不同 —— 它自称是**"质量平台"**（整合 E2E + 组件测试 + 可访问性检查 + 覆盖率可视化），而不是"一个测试框架"。

**但真正的差异在架构**，官方原文说得很直接：

> **多数测试工具（如 Selenium）通过在浏览器之外运行、跨网络执行远程命令来工作。Cypress 恰好相反 —— Cypress 与你的应用在同一个 run loop 中执行。**

而它还有**另一半**：

> Cypress 背后有**一个 Node 服务进程**。Cypress 与这个 Node 进程持续通信、同步、互相代办任务。**能同时访问前后两部分**，让我们可以实时响应应用事件，同时在浏览器之外完成需要更高权限的任务。

**这条双层结构解释了两件事**：

| 能力 | 为什么能做到 |
|---|---|
| 能同步感知应用状态（不用轮询/等待） | 因为**在同一 run loop 里** |
| 能截图、录屏、读写文件 | 因为**有浏览器外的 Node 进程** |

**它的代价也是结构性的**：**运行在浏览器内意味着受浏览器约束**（单标签、难以做真正的多标签/多域场景）。

**⚠️ 三处必须如实标注的缺口**：

1. **Cypress 支持哪些浏览器**：该页只明确写了 **"Firefox 与 Chrome 系（含 Edge）"**，**完全未提 Safari / WebKit**。所以本章**不断言支持或不支持 WebKit** —— 只能说"该页未提"。
2. **`retry-ability` 的定义不在该页**（只在导航里）。所以本章**不给它的定义与边界**（例如"是否作用于有副作用的命令"这一点，本章不外推）。
3. **该页没有任何 Playwright 对比**（它对比的是 Selenium / WebDriver，并另有"Migrate from Playwright"的迁移指南）。

**能确定的只有一条**：关于"自动等待"，Cypress 官方说的等待条件包括 —— **元素可见、可用（enabled）、不再被遮挡、动画停止、页面加载完成、指定网络请求完成**。**这与 Playwright 的五项检查在方向上一致**，机制不同。

## 2.5 视觉回归与测试数据

`D5.L3.02` / `D5.L3.03`。

### 视觉回归：它只回答一个问题

> **"看起来变了吗？"**

**它不回答"对不对"。** 一条渲染错误（数字算错、文案写错）在像素上与"正确"可能只差几个字，但**语义完全不同**；而一次纯重构（改结构不改外观）**像素完全一致**，视觉回归会安静地通过 —— 这两点决定了它的定位：

| 它擅长 | 它不擅长 |
|---|---|
| 发现**意外的样式变化**（布局塌陷、字号错、颜色错） | 判断**内容是否正确** |
| 保护**设计系统组件**与**关键页面** | 覆盖大量业务逻辑 |
| 在**重构中**发现"不该变的地方变了" | 作为唯一的回归防线 |

### 两个失效方向

| 方向 | 表现 | 成因 |
|---|---|---|
| **误报**（假红） | 明明没改，就是不一致 | 字体渲染/抗锯齿差异、动画时序、光栅化差异、**不同操作系统** |
| **漏报**（假绿） | 明显错了，却通过 | 容忍度设得太宽；只截了稳定区域，问题在别处 |

**误报的代价更隐蔽**：**它会让团队给截图测试加上"自动更新快照"的肌肉记忆** —— 于是**真正的变化也会被一起"更新"掉**。这与 §2.1 的"假红会训练出忽略"是同一个机制。

**四个可落地的抑制手段**：

| 手段 | 抑制什么 |
|---|---|
| **固定视口与设备像素比** | 光栅化差异 |
| **字体本地化 + 显式等待 `document.fonts.ready`** | 字体加载时序 |
| **测试前禁用动画 / 设置 `prefers-reduced-motion`** | 动画中间态 |
| **只截稳定区域（而不是整页）** | 无关区域的抖动 |

**⚠️ 一处如实标注**：**Playwright 确实有视觉对比能力**（官方文档有 "Visual comparisons" 与 "Snapshot testing" 章节，并在安装页的导航中列出），但 **`toHaveScreenshot` 的具体 API 语义不在本次核验的 actionability / installation 页面上**。所以本章**不给参数与用法**。

### 测试环境与数据构造

`D5.L3.03`。这一节回答：**为什么同样的代码，测试有时红有时绿。**

#### 三种数据来源

| 来源 | 优点 | 代价 |
|---|---|---|
| **真实生产数据（脱敏）** | 最接近真实分布 | **脱敏本身是风险**；数据会漂移 |
| **工厂函数构造** | 每个用例只声明需要的字段，其余走默认 | 需要维护工厂；默认值可能掩盖问题 |
| **固定 fixture** | 完全可复现 | 容易与真实结构脱节 |

**推荐组合**：**工厂函数为主 + 少量 fixture 守住"真实形状"**。理由是工厂函数让"这个用例在测什么"变得显式（只写相关的字段），而 fixture 负责防止工厂"越简化越失真"。

#### 一条判据：可变性决定稳定性

> **测试里任何"会变的东西"，都必须可被注入或冻结。**

| 会变的东西 | 不处理的后果 | 处理方式 |
|---|---|---|
| **当前时间** | 跨日/跨时区跑出不同结果 | 注入 clock 或伪造时间 |
| **随机数 / UUID** | 快照永远不一致 | 固定种子或 stub |
| **时区 / locale** | 本地绿、CI 红 | 显式设定 |
| **网络** | 抖动导致偶发失败 | 见下 |
| **自增 id / 排序不稳定** | 断言位置错乱 | 排序稳定化，或按内容而非位置断言 |

**这张表的第二、三行是"本地绿、CI 红"的头号来源** —— 因为**本地与 CI 的时区/locale 常常不同**，而开发者很难意识到自己在依赖它。

#### 网络的三个层次

| 层次 | 机制 | 适用 |
|---|---|---|
| **真实服务** | 连真实后端（或容器化后端） | 少量关键集成测试 |
| **Mock server** | 本地起一个假服务，返回固定响应 | 契约测试、错误分支 |
| **拦截（route/network stub）** | 在浏览器/进程内拦截请求 | E2E 的稳定化、构造异常场景 |

**一条纪律**：**"拦截"是构造"服务不可用/超时/异常响应"的唯一实用手段** —— 真实服务很难按需返回 500。所以**错误分支的测试几乎一定要用拦截**。

**⚠️ 但拦截有一个陷阱**：**它让 E2E 失去了"真实"这个唯一优势**。如果所有请求都被拦截，你的 E2E 实际上是在测"前端对着假数据的行为" —— 那与组件测试的差别就只剩"环境更重"。**所以主路径上不要拦截。**

## 2.6 治理动作：六个判定阈值

与前几章同体例。**全部是起点值，需按项目校准。**

| # | 现象 | 判定阈值（起点值） | 动作 | 依据 |
|---|---|---|---|---|
| 1 | 覆盖率 95% 但很多代码从没跑过 | **`coverage.include` 未显式配置** | 显式设成源码目录；默认只统计"被导入过的文件" | §2.2 |
| 2 | 测试里 import 解析不到，构建却正常 | **`vitest.config.*` 与 `vite.config.*` 同时存在** | 前者存在时**后者整体被忽略**，不是合并 | §2.2 |
| 3 | 测试全绿但有类型错误 | **TypeScript 走 Babel 路径** | Babel **只转译不做类型检查**；改用 ts-jest 或单独跑 `tsc` | §2.2 |
| 4 | 组件测试在重构中频繁假红 | **一次纯重构导致 > 3 个测试失败** | 检查是否在测**内部 state / 方法 / 生命周期 / 子组件** | §2.3 |
| 5 | E2E 偶发失败，重跑就好 | **重跑成功率 < 95%** | 查三处：用了普通断言而非自动重试断言；`press()` 绕过了可见性检查；`force` 关掉了命中检查 | §2.4 |
| 6 | 视觉回归经常"没改也红" | **一周内 > 3 次无改动失败** | 固定视口与像素比、字体本地化、禁动画、只截稳定区域 | §2.5 |

### 三条使用说明

**① 阈值 2 与 3 是"静默失效"类。**

它们不报错 —— 配置看起来生效了、测试看起来通过了。**只有知道有这个坑才能发现。**

**② 阈值 4 与 6 都指向"假红训练出忽略"。**

这是本章反复出现的机制：**当红色的信噪比太低，团队会开始不看红色**。而**一旦不看，真正的红也会被错过**。

**③ 阈值 5 的排查顺序不能乱。**

先确认**断言类型**（最常见），再确认**是否用 `press()` 绕过**，最后才怀疑框架。**先怀疑框架是成本最高的路径。**

### 什么时候"不该加测试"

| 情况 | 为什么 |
|---|---|
| **逻辑本身还在剧烈变化** | 测试会跟着改，收益为负 |
| **没有能力在失败时判断"是不是误报"** | 会训练出忽略（§2.1） |
| **靠 `force` / 拦截才能跑通的 E2E** | 它已经失去了 E2E 的唯一优势（真实） |
| **纯粹为了覆盖率数字** | 会产出"执行了但没断言"的测试 —— 它增加维护成本，不增加信心 |

## 2.7 动手

**每一项都要求说出理由**：

| 任务 | 验收 |
|---|---|
| 数出你项目各层测试的数量，按 §2.1 的表判断结构是否合理 | 说出 E2E 的失败中有多少比例真正指向"代码错了" |
| 查一次 Jest 与 Vitest 的官方口径（谁不支持 Vite） | 说出这条事实出自哪一方的文档（不是猜测） |
| 检查你项目是否同时存在 `vitest.config.*` 与 `vite.config.*` | 若同时存在，说出 `resolve.alias` 这类配置现在还在不在 |
| 故意删掉 `coverage.include`，对比覆盖率数字 | 说出"默认口径"与"全量口径"差多少、差在哪 |
| 用 `lines: -10` 这种负数阈值试一次 | 说出它比百分比更适合什么样的模块 |
| 检查 TS 项目走的是 Babel 还是 ts-jest | 若走 Babel，说出类型错误为什么不会让测试失败 |
| 在组件测试里把一个 `getByRole` 换成 `getByTestId` | 说出这个替换丢掉了什么（§2.3 的推论） |
| 用 `getByRole` 查一个自定义组件 | 若查不到，说出这可能意味着什么（不一定是测试写错） |
| 查一次你 E2E 里断言用的是自动重试的还是普通的 | 说出把自动重试换成普通会怎么变 flaky |
| 查一次有没有用 `press()` 代替 `click()` | 说出这漏掉了哪两项检查 |
| 统计一次视觉回归的误报率 | 若误报多，说出"自动更新快照"这个动作的风险 |
| 找出你测试里所有依赖"当前时间"的地方 | 逐项标注是否可注入 |

**进阶挑战**（任选一项）：

1. **做一次"层级重新分配"**：挑 10 条现有 E2E，判断其中哪几条其实可以在组件层或集成层覆盖。迁移后对比"跑一次的时间"与"失败的归因清晰度"。
2. **给视觉回归建一套稳定基线**：固定视口与像素比、字体本地化、禁动画、只截稳定区域。要求记录"改动前后误报率"。
3. **把"会变的东西"全部冻结**：时间、随机、时区、locale、网络。目标是把"本地绿 CI 红"这一类失败降到 0，并记录每项的处理方式。

## 2.8 本章常见误区

| # | 误区 | 纠正 |
|---|---|---|
| 1 | "测试写完就只花跑的时间" | **维护成本与真实度强正相关**，且会因外部依赖变化而增长（第三方改了、接口变了） |
| 2 | "E2E 越多越好" | E2E 数量应**等于"业务上绝不允许坏掉的路径"的数量**（通常 3–5 条主路径） |
| 3 | "Vite 项目可以用 Jest" | **Jest 官方文档明确说 Vite 不受支持**，并指向 **API 兼容 Jest 的 Vitest** |
| 4 | "`vitest.config` 会补充 `vite.config`" | **前者存在时后者整体被忽略**（不是合并）。症状是 alias 等配置静默失效 |
| 5 | "覆盖率 95% 说明覆盖很全" | Vitest 的 `coverage.include` **默认只统计"被导入过的文件"** —— 从没被 import 的模块不在分母里 |
| 6 | "覆盖率阈值只能设百分比" | Vitest 支持**负数**：`lines: -10` 表示"未覆盖行数不得超过 10 行"。对小块重要代码比百分比更合理 |
| 7 | "glob 分组会继承顶层阈值" | Vitest 官方明确：**不继承**，只对匹配文件生效 |
| 8 | "Jest 零配置就能跑 TypeScript" | 纯 CJS 才零配置。TS 要走 Babel 或 ts-jest，**Babel 路径只转译不做类型检查** |
| 9 | "测试全绿说明类型也没问题" | Babel 路径下**类型错误不会让测试失败**。需要 ts-jest 或单独 `tsc` |
| 10 | "测内部 state 更精确" | 官方明确列为**应当避免的四类实现细节**之一 —— 它会在正确重构中变红 |
| 11 | "`getByTestId` 最稳定，所以最该用" | 官方把它排在优先级**最后**："用户看不到（也听不到）这些" |
| 12 | "`getByPlaceholderText` 和 label 差不多" | 官方："**placeholder 不是 label 的替代品**"，仅在别无他法时用 |
| 13 | "`getByRole` 查不到就是测试写错了" | 官方：**可能意味着你的 UI 存在无障碍问题**。于是组件测试顺带成了无障碍检查 |
| 14 | "查询到多个元素会用第一个" | **`get` / `query` / `find` 在 >1 个匹配时一律抛错**（除 `*AllBy*`）。这是刻意的：强迫面对歧义 |
| 15 | "用 `getBy` 断言元素不存在" | 会抛错导致"失败得莫名其妙"。断言不存在应当用 **`queryBy`**（返回 `null`） |
| 16 | "要等待就手写 `waitFor` + `expect`" | 用 `findBy*`（= `getBy*` + `waitFor`）。**错误信息更准**：一个说"找不到"，一个说"等超时" |
| 17 | "`exact: false` 比正则方便" | 官方更推荐用正则；且 `exact` 对正则/函数参数**无效** |
| 18 | "`opacity: 0` 的元素点不到" | Playwright 官方：**`opacity: 0` 仍算可见**。要隐藏得用 `visibility: hidden` / `display: none` |
| 19 | "所有断言都会自动重试" | 只有**自动重试断言**会。先取文本再用 `toBe` 比较，就丢掉了等待能力 —— 这是变 flaky 的常见路径 |
| 20 | "用 `press()` 更稳，因为它不用等可见" | 它**绕过了可见性与遮挡检查**。"键盘能操作"≠"鼠标能操作" |
| 21 | "`force: true` 能解决点击失败" | 它**放弃了"元素真能被点到"这个保证** —— 而那正是 E2E 的主要价值 |
| 22 | "Cypress 和 Playwright 只是语法不同" | 架构不同：Cypress **与应用在同一 run loop 中执行**（另有一个浏览器外的 Node 进程）；Playwright 通过驱动协议 |
| 23 | "Cypress 支持所有主流浏览器" | 本次核验的官方页只写了 **Firefox 与 Chrome 系（含 Edge）**，**完全未提 Safari/WebKit**。本章不外推 |
| 24 | "视觉回归红了就更新快照" | 这个动作会**把真实变化一起更新掉**，并训练出"红就点更新"的肌肉记忆 |
| 25 | "测试数据用真实的更可信" | 真实数据会漂移，且脱敏本身是风险。推荐**工厂函数为主 + 少量 fixture 守住真实形状** |
| 26 | "本地跑绿就行了" | **时区/locale/时间/随机**是"本地绿 CI 红"的头号来源。这些必须显式冻结 |
| 27 | "E2E 里把所有请求都拦截最稳" | 那样它**失去了"真实"这个唯一优势**，与组件测试的差别只剩"环境更重"。**主路径不要拦截** |
| 28 | "为了覆盖率数字补测试" | 会产出"执行了但没断言"的测试 —— 增加维护成本，不增加信心 |

> **本章核验到的官方事实（2026-10-17）**：
> - **Jest 30.5（最后更新 2026-08-28）**：**"Vite 不受支持"**（与 Vite 插件系统不兼容，`vite-jest` 不兼容 Vite > 2.4.2），**替代方案是 API 兼容 Jest 的 Vitest**；纯 CJS 零配置；`babel-jest` 自动安装；TS 走 Babel（**只转译不做类型检查**）或 ts-jest。
> - **Vitest v5.0.5**：定位"由 Vite 驱动"；默认读 `vite.config.*`，"现有插件与配置开箱即用"；**`vitest.config.*` 存在时 `vite.config.*` 全部选项被忽略**；要求 **Vite >= 6.4.0 / Node >= 22.12.0**；`coverage.enabled` **默认 false**、`coverage.provider` **默认 `'v8'`**、`coverage.include` **默认=被导入的文件**、`reportsDirectory` 默认 `./coverage` 且 clean 默认 true；**阈值支持负数 = 未覆盖条数上限**；**glob 分组不继承顶层阈值**。
> - **Testing Library**：核心理念"测试越接近使用方式，信心越多"；**四类应避免的实现细节**（内部 state / 方法 / 生命周期 / 子组件）；**查询优先级三层**（Accessible to Everyone → Semantic → Test ID）；`getByRole` "几乎所有场景的首选，**取不到可能说明 UI 有无障碍问题**"；`getByTestId` "用户看不到也听不到"；**get/query/find 语义表**（find 默认 1000ms 超时且重试，>1 匹配一律抛错）；**推荐用 `screen`**；`exact` 默认 true；默认空白归一化。
> - **Playwright**：定位"打包 runner/assertions/isolation/parallelization/tooling"；**默认 headless 并行跑 Chromium/WebKit/Firefox**；**auto-waiting = 执行前五项可操作性检查**（Visible / Stable / Enabled / Editable / Receives Events），**`opacity: 0` 仍算可见**、**零尺寸不算**、**Stable = 连续两帧边界框相同**、**Receives Events = 未被遮挡**；各操作对应检查项表；`force` 关闭非必要检查；**断言是 auto-retrying**。
> - **Cypress（2026-09-20 更新）**：定位"**质量平台**"；架构"**与你的应用在同一 run loop 中执行**"（对比 Selenium 的"浏览器外发远程命令"），**另有浏览器外的 Node 进程**；浏览器仅明确 **Firefox + Chrome 系（含 Edge）**。
>
> **四处如实标注的缺口**：① **Jest 页完全未提 ESM**，也未提 `testEnvironment` 与 snapshot testing；② **Vitest Coverage 页未给 v8 与 istanbul 的优劣对比**；③ **Playwright 的 actionability 页未给默认超时数值**，且 `toHaveScreenshot` 的 API 语义**不在所核验页面**；④ **Cypress 页未提 Safari/WebKit**，且 **`retry-ability` 的定义不在该页**（本章据此不外推）。
