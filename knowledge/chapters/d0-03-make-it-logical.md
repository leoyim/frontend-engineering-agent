## 3.1 值、类型与转换：ECMA-262 的底层模型

### 语言类型只有八种

ECMA-262 的《Language Types》把值分成八类：

| 类型 | 说明 | 例子 |
|---|---|---|
| Undefined | 唯一值 `undefined` | 未赋值的变量 |
| Null | 唯一值 `null` | 显式表示"无对象" |
| Boolean | `true` / `false` | — |
| String | 不可变的 UTF-16 码元序列 | `"abc"` |
| Symbol | 唯一且不可变，可作属性键 | `Symbol("id")` |
| Number | **IEEE 754 双精度 64 位浮点** | `42`、`0.1` |
| BigInt | 任意精度整数 | `42n` |
| Object | 其余一切（含数组、函数） | `{}`、`[]` |

**前七种不是对象**（常说的"原始类型"），只有第八种是。

### 为什么 `0.1 + 0.2 !== 0.3`

不是"精度 bug"，而是**表示能力的必然结果**。Number 的规范值就是 IEEE 754 双精度浮点：1 位符号 + 11 位指数 + 52 位有效数字。

`0.1` 与 `0.2` 在二进制下都是**无限循环小数**，只能截断存储。两个近似值相加后，结果落在最近的另一个近似值上：

```js
0.1 + 0.2                 // 0.30000000000000004
0.1 + 0.2 === 0.3         // false
Number.EPSILON            // 2.220446049250313e-16，相邻 1 与下一个可表示数之差
```

由此推出三条实践结论：

- **金额一律用整数最小单位**（分）或字符串计算，不用浮点。
- **比较浮点用容差**：`Math.abs(a - b) < Number.EPSILON`，而不是 `===`。
- **安全整数范围是 ±(2^53 − 1)**，即 `Number.MAX_SAFE_INTEGER`。超出后用 `BigInt`。

另外两个 IEEE 754 的直接后果：`NaN` 不等于任何值（包括自身），所以判断要用 `Number.isNaN()`；`-0` 存在且 `Object.is(-0, 0)` 为 `false`。

### 值语义与引用语义

这一条决定了"改了为什么会串"：

```js
let a = 1, b = a;   b = 2;   // a 仍是 1        —— 复制的是值
let o = {}, p = o;  p.x = 1; // o.x 也是 1     —— 复制的是引用（指向同一对象）
```

对象赋值不复制内容，只复制"指向对象"的引用。所以"想改副本"必须显式复制：`{ ...o }`（浅拷贝）、`structuredClone(o)`（深拷贝）。

### 类型转换是规范定义的算法，不是"玄学"

ECMA-262 为每一次转换都定义了**抽象操作**（abstract operation）。记住这几个名字，一切转换都有确定答案：

| 抽象操作 | 何时触发 | 关键规则 |
|---|---|---|
| `ToBoolean` | 条件判断 | 只有 7 个**假值**：`undefined` `null` `false` `+0` `-0` `NaN` `""`。其余全真（包括 `[]` `{}` `"0"`） |
| `ToPrimitive` | 需要原始值时 | 先试 `Symbol.toPrimitive`，再 `valueOf`，再 `toString` |
| `ToNumber` | 算术运算 | `""` → 0；`"12abc"` → NaN |
| `ToString` | 字符串拼接 | 对象会走 `ToPrimitive` |

**`==` 与 `===` 的差别就在规范层面**：

| 运算符 | 规范算法 | 行为 |
|---|---|---|
| `===` | **Strict Equality Comparison** | **不做**类型转换，类型不同直接 false |
| `==` | **Abstract Equality Comparison** | 类型不同时按规则转换后再比 |

于是这些"奇怪"结果都有确定解释：

```js
null == undefined      // true   —— 规范中二者互等，这是唯一"跨类型相等"的特例
null === undefined     // false
"1" == 1               // true   —— String 被 ToNumber
[] == false            // true   —— 双方都转成 0
0 == ""                // true
```

**实践结论：默认用 `===`**。`==` 只有一个安全的常见用法——`x == null` 同时判 `null` 与 `undefined`。

### 运算符返回的是操作数，不是布尔值

```js
"a" && "b"        // "b"    —— 返回操作数，不是 true
0 || "default"    // "default"
"" ?? "fallback"  // ""     —— ?? 只对 null/undefined 回退
```

`??` 与 `||` 的差别是**触发条件**：`||` 对全部 7 个假值回退，`??` 只对 `null` / `undefined` 回退。所以"用户填了 0 就不该被覆盖"这种场景必须用 `??`。

另外注意 `typeof null === "object"`——这是规范早期实现留下的历史结果，无法修正（会破坏既有代码），只能记住。

## 3.2 作用域、提升与 TDZ：词法环境模型

### 作用域是规范里的数据结构

作用域在规范中叫**词法环境**（Lexical Environment），它由**环境记录**（Environment Record）和一个指向外层的引用组成。变量查找 = 沿这条链上行，直到全局环境。

**所以"作用域"不是抽象的比喻，而是可以逐字实现的对象结构。**

### "提升"不是把代码搬到顶部

这是最普遍的错误理解。真实机制是**实例化阶段**（Instantiation）：进入一个作用域时，引擎先扫描声明并创建绑定，然后才逐句执行代码。

不同声明方式在实例化阶段的行为完全不同：

| 声明 | 实例化阶段做什么 | 结果 |
|---|---|---|
| `var` | 创建绑定，**初始化为 `undefined`** | 声明前访问得到 `undefined`（这就是"提升"） |
| 函数声明 | 创建绑定，**初始化为函数对象** | 声明前**可以调用** |
| `let` / `const` | 创建绑定，但**不初始化** | 声明前访问**抛 `ReferenceError`** |
| `class` | 同 `let` | 声明前访问抛错 |

### TDZ 的准确含义：存在，但未初始化

**暂时性死区**（Temporal Dead Zone）不是"变量不存在"，而是：

> **绑定已经创建了，但它处于 uninitialized 状态；在初始化完成前访问它 → `ReferenceError`。**

这个区别有实际后果——TDZ 是**词法位置**决定的，不是时间先后：

```js
// 抛 ReferenceError：函数在 TDZ 期间被调用
function f() { return x; }
f();                  // ← 此时 x 还没初始化
let x = 1;

// 正常：函数在初始化之后才被调用
let y = 1;
function g() { return y; }
g();                  // 1
```

也就是说，**问题不在于"函数定义在哪"，而在于"函数被调用的那一刻，绑定初始化了没有"。**

`typeof` 也挡不住 TDZ：`typeof undeclaredVar` 安全返回 `"undefined"`，但 `typeof x` 在 TDZ 中会抛错。

### 块级作用域与 `let` 修复的经典问题

```js
for (var i = 0; i < 3; i++) setTimeout(() => console.log(i));  // 3 3 3
for (let i = 0; i < 3; i++) setTimeout(() => console.log(i));  // 0 1 2
```

机制差异在**绑定数量**：`var` 的绑定属于函数/全局环境，三个回调共享同一个 `i`；而 `let` 在 `for` 循环中**每次迭代创建一个新的绑定**，并把上一次的值复制进新绑定。所以三个回调各自捕获了不同的环境。

（这叫"每次迭代环境"（per-iteration environment），是规范为 `for` + `let` 定义的专门行为，不是 `let` 的通用性质。）

## 3.3 函数：三种写法与参数机制

### 三种声明方式的差异来自规范

| 写法 | 提升 | 有自己的 `this` | 可作构造函数 |
|---|---|---|---|
| 函数声明 `function f() {}` | **有**（实例化阶段初始化为函数对象） | 有（动态） | 可以 |
| 函数表达式 `const f = function () {}` | 无（按 `const` 规则进 TDZ） | 有 | 可以 |
| 箭头函数 `const f = () => {}` | 无 | **没有**（取定义处外层的 `this`） | **不可以** |

箭头函数"没有自己的 `this`"不是省略，而是规范规定它**不定义 `[[ThisMode]]` 为 lexical 以外的模式**——它没有 `this` 绑定，访问 `this` 时沿作用域链找。这一条带来的连锁后果（不能作构造函数、没有 `arguments`、不能用作 `yield` 的宿主）在D0 第 4 章展开。

### 参数：默认值、剩余参数、`arguments`

```js
function f(a, b = 2, ...rest) {
  return [a, b, rest];
}
f(1, undefined, 3, 4);   // [1, 2, [3, 4]]
```

- **默认值只在实参为 `undefined` 时生效**（传 `null` 不会触发默认值）。
- **`...rest` 是真正的数组**，而 `arguments` 是"类数组对象"（有 `length` 与索引，但没有数组方法，也不是 `Array` 实例）。
- 参数与 `arguments` 的映射关系在**严格模式下会断开**——这就是"用剩余参数更好"的原因之一。

### 函数是对象

函数是 `Object` 类型的实例，因此可以有属性：`length`（形参个数，不含默认值与剩余参数）、`name`（推导出的函数名）。这使得"把函数当值传递"在规范层面完全自然。

## 3.4 数组与对象：方法分类与迭代协议

### 数组是"特殊对象"

数组的索引本质是**字符串属性键**（`arr[0]` 等价于 `arr["0"]`）；`length` 是特殊属性——**写入它会截断元素**。理解这一点就能解释：

```js
const a = [1, 2, 3];
a[5] = 6;          // [1, 2, 3, <2 empty>, 6]  —— 不会报错，中间是"空槽"
a.length = 1;      // [1]                     —— 直接截断
```

### 分类方法：变更 vs 非变更

这是数组方法最该记住的分类维度，因为它直接决定"原数组有没有被改"：

| 类别 | 方法 | 特征 |
|---|---|---|
| **非变更**（返回新数组） | `map` `filter` `slice` `concat` `flat` `flatMap` `toSorted` `toReversed` | 原数组不变，适合链式组合 |
| **变更**（原地修改） | `push` `pop` `shift` `unshift` `splice` `sort` `reverse` `copyWithin` | 直接改原数组 |

**`sort` 默认按字符串比较**，这是常见 bug 的来源：

```js
[10, 9, 100].sort();              // [10, 100, 9]   —— 按字符串序
[10, 9, 100].sort((a, b) => a - b); // [9, 10, 100] —— 必须给比较函数
```

`reduce` 的语义需要记准：`(累加器, 当前值) => 新累加器`，加上可选的**初值**。不给初值且数组为空会抛 `TypeError`。

### 遍历方式：机制完全不同

| 写法 | 依据什么遍历 | 关键差异 |
|---|---|---|
| `for (let i…)` | 索引 | 最原始，可精确控制步进与中断 |
| `for...of` | **迭代器协议**（`Symbol.iterator`） | 遍历"值"，可遍历任何可迭代对象；普通对象不可迭代 |
| `for...in` | **可枚举属性**（含原型链上继承的） | 遍历"键"，且会拿到继承属性——基本不该用于数组 |
| `forEach` | 回调 | **不能 `break`**，也无法 `await` 中断 |

`for...of` 走的是**迭代器协议**：对象提供 `[Symbol.iterator]()`，返回带 `next()` 的迭代器。所以"哪些东西能 `for...of`"有确定答案：原生字符串、数组、Map、Set、`arguments`、NodeList 都可迭代；**普通对象不可迭代**（想遍历键用 `Object.keys`）。

### 对象与语法糖

```js
const { name, age: a = 18, ...others } = user;   // 解构：可重命名、可给默认值、可收集剩余
const merged = { ...a, ...b };                    // 展开：浅拷贝 / 合并
const list = items.map(({ id, title }) => `${id}: ${title}`);  // 参数处解构 + 模板字符串
user.address?.city ?? "未知";                      // 可选链 + 空值合并
```

**可选链 `?.` 是"短路"的**：`a?.b.c` 中若 `a` 是 `null`/`undefined`，整个表达式直接返回 `undefined`，`c` 的访问不会执行。这解释了它与 `a && a.b && a.b.c` 等价，但更短。

## 3.5 DOM 与事件：从接口到渲染管线

### DOM 不是 JavaScript

这一点必须先立正：**DOM 由 WHATWG 的 DOM Standard 定义，它是一组语言无关的接口**。JS 只是众多调用者之一（浏览器还允许在页面里用别的语言驱动 DOM）。

这解释了 TypeScript 里的一个现象：`document` 的类型来自 `lib.dom.d.ts`，**不来自 ECMA-262**——语言规范里根本没有 DOM。

### 树的两个视图

| 视图 | 遍历属性 | 包含什么 |
|---|---|---|
| 节点树 | `childNodes`、`parentNode` | 所有节点：元素、文本、注释 |
| 元素树 | `children`、`parentElement` | 只有元素 |

"为什么 `childNodes` 长度和我数的元素个数不一样"的答案就在这里——**文本节点也在其中**（换行与缩进产生的空白也是文本节点）。

### 改一次 DOM 为什么不立刻重排

这是本章第一个"渲染管线"接口。DOM 接口的调用本身是**廉价**的——它主要修改树结构并**把相关阶段标记为脏（dirty）**。真正昂贵的清算发生在浏览器下一次 **update the rendering** 时（HTML Standard《Event loops》中的一个步骤）。渲染须依次走过这些阶段：

```text
解析 → DOM → 样式计算（Recalc Style）→ 布局（Layout / 几何）→ 绘制（Paint / 生成绘制指令）→ 合成（Composite / 分层与合成）
```

线程分工（这是理解性能的前提）：

| 阶段 | 主要执行者 | 说明 |
|---|---|---|
| 样式计算、布局、绘制记录 | **主线程** | 与你的 JS、事件处理共享同一条线程 |
| 合成 | **合成线程** | 把已分层的图层合成输出 |
| 光栅化 | **光栅线程** | 把绘制指令转成像素 |

**关键推论**：只要你的 JS 还在跑，**渲染就排不上队**。这就是"长任务会卡住页面"的机制（见 本章 §3.6）。

### 强制同步布局：性能规则背后的机制

```js
el.style.width = "100px";        // 写：把布局标记为脏
const h = el.offsetHeight;       // 读：浏览器必须立刻清算布局才能给出准确值
```

第二行的读取迫使浏览器**提前**执行本可以批量延后的布局工作，这被称为**强制同步布局**（forced synchronous layout）。这就是"批量写、再批量读"（读写分离）这条性能规则的全部机制来源——不是玄学，而是"读几何属性需要最新的布局结果"。

### 事件：传播模型由 DOM Standard 定义

事件系统由 DOM Standard 的《Events》定义，核心是两个接口：`EventTarget` 与 `Event`。

```js
el.addEventListener("click", handler, { capture: false, once: false, passive: false });
```

**事件传播分三个阶段**：

```text
① 捕获阶段（capture）：从 window 自上而下，直到目标的父节点
② 目标阶段（target）：在目标自身触发
③ 冒泡阶段（bubble）：从目标的父节点自下而上，直到 window
```

`addEventListener` 的 `capture: true` 让处理器在**捕获阶段**执行——这就是"同一个事件，两个处理器执行顺序不同"的原因。

几个必须分清的区别：

| 概念 | 含义 |
|---|---|
| `event.target` | **实际触发**事件的最深元素 |
| `event.currentTarget` | **当前正在执行**处理器的元素（即挂载处） |
| `event.preventDefault()` | 阻止**默认行为**（链接跳转、表单提交），不影响传播 |
| `event.stopPropagation()` | 阻止**继续传播**，但同一元素上的其他监听器仍会执行 |
| `event.stopImmediatePropagation()` | 连同一元素上的其他监听器也一并阻止 |
| `{ passive: true }` | 声明"不会调用 `preventDefault`"，让引擎不必等 JS 就能开始滚动 |

### 事件委托：冒泡的直接应用

因为事件会冒泡，所以可以在**祖先**上挂一个处理器，通过 `event.target` 判断来源：

```js
list.addEventListener("click", (e) => {
  const item = e.target.closest("li");
  if (item) handle(item);
});
```

它解决两个真实问题：动态新增的子元素无需重新绑定；上百个子元素只占一个监听器。

### 事件处理器是"任务"

最后把这条接线到下一节：**事件处理器不是立即执行的函数调用栈延续，而是作为任务进入事件循环的队列**。这就是"为什么事件处理里抛出的错误不会被外层 `try/catch` 捕获"的原因（见 本章 §3.7）。

## 3.6 异步：任务、微任务与事件循环

### 单线程的准确含义

JS 只有一个**执行线程**，但浏览器不是单线程。准确说法是：**JS 执行、样式计算、布局、绘制记录共享主线程；合成与光栅化在别的线程。**

这解释了两件事：为什么长任务会**同时**卡住 JS 与渲染；为什么 `transform` / `opacity` 的动画可以比改 `width` 更流畅（前者可能只需合成线程参与，后者必然触发主线程的布局）。

### 事件循环的一次迭代

HTML Standard 的《Event loops》定义了处理模型，简化后可写成三步：

```text
① 从任务队列取出一个任务并执行（事件回调、setTimeout 到期、网络回调……）
② 执行「微任务检查点」：清空微任务队列 —— 全部执行完，且执行期间新增的微任务也要执行
③ 若到了渲染时机 → update the rendering（样式计算 → 布局 → 绘制 → 合成）
```

**顺序是硬性的**，由此可以推出本章最重要的一条结论。

### 任务 vs 微任务

| | 任务（task，常称宏任务） | 微任务（microtask） |
|---|---|---|
| 典型来源 | `setTimeout` / `setInterval`、事件回调、网络回调、`MessageChannel` | **Promise 的回调**（`then` / `catch` / `finally`）、`queueMicrotask`、`MutationObserver` |
| 每轮执行几个 | **一个** | **全部清空** |
| 相对渲染的位置 | 在渲染之前 | **也在渲染之前**，且比下一个任务更早 |

于是这条常被当作"面试题"的结论有了机制解释：

```js
setTimeout(() => console.log("timeout"), 0);

Promise.resolve().then(() => console.log("promise"));

console.log("sync");

// 输出顺序：sync → promise → timeout
```

**理由**：`sync` 在首个任务（脚本求值）里执行；脚本任务结束后进入微任务检查点，Promise 回调在此执行；`setTimeout` 的回调是**下一个任务**，要等微任务队列排空之后才轮到。

### Promise 的机制要点

| 特性 | 含义 |
|---|---|
| 三种状态 | `pending` → `fulfilled` / `rejected`，**单向不可逆** |
| 回调时机 | 状态变更时把回调作为**微任务**入队（不是立即调用） |
| `then` 的返回值 | 返回**新的** Promise —— 这是能链式调用、能"传递值"的原因 |
| 拒绝的传播 | 沿链向下传递，直到遇到带 `onRejected` 的 `then` 或 `catch` |
| `finally` | 不接收值、不改变传递结果 |

`async` / `await` 是 Promise 的**语法糖**：

```js
async function f() {
  const r = await g();   // 等价于 g().then(r => …后续代码)
  return r;
}
```

`await` 之后的代码等价于放在 `then` 回调里——**所以它走微任务队列**，不是"同步续跑"。

### 与渲染的关系：长任务与活锁

- **长任务**：一个任务执行时间过长，事件循环无法进入第 ③ 步，页面看起来"卡住"。
- **微任务活锁**：微任务里无限追加微任务，检查点永不清空，渲染**永远等不到**。这与"死循环"的差别是：它依然能响应任务队列以外的调度，但页面不再更新。
- 由此得到一条实用规则：**把长计算切片**，让出主线程（分片、`requestIdleCallback`、或移入 Worker）。D0 第 5 章会展开。

## 3.7 错误：抛出、捕获与边界

### 错误对象与类型

| 类型 | 典型触发 |
|---|---|
| `SyntaxError` | 语法解析失败（多数在**解析阶段**就抛出，`try/catch` 根本来不及） |
| `TypeError` | 对错误类型的值做操作，如调用 `undefined()` |
| `ReferenceError` | 访问未声明变量，或访问 TDZ 中的绑定 |
| `RangeError` | 数值越界，如 `new Array(-1)` |
| `URIError` | `decodeURIComponent("%")` |

**注意第一行**：语法错误发生在解析期，整段脚本都不会执行，所以**包一层 `try/catch` 是没用的**。

### `throw` 可以抛任意值，但只有 `Error` 有 `stack`

```js
throw "字符串错误";      // 合法
throw new Error("好一些"); // 有 stack 与类型
```

抛非 `Error` 会丢掉堆栈信息，排障时只能靠猜——所以规范做法是抛 `Error` 的子类。

### `try` / `catch` / `finally` 的执行顺序

`finally` **一定执行**，且它能"吞掉"控制流：

```js
function f() {
  try { return 1; }
  finally { return 2; }   // 覆盖前面的 return
}
f();  // 2
```

这是规范里 `finally` 块中完成记录（Completion Record）覆盖规则的结果——**知道规则，就不会把它当 bug**。

### 核心：错误的传播边界

这是异步编程里最容易出错的地方。判断标准只有一个：**错误发生时，与外层 `try` 是不是同一个调用栈？**

| 错误发生位置 | 外层 `try/catch` 能捕获吗 | 为什么 |
|---|---|---|
| 同步代码 | **能** | 同一调用栈 |
| `setTimeout` 回调内 | **不能** | 回调是**另一个任务**，调用栈已不同（错误会冒到全局 `error` 事件） |
| `Promise` 的 `then` 回调内 | **不能** | 它变成**下一个 Promise 的拒绝** |
| `async` 函数体内（`await` 之外） | 不能直接捕获 | 变成该函数返回的 Promise 的拒绝 |
| `async` 函数内 `await` **外层**包 `try` | **能** | 等价于把 `catch` 挂在 Promise 链上 |
| 未处理的 Promise 拒绝 | 不能 | 触发全局 `unhandledrejection` 事件 |

**结论**：异步代码必须让错误**沿 Promise 链传播**，而不是依赖外层 `try`：

```js
// 反例：错误逃逸
try { setTimeout(() => { throw new Error("x"); }, 0); } catch (e) { /* 永远不会执行 */ }

// 正例：在异步链路内部捕获
setTimeout(() => {
  try { risky(); } catch (e) { report(e); }
}, 0);

// 正例：Promise 链上捕获
fetch("/api").then(r => r.json()).catch(report);

// 正例：await 外层 try
async function load() {
  try { return await fetch("/api"); } catch (e) { report(e); }
}
```

## 3.8 模块：静态结构与"只求值一次"

### `import` / `export` 是语法，不是函数

```js
import { readFile } from "./fs.js";   // 声明
export const VERSION = "1.0";         // 声明
```

因为它是**语法声明**，所以有三条硬约束：

| 约束 | 后果 |
|---|---|
| 只能出现在模块顶层 | 不能写在 `if` 里、不能写在函数里 |
| `import` 声明被**提升** | 无论写在文件哪一行，导入在模块求值前就已解析完成 |
| 导入名是**只读**的 | `import` 进来的绑定不能重新赋值（重新导出请用 `export`） |

**第二条正是"能被静态分析"的根本原因**——工具不必运行代码，只看语法就能算出依赖图。这是 D2 领域 Tree Shaking 的全部前提，也是 ESM 与 CJS 的关键分野。

### 模块作用域不是全局作用域

| 差异 | 说明 |
|---|---|
| 顶层 `var` / 函数声明 | **不会**成为 `window` 的属性（脚本文件会） |
| 严格模式 | 模块**自动**处于严格模式 |
| 顶层 `this` | 是 `undefined`（脚本里是 `window`） |
| 求值次数 | **同一模块只求值一次**，结果被缓存（Module Record） |

"只求值一次"带来两个可观测现象：**模块天然是单例**（适合放配置与共享状态）；**循环依赖时可能拿到尚未初始化的绑定**——因为 ESM 的导入是**实时绑定（live binding）**，不是值拷贝，所以读到的是"那个绑定此刻的值"。

### 与 CJS 的一句话差别（详见 D2 领域）

| | ESM（`import` / `export`） | CJS（`require` / `module.exports`） |
|---|---|---|
| 本质 | **语法声明**，静态可分析 | **运行时函数调用** |
| 依赖图 | 运行前即可算出 | 执行到那一行才知道 |
| 能否摇树 | 能 | 只能保守处理 |

## 本章小结

**七条最该记住的结论**

1. **一切类型转换都是规范定义的抽象操作**（`ToBoolean` / `ToPrimitive` / `ToNumber` / `ToString`）。转换不神秘，`==` 与 `===` 的差别就是"要不要走 `Abstract Equality Comparison`"。
2. **"提升"是实例化阶段创建绑定的结果**，不是代码搬移。`var` 初始化为 `undefined`，函数声明初始化为函数对象，`let` / `const` 保持未初始化 —— 这就是 TDZ。
3. **DOM 是语言无关的规范接口**，不是 JS 的一部分。**修改 DOM 只是标记脏**，昂贵的清算发生在事件循环的 `update the rendering` 步骤。
4. **渲染与 JS 共享主线程**，合成与光栅在别的线程。这同时解释了"长任务卡页面"与"为什么 `transform` 动画更流畅"。
5. **事件循环的顺序是硬性的**：一个任务 → 清空微任务 → 可能渲染。所以 Promise 回调一定早于 `setTimeout`。
6. **错误的传播边界由调用栈决定**：异步错误逃出外层 `try`。异步代码必须让错误沿 Promise 链传播。
7. **`import` 是语法声明**，因此可静态分析、被提升、不能条件化、且同一模块只求值一次——这些是后续 Tree Shaking 与模块体系讨论的前提。
