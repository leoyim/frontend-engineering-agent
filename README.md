# 前端工程化学习助手

一个**真能跑起来**的分节互动教学应用：对话界面 + 大模型调用 + 学习状态持久化。
零第三方依赖，只用 Node 内置模块，`node server.js` 即可启动。
界面按初学者友好来设计：三步上手引导、随进度变化的鼓励语、每完成一节放礼花、
全部学完放烟花。

它把《前端工程化：从底层原理到工程实践》那份电子书当作检索语料，
按「讲解 → 提问 → 批改 → 确认闸门 → 推进」的节奏带学习者走完 **10 个领域、42 章**：
D0 入门（HTML/CSS/JS/浏览器/网络）→ D1 规范与协作 → D2 语言与模块化 → D3 构建与打包 → D4 样式工程 → D5 质量与测试 → D6 交付与运维 → X1 脚手架 → X2 架构模式 → X3 AI 与工程化。

## 快速开始

```bash
cd frontend-build-tutor-app
node server.js
```

打开 http://localhost:7310 ，点右上角「模型设置」填模型，然后输入「开始第 1 节」。

要求 Node ≥ 20（用到内置 `fetch` 与 `AbortController`）。无需 `npm install`。

端口可用环境变量改：`PORT=8080 node server.js`。

## 配置大模型

应用走 **OpenAI 兼容接口**，自带 key 或指向本地 Ollama 都行。设置弹窗里有四个预设：

| 预设 | Base URL | 模型名示例 |
|---|---|---|
| 本地 Ollama | `http://localhost:11434/v1` | `qwen2.5:7b` |
| DeepSeek | `https://api.deepseek.com/v1` | `deepseek-chat` |

| 智谱 GLM | `https://open.bigmodel.cn/api/paas/v4` | `glm-4-flash` |

任何接口响应里都只有 `hasApiKey: true` 和 `apiKeySource`，不会把密钥下发到浏览器。
`data/` 下的运行时文件已在 `.gitignore` 里逐个排除。

填完可以点「测试连通性」直接验证 —— 它会真的发一次请求过去。

## 知识库从哪来

语料作为**数据元随应用一起提交**，放在项目内的 `knowledge/`：

```
frontend-build-tutor-app/
├── knowledge/             ← 语料源（66 个 Markdown：42 章正文 + 术语/配置参考/习题等）
├── public/                ← 这整个目录就是静态站点，能直接托管
│   ├── index.html         ← 站点根：一个跳转页
│   ├── CNAME              ← 自定义域名 app.leoyim.cn
│   └── frontend-agent/   ← 应用本体住在这里
│       ├── index.html
│       ├── core.js        ← Node 与浏览器共用的内核
│       ├── client-backend.js  ← 静态形态的后端（浏览器内）
│       ├── app.js
│       ├── knowledge.json ← 由 knowledge/ 生成，两端共用
│       └── ...
├── tools/build-knowledge.js
└── server.js              ← 服务端形态；只在用它时才有后端
```

**为什么应用要下沉一层。** 线上地址是 `app.leoyim.cn/frontend-agent/`。
GitHub Pages 一旦给仓库配上自定义域名，URL 里的「仓库名」那一段就会消失、站点整体
平移到域名根 —— 没法既用自定义域名、又靠 Pages 自动得到这条路径。所以把路径做成
真实的目录结构：应用住在 `frontend-agent/` 里，站点根只放一个跳转页。

代价是路径在几个地方被硬编码，改目录名时要一起改：`tools/build-knowledge.js`（输出位置）、
`server.js`（`APP_DIR` 常量、静态目录、知识库文件、`/api` 前缀）、两个 workflow 的自检断言。
`APP_DIR` 在 `server.js` 里是常量，本地服务的路由也跟着它走 —— 这样本地与线上形态一致，
「子路径下相对路径探测后端」这类只在线上才暴露的问题，本地同样会碰到。

早先这里是「就地读取同级的 `frontend-build-learning-book/`」，理由是不复制、避免双份真相。
但那个方案有个前提：应用必须和电子书并排放着。**一旦要部署到服务器、只带走应用本身，
这个前提就不成立了** —— 仓库里没有那份语料，应用启动后检索到 0 个片段，
系统提示词里的资料区会退化成「本轮未检索到相关资料」，模型只能靠自身知识作答，
而且**界面和日志都不会报错**。

所以现在把语料放进 `knowledge/`，应用自包含。代价是这份拷贝只在应用仓库里维护，
不再跟随电子书仓库更新 —— 换来的是可部署性，以及「不会静默退化成空检索」。

同级的 `frontend-build-learning-book/` 回退已从 `resolveKnowledgeDir()` 里移除：
留着它就等于允许出现「应用指向的书和仓库里的书不是同一份」这种状态。

### 语料要先预处理成 knowledge.json

浏览器读不了目录，只能读一份提前准备好的数据。所以分块不在运行时做，而是构建时做一次：

```bash
npm run build:course      # knowledge/chapters/*.md -> core.js 的 COURSE（42 章 / 10 领域）
npm run build:knowledge   # knowledge/*.md -> public/frontend-agent/knowledge.json
```

**服务端也读这份生成物**，不是自己遍历 `knowledge/`。这是刻意的：如果两端各有一套
「遍历目录 + 过滤 + 按标题分块」的规则，它们迟早会分叉，之后同一个问题在本地跑和
部署到 Pages 上会检索到不同资料，而两边都不会报错。分块规则的唯一实现在
`public/frontend-agent/core.js` 的 `chunkMarkdown()`，构建脚本调的就是它。

代价是引入了一个构建步骤。为了不让它变成隐性陷阱：

- 启动时会打印告警，如果 `knowledge/` 里的 Markdown 比生成物
  `public/frontend-agent/knowledge.json` 新
- CI 会重新生成一遍并 `git diff`，不一致直接失败

启动日志会打印实际使用的目录和分块数；`GET /api/health` 也会返回 `knowledgeChunks`。
**这个数是 0 就说明语料没接上**，CI 里对它做了断言。

想把书里某个章节从检索里排除，把文件名加进 `server.js` 的 `KB_EXCLUDE_FILES`；
想整体排除某个目录，在 `loadKnowledge()` 的 `walk()` 里加一行 `continue`。

## 按需组课：模型选范围，代码排顺序

书稿扩到 10 个领域、179 个知识点后，"固定一张 42 章课表"只是**默认路径**，不是唯一路径。
界面右上角的 **「按需组课」** 可以按领域 / 层级 / 上限生成一条**满足前置依赖**的路径。

关键设计是把一件事**拆给两个角色**：

| 谁 | 做什么 | 为什么 |
|---|---|---|
| 模型 / 用户 | 决定**学哪些**（判断） | 这是需求问题，只有人和模型知道 |
| `assemblePlan()` | 前置闭包 + 拓扑排序（正确性） | 让模型即兴排序会偶发"跳前置、顺序反了"，且难以发现 |

三条硬规则（都在 `core.js` 的 `assemblePlan` 注释里）：

1. **闭包只往前置方向扩**，绝不拉后继 —— 学 X 不会顺手把 X 的所有后续都塞进来。
2. **顺序取全局拓扑序**（`nodes.json` 的 `order`），因此同一份输入永远排出同一序列，可复现。
3. **上限是软约束**：明确目标时**不删目标**（删了路径就不成立），装不下就照实返回全量并回报 `needed`；
   只给范围时才缩小范围去凑上限。裁剪按"离目标的距离"而不是"层级高低" ——
   后者会把目标本身砍掉，出现"要 D5 的 L3，结果计划里一个 D5 都没有"。

数据源是 **`nodes.json`（179 节点 / 前置边 / 4 个入口）**，由 `tools/build-nodes.js` 从
`knowledge/KNOWLEDGE_MAP.md` 生成，并在生成时校验三条不变量：**悬空前置 0、依赖环 0、层级倒挂 0**。

```bash
npm run build:nodes      # 地图 -> nodes.json（含校验）
```

### 两种模式并存（2026-10-19 起）

组课不是"看一眼就算"，它会真的**切到计划模式**；两种模式**各存各的进度**：

| 模式 | 课表 | 分母 | 完成记录存在 |
|---|---|---|---|
| **章表** | 固定 42 章 | 42 | `progress.completed` |
| **计划** | 组装出来的一条节点路径 | 该路径的节数 | `progress.completed_plan` |

**为什么进度要分两份**：一份进度里混着"章的 id"和"节点的 id"，分母就说不清了 ——
切回章表时进度会突然从 3/24 变成 3/42，使用者会以为数据坏了。分开存之后，
**来回切换是无损的**，各自的进度原地保留。

**切换必须明确提示**：`setCourseMode()` / `applyPlan()` 都返回一句提示（含"已完成 N/M"），
由后端原样播报，界面同时更新进度条、分母与课表 —— 这条是用户明确要求的，
因为"分母变了而没人说"比"没有这个功能"更让人困惑。

**入口有两个**：

- 界面：侧栏「章表 / 计划」开关；「按需组课」弹窗生成后直接切入计划模式。
- 模型：在状态补丁里带 `plan` 字段（见系统提示词的补丁协议），由程序组装后切换。
  模型只决定"学哪些"，**排序与闭包永远由代码算**。

## 两种交付形态

同一份 `public/` 可以直接扔到任何静态托管上跑。前端启动时探测一次
`api/bootstrap`：

| 探测结果 | 走哪个后端 | 密钥在哪 | 状态存在哪 | 语料从哪读 |
|---|---|---|---|---|
| 200 + JSON | `server.js` 的 `/api/*` | 服务端文件 / 环境变量 | `data/*.json` | `knowledge/`（经生成物） |
| 404 | `client-backend.js`（浏览器内） | **使用者的浏览器** localStorage | localStorage | `public/frontend-agent/knowledge.json` |

探测用的是相对路径 `api/bootstrap`，所以在 `/frontend-agent/` 这类子路径下同样成立
（服务端会把该子路径下的 `/api/*` 一并接住）。除了存储介质，两边跑的是**同一份内核**
（`public/frontend-agent/core.js`）：课程结构、状态补丁、
BM25 检索、系统提示词、模型调用。这是刻意的 —— 如果各写一份，同一个问题在本地跑和
部署在 Pages 上会得到不同结果，而且不会报错。

### 部署到 GitHub Pages

Pages 只能托管静态文件，没有进程、没有服务端语言、没有可写磁盘。
所以它跑的是上表第二行那个形态，`.github/workflows/pages.yml` 已经把这件事做好了：

1. 仓库 Settings → Pages → Source 选 **GitHub Actions**
2. push 到 `main`，工作流会：校验语料生成物是最新的 → 检查应用文件齐备、站点根跳转目标正确、
   资源引用都是相对路径 → 把 `public/` 作为产物发布

本项目配了自定义域名 `app.leoyim.cn`（产物里的 `public/CNAME`），应用地址是
`https://app.leoyim.cn/frontend-agent/`。不配自定义域名时则是
`https://<用户名>.github.io/<仓库名>/frontend-agent/`，站点根会跳转到它。

首次打开会提示配置模型 —— 填自己的 API Key，它只存在**你自己的浏览器**里，
由浏览器直接发往模型服务，站点本身不持有也不转发任何密钥。

三点必须先知道：

- **访问者要自备 API Key。** 静态站点没有服务端可以替你保管密钥，这是静态托管的固有代价。
  自己用没问题；发给别人时，对方要么自己填，要么你换成有服务端的部署方式。
- **模型服务必须允许浏览器直连（CORS）。** DeepSeek / OpenAI 都开放；自建或内网服务
  往往不开放，那种情况下静态版会失败。报错信息里已经写了这个排查方向。
- **换浏览器或清除站点数据后，进度、对话、密钥都会没。** 它们都在 localStorage 里。

### 部署到有服务端的环境

需要密钥保存在服务端、或多设备共享进度时，用这个形态。任何能跑 Node ≥ 20 的地方都行：

```bash
PORT=7310 \
KNOWLEDGE_DIR=./knowledge \
LLM_BASE_URL=https://api.deepseek.com/v1 \
LLM_API_KEY=sk-xxxx \
LLM_MODEL=deepseek-chat \
node server.js
```

### 环境变量（仅服务端形态）

密钥优先走环境变量，而不是写进 `data/config.json`：

| 变量 | 作用 | 默认 |
|---|---|---|
| `PORT` | 监听端口 | `7310` |
| `KNOWLEDGE_DIR` | 语料目录 | `./knowledge` |
| `LLM_BASE_URL` | OpenAI 兼容地址 | 空（界面里配） |
| `LLM_API_KEY` | 密钥 | 空 |
| `LLM_MODEL` | 模型名 | 空 |
| `LLM_TEMPERATURE` | 温度 | `0.4` |
| `LLM_MAX_TOKENS` | 上限 | `2000` |

未设置的变量不参与覆盖，所以「只给密钥、地址仍在界面里配」也成立。

**密钥来源为环境变量时，磁盘上不留任何副本**：`saveConfig()` 会主动从
`data/config.json` 里删掉 `apiKey` 字段，界面填的也会被环境变量压住。
理由是同一把密钥不该散落在两处、其中一处还是明文躺在工作区里。
设置弹窗会显示「由服务器环境变量提供，界面上改不动」，避免使用者反复尝试保存。

无论密钥来自哪里，接口响应里都只有 `hasApiKey: true` 和 `apiKeySource`，
密钥本身永不下发给浏览器。

### 健康检查

`GET /api/health` 返回进程存活、运行时长、知识库分块数、模型是否已配置。
探针刻意**不查模型连通性** —— 模型服务抖动不该让整个实例被判为 unhealthy。

## 设计要点

### 1. 状态外置，不寄生在对话历史里

学习进度、待作答题目、学习者画像全部落在 `data/state.json`，对话记录落在 `data/history.json`。
进程重启、开新会话、刷新页面都不会丢。

**对话记录一开始是刻意不保存的**（理由：「它是过程，不是状态」）。这条分工后来被推翻了：
实际使用里，刷新后想回看上一轮讲过的原文、想想自己当时错在哪，全都拿不回来，
而学习恰恰依赖回看。所以现在对话和进度一样持久化，重置时一起清掉。

历史由**服务端持有**，不放在浏览器 localStorage：这个应用本来就是单用户、状态全在服务端，
历史放浏览器会让「换个浏览器就断片」，与「刷新或重启不丢」的承诺不一致。
`/api/chat` 不再接受前端传来的 context，服务端用自己落盘的那份 —— 两边都持有一份迟早会不一致
（比如刚重置过但页面还没刷新）。上限 `MAX_HISTORY = 400` 条，超出丢弃最早的。

先看看文件长什么样（第一次启动就会生成）：

```jsonc
{
  "progress": {
    "total_sections": 22,
    "progress_formula": "已完成节数 ÷ 总规划节数（三条齐才算完成：作答 + 批改 + 确认）",
    "completed": [{ "id": "M1.1", "title": "依赖图构建", "date": "2026-10-10" }],
    "current": "M1.2"
  }
}
```

注意 `progress_formula`：**口径本身也存进台账**。只存数字迟早会被算糊，
把「什么算完成」一起写下来，才能事后核对。

### 2. 进度单调不减是服务端强制的

模型每轮回复末尾要追加一个 ` ```state ` 围栏包裹的 JSON 补丁，服务端据此更新台账。
但**模型改不回退**：`complete` 字段采用只追加写法，重复提交同一批 id 会被去重，
提交空数组等于什么都没说。越界的章节 id 直接丢弃。

这条规则的实现位置在 `applyPatch()`，不在提示词里 —— 提示词是请求，代码才是保证。

### 3. 检索用 BM25，不用余弦相似度

这本书的片段长度相差上百倍（60 字到 5000 字）。余弦式地「除以片段长度」
会把内容最全的长片段压到接近零分，正好和我们要找的东西相反。
BM25 用饱和式长度归一化（`k1=1.2`、`b=0.75`），短片段占不到便宜、长片段不被埋没。

中文没有引分词库，用的是二元字组切分 + 一份虚词停用表。
停用表是必需的：二元切分不认词性，「为什」「什么」会被当成独立技术词，
而有些偶然组合在语料里恰好罕见，按 IDF 算下来权重竟高于真正的技术词。

### 4. 庆祝动效挂在「新增完成节」上，不挂在渲染上

`public/frontend-agent/app.js` 里有一个 `FX` 粒子引擎（canvas，单个合成层，不参与布局与命中测试）：

| 触发条件 | 动效 |
|---|---|
| 本轮新确认完成 1 节 | `FX.confetti()` —— 屏幕左右两支礼花棒朝内上方喷射彩纸 |
| 本轮完成最后一节 | `FX.fireworks()` —— 连续放约 6.5 秒烟花，并追加一条结业小结 |

触发点在 `send()` 里比较「本轮之前的完成集合」与「本轮之后的完成集合」，
**不在 `renderSidebar()` 里** —— 后者在启动、重置、每次刷新时都会跑，
挂上去会导致「一开页面就放礼花」。

`prefers-reduced-motion: reduce` 时脚本直接 return，CSS 里也把 `#fx` 关掉，
两道保险。动效只在真的发生了事情时出现，不是常驻背景装饰。

### 5. 应用标记：一个立方体，和它否掉的三版

标记文件是 `public/frontend-agent/logo.svg`，**侧栏品牌位和标签页图标共用这一个文件**。
以前图标是一段写死在 `index.html` 里的 data URI，两处各画一份，迟早有一天会对不上。

图形是一个等距立方体，也就是「包」—— 应用名字里的「打包」对应它；
课程里讲的代码分割（chunk）、产物（bundle），本质都是把碎块收成一个包。

它是被否掉三版之后才定下来的，理由留在文件里以免日后被改回去：

| 版本 | 图形 | 为什么不留 |
|---|---|---|
| v1 | 三个圆点向右汇聚成一个产物 | 34px 实际渲染出来是**「分享 / 导出」**。三个点向一个点扇出正是 share 图标的标准拓扑，而分享 ≠ 打包，语义完全错位 |
| v2 | 圆点换方块，并补一条依赖链 | 拓扑没变，仍然读成分享。而且横向排布在方形徽标里上下大量留白 |
| v3 | 改成纵向：模块在上、产物在下 | 离开了横向扇形，但三根汇聚线加底座读起来是**三叉戟或插头** |
| v4 | 等距立方体 | 「包」的语义直接成立，且不与任何常见 UI 图标撞形 |

两条实现细节：

- **内部两条棱用 `mask` 挖空，而不是描边**。描边在小尺寸下会变粗、糊成一团；
  挖空则宽度恒定，缩放时只变细不变胖。
- **背景渐变写死在 SVG 里，不交给 CSS 变量**。favicon 读不到 CSS，
  放变量里等于维护两份会漂的真相。

附带一个坑：这个文件的头部注释里**不能出现连续两个连字符**（XML 规范不允许，
解析器会提前闭合，文件直接变成非法 XML，图标位置变成裂图）。已经被这个坑绊过一次。

尺寸验证：`logo.svg` 在 64 / 48 / 34 / 24 / 16px 下逐一渲染检查过，
16px 时细节必然糊掉，但轮廓仍是「几块收进一块」，语义不丢。

## HTTP 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/health` | 存活探针：运行时长、知识库分块数、模型是否就绪 |
| GET | `/api/bootstrap` | 状态 + 对话历史 + 脱敏配置 + 知识片段数 |
| POST | `/api/config` | 保存模型配置。字段非法返回 400 与具体原因 |
| POST | `/api/config/test` | 真发一次请求验证连通性 |
| GET | `/api/knowledge/search?q=` | 检索知识库，返回命中片段与得分 |
| GET | `/api/nodes` | 179 个知识点及其前置依赖（给组课与排查用） |
| GET | `/api/plan?targets=&domains=&levels=&max=` | 按前置闭包生成一条有序学习路径 |
| POST | `/api/chat` | 一轮对话。上下文取自服务端落盘的历史，成功后把这一问一答追加进去 |
| POST | `/api/reset` | 重置学习状态与对话历史（会记一条 changelog） |

`/api/chat` 的返回里有两个字段专门用来排查「进度怎么没动」：

- `patchApplied` —— 补丁是否真的落地了
- `notes` —— 逐条说明发生了什么，例如 `忽略非法的节 id: M9.9`、
  `状态块存在但 JSON 解析失败，进度未变动`、
  `本轮回复未包含状态块，进度未变动`

## 工作流

两个文件，都是零依赖、没有 `npm ci` —— 这个项目真的不需要装任何东西。

**`.github/workflows/ci.yml`**（每次 push 与 PR）：语法检查 → 断言 `knowledge/` 在仓库里 →
断言语料生成物是最新的 → 起服务 → 打 `/api/health` 并断言 `knowledgeChunks` 非 0。

后两条是专门为「语料」加的，因为这两种坏法都**不会报错**：
缺语料时应用静默退化成空检索；改了 `knowledge/` 却忘了重新生成
`public/frontend-agent/knowledge.json` 时，两端会继续用旧资料作答。靠人看是看不出来的。

**`.github/workflows/pages.yml`**（push 到 main）：校验语料生成物 → 检查应用文件齐备、
`CNAME` 在位、站点根跳转目标正确、资源都是相对路径 → 发布到 GitHub Pages。
后两条是为「子路径部署」加的：跳转目标写错或出现绝对路径，都会得到一个能打开、
但进不去或没有样式的站点。

## 已知限制

- **检索质量受限于无分词器**。9 个典型查询里 8 个命中正确章节；
  「为什么 contenthash 会变」这类问句仍会被「为什么要设计」这类标题挤到前面。
  接 `nodejieba` 之类的分词器能根治，但那会引入依赖，与「零依赖」冲突 —— 目前选择接受。
  检索只是给模型的**参考**，提示词里已注明「不要整段照抄」。
- **对话历史有上限**。`MAX_HISTORY = 400` 条（约 200 轮），超出后丢弃最早的。
  这是为了不让上下文和文件无限膨胀；被丢掉的部分不会再出现在首屏。
- **对话历史只在本机**。它落在 `data/history.json`，不随浏览器走：换一台机器打开同一个服务看不到，
  清空 `data/` 也会没。这是「服务端持有状态」的直接后果。
- **`knowledge/` 是一份拷贝，不会自动跟随电子书仓库**。这是为可部署性付的代价：
  应用必须自包含，否则部署到服务器上就检索不到任何资料。电子书更新后需要手动同步这份拷贝。
- **单用户**。没有登录，`data/state.json` 就是唯一一份状态。多人用要各自部署。
- **静态形态下数据只在这台机器这个浏览器里**。进度、对话、API Key 全在 localStorage，
  换浏览器、换设备、清站点数据都会没。要跨设备就得上服务端形态。
- **静态形态依赖模型服务开放 CORS**。DeepSeek / OpenAI 等公开服务都开放；
  自建或内网服务通常不开放，那样浏览器直连会被拦下，只能改用服务端形态。
- **不校验模型输出的事实性**。提示词要求遇到版本号、性能倍数时标注「待核实」，
  但这是请求不是保证。

## 和 Skill 版本的关系

同一个教学法有两个交付形态，**知识底座相同但已解耦**：

| | Skill（`frontend-build-tutor`） | 本应用 |
|---|---|---|
| 运行环境 | 宿主智能体内部 | 独立进程，浏览器访问 |
| 状态载体 | 项目内 `状态台账.md` | `data/state.json` + `data/history.json` |
| 模型 | 宿主自带 | 自己配（OpenAI 兼容，或环境变量） |
| 检索 | 宿主自己读文件 | BM25，读项目内 `knowledge/` |
| 适合 | 已有智能体环境，想直接用 | 想发给别人、可部署到服务器 |

本应用把语料收进自己的 `knowledge/`，是为了能独立部署；两边不再共用同一份文件，
电子书更新后需要分别同步。

两者不共享状态。在一个里面推进的进度，不会出现在另一个里 —— 这是设计如此，
不是缺陷：状态外置的前提就是「状态归属明确」。
